## Objective
The theme choices already behave like native radios for keyboard users, and
this card locks that in: the theme group's roving `tabIndex`, its
`aria-checked`, and its arrow-key handler get unit and e2e coverage so a
regression shows up as a failing test rather than as a broken control. The
behaviour is shipped; the tests are the deliverable.

## Fixed decisions
The theme group is already correct and this card changes none of it. The
already-shipped behaviour these tests must pin:

- **Markup stays as it is.** `role="radiogroup"` (`:595`) over three
  `role="radio"` buttons with `aria-checked={value === option}` (`:600-601`),
  an `aria-label`/`title` per segment (`:602-603`), `is-selected` for the
  styling (`:605`) and `data-testid={`theme-${option}`}` (`:606`). They do
  **not** become `<input type="radio">` — C-SETTINGS@1's radio bullet is
  satisfied by `role="radio"` buttons, and `docs/v2/cards/P1.1.md` forbids the
  change for the Drafting model group for the same reason.
- **One tab stop, on the selection.** `tabIndex={value === option ? 0 : -1}`
  (`:604`), so Tab enters the group at the currently selected option and
  leaves the other two unreachable by Tab alone.
- **Arrow keys move and select within the group**, in the order `THEMES` gives
  (`shared/src/settings.ts:86`): `ArrowRight`/`ArrowDown` → next with wrap,
  `ArrowLeft`/`ArrowUp` → previous with wrap, `Home` → `system`, `End` →
  `dark` (`rovingTarget`, `:634-639`). Because the order is
  `system, light, dark`, **ArrowRight from Dark wraps to System**, not to
  Light — read the constant, do not assume "next" means Light. Every other key
  is left to the browser.
- **Selection is immediate, not deferred to Enter or Space.** The handler
  `preventDefault()`s and calls `onChoose(option)` (`:613-616`), which is
  `applyTheme(option)` then `save({ theme: option })` (`:483-486`) — the same
  path a click takes, so the control is optimistic and the painted
  `document.documentElement.dataset.theme` changes before the save settles.
  Focus follows the selection in a `requestAnimationFrame` (`:617-619`).
- **The selected option carries `aria-checked="true"`** and the roving
  `tabIndex` moves with it; the other two read `"false"` and `-1`.
- **The keyboard path's failure behaviour is C-SETTINGS@1's Rejection
  example**, already covered through a click by
  `web/src/routes/Settings.test.tsx:152-181`. This card does not re-cover it and
  does not change it.
- **No production change.** `Settings.tsx` is out of write scope entirely; if
  honouring an assertion seems to need an edit there, that is a stop, not a
  task.

## Steps
1. Add the unit cases to `web/src/routes/Settings.test.tsx`, one `describe`
   block for the theme group's keyboard behaviour, following the Drafting
   model case at `:184-221` for shape. Cover: the group starts with one tab
   stop on the selected option (`tabIndex` 0 there, -1 on the other two, and
   `aria-checked="true"` on the selected one) with the stored fixture theme
   `dark` (`:27`); `ArrowRight` from Dark → `theme-system` selected
   (the wrap) with `dataset.theme` painted `system`; `ArrowLeft` from Dark →
   `theme-light`; `Home` → `theme-system` and `End` → `theme-dark`; and that
   focus follows the selection (`document.activeElement` after the
   `requestAnimationFrame`). Run `npm run build:shared && npx vitest run
   web/src/routes/Settings.test.tsx` and record the result **as observed**.
2. Extend `e2e/tests/settings-appearance.spec.ts` with a keyboard case driving
   the real browser: set a known theme through the API first (as the existing
   test does at `:26`), focus the selected segment, press `ArrowLeft` and
   assert `aria-checked="true"` and `page.locator('html')`'s `data-theme` both
   followed, then `Home` and the same pair. **Every new `test()` is titled
   `settings appearance: …`** — that is what V2's `--grep` matches, and a
   hyphenated `settings-appearance` matches nothing.
3. Record what each run actually printed, including a first run that passes
   unchanged: this behaviour already exists, so a pass on the base commit is
   the expected outcome and is the evidence, not a missing failure. Leave the
   change uncommitted for the coordinator.

## Stop conditions
- A new test shows the shipped behaviour does **not** match Fixed decisions —
  a wrong `aria-checked`, a wrong wrap order, a `tabIndex` that does not
  follow the selection, or focus that does not move: report it as a finding
  for the coordinator and **do not** change `Settings.tsx` to make the test
  pass. Record the failing assertion, the observed value and the source line.
- The keyboard cases pass on the base commit: that is the expected result, not
  a missing failure. Record it and finish as a test-only change. Do **not**
  edit `Settings.tsx` to manufacture a failure, and do not remove or weaken
  any case already in `Settings.test.tsx` or the spec.
- V2 cannot launch a browser or the `--grep` filter matches no test: `BLOCKED`
  with the command, the exit code and the full output, not `FAIL` and not
  `PASS`.
- Honouring an assertion would require changing the theme group's markup,
  roles, testids or the owner-authorised AM-028 baseline
  (`Settings.tsx:572-586`): stop and report it as a finding; do not edit the
  file.
