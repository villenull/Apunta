## Objective

A name typed into the Add-patient window is still there — in the app, for her,
and in the e2e run — after the window has finished settling behind it.

S2.10 is APPROVED on its objective (**AM-100**,
`docs/v2/state/AMENDMENTS.md:123`) and its spell-check flake is *diagnosed*:
its own new diagnostic at `e2e/tests/spelling.spec.ts:92` fired in the reviewer's
V3 with `Received: ""` and a disabled Add-patient button, i.e. `name` was never
set (`docs/v2/state/reviews/S2.10-impl2.md:126-161`, `:245-256`). S2.10 may not
touch production code, so the fix is this card's, and it is a **product** fix:
on a cold `/patients/new`, Apunta makes itself unfocusable for as long as it
takes the single-primary-window lock to be granted, and then takes the caret
away from the field the dialog had just focused. Fixed decisions 1 and 2 name
the cause, the measurement that pins it, and the two lines that fix it.

The card's objective is the **property**, not the flake: whatever else happens
behind the window — the recency storm, the settings arriving, a focus handoff —
the name she typed stays in the field and stays in her hands. No e2e assertion
is changed to get there; `spelling.spec.ts` is the gate, not the subject.

**The word "remount" in this card's title is the owner's (AM-100) and it is a
disconfirmed hypothesis**, recorded in the Confidence field above rather than
quietly dropped: the fix is not a remount-proofing mechanism, because there is
no remount to survive (Fixed decision 5). The card id and title are not changed
here; if the owner wants the title to match the mechanism, that is §6's.

## Fixed decisions

1. **The cause, and the one measurement that separates it from the remount.**
   The diagnosis, in the order the evidence forced it:
   - **Not a remount.** `AddPatient` is a module-level component rendered by
     `<Route element={<AddPatient />} />` under a `<Suspense>` under one keyed
     `<div>`; the key is `location.pathname` (`App.tsx:99`), the only key above
     it, and the only `Suspense` and the only `<Navigate>` in `AppRoutes` are at
     `:103` and `:122`. `main.tsx:28` mounts a single `path: '*'` data route, so
     no navigation inside the app can re-create `AddPatient` in place. A pathname
     change is the only thing that moves that key, and it takes the
     `/patients/new` match — and therefore the whole dialog — **off the screen**,
     which the failing run contradicts: the locator resolved to
     `<input id="patient-name">` fourteen times across the full five-second
     timeout (`S2.10-impl2.md:136-143`). No provider re-creates its children
     (`SettingsProvider.tsx:142`, `i18n.tsx:90`, `SpellingProvider.tsx:117` — one
     `Provider` each, stable element types), no component in the subtree is
     defined inside another component's body (the class of bug
     `docs/v2/evidence/UI-BATCH2/handoff.md:40-42` records, fixed there and not
     present here), and `SpellLayer` renders its input at a fixed position
     (`SpellLayer.tsx:97-122`).
   - **The gate, which the code does show.** `blocked` is
     `primary.phase !== 'primary'` (`App.tsx:62`) and is written onto
     `#apunta-content` imperatively at `:80-88` — the subtree the whole app
     lives in, the Add-patient window included. The phase starts `'acquiring'`
     (`:194`) and only becomes `'primary'` inside the lock grant (`:361-372`),
     so **on every cold load the app is `inert` from its first commit until the
     grant lands**, and the blocker's own comment says `inert` is there for "a
     non-primary window" (`:74-79`) — a window still deciding is not one.
   - **The keystroke that never arrives.** The failing test's first interaction
     on that page is a `fill` (`spelling.spec.ts:86`), and Playwright's `fill`
     on a text input is `select()` + `focus()` followed by `Input.insertText`
     into the focused element, with `visible`/`enabled`/`editable` as its only
     actionability states (Read). On an element inside an `inert` subtree
     `focus()` is a no-op, so the text is delivered to whatever else holds
     focus and the call still reports success. The value in the field therefore
     stays `""`, the Add-patient button stays disabled because `name` never
     became `'Teh'` (`AddPatient.tsx:150`), and the assertion at `:92` reports
     exactly what the reviewer saw.
   - **Why it is state-dependent, which is the dirty-versus-fresh correlation
     S2.9 measured.** The grant is a promise resolution behind a busy main
     thread: a populated practice loads the patient list, then fires one
     `GET /api/patients/<id>/notes` per patient six at a time
     (`usePatientRecency.ts:24`, `:69`), each completing fetch re-rendering the
     workspace. The longer that storm runs, the longer the window in which the
     field is unfocusable — and the test's `fill` lands within a few
     milliseconds of `goto` returning. A fresh sandbox resolves the grant first;
     a used one often does not (1 of 5 in a used sandbox, 6 of 6 in a fresh one:
     `docs/v2/state/reviews/S2.9-impl.md:206-220`).
   - **And the second half of the same cause, which is the one a user feels.**
     `becomePrimary` computes `wasBlocked = phase !== 'primary'` (`App.tsx:248`),
     which is true on the *initial* grant as well as on a handoff, so the rAF at
     `:269-274` focuses `#apunta-content` on every cold load. Combined with the
     gate — the dialog's own `focus()` at mount was dropped, because it ran
     inside the inert window — the caret is **never** in the name field on a cold
     load, which is the clause `AddPatient.tsx:39-42` asserts and
     `App.test.tsx:816-819` argues nobody can hit.

   **A real user does lose typed text, and it is not the test's problem to work
   around.** She clicks the name field as the window unblocks and starts typing;
   if the rAF lands between her click and the rest of the word — and on a loaded
   practice that frame can be hundreds of milliseconds late, because the storm is
   holding the main thread — the caret moves to the page container and the rest
   of what she typed goes there, leaving the field with a silent prefix.

   **The measurement, and it is the card's own negative control (V3), not a
   flake to reproduce.** In the new test file, with a Web Locks shim whose
   `ifAvailable` grant the test holds until it releases it:
   - at the base commit, on a cold `renderApp('/patients/new')`, the content
     subtree is `inert` **while the phase is still `'acquiring'`** — the cause,
     asserted directly, with no dependence on a browser, a dictionary or a
     populated practice; and
   - at the base commit, once the grant is released, the caret is on
     `#apunta-content` rather than in the name field — the steal, and the thing
     a user feels.
   Both must **fail** at the base commit and pass on the fixed tree; that pair is
   what makes the diagnosis a measurement. Neither needs the e2e flake, and
   neither may be replaced by one.
   **If both pass at the base commit, the cause is not this and the card stops**
   (Stop condition 1). **If an amplified `spelling.spec.ts` run does fail after
   the fix**, read the trace once and record, at the moment the field reads
   `""`, the value of `document.getElementById('apunta-content').inert` and
   `document.activeElement === document.getElementById('patient-name')`; if the
   gate is closed and the field is focused there, the emptying is a genuine state
   reset and this is Stop condition 2.
2. **The fix is two lines of judgement in `App.tsx`, each narrowing the gate to
   what the gate is for.** The blocker stays exactly as it is; only the two
   reactions to the phase change.
   - **The gate: `inert` while the window is known to be blocked, not while it is
     still finding out.** A window in `'acquiring'` has not been found to be a
     second window, and the code that follows the grant already treats the two
     differently (`:251`). So the `inert` write must apply to `'secondary'` and
     `'unsupported'` — the states the comment at `:74-79` describes — and not to
     `'acquiring'`. **The existing test at `App.test.tsx:1515-1516` must keep
     passing unchanged**: with no Web Locks the phase is `'unsupported'` and
     `content.inert` is still `true`. The blocker keeps covering the screen
     meanwhile (`app.css:2520-2523`, `z-index: 100`) and keeps its own Tab trap
     and Escape handling (`:511-534`), so nothing behind it becomes reachable;
     what changes is that the app behind is no longer removed from the tab order
     and the accessibility tree during the one window in which it is about to be
     the app she is allowed to use.
   - **The caret: move it on a handoff, not on the first grant.** The rAF at
     `:269-274` stays, and it keeps firing for a **takeover** — a window that was
     `'secondary'` and has just been unblocked should land the keyboard back in
     the app, and that is the case it was written for. What must not happen is
     the same move on the `'acquiring'` → `'primary'` grant, where it yanks the
     caret out of a field the app itself focused. The discriminator is already in
     the file: `phase === 'secondary'` at `:251`, one line above. The fix is to
     use that one and not `wasBlocked`.
   - **What this buys, concretely:** on a cold `/patients/new` the name field is
     focusable from its first commit, `Dialog`'s `initialFocusRef` call lands,
     the caret stays where she put it through the grant, and a `fill` — or a
     keystroke, or a click followed by typing — reaches the field. Typed text now
     survives the gate, the handoff, and every re-render behind the window,
     because the value lives in `AddPatient`'s state and nothing in this card
     re-creates that component (decision 1).
   - **Rejected, with the reason.** *Deleting the rAF* — it is the keyboard
     landing for a takeover, and decision 3's third case exists to stop that.
     *Re-focusing the name from `AddPatient` when the window becomes primary* —
     that is a second focus call papering over a gate, which is precisely what
     `AddPatient.tsx:39-42` says it refused to do, and it leaves the field
     unfocusable for the fill. *Removing `<Workspace />` from `/patients/new` to
     quieten the storm* — that is the owner's design (2026-09-27), not this
     card's. *Widening the e2e spec's wait* — the spec does not change.
3. **The new test file is the proof; three cases, and one of them keeps the fix
   honest.** `web/src/App.primaryWindow.test.tsx`, all against the real `<App />`
   and the real `AddPatient`, through `installFakeApi`:
   - **(a) The gate, cold.** With a deferred grant, on a cold
     `/patients/new`, the content subtree is **not** `inert` while the phase is
     `'acquiring'`, and the blocker's takeover prompt is still on screen — so the

   - **(b) The caret, cold — the case that reproduces the user's loss.** Same

   - **(c) The handoff keeps its focus move.** The one case that fails if the

5. **No remount-proofing is invented, and the latent reset in `AddPatient.tsx:31`
   is a recorded finding.** `name` is state initialised once from `?name=`
   (`AddPatient.tsx:31`), so a remount *would* lose a typed name — there is just
   no remount (decision 1). The obvious hardening, keeping the name in
   `sessionStorage` or `localStorage`, is **refused here on privacy grounds**:
   `useDocumentTitle.ts:10-13` goes to some length to keep a patient name out of
