## Objective

The e2e line at **default workers** exits 0, N times in a row, so S2.R's
borrowed S2.8 V3 row passes as written.

Every failure recorded against that row is a race between specs over **stored
state**, not over product behaviour: the single `theme` row in
`GET/PUT /api/settings`, and the number of rows in `GET /api/formats`. The
suite runs `fullyParallel: true` (`e2e/playwright.config.ts:85`) against one
server and one data folder, so a spec that writes a global row and a spec that
reads it can be in flight at the same moment. S2.8's reviewer ran the literal
row four times and got **exit 1 on runs 1–3 and exit 0 on run 4**
(`S2.8-impl.md:68-74`), on a different failing spec pair each time; S2.8's
implementer got exit 1 on 3 of 3 with the change and 2 of 3 **at base
`f4c7696`** with the change reverted (`returns/S2.8.md:50-74`). The owner
accepted V3 on the serial run under **AM-086** and authorised this card in the
same amendment.

This card changes the tests' isolation and nothing else.

## Must not edit
- **Any production code.** Not `web/`, not `server/`, not `shared/`, not
  `src-tauri/`. There is no product defect here: the API is a correct
  single-global-row API and the tests are wrong about owning it. A change to
  `server/src/routes/settings.ts` or `server/src/db/settings.ts` would be a
  behaviour change this card has no authorisation for (Stop condition 5).
- `e2e/playwright.config.ts`, in particular **not** `:88`. Setting `workers: 1`
  unconditionally, or moving the CI-only spread to always apply, is the
  tempting one-line fix and it is exactly the thing this card exists to refuse:
  it trades a four-worker suite for a one-worker suite to hide a test-isolation
  bug, and it makes every future row slower while proving nothing. The pass
  condition in Verification is **default workers**.
- `e2e/support/no-english.ts`, and in particular **not** the
  `checkVisibility({ checkOpacity: true })` call at `:138`. Narrowing it, or
  dropping `checkOpacity`, is the tempting wrong fix for a flaky Spanish screen

  sanctioned answer to AM-076's staggered-entrance flake is to wait the screen

- No skip, no `test.fixme`, no `test.slow`, no `test.describe.configure({ mode:

- `docs/v2/evidence/P2.2/screenshots/*.png` — **never committed and never

## Fixed decisions
1. **The fix is isolation, and it is chosen per race.** Two shapes are
   sanctioned and both are the repo's own: **(a)** a per-test save/restore of
   the contested row, exactly as `brand.spec.ts:297-330` does it and as the
   `storedLanguage` auto-fixture at `support/fixtures.ts:42-55` does it for the
   stored language; and **(b)** `test.describe.configure({ mode: 'serial' })` on
   **only the describe block or test that writes the contested row**, never on a
   whole file that does not need it. Where one row is read and written by
   **different files** — the theme row is read by `settings-appearance.spec.ts`
   and written by both it and `workspace.spec.ts:553` — (a) and (b) alone are
   not enough, because Playwright's `serial` mode orders tests **within** a
   file or block and does not stop another worker entering the same row at the
   same moment. In that case the sanctioned addition is a **narrow lock around
   the appearance tests only**, in `support/fixtures.ts`, held for the duration
   of the test: every spec that writes or asserts the theme row takes it, and
   nothing else in the suite does. The suite keeps its default workers and its
   wall-clock. A lock the whole suite would have to take is not a lock, it is
   `workers: 1` with extra steps.
2. **The formats race is fixed by scoping the assertion, never by weakening
   it.** `formats.spec.ts:56`'s `expect(formats).toHaveLength(before + 1)`
   reads a **global** count and is therefore unanswerable while a sibling
   worker POSTs a format. The fix is to assert the same proposition about the
   rows this test can be responsible for — the count of formats named
   `Progress note` is exactly `before + 1`, and the created row is that one —
   which is **strictly stronger** than the global count, because it cannot be
   satisfied by an unrelated sibling's row. Deleting the count assertion, or
   replacing it with `toBeGreaterThanOrEqual`, is not the fix and is Stop
   condition 3.
3. **Nothing is skipped, retried or weakened to get the row green.**
   `retries` stays at its config value (`:87`, zero outside CI) and V3's pass
   condition is **five consecutive exit-0 runs at default workers**, not one
   green run with a retry behind it. In CI `retries: 2` would mask a race that
   this card exists to remove, so a CI-only green is not evidence and must not be
   quoted as one.
4. **The flake at `settings-appearance.spec.ts:63-64` is part of this card, and
   it is the same root cause.** Those two assertions re-read the theme after a
   reload, and the reload is a window in which a sibling's PUT lands — the same
   shared row as the recorded races, not a separate animation or timing defect.
   It is fixed by decisions 1 and 2 and is proved fixed by V1 and V3. If after
   those changes `:63-65` still flakes, that is a **new finding for the
   coordinator**, reported with the run it was seen in — and it is emphatically
   not a licence to touch `no-english.ts` or to inflate a timeout (Must not
   edit; NEXT-SESSION's residual on AM-076 says what a future flake there is
   and is not).
5. **`plan.spec.ts:58` is not touched speculatively.** The review saw it fail
   once and did not capture the assertion (`S2.8-impl.md:95-97`), and its `:21`
   citation is not a test — see Stop condition 4. Its setup does write shared
   state (`:69-76`), so it **must** take whatever isolation the other writers of
   those rows take, and that is the whole of its change. If it fails at V1 or V3
   for a reason its own code does not explain, stop and report; inventing a fix
   for an uncaptured failure is how a test becomes a false promise.
6. **The evidence of the fix is repetition, at default workers, on the whole
   suite.** V3 runs the RUN-CONFIG §3 e2e line five consecutive times, in one
   sandbox run, with nothing between the runs but the screenshot restore. The
   expected result is **exit 0 five times out of five**, with the suite's passed
   and skipped counts recorded from every run. The tripwire is the repetition:
   a card that reports one green run has not shown what it was asked to show,
   and the base fails this row on 2 of 3 and 3 of 4 runs respectively
   (`returns/S2.8.md:50-57`, `S2.8-impl.md:68-74`) — so a single run is
   indistinguishable from the flake it is meant to have fixed.
7. **The serial invocation is not the pass condition.** `npx playwright test
   --workers=1` from `e2e/` is how the green serial evidence in S2.8 was
   obtained, and `npm run e2e -- --workers=1` **silently drops the flag** (npm
   warns `Unknown cli config "--workers"` and runs default workers anyway —
   `S2.8-impl.md:76-80`, finding 2). Either form may be run **in addition** to
   V3 to narrow a failure down; neither may be reported as V3, and a report that
   only contains a serial run is `FAIL` on this card's row as written.
8. **The card is L1 and offline.** It edits test files only, changes no
   production code, needs no new build of its own, no model, no vendor and no
   acquisition. It does start servers, exactly as the L1 cards P2.2, P3.2, P4.1
   and S2.1 do, so the dispatch assigns a port from 7800 to 7889, every launch
   goes through `scripts/v2/sandbox.mjs` (C-ISO@1), and **7717 is never
   contacted**. `npm run e2e` builds the app and starts both servers itself, so
   the row needs one sandbox env for the English port and one more for the
   es-MX project, per `e2e/playwright.config.ts:32-36`. Playwright's browsers
   are **not** in `docs/v2/ACQUISITION.md`, so `npx playwright install` is not
   run; this box uses the config's own documented escape hatch,
   `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium` (`:57-61`), which is an
   addition to the row's command and not a substitution for it. Nothing is
   downloaded (HS-3).
9. **The May-edit list is this list and no wider.** A discoverable second race —
   a new spec writing the theme row, or a seventh spec asserting a global count
   — is a **finding to report**, not a licence to add that file here (§6
   reserves widening to the owner; AM-086 authorised this card's scope
   specifically). Report the path, the line, and what would need isolating, and
   stop if the fix cannot be made without opening it.

## Steps
1. Confirm the base and the tripwire **before** editing anything: run the
   RUN-CONFIG §3 e2e line three times at default workers in a sandbox env, with
   `PLAYWRIGHT_CHROMIUM_EXECUTABLE` exported, and record each run's exit code,
   failing spec files and line numbers, and passed/skipped counts. The
   expectation is that **at least one of the three fails** (base evidence: 3 of 4
   and 2 of 3). If all three pass, that is not a licence to do nothing — it is
   Stop condition 1, because the card would have no reproduction to fix and its
   green would be luck. Restore the P2.2 screenshots after each run.
2. Apply decision 1 to the theme row: the save/restore and/or the narrow lock in
   `support/fixtures.ts`, taken by every spec that writes or asserts it —
   `settings-appearance.spec.ts`, `workspace.spec.ts:548`, and `brand.spec.ts`.
   Add decision 2's scoped count to `formats.spec.ts:56`. Add decision 5's
   participation to `plan.spec.ts:58`. Change nothing else in those files: not
   the fixtures, not `checkScreen` calls, not the `NOTES`/`SOAP` constants, not
   the comments that explain what a test is for.
3. Run V1 — the amplified, targeted repetition over the racing files. This is
   cheap and it localises, so it goes before the whole suite.
4. Run V2 — the L1 gate and the changed-path check.
5. Run V3 **last and uninterrupted**: five consecutive default-worker runs of the
   RUN-CONFIG §3 e2e line in one sandbox, restoring the P2.2 screenshots between
   runs and not touching the tree between them. Write each run's command, exit
   code, start and end time and output excerpt into `docs/v2/evidence/S2.9/`
   with sandbox paths written `<sandbox>` and the home folder `~` (RUN-CONFIG
   §4), and record in the return file: the base runs from Step 1, the
   per-file change you made and why that shape, the five exit codes with their
   passed/skipped counts, and — if any run failed — the failing spec and line
   verbatim rather than a summary. Then V4. Leave everything uncommitted for the
   coordinator.

## Why this is a new card, and not an amendment

Recorded so the next reader does not repeat the detour.

- **Not an amendment to S2.8.** Its May edit is `shared/src/i18n/es-MX.ts` and
  `docs/v2/evidence/S2.8/responses.md` (`S2.8.md:19-23`); it cannot open an
  `e2e/tests/*.spec.ts` file, and it is `APPROVED`
  (`docs/v2/state/PROGRESS.json`), which is not a thing an amendment can act on.
- **Not a change to S2.8's V3 row.** AM-086 accepted V3 on the serial run and
  **changed no row text and no threshold**; rewriting an acceptance row is the
  owner's, per §6 and NEXT-SESSION's residual on V1's wording. This card leaves
  the row exactly as written and makes the tree pass it.
- **Not S2.9 folded into S2.R.** S2.R is the parent review and its V3 is S2.8's
  borrowed e2e row. Folding this work into the review would mean the review
  edits test files, which is a review's job nowhere in this plan, and it would
  put a fix and an acceptance in one attempt.
- So: a new card, **S2.9**, parent S2, depending on **S2.8**, and therefore
  picked up automatically by **S2.R** — a parent review's `Depends` is generated
  from its child list (`docs/v2/tools/plan-lib.mjs:parseMilestones`), so no
  hand-edited edge is needed, and `docs/v2/DEPENDENCIES.md` is regenerated by
  `node docs/v2/tools/check-plan.mjs` rather than edited. It is placed before
  S2.R for the reason AM-086 gives: S2.R borrows S2.8's V3, which would otherwise
  fail the same way.

## Stop conditions
1. **The three base runs all pass.** Stop and report, with the counts. There is
   no reproduction to fix, the card's premise cannot be shown on this box, and
   a change made on an unreproduced flake is a guess. The coordinator decides
   whether to run V3's five-run tripwire as the base instead — that is a
   coordinator call, not a silent substitution.
2. **The fix needs `workers: 1`, or anything in `e2e/playwright.config.ts`.**
   Stop and report. The pass condition is default workers; a config change hides
   the isolation bug instead of fixing it and makes every later row slower.
   (Must not edit, Fixed decision 2.)
3. **The formats count cannot be scoped without losing an assertion.** Stop and
   report the exact assertion and what it would take. Replacing
   `toHaveLength(before + 1)` with `toBeGreaterThan`, deleting it, or `test.skip`
   are all masking, not fixing (Fixed decision 2, 3).
4. **`plan.spec.ts` fails for a reason its own code does not explain, or you
   cannot tell which assertion failed.** Stop and report the run's output
   excerpt. Note first that the review's second citation is not a test:
   `plan.spec.ts:21` is the doc comment above `SPANISH_ATTESTATION` (`:20-24`),
   not a racing case, and the review itself did not capture the failing
   assertion (`S2.8-impl.md:95-97`). Fixing an uncaptured failure by reading
   around it is how a test stops being a promise.
5. **The fix looks like it needs production code** — a settings route that
   stops being global, a per-test database, a new API, a change to
   `server/src/db/settings.ts`'s merge. Stop and report why (HS-9). There is no
   product defect here.
6. **`docs/v2/evidence/P2.2/screenshots/` shows a diff after a run, or any May-edit
   path outside the six is needed.** For the screenshots, revert and continue —
   that is routine. For a seventh spec that writes the theme row or asserts a
   global count, stop and report the path and the line: AM-086 authorised this
   card's scope, and §6 reserves widening to the owner (Fixed decision 9).
7. **V1, V2, V3 or V4 fails in a file outside May edit** — including a prettier
