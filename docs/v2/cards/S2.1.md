## Objective
The data and settings foundations of C-LANG@1 exist, with no visible UI
change: setting, availability flag, locale table, `locale` columns, section
roles, job context and the server's active-job registry. Nothing a screen
shows moves: every existing note and format keeps its language, its text and
its section names exactly as they are (D11), and the English settings
response keeps the keys it has today plus the two C-LANG rule 1 adds.

## Fixed decisions
1. **Scope of the contract.** C-LANG@1 rules 1, 2, 3, 4 (types and the capture helper
   only), 5, 8 (data side) and 9. Rule 6 is S2.6's (`language_change_blocked`, the
   409, the disabled control) and rule 7 is S4b.1's; neither is touched here, and
   this card adds **no** 409 rule to `PUT /api/settings`.
2. **The error code.** `language_unavailable` is added to `ApiErrorCodeSchema`
   (`shared/src/errors.ts:4-17`) and the 400 that carries it is built in
   `server/src/http/errors.ts`. The body is the existing `ApiErrorSchema`
   (`{ error, message, details? }`) with an English `message` — S2.5 moves server
   text into the catalogues, and nothing here writes Spanish server text. The status
   is **400**: the contract fixes the code, not the status, and 400 is what the
   existing rejection path already answers. This card is the only card in S2 that
   widens the enum; S2.6's `language_change_blocked` is **not** added here, and
   needing it is a stop condition, not a quiet widening.
3. **The `spanishAvailable` seam.** The settings route reads
   `process.env['APUNTA_DEV_SPANISH'] === '1'` at request time, exactly as
   `server/src/routes/health.ts:104` reads `APUNTA_TEST_RUN_ID`. No `AppConfig`
   field, no `loadConfig` change, no harness change. A case that sets the variable
   sets it in `beforeEach` and restores the previous value in `afterEach` (deleting
   it when it was absent), so no later case in the file can inherit it.
4. **The settings response.** `GET /api/settings`, and the response of
   `PUT /api/settings`, are the stored rows plus these synthesised keys:
   - `language`: the stored `language` setting when the row exists, otherwise `'en'`.
     It is **synthesised**, so a client never has to tell "unset" from English (A3),
     and no row is written until she actually chooses Español.
   - `spanish_available`: `true` only when `APUNTA_DEV_SPANISH=1` (D12). It is never
     stored — the route strips it from a `PUT` patch before `putSettings`, and a case
     asserts the `settings` table holds no such key.
   - the two LLM-profile keys that ship today, unchanged.

   `PUT /api/settings` accepts `language: 'en' | 'es-MX'`: `en` always, `es-MX` only
   when `spanish_available` is true; any other value is the existing schema 400
   (`bad_request`).
5. **Rule 2's table, spelled out so it can be filled**, in
   `shared/src/i18n/locales.ts`:

   | App | UI and `Intl` | Whisper `-l` | Speech model | Dictionary | Prompts |
   | --- | --- | --- | --- | --- | --- |
   | `en` | unchanged from today | `en` | `ggml-tiny.en.bin` | `null` (no English dictionary ships today) | the current English set |
   | `es-MX` | `es-MX` | `es` | `null` until S4a.2 (C-STT@1) | `dictionary-es-mx@2.0.0` | the `es-MX` set (S5.4) |

   The speech-model cell is `string | null`. `null` means C-STT@1 has not selected a
   file yet: **S4a.2** writes `docs/v2/state/STT-SELECTION.json` and **P4.3** wires the
   selection into production code (S4a.2's May edit is production code: none), so
   this card names no candidate and downloads nothing (HS-3). A
   `NO QUALIFYING CANDIDATE` result leaves the cell `null`, which keeps Spanish
   dictation off and Spanish held (C-ES-GATE@1). The dictionary cell is S1.5's
   recommendation, `dictionary-es-mx@2.0.0` (`es-mx-spellcheck.md:27`, acquisition row
   A11); S6.1 is the card that uses it. The Prompts column names set ids only — no
   Spanish prompt text ships here.
6. **Rule 5's role vocabulary, in full: fourteen ids plus `custom`.** The seven the
   contract names (`location`, `presentation`, `risk`, `discussion`, `intervention`,
   `actions`, `next_session`), the SOAP roles (`subjective`, `objective`,
   `assessment`, `plan`) and the intake roles (`presenting_problem`, `history`,
   `formulation`, `plan`). The map is keyed by **name alone** — no format, no section
   index — normalised case- and accent-insensitively (NFD, combining marks stripped,
   lowercased). English `Plan` is the fourth section of both the SOAP fingerprint
   (`default-instructions.ts:629`) and the intake fingerprint (`:633`,
   `seed.ts:44`), so it is registered **once**, mapping to the single role `plan`; no
   `soap_plan` or `intake_plan` is invented. In Spanish the two are different strings
   anyway — SOAP `Plan` (`es-mx-clinical-documentation.md:173`) and intake
   `Plan terapéutico` (`:182`) — and both map to `plan`, so nothing is lost. A
   consumer that must tell SOAP `Plan` from intake `Plan` needs the **format**, not
   the role; S5.1 is the card that passes it in. Anything unrecognised is `custom`,
   and the map is read-only: a stored string is never rewritten.
7. **Rule 8, data side.** A format's `locale` is written and changed through
   `POST /api/formats` (default `'en'`) and `PATCH /api/formats/:id` — that is the
   user changing a format's locale. `POST /api/formats/standard` stays English here;
   **S5.1** is the card that makes it take a locale and creates the Spanish standard
   formats. The import half — "imported formats take the UI language at import time" —
   is **not** this card's scope: `server/src/routes/{import,halaxy,formats-detect}.ts`
   are in no May edit list anywhere in this plan, and adding them would be a quiet
   scope change. Until a card owns them an imported format takes the column default
   `'en'`, which is what D11 asks of existing content in any case. Record the owed
   sentence in the return file with those three paths, so the coordinator can
   schedule it.
8. **Rule 3, and the only legacy rule this card has.** A new note's `locale` is its
   format's `locale`, in all three creation paths — `POST /api/notes`
   (`routes/notes.ts:47-63`) and the drafts that end in `draft.ts:187-201` — because
   the format is what the note is written in, and the format's locale is the only
   locale a note can inherit today. That is the job's locale in rule 3's sense: S5.4
   later captures the whole job context in the same routes, and the locale it
   captures for a draft is the format's. No existing note or format is ever
   translated or relabelled. The three exhaustive `toEqual` assertions in
   `settings.test.ts:21-24,43-50,63-67` gain exactly the two synthesised keys and
   nothing else: an extended expectation, not a loosened one. HS-7 forbids weakening
   an assertion, and these three stay exhaustive over the whole response — every
   existing key, value and case survives byte for byte.
9. **Rule 4, types only.** `shared/src/job-context.ts` declares
   `{ locale, sttModel, llmModel, promptSet }` and the capture helper. No route
   consumes the object yet: S5.4 selects prompts from it, P4.3 the STT model.
10. **The registry, and this card's first users.** `server/src/jobs/registry.ts`
    exports `begin(kind, id)`, `end(id)` and `active()`; the kinds are `recording`,
    `transcription`, `draft`, `refine`, `plan`, `briefing`, `brainstorm`, `import`,
    `restore`, `backup`, `save`. Only `draft` and `refine` are wired here, in
    `draft.ts` and `chat.ts`, and `end(id)` runs in a `finally`, so a failed or
    abandoned stream leaves nothing active. Because `draft.ts` is the shared drafting
    path, the transcribe route's drafting half registers a `draft` job too — that is
    the same code, not a second choice. The other kinds are adopted in later cards;
    S2.6 reads `active()` for its 409. New cases for this leg are titled with
    `active job registry`, so a reviewer can find them in the runner's output.
11. **Migration 008 and the one hard-coded level.** `server/migrations/008_locale.sql`
    adds `locale TEXT NOT NULL DEFAULT 'en'` to `notes` and `note_formats` (both
    created in `001_init.sql:19-46`), so every existing row becomes `'en'` and no
    other column moves. The interaction with `server/src/db/migrate.test.ts:107` is
    the point: that line asserts `migrations.level` is `7`, so adding 008 makes V5
    red on an assertion that contradicts the shipped schema. The line is in May edit
    and is updated to the shipped level (`8`) as part of this card — **not** a
    loosened test under HS-7, but a hard-coded number this card's own migration made
    stale, and the expectation stays exactly as strict. It is the pattern for every
    later v2 migration: that is the only hard-coded level in the tree (`grep` for
    `migrations.level` across `shared/`, `web/` and `e2e/` finds only
    `toBeGreaterThanOrEqual(1)` and fixture values). Any *other* red assertion in a
    file this card does not own is a `BLOCKED` return with the failing output, not a
    fix.
12. **Backups.** `dump.ts:50-55` already selects `*`, so `locale` travels by itself,
    and the level checks in `archive.ts` and `restore.ts` are derived. The rule-9
    evidence is a round trip in `server/src/backup/*.test.ts`: a backup taken with a
    Spanish format and note restores both `locale` values exactly.
13. **The cardinality of every `locale` field, and the call sites it fixes.** The
    column is `NOT NULL` (Fixed decision 11), so "required" would be the natural
    reading — and a required field at the wrong level breaks `tsc` in files this
    card does not own, two of them in Must not edit. So each level is fixed here
    and the compiler gets no vote:
    - **Output shapes are required.** `NoteFormatSchema.locale` and
      `NoteSchema.locale` are `locale: LocaleSchema`, **not** `.optional()`: a row
      can never be null, so a `locale?:` on an API shape would be a lie every
      consumer would have to re-check, and the reviewer of the note would reject
      it. This is the one level where required costs an edit, and every file it
      costs is licensed: `web/src/test/fakeApi.ts` (`:83-97` `makeFormat`,
      `:129-141` `makeNote`, `:729` the `PATCH /api/formats/:id` literal) and
      `server/src/ai/prior-notes.test.ts:15-30` (the synthetic `Note` helper) for
      fixtures, plus `server/src/db/{notes,formats}.ts`, already in May edit — four
      files, three literals and one helper between them, nothing else in any of
      them. `web/package.json:10` runs `tsc -p tsconfig.json` over `web/**` from
      the root `typecheck` (`package.json:25`), which is why a fixture there is a
      real `tsc` error and not a test-only inconvenience. A **fifth** such file is
      the stop condition below, not a licence.
    - **Repository inputs are optional, defaulting to `'en'`.**
      `CreateNoteInput.locale` and `CreateFormatInput.locale` are `locale?: string`,
      and `createNote`/`createFormat` fall back to `'en'` when it is absent.
      Optional here is the correct value, not a dodge around the compiler: every
      caller that exists today writes legacy content that rule 3 and D11 leave
      English — `server/src/seed.ts:194,211`, `server/src/routes/import.ts:89`,
      `server/src/routes/halaxy.ts:81`, `server/src/db/notes.test.ts:29-31`,
      `server/src/db/repositories.test.ts:32-34,96,135,142,169`,
      `server/src/seed.test.ts:103`, `server/src/backup/readable-export.test.ts:32,35,42,72,74`
      — and two of those source files are in Must not edit, so a required field
      would demand a `BLOCKED` return for a value that is always `'en'`. The
      fallback is also what Fixed decision 7 already says an imported format gets.
    - **Request bodies are optional.** `CreateNoteFormatRequestSchema.locale` is
      optional with default `'en'` (Fixed decision 7), so
      `web/src/routes/OnboardingPreview.tsx:105` and
      `web/src/api/client.test.ts:151` compile untouched and a client that names no
      locale gets English. `UpdateNoteFormatRequestSchema.locale` is optional for
      the same reason — a `PATCH` is a partial by definition, and the
      `note-format.ts:73-75` refine still only requires a non-empty body.
      `UpdateFormatInput.locale` is optional on the same grounds.
    - **`CreateNoteRequestSchema` still gains nothing** (May edit): rule 3 gives a
      note its language server-side, so no client chooses one. That is a request,
      not an output — a note's `locale` still leaves the server **required**, as
      above.
