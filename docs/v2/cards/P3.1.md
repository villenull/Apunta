### AM-058: self-contained version metadata (owner-approved)

The bundle carries no application `package.json`. The packaging script reads
`server/package.json` as the version source and injects its JSON-encoded string
with esbuild `--define:__APUNTA_VERSION__`. Both application version readers
use that constant when defined and retain their existing relative
`createRequire` reads as lazy source-execution fallbacks otherwise. Preserve
source/tsx/dist/Node type-stripping execution and the existing English version
semantics. Do not use blind source replacement or place metadata outside the
bundle. **Verify that these two runtime version reads no longer carry their package
metadata into the bundle, by a fingerprint that can actually fail** (independent review D1: the value assertion
alone cannot discriminate, because `server/package.json`'s version is `0.0.0` and
both readers fall back to that same literal, and because an esbuild that inlines
the read as an object literal travels with the bundle and takes the path strings
with it, so a path grep passes while the metadata still ships). So the check is:

- **Source shape, required.** The define guard must be
  `typeof __APUNTA_VERSION__ === 'string'`, never a bare reference — `declare
  const` is erased by type stripping, and a bare reference throws
  `ReferenceError` in exactly the raw type-stripped case named above.
- **What the greps do and do not prove, stated exactly.** They prove the
  package metadata is **not inlined** into the bundle, which is the failure the
  card cares about: an inlined read travels with the bundle, and a relocated
  read is what produced the original defect. They do **not** prove the word
  "eliminated" in the strongest sense — `config.ts`'s `createRequire` is a local
  binding, so esbuild leaves `require('../package.json')` unresolved and the JSON
  is never inlined even though the read is still textually present. That
  survivor is unobservable in every row here, because the required `typeof`
  guard makes the defined path the only one that can execute. Stating it
  plainly is better than letting the row's name imply more than it checks.
- **Bundle shape, required, and now falsifiable.** Two greps over
  `build/linux-resources/server/server.mjs`, each of which must be `0`:
  - `grep -c '__APUNTA_VERSION__'` — esbuild substitutes the define, so any
    surviving occurrence means the define was not applied on that path. No
    dependency uses this name, so the count is attributable.
  - `grep -c '@apunta/server'` — the `name` field of the `package.json` both
    readers resolve, which esbuild drags in whole whenever it inlines that file.
    Both
    readers require **relative** paths, so a self-resolving name is exactly the
    failure; the string appears in zero files under `server/src` or `shared/src`
    today.
  A non-zero count on either is `FAIL`. These two are the whole check;
  unrelated dependency metadata strings are not a failure.

  **Correction, and the reason this text exists at all:** the first attempt at
  this fingerprint counted `createRequire`, on the reasoning that it occurs in
  exactly two hand-written files. That is true of the repository and false of
  the **bundle**, which inlines `node_modules`: `fflate`'s Node ESM entry calls
  `createRequire` at module scope, is unconditionally live, and is reached from
  the server's own entry. The count could never be `0`, so the check could never
  pass and would have blocked a correct implementation. A fingerprint has to be
  checked against the artefact it will be run on, not against the source tree it
  came from.

The packaging test must assert both health's `version` and the sandbox lock's
`appVersion` equal the version read from `server/package.json`, including after
relocation. Run associated source regression tests plus lint/typecheck on the
stable implementation tree. Keep the original missing-SQLite failure assertions.
Stop only the first owned PID and establish the port is free before launching
the broken copy; preserve C-ISO ownership verification for that launch too.
**The rule-5 ownership proof, resolved (independent review D2).** The
boot-error app hard-codes its health response and cannot carry `testRunId`
without an edit outside May edit, and `boot-error.ts` is not editable — so the
poll-based proof is unavailable for the broken-copy launch. **No waiver is
needed, because a stronger proof exists and it is the one C-OWN@1 already uses:**
prove ownership from the data-folder lock file the process itself writes.
Assert, while the process is **alive** (a clean release unlinks it, so a
post-mortem read is not a proof of anything):

1. `acquireDataFolderLock` precedes `openDatabase`, which precedes serving the
   boot error, so by the time `/api/health` answers the lock is already written
   by that process — there is no race to lose.
2. On `$APUNTA_DATA_DIR/apunta.lock`: `pid` equals the spawned pid;
   `processStart` equals field 22 of `/proc/<pid>/stat` for that same live pid
   (what the production helper computes); that pid is alive; and the port was
   bound-and-released free immediately before launch.
3. The folder is the wrapper's own `0700` run directory, so no foreign process
   can have written our pid's kernel start time into it.

This catches every failure mode rule 5 exists for — a pre-existing dummy on the
port, a lost race, pid reuse, a stale lock, a healthy server left running —
because it compares a kernel identity rather than an environment echo, and a
stale lock needs no instruction: taking over replaces a dead owner's file and a
clean exit unlinks it. **The missing-SQLite assertions are kept and this proof is
added to them**; the `appVersion` assertion reads from the same live lock file.

**One residual, named rather than papered over (independent review).** The lock
proves that *our process* owns the data folder. It does not, by itself, prove
that the process answering HTTP is that same process: a third party that bound
the port in the window between our free-port check and our `listen` would satisfy
every lock assertion. So the card requires one further assertion at the moment
the server answers: **the listening socket on the test port must be owned by the
spawned pid** (read the socket's owning pid from `/proc/net/tcp` matched against
`/proc/<pid>/fd`, or `ss -ltnp` under the bundled environment). With that, the
proof covers both halves — the responder is our process, and our process holds
the lock. Without it, do not claim the proof is equivalent to `testRunId`.
Mac build-time version alignment is carried to P6.1, not edited by this card.

## Steps
1. Write the test first, and run it through `sandbox.mjs` in **`env` mode**,
   never `run` mode. `run` spawns `join(repoRoot, 'server', 'dist', 'index.js')`
   with `process.execPath` and `cwd: repoRoot` (`sandbox.mjs:50,258-268`) and
   refuses outright when that entry is missing, so it would start the **repo's**
   server under whatever Node ran the wrapper — never the bundled one — and the
   run would pass without proving the objective. The test therefore:
   `<folder>/node/bin/node <abs-repo>/scripts/v2/sandbox.mjs env --port <p>`
   (the wrapper is a Node script in the checkout, so it is named by absolute
   path and run with the bundled Node rather than found on `PATH`; `<p>` is
   `--port` from the dispatch), then source the seven `export` lines it prints;
   copy the whole output to `/tmp/apunta-v2/${APUNTA_TEST_RUN_ID}/bundle/`;
   `cd /`; and start `<folder>/node/bin/node <folder>/server/server.mjs` itself,
   with the launch contract above plus the wrapper's `APUNTA_DATA_DIR` and
   `APUNTA_PORT`, and a `PATH` holding no host Node at all (`/usr/bin:/bin` —
   the box's default `node` is a mise shim, v26.8.2).
2. **The rule-5 ownership check is the test's own here**, because `env` mode
   only creates the run folder and prints the exports (`sandbox.mjs:353-361`) —
   it performs no poll. Before any assertion the test polls `/api/health` for up
   to 30 s and proceeds only when `testRunId` equals `$APUNTA_TEST_RUN_ID`;
   silence, a missing id or a foreign id fails the run. On exit, including on
   failure, it stops only the PID it started (never `pkill`, C-ISO@1 rule 7) and
   asserts that nothing is still listening on `<p>`.
3. The checks, each printing `PASS <name>` or `FAIL <name>: <detail>`, the
   script exiting non-zero on the first failure:
   - **health** — `GET /api/health` is 200, `ok` is `true`, and `testRunId` is
     this run's.
   - **migration on a fresh database** — `db.path` from that response is under
     `$APUNTA_DATA_DIR`, and `db.migrationLevel` equals the highest version
     among the `.sql` files in the bundled `migrations/` (all of them applied
     on an empty database).
   - **note creation needs a patient and a format first**: `POST
     /api/patients`; `POST /api/formats` with the route's own required body
     (a fresh database has **zero** formats,
     so `GET /api/formats` returns an empty list and the note call cannot be
     made otherwise); then `POST /api/notes` with that `format_id` →
     `GET /api/notes/<id>` returns the same id. On a fresh data dir `POST
     /api/notes` alone is `404 not_found` (`notes.ts:47-53` calls
     `requirePatient`, which throws `notFound('Patient not found')` →
     `server/src/http/errors.ts:85-87`; there is no `patient_not_found` code).
   - **the shipped SPA** — `GET /` is 200 with `content-type: text/html` and a
     non-empty body, read from the bundled `web/dist` through
     `APUNTA_WEB_DIST`; an empty or truncated copy of `web/dist` must fail here
     rather than in a person's browser.
   - **the whisper binary** — `<folder>/bin/whisper-cli --help` exits 0, so the
     copied shared libraries resolve next to it.
   - **the failure case** — in the copied folder, rename
     `native/better_sqlite3.node` and start the bundled server again:
     `server/src/index.ts:27-80` catches the `openDatabase` failure, serves the
     boot-error page and **keeps the port bound**, so the process does **not**
     exit. The test asserts the boot-error behaviour instead — `GET /` is the
     boot-error page and `/api/health` answers `503` with `storage_error` — and
     then kills the process it started. A server that starts normally and answers
     health `200` is `FAIL`; the test's own exit code stays 0 because the broken
     copy really did fail to open the database.
4. Implement until it passes.
