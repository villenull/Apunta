## Objective

The eval measures Spanish and English, on both the provider path and the
persisted pipeline path, and proves it can see every critical error. It does
that by making three things real: a **locale-scored** Spanish path whose
negation, number, unit and medication vocabulary is authored once, at authoring
time, and reached as **vocabulary** through the sidecars of the controls; a
**control suite** — twenty controls, one per C-EVAL@1 §4 critical class per
locale plus a clean, an empty and a degenerate one — that proves the scorer sees
those classes without borrowing the production guards; and a **pipeline runner**
that posts each fixture through the server's draft route and scores the note
**read back from the API after persistence**. The eight pipeline reports are then
measured against `docs/v2/BASELINE.md` §5's recorded ranges by the numeric rule in
FD10, and anything outside them is a `FAIL` routed to the owner.

The Objective above reflects the adopted amendment: it is the amendment's
Objective plus what the amendment decides. It adopts no threshold, no gate, no
contract change and no scorer behaviour beyond what that amendment itself states
(`AM-113`).

## Fixed decisions

**FD1 — New flags, and what "unchanged" means.**
`--locale en|es-MX` (default `en`), `--mode provider|pipeline` (default
`provider`), `--blind-lexicon <negation|clinical|number|unit|medication|all>`
(default: none), `--controls <dir|none>` (default
`server/src/eval/fixtures-controls/<locale>`, relative to the repository root
resolved the way `--corpus` is, `cli.ts:237-240`; `none` loads no controls and
suppresses the controls table). An unrecognised
`--controls` value, or one that is not a directory containing
`expectations.json`, is exit 2 with a named reason, matching FD1's flag
discipline.
`--blind-lexicon` is a **test-only negative control**: for the run it substitutes
the FD2b never-matching form at every `{{lexicon}}` token of the named lexicon and
changes nothing else — **the lexicon file is read exactly as authored and is never
emptied, in memory or on disk** (B-3). It is not a scoring option, not a
threshold, and not something any acceptance run passes.
Provider mode with no new flag behaves exactly as it does at the base commit:
same prompts, same corpus handling, and **the same corpus block of the report**.
The report additionally carries the controls table FD6 specifies, and
`--controls none` suppresses it; `--controls` defaults to
`server/src/eval/fixtures-controls/<locale>`, so the default `npm run eval
-- --fake` self-check loads the `en` controls, which FD6 states as deliberate.
A test asserts that `runEval({models, runs, fake}, no locale)` and the same call
with `locale: 'en'` produce identical reports.

**FD2 — Where the Spanish lexicons come from, and how they load.**
**Source of the Spanish terms.** The number, unit and medication lexicons are
built **once, at authoring time**, into `server/src/eval/lexicons/es-MX.txt` from
`docs/research/es-mx-clinical-glossary.json`, filtered to
`category ∈ {number, unit, medication}` — 51 + 8 + 93 = **152** entries, verified
present. Every one of the 152 is admitted: each `es_mx` value is split into
**atomic alternatives** on `/`, on `(`/`)` and on the ellipsis (` … ` or `...`),
each piece is trimmed, and **no entry and no piece is dropped for being more than
one word.** That is the point — measured on the glossary, **87** of the 152 are
single tokens and **65** are multi-word surface forms (`mg (miligramo)`,
`mcg / µg (microgramo)`, `ácido valproico`, `"uno / una"`, `"seis y medio"`,
`veintiuno ... veintinueve`) and a single-token-only rule would silently discard
a third of F3's and F4's vocabulary while leaving the loader looking complete. The
alternatives of `"mcg / µg (microgramo)"` are `mcg`, `µg`, `microgramo`; the
alternatives of `"uno / una"` are `uno`, `una`; `"seis y medio"`, and `veintiuno`
and `veintinueve` separately, are whole phrases matched as such. The file's header
records, per line, the glossary entry it came from and the totals **152 = 87 + 65**,
so a reviewer can check the provenance without the glossary, and a test asserts
that **every one of the 152 entries is present in `es-MX.txt` as at least one
alternative** — an absent entry fails the test rather than quietly shrinking the
lexicon. **Nothing is read from production guard code** — not `server/src/ai/fact-guard.ts`,
`retractions.ts`, `refine-guard.ts` or any other guard module — and at scoring
time or authoring time **nothing is read from the glossary**; no new entry is
added to that file. The negation entries are authored separately, per
§B-negation below, and are the only entries with no glossary source.
Negation: the rule in §B-negation below. It is the one lexicon with no entry in
the glossary (verified: 399 entries, categories `medication` 93, `presentation`
92, `intervention` 65, `number` 51, `risk` 45, `pattern-marker` 31,
`frequency-time` 14, `unit` 8, and no `negation` category), and inventing one is
a stop, not a decision (see Stop conditions).

**FD2b — The negation lexicon is a scoring input, reached through the sidecar's
`{{lexicon}}` token.** This paragraph is the whole of N-1's answer, and it is
normative: the host, the token, the exact JSON, the validation, the ordering and
the legacy path are all named, so the pattern `scoreNote` finally compiles is
derivable from this document alone.

- **Host — one key, on the controls sidecar, at the top level, and only on an
  `es-MX` sidecar.** The key is
  `lexicon`, its value is a lexicon name (`"negation"` is the only one this card
  authors), and it sits beside `control`, `controlSource`, `controlNote`,
  `expect` and `mechanism` — **not** inside `mustNotContain`, **not** inside a
  `mustCapture` fact, and not on `CaptureFact`. So `mustNotContain` keeps
  `readonly string[]` (`corpus.ts:51`), `CaptureFact` keeps `{ id, any, tags? }`
  (`corpus.ts:29-33`), and the only type that gains a field is the new control
  type, which gains exactly one optional key. The review's suggested
  per-entry field is **not** adopted: a field on a string list still has to say
  *where* in the pattern the vocabulary goes, and here the fixed token does that
  without touching a shared type. **Locale scope is part of the host (B-2):** only
  the `es-MX` `positive/01-negacion-perdida.txt` and
  `positive/02-negacion-inventada.txt` sidecars carry the key. The `en`
  lost-negation and invented-negation controls carry **neither** the key nor any
  `{{lexicon}}` token and are matched by authored English phrases, because
  `negation` is an es-MX lexicon and validation rule (2) below makes a lexicon the
  run's locale does not have a load-time `CorpusError` — a key on an `en` sidecar
  would kill the default `--locale en` self-check at load.
- **Token — the literal 11 characters `{{lexicon}}`.** The token is **fixed and
  does not carry the lexicon's name**; the sidecar's `lexicon` key says which
  lexicon it means. `{{negation}}` is **not** a token: two spellings of the same
  idea would let a sidecar name a vocabulary its own `lexicon` key contradicts.
- **Placement — the token goes in the negator's slot, and only there (B-1).** The
  expansion **replaces** the negator the authored phrase already carries; it is
  never prefixed to a phrase that already has one. **The corollary, stated because
  V1 depends on it: a phrase with no negator slot of its own is EXCLUDED from the
  lexicon-driven invented-negation control's `mustNotContain` rather than entered
  without a token.** `"niega(?:ndo)?"` and `"jam[aá]s"` are exactly that shape — the
  word *is* the negator — so they belong to the sidecar-shaped controls that carry
  no `{{lexicon}}` key and are matched by their own authored phrase. A future
  author who adds one of them to a `lexicon`-keyed control's `mustNotContain` does
  not weaken a check; they make **V1 fail**, which is the intended alarm. `"{{lexicon}} no refiere"`
  would compile to `(?:no|nunca|jamás|…) no refiere` — two adjacent negators —
  and would fire on nothing at all. A phrase whose negator is not a lexicon term
  (`sigue sin dormir(?: bien)?`, whose `sin` is excluded per S4a.2's own reason)
  carries its own authored negator and **no** token, which is also why
  `mustNotContain` never receives a bare negator: a bare negator term matches
  every faithful Spanish note, and these corpora exist to keep those negations.
- **Expansion — exactly one non-capturing group.** The token expands to
  `(?:ALT₀|ALT₁|…|ALTₙ)` — one group, so it is safe to drop into the middle of a
  larger pattern without changing the enclosing alternation's precedence — where
  each `ALTᵢ` is one lexicon term or multi-word cue, `escapeRegExp`'d
  (`lexicon.ts:65-67`) and wrapped in FD2c's boundary assertion. A multi-word cue
  keeps its internal spaces and is matched as a whole phrase.
- **Order — substitution happens in the loader, before `compile()`, and never in
  `score.ts`.** The controls loader reads the lexicon, substitutes, and only then
  hands a **complete `Fixture`** (FD6) to the **unchanged** `scoreNote`. Nothing
  downstream can tell a substituted pattern from an authored one, which is the
  point: `score.ts`, `patterns.ts` and `compile()` are not edited, and
  `assertFixture`'s existing compile checks (`corpus.ts:142-170`) therefore
  validate the substituted strings exactly as they validate authored ones.
- **Blinding is a substitution, it happens at the token, and it substitutes
  *nothing matching* (B-3, M-1).** Under `--blind-lexicon negation` the token
  expands to `(?!)`, not to `(?:)`, and **the lexicon file is read and validated
  exactly as authored** — this is a substitution, not an emptying, and the loader
  never loads zero terms for a blinded run. The reason for `(?!)` over `(?:)` is
  measured against this card's own shapes: an empty group drops the **negator
  requirement** and keeps the rest of the phrase, so `(?:) refiere` matches a text
  that contains no negator at all — the affirmative restatement — and a blind run
  would **manufacture** gating rather than remove it. `(?:) no refiere`, the
  doubled-negator shape B-1 removes, does not do that; which is exactly why the
  placement rule above and `(?!)` are one decision and not two. (An empty group also
  matches the empty string, so for any pattern whose remainder is optional it would
  additionally fire on every note; `(?!)` is a lookahead that can never be
  satisfied, so a blinded entry matches nothing under either shape.) This is what
  makes FD8 and V3's cell exact rather than a description of a hope.
- **Validation — four `CorpusError`s at load, each naming the control's key.**
  (1) a `{{lexicon}}` token with no `lexicon` key beside it; (2) a `lexicon`
  value the run's locale does not have — `negation` under `--locale en` is this
  error, because FD2c's lexicons are locale-scoped; (3) a `lexicon` key, or a
  `{{lexicon}}` token, on a **corpus** sidecar — corpus sidecars are
  Must-not-edit and corpus scoring stays exactly as it is today, so this is an
  error rather than a feature; (4) a named lexicon that loads **zero** terms
  **as authored on disk**, which is the half-empty-lexicon failure FD2c names,
  reported here rather than producing a pattern that quietly matches nothing.
  Rule (4) is evaluated **once, at load, before any blinding is applied** (B-3),
  so a `--blind-lexicon negation` run — which substitutes `(?!)` at the token and
  never loads zero terms — cannot trip it, and V3 reaches its reserved exit 3
  instead of a usage exit 2. A `{{` that is not exactly
  `{{lexicon}}` is left alone and must still compile, so `assertFixture` keeps
  the last word.
- **The legacy path is untouched, and that is a testable statement.** A sidecar
  with **no** `lexicon` key and **no** `{{lexicon}}` token is compiled exactly as
  at the base commit: no rewrite, no normalisation, no boundary change, no new
  key in the `Fixture`, and `lexicon.ts:39`'s `\b` construction for the English
  clinical file stays byte-identical. All four `expectations.json` files — the
  two English and the two Spanish tuning — carry no `lexicon` key and no `{{` at
  all (measured: zero occurrences in each), so neither the S3.1 gold nor the
  English corpora can reach this mechanism even by accident, and the `en` controls
  sidecar is required by the same rule (B-2): no key, no token, the legacy path.

The lexicon supplies **vocabulary only**, never a direction and never a detector.
Which way the error runs is stated per control by the sidecar's own keys, and the
two run in opposite directions, exactly as in the S3.1 gold:

- **invented negation** — a negator in the note that the source does not support
  — is `mustNotContain`. The `{{lexicon}}` token sits in those `mustNotContain`
  strings **in the negator's own slot**, so the sidecar authors
  `"{{lexicon}} refiere"`, `"{{lexicon}} reporta"`, `"{{lexicon}} ha tomado"`
  and the rest of its own list — **every one of them token-bearing, because V1 asserts
  that every `mustNotContain` entry of this control carries the token** — and the
  expansion
  supplies the negator vocabulary **as** the negator. The token replaces the
  negator the phrase already carries and is never prefixed to a phrase that
  already has one (B-1); an entry whose whole phrase *is* a lexicon term keeps its
  own authored negator and no token, which is the only way `jam[aá]s`-shaped
  coverage can exist without a bare negator in `mustNotContain`.
- **lost negation** — a negator in the source that the note dropped — is **not**
  detectable from negator vocabulary at all: the negator is what is missing. It is
  `mustNotContain` over the *affirmative restatement* the note wrongly asserts
  (sidecar-authored, **no** token), plus a `mustCapture` fact whose `any`
  patterns are the negated form, quoted from the gold's own alternatives with the
  token in each one's negator slot, and which **does** carry the token — so the one
  `lexicon` key on the sidecar covers the whole control, and the class's
  vocabulary reaches it through the `mustCapture` side.

A loader running these two entries substitutes, before anything is compiled:

```
"{{lexicon}} refiere"                ->  "(?:ALT₀|ALT₁|…|ALTₙ) refiere"
"sueno-no-restaurado"/any[0]         ->  "(?:ALT₀|ALT₁|…|ALTₙ) ha vuelto a dormir(?: bien)?"
"sigue sin dormir(?: bien)?"         ->  unchanged  (its negator `sin` is not a lexicon term)
"ya no (?:se )?despierta …"          ->  unchanged  (no token)
```

which is the exact string `assertFixture` compiles and `score.ts:303-310` /
`:342-344` then test. The alternation's own members are visible in
`server/src/eval/lexicons/es-MX.txt`; a reviewer can print them without running
anything. Note what each row does **not** say: `(?:ALT₀|…) no refiere` never
appears, because a doubled negator matches nothing, and a row like
`(?:ALT₀|…) jam[aá]s` never appears either, because `jamás` is itself one of the
alternatives and `jam[aá]s` on its own would be a bare negator in
`mustNotContain`. Both are the two shapes B-1 removes.

`mustNotContain` never receives a bare negator term. A negator on its own matches
every faithful Spanish note, and the corpus exists to keep those negations.

The consumer is therefore **phrase-level and sidecar-referenced**: one entry may be
a single closed-class word (`nunca`) or a multi-word cue quoted from the approved
gold (`no refiere`, `dejó de`, `sigue sin dormir(?: bien)?`), and a multi-word cue
is compiled and matched as a whole phrase, never reduced to single tokens and
never matched as a substring. This is what "a lexicon" means here: **vocabulary,
consumed per control through the sidecar's token, never a general lost-negation
detector and never a threshold.** A control with no `lexicon` key — every `en`
control, including the two `en` negation controls — is scored
exactly as it is at the base commit, and no corpus fixture is scored any other
way at all.

**FD2c — Loader compatibility, stated so the file cannot load half-empty.**
The lexicon loader is **locale-scoped**: `--locale en` loads only
`e2e/fixtures/eval/lexicon/clinical-terms.txt` (its 239 entries are in the five
existing categories, verified: `general` 71, `diagnosis` 53, `medication` 47,
`mse` 39, `risk` 29), and `--locale es-MX` loads only
`server/src/eval/lexicons/es-MX.txt`. Nothing is shared across locales —
`\bno\b` is the English word "no", and a Spanish lexicon reachable from an
English run would match it in every note. The category filter is widened from
`CATEGORIES` (`lexicon.ts:24`) to those **eight** categories — the five existing
plus `negation`, `number` and `unit` — and a line in `es-MX.txt` whose category is
outside the widened set is a **load-time error naming the file and the line**, not
the silent `continue` at `lexicon.ts:35`. A half-empty lexicon is the failure this
prevents. The glossary's other five categories (`presentation` 92, `intervention`
65, `risk` 45, `pattern-marker` 31, `frequency-time` 14) are filtered out at
**authoring** time and never reach the loader, so the load-time error applies to
`es-MX.txt`'s own lines and to nothing else.

**Whole-token boundaries, stated, because the one the file already uses cannot
match Spanish (N-3).** `lexicon.ts:39` builds `\b${stem(term)}\b`, and JavaScript's
`\b` is defined over `[A-Za-z0-9_]` — so **a term whose last character is
non-ASCII can never match at all.** That is not hypothetical: the `dejó` row in
§B-negation's attestation is 10 of 66, and `\bdejó\b` matches **0** of the 66;
of the 217 atomic alternatives the 152 glossary entries yield, exactly one
(`mié`, the alternative of `miércoles / mié`) ends in a non-ASCII character, and
none of the nine owner-approved negation terms does. The `en` clinical file is
unaffected — none of its 239 terms ends in a non-ASCII character after `stem()`,
and on all 239 the two constructions agree on a sentence containing the term
(0 disagreements) — so **its `\b` construction stays byte-identical** and F7's
English semantics do not move. The rule for everything in `es-MX.txt` is:

```
BOUNDARY(alt)  =  (?<![A-Za-zÀ-ÖØ-öø-ÿ0-9_]) alt (?![A-Za-zÀ-ÖØ-öø-ÿ0-9_])
```

An **explicit Latin-script class**, deliberately **not** `\p{L}\p{N}_`. The
review's suggested fix would have been wrong here, and the reason is a flag:
`compile()` builds every sidecar pattern as `new RegExp(source, anchored ? 'im' :
'i')` (`patterns.ts:66-69`) — with **no `u` flag** — and in a non-unicode
`RegExp` a `\p{…}` escape is not a property escape at all, it degrades to the
literal characters `p`, `{`, `L`, `}` (measured: `new RegExp('[\\p{L}]').test('p')
=== true`). A `\p`-based boundary would therefore be a class of punctuation
letters, silently. The explicit class is exact for the vocabulary FD2 admits,
which is Spanish and therefore Latin-script, and its two properties are both
testable: hyphen, punctuation and whitespace **are** boundaries (so `no-we` and
`nos` differ, while `nosotros` does not match `no`), and an accented final
character is inside a token (`mié`, `dejó`, `reportó` all match as whole
tokens). What it is **not** is general Unicode word segmentation, and it is not
claimed to be. A `es-MX.txt` term ending in a non-Latin script is not admissible
and raises the same load-time error, naming the file and the line. Measured
consequences of the rule, on the 66 tuning transcripts: the attestation table in
§B-negation reproduces **to the digit** — `no` 65, `nada` 50, `sin` 29, `nunca`
19, `nadie` 10, `dejó` **10**, `tampoco` 5, `ningún` 1, `ninguna` 1, `ninguno`
0, `jamás` 0 — and only `dejó` differs from what `\b` would have given, which is
the whole defect.

**Normalisation, stated because the boundary has a precondition it did not have
before (m-2).** FD2c's boundary is defined over **NFC** text.
`server/src/eval/lexicons/es-MX.txt` is authored and validated in NFC; every note
this card authors — every corpus expectation it writes and every `controlNote` — is
NFC and is asserted to be; and the 66 tuning transcripts are 66/66 NFC (measured),
so nothing in the attestation above depends on this clause. The measured reasons it
is stated rather than assumed: the precomposed pattern for `dejó` does **not**
match the NFD decomposition of the same word (`false`), and a combining mark is a
boundary, so `no` followed by U+0301 matches as a whole token (`true`) — which is
why an un-normalised NFD note would silently lose matches, not gain them. **The
guarantee that is deliberately not claimed** is for model output, which this card
does not control: normalising the note body before the lexicon patterns run happens
in `scoreNote`, and C3 does not license editing it. That is recorded as unresolved
item **U-1** below, with the two options and the owner's choice between them;
nothing else in this card text depends on the answer, and no number in §5, FD10 or
V4 moves whichever way it goes.

**Stemming is stated on both sides, and it is not the same rule for both kinds of
term.** `stem()` (`lexicon.ts:55-63`) strips a trailing `ing|es|ed|ly|s`, which is
right for F7's clinical vocabulary and wrong for a closed-class function word:

- The **negation** entries are matched as **whole tokens — and whole phrases —
  against the normalised (lowercased, whitespace-collapsed) note text, not the
  stemmed text.** None of the nine terms takes an inflection the stripper would
  have to remove, and stemming is not harmless here in either direction:
  `stem('jamás')` is `jamá`, so a stemmed `jamás` entry could never match `jamás`
  in a note, and `stem` turns the very common `nos` into `no`, so a `nosotros`-
  family or `nos` use in a note would match the `no` entry. Verified on all 66
  tuning transcripts under FD2c's boundary: whole-token matching on normalised
  text gives `no` 65, `nada` 50,
  `nunca` 19, `nadie` 10, `tampoco` 5, `ningún` 1, `ninguna` 1, `ninguno` 0,
  `jamás` 0, and **there is no file on which stemmed matching would differ** —
  so nothing is lost by not stemming, and a live false positive is avoided.
  `stem('ninguno')` is `ninguno` unchanged (it ends in `o`); nothing is stripped
  from any of the nine. The file's header lists the terms as written, unstemmed:
  `no`, `nunca`, `jamás`, `ningún`, `ninguna`, `ninguno`, `nadie`, `nada`,
  `tampoco`, with `sin` excluded and S4a.2's reason.
- The **number, unit and medication** entries keep F7's stemming **on both
  sides**, unchanged: the term and the note text are stemmed, and a multi-word
  alternative is stemmed per word and matched as a whole phrase.

**FD3 — `loadCorpus`: nested corpora load today; the integrity guard does not.**
`loadCorpus` already reads the split root's `expectations.json` and resolves each

and this card must not "fix" a failure that does not exist.
The real defect is the transcript inventory at `corpus.ts:82`: a **non-recursive**

**FD4 — Pipeline mode: the exact call sequence.**
Pipeline mode drives the HTTP surface; it does not call a provider. Per
invocation, once:

0. Refuse and exit 2 unless `APUNTA_CHECK_URL` is set, matches
   `^http://(127\.0\.0\.1|localhost)(:\d+)?$`, and its port is 7800–7889 and
   not 7717 — the check `scripts/check-note-format.mjs:37-56` already makes, for
   the same reason. Then `GET /api/health` and require `ok: true`,
   `fakeAi: false`, and a `testRunId` equal to `APUNTA_TEST_RUN_ID`
   (C-ISO@1 rule 5). Record `ollama.tag` and `ollama.model`. Any of these
   failing is exit 2 before a single fixture is touched: a pipeline run against
   a fake or foreign server measures nothing and says so.
0a. **The drafting language is a setting, not the format's locale.**
   `routes/generate.ts:39` reads `storedLanguage(db)`, and
   `routes/draft.ts:230` copies `format.locale` onto the note — so a run with
   `--locale es-MX` against a fresh sandbox database would draft **in English**
   and stamp the note `es-MX`, and `note.locale` could not reveal it. When
   `--locale es-MX`: require the server to have been started with
   `APUNTA_DEV_SPANISH=1` (`routes/settings.ts:26-32`; the sandbox wrapper's
   `serverEnv` inherits `process.env`, `sandbox.mjs:246-252`, so the implementer
   exports it), then `PUT /api/settings {"language":"es-MX"}` **before the first
   fixture**, require the response's `language` to be `es-MX`, and re-read
   `GET /api/settings` before the first fixture and after the last. A
   `language_unavailable` refusal (`routes/settings.ts:84-85`) or a 409
   `language_change_blocked` (`routes/settings.ts:88-90`) is `BLOCKED`, owner,
   with the response recorded. The settings read is the evidence of drafting
   language; `note.locale` is not.
1. `POST /api/patients` **once per invocation**, `{"name": …}` — `John Smith`
   for the English corpora (HS-8, the prototype's sample practice), a name from
   `e2e/fixtures/eval-es/NAMES.md` when `--locale es-MX`. One patient for the
   whole invocation, never deleted mid-run.
2. `POST /api/formats` **once per distinct `(format, sections)` pair** in the
   corpus, `{"name": <formatNameFor(fixture)>, "sections": [...], "locale":
   <run locale>}`, with **no `instructions` field**. The `name` is pinned to the
   exact literal the provider path uses — `"Progress note"` or `"Intake note"`
   (`run.ts:77-80`) — because `defaultInstructionsFor`
   (`default-instructions.ts:644-656`) matches the **section list first**, then
   `BY_FORMAT_NAME`, then a generic fallback, and the owner's own format (the
   `eval-owner` corpus) matches no `BY_SECTIONS` entry, so the name alone decides
   its instructions there. An unpinned or differently named format would get
   `GENERIC_INSTRUCTIONS` while the provider path gets the owner's progress
   instructions, and the two modes would stop measuring the same prompt. With no
   instructions field the server applies `instructionsFor('', name, sections)` →
   `defaultInstructionsFor(...)` (`default-instructions.ts:659-666`), the same
   selection the provider path makes (`run.ts:67-75`). The runner asserts the
   created format's `sections` deep-equal the fixture's, `format.locale` equals
   the run locale, `format.instructions` is `''`
   (`shared/src/note-format.ts:43-57` returns the stored string), and records
   `formatName` per fixture in the report.
3. Per fixture, per run: `POST /api/generate`
   `{"patient_id", "format_id", "title", "typed_notes" | "transcript"}`, with
   the source field chosen by the existing `draftSourceFor(fixture)`
   (`corpus.ts:215-219`), and `accept: text/event-stream`. Frames `status` and
   `token` are progress and are ignored. Frame `note` yields `note.id`. Frame
   `error` is a failure under FD5.
4. **The read-back is the scored artefact, and it is not optional.**
   `GET /api/notes/:id`, then score
   `textToSections(note.content, format.sections)` from `@apunta/shared`
   (`shared/src/sections.ts:179`, exported at `shared/src/index.ts:297`). The SSE
   `note` payload is **not** scored and is not a fallback: C-EVAL@1 §1 says the
   pipeline measurement is the note read back from the API *after persistence*,
   and the difference between what the stream carried and what was stored is
   exactly what this mode exists to see. The note stays `draft`; the runner never
   calls `POST /api/notes/:id/publish`, so `fitDraftingPriorNotes` — which keeps
   only published notes (`server/src/ai/prior-notes.ts:101, 109`) — can never feed
   one fixture's note to another. A test asserts it.
5. `--prior-notes > 0` and any `--instructions` are **refused in pipeline mode**
   with exit 2 and a named reason: the draft route reads prior notes from the
   database itself (`routes/draft.ts:97`) and `POST /api/generate` takes a
   `format_id`, so the two flags would otherwise measure something the pipeline
   does not do. V4 uses neither.
6. `--models` is a **label** in pipeline mode, not a control: the server
   resolves its own model (`defaultModelForMachine()` →
   `PROMOTED_DEFAULT_MODEL` = `qwen3.5:4b-q4_K_M`,
   `server/src/ai/model-picker.ts:88-90`). The runner cross-checks
   `/api/health`'s `ollama.tag` against `--models` and exits 2 on a mismatch.
   A silent difference between the tag in the report and the tag that answered
   is the one failure mode that makes a whole baseline section worthless.

**FD5 — The error rule. One rule, no judgement.**
Any of the following is recorded through the existing
`failedNote(fixture, model, run, message)` (`score.ts:127-158`) with
`gating: ['call_failed']`: a non-2xx from `POST /api/generate`; an `error`
frame; a stream that ends with no `note` frame; a non-2xx or 404 from
`GET /api/notes/:id`; a `note.content` that is empty or whitespace; a
`textToSections` result whose every section body is empty; a `note.format_id`
that does not equal the created format's id; a `note.locale` that does not equal
the created format's `locale`. The last two are **format-integrity checks** and
are described as such: `note.locale` is copied from the format
(`routes/draft.ts:230`), so on its own it says nothing about the language the note
was drafted in — FD4 step 0a's settings read is what says that. A failed run
**counts**: one run in that fixture's denominator, `safetyPassed: false`,
printed per fixture with its message verbatim. It is never retried inside the
invocation, never dropped from the min or the max, and never replaced by a
re-run — a re-run is the next invocation, in a fresh run folder, and its result
stands on its own. Bounded: four invocations per corpus, nothing repeats.

**A report already on disk is evidence and is never silently replaced (N-5).**
Two rules, because either alone leaves a hole:

1. **One directory per attempt.** Every V4 report goes to
   `docs/v2/evidence/S3.2/attempt-{{S32_ATTEMPT}}/`, with `{{S32_ATTEMPT}}` an
   integer supplied at dispatch (see Dispatch-time placeholders) and **never
   reused**. A re-attempt is
   additive: it writes `attempt-<n+1>/` and leaves every earlier report byte for
   byte where it was, readable, comparable, and attributable to the attempt that
   produced it. A partially completed attempt is **kept**, not cleaned up — its
   completed reports are the record of how far V4 got, which is the only progress
   marker there is, since `state/cards/S3.2.json` carries `sideEffectsDone: []`
   and `criteria: {}`.
2. **The runner refuses to overwrite, and it refuses pre-flight (m-4).** In
   `--mode pipeline`, if the resolved `--out` path already exists, the run
   **exits 2 with a named reason** printing the path — it does not write, and it
   does not report a measurement. The check is made **before the first fixture and
   before any model call**, as part of the same pre-flight that FD4 step 0
   performs: a spent path costs no measurement, and the invariant (a report is
   never overwritten) holds whatever happens later in the run. This is
   the check `cli.ts:252-253` cannot make for us: it resolves `--out` against
   `INIT_CWD` and then `writeFileSync`s it bare, which truncates. **`--mode
   provider` keeps today's behaviour byte for byte**, including the overwrite, so
   no existing card's `--out` changes meaning; the refusal is scoped to the mode
   this card introduces.

The consequence for the measurement is stated rather than left to the
implementer: FD10's four samples per corpus are **four samples of one attempt**,
taken from one directory. A set assembled from two directories is a **FAIL** on
the row (`BLOCKED`, owner, "samples from attempt `<n>` and attempt `<m>`"), not a
pooled average, because two of them would otherwise be silent replacements for
first-generation measurements. V1 tests the refusal with a pre-created target
path.

One `expectations.json` per locale, keys `<class>/<name>.txt` relative to the

**The sidecar type is narrower; the loaded `Fixture` is not, and that is the whole
of N-2.** An earlier revision said both "the control type omits the keys that do
not apply" and "the existing `assertFixture` checks apply unchanged", which cannot
both be true: `assertFixture` reads `fixture.markerFreeSource` whenever
`fixture.f6 === 'gating'` (`corpus.ts:124-127`) and iterates
`fixture.requiresHedge` (`:160-163`), and `Fixture extends
FixtureExpectations` types six keys required (`:40-60`). The contradiction is
resolved on the **load** side, not the assertion side:

- The **sidecar** type is a strict subset of `FixtureExpectations` — the keys the
  table below marks "as needed", plus the control-only keys — and omits
  `words`, `difficulty`, `markerFreeSource`, `requiresHedge`, `requiresMarker`
  and `novelTermAllow`. Nothing is weakened: a control is a different *kind* of
  thing and its sidecar is allowed to be a different *shape*.
- The **controls loader** then converts that sidecar into a **complete
  `Fixture`** with the six keys supplied by the rule below, deterministically,
  before anything else sees it. `scoreNote(fixture: Fixture, …)` (`score.ts:260`)
  and `assertFixture(fixture: Fixture)` (`corpus.ts:102`) are then called
  **unchanged**, on a value that satisfies their own type, with **no parameter
  added and no branch inside either function**. The claim "the existing
  `assertFixture` checks apply unchanged" is therefore true, and the claim "the
  sidecar is narrower" is also true — of the sidecar, which is where it belongs.

The six supplied keys, each with a value that is measured or copied rather than
invented:

| Supplied key | Value | Why it is not a weakening |
| --- | --- | --- |
| `markerFreeSource` | **measured** by the same expression `assertFixture` uses to verify it: `collapse(controlSource).match(f6Core()) === null` | It is the *answer*, not an assertion of the answer, so it cannot disagree with the check. | `requiresHedge` | copied from the sidecar when declared, else `[]` | `[]` makes `assertFixture`'s compile loop and `scoreNote`'s `hedgesRequired` zero-iteration rather than undefined-iterated, which is the whole collision the finding describes. A control that *wants* a hedge requirement declares it, so the capability is not lost |
| `requiresMarker` | copied when declared, else `[]` | same |
| `novelTermAllow` | `[]` | A control introduces no vocabulary the class is not about; the `clean` control's agreement with its `controlSource` (below) is what keeps F7 quiet, not an allow-list |

Every one of these six is a **default that the control could have written itself**,
which is the test of whether a default is a weakening: none of them can turn a
gating check off, add a fixture to a denominator, or lower a number a contract
reads. A control's own `format`, `sections`, `modality`, `f6`, `blank`,
`statedAbsence`, `noConclusion`, `mustNotContain`, `mustCapture` and `phraseBait`
pass through **unchanged**, so FD6's `degenerate` control still sets
`f6: "gating"` and still lists its section in `noConclusion`, and `assertFixture`
still verifies both against the sections it declares.

| --- | --- | --- |

**The three words are predicates on the control's `NoteScore`, stated here so no
implementation can disagree.** They use the score's own fields — `gating`,
`capturedFacts` and `totalFacts` (`score.ts:87, 92, 418` and `failedNote`'s
`totalFacts`, `score.ts:144`):

- `flagged` ⇔ `gating.length > 0` **or** `capturedFacts < totalFacts` — some
  gating entry exists, or at least one of the control's own `mustCapture` facts
  went uncaptured. The second disjunct is there because it is a real score field
  and a real state: `mustCapture` is scored at `score.ts:342-349`, where an
  uncaptured fact costs `c1`/`c2` points and adds **no** `gating` entry, so a
  control whose whole mechanism is an un-captured fact is detectable only through
  `capturedFacts < totalFacts`. Gating alone would call the lost-negation control
  unflagged on a correct implementation, which is exactly the defect IR-02 and
  IR-03 describe.
- `pass` ⇔ `gating.length === 0` **and** `capturedFacts === totalFacts`.
- `fail` ⇔ `gating.length > 0` **and** the named `mechanism` is present in it.

And in every case the sidecar's `mechanism` must be the one observed: for
`empty`, `gating` contains `S4 every section blank` (the `collapsedNote` branch,
`score.ts:300, 395`); for `degenerate`, `gating` contains
`F6 unsupported conclusion`, which requires the sidecar to set `f6: "gating"` and
to list the repeated boilerplate's section in `noConclusion` so the existing F6
path supplies it (`score.ts:319, 397`); for a `positive` control, either the named
`gating` entry is present, or the mechanism is `missed mustCapture` and
`capturedFacts < totalFacts`. A control whose `expect` is `flagged` and which
moves neither is a **missed control** under FD6's admissibility rule; a `fail`
control whose named mechanism is absent is also a missed control, because the
class did not test what it claims to test.

**`controlSource` exists because `scoreNote` compares the note against the source
in six places** (F2 quoted spans, F3 numbers, F4 medications, F7 novelty, the
novel-content-word rate, the expansion ratio — `score.ts:270, 314-316, 496-505,
600-622, 677-681`). A control whose source is empty is not a control: F7 tests
each lexicon entry with `entry.pattern.test(stemmedBody) && !entry.pattern.test(stemmedSource)`
(`score.ts:499-501`), so with an empty source the second term is true for every
term, every diagnosis and risk term in the note becomes `gatingNovel`, and
`F7 novel diagnosis/risk term` enters `gating` (`score.ts:321-323, 398`) — the
`clean` control, a faithful note and therefore exactly the note most likely to
name a diagnosis or a risk, could not pass on a correct implementation. Each
`controlSource` therefore contains the same clinical vocabulary its `controlNote`
does wherever the control is not *about* introducing it: the `clean` control's
source and note agree on every term, the `lost-negation` control's source carries
the negation its note drops, the `invented-negation` control's source does not.
The `empty` control's `controlSource` is a real transcript and its `controlNote`
is `""`. **F7 source validity is asserted, not assumed, and the assertion is an `en` test

**FD8 — The negative-control flag is named and owned.**
`--blind-lexicon <name>` (FD1). V3 uses `--blind-lexicon negation`. The flag
**substitutes FD2b's never-matching form at the run's `{{lexicon}}` tokens** — the
lexicon is read and validated exactly as authored and is never emptied (B-3) —
prints `negation lexicon blinded (negative
control)` in the report header so no report from it can be mistaken for a
measurement, and changes no threshold and no other behaviour. Because FD2b makes
the lexicon a real scoring input, the blinded run genuinely changes scores — and
**which controls flip is stated, not assumed.** Blinding removes the negator
vocabulary inside the lexicon-expanded patterns, so:

- The **`es-MX` invented-negation** positive control's `mustNotContain` patterns
  each contain the `{{lexicon}}` token in the negator's slot (FD2b) — an
  **author-time rule, not a description**: EVERY `mustNotContain` entry of the
  `es-MX` invented-negation control carries that token in the negator's slot, and
  a single entry without it makes the control unreachable for V3's exit 3 rather
  than merely weaker. V1 asserts it mechanically, so a later edit cannot quietly
  drop one. So under blinding every one of them
  expands to `(?!)` plus its own authored remainder — a pattern that can never
  match — its `F1 banned string` entry disappears from `gating`, and the control
  is **missed** — the control miss V3 expects, and the one that makes exit 3
  reachable. (`(?!)` and not an empty `(?:)`, and the reason is measured on this
  card's own shape: `(?:) refiere` matches a text with **no** negator in it, so
  the pattern would fire and the blind run would manufacture gating instead of
  removing it.) Its `en` counterpart carries no token and no key, so it is
  **expected to stay flagged** under any lexicon flag, for the same reason the
  lost-negation control does.
- The **lost-negation** positive control is **expected to stay flagged**, because
  per FD2b its detection is the affirmative restatement in `mustNotContain`
  (sidecar-authored, not lexicon-derived) plus the un-captured `mustCapture` fact,
  and the blinded token removes the vocabulary from a `mustCapture` pattern that a
  faithful note already failed to satisfy under revision 2's shapes and now
  satisfies only through its own gold-quoted alternatives. A blind run in which
  that control *also* un-flags is a finding to
  report, not a defect; a blind run in which it stays flagged is the expected
  result and is **not** a missed control. This is a direct consequence of the
  corrected direction in IR-02, and it is the honest scope of what a blinded
  negation lexicon can demonstrate — which is part of what Choice 2 asks the
  owner to weigh.

**FD10 — The numeric acceptance rule, and what is a measurement versus what is an
inadmissible run.**
Two different failures must not be confused, so they are named apart:

- **Inadmissible (the measurement does not exist).** A control miss (FD6, exit
  3); a
  corpus or controls directory that loads zero fixtures; the sandbox, `/api/health`
  or `testRunId` refusals of FD4 step 0; a `language_unavailable` or 409 from
  FD4 step 0a; an `ollama.tag` that disagrees with `--models`; a missing or
  blank digest; a format-integrity failure from FD4 step 2; an incomplete set of
  the eight reports; an `--out` path that already existed (FD5's refusal, exit 2);
  and a corpus whose four reports are not all under one `attempt-<n>/`
  directory. An inadmissible run is **fixed and re-run into a new
  `attempt-<n+1>/`**; it is never
  converted into a pass, a partial average, or a "reported anyway".
- **Measured (a number exists).** Exit 0 or 1 per invocation, the gated-run
  count, and every rate. These are results, not verdicts. The verdict is computed
  per corpus and per metric by this rule and nothing else:

  For each corpus `C` in {`e2e/fixtures/eval`, `e2e/fixtures/eval-owner`} and
  each metric `M` in exactly §5's seven rows — fabrication rate, safety facts
  (C2), salient facts (C1), gated runs, schema valid, unwarranted blanks, blank
  preserved — take the four invocations' numerators and denominators as printed,
  form `min(C,M)` and `max(C,M)`, and compare against §5's recorded range for
  that cell (`BASELINE.md:202-212`):

  - **The four are four reports from ONE attempt directory** (FD5's
    `attempt-<n>/`). A cell whose four reports are not all under one
    `attempt-<n>/` is **BLOCKED**, owner, naming the two attempts — never a
    pooled set. Two of the four being second-generation replacements for
    first-generation measurements is exactly the substitution the min/max rule
    cannot see, so the rule refuses the set rather than reading it.

  - **IN RANGE** iff `min(C,M) ≥ §5min(C,M)` **and** `max(C,M) ≤ §5max(C,M)`.
  - **FAIL** otherwise, recorded with the §5 value, the measured value and the
    delta. "Outside → fail" is C-EVAL@1 rule 8's own words; the runner implements
    it and does not soften it.
  - **NOT MEASURED** when a report carries no denominator for that cell. Never
    IN RANGE, never PASS.
  - No tolerance, no rounding, no interpolation, and no metric outside §5's
    seven rows enters the verdict — other rates are recorded in §9 as
    measurements and gate nothing.
  - The integers, not the rounded percentages, are the comparison, per §7 of
    `BASELINE.md`.

  Row status: **PASS** only when every cell of both corpora is IN RANGE and the
  run was admissible; **FAIL/BLOCKED, owner** when any cell is FAIL, with the
  cells listed; **BLOCKED, owner** when the run was inadmissible. The eight
  provider measurements of §5 are the comparison point and nothing more: an exit
  1 on `e2e/fixtures/eval` is **not** accepted by inference from P0.4's provider
  exit codes (4 of 20 runs gated, exit 1 on all four invocations,
  `BASELINE.md:60-62, 80-83`) — it is measured and compared, like every other
  number, and on `e2e/fixtures/eval-owner`, where §5 records **0/4** gated, a
  pipeline count above zero is a FAIL.
