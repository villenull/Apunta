## Objective

Give `scripts/check-refine.mjs` and `scripts/check-note-format.mjs` a command
line that can go red, and give the sandbox a step that seeds an empty database.

That is one thing, not two. Neither script can currently report a failed
assertion: the only non-zero exits are pre-flight refusals, so a measurement row
asserting "exit 0" asserts something the tool has no way to report otherwise,
and `check-refine.mjs:62` funnels every argument except the literal `--only`
into one filter set, so `:239`'s guard skips **every** scenario and the run
exits 0 having measured nothing. Both are defects in the scripts, not in any
card's prose, which is why AM-165 split them out of S3.3 rather than widening
S3.3's May edit: S3.3's rows now describe what must be true, and this card is
what makes it true.

**Nothing in this card changes what a check measures.** The rule functions, the
fixture sets, the English section constants, the lexicons and the summaries are
all S3.3's business and are untouched here. This card adds argument parsing,
four assertions that can fail (codes `3`, `4`, `5` and `6`), one hermetic rules dump,
one seeder, and the in-process stub Fixed decision 8 grants the test suites.

## Preconditions

`npm run build` — `sandbox.mjs` refuses to start without `server/dist`
(`startServer`), and **`check-refine.mjs:48` exits 2 without it**. That import
sits **above** the loopback guard, and that is the one place the build reaches a
row that is otherwise hermetic: **V1's third conjunct** (`check-refine.mjs`
against a non-loopback `APUNTA_CHECK_URL`) is refused by the build before the
loopback guard can fire, so it needs `server/dist` and V1's other three conjuncts
do not — `check-note-format.mjs` imports nothing from `server/dist` at all. By
Fixed decision 3 the build is also not needed by V2, V3, V4, V5 or V8.

**V6 and V7 drive a real model**: both scripts exit 2 on `health.fakeAi`
(`check-note-format.mjs:153-158`, `check-refine.mjs:207-211`), so
`APUNTA_FAKE_AI` must be off and `qwen3.5:4b-q4_K_M` must be up.

**V2, V3, V4 and V8 need none of that** — no Apunta server, no model, no
database, no build — and with V1 they are the rows that carry the
falsifiability. **V5 needs no Apunta server, no model and no build either, but
it is not portless and no longer claims to be** (Fixed decision 8): `0` and `3`
are reachable only after a run completes, so its suites bind one in-process
`node:http` stub on an **ephemeral** loopback port and point the scripts under
test at it. That is the only listener this card creates, it is granted explicitly
by Fixed decision 8, and Stop 1 is written around it.

**No row ever leaves `APUNTA_CHECK_URL` unset.** `BASE` falls back to the
live instance's port when it is (`check-note-format.mjs:26`,
`check-refine.mjs:17`), so a row that forgets it would dial the live port —
which HS-1 forbids — on any machine where that instance is up. Every
invocation in V1 to V5 therefore either sets it to a dead loopback port or is a
refusal that happens before a request object exists; the sandbox rows have
`sandbox.mjs` set it to the run's own port (`childEnv`), and **V5 sets it to
`http://127.0.0.1:1` on the `node --test` invocation**, so every process the
suites spawn inherits a dead URL unless the case deliberately overrides it with
Fixed decision 8's stub. The one deliberate exception to "set it" is **V1's first
two conjuncts, which set it to the empty string on purpose**: the `APUNTA_V2`
guard fires only when `APUNTA_CHECK_URL` is unset or empty, so an inherited
value from a dispatcher would let both of them fall through it and turn the row
red for a reason that has nothing to do with the parse.

Each sandbox row allocates its own run folder under `/tmp/apunta-v2/` with an
**empty data directory**; nothing in this card reads or writes the live data
folder and nothing here touches the live instance's port (HS-1).

## Fixed decisions

**1 — The exit-code table, and no two failures share a code.**

| Code | Means | Reachable by |
| --- | --- | --- |
| `0` | the run exercised what it claimed and printed its measurement | a complete measurement run; `--print-rules`; `--self-test` with every control firing |
| `2` | **usage or pre-flight refusal, unchanged** | unknown flag; unknown locale tag; a flag with no value; a repeated flag; a non-integer count; `--only` with no value; an unknown `--only` id; the existing four pre-flight paths (`APUNTA_V2`, non-loopback `APUNTA_CHECK_URL`, fake AI, missing format or patient) and the built-server refusal |
| `3` | **an assertion about the run was not met** | `--expect-fixtures N` / `--expect-scenarios N` where the number actually read or actually run is not `N` |
| `4` | **a control did not fire** | `--self-test`, a pinned control whose named flag did not appear |
| `5` | **the flag was understood and the thing it names is not here** | a locale with no fixture tree (`es-MX` at this card's base) or no self-test controls; `--print-rules` never raises it |
| `6` | **the run could not be measured at all** | an `--expect-*` flag was passed and the set it counts could not be enumerated — an unreadable or unparseable fixture file, named in the message |

`0` and `2` are S3.3's own FD 1 codes and are **not renumbered**: an
implementer who "improves" the numbering breaks S3.3's V1, V2 and V6 rows,
which are stated against `2` and `3`. `3` and `4` are S3.3's FD 1 codes for the
count assertion and the control. `5` and `6` are this card's additions, and each
covers a failure no other code covers — `5` is reachable **only** by correctly
consuming a flag, and `6` is the one case where "no count exists" must not be
mistaken for "the count is zero". A code collision is how an infrastructure
crash gets read as a measurement, so `6` exists rather than letting a parse
error surface as an uncaught `1`.

**`1` is never returned deliberately.** It is what node gives an unhandled
rejection — a `fetch` to a server that is not there — and it belongs to node,
not to these scripts. **V4's two dead-URL conjuncts are the only rows that
assert anything about a failing measurement path, and they assert
`non-zero`** — **not** "non-zero and not `1`", which this paragraph asserted
once and which no conforming implementation can satisfy: both scripts reach
`await api('/api/health')` at top level with no `catch`, so that run *is* an
unhandled rejection and *does* exit `1`, and this paragraph was forbidding the
code its own named mechanism produces. So no row pins `1`, none enshrines a
crash as an interface, and **no row may make the crash a code**: giving an
unreachable server a code of its own would mean catching the first `fetch` in
both scripts, which changes what the no-flag path does when the server is down —
Stop 5 and Fixed decision 2's byte-identical stderr — so it is a decision for
the coordinator and not something a verification row may quietly require. What
the two conjuncts are for is the thing they still do check: a `--print-rules`
that ignored `APUNTA_CHECK_URL` would exit `0` against the dead URL.

**The flag grammar is one grammar in both scripts; only what each flag counts is
per-script.** S3.3's Fixed decision 2 lists the six flags "for both scripts", and
that is the specification, so **both scripts consume all six** and refuse an
unknown token on the same rules with the same codes — a flag is not refused on
one script merely because the other one owns it. What a flag *names* is the only
thing that differs, and this is where it is said once so no row has to guess:

- `--only <id>` takes ids out of the tree the locale names — **scenario** ids in
  `check-refine.mjs`, **fixture base names without the `.txt`** in
  `check-note-format.mjs`, which are exactly the entries its fixture loop at
  `:180-182` has. An id that is in neither set is **`2`, in either script, with
  or without `--locale`** (Fixed decision 2, and Stop 4).
- `--expect-scenarios N` counts scenarios that **ran** in `check-refine.mjs`.
  `check-note-format.mjs` has no scenarios, so there the same flag counts the
  **fixtures read** — the number `--expect-fixtures N` asserts — and a mismatch
  is `3`. The flag is consumed rather than refused because the grammar is
  shared, and it is not vacuous because the comparison behind it is a real one.
- `--expect-fixtures N` counts fixtures **read**, in either script.
- `--locale`, `--print-rules` and `--self-test` behave identically in both.

Nothing in this paragraph widens S3.3. It says, per script, what the ids and the
counts are, so that "accept the flag set" is a specification and not a licence
to make one of the two flags meaningless.

**2 — Nothing in the new surface runs unless its flag was passed.** This is the
whole backward-compatibility guarantee, in one sentence, and V1 is the row that
proves it. With no flag in `argv`:

- the argument parser consumes nothing and computes no locale, so `--locale`'s
  tree check (which would otherwise be a new failure) does not run;
- the `--only` id set is **empty**, exactly as `:62`'s filter yields an empty set
  for an empty argv. There is no `--only` to have been passed, so no id is
  unknown and **none is refused** — today an unknown id matches nothing and the
  run measures zero scenarios, and that is preserved;
- no fixture file is read earlier than it is read today, so an unparseable
  fixture still throws where it throws and no new `6` appears;
- stdout and stderr are byte-identical on all four pre-flight paths.

**An unknown `--only` id is refused whenever `--only` was passed — with or
without `--locale`.** S3.3's Fixed decision 2 says "An unknown id, or `--only`
with no value, exits 2" and is the specification; narrowing it to the
`--locale <tag> --only <id>` combination would narrow a neighbouring card's
decision from its prerequisite, which is the collision HS-9 exists to prevent,
and there is no reading under which refusing an id the user asked for is a
backward-compatibility hazard. The two rules do not collide: with no flag in
`argv` there is no `--only`, so the unconditional refusal has nothing to refuse.
V2 asserts both halves — `--only nosuch-scenario-id` with no `--locale`, and
`--locale en --only nosuch-scenario-id`.

**3 — The whole argument parse sits at the top of the module, above every
`import()` of `server/dist/**` and above every HTTP call, in both scripts.**
Today `check-refine.mjs:48` imports the fact tokeniser and **exits 2** if the
build is missing, above the loopback guard and above everything. If the flags
were parsed after it, `--print-rules` and `--self-test` would need a build, and
S3.3's V3 ("hermetic — no server, no port, no model, no database") and V7
("hermetic") would be untrue.

Order inside the parse, and the order is fixed because two rows depend on it:

1. flag grammar — an unknown flag, a flag with no value, a repeated flag, a
   non-integer count, or a bare positional → **2**, and the offending token is
   in the message;
2. locale — `--locale <tag>` where tag is `en` or `es-MX`; anything else → **2**,
   naming the tag. **`--locale` is consumed here and never reaches `only`.**
   That is the whole of `check-refine.mjs:62`'s defect, and this is its fix:
   `only` is now built from the value that **follows** `--only` and from
   nothing else.
3. `--print-rules` → print the blob and exit **0**, here, before anything below.
4. `--self-test` → run the controls and exit **0**, **4**, or **5** — `5` when
   the locale named has no controls — here, above step 5, so it does not depend
   on a tree existing.
5. locale **tree** resolution — the fixture directory the locale names must
   exist. It does not at this card's base for `es-MX` (the `-es` trees are
   S3.3's), so `--locale es-MX` is **5** on a clean checkout, and that is what
   makes V3 hermetic and falsifiable. **Only reached when `--locale` was
   passed** (Fixed decision 2).
6. `--only` id validation — reached **whenever `--only` was passed**, with or
   without a locale, against the ids that tree actually contains; an unknown id →
   **2**, naming the id. It sits after step 5, so `--locale es-MX --only
   anything` against a tree that does not exist is **5**, not 2. With no
   `--locale` passed that tree is the **English** one the script reads today
   (`e2e/fixtures/refine/`, `:223-224`) and `check-note-format.mjs`'s
   `e2e/fixtures/her-format/`, because Fixed decision 2 leaves the no-flag path
   exactly as it is.
7. the existing pre-flight guards, in their existing order and with their
   existing messages, then the first HTTP call, then the counts.

**4 — `--print-rules` makes no HTTP call and, whatever the locale, exits 0.**
It reads constants and, for `check-refine.mjs`, the fixture files of the tree it
is printing. A locale with no tree is not an error here: `sectionsByFixture` is
`{}` and the run still exits 0. That is deliberate and it is why S3.3's V3
command `node scripts/check-note-format.mjs --print-rules --locale es-MX` keeps
its meaning on a tree that exists and on one that does not, and why the rule
"tree resolution raises 5" is scoped to step 5 above and not to the dump.

The blob's **shape is pinned here; its bytes are S3.3's.**
`docs/v2/evidence/S3.3/english-rules.json` is S3.3's pin and
`scripts/v2/assert-english-rules.mjs` is S3.3's checker, so this card fixes only
the shape the checker reads:

- `check-refine.mjs` emits exactly these keys: `script`, `locale`,
  `sectionsByFixture`, `headingPattern`, `fixtureFilter`, `wordCountSplit`,
  `claimVerbs`, `serverOpenings`.
- `check-note-format.mjs` emits exactly these keys: `script`, `locale`,
  `sections`, `riskSentinel`, `headingPattern`, `flagRules`,
  `borrowedExtractor`.

`sections` in `check-refine.mjs` is a **map from fixture file name to that
file's section-name array**, because those names come from the fixture
(`:224`), not from a constant — a single `sections` array would be a claim the
script cannot make. `sections` in `check-note-format.mjs` is the four English
constants of `:123-126`. `fixtureFilter` is the ordered list of fixture **file
names** the filter accepts (`check-refine.mjs:223`).

**The type of every key is pinned here as well, because a shape a reader has to
infer is a shape nobody checks.** `script` and `locale` are strings;
`sectionsByFixture` is a plain object whose every value is an array of strings;
`sections`, `fixtureFilter` and `serverOpenings` are arrays of strings;
`claimVerbs` and `flagRules` are arrays of objects with the entry shapes above;
`headingPattern`, `wordCountSplit` and `borrowedExtractor` are `{source, flags}`
pairs whose two values are strings; `riskSentinel` is a string. **Empty is
legal** — a tree with nothing in it is exactly the `es-MX` case below — and V4
asserts each of these types, not only each key's presence.

**Every pattern is emitted as its `source` string and its `flags` string
separately, never as a re-serialised `/…/flags` literal.** This is the one
shape decision that has to be right for S3.3's V3 to work at all: that row
proves every pin literal **byte-present** in `git show {{BASE}}:…`, and a
slash-delimited re-serialisation is byte-present only by luck. A `.source` is
the substring the file actually contains. `claimVerbs` entries are
`{kind, source, flags}`; `flagRules` entries are `{name, source, flags}`;
`borrowedExtractor` is `{source, flags}`; `headingPattern`, `wordCountSplit`
are `{source, flags}`. The shared constants — `CLAIM_VERBS`, `SERVER_OPENINGS`,
the fixture filter, the heading pattern, the word-count split, the section
names, `None.` — are exactly S3.3 FD 6's nine pinned groups, one key each, so
the pin has a key to live in.

`sections`, `sectionsByFixture`, `riskSentinel` and `flagRules` vary with
`--locale`; everything else is a shared constant repeated in every blob.
Repetition is harmless and it keeps one flat reader in S3.3's checker. **`es-MX`
at this card's base carries `{}`, `[]`, `""` and `[]`** for those four
locale-varying keys, and turns them real in S3.3.

**5 — `--expect-scenarios` counts scenarios that RAN, and
`--expect-fixtures` counts fixtures that were READ.** Not the number present on
disk. (Which of those two names does the counting on which script is Fixed
decision 1's per-script list, not this one.) S3.3's V2 passes the whole `-es` count with no `--only` (present == ran),
and its V8 passes `--only <one-id> --expect-scenarios 1` against a tree of
sixteen — which is only correct if the count is of what ran. The comparison
happens after the run and after the summary is printed, so the measurement is
on record whether the assertion holds or not; the exit code is the assertion,
never the summary. The count is computed from the **same list the script iterates
** (`check-note-format.mjs:180-182`, `check-refine.mjs:223` and `:239`), so a
card that counts the directory differently gets a mismatch rather than a
vacuous agreement.

**6 — `--self-test` is a control that must be able to fail, and at this card's
base it has only English controls.** Each control asserts a **named** flag and
prints its name and outcome; any control that does not fire is **4**. The
controls' inputs are pinned **in-script** — a canned draft, never a generated
one — so `--self-test` needs no server, no model and no fixtures. The English
controls exercise what exists at this base: that a draft under the English
headings parses into the four English sections (`splitSections` /
`sectionsOf`), that the borrowed-sentence extractor returns a non-empty list for
the English worked example, and that the fixture filter names the two English
refine files.

**`--self-test --locale es-MX` is `5` on this card, and that is the point.**
A locale with no controls is not a passing self-test, and the code is the one
Fixed decision 1 gives a thing that is understood but not here. S3.3 supplies
the `es-MX` controls when it supplies the `es-MX` rule table, and **S3.3's V7
(`--self-test --locale es-MX`, expected `0`) is a genuine requirement on S3.3
because of this**, not a formality: a tree that lands without its controls
exits 5 and V7 is red. **Both producers of `5` have a row here** — tree absence
and control absence — so neither is a code an implementer can satisfy by
asserting nothing: V3's first two conjuncts are the tree and **V3's last two are
`--self-test --locale es-MX`, one per script**, which need no tree and no build
because step 4 sits above step 5.

**7 — `scripts/v2/assert-english-rules.mjs` stays S3.3's, and is not
duplicated here.** It is the checker for a pin file that lives in S3.3's
evidence directory, it asserts S3.3's claim about the English rules, and its
input is the blob whose shape this card fixes. Two cards creating one file is a
scope collision HS-9 cannot resolve, and this card cannot own a checker whose
fixture it does not author. **What this card owes S3.3 instead is the shape:**
Fixed decision 4's two key lists — **eight keys for `check-refine.mjs`, seven
for `check-note-format.mjs`, twelve distinct names** — with the `source`/`flags`
split and the per-key types are the contract S3.3's checker is written against,
and the implementer reports that shape in the return file **verbatim: both lists,
exactly as Fixed decision 4 writes them, plus the type of each key**, so S3.3's
checker is written to what exists rather than to what S3.3 hoped for. The
