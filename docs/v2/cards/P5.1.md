## Objective
Every part of a backup archive describes the same moment, and concurrent
backups cannot erase each other's staging files.

## Fixed decisions
C-SNAP@1 **in full**, rules 1-4, and these say how each one is met.

1. **One snapshot function.** `server/src/db/snapshot.ts` exports the single
   copy-making function backups use now and that P5.2's pre-migration snapshot
   uses later. It takes the source handle and a destination path and returns the
   copy's path. `server/src/backup/archive.ts` does not grow a second copy path
   of its own.
2. **Rule 3's 409 — which layer raises it, and which one only names it.** The
   lock and the wait live in the **backup module**, wrapping both `runBackup` and
   `runBackupAsync` (`index.ts:74-173`), so `POST /api/backup`
   (`routes/backup.ts:60`) **and** the daily automatic backup
   (`maybeRunDailyBackupAsync`, `server/src/index.ts:94`) are both covered — not
   the HTTP request path alone. The module throws
   `new BackupError(message, 'backup_in_progress')`, a fourth member of
   `BackupError`'s code union (`archive.ts:41-49`). The **route** is what turns
   that into a status, because only the route knows the caller is HTTP:
   `routes/backup.ts:73-76` maps that one code to
   `new HttpError(409, 'backup_in_progress', …)` and every other `BackupError`
   keeps today's `badRequest` (400). A day-startup `maybeRunDailyBackupAsync`
   that loses the race records the error in Settings and moves on; it shows
   nobody a 409.
3. **The step-1 hook is named, and it covers both entry points.**
   `CreateBackupOptions` (`archive.ts:51-61`) gains `onCopied?: () => void`,
   invoked in `finishPreparation` **after** `integrityCheck` and **before** any
   read of `options.db` — so both `createBackup` (sync, `VACUUM INTO`,
   `:155-166`) and `createBackupAsync` (online backup, `:168-179`) fire it. The
   async one is the path HTTP uses (`routes/backup.ts:60` → `index.ts:136`); the
   sync one is what the existing tests call. Step 1's assertions therefore run
   against **both**, or rule 2 holds for one entry point and not the other while
   V1 is green. The hook is an ordinary optional field on a shipped options
   type, not a test-only export: production callers omit it.
4. **Rule 1's primitive, and both entry points stay.** The online backup API
   (`backupInto`, `archive.ts:290-296`) is the primitive. The sync
   `VACUUM INTO` path (`vacuumInto`, `:282-288`) and `createBackup` are **kept**:
   the file defends each on purpose today (`:25-39`, `:221-226`) and this card
   authorises no deletion — "One primitive" in the contract names the choice of
   snapshot method, not a licence to remove a code path this card's own tests
   call. Step 1's assertions run against both. The copy always lands inside
   `<dataDir>`, so `backup.test.ts:135` ("writes nothing into TMPDIR") stays
   green; pointing `db.backup()` at `tmpdir()` is not one of the ways to
   satisfy rule 1.
5. **`<op>` is defined, and so is the staging root.** `<op>` is `backup` for a
   manual or daily backup and `pre-migrate` for P5.2's C-UPD@1 step-3 safety
   snapshot, so P5.2 needs no contract change and the safety file stays
   identifiable by path. The parent is `<dataDir>/staging/` — a **sibling** of
   `backups/`, not nested under it — created with
   `mkdirSync(…, { recursive: true, mode: 0o700 })`; one operation gets
   `<dataDir>/staging/<op>-<uuid>/` with a fresh UUIDv7. A
   `<dataDir>/backups/.staging` folder left by an install that predates this
   change (`archive.ts:86`) is removed **only when it is empty**, and never
   recursively while it still holds anything.
6. **Rule 2, stated exhaustively.** Every manifest field except `app_version`,
   `generated_at` and `encrypted` — **including** `migration_level` and
   `sqlite_version` — is read from the read-only copy handle, never from
   `options.db`. `migrationLevel` is not a file header: it reads the
   `schema_migrations` table of the handle it is given
   (`server/src/db/migrate.ts:69-72`), so it is exactly as live as the counts
   are; `sqlite_version` is SQLite's library version, identical either way, and
   naming it removes the argument. Only the caller's own inputs (destination,
   passphrase, `now`, app version) come from the request.
7. **Rule 3's 60 s has a test seam, and the production number does not move.**
   The wait is an exported constant `BACKUP_LOCK_WAIT_MS = 60_000` in
   `server/src/backup/`, released in a `finally`. Production stays 60 s (HS-7
   forbids loosening a contract threshold) and one case asserts the constant is
   still `60_000`; a test-only option (e.g. `lockWaitMs`) overrides it so step
   2 sees the 409 in well under a second. No test sleeps a minute, and no
   fake-timer trick is needed around a synchronous `better-sqlite3` path. The
   lock's coverage of both entry points is decision 2.
8. **The staging-cleanup case is re-pointed, not deleted.**
   `backup.test.ts:160-162` ("leaves no staging copy of the database behind") is
   updated to assert on `<dataDir>/staging` — left alone it would go vacuous,
   passing while watching a folder nothing writes to any more — and extended to
   assert that no `<op>-<uuid>` folder remains after a **successful** backup and
   after a **failed** one.

## Steps
1. **Consistency case, test first.** A synthetic database in a temp data dir
   (`mkdtempSync`, the `backup.test.ts:62` shape) is WAL already —
   `openDatabase` sets `journal_mode = WAL` (`server/src/db/index.ts:48`), so no
   step turns it on. Run a backup whose `onCopied` writes one new synthetic note
   (the prototype's John Smith practice, HS-8) between the copy and the
   derivation, and assert against **both** `createBackup` and
   `createBackupAsync` that the archive's database, manifest counts,
   `data.json` and readable notes all exclude that note. Record the initial
   result (expected to fail).
2. **Overlap case.** Two backups over one data dir: the first holds the lock,
   the second waits and then gets `409 backup_in_progress`, observed through
   `lockWaitMs`. A failed run's cleanup never deletes the other run's staging
   folder, and afterwards `<dataDir>/staging` holds no `<op>-<uuid>` folder.
3. **WAL case.** Insert and commit without checkpointing, then assert the row is
   readable from the archive's `.db` **and** that the zip carries no `-wal` or
   `-shm` entry. `backup.test.ts:120-133` already pins the second half, so this
   extends that case rather than inventing one — and it is the case that catches
   a bare `copyFileSync` of the database file, which step 1's post-copy write
   cannot.
4. Implement, in the order the Fixed decisions give.
