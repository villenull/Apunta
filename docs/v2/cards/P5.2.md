## Fixed decisions
C-UPD@1 migration steps 1 to 5 and decision E8. Error codes
`newer_schema`, `snapshot_failed`, `migration_failed` map to the boot-error
page (bilingual, S2.5).

**The three codes are the whole vocabulary, and a test sees the code.**
`newer_schema`, `snapshot_failed` and `migration_failed` are each the `code`
property of a thrown `MigrationSafetyError` (new, exported from
`server/src/db/safety.ts`; `new MigrationSafetyError(message, code)`), modelled
on the `BackupError` shape P5.1 shipped
(`server/src/backup/archive.ts:50-62`). Not an HTTP status, not a member of
`ApiErrorCodeSchema` (`shared/src/errors.ts` stays closed — S2.5's
out-of-scope list, `S2.5.md:41-42`), and not a string a test greps out of a
message. The plain `Error` `snapshotDatabase` throws (`snapshot.ts:63`, `:71`)
is wrapped, not re-thrown. Every case in Steps asserts `code`;
`migrate.test.ts:130-132`'s message assertion is re-pointed at the new type.

**The boot-error page's own sentences are S2.5's, not this card's.** This card
raises the code and stops. `server/src/index.ts:57`'s existing
`storageBootMessage` call carries it exactly as it carries every other boot
failure today, and the bilingual copy on the page is S2.5's file —
`server/src/boot-error.ts` is not in May edit and S2.5 is `NOT STARTED`
(`PROGRESS.json:30`).

**A data folder with no `apunta.db` is not an inspect case.** "Migrations are
pending" means pending **on an existing database**. With no `apunta.db`: no
read-only open, no `newer_schema`, no `safety/` file, no snapshot — create the
database at the current level exactly as `openDatabase` does today
(`server/src/db/index.ts:41-46`). A first run therefore never writes a safety
snapshot and can never evict a real one under step 5.

**Where the order lives, and where it is asserted.** The sequence C-UPD@1 steps
1-4 describe — pending restore, then the safety snapshot, then the migration,
then the open — is one exported function in `server/src/db/safety.ts`, and
`server/src/index.ts`'s entire edit is that call in that position between
`applyPendingRestore` (`:33`) and `openDatabase` (`:34`).
`server/src/index.ts:144` runs `void start()` at module scope, so it cannot be
imported by a test; the ordering assertion lives in
`server/src/db/safety.test.ts` (new, this card) and is made through that
function's observable effects — the restored file is the one the snapshot
copies, and the snapshot is the pre-migration one — not through `index.ts`. A
spawned-server test is not available: it would need a helper in May edit and a
sandbox port, and this card has neither.

**Staging, the destination, and the stamp.** C-UPD@1 step 3's destination and
C-SNAP@1 rule 1's staging root are one mechanism, not two: stage under
`staging/pre-migrate-<uuid>/` with mode `700`, `PRAGMA integrity_check` the
copy, then move it to `safety/pre-migrate-<from>-<to>-<utc>.db`. `<utc>` is the
house convention `restore.ts:242-245` already fixes —
`now.toISOString().replace(/[:.]/g, '-')` — which sorts lexically, so "keep the
last 3" is orderable by that stamp.

**Nothing here launches anything.** The rows are in-process vitest,
eslint/prettier and `tsc`, so they run bare rather than through
`scripts/v2/sandbox.mjs` (as in AM-025 and P5.1). No test resolves
`loadConfig({}).dataDir` or `.dbFile`, which without `APUNTA_DATA_DIR` is the
platform default and therefore the live folder (HS-1); take only
`migrationsDir` from `loadConfig({})`, as `migrate.test.ts:13` does.

## Steps
Tests first with synthetic v5, v6 and v7 databases (WAL, representative
formats, settings, notes): pending restore then snapshot then migrate;
snapshot failure (read-only safety folder) leaves schema unchanged; a
deliberately failing second migration rolls back the first; a database with
a schema version above the code's → `newer_schema`, untouched; the safety
snapshot restores to a working database; retention keeps 3.
