## Objective
Server, installer and sandbox compute the data folder with the same function,
and the three of them are *provably* that one function rather than three copies
that happen to agree: one module, one re-export from the single shared entry,
three one-line call sites, and a check a surviving local copy cannot pass. R13
is "installer has no `win32` branch" (`docs/v2/TRACEABILITY.md:23`), so the
delegation is the deliverable, not the pure function on its own.

## Fixed decisions

- **The one function, its exact signature, and how the TypeScript consumers
  reach it.** `shared/src/platform-paths.ts` exports exactly one function:

  ```ts
  export function platformDataDir(
    platform: string,
    env: Readonly<Record<string, string | undefined>>,
    home: string,
  ): string
  ```

  `platform` is a plain `string`, **not** `NodeJS.Platform`:
  `installer/src/cli.ts:43` types `platformName: string` and passes it at
  `:49`, so a `NodeJS.Platform` parameter fails V3's `typecheck` on that line
  and tempts a cast. `env` is a read-only record so `NodeJS.ProcessEnv`, the
  installer's argument and a plain object literal in a test all satisfy it
  without a conversion. `home` is a parameter, never `homedir()` read inside the
  function, so the function stays pure and the sandbox can pass `tmpdir()`.
  `shared/package.json:8-13` publishes `"."` and nothing else, and
  `shared/src/index.ts:546` says so in the repo's own words, so both consumers
  import from the package root —
  `import { platformDataDir } from '@apunta/shared';` — which is why the single
  added line in `shared/src/index.ts` is not optional, and why a deep path such
  as `@apunta/shared/src/platform-paths.js` is forbidden: it resolves to nothing
  at runtime and to nothing in `tsc`.

- **Both existing `defaultDataDir` wrappers keep their signatures and their
  exports, and become one-line calls.** This is what lets V3's `npm test` pass
  without either test file's imports changing:

  - `server/src/config.ts:138` — `export function defaultDataDir(): string`
    stays zero-argument and exported; the body becomes
    `return platformDataDir(platform(), process.env, homedir());`. It keeps
    reading `process.env`, as today, so `config.test.ts:21`'s
    `config.dataDir === defaultDataDir()` still holds. `loadConfig` keeps its own
    `resolve` at `:157-158`, so the **server's** `APUNTA_DATA_DIR` handling is
    byte-identical to today and the function's own override row never runs on
    the server path.
  - `installer/src/cli.ts:35` — `export function defaultDataDir(platformName:
    string, env: NodeJS.ProcessEnv): string` keeps both parameters and its
    export; the body becomes `return platformDataDir(platformName, env,
    homedir());`.

  Neither wrapper is deleted, renamed, given a parameter or a default, and
  neither call site (`:49`, `config.ts:158`) gains a cast. `node:path` stays
  imported in both files for their other uses (`cli.ts:60`'s flag,
  `config.ts`'s `repoRoot`), so no import is left unused.

- **The new module imports nothing — no `node:` import, `/` is the only
  separator.** `shared/src` has zero `node:` imports today and the whole barrel
  is what the browser imports (`web/package.json` depends on `@apunta/shared`;
  the web app imports the package root), so a `node:path` import inside a module
  re-exported from `shared/src/index.ts` would enter the browser graph. It would
  also make the two `win32` rows host-dependent: on this Linux box
  `resolve('C:\Users\x\AppData\Roaming')` returns a POSIX path, so a Windows row
  asserted through `join`/`resolve` is green here and wrong on Windows — the one
  platform the card exists to fix. So the module is pure string handling:

  - **Normalisation**, applied to every path input (`APUNTA_DATA_DIR`,
    `APPDATA`, `XDG_DATA_HOME`, `home`): `\` becomes `/`, runs of `/` collapse to
    one, a trailing `/` is trimmed. A non-empty contract input never normalises
    to empty.
  - Every row is then the normalised prefix plus `/` plus its segments, in the
    table's order, first match wins: override, `darwin`, `win32` with `APPDATA`,
    `win32` without, other with `XDG_DATA_HOME`, other. An empty
    `APUNTA_DATA_DIR`, `APPDATA` or `XDG_DATA_HOME` is **not** a value, exactly
    as the table's "non-empty"/"set" wording and today's two implementations
    read.
  - **The override row** wins over every other row, and its result is the
    normalised value: the contract's `resolve(...)` honoured in the sense that
    matters here (absolute, normalised, `/`-separated). An already-normal
    absolute value round-trips **byte-identically**, which is what
    `cli.test.ts:16`'s `'/tmp/y'` → `'/tmp/y'`, `sandbox.mjs:186`'s refusal and
    the selftest's `:466-477` case all depend on. `..` segments are **not**
    collapsed: the value is normalised, not resolved against a real tree.
  - **The one divergence, stated rather than hidden.** The function is pure and
    takes no working directory, so a **relative** `APUNTA_DATA_DIR` is joined
    onto `home` instead of onto `process.cwd()`. Nothing in this repository, the
    sandbox, the e2e harness or the installer writes a relative
    `APUNTA_DATA_DIR` (all of them write absolute paths), the divergence is
    recorded in the return file and in `docs/v2/evidence/P4.2/`, and if any
    caller or test turns out to depend on cwd-relative resolution that is a stop
    condition — not a licence to import `node:path` or to read `process.cwd()`
    inside the function.
  - A literal `\` inside a POSIX filename is therefore read as a separator. No
    producer in this repository creates one; it is out of scope and recorded
    here so it is a decision rather than an accident.

- **The cases, with the exact string each must produce.** Every one is a case in
  `shared/src/platform-paths.test.ts`, and every returned string is written into
  `docs/v2/evidence/P4.2/` — that record is the artifact a reviewer needs for a
  Windows path asserted from Linux, since the suite itself runs on Linux.

  | Call | Must return |
  | --- | --- |
  | `platformDataDir('linux', { APUNTA_DATA_DIR: '/tmp/apunta v2/Ω' }, '/home/x')` | `/tmp/apunta v2/Ω` (spaces and non-ASCII, byte-identical) |
  | `platformDataDir('win32', { APUNTA_DATA_DIR: '/tmp/d', APPDATA: '/appdata' }, 'C:\Users\x')` | `/tmp/d` (the override beats every platform row) |
  | `platformDataDir('linux', { APUNTA_DATA_DIR: '' }, '/home/x')` | `/home/x/.local/share/apunta` (an empty override is not an override) |
  | `platformDataDir('darwin', {}, '/Users/x')` | `/Users/x/Library/Application Support/Apunta` |
  | `platformDataDir('win32', { APPDATA: 'C:\Users\x\AppData\Roaming' }, 'C:\Users\x')` | `C:/Users/x/AppData/Roaming/Apunta` |
  | `platformDataDir('win32', {}, 'C:\Users\x')` | `C:/Users/x/AppData/Roaming/Apunta` |
  | `platformDataDir('win32', { APPDATA: '' }, 'C:\Users\x')` | `C:/Users/x/AppData/Roaming/Apunta` (an empty `APPDATA` is not a value) |
  | `platformDataDir('linux', { XDG_DATA_HOME: '/data' }, '/home/x')` | `/data/apunta` |
  | `platformDataDir('linux', {}, '/home/x')` | `/home/x/.local/share/apunta` |
  | `platformDataDir('freebsd', {}, '/home/x')` | `/home/x/.local/share/apunta` (any platform that is not `darwin` or `win32` is "other") |

- **The server's `win32`-without-`APPDATA` result moves, deliberately, and this
  card migrates nothing.** C-PATH@1's table wins for the server as well as for
  the installer: `server/src/config.ts:144` returns `<home>/Apunta` today, and
  after this card it returns `<home>/AppData/Roaming/Apunta`. The move is
  explicit, not silent:

  - it is stated here, in the return file and in `docs/v2/evidence/P4.2/`, as an
    accepted consequence of the table row, and it is the one behaviour change
    the server makes;
  - this card performs **no migration**: it never reads, lists, copies, renames
    or deletes the old folder. HS-1 forbids touching a live data folder, and
    nothing in May edit could carry an honest migration;
  - an existing Windows install therefore keeps its data in `<home>/Apunta`
    while the server looks in the new location. Carrying it over needs a
    separate card with its own owner action; this card neither creates that
    action nor decides it, and it does not edit C-PATH@1's Compatibility clause
    (HS-7).

  The server's Linux and macOS results are unchanged, as the contract requires.
  The installer's Windows result changes from the Linux-style path to the
  table's two rows — that is the defect R13 names.

- **How the dependency-free sandbox consumes the TypeScript.**
  `scripts/v2/sandbox.mjs` keeps its header promise (`:21`, "**No
  dependencies.** Loopback only") and imports the TypeScript **source**, never
  the build:

  ```js
  import { platformDataDir } from '../../shared/src/platform-paths.ts';
  export { platformDataDir };
  ```

  - Node 24.19.0 strips the annotations itself, so `run`, `env` and `selftest`
    work on a clean worktree with no `shared/dist`. Importing
    `../../shared/dist/platform-paths.js` instead would make the live-data guard
    depend on a build artefact that `.gitignore:2` keeps out of the tree, and a
    stale `dist` would guard with logic `src` no longer has — so V2 deletes
    `shared/dist` first, and a V2 that passes with `dist` present proves
    nothing.
  - Because `node` runs the file directly, `shared/src/platform-paths.ts` must
    stay **erasable-syntax-only**: type annotations, `type` and `interface` are
    fine; `enum`, `namespace`, parameter properties and anything else that needs
    emit are not, and would make the sandbox fail to start.
  - `platformDataDir` **stays exported** from `sandbox.mjs`:
    `scripts/v2/sandbox.test.mjs:140` does
    `const { platformDataDir } = await import('./sandbox.mjs')` and V2 runs that
    file, so dropping or renaming the export fails the row. That test file is
    not in May edit and is not modified to accommodate anything.
  - The refusal at `:186-188` compares the two sides **after normalising both
    the same way**: the function returns `/`-separated strings while
    `resolve(raw)` at `:178` returns native separators, so on Windows a
    native-separator `dataDir` would otherwise stop matching a `/`-separated
    `def` and the guard would silently stop refusing. It still compares **as a
    string only** and never lists or opens the default folder (C-ISO@1).

- **Packaging and dependencies are untouched.** The installer already depends on
  `@apunta/shared` (`plan.ts:1`, `catalog.ts:7`) and
  `installer/src/containment.test.ts:71-75` pins its dependency list to exactly
  `['@apunta/shared', 'zod']`; this card adds none. `scripts/package-mac.sh:235-237`
  bundles `installer/dist/main.js` with esbuild, so the new shared import is
  inlined into `setup.mjs`; the server bundle is unaffected because the server
  imports nothing new.

  That is a trigger for a card amendment about the shape, never a licence to add
  the import here.

  overload to compile: the parameter is `string` and stays `string`
  (`cli.ts:43`). Record the site and the error.
- V1's second `rg` matches one of the three consumers: a surviving local copy of
  the table, which is the defect this card exists to remove. Do not fix it by

- Deleting or renaming `defaultDataDir` in either file, or changing either

- Any caller or test depends on a **relative** `APUNTA_DATA_DIR` resolving

  in this card (HS-7, HS-9).
- Anyone proposes moving, merging or copying an existing Windows `<home>/Apunta`

  (HS-1).
