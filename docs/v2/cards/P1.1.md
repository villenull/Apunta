## Fixed decisions
C-SETTINGS@1 in full, with these readings of it.

- **`update()` shape.** `update(patch: UpdateSettingsRequest): Promise<void>`.
  It applies `patch` to the provider's state immediately, calls `putSettings`,
  resolves on success and **rejects with the API error**. That rejection is the
  only failure channel: the provider holds no error state, so each control
  keeps its existing `error` / `role="alert"` block unchanged
  (`web/src/routes/Settings.tsx:356-360` and `:556-560`), and the contract's
  "the control shows the existing error message style" is that block.
  `putSettings` resolves the whole `Settings` record
  (`web/src/api/settings.ts:11`); `update()` does not hand it back, because no
  control resyncs from it.
- **Scope.** The controls that move to `update()` are the Appearance card's —
  `accent-color`, `reset-accent`, `theme-{option}`, `font-size-{size}`,
  `animations-toggle` — and the Drafting model control,
  `llm-profile-{profile}`. All of them are in `web/src/routes/Settings.tsx`; the
  two `putSettings` call sites are `:324` and `:422`. Nothing else moves.
- **The spelling-words save stays as it is.**
  `web/src/components/SpellingProvider.tsx:99` is the only other `putSettings`
  caller, it persists `SPELLING_WORDS_SETTING`, and it keeps the saved list in
  local state — so the fourth bullet ("no control keeps a persisted setting in
  local component state as its source of truth") does reach it. It is
  deliberately **not** in this card's write scope: it is not a Settings control,
  nothing on any page is painted from it, and its failure behaviour is
  intentionally different (the click stands for the tab, per the comment on that
  line), so moving it would change behaviour that neither contract example
  covers. If you read that bullet as binding on it, stop, record it as a finding
  in the return file and leave the file alone: that is a contract-scope question
  for the coordinator, not this card's to settle.
- **Radio groups** stay `role="radio"` buttons with a roving `tabIndex`; they do
  not become `<input type="radio">`. The Drafting model group
  (`web/src/routes/Settings.tsx:335-354`) **is** in scope for the radio bullet
  and gains the same `tabIndex` handling the theme and font-size groups already
  have (`:610`, `:508`): today it sets no `tabIndex` at all, so Tab enters the
  group at the first option instead of the selected one. That is the violation,
  and fixing it is this card's work. P1.2 owns the theme group's own keyboard
  behaviour.
- **Language** is a later consumer (S2.6) and is not added here; no Language
  control exists at base.
- **Toolchain.** Every row runs with the provisioned Node first on `PATH`:
  `export PATH="$HOME/.local/share/apunta-node/node-v24.19.0-linux-x64/bin:$PATH"`,
  which gives `node --version` → `v24.19.0`. This box's default Node is v26.8.2,
  outside `engines: ">=24.19.0 <25"`. V1 and V2 carry the export in the row
  itself; export it in the same shell before V3 and V4.
- **Port and browser for V1/V2.** Both rows use this card's assigned port
  **7811**, not the 7810 literal in RUN-CONFIG §3 — 7810 is held by another
  session's preview server and C-ISO@1 rule 2 refuses a port that is not free.
  This box has no Playwright browser (`~/.cache/ms-playwright` does not exist),
  and `e2e/playwright.config.ts:21` only sets `launchOptions.executablePath` when
  `PLAYWRIGHT_CHROMIUM_EXECUTABLE` is present, so both rows set it to the system
  Chromium (`/usr/bin/chromium`, 152.0.7977.82).

## Known facts
The provider loads once per mount and exposes only `reload`; controls call
`putSettings` and keep local state; returning to Settings remounts the
controls from stale provider data. A reload hides the bug. The three direct
`putSettings` callers under `web/` are `web/src/routes/Settings.tsx:324`
(Drafting model), `web/src/routes/Settings.tsx:422` (Appearance) and
`web/src/components/SpellingProvider.tsx:99` (spelling words). Appearance is the
default Settings section (`web/src/routes/Settings.tsx:95`).

## Steps
1. Write `e2e/tests/settings-appearance.spec.ts`, every `test()` titled
   `settings appearance: …` (V1 and V2 filter on that prefix). The first test
   is the C-SETTINGS@1 Normal example with no reload in the middle: on
   `/settings` click `[data-testid="theme-light"]`, navigate to `/` and back to
   `/settings` **without reload**, then assert `[data-testid="theme-light"]`
   carries `aria-checked="true"` and
   `document.documentElement.dataset.theme === 'light'` — the selected segment
   is derived from provider state, so that pair *is* the "provider value light"
   half of the contract — then `page.reload()` and assert light again. Run it
   and record that it fails on this commit.
2. Add unit tests in the two new test files for: the optimistic update (the
   control and the painted `data-theme` change before the promise settles);
   rollback on failure (a rejected `putSettings` puts
   `document.documentElement.dataset.theme` back to `dark`, a `role="alert"`
   error is visible, and the control is not left claiming Light); out-of-order
   responses (an older response for a key is ignored and the newer value stays);
   and the radio bullet (ArrowRight and ArrowLeft move and select within the
   Drafting model group, and Tab enters it at the selected option).
3. Implement `update()` with a per-key sequence number and move the covered
   controls to it, giving the Drafting model group the roving `tabIndex`.
