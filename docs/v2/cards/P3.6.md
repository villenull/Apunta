## Fixed decisions

- **Rule B — what makes an AppImage stale. One statement of the set: V0's and
  V1's producer invocation, V3's precondition and the resume anchor refer to
  this bullet and name no path of their own.** `src-tauri/tauri.conf.json`
  `bundle.resources` ships `build/linux-resources/`, and that folder is produced
  by `scripts/v2/package-linux-resources.sh`, which **rebuilds the server and the
  web app itself**. **A server-side change and a web-side change therefore make
  the AppImage stale exactly as a Rust change does**, and `npm run tauri:build` /
  `npm run tauri:build:test` **alone refresh neither**: `tauri.conf.json` declares
  no `beforeBuildCommand`, so `tauri build` copies whatever `build/linux-resources/`
  already holds. **That is verbatim the defect that cost P3.4 an attempt** — its
  attempt 1 launched a binary whose bundled server predated the card's own
  source — and V0 and V1 exist so this card cannot repeat it. The set is
  P3.4's, unchanged: `server/src/**`, `shared/src/**`, `server/package.json`,
  `server/migrations/**`; `src-tauri/**` excluding `src-tauri/target/` and
  `src-tauri/gen/`; and `web/src/**`, `web/public/**`, `web/index.html`,
  `web/vite.config.ts`, `web/package.json`, the root `package.json` and
  `package-lock.json`. **Never inputs, only outputs:** `build/linux-resources/**`,
  `server/dist/**` and `web/dist/**` are what the producer rewrites — a stale one
  of those is the symptom Rule B detects, never a trigger. **P3.6 adds nothing to
  this set and restates none of it:** P3.4 owns the statement, and this card
  refers to it rather than forking it, because two copies of the set would drift
  and the copy that drifts is the one that ships a stale bundle.
- **There is no `package:linux` script, so the literal producer invocation is the
  only correct one.** `bash scripts/v2/package-linux-resources.sh` is what V0 and
  V1 run, and adding a wrapper would be an edit to `package.json`, which is not in
  May edit.
- **V0 is the producer, and the build is its second half.** A bare
  `npm run tauri:build` with no producer in front of it is the D3 defect and is
  not a row this card is allowed to write; a bare producer with no build after it
  is equally wrong, because then V3 has no test AppImage and V1 has no
  production one.
- **The harness launches the binary; it does not re-implement a flow.** V3's
  script is one mode, `smoke`, and any other argument exits 2 (P3.4's `security`
  shape). It resolves `src-tauri/target/release/bundle/appimage/*.AppImage` **once**
  and fails with the directory listing if the glob matches zero or more than one
  file, so a stale AppImage from another card's run cannot be launched silently;
  the filename contains a space (`Apunta (test)_0.0.0_amd64.AppImage`), which is
  why it resolves the glob and never assembles the name. It captures both pipes,
  stops the child **by pid** on every path, and reads its assertions from the
  accumulated stderr buffer rather than from any tail it prints at the end.
- **What the ten flows are, and what a flow completing means.** Onboarding,
  capture (fixture), draft, refine, publish and copy, patient list, plan,
  briefing, brainstorm, settings, backup — the same list the card has always
  carried, unchanged. A flow **completes** when the app reached the next screen
  and the harness read the fact proving it, through P3.4's observation hook where
  one exists and otherwise through the app's own API over the sandbox origin. A
  screenshot is evidence, never the assertion: **a screenshot of a screen that was
  never reached is a `FAIL`, not a pass**, and no flow is recorded `PASS` on a
  picture alone.
- **`NOT RUN` is never `PASS`.** A flow that could not be driven — no window, no
  reply from the hook, a tool absent from the machine — is `NOT RUN` with its
  cause, and a `NOT RUN` blocks approval pending a coordinator decision. **Zero
  windows found on the display is `NOT RUN`**, never a pass, for P3.8's reason: an
  empty window list is indistinguishable from a row that observed nothing.
