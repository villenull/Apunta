## Objective
`scripts/v2/package-linux-resources.test.sh`'s SPA check can no longer pass on
a bundle that contains no JavaScript, and the assertion that does the work is a
**content type**, not a byte count.

P3.1's Step 3 fixed the check as "`GET /` is 200 with `content-type: text/html`
and a non-empty body … an empty or truncated copy of `web/dist` must fail here
rather than in a person's browser" (`docs/v2/cards/P3.1.md:304-307`). The
implementation review returned **PASS** and found that the check cannot do the
second half of that sentence. All three SPA assertions inspect `GET /` only
(`:429-448`), and `index.html` survives `rm -rf web/dist/assets` intact, so
`spa-status`, `spa-content-type` and `spa-body` **all pass on a bundle with no
script and no fonts in it** (`P3.1-impl.md:46-56`). The review demonstrated it,
judged it major, and carried it forward rather than blocking; P3.1's green does
not close it (`P3.1-impl.md:186-190`).

This card adds the one assertion that was missing. It changes nothing else.

## Fixed decisions
1. **One check, named `spa-asset`, placed immediately after `spa-body`** (so
   between `:448` and `:450`) and before the whisper check. It fetches **the
   one hashed script the served shell actually references** and requires the
   following of that response:
   - the reference is **found**: the `src="…"` attribute is extracted from the
     **served** `GET /` body (the `$ROOT_BODY` the script already captured at
     `:429-430`, not the file on disk, so the shell and the server are proven to
     agree). Exactly one `src="` is expected. **Zero, or more than one, is a
     `FAIL spa-asset` with the count in the detail — never a skip and never a
     pass**, because a check that quietly finds nothing is the defect this card
     exists to remove.
   - `GET <that path>` answers **200**.
   - its `content-type` contains `javascript`.
   - its body length, **counted in bytes**, equals the `bytes` `manifest.json`
     records for that path (Fixed decision 3).
   The failure detail names which of these failed and prints the observed
   status, content type and byte count, so a reviewer reads the reason from the
   row's own output.

   Two things the comparison is **not**, both because the file's own idiom is the
   trap. The length is **bytes the server sent, not characters of a shell
   variable**: the asset body is written to a file in the run folder and measured
   with `wc -c <file>` or `curl -o <file> -w '%{size_download}'`, never with
   `${#VAR}`. Under the run's `LANG=en_US.UTF-8` `${#VAR}` counts characters, and
   on the bundle on disk today the two readings differ — `index-D7iOgJVA.js` is
   169523 bytes and 169480 characters — so mirroring `spa-body`'s
   `${#ROOT_BODY}` (`:444`) would `FAIL spa-asset` on a **perfect** bundle. The
   manifest is read from the bundle under test, keyed on `web/dist` + the served
   path; a path the manifest does not list is `FAIL spa-asset` with the path in
   the detail, which is Stop condition 3's case stated in the check rather than
   only in the stop list.

   **The success path prints the four values too**, as one informational line
   that is **not** prefixed `PASS ` and does not go through `pass()` — e.g.
   `spa-asset /assets/index-D7iOgJVA.js 200 application/javascript 169523`, in
   that order, separated by single spaces. `pass()` prints the name alone
   (`:37-39`) and is not changed, so this is the one extra line the check is
   allowed to print; it exists because the row's acceptance and the return file
   both ask for those four values, and they have to reach the evidence from
   somewhere. One line, only on success, never `FAIL`-prefixed.
2. **`server/src/app.ts` is not changed, and the content-type assertion is what
   carries the check.** This is worth stating plainly because the review
   suggested the static handler would also have to change
   (`P3.1-impl.md:64-67`): it does not, and it must not. The fallback answers a
   missing asset `200 text/html`, and a real one `200 application/javascript`,
   so the content type alone separates a truncated bundle from a good one — the
   control returned 1265 bytes of HTML where a real asset returned 169523 bytes
   of JavaScript. A future implementer who "fixes" the fallback to return
   `404` for unmatched asset paths would change what a reload of a client-side
   route does — that fallback is why `/patients` resolves on a fresh load — and
   it would buy this row nothing it can measure, because the content type
   already discriminates. Do it and it is a Stop condition.
3. **The length assertion is the bundle's own record, not a constant.** The
   expected size is the `bytes` value `manifest.json` records for that exact
   path, read from the bundle under test with the bundled `node` (the way the
   script already reads JSON at `:64-67`). Two reasons, both load-bearing. The
   manifest is P3.1's record of the bundle and is already inside the folder
   being tested, so this invents nothing. A hard-coded floor **would** be a new
   threshold, and HS-7 forbids inventing one inside a card; the review's
   169523 bytes is one measurement of one build, not a rule, and a floor under
   it would pass a half-copied bundle. The manifest's symlink convention
   (review finding 4) does not apply here: a Vite asset is a regular file, so
   its `bytes` is the file's own length.
4. **The check reads the served shell, so a bundle whose `index.html` and
   `assets/` disagree cannot pass.** Asserting against a file on disk would let
   a shell that references a script the bundle does not contain pass, which is
   the browser-side failure the card exists to move off the person.
5. **One `PASS` line, so the count is a tripwire.** The script prints
   `PASS spa-asset` once, and nothing else on the success path carries the
   `PASS ` prefix — the informational line Fixed decision 1 specifies does not
   touch the count. At this card's base the file prints **28** `PASS`
   lines; after this card it prints **29**, with the 28 pre-existing names in
   the same order and none weakened. A run that prints 28 means the check was
   never added, and that is `FAIL`, not `PASS` — the P4.5 V1 shape.
6. **Nothing about the launch changes.** Same `sandbox.mjs env` run, same
   relocation, same `env -i` launch under the bundled Node, same port from
   `APUNTA_P31_PORT`, same ownership poll before the first assertion, same rule-7
   shutdown, same missing-SQLite negative case, same exit-1-on-first-failure.
   The script still fails at the **first** failure, which is why the control
   stops at `spa-asset` and never reaches the whisper check.
7. **The card is L1 and offline.** It edits one test file, changes no
   production code, and needs no new build, no model, no vendor and no
   acquisition. It does launch a server on a dispatch port, exactly as the L1
   cards P2.2, P3.2, P4.1 and S2.1 do, so the dispatch assigns a port from 7800
   to 7889 and 7717 is never contacted. The one level it does **not** claim is
   the reason it does not run `scripts/v2/package-linux-resources.sh`: that
   script is L3 because it compiles whisper, and P3.1 review finding 2 records
   that it re-fetches A06 from `github.com` on **every** run. A re-run of it
   here would be a second fetch this card has no authorisation for. If
   `build/linux-resources/` is absent, the rows are `NOT RUN` and the
   coordinator re-runs P3.1's V1 — never this card (Stop condition 3).

6. **V1, V2 or V3 fails in a file outside May edit** — including a prettier or
