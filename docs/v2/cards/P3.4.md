## Fixed decisions
C-BRIDGE@1 rules 4, 5, 6, 7. Extra CSP sources only with a failing test as
evidence.

- **The CSP is registered as an `onSend` hook**, beside the existing `onRequest`
  guard, in **both** servers — `buildApp` in `server/src/app.ts` and
  `buildBootErrorApp` in `server/src/boot-error.ts` — by one exported function
  from `server/src/http/csp.ts`. An `onSend` hook sees the finished payload and
  the reply's status, which is what "every HTML response" needs: it cannot tell a
  static file from the SPA fallback or the boot page by route table, but it can
  tell a `text/html` response from JSON. `onRequest` would be wrong (the reply
  does not exist yet); a per-route `reply.header` would put the header inside
  route bodies, which Must not edit forbids.
- **The minimum set is rule 6's six directives, exactly** — `default-src
  'self'`, `script-src 'self'`, `connect-src 'self'`, `object-src 'none'`,
  `base-uri 'none'`, `frame-ancestors 'none'` — and nothing weaker. `style-src`
  is **not** in rule 6, so with no `style-src` inline styles fall back to
  `default-src 'self'` and are blocked.
- **The boot-error page's inline `<style>` is authorised by a per-response
  nonce, not by `'unsafe-inline'`.** `server/src/boot-error.ts:46` carries
  `<style>body{…}</style>` inside the document, and rule 7's bilingual error
  screen is worthless unstyled. So `csp.ts` generates a fresh nonce per
  response, emits `style-src 'self' 'nonce-<that nonce>'`, and
  `bootErrorHtml` puts the same nonce on the `<style>` element as
  `nonce="<that nonce>"`. **V1 asserts the nonce form and asserts that
  `'unsafe-inline'` appears nowhere** — in `csp.ts`, in the test, or in any header.
  The alternative rule 6 and the stop condition allow — `style-src
  'unsafe-inline'`, justified by a failing test submitted **first** — is **not**
  the decision this card makes; if the nonce form turns out not to work on this
  stack, that is a stop condition, not a licence to switch (see Stop
  conditions). No `script-src` relaxation is contemplated: the boot page has no
  inline `<script>`.
- **`src-tauri/ui/error.html` is out of rule 6's reach and out of scope.**
  `tauri.conf.json:13` sets `"csp": null`, so Tauri injects no CSP into that
  asset window, and C-BRIDGE@1 rule 6 is a rule about what **the server** sends.
  Its inline `<style>` and `<script>` (`src-tauri/ui/error.html:20,93`) therefore
  need nothing here. Do not add a CSP, do not move the file, do not widen this
  card into `src-tauri/ui/` — the `**` in May edit is written as `src-tauri/**`
  **except** `src-tauri/ui/` for that reason.
- **Which responses carry the header** (N2): every `text/html` response, and only
  those — the static `index.html` served by `@fastify/static`, the SPA fallback
  `sendFile('index.html')` at `app.ts:163` (so `GET /patients`, the note view's
  URL, carries it), any stray `.html` asset, and the boot page's `/` at
  `boot-error.ts:66` and its non-`/api` not-found HTML at `:69`. **JSON, SSE and
  the `/api` 404 JSON carry no header** (`app.ts:156-162`, `boot-error.ts:67,70`):
  they are not HTML, adding one would be scope, and V1 asserts their absence so
  "the header is on HTML" is a property and not "the header is on everything".
- **The new work is the server CSP and the harness.** At `07dce9c` the shell
  side already satisfies rule 4 and rule 5: `withGlobalTauri: false`, `"csp":
  null`, `"capabilities": []`, no `src-tauri/capabilities/` directory, and the
  two navigation guards with their Rust unit tests. **No CSP string exists
  anywhere in `server/src` today.** A `src-tauri/**` edit is therefore expected
  only if V2 shows the guards do not hold in the shipped binary; V0 exists for
  that case and V2's freshness anchor exists because of it.

## Stop conditions
The installed Tauri version cannot load an `http://127.0.0.1` URL in the main
window without granting it capabilities: stop and report (E3 forbids
capabilities).

The app needs a CSP relaxation the contract does not list: submit the failing
test as evidence and stop for the coordinator. **The per-response nonce is the
decision, so a request to replace it with `style-src 'unsafe-inline'` is this
stop condition**, not an implementer's choice — and if the nonce form cannot be
made to work on this stack, that is likewise a stop and a report, never a silent
switch to `'unsafe-inline'` after the fact.

The WebKitGTK inspector on 7836 cannot be reached from the harness, so V2(a) and
V2(c) cannot be read in-page: record those sub-assertions `NOT RUN` with that
cause, never `PASS`, and report it to the coordinator rather than substituting a
config-level reading of rule 4.
