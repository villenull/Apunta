# P3.8 The reader keeps forwarding the child's stdout after `ready`

| Field | Value |
| --- | --- |
| Parent | P3 |
| Role | IMPLEMENTATION |
| Level | L3 |
| Contracts | C-BRIDGE@1 |
| Depends | P3.3 |
| Findings | R04, R05 (P3.3's — this card changes the code those two findings produced) |
| Confidence | reproduced in source at this card's base: `src-tauri/src/main.rs:298` breaks the read loop the moment `ready` has been handled, so the forwarding arms at `:318-325` are unreachable after that point |

## Objective

**One behaviour:** after the `ready` line has been handled, `drive` keeps
forwarding the bundled server's unrecognised stdout lines to stderr, until the
child exits or the window closes — instead of leaving the loop at that instant.

Nothing else changes. The single navigation stays single, the early-exit path
stays an early exit, the error screen stays an error screen, and the
`settled` bookkeeping keeps deciding exactly what it decides today.

### Why this card exists, and why the defect is real

`docs/v2/state/AMENDMENTS.md` row **AM-138** records the owner's decision and the
diagnosis; this card is the work that decision authorises. The defect, verified
against the file at this card's base:

- The reader thread (`main.rs:240-252`) drains the child's **stdout** line by
  line and sends every line on as `Event::Bridge(parsed, line)`. That part is
  correct and is not this card's business.
- `drive` (`main.rs:284`) iterates that channel. Its two forwarding arms —
  `Event::Bridge(Ok(Message::Other { kind }), _)` at `:318-320` and
  `Event::Bridge(Err(rejection), line)` at `:321-325` — both `eprintln!` to
  stderr and both fall through to the next line. **These arms are the delivery
  chain, and they work** (P3.4's AM-131 recorded it working in attempt 2).
- The `ready` arm at `:291-306` calls `show_main`, closes the splash, sets
  `settled = true`, and then **exits the loop**:

  > ```rust
  >                 if show_main(&handle, port) {
  >                     close_window(&handle, "splash");
  >                     settled = true;
  >                     break;
  >                 }
  > ```
  > — `src-tauri/src/main.rs:295-299`

  Every line the child writes from that moment on is read off the pipe by the
  reader thread, pushed onto a channel whose only receiver has left, and
  dropped. `drive` then parks in the tail loop at `:354-360`, which does
  `Ok(_) => continue` — it **discards** what arrives.

So the chain is intact at both ends and severed in the middle. P3.4's
observation hook (`docs/v2/cards/P3.4.md:542`, V2's channel description) can
only publish once the page exists, and the page only exists after `ready`, so
its in-page assertions can never be observed: **five `NOT RUN` assertions, and
P3.4 BLOCKED at 3/3.**

The remedy is one line's worth of control flow. It is a change to a lifecycle
loop, which is exactly the kind of change that passes a smoke test and breaks
the thing the loop exists for — so this card's rows are built around that, not
around the fix.

## Fixed decisions

1. **The change is the removal of the success-path `break`, and nothing that
   could reasonably be called more than that.** After `show_main` succeeds the
   `ready` arm falls through to the next event like every other arm. The
   `settled = true` assignment **stays**, because `settled` is what tells the
   `:340-348` tail that the launch succeeded and must not paint an error
   screen over a working app.
2. **The `break` at `:305` — the window-would-not-open path — stays exactly as
   it is.** That arm is C-BRIDGE@1 rule 7's shape: an error screen rather than
   a splash that never resolves, and then the shell is done. Removing it would
   leave the shell forwarding lines from a server nobody is looking at, behind
   an error window, for the rest of its life. Only the **success** `break` goes.
3. **`show_main` is called at most once in the process lifetime, and this is
   asserted, not asserted-in-a-paragraph.** V4 counts the navigations and the
   window shows and fails the row if either exceeds one. C-BRIDGE@1 rule 1
   makes the single navigation load-bearing: a second `show_main` after `ready`
   is a re-navigation, which is Stop condition 1 and a contract break
   regardless of how the row's other assertions read.
4. **`Ready` is never swallowed.** The `eprintln!` at `:292` fires on every
   `ready` line the child writes, whether or not the loop then continues. A
   change that keeps forwarding but drops or defers that line has broken
   P3.4's harness's ability to find the boundary between "before ready" and
   "after ready", and V3 and V4 both assert the `ready` line is present on
   stderr **before** the marker line.
5. **stderr is the only destination.** No new file, no log file, no ring
   buffer, no IPC, no environment variable, no new capability. The forwarding
   is `eprintln!`, which is what `:318-325` already does and what P3.4's
   harness already reads. This defect is fixed by *not stopping*, not by
   *adding a channel*.
6. **The child and the reader thread must stay distinguishable at shutdown.**
   Today `ChildGone` after a successful `ready` is discarded by the tail loop's
   `Ok(_) => continue`, which is correct. Once the loop keeps forwarding, a
   `ChildGone` arriving **after** a settled `ready` must still not paint an
   error screen over a running app whose server has just exited — and a
   `ChildGone` arriving **before** any `ready` must still paint one, because
   that is C-BRIDGE@1 rule 7's early exit. Both halves are asserted in V4. If
   the change cannot tell those two apart, that is Stop condition 3.
7. **The end-to-end row's publisher is a route that already exists, driven by
   the server's own request logger — no server edit, no new route, no marker in
   the bundle.** The bundled server runs Fastify with `logger: true`
   (`server/src/app.ts:70`), so **every request's URL is written to the child's
   stdout (fd 1)** by the request logger; that is the same channel P3.4's hook
   uses, and P3.4's own card says so. V3 therefore drives `GET /api/health` with
   a run-unique query string, **after** the app window is up, and asserts the
   marker reaches stderr. The route exists, the logger exists, and neither is
   touched. **If the observed line does not name the request at all**, that is a
   finding for the coordinator and Stop condition 2 — the card may **not**
   respond by adding a log line, a route, an env var or a build flag.
8. **Every C-BRIDGE@1 rule still holds, and V1 re-runs the tests that hold
   them.** The thirteen `#[test]` cases in `mod tests` (`main.rs:705` onward) are
   unchanged and are re-run by V1: they carry P3.3's navigation guards
   (`main.rs:486-487`, rule 5), the nonce and protocol checks on the bridge
   parser (rule 1), the unknown-type handling (rule 2), and the code-to-word
   mapping. **V1 runs `cargo test` and it must report the same thirteen passing
   and zero failing — no test is deleted, renamed, `#[ignore]`d, or loosened to
   accommodate the change.** A lifecycle change that needs a weakened guard is a
   stop.
9. **This card is L3 and offline.** It compiles Rust and it launches a built
   binary — the same weight P3.3 and P3.4 carry, in the same directory — but it
   acquires nothing, needs no model and contacts no host beyond the loopback
   sandbox port (HS-1, HS-3). It does **not** re-bundle
   `build/linux-resources/`: `tauri.conf.json` declares no `beforeBuildCommand`
   (which is why that file stays out of May edit), so V0's build consumes the
   bundle already on disk. If that folder is absent, V0 and the launching rows
   are `NOT RUN` and the coordinator runs P3.1's V1 — never this card.

## Stop conditions

1. **A change that would re-navigate after `ready`.** Anything that can call
   `show_main`, `close_window` or `show_error` a second time on a path reachable
   after the first `ready` — re-navigating on every forwarded line, re-showing
   the main window per line, treating a later `Ready` as a fresh launch. C-BRIDGE@1
   rule 1 makes the single navigation load-bearing, and V4(a)/(b) are the
   assertions. Stop and report; do not "make it idempotent".
2. **The fix needs anything outside `drive`.** In particular: a capability or a
   `tauri.conf.json` edit; a `server/` change to make a line appear (a new log
   line, a new route, a new env var, a build flag); a new harness or test file;
   a change to the reader thread at `:236-252`; or a re-bundle.
   **If the loop turns out to need more than the forwarding loop, that is a
   finding to report, not a scope to widen into** — the card says "report rather
   than widen" precisely because the obvious-looking widening is the one that

3. **The child cannot be distinguished from the reader thread at shutdown.**
   Once the loop keeps forwarding, `ChildGone` arrives on the same channel as
   every line, after `ready` as well as before it. If the change cannot both
   keep painting an error screen on a **pre-`ready`** exit and keep **not**
   painting one on a **post-`ready`** exit, the shell has lost the distinction
   that C-BRIDGE@1 rule 7's early exit depends on. Stop and report; do not
   resolve it by re-navigating or by suppressing the error screen.
4. **`Ready` cannot be kept on stderr while forwarding continues**, or the
   ordering between the `ready` line and a later line cannot be observed.
   P3.4's harness reads both, and a channel that reports the second without the
   first cannot be read at all.
5. **V1 is red in `main.rs`, in any of the thirteen tests.** Report and stop. A
   navigation guard, a nonce check or an unknown-type arm that has to be
   weakened for this change to compile is a stop (Fixed decision 8).
6. **`build/linux-resources/` is absent**, so V0 and the launching rows cannot

7. **V2's file list names a second path**, or a lint/typecheck failure lands in

   this plan.
8. **The app cannot be observed from outside** — no display, no `xvfb-run`, no
   window title or geometry readable. Then V3 and V4 are `NOT RUN` with that
   cause and the card **does not** fall back to asserting the behaviour from the
