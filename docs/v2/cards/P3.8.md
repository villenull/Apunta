# P3.8 The reader keeps forwarding the child's stdout after `ready`

| Field | Value |
| --- | --- |
| Parent | P3 |
| Role | IMPLEMENTATION |
| Level | L3 |
| Contracts | C-BRIDGE@1, C-ISO@1 |
| Depends | P3.3 |
| Findings | R04, R05 (P3.3's — this card changes the code those two findings produced) |
| Confidence | reproduced in source at this card's base: `src-tauri/src/main.rs:298` breaks the read loop the moment `ready` has been handled, so the forwarding arms at `:318-325` are unreachable after that point — and the `ChildGone` arm at `:326-336` has no `settled` test, while the `!settled` tail at `:340` shows the author knew the pattern |

## Objective

**One behaviour:** after the `ready` line has been handled, `drive` keeps
forwarding the bundled server's unrecognised stdout lines to stderr, until the
child exits or the window closes — instead of leaving the loop at that instant —
**and every line a run can produce after the `ready` has settled is logged and
ignored: a `ChildGone`, a `fatal`, an `Other`, a `Rejection` — with the `ready`
line itself still exactly one.** The second clause is not a second behaviour: it is what the first one
costs. Keeping the loop alive makes the `ChildGone` arm reachable at every
ordinary server exit, and that arm (`main.rs:326-336`) calls `show_error` with no
`settled` test, so a normal post-`ready` exit would paint
`Apunta — exited_before_ready` over a working app unless the arm is guarded.

Nothing else changes. The single navigation stays single, the early-exit path
stays an early exit, the error screen stays an error screen, and the
`settled` bookkeeping keeps deciding exactly what it decides today.

### Why this card exists, and why the defect is real

`docs/v2/state/AMENDMENTS.md` row **AM-138** records the owner's decision and the
diagnosis; row **AM-140** is the authorisation for this card and it names both
contracts and the mandatory negative-control row. The defect, verified against the
file at this card's base:

- The reader thread (`main.rs:240-252`) drains the child's **stdout** line by
  line and sends every line on as `Event::Bridge(parsed, line)`. That part is
  correct and is not this card's business.
- `drive` (`main.rs:284`) iterates that channel. Its two forwarding arms —
  `Event::Bridge(Ok(Message::Other { kind }), _)` at `:318-320` and
  `Event::Bridge(Err(rejection), line)` at `:321-325` — both `eprintln!` to
  stderr and both fall through to the next line. **These arms are the delivery
  chain, and they work** (P3.4's AM-131 recorded it working in attempt 2).
- The `ready` arm at `:291-306` calls `show_main`, closes the splash, sets
  `settled = true`, and then **exits the loop**:

  > ```rust
  >                 if show_main(&handle, port) {
  >                     close_window(&handle, "splash");
  >                     settled = true;
  >                     break;
  >                 }
  > ```
  > — `src-tauri/src/main.rs:295-299`

  Every line the child writes from that moment on is read off the pipe by the
  reader thread, pushed onto a channel whose only receiver has left, and
  dropped. `drive` then parks in the tail loop at `:354-360`, which does
  `Ok(_) => continue` — it **discards** what arrives.

So the chain is intact at both ends and severed in the middle. P3.4's
observation hook (`docs/v2/cards/P3.4.md:542`, V2's channel description) can
only publish once the page exists, and the page only exists after `ready`, so
its in-page assertions can never be observed: **five `NOT RUN` assertions, and
P3.4 BLOCKED at 3/3.**

And the fix has a price, which the base file already shows: the same loop's
`ChildGone` arm is unconditional, so removing the `break` hands it every ordinary
exit. The remedy is two parts of one control-flow change, both inside `fn drive`
— see May edit and Fixed decision 1.

## Fixed decisions

1. **The change is two named parts of one control-flow decision in `fn drive`,
   and nothing that could reasonably be called a third.**
   **(i) Remove the success-path `break` at `:298`.** After `show_main`
   succeeds the `ready` arm falls through to the next event like every other
   arm. The `settled = true` assignment **stays**, because `settled` is what
   tells the `:340-348` tail that the launch succeeded and must not paint an
   error screen over a working app — and it is now also the input to part (ii).
   **(ii) Make the `ChildGone` arm a no-op once `settled` is already true** —
   log it, and do **not** `show_error`, do **not** `close_window`, and either
   `continue` or leave the loop without painting.
   *Why (ii) is not optional, and why it is not scope creep:* with (i) alone,
   the next event the loop receives is the `ChildGone` the reader thread sends
   the moment `child.wait()` returns (`main.rs:250-251`) — which is what it
   sends whenever the child exits, including the ordinary case of a server that
   was working and then stopped. That arm (`main.rs:326-336`) is unconditional
   today, so (i) alone paints `Apunta — exited_before_ready` over a healthy app
   on a normal shutdown. Fixed decision 6, V4(e), V4(f) and AM-140's "not
   painted when it dies after" all forbid that, and the coordinator confirmed the
   missing `settled` test in source. Both parts live in the **same file and the
   same function**, which is where AM-140's "exactly the forwarding loop in
   `src-tauri/src/main.rs`" is satisfied. Anything beyond these two parts is Stop
   condition 3.
2. **The `break` at `:305` — the window-would-not-open path — stays exactly as
   it is.** That arm is C-BRIDGE@1 rule 7's shape: an error screen rather than
   a splash that never resolves, and then the shell is done. Removing it would
   leave the shell forwarding lines from a server nobody is looking at, behind
   an error window, for the rest of its life. Only the **success** `break` goes.
3. **`show_main` is called at most once in the process lifetime, and this is
   asserted, not asserted-in-a-paragraph.** V4(a) counts the shell's own
   `apunta: the main window is open on …` stderr lines (`main.rs:517`, written
   by `show_main` on success) and fails the row unless there is exactly one
   across the whole run; V4 also counts the `ready` line. The count is the
   assertion because a second `show_main` cannot be **silent**, not because it
   cannot be built: a duplicate call **does** compile — the window label is a
   runtime string, and `main.rs:469` is only the `WebviewWindowBuilder::new(`
   call — but the label `main` is already taken at `main.rs:471`, so the second
   `build()` returns `Err`, `show_main` takes its `Err` branch (`main.rs:519`,
   `apunta: the main window could not be opened: …`), returns `false`, and the
   `ready` arm then falls into its `:302` failure path and paints
   `the_window_would_not_open`. That is why V4(a) counts the success line rather
   than trusting compilation, and why V4's `c-ready-line-count` is the predicate
   that catches the case.
   **The count is not independent of the change it judges** (V4's Expected cell
   says so in full): it reads a stream the change itself influences, which is why
   V4(b), (c), (e) and (f) exist beside it. C-BRIDGE@1 rule 1 makes the single
   navigation load-bearing: a second `show_main` after `ready` is a
   re-navigation, which is Stop condition 1 and a contract break regardless of
   how the row's other assertions read.
4. **`Ready` is never swallowed.** The `eprintln!` at `:292` fires on every
   `ready` line the child writes, whether or not the loop then continues. A
   change that keeps forwarding but drops or defers that line has broken
   P3.4's harness's ability to find the boundary between "before ready" and
   "after ready", and V3 and V4 both assert the `ready` line is present on
   stderr **before** the marker line.
5. **stderr is the only destination.** No new file, no log file, no ring
   buffer, no IPC, no environment variable, no new capability. The forwarding
   is `eprintln!`, which is what `:318-325` already does and what P3.4's
   harness already reads. This defect is fixed by *not stopping*, not by
   *adding a channel*.
6. **The child and the reader thread must stay distinguishable at shutdown, and
   the rule covers every event, not only `ChildGone`.** Four clauses:
   **(a)** a `ChildGone` arriving **before** any `ready` must still paint an
   error screen, because that is C-BRIDGE@1 rule 7's early exit; **(b)** a
   `ChildGone` arriving **after** a settled `ready` must be **logged and
   ignored** — no `show_error`, no `close_window`, nothing painted; **(c)** the
   same holds for **any other line arriving after a settled `ready`** — a
   `fatal`, an `Other`, a `Rejection` — because the `fatal` arm at `:307-317`
   is exactly as unconditional as `ChildGone` (`show_error` at `:313`,
   `close_window` at `:314`, `break` at `:316`) and becomes newly reachable the
   moment `:298` goes. Clause (c) is a statement about reachability, not a third
    part of the change: **the card does not edit the `fatal` arm.** What it
    requires is that the change make such a line harmless in that state or leave
    it unreachable by construction; if a `fatal`, an `Other` or a `Rejection`
    arriving after a settled `ready` would still paint, the shell has lost the
    distinction and that is Stop condition 3. (A second `Ready` is not in this
    clause — it is (c-ii) below.) Today no code path produces a post-`ready`
    `fatal` (`server/src/index.ts` writes `Fatal` only at startup), so V4 asserts clause
    (c) over the events the run can actually produce — the post-`ready`
    `ChildGone` — and says so rather than manufacturing one.
    **(c-ii) A `Ready` arriving after a settled `ready`** is the same case and is
    the only line besides `fatal` that can paint: the `main` label is taken at
    `main.rs:471`, so the second `show_main` returns `false` (`main.rs:519`) and
    the arm would paint `the_window_would_not_open` at `:302`. **C-BRIDGE@1 rule 1
    says the server prints exactly one `ready` line**, so no code path produces
    one, and V4's `c-ready-line-count` asserts exactly one over the whole run.
    **The card does not authorise a guard on the `ready` arm** — part (i) only
    removes the success `break`, and a `settled` test inside the `ready` arm
    would be a third part and Stop condition 3. **A second `ready` is Stop
    condition 1: reported, not repaired.** Do not "make it idempotent".
    V4(d), (e) and (f) assert clauses (a), (b), (c) and (c-ii) where they can be
    observed from outside.
7. **The end-to-end row's publisher is a route that already exists, driven by
   the server's own request logger — no server edit, no new route, no marker in
   the bundle.** The bundled server runs Fastify with `logger: true`
   (`server/src/app.ts:70`), so **every request's URL is written to the child's
   stdout (fd 1)** by the request logger; that is the same channel P3.4's hook
   uses, and P3.4's own card says so. V3 therefore drives `GET /api/health` with
   a run-unique query string, **after** the app window is up, and asserts the
   marker reaches stderr. The route exists, the logger exists, and neither is
   touched. **If the observed line does not name the request at all**, that is a
   finding for the coordinator and Stop condition 2 — the card may **not**
   respond by adding a log line, a route, an env var or a build flag.
8. **Every C-BRIDGE@1 rule still holds, and V1 re-runs the tests that hold
   them.** The thirteen `#[test]` cases in `mod tests` (`main.rs:705` onward) are
   unchanged and are re-run by V1: they carry P3.3's navigation guards
   (`main.rs:486-487`, rule 5), the nonce and protocol checks on the bridge
   parser (rule 1), the unknown-type handling (rule 2), and the code-to-word
   mapping. **V1 runs `cargo test` and it must report the same thirteen passing
   and zero failing — no test is deleted, renamed, `#[ignore]`d, or loosened to
   accommodate the change.** A lifecycle change that needs a weakened guard is a
   stop. The count was verified against the file at this base (`mod tests` at
   `:705` holds exactly thirteen `#[test]` attributes); **if a dispatch finds a
   different number of attributes, the *expectation* is corrected to match the
   file and reported — never the tests.**

   rows run the launch and every probe inside one `xvfb-run -a bash -c` precisely
   so that this condition means "no display here" rather than "the probe read the
