- Identity `app.apunta.desktop`; test builds (`tauri:build:test`, Cargo
  feature `test-identity`) use `app.apunta.desktop.test` and read

- **The bridge wire format, fixed here because C-BRIDGE@1 fixes the shape and
  the card has to name the parts.** Every line is one JSON object on the
  child's **stdout**, written by `server/src/shell-bridge.ts`, and the shell
  reads nothing else on that stream.
  - `APUNTA_SHELL=1` means "a shell is listening": the ready line and the
    stdin bridge are written **only** when it is set, so browser mode's
    stdout is byte-for-byte today's stdout.
  - `APUNTA_SHELL_NONCE` is the nonce's variable. The **shell** generates it,
    sets it on the child, and accepts the ready line **only** if the line's
    `nonce` equals it; a line with any other value is logged and ignored and
    the shell never navigates. It is a distinct value from the C-OWN lock
    nonce `acquireDataFolderLock` generates internally, and the two are never
    compared, stored in the same place, or derived from one another — the lock
    nonce proves folder ownership on disk, the bridge nonce proves this line
    came out of this spawn.
  - `fatal` carries `{"type":"fatal","code":…}` and **no nonce**: it is read
    from the same trusted stdout stream, and C-BRIDGE@1 rule 2's shape has no
    nonce field to add. The code set this card fixes is
    **`data_folder_in_use`** and **`port_in_use`**, and no third. An unrecognised
    code still shows the error screen, carrying the code verbatim.
  - The code travels **only** as that JSON line. It is never parsed out of a
    pino log line, never read from an exit status, and never matched on a
    substring. A log line and a bridge line are different channels, and
    guessing across them is the mistake that would make the app report
    "port in use" for a folder that is already owned.
  - An unknown **inbound** type from the shell is logged and ignored
    (C-BRIDGE@1 rule 2).
- **`writeFatal` is called at exactly two sites, and nowhere else.**
  1. The exit-75 lock refusal, `index.ts:59-62`: call
     `writeFatal('data_folder_in_use')` **before** `process.exit(75)`. The
     existing `console.error` line stays — it is the log, and it is how P3.2's
     own evidence proves the refusal; the bridge line is additional, not a
     replacement.
  2. The `catch` around `app.listen`, `index.ts:155-158`: when the error is a
     listen failure whose `code` is `EADDRINUSE`, call
     `writeFatal('port_in_use')` before exiting. **Every other error in that
     `catch` keeps today's `app.log.error(error); process.exit(1)` exactly as
     it is.** That `catch` also covers the daily-backup and open-browser calls,
     and a failure in either of those is not a port clash; saying so is what
     keeps the mapping honest.
  `writeFatal` never binds, never serves a boot-error page and never returns;
  the caller exits immediately after it. **The line is written
  synchronously — `fs.writeSync(1, …)` — at both sites, and never with
  `console.log` or `process.stdout.write` ahead of a `process.exit`.** On a
  pipe, which is exactly what a Tauri child's stdout is, `process.stdout` is
  asynchronous and `process.exit()` does not wait for pending writes, so a
  queued line can be discarded by the exit it was written to precede; the shell
  would then see a child that exited 75 with no `fatal` line, and the
  intermittent failure would be read as a broken bridge rather than a lost
  write. A flushed `await`ed write is the only other acceptable form.
- **`tauri:dev` is a test-identity script, and it can never reach the live
  instance.** It is defined to build with the `test-identity` Cargo feature
  like `tauri:build:test`, and it is only ever run as
  `node scripts/v2/sandbox.mjs run --port 78xx -- npm run tauri:dev`, which
  supplies `APUNTA_DATA_DIR`, `APUNTA_PORT` and `APUNTA_NO_OPEN`. The existing
  refusal — both environment variables present or no start at all — is the
  primary guard and needs no change. This card adds one belt-and-braces check
  **in the script**, because a guard that only exists in Rust is one careless
  flag away from being off: the script refuses to start when `APUNTA_PORT` is
  7717 or when `APUNTA_DATA_DIR` equals the platform default string, printing
  which one and exiting non-zero before `tauri` is invoked. So a bare
  `npm run tauri:dev` at a terminal is a **refusal with a reason**, not a
  launch — HS-1 in both halves is structurally impossible to cross with this
  script, rather than merely discouraged. `tauri:build` (the production build)
  is unaffected: it builds without starting anything.
- Production: port 7717 (E5). `port_in_use` is the code for **one** condition
  only — the server could not listen because 7717 was already taken — and
  `data_folder_in_use` is the code for **one** other condition: the data
  folder is owned by a live Apunta (C-OWN@1, exit 75). The two are never
  interchanged, and neither is ever inferred from the other. The bilingual
  error screen carries whichever code arrived, and for C-OWN@1's rejection
  example that is the screen saying Apunta is already open, not "port in
  use".
- Single instance via `tauri-plugin-single-instance` (second launch focuses
  the window). Data ownership is C-OWN, not this plugin.
- Splash (the A mark, no text needed) until `ready`; `fatal` or early exit →
  bilingual error screen with the code. "The A mark" is
  `docs/v2/assets/apunta-a.currentcolor.svg` for the in-app colour rule or
  `apunta-a.teal.svg` for a fixed-colour export, brand teal `#1f6f63` on the
  `#f6f4ef` tile with the `#e3e0d6` hairline
  (`docs/v2/assets/README.md`, Rules) — not the full app icon
  `apunta-icon.png`, which is the 1024 px master the `tauri-icons/` set is
  generated from. Rasterising it for the splash window is
  `build-brand.py`'s job, which is already in the repo and touches no
  network; the card does not run it and does not rebrand anything.
- Quit: send `shutdown`, wait 10 s, then SIGTERM the child's process group,
  then SIGKILL after 5 s. Never signal any process the shell did not spawn.
- **Nothing else in this repository needs an ignore entry for Cargo output, and
  the reason is worth knowing.** `.gitignore` is enough on its own: Prettier 3
  reads `.gitignore` by default, which is exactly what the `build/` entry at
  `.gitignore:50-55` relies on, so there is deliberately **no** matching
  `.prettierignore` line. `eslint.config.js` needs its own one only because
  ESLint does not read `.gitignore`. Do not add a third file for this: no
  `.prettierignore` entry, and **no `src-tauri/.gitignore`**.
  **The one `.gitignore` line is extended to cover the generated
  `src-tauri/gen/schemas/` tree as well, and it is ignored rather than
  committed — that is the choice, and the Tauri project template is what
  supports it.** `tauri build` runs `tauri-build`, which writes
  `src-tauri/gen/schemas/*.json`; the tree's own template `.gitignore` ignores
  `/target/` **and** `gen/schemas`, and Tauri's own guidance is that both are
  regenerated build output, so the single repository-level line names both and
  the generated schemas are never staged. Committing them instead would mean
  committing files no code reads, keeping a `git add src-tauri` from sweeping
  machine-local build output into the commit, and leaving a tree on disk that
  Prettier walks in V6. An implementer who sees `src-tauri/gen/schemas/` on
  disk confirms it with one `ls` at S4 and adds neither a third file nor a
  second rule beyond the two paths above.

rule is "newest 2.x patch on acquisition day" — re-resolving a day later picks

## Stop conditions
The installed Tauri version cannot load an `http://127.0.0.1` URL in the
main window without granting it capabilities: stop and report (E3 forbids
capabilities).
