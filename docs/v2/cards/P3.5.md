## Objective
WebKitGTK **captures** microphone audio inside the Linux app window and hands
it to the note's own transcript path, proven with intelligible synthetic English
speech; and silence or a tone never produces a note.

This card is **capture-only** (owner decision 2026-10-02, `AM-109`). It proves
two things and defers everything else to **S4a.2**:

- **Proved here:** the real `getUserMedia` → `AudioContext` → `AudioWorkletNode`
  → WAV path (`web/src/lib/recorder.ts`) receives frames from the host's capture
  device; the app's own record button really starts and stops it; the finished
  WAV is really POSTed by the app to `/api/transcribe`; and neither a tone nor
  digital silence creates a note.
- **Deferred to S4a.2 (the transcription half):** every claim about *words* —
  that the transcript contains the negated risk statement and the dose, the
  `transcription_empty` assertion, whisper accuracy, model selection (A07) and
  the `whisper_model` setting. **No model is acquired, downloaded, selected or
  run by this card** (HS-3; A07 belongs to S4a.2, which is `NOT STARTED`). A row
  that would need a model to pass is written here as deferred to S4a.2, never as
  a row that fails.

### The one test-only hook (`web/src/main.tsx`)
There is no driver for a WebKitGTK window: Playwright drives Chromium only
(`e2e/fixtures/audio/README.md:5-7`), and P3.3's harness runs "no stub, no fake
bridge line and no test hook" (`scripts/v2/tauri-lifecycle.test.mjs:12-14`).
Owner decision `AM-109` permits **exactly one** such hook in `web/`. It is:

- **File:** `web/src/main.tsx`, the entry point every build loads, beside the
  boot-time side effects it already owns (`applyTheme`, `installAutoHideScrollbars`).
  Not `Capture.tsx`, not `useLiveRecording.ts`: the harness has to reach the
  capture screen from the home screen, and a hook mounted only on the capture
  screen cannot report the two clicks before it. **No other `web/` file changes**,
  so no component, no prop, no route, no type and no test outside `main.tsx`
  moves.
- **Gate:** Vite's built-in env prefix, with **no config change**:
  `import.meta.env.VITE_APUNTA_TEST_IDENTITY === '1'`. Vite replaces every
  `import.meta.env.VITE_*` reference at build time and defaults an absent one to
  `undefined` (`node_modules/vite/dist/node/chunks/node.js:25363`,
  `define["import.meta.env.*"] = "undefined"`; the default prefix is `VITE_`,
  same file `:5931`). The hook is one `if` around one block: absent variable →
  `undefined === '1'` → dead branch, removed by the bundler's minifier.
  `web/vite.config.ts` declares no `envPrefix`, no `define` and no test env, so
  nothing else can switch it on.
- **Release-build evidence (the gate cannot exist in a release build):**
  1. The only producer of a shipped bundle is
     `scripts/v2/package-linux-resources.sh:104`, which runs
     `npm run build` and copies `web/dist`
     (`:155-160`); `npm run build` reaches the web workspace's `vite build`
     (`web/package.json`). None of `package.json`, `package-linux-resources.sh`,
     `scripts/package-mac.sh`, `.github/workflows/ci.yml` or any other script in
     this repository sets `VITE_APUNTA_TEST_IDENTITY` — a repository-wide search
     finds no occurrence outside this card and `vite.config.ts`'s absence of it.
     The only `VITE_` string in shipped code is the unrelated
     `VITE_HOST = '127.0.0.1:5173'` constant in
     `server/src/http/request-guard.ts:32`.
  2. The **only** build that sets it is this card's V2 row, which prefixes the
     flag inline on the `npm run build` it runs before `npm run tauri:build:test`
     (`tauri:build:test` = `tauri build --features test-identity --config
     src-tauri/tauri.test.conf.json`, P3.3's gate). A release build
     (`npm run tauri:build`, `npm run package:mac`) never carries it.
  3. V2 asserts the positive half mechanically: after the flagged build, the
     hook's marker string **is** present in `web/dist/assets/*.js`; V5's
     invariant, restated for any later release build, is that a release
     `web/dist` must contain **zero** occurrences. A release build that ever
     contains the marker is a `FAIL` and an owner escalation, not a row to be
     relaxed.
- **What the hook does — nothing but report.** It publishes, and it never
  actuates:
  - the **screen rectangle** of named elements, so the harness can put a real
    pointer click on the real button: `[data-testid='home-action-note']`,
    `[data-testid='home-search']`, the first `li[role='option']` in the home
    results list, `[data-testid='record-start']`, `[data-testid='record-stop']`
    (`HomeLauncher.tsx:136,166`, `Capture.tsx:360,426` — attributes that already
    exist for e2e, added by nothing here);
  - the **capture state** it reads out of the DOM the app already renders:
    which of `record-start` / `record-stop` / `record-stage` / `record-done` /
    `capture-error` is present (the phase, `Capture.tsx:344-435`), the
    `record-timer` text (`LiveRecording.tsx:66-68`) and the `--level` custom
    property on `record-dot` (`LiveRecording.tsx:60-65`).
  - **The trigger is a real click.** The harness clicks those rectangles with
    `xdotool mousemove --sync --window <id> <x> <y> click 1`; the app's own
    `onClick` handlers run (`HomeLauncher.start` → `navigate('/capture/<id>')`,
    `Capture.startRecording` → `useLiveRecording.start`, `Capture.stopRecording`
    → `process()` → `POST /api/transcribe`). Nothing in `web/`, `server/` or
    `src-tauri/` is asked for a new capability, a new IPC command, a new route
    or a new Rust API — there is none.
  - **Delivery channel, and why it is one that works headlessly:** the marker
    line is written to `document.title` **and** with `console.info`, and — the
    channel the harness *requires* — as a same-origin
    `fetch('/p3.5-marker?...')`, whose URL Fastify's request logger
    (`server/src/app.ts:69`, logger on by default) writes to its own stdout. The
    AppImage's shell and the bundled server inherit the AppImage's stdout, the
    harness already captures that pipe (`tauri-lifecycle.test.mjs:214-247`) and
    already prints it as evidence (`:764-774`), so the marker arrives on a pipe
    this repository has been reading for three cards. The same origin means no
    new network access (HS-6: loopback only, the server Apunta already talks
    to); the marker carries **phase, timer and level only** — never a patient
    name, never transcript text, never anything from the live instance. The
    other two channels are conveniences and the harness records which of the
    three delivered the line.
  - It polls on a 250 ms interval and re-publishes only on change, so the
    harness always has a current rectangle; it removes its interval and its
    listeners when the flag is off, which is every release build.
- **Privacy of the marker:** HS-8 holds — the only name in the run is John
  Smith, created by the harness through the API in the sandbox run folder, never
  read from the live instance.

### Microphone containment (the host-global mutation)
The host's default capture device is a **real USB microphone**
(`alsa_input.usb-UGREEN_Camera_2K_…`). The run must never touch it. Owner
decision `AM-109`:

- **The virtual PipeWire source is the ONE permitted host-global mutation
  outside the run folder.** Nothing else in this card changes host state: the
  data folder, the port, the cache/config/XDG homes and the display all come
  from the sandbox environment and the harness, as in P3.3.
- **Mechanism, pinned for this host: PipeWire through `pactl` only.** This host
  runs `pipewire-pulse`; there is no `pulseaudio` daemon and no `pacmd`, and
  **neither may be used or installed**. The modules are provided by
  pipewire-pulse's own Pulse module layer — `module-null-sink` and
  `module-remap-source` are both implemented in
  `/usr/lib/pipewire-0.3/libpipewire-module-protocol-pulse.so` (verified by
  `strings`, read-only; no module was loaded while this card was written).
  `pactl` is 17.0 (`pactl --version`), so `pactl get-default-source` exists.
- **Exact commands, in this order, from the repo root:**

  ```sh
  PREV_DEFAULT="$(pactl get-default-source)"                     # 1. remember
  SINK_ID="$(pactl load-module module-null-sink \
      sink_name=apunta_p35 sink_properties=device.description=Apunta_P3.5)"
  SRC_ID="$(pactl load-module module-remap-source \
      source_name=apunta_p35_mic master=apunta_p35.monitor)"    # 2. create
  pactl set-default-source appointa_p35_mic                     # 3. default
  paplay --device=apunta_p35 --rate=16000 --channels=1 \
      "$(dirname "$APUNTA_DATA_DIR")/audio-en/dictation-30s.wav" &   # 4. feed
  #   ... the harness launches the AppImage and drives the real buttons ...
  pactl set-default-source "$PREV_DEFAULT"                      # 5. restore
  pactl unload-module "$SRC_ID"; pactl unload-module "$SINK_ID"  # 6. remove
  ```

  The names are `apunta_p35` / `apunta_p35_mic` in every row, so two runs never
  collide and V5 can assert on them exactly.
- **Step 3 happens before the AppImage is launched, and step 4 before the record
  click.** The default is what WebKitGTK's `getUserMedia` opens, so the real
  microphone is not merely un-defaulted, it is not the device the app asks for.
- **`trap`-based removal, on every exit path.** The harness installs
  `process.on('SIGINT'|'SIGTERM'|'SIGHUP')` and an exit handler that runs
  `pactl set-default-source "$PREV_DEFAULT"` and both `unload-module` calls, in
  that order, whether the row passed, failed, threw or was signalled. A row that
  cannot restore and remove is a `FAIL`, not a cleanup detail: the owner's
  microphone must be the default again whatever happened.
- **The playing stream is stopped by pid** (C-ISO@1 rule 7: never `pkill`), and
  `paplay` is never pointed at a sink other than `apunta_p35`, so the owner's
  audio output is untouched.
- **V5 is the only check that the source is gone** — and it is checked from the
  outside, not from the harness's own bookkeeping.

### The relationship with the Spanish generator (no second wrapper)
`scripts/v2/generate-es-audio.mjs` already solves most of V1: it takes
`PIPER_BIN` and `PIPER_MODEL` as environment inputs, refuses an output path
inside this repository and refuses a path directly under `/tmp/apunta-v2`
(`:263-286`), pins the synthesis (`--noise_scale 0 --noise_w 0`,
`OMP_NUM_THREADS=1`), resamples Piper's 22,050 Hz to 16 kHz mono 16-bit with
`ffmpeg` and `bitexact` flags (`:624-653`), and writes a `reference.json` of
provenance; `check-es-audio.mjs` is its checker. **P3.5 uses exactly those
inputs, exactly that resample rule and exactly that refusal**, and V1 is the
literal command that does it — which is why:

- **`scripts/v2/make-en-audio.sh` is dropped from May edit.** A second bash
  wrapper around Piper is the exact defect the review named (D6): it could
  write audio into the repository, undoing the refusal the Spanish script
  exists to enforce, and it would be a weaker copy of a working tool.
- **Why a separate script is nevertheless not required:** V1 needs **one**
  30-second clip and **one** 10-second silence clip — not a 295-clip corpus, no
  seeded variants, no SNR arm and no `reference.json`. A row that runs Piper
  once and resamples once is shorter than the refusal logic any new script would
  need, and it is reviewable in the card.
- **The refusal is enforced twice anyway, in code the harness owns:**
  `scripts/v2/tauri-audio.test.mjs` refuses any `--audio` directory that is
  inside this repository or sits directly under `/tmp/apunta-v2`, exactly as
  `generate-es-audio.mjs:276-281` does, and V1's output path is *derived* from
  `$APUNTA_DATA_DIR` (`$(dirname "$APUNTA_DATA_DIR")/audio-en`), so it cannot be
  anywhere else.
- If a later card wants one English corpus rather than one clip, extending the
  two `.mjs` scripts is the right move and needs an amendment; this card does not
  assume it.
