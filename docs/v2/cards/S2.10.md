## Objective

The e2e line at **default workers** exits 0, five times in a row, so S2.R's
borrowed V3 row passes as written.

S2.9 removed the theme-row and formats-count races and was APPROVED on its
objective under **AM-092**, which authorised this card in the same amendment
(`docs/v2/state/AMENDMENTS.md:115`). It did not pass its V3: **2 of 5 runs
exit 0** for the reviewer (`S2.9-impl.md:80-86`, 4 of 5 for the implementer,
`docs/v2/evidence/S2.9/runs.md:168-174`). The three failures are two residuals
that predate S2.9 — both racing files and the hook that fires the request are
byte-identical at the base commit — and both are **test isolation**, so that is
all this card touches:

1. **The import-undo race.** The two import specs delete the patients their
   imports created with `POST /api/import/batches/<id>/undo`, and the Halaxy
   spec clicks the **first** row of the shared, global batch list
   (`e2e/tests/halaxy-import.spec.ts:76-80`) rather than its own. Every
   workspace page lists **all** patients and `usePatientRecency` fires
   `GET /api/patients/<id>/notes` for each one (`web/src/hooks/usePatientRecency.ts:45-70`),
   so a page that listed an imported patient gets a 404 when the recency fetch
   lands after the undo, and the **test whose page it was** fails on the
   `consoleErrors` auto-fixture (`e2e/support/fixtures.ts:70-85`) —
   `plan.spec.ts:58` in both S2.9 runs. Fixed decision 1.
2. **The `spelling.spec.ts:14` flake**, a state-dependent failure at
   `spelling.spec.ts:87` that no lock reaches. Fixed decision 5, which
   diagnoses before it prescribes and stops when the cause cannot be pinned.

This card changes the tests' isolation and nothing else.

## Fixed decisions
1. **Each import test undoes its own batch, by id, and the id is asserted —
   never `.first()`.** `halaxy-import.spec.ts` is the only spec that clicks a
   shared list. The shape, in the order it must be done:
   - **Capture the id at the moment the server gives it.** `POST
     /api/import/halaxy` answers 201 with `{ batch_id, patients, notes }`
     (`server/src/routes/halaxy.ts:49`, `:57`, `:102`), so a
     `page.waitForResponse` armed **before** the `halaxy-run` click at
     `:48` yields the batch this test just created. Reading it afterwards
     "from the newest row" is `.first()` with extra steps.
   - **Locate that batch in the list, and prove the mapping.** The rows carry no
     id (`ImportBatchList.tsx:44-62`), so the index is taken from the API —
     `GET /api/import/batches`, the same call the UI's own list is
     `useImportBatch.reload`'d from — and **asserted** before the click: the id
     at that index is the captured `batch_id`, and the number of undo buttons
     in `halaxy-batches` equals the number of rows the API returned. Two
     assertions, both cheap, both about identity rather than position.
   - **Click that index**, never `.first()`.
   - Everything after the click is unchanged, including the undone-line
     assertion at `:81-83` and the `checkScreen` at `:75`.

   **Why the mapping cannot drift.** The UI's list is loaded when the page
   loads (`:73-74`) and is only reloaded after an undo, so the DOM and the API
   agree unless a batch is created in between — and the only creators are the
   two import specs, each of which removes its own batch before it ends. The
   button-count assertion is what turns that argument into a check rather than a
   hope, and it is why **no lock is needed** (decision 2).

   **`import.spec.ts`'s id change is none**, and that is the finding: its
   `import-undo` button is already bound to `report.batch_id`
   (`web/src/routes/Import.tsx:183-193`). What is wrong on that spec is
   decision 3, and the wrong-batch delete it could suffer — its own undo taken by
   the Halaxy spec's `.first()` — disappears with decision 1.
2. **No new lock, and the arithmetic that says so.** A second key in
   `support/fixtures.ts` is the shape S2.9 already built, and it is the wrong
   tool for the remaining import coupling, for three reasons, each a number:
   - **The coupling left after decision 1 is one-sided.** With each test undoing
     only its own batch, neither import spec can delete the other's patients,
     can 404 on the other's batch, or can see the other's notes: the Halaxy run
     creates **no transcripts** (`server/src/routes/halaxy.ts:49-106` inserts
     none), so it cannot move the Claude preview's dedupe keys
     (`server/src/routes/import.ts:142-150`), and the halaxy patient is
     `uniqueName`'d at `:44` so it cannot be matched into an existing patient
     (`halaxy.ts:63-67`).
   - **In V3 the queue would be empty anyway.** Each spec runs **once per
     project** (`e2e/playwright.config.ts:100-113`), so at most two lock-takers
     could ever be in flight, and they would not be at the same moment.
   - **The hold could not fit the budget.** The window that would need protecting
     runs from the preview (where the dedupe state is *read*, `import.spec.ts:37`)
     to the undo (`:53`) — the whole body, and for the Halaxy spec it includes
     the patient-list detour at `:54-71`. S2.9 measured its longest hold at
     661 ms and capped it at 6 s precisely so that `(W − 1) × H` sits under the
     20 s deadline and under Playwright's **30 s** default
     (`fixtures.ts:119-129`). A 10–15 s hold does not: at `--repeat-each=1` the
     worst wait is `1 × 15 s = 15 s`, and the waiting test then spends its own
     ~15 s inside the same 30 s default, **before** setup and teardown. A lock
     that wide is `workers: 1` with extra steps, which is the one thing S2.9's
     decision 1 exists to refuse.

   **A short lock around the two undo clicks was considered and rejected**,
   with the number: the failing run's log has the two undos 651 ms apart
   (`S2.9-impl.md:247`, `:250`) and each victim's fetch lands 25–105 ms after
   *its own* delete, so the two exposure windows barely overlap and a lock
   separating them changes neither.

   If Step 1 or V1 still shows a `POST /api/import/batches/<id>/undo` **404**, or
   a "Nothing new to import." in either spec, that is **Stop condition 2** — the
   endpoint, the run and the failing assertion verbatim — not a licence to add a
   key. The alternatives are listed in decision 4.
3. **The self-inflicted second copy is a scheduling choice, not a fixture
   rewrite.** `import.spec.ts:15` imports a **committed** fixture, and the server
   dedupes an import against the transcripts already stored
   (`server/src/routes/import.ts:142-150`), so a second concurrent copy gets
   nothing — the F1(b) failure, verbatim in `findings.md:63-69`. It is reachable
   **only under amplification**: in V3 each spec runs once per project. The
   fixture is not available per copy — the counts the sentences at
   `import.spec.ts:39-49` are built from are the fixture's own shape, and a
   generated copy would make those sentences test the generator. So the
   amplification in V1 runs the import specs at `--repeat-each=1`, **stated here
   with this reason** rather than left as an unexplained failure, and the
   dedupe is what makes serialised copies safe if a future row does amplify
   them: undoing a batch deletes its notes first
   (`server/src/db/import-batches.ts:64-80`) and `transcripts.note_id
   REFERENCES notes (id) ON DELETE CASCADE`
   (`server/migrations/003_import_transcripts.sql:12`), so the imported keys
   are released and the next copy imports cleanly.
4. **The notes-404 victim: the author is fixed, the victim side is not a test
   fix, and the card measures it instead of guessing.** With decision 1 in
   place, the remaining exposure is exactly this: another spec's page lists a
   patient this card's specs created, and its recency fetch for that patient
   lands after the undo deleted it. Read off the code, that has **three**
   levers and only two of them are anywhere near a test:
   - **(a) Stop the delete reaching a page that has listed the patient.** Not
     available to a test. The undo's own rule is already the server's
     (`import-batches.ts:78-97`: a patient with anything attached is kept), and
     the only way a test could exploit that is to attach something to the
     imported patient before undoing — which changes the undone line the test
     asserts (`:81-83`) and leaves rows behind. That is weakening an assertion
     to dodge a race. No.
   - **(b) Shorten the window between the run and the undo.** Bounded by the
     assertions themselves: the Halaxy spec's patient-list detour at `:54-71` is
     the proof that the patient landed, and it must happen while the patient
     exists. The one piece of fat is the `waitForTimeout(500)` at `:56`; if Step
     1's traces show it load-bearing, leave it, and if they show it is not,
     removing a sleep is not a weakened assertion. Everything else in that
     window is an assertion.
   - **(c) Stop the 404 being an error.** Two sub-levers, both out of scope
     here: a product change in `usePatientRecency` (do not fetch for a patient
     the list can no longer vouch for) — production code; or a scoped
     `consoleErrors` allowlist for exactly `GET /api/patients/<id>/notes` — a
     guard narrowed for the whole suite, which Must not edit forbids and which
     is the owner's to take.

   So the card fixes (a)'s *author* half, leaves (b) to the one change it
   permits, and **counts** the residual: every `GET /api/patients/<id>/notes`
   404 seen in V1 and in V3's five runs is recorded in the return file with its
   run number, its spec and the server-log timestamp beside the undo. **If any
   remain at V3, that is Stop condition 5**: report the count, the three levers
   and their costs, and let the coordinator put the choice to the owner (§6,
   and AM-092's own boundary). Do not invent a fourth lever, and do not edit
   `plan.spec.ts`.
5. **The spelling flake is diagnosed before it is fixed, and the diagnosis
   decides the fix.** What the code already rules out, so the implementer does
   not spend the session on it:
   - **The settings `PUT` at `:22` is not a racer.** `PUT /api/settings` is a
     per-key merge, not a replace (`server/src/routes/settings.ts:70-77`,
     `server/src/db/settings.ts:36-46`), so writing `stt_vocabulary` and
     `spelling_words` cannot touch the theme or language rows, and no other spec
     reads those two keys. The global-row problem S2.9 fixed does not reach here.
   - **The module-level `pending` in `speller.ts:22-33` cannot cross a
     `page.goto`.** It poisons a *document*, and `:84` is a fresh document, so a
     failed dictionary load on the note page cannot explain a missing mark on
     `/patients/new`.
   - **`no-english.ts` is not involved** — the failure is `.misspelt` being
     absent, not a string count.

   What remains is two candidates, and the code says which observation tells them
   apart. The one thing both share: `misspellings` is `[]` while `speller` is
   `null` (`useSpelling.ts:35-37`), so **no mark is ever drawn before the
   dictionary has loaded**:
   - **S1 — the dictionary had not finished loading in the `/patients/new`
     document.** `loadSpeller` fetches two files from the app's own origin
     (`speller.ts:19-26`) and `/patients/new` renders `<Workspace />`
     (`AddPatient.tsx:81`), so the same recency storm runs there; its six
     concurrent fetches (`usePatientRecency.ts:24`, `:69`) sit on the same
     HTTP/1.1 origin budget the two dictionary requests need, and every
     completed fetch re-renders the workspace. The longer the storm, the later
     the dictionary lands — and the storm grows with **accumulated** patients,
     which is why a fresh sandbox passes 6 of 6 and a used one fails
     (`S2.9-impl.md:206-220`).
   - **S2 — the name field lost its value, so there was nothing to mark.** `name`
     is React state initialised once from `?name=` (`AddPatient.tsx:31`) and
     passed to `SpellLayer` at `:114`, so a remount resets it to `''` — which
     is also why the review saw the "Add patient" button disabled at the moment
     of failure (`S2.9-impl.md:216-220`).

   **Evidence to gather (Step 2), and nothing else:** a traced, unfiltered
   `spelling.spec.ts` run in a **populated** sandbox that fails, from which
   read (i) the two dictionary requests' start and finish against the failing
   assertion's timestamp, (ii) how many `GET /api/patients/<id>/notes` requests
   were in flight in that window, (iii) the DOM snapshot at the failure — the
   value of `#patient-name` and the `.misspelt` count — and (iv) the same
   command's exit codes in a **fresh** sandbox, which is the dirty-versus-fresh
   contrast that makes the shared-state claim a measurement instead of a story.
   One run of `--repeat-each` in a used sandbox is the cheapest way to get (i)
   to (iii) in a single trace.

   **Then, and only then:**
   - **Add the `toHaveValue('Teh')` assertion before `:87`, unconditionally.**
     It is an addition that costs nothing and it separates the two candidates in
     the failure message itself: the value is present and the mark is absent
