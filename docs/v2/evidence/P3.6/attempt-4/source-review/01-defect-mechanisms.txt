D2 (MEDIUM) — F7's mechanism is the one the review prescribed and is implemented
correctly, but as narrowed the check can never fail.

  harness:1713  function ownershipContainment(baseline, after) {
  harness:1715    const appeared = after.filter((name) => !baseline.includes(name));
  harness:1716    return { owned, secondOwned: appeared.filter((n) => owned.includes(n)), ... };
                }
  harness:1689-1693  ownershipBaselineProof asserts ALL FOUR names are present in the baseline
                     (checked at the run's baseline step; attempt 3 verified this too)
  harness:1662-1667  ownershipFiles() === ['apunta.lock','apunta.db','apunta.db-wal','apunta.db-shm']
  harness:2045-2055  check('smoke no second lock, database, -wal or -shm', own.secondOwned.length === 0, ...)

A name already in the baseline can never be in `appeared`, so secondOwned === [] always.
The check is one of the card's five containment assertions, and a second server owning the
folder cannot show up as a NEW filename there — it either fails the lock or writes the same
four names. So the assertion moved from falsely-red (attempt 3's F7: the backup's own backups/)
to falsely-green.

The one way it can still fire is a false positive of the same class: SQLite creates and removes
apunta.db-wal, so if it were absent at baseline and the FIRST instance's own later writes
re-created it, the row would report 'a second owner appeared'.

Ways forward, both inside the harness file:
  (a) make it falsifiable for the same four names: record device+inode (or mtime+size) per file
      in the baseline and assert it is unchanged at the end, and/or read the holder out of
      apunta.lock and assert it is still this run's pid; or
  (b) keep it as a re-assertion of baseline presence and say so in the check's name and in the
      file header, so no reader takes it for a second-owner detector.
