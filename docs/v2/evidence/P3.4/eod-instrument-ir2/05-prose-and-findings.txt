## 4. §7 "not requested" vs §5 — intent is coherent; no new gate

`P3.4-EOD-INSTRUMENT-PROPOSAL.md` §7 says:

  > **Requested:** the approvals in §5 Option A — now four patches …
  > **Not requested, not assumed:** any source, tool, card, checkpoint, contract,
  > manifest or old-evidence edit; … any runtime run; …

Read literally, "any source, tool … edit" sits next to §5's request to approve
`candidate.patch`/`tooling.patch`, which ARE source/tool edits, and "any runtime
run" sits next to Option A's one final V0–V4 measurement. The apparent tension is
wording, not scope:

  - §7's "Requested" is the *authority* to approve the four enumerated patches;
    it is not a request that the preparer make the edits now, and the header
    states nothing is adopted or in force.
  - §7's "Not requested, not assumed" is the standard preparation disclaimer:
    no *further* authority beyond §5, and none of it silently assumed. "any
    runtime run" means this document does not self-authorise a runtime — the run
    is Option A's consequence, after the separate independent source review §5
    already requires.

The intent is therefore coherent with §5 and with COORDINATOR §6 (the coordinator
may not approve a row with a FAIL/NOT RUN; only the owner may authorise the
attempt-6 exception). No new gate should be invented here. If the owner wants
zero ambiguity, the minimal prose option is to scope the disclaimer: "**Not
requested or assumed beyond the four patches in §5:** any *other* source, tool, …
edit; … any runtime run beyond the single Option-A measurement; …". That is
optional wording, not a condition of owner-readiness.
