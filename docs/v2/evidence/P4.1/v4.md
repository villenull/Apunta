## Side effect caused by M5, disclosed in full

M5 removes the entry-point guard, so during that one mutation run the probe
**executed**: `main()` ran at import, issued its seven `HEAD` calls, and
overwrote `docs/v2/evidence/P4.1/redirects.md` at `2026-09-27T23:23:22.520Z`
with seven transport-failure records. That was not intended and it was not
invisible — the V2 run's own diff against the pre-run file is what surfaced it.

**No egress was spent, and this is demonstrable rather than asserted.** All
seven calls were intercepted by the throwing `fetch` stub this very test file
installs before importing the module, so no packet left the process. The
signature in the overwritten file proves it: each record read

```
- **Response status:** _none_ — no HTTP response — transport failure (Error)
```

`describeTransportFailure` uses `error.cause.code` when there is one and falls
back to `error.name` when there is not. A real undici transport failure always
carries a `cause` code — `ENOTFOUND`, `ECONNREFUSED`, `UND_ERR_*` — and would
have rendered one of those. `(Error)` is `error.name` with no `cause`, which is
precisely the stub's signature. There is also no `Location` host in that file
and no hosts table, consistent with seven responses that never arrived rather
than seven `302`s.

**The file is now correct.** V2's run at `2026-09-27T23:24:48.835Z` regenerated
it by the script, and it carries seven `302`s, zero transport failures and the
hosts table. The committed version was never touched — `git status` shows
`redirects.md` modified against `d0b8292` solely by V2's legitimate run, and the
committed content is still the 2026-09-26 record.

The lesson is worth keeping: a mutation that removes a guard runs the thing the
guard was protecting. The next card that mutation-checks an entry-point guard
should stub `fetch` on the *probe* side too, not only on the importing side.
