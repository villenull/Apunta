## The response bodies and the stored rows

Every body below is asserted exhaustively (`toEqual` on the whole body), so what
the test compares is what is recorded here.

**`GET /api/settings`, fresh database, no `language` row stored:**

```json
{
  "llm_available_profiles": ["quick"],
  "llm_effective_profile": "quick",
  "language": "en",
  "spanish_available": false
}
```

`SELECT key, value FROM settings` at that moment: *no rows*.

**`PUT /api/settings { "language": "es-MX" }`, `APUNTA_DEV_SPANISH` unset →
400:**

```json
{
  "error": "language_unavailable",
  "message": "Español is not available in this build of Apunta. Choose English, or install the Spanish edition."
}
```

`SELECT key, value FROM settings` after it: *no rows*.

**`GET` then the same `PUT` with `APUNTA_DEV_SPANISH=1` set → 200:**

```json
{ "language": "en", "spanish_available": true }   // the GET, before the choice

{
  "llm_available_profiles": ["quick"],
  "llm_effective_profile": "quick",
  "language": "es-MX",
  "spanish_available": true
}                                                  // the PUT response
```

`SELECT key, value FROM settings` after it:

| key | value |
| --- | --- |
| `language` | `"es-MX"` |

and after `PUT { "language": "en" }` on the same build:

| key | value |
| --- | --- |
| `language` | `"en"` |

**`PUT /api/settings { "language": "de" }` (with the switch **on**, so the
answer cannot be the availability guard) → 400:**

```json
{
  "error": "bad_request",
  "message": "Language must be \"en\" or \"es-MX\".",
  "details": { "language": "de" }
}
```

`SELECT key, value FROM settings` after it: *no rows*.

**`PUT { "language": "en", "spanish_available": true }` → 200.** The response
reports `spanish_available: false` — the build's answer, not the request's — and
the table holds one row, `language` = `"en"`. The key the client tried to write
is dropped before `putSettings`, so it is never a row.
