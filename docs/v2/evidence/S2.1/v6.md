### How "from inside the stream" is read

By a provider that is the real `FakeLlmProvider` with one method wrapped:

```ts
private async *watched(events: AsyncIterable<LlmEvent>): AsyncGenerator<LlmEvent> {
  for await (const event of events) {
    this.readings.push(active().map((job) => ({ ...job })));
    yield event;
  }
}
```

Every reading is taken while the provider holds an event the server has not yet
forwarded, so the reading sits strictly between the first and the last event —
which is the only window in which a job is observably in flight, because by the
time a response body exists the job is over. Each case asserts that the provider
produced more than one event, and that **every** reading saw exactly one job of
the expected kind and nothing else.

| Case | Assertion on each mid-stream reading | After the response |
| --- | --- | --- |
| draft | `jobs.map(kind) === ['draft']`, and the id is a UUIDv7 | `active()` is `[]` |
| refine | `jobs.map(kind) === ['refine']` | `active()` is `[]` |
| failure | — | the last event is `error`, then `active()` is `[]` |

The refine job's id is the target note's id, so `active()` can name the note a
later refusal is about. The draft job has no note yet, so `streamDraft` mints an
id with `uuidv7()`; the case asserts its shape, which is what proves the two paths
are registering different things.

Case 2 is the failure path the row asks for. `end(jobId)` runs in a `finally`
around the whole of `streamDraft`, so a provider that dies before producing
anything still releases the job — which is exactly the case that would otherwise
leave the app refusing language changes until it was restarted.
