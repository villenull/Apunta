### 0.2 One correction to the review itself (recorded, not resolved by convenience)

The review's F1 says "`e2e/playwright.config.ts:127,139` sets a 60 s per-test
timeout, so even a deliberate >30 s hold would be a slow, fragile row". The
source says otherwise: `:127` and `:139` are `timeout: 60_000` **inside the two
`webServer` entries** — the *server startup* budget. The config sets **no**
`timeout` at top level and nothing in `use`, so Playwright's **default 30 000 ms
per test** applies, and no spec in the repo calls `test.setTimeout`.

The correction makes F1 **harder**, not easier: a V2 that genuinely waits out a
30 s drain cannot fit in one Playwright test at all under this config, and
`e2e/playwright.config.ts` is in Must-not-edit. That is precisely why §2's
recommended package proves the 30 s boundary in **V1**, through an injected
clock, in milliseconds, and why the browser rows must prove the *protocol*, not
the timeout. An implementer who "solves" this by editing `fake.ts`, by editing
`playwright.config.ts`, or by adding an in-spec `setTimeout` has silently picked
the wrong design.

### 0.3 The sandbox seam and controlled dependencies (the one technical spine)

Revision 1 had a clock seam for the drain and nothing for the browser. This
revision states one strategy and uses it in both places, so the 30-second bound
stays the contract's 30 seconds, stays module-owned, and is never raised by a
caller, an environment variable, a test, or a route body:

1. **Dependency injection at the existing seam.** `buildApp(options)`
   (`server/src/app.ts:67`) already takes `db`, `logger` and `providers`.
   `BuildAppOptions` gains one optional `maintenance?: MaintenanceDeps`, where
   `MaintenanceDeps = { now?: () => number; sleep?: (ms: number) => Promise<void> }`
   — the shape of `BackupOptions.now` (`server/src/backup/archive.ts:82`), the
   precedent P5.2 set in this same contract. **Production passes nothing**, so
   production runs a real clock and the real `DRAIN_MS = 30_000`. The constant
   is module-internal: not exported, not read from `process.env`, not in a
   request body, not in a query string, not writable from a route. This is what
   makes V1's "the bound is reached and returns `ok:false`" a millisecond test
   rather than a 30-second one.
2. **A controlled dependency for the registry input, not for the clock.** The
   browser rows never wait on a clock. They hold a *registration* open through a
   production mechanism and wait for the server to *see* it: `GET
   /api/app/quiesce/status` (the sibling status route the P5.4 amendment needs
   anyway) reports `{"quiescing": bool, "activeJobs": [{kind}], "windows": n}`,
   and a spec **polls that until the precondition holds** before it triggers.
   Waiting for a precondition is deterministic; assuming a timing is not. The
   existing in-repo pattern for holding a registration open in a browser is
   `e2e/tests/language-control.spec.ts:104-113`, whose own comment says it keeps
   the refine job open for "seconds rather than milliseconds".
3. **What the seam deliberately does not do.** It does not add an env-gated
   virtual clock. CI runs `npm run e2e` **outside** the sandbox wrapper
   (`.github/workflows/ci.yml:61`, no `APUNTA_V2` / `APUNTA_TEST_RUN_ID`), so any
   behaviour keyed on the sandbox marker would make the same spec behave
   differently in CI than locally — the opposite of deterministic, and invisible
   until the row goes red on a branch. Everything in this card therefore
   behaves identically with and without the sandbox wrapper, and the sandbox's
   role is isolation (C-ISO@1) rather than behaviour.

If the owner rejects the recommended package in Choice 2 and keeps the 30 s
wait, the honest consequence is stated there rather than engineered around.

# Part A — Three grouped owner choices

Everything in Part B is a correction and needs no judgement. These three are
protocol or product choices that no repository fact settles. Each carries one
recommendation, and the recommendation keeps every existing gate.

## Choice 1 — the client channel, and who may start a quiesce

**A1. Transport.** Carried forward from revision 1 and confirmed here:
long-poll + report. `GET /api/app/quiesce/wait` held open per window; the server
answers `{"request":"flush","quiesceId":"<id>"}` when a quiesce begins; the
window flushes and `POST`s `{"quiesceId":"<id>","ok":boolean,"blockers":[]}` to
`POST /api/app/quiesce/report`. Not SSE (a new event name in `shared/`, a second
long-lived transport beside `web/src/api/sse.ts`, and `EventSource` is a pattern
this app does not use); not polling (a new interval number and up to N ms of
latency inside a 30 s budget). The correlation id, the concurrent phases and
the registration rules below are F4/F5/F6/F7 corrections and are **not** part of
the choice.

**A2. Authorization of `POST /api/app/quiesce`.** This is the part the review
raised as F9, and it is a **contract** question.

> C-BRIDGE@1 rule 3: "Update endpoints … exist only when the server was started
> by the shell; in browser mode they return 404."

`/api/app/quiesce` is a new app-level route with the opposite policy. Three
coherent answers:

- **(i) Ungated in browser mode; a successful quiesce leaves maintenance on.**
  The review's recommendation. The argument for it is not convenience: quiescence
  is a *server* state whose participant is the web client, and rule 3's gate
  exists because the updater's endpoints are shell-only features. The cost is
  real and must be recorded: browser mode gains an authority it did not have —
  any same-origin script can put the app into maintenance, and with maintenance
  left **on**, that state persists until restart.
- **(ii) Gated on shell mode.** Coherent with rule 3 read literally. Cost, and it
  is not a cost this proposal can argue away: `grep -rn APUNTA_SHELL` matches no
  source file, the predicate does not exist yet, and P3.3 owns its creation, so
  V2, V3, V4 and V6 become `BLOCKED` "no shell in the sandbox" — four of the
  card's rows unevidenced, and the review's D15 closure undone.
- **(iii) Ungated in browser mode, and maintenance is released when the last
  window goes — RECOMMENDED.** The trigger is available in browser mode, but the
  state it leaves behind is **bounded without a restart**: in browser mode a
  successful quiesce holds maintenance while **at least one window is
  registered**, and the last unregistration (socket close, page unload, hook
  teardown) releases it. In shell mode nothing changes — maintenance stays on
  through the snapshot, exactly as C-UPD@1's state machine needs, and is
  released by the shell's next transition. This removes the (i) hazard
  (persistence until restart) without moving a single boundary to make a test
  pass, and it costs almost nothing because F6 already forces the server to
  track the registered-window set. V4 keeps both of its assertions: the spec's
  own window is open when it checks the 503.

**Recommendation: (iii)**, with (i) recorded as acceptable if the owner prefers
the simplest rule and accepts persistence until restart, and (ii) as the
strict-reading option that BLOCKs four rows.

**Whichever is chosen**, one clause is added to **C-BRIDGE@1 rule 3** (and the
mirror clause to C-UPD@1's Quiescence paragraph) recording that
`/api/app/quiesce*` is a server-mode route rather than an updater endpoint, and
what releases maintenance in each mode — so rule 3 and the new route cannot be
read as contradicting each other later. This is a contract amendment and is
reserved to the owner; it is not this file's to make.

**What is explicitly *not* being recommended:** ungating anything to make a
test pass. C-REQ@1's request guard stays exactly as it is; the quiesce routes sit
behind it unchanged (`Host`/`Origin`/`Sec-Fetch-Site` against loopback already
admit them, and Playwright's `request` fixture already sends a conforming
`Host` with no `Origin`); and the shell-only status of the **updater** routes is
untouched.

## Choice 2 — what a non-empty registry does at entry, and where the unsaved-text guard lives

**B1. The entry rule (F1).** This is a **behaviour** question and the owner
should answer it as one. It is not "immediate refusal versus waiting" in the
abstract; it is what the therapist sees and how long she waits.

- **(i) Refuse at once on a non-empty registry — RECOMMENDED, and it needs your
  explicit sign-off because it changes behaviour.** The quiesce snapshots
  `active()` at entry. If the snapshot is non-empty it returns `ok:false` at
  once, with the still-active kinds as blockers, and the drain is never entered.
  If the snapshot is empty the drain still runs — a job already past the refusal
  hook must be allowed to finish — under the same `DRAIN_MS = 30_000` bound. The
  30 s then bounds the **client flush/report window** and the drain of a job
  that started between the snapshot and the hook. This makes V2 deterministic
  (`ok:false` + blocker `refine`), keeps the stream completing (FD9), needs no
  change to `server/src/ai/fake.ts`, and matches C-UPD@1's own failure row at
  `CONTRACTS.md:373` — "quiescing (active job, failed save, edit conflict) →
  back to `verified`; notice says what to finish first" — which describes an
  immediate, named refusal, not a silent half-minute. The contract sentence
  "waits **up to** 30 s" is preserved verbatim as an **upper bound** and the
  reading is recorded in the amendment, not silently reinterpreted.
- **(ii) Keep the 30 s wait and change V2's expectation.** Honest consequences,
  stated rather than hidden: with `fake.ts` capping any fake stream at ~2.4 s
  (`MAX_FAKE_DELAYED_WORDS = 200` × 12 ms), the fake refine drains long before
  the bound, so V2's `ok:false` + `refine` is **unreachable in a browser row**
  without either (a) editing `server/src/ai/fake.ts` — outside May edit, and a
  new fake-mode timing threshold under HS-7 — or (b) a virtual clock for the
  drain available in fake mode, which changes fake-mode fidelity and is itself
  an owner decision. Under (ii) the 30 s boundary is proven in V1 through the
  injected clock, and V2 asserts only that a quiesce with an open refine does
  not succeed until that stream drains. That is a **weaker row than the card's
  own V2** — it no longer proves a quiesce is refused while a refine runs — so it
  is listed to be considered, not recommended.

**Either way**: FD10's "not a timeout inflation" clause stays, the bound is never
configurable from outside the module, and V2 states that the refusal is observed
**while** `chat-streaming` is visible with the `refine` registration asserted by
the server's own view (the status route), never by elapsed time.

**B2. The unsaved-text close guard (F2).** C-UPD@1 says "unsaved text is never
discarded silently". On the note screen today there is **no guard**: no
`beforeunload`, no confirm, and no durable copy of the text anywhere in
`web/src`. `NoteView.tsx:338-359` is a *best-effort flush* on
`pagehide`/`visibilitychange` — a request that may or may not leave the browser —
and it is **not** claimed to be sufficient by this proposal, for two reasons
that make the current V6 unpassable *or* passing for the wrong reason:

- a spec that types, waits a beat and reloads has already saved through the
  ordinary 400 ms debounce (`NoteView.tsx:32`), so "the text is recoverable after
  reload" is true with no unload path involved;
- a spec that reloads inside 400 ms depends on Chromium honouring a keepalive
  `PATCH` during unload — exactly the "unload saves are best effort" the card's
  own Confidence line disclaims.

- **(i) Add `web/src/components/NoteView.tsx` back to May edit for one addition
  — RECOMMENDED.** A `beforeunload` handler mirroring `Capture.tsx:157-165`,
  reading the refs that already exist (`latestTextRef`, `persistedContentRef`,
  `saveStateRef`, `staleRef`, `:133-143`), attached in the effect that already
  registers `pagehide`/`visibilitychange` and deleted in the same cleanup. The
  condition is "the editor holds text the server has not acknowledged":
  `latestTextRef.current !== persistedContentRef.current || saveStateRef.current
  === 'saving' || saveStateRef.current === 'error'`. The existing
  `__apuntaFlushBeforeRelease` hook stays **read-only** to this card and remains
  the flush interface. V6(a) then asserts something deterministic: the dialog
  appears, and after it is dismissed the editor **still holds the typed text**,
  because the navigation was refused. This is the screen where the text actually
  lives, so this is where C-UPD@1's sentence becomes enforceable.
- **(ii) No `NoteView.tsx` edit.** Then V6(a) must be recorded `BLOCKED` —
  "no unsaved-text guard and no durable draft exists on the note screen" —
  which is honest and leaves the contract sentence unverified by anyone.

**Consequence of (i), and it is a real cost:** a `beforeunload` guard is global
unload behaviour, so other e2e specs can feel it (`save-integrity`, `plan`,
`capture`). That is why §2 adds **V8**: the full `npm run e2e` inside
`sandbox.mjs env --port <p5>`, expected exit 0. CI runs `npm run e2e`
(`ci.yml:61`), so this row is the only place the card's own web change is seen
by the rest of the suite, and V5 (`npm test && lint && typecheck`) never runs
Playwright at all.

## Choice 3 — the write boundary: which writes are registry jobs

**C1.** Revision 1's FD2 said "a route is registered when it **writes** or holds
an open stream", then assigned ten kinds to ten sites. The rule and the table
disagree: `JOB_KINDS` is a closed eleven-member vocabulary (`registry.ts:18-30`,
docstring `:15-17`), the card may not widen it (Must-not-edit), and there are
roughly thirty writes that would then need a kind. An implementer would have had
to guess whether a patient rename is a `save`, a `briefing`, or unregistered —
and two of those readings are defensible. That is the instruction review's D3
recurring inside the fix for D3.

- **(i) The registry is job-shaped: eleven kinds, no others — RECOMMENDED.** The
  rule becomes "a route is registered when it **starts a long-running job or
  holds an open stream**". A short write — a patient rename, a format edit, a
  plan-version activation, `prep/save`, settings — is **refused by the maintenance
  hook like every other write** but is not a registry job. The excluded writes
  are **listed by path**, so the boundary is decided rather than argued. This is
  faithful to C-UPD@1, whose list is job-shaped (recording, transcription,
  draft, refine, plan, briefing, brainstorm, imports, restore, backup, saves) and
  does not claim that every write is a job, and it keeps `JOB_KINDS` closed.
- **(ii) Every write is registered, with new kinds.** Rejected: it widens
  S2.1's vocabulary, which this card may not do, and it would make the registry a
  request counter rather than the "what is long-running" answer C-LANG@1 rule 6
  already reads.
- **(iii) Every write is registered under the existing `save` kind.** Rejected:
  it makes `settings.ts:92`'s `anyActive()` and the C-LANG@1 notice say
  "a save is running" when a rename is, which is a user-visible lie.

**Recommendation: (i).** V1's expectation changes with it: **ten**
server-observable kinds register and release, and `recording` is never registered
server-side, with its blocker arriving on the client channel.

### Fixed decisions

1. **The flush channel is three routes, and only HTTP.** Named exactly, with
   method, path and body, because revision 1 named two in the card and the third
   only in prose:
   - `GET /api/app/quiesce/wait` — held open by **every** window, from mount. On
     quiesce entry it answers `200 {"request":"flush","quiesceId":"<uuidv7>"}`;
     otherwise it stays open until the server resolves it.
   - `POST /api/app/quiesce/report` — body
     `{"quiesceId":"<id>","ok":boolean,"blockers":["conflict"|"save_error"|"recording"]}`.
   - `POST /api/app/quiesce` — body `{}`; starts a quiesce, returns
     `200 {"quiesceId":"<id>","ok":boolean,"blockers":[…]}` when it settles.
     It is the **same exported entry point** the shell's `quiesce{}` case calls:
     one function, two callers, not a test-only switch and not a fault-injection
     flag. Its authorization is Choice 1; whichever answer is approved is
     written into FD1 and into the C-BRIDGE@1 amendment.
   A fourth read-only sibling exists because FD7 hands one to P5.4 and V2 needs
   it: `GET /api/app/quiesce/status` → `{"quiescing":boolean,"activeJobs":[{"kind"}],"windows":number,"maintenance":boolean}`.
   There is **no** SSE event for this, **no** `BroadcastChannel` message
   (C-BRIDGE@1 rule 3: the page talks only to the server over HTTP) and **no**
   new browser API. A `quiesceId` is minted at quiesce entry (UUIDv7, the
   repository convention) and is the **only** thing that ties a report to a
   quiesce.
2. **Registration, reporting, and the client transport's whole lifecycle.** Five
   named rules, replacing revision 1's two contradictory ones:
   - **(a) Registration is the held-open `GET /api/app/quiesce/wait`.** Every
     window that mounts the reporter registers, *including* a window with no
     editor; such a window answers `ok` immediately once asked, **holding the
     request open until it is asked** — revision 1's "without holding a request
     open" is deleted, because it is exactly what makes the window invisible to
     the server and turns "no editor" into "no window".
   - **(b) Every window with an editor registers and reports**, primary or not.
     "The primary window is the only reporter" is deleted: the reporter is
     mounted once per window at `main.tsx`, outside `App.tsx`'s primary logic,
     and it cannot read `usePrimaryWindow`'s phase without editing `App.tsx`,
     which is in Must-not-edit. The stronger rule loses nothing — a covered
     secondary window is `inert` (`App.tsx:67-91`) and can hold neither unsaved
     text nor a microphone — and it is strictly safer.
   - **(c) A report is applied only when its `quiesceId` equals the in-flight
     quiesce's id *and* that window has a registered wait in the current
     quiesce.** Anything else — a stale id, a spoofed id, a report from a window
     that is not registered, a report for a quiesce that already settled — is
     **refused with 409, counted, and never applied**. This is F4's hole closed:
     without it, the ignored report from a timed-out quiesce satisfies the next
     one and the text it was protecting is lost with both rows green.
   - **(d) A closed socket removes that window's wait.** If the registered set is
     empty when the deadline ends, the quiesce returns `ok:false` with blocker
     `no_response`: **a disconnect is never read as `ok`**.
   - **(e) "No browser attached at all" is a named state, distinct from a
     disconnect**: the set has been empty since entry (shell up, window not yet
     loaded). It also returns `ok:false` with `no_response`, unless the owner
     names a different sourced answer. Both cases get a V1 case.
   - **(f) Transport lifecycle.** The reporter holds **exactly one** long-poll,
     armed with an `AbortController`, aborted on unmount, on `pagehide`, after a
     report is sent, and when the server resolves it at the deadline; it
     re-arms immediately after each of those. It **never** reuses, wraps or
     aborts the SSE reader in `web/src/api/sse.ts`. It calls
     `window.__apuntaFlushBeforeRelease` **if it is a function** and reports `ok`
     when it is not (that hook is deleted by its own owner cleanup,
     `NoteView.tsx:356`), so the reporter cannot throw on a torn-down editor.
     It is mounted once per window, never per route. Nothing kills it for it
     otherwise: `web/src/api/client.ts:55-58` applies no global timeout.
   - **A window that has not answered when the budget ends is a blocker named
     `no_response` and is never read as `ok`; a window that answers after the
     deadline is refused under (c).**
3. **One deadline, two concurrent phases.** The deadline is measured from the
   instant the quiesce begins — `deadline = now() + DRAIN_MS` — and the two
   phases run **concurrently**: the flush request is answered to every registered
   window **at entry**, not after the drain, and the drain runs alongside it.
   Each phase gets `deadline − elapsed`; the two phases never extend the budget
   between them. Revision 1 sequenced the report phase *after* the drain, so a
   drain that consumed the whole 30 s ended the quiesce before any window was
   ever asked to flush — the editor's unsaved text unrequested, no conflict ever
   detected, and `no_response` unable to fire because nobody had been asked. The
   drain's own exit is FD4's rule; the deadline resolves **every** outstanding
   wait at its end, so no request is left hanging past the budget.
4. **The drain's entry rule and its bound.** `DRAIN_MS = 30_000`, module-internal,
   **not exported**, not read from `process.env`, not in any request body, not
   settable by a caller or a route. Per Choice 2: the quiesce snapshots `active()`
   at entry; a non-empty snapshot returns `ok:false` at once with the still-active
   kinds as blockers and never enters the drain; an empty snapshot runs the drain
   — so a job already past the refusal hook still gets to finish — under the same
   bound, returning success when the registry empties and failure with the
   still-active kinds as blockers when the bound is reached. It never returns
   `ok:true` on a timeout and never waits past the bound. The clock seam is an
   options object on `buildApp` in the house style of `BackupOptions.now`
   (`server/src/backup/archive.ts:82`) — `{ now?: () => number; sleep?: (ms) =>
   Promise<void> }` — with production passing **nothing**, so a unit test drives
   the boundary in milliseconds and no 30-second test exists (§0.3). The
   contract sentence "waits up to 30 s" is an **upper bound**, and the entry rule
   above is the reading the owner approves; the amendment records both.
5. **Maintenance mode is left on every failure path, and re-entry is
   idempotent.** A quiesce that fails — an active job, a client `conflict`, a
   `save_error`, a `no_response` — returns `ok:false` **and puts the server back
   into normal service in a `finally`**, so the next request is not a 503 until
   restart. A second `quiesce` while one is in flight **joins** the first and
   returns its result; it does not nest, and no state is left set. A quiesce
   that succeeds leaves maintenance **on** in shell mode, because the next
   contract step (the snapshot) must not be able to write either; in browser mode
   it is held while at least one window is registered and released when the last
   one unregisters, if that is the Choice 1 answer approved.

   The **native** close request is a Tauri window event, so it belongs to

### 3.2 The one C-UPD@1 sentence (unchanged from revision 1, confirmed)

> **Quiescence.** The server enters maintenance mode: new jobs and writes get

close-policy sentence stay as C-UPD@1 wrote them.

### 3.3 F5 and F3, restated as one mechanism

Revision 1 had windows that "each hold a request open" (FD1) and windows where
"the primary is the only reporter" (FD3) — two rules that cannot both hold, in a
mount that cannot tell which window it is. Revision 2 has one rule (every window
registers, every window with an editor reports) and one mechanism (one deadline,
two concurrent phases, so the ask and the wait happen together). Both changes
make the card safer rather than looser: a window that could hold unsaved text now
reports it whatever its window role, and the ask can no longer be skipped by a
slow drain.

### 3.4 F4's hole, named

Without a correlation id, quiesce #1 timing out with its report in flight and
quiesce #2 starting means #1's report satisfies #2 — no window flushed for #2, and
the unsaved text #2 existed to protect is lost, with both rows green. FD2(c) makes
that report a 409, counted and unapplied; FD2(f) makes the deadline resolve every
outstanding wait; V1 names the case.

### 3.5 F6's three states, named

A window with no editor still registers and answers `ok` (FD2(a)). A registered
wait whose socket closes is removed, and an empty set at the deadline is
`no_response`, never `ok` (FD2(d)). A server with no browser attached at all is a
**distinct** state from a disconnect and also yields `no_response` (FD2(e)). The
review's failure — a *disconnected* client read as a spurious `ok` — is closed;
the cost of not naming it (a closed window burning the full 30 s) is closed too.

### 3.6 F8's boundary, decided

Every write at this base is now either a registry site with a line number or an
enumerated exclusion with a reason (FD8). `generate.ts` is in May edit because
