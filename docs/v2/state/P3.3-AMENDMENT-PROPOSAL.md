## 3. IR-03 — the server half of C-BRIDGE@1 has no owner in the card

producer instruction is "print the `ready` line" (`:23`) and its only named
environment variable is `APUNTA_SHELL=1` (`:24`). Meanwhile
`server/src/index.ts:59-62` today does `console.error(`${DATA_FOLDER_IN_USE}: …`);
process.exit(75)` — stderr, unstructured, and no shell to read it.

> `shutdown` from stdin when `APUNTA_SHELL=1`)
> ```

> **After**
> ```
> `server/src/index.ts` (print the `ready` line; read
> `shutdown` from stdin when `APUNTA_SHELL=1`; **and nothing else in this
> file** — call `writeFatal` at the two sites the next bullet names)
> ```

*May edit*, naming the test file the review noted was unnamed (IR-05's soft
spot):

> **Before**
> ```
> `server/src/shell-bridge.ts`
> (new) and test
> ```
> **After**
> ```
> `server/src/shell-bridge.ts` (new) and
> `server/src/shell-bridge.test.ts` (new)
> ```

*Fixed decisions*, one new bullet after the "Identity" bullet:

> - **The bridge wire format, fixed here because C-BRIDGE@1 fixes the shape and
>   the card has to name the parts.** Every line is one JSON object on the
>   child's **stdout**, written by `server/src/shell-bridge.ts`, and the shell
>   reads nothing else on that stream.
>   - `APUNTA_SHELL=1` means "a shell is listening": the ready line and the
>     stdin bridge are written **only** when it is set, so browser mode's
>     stdout is byte-for-byte today's stdout.
>   - `APUNTA_SHELL_NONCE` is the nonce's variable. The **shell** generates it,
>     sets it on the child, and accepts the ready line **only** if the line's
>     `nonce` equals it; a line with any other value is logged and ignored and
>     the shell never navigates. It is a distinct value from the C-OWN lock
>     nonce `acquireDataFolderLock` generates internally, and the two are never
>     compared, stored in the same place, or derived from one another — the lock
>     nonce proves folder ownership on disk, the bridge nonce proves this line
>     came out of this spawn.
>   - `fatal` carries `{"type":"fatal","code":…}` and **no nonce**: it is read
>     from the same trusted stdout stream, and C-BRIDGE@1 rule 2's shape has no
>     nonce field to add. The code set this card fixes is
>     **`data_folder_in_use`** and **`port_in_use`**, and no third. An unrecognised
>     code still shows the error screen, carrying the code verbatim.
>   - The code travels **only** as that JSON line. It is never parsed out of a
>     pino log line, never read from an exit status, and never matched on a
>     substring. A log line and a bridge line are different channels, and
>     guessing across them is the mistake that would make the app report
>     "port in use" for a folder that is already owned.
>   - An unknown **inbound** type from the shell is logged and ignored
>     (C-BRIDGE@1 rule 2).
> - **`writeFatal` is called at exactly two sites, and nowhere else.**
>   1. The exit-75 lock refusal, `index.ts:59-62`: call
>      `writeFatal('data_folder_in_use')` **before** `process.exit(75)`. The
>      existing `console.error` line stays — it is the log, and it is how P3.2's
>      own evidence proves the refusal; the bridge line is additional, not a
>      replacement.
>   2. The `catch` around `app.listen`, `index.ts:155-158`: when the error is a
>      listen failure whose `code` is `EADDRINUSE`, call
>      `writeFatal('port_in_use')` before exiting. **Every other error in that
>      `catch` keeps today's `app.log.error(error); process.exit(1)` exactly as
>      it is.** That `catch` also covers the daily-backup and open-browser calls,
>      and a failure in either of those is not a port clash; saying so is what
>      keeps the mapping honest.
>   `writeFatal` never binds, never serves a boot-error page and never returns;
>   the caller exits immediately after it.

*Fixed decisions*, the existing port bullet amended in place:

> **Before**
> ```
> - Production: port 7717 (E5); if the server exits with a port error, show the
>   error screen with code `port_in_use`.
> ```

> **After**
> ```
> - Production: port 7717 (E5). `port_in_use` is the code for **one** condition
>   only — the server could not listen because 7717 was already taken — and
>   `data_folder_in_use` is the code for **one** other condition: the data
>   folder is owned by a live Apunta (C-OWN@1, exit 75). The two are never
>   interchanged, and neither is ever inferred from the other. The bilingual
>   error screen carries whichever code arrived, and for C-OWN@1's rejection
>   example that is the screen saying Apunta is already open, not "port in
>   use".
> ```

*Fixed decisions*, one clause added to the splash bullet (the review's "brand A"
is a term used **only** in this card across all of `docs/v2`):

> **Before**
> ```
> - Splash (brand A, no text needed) until `ready`; `fatal` or early exit →
>   bilingual error screen with the code.
> ```

> **After**
> ```
> - Splash (the A mark, no text needed) until `ready`; `fatal` or early exit →
>   bilingual error screen with the code. "The A mark" is
>   `docs/v2/assets/apunta-a.currentcolor.svg` for the in-app colour rule or
>   `apunta-a.teal.svg` for a fixed-colour export, brand teal `#1f6f63` on the
>   `#f6f4ef` tile with the `#e3e0d6` hairline
>   (`docs/v2/assets/README.md`, Rules) — not the full app icon
>   `apunta-icon.png`, which is the 1024 px master the `tauri-icons/` set is
>   generated from. Rasterising it for the splash window is
>   `build-brand.py`'s job, which is already in the repo and touches no
>   network; the card does not run it and does not rebrand anything.
> ```

**Classification.** **Widens May edit** — one existing file's scope, widened
from two named changes to three, with the third pinned to two line-numbered call
