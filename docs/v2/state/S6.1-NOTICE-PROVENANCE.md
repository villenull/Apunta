## 3. The two questions the blanks turn on

### 3.1 What MPL-1.1 itself says about these fields

Source: Mozilla Public License 1.1, full text —
<https://www.mozilla.org/media/MPL/1.1/index.txt> (read 2026-10-01; this is the
same URL S1.5 §5 cites, unchanged).

§1.6, quoted (21 words, the whole quote budget of this file from this source):

> "Initial Developer" means the individual or entity identified as the Initial
> Developer in the Source Code notice required by Exhibit A.

Three consequences follow from that one definition. **They are not all
`[verified]`**, and the labels below are corrected on the report's own §1
definitions: `[verified]` is "read verbatim or near-verbatim on the cited page",
`[inferred]` is "reasoning, with the basis stated", and `[interpretation]` is "a
question of what the licence *means*". Consequences 2 and 3 are readings drawn
*from* the definition, not the definition itself, so they are labelled as such and
are not passed on as settled text.

1. `[verified]` The Exhibit A notice is the mechanism that *identifies* the Initial
   Developer. There is no separate register the distributor could consult
   instead, and no upstream field that is "the" authoritative value — the notice
   is the record.
2. `[inferred]` Therefore a blank is not a form to be filled in from a registry. It
   is a statement the distributor makes, and it is checkable against upstream.
   Basis: consequence 1, read against the fact that the upstream file leaves the
   fields blank (§3.2, Source A).
3. `[inferred]` §1.10: "Original Code" means source-form computer software code
   *as described in the Exhibit A notice*, and which, at the time of its release
   under the licence, is not already covered code. §3.5: the Exhibit A notice is
   to be duplicated in each source file, or, where a file's structure prevents
   that, placed where a user would be likely to look for it. Basis: the two clauses
   as read today, with their section numbers, paraphrased and not quoted.

`[interpretation]` — **not answered here.** Whether a Hunspell `.aff`/`.dic`
pair is "computer software code" and "Source Code" under §1.10/§1.11 is S1.5
§3.7 question 1 and remains a question for a Mexican lawyer.

**A scope finding the v2 proposal's first draft did not have, and whose current
text now carries.** Exhibit A is not two fields.
It is a fixed template with **four**: Original Code; Initial Developer of the
Original Code; "Portions created by … are Copyright (C) … All Rights Reserved";
and "Contributor(s)", followed by an alternative-licence paragraph that applies
only where a file is designated Multiple-Licensed. As first drafted,
`S6.1-AMENDMENT-PROPOSAL-v2.md` §8.5 and §11 item 2 spoke only of "two blanks"
and two `{{OWNER: …}}` placeholders, so an owner item drafted from §11 item 2
would have covered **half the template**. Both sections have since been corrected
to the four-field framing — §8.5 states the template and names the two fields
that have no upstream evidence, and §11 item 2 offers a decision per unresolved
field — and §13 stop 2 adds the outcome this file §4.2 describes. §4 below treats
all four, as it always did.

### 4.1 The one branch that is genuinely unresolved

`[interpretation]` — **not answered here.** "Original Code" is fixed by §1.10 as
code *as described in the notice*, so a distributor may legitimately describe the
bytes it actually ships. But if the normalisation constitutes a Modification, the
shipped bytes are not the Original Code, the Exhibit A notice attaches to the
*upstream* code, and the normalisation belongs in the Contributor line instead.
Both readings are available on the sources read today; nothing read today
settles it. **Consequence: the candidate string in the table above is a template
whose final clause depends on that ruling, and the ruling is the owner's, on
advice.** No agent fills it either way.

### 4.2 What this means for the owner item, as it stands now

`S6.1-AMENDMENT-PROPOSAL-v2.md` §8.5 and §11 item 2, **as first drafted**,
presented the two blanks as strings only the owner could supply, with option (a)
"the owner supplies both strings" recommended; both have since been corrected to
the four-field framing and the adopt-the-attribution decision this research
supports, and no option in §11 item 2 now asks the owner to author a name for the
Initial Developer field. This research supports the narrower and more accurate
framing, which is the one the proposal now carries:

- The **Initial Developer** field is not an owner-supplied string. An
  authoritative, `es_MX`-specific upstream statement supplies a name, and the
  project owner's name must **never** be substituted for it — the owner
  distributes the code, they did not first release it. §3.5 in paraphrase allows
  the distributor to add *their own* name, and only as a **Contributor**; that is
  the one place an owner name would ever belong, and it is optional.
- What remains for the owner on that field is a **decision** (adopt the upstream
  attribution) rather than an invention.
- The **Original Code** field's descriptive half is sourced; its scope half is a
  legal question (§4.1).
- **Two of the four fields have no upstream evidence at all** (§4 table). The
  v2 proposal's first draft did not raise them; its current §8.5 names exactly
  those two fields, and §11 item 2(a) records them as `[unknown]` with their next
  steps and states that they leave the notice unshippable, with §13 stop 2 and
  §8.5 naming `BLOCKED` as the only other outcome. **That remains the honest
  position and nothing here closes it:** both fields are still `[unknown]`, both
  still need separately authorised evidence, and no agent fills either.
  - **Partly superseded 2026-10-06.** The *evidence* half of that sentence no
    longer holds: §7.3 supplies the `es_MX` copyright statement (U2) and §7.4
    measures the normalisation (U3's facts). What is still open is the *ruling*
    those facts feed — plus the pre-existing `[interpretation]` on the Original
    Code field. So §8.5's two outcomes are unchanged: an unresolved field means
    the notice is not written and the card is `BLOCKED`. Nothing in §7 changes
    that, and no field is filled by an agent.

**This file proposes no incomplete notice and no shipment path.** If any field
lacks a sourced value, the outcome is that the notice is not yet shippable and
the card is `BLOCKED` — which the v2 proposal already states for its own case.
