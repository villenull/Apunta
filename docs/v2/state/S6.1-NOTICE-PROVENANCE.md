## 3. The two questions the blanks turn on

### 3.1 What MPL-1.1 itself says about these fields

Source: Mozilla Public License 1.1, full text —
<https://www.mozilla.org/media/MPL/1.1/index.txt> (read 2026-10-01; this is the
same URL S1.5 §5 cites, unchanged).

§1.6, quoted (21 words, the whole quote budget of this file from this source):

> "Initial Developer" means the individual or entity identified as the Initial
> Developer in the Source Code notice required by Exhibit A.

`[verified]` Three consequences follow from that one definition, and each one is
a plain reading rather than an interpretation:

1. The Exhibit A notice is the mechanism that *identifies* the Initial
   Developer. There is no separate register the distributor could consult
   instead, and no upstream field that is "the" authoritative value — the notice
   is the record.
2. Therefore a blank is not a form to be filled in from a registry. It is a
   statement the distributor makes, and it is checkable against upstream.
3. Paraphrase, §1.10: "Original Code" means source-form computer software code
   *as described in the Exhibit A notice*, and which, at the time of its release
   under the licence, is not already covered code. §3.5: the Exhibit A notice is
   to be duplicated in each source file, or, where a file's structure prevents
   that, placed where a user would be likely to look for it.

`[interpretation]` — **not answered here.** Whether a Hunspell `.aff`/`.dic`
pair is "computer software code" and "Source Code" under §1.10/§1.11 is S1.5
§3.7 question 1 and remains a question for a Mexican lawyer.

**A scope finding the v2 proposal does not have.** Exhibit A is not two fields.
It is a fixed template with **four**: Original Code; Initial Developer of the
Original Code; "Portions created by … are Copyright (C) … All Rights Reserved";
and "Contributor(s)", followed by an alternative-licence paragraph that applies
only where a file is designated Multiple-Licensed. `S6.1-AMENDMENT-PROPOSAL-v2.md`
§8.5 and §11 item 2 speak only of "two blanks" and two `{{OWNER: …}}`
placeholders. Any owner item drafted from §11 item 2 therefore covers **half the
template**. §4 below treats all four.

### 4.1 The one branch that is genuinely unresolved

`[interpretation]` — **not answered here.** "Original Code" is fixed by §1.10 as
code *as described in the notice*, so a distributor may legitimately describe the
bytes it actually ships. But if the normalisation constitutes a Modification, the
shipped bytes are not the Original Code, the Exhibit A notice attaches to the
*upstream* code, and the normalisation belongs in the Contributor line instead.
Both readings are available on the sources read today; nothing read today
settles it. **Consequence: the candidate string in the table above is a template
whose final clause depends on that ruling, and the ruling is the owner's, on
advice.** No agent fills it either way.

### 4.2 What this means for the owner item as currently drafted

`S6.1-AMENDMENT-PROPOSAL-v2.md` §8.5 and §11 item 2 present the two blanks as
strings only the owner could supply, with option (a) "the owner supplies both
strings" recommended. This research supports a narrower and more accurate
framing:

- The **Initial Developer** field is not an owner-supplied string. An
  authoritative, `es_MX`-specific upstream statement supplies a name, and the
  project owner's name must **never** be substituted for it — the owner
  distributes the code, they did not first release it. §3.5 in paraphrase allows
  the distributor to add *their own* name, and only as a **Contributor**; that is
  the one place an owner name would ever belong, and it is optional.
- What remains for the owner on that field is a **decision** (adopt the upstream
  attribution) rather than an invention.
- The **Original Code** field's descriptive half is sourced; its scope half is a
  legal question (§4.1).
- **Two of the four fields have no upstream evidence at all** (§4 table), which
  the v2 proposal does not currently raise.

**This file proposes no incomplete notice and no shipment path.** If any field
lacks a sourced value, the outcome is that the notice is not yet shippable and
the card is `BLOCKED` — which the v2 proposal already states for its own case.

### 4.3 The verification is only possible because Apunta writes the notice

`[verified]` The upstream notice is **not preserved in the bytes Apunta ships**.
Direct observation today of the two files at
`raw.githubusercontent.com/wooorm/dictionaries/main/dictionaries/es-MX/`:

- `index.aff` **begins** `SET UTF-8` / `FLAG UTF-8` / `TRY …` — no `#` comment
  block, no AUTOR text, no copyright line, nothing.
- `index.dic` **begins** `58263` (the word count) then the word list — no header.

Compare Source C: upstream's own affix source *does* carry a comment header with
its copyright line and its licence statement. The normalisation strips it.
`[inferred]` So "preserve the upstream notice" is not available as an option:
there is nothing in the shipped data to preserve. Apunta must **reproduce** the
notice in its own documents, which is the same conclusion S1.5 §3.5 item 4
reached from the other direction.

`[unknown]` Whether the **published tarball** carries `license`: Source D's
`files` array omits it, the registry reports `fileCount: 7`, and the seven are
accounted for by the five listed files plus npm's always-included `package.json`
and the readme. That is arithmetic, not proof. Today it cannot be closed: no
cached copy of the package exists on this machine (§2). **Next step:** after the
acquisition the owner authorises, read the installed tree — one `ls`, no further
download, and it settles the point for `2.0.0` permanently.
