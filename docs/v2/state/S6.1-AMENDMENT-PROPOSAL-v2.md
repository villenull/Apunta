## 0. The same thing in plain English

1. The card fixes a Spanish-aware word splitter, but the splitter lives in a file
   the card is not allowed to touch, so today every accented Spanish word would
   be cut in half. This proposal names the files that must be editable, and
   nothing more.
2. The card promises Spanish keeps its own list of "words I always accept" and
   that the English list carries over untouched. It never says where that list
   is stored. This proposal fixes the storage, says the English list is read and
   never rewritten, and says what happens to a word added in Spanish. **No
   database migration exists and none is created.**
3. The card promises "if the dictionary will not load, show an error and let
   typing continue" and there is no way to show an error today: the app
   deliberately says nothing, and any message the therapist reads has to exist
   in both languages. This proposal names the state, its **type**, the exact
   message key with **both** languages written out, the surface it appears on,
   and the tests that prove it.
4. Two of the card's four checks are not commands, and the two browser rows in v1
   asserted a **package path** that the production build rewrites into a hashed
   asset name — so those rows would have gone red for a reason that has nothing
   to do with the code. This proposal makes every row an executable command and
   makes the asset rows observe **what the build actually emitted**, with a
   positive fetch proof so a green negative cannot mean "the file was never
   reachable".
5. Adding the Spanish word list is the one thing this project has ever been
   allowed to ship under a copyleft licence, and the owner has never said so in
   writing. This proposal stops the card until the owner answers, and asks three
   questions, all three of them the owner's alone.

## 4. Design decision 1 — storage shape and the read rule (D3)

**Storage.** Settings is a flat key → JSON-value store
(`shared/src/settings.ts:6-18`: "later packets add keys … without a migration"),
and keys must match `/^[a-z][a-z0-9_]*$/`, so a key cannot be spelled `es-MX`.
The two lists are therefore two keys:

| Locale | Key | Value |
| --- | --- | --- |
| `en` | `spelling_words` (unchanged, `shared/src/spelling.ts:16`) | JSON array of strings, exactly as today |
| `es-MX` | `spelling_words_es_mx` (new) | JSON array of strings |

**Read rule, stated so there is nothing to guess.**

1. The active list is chosen by the **active UI language** (`language` setting),
   not by a note's locale and not by the text in the field. One checker, one
   dictionary, one list.
2. `en` reads `spelling_words`. `es-MX` reads `spelling_words_es_mx`; an absent or
   malformed value reads as `[]`, which needs **no new code** —
   `spellingWordsFrom` (`shared/src/spelling.ts:22-31`) already reads
   defensively and is reused as-is.
3. **A Spanish list is never seeded from the English list.** The two are
   independent: a word she adds in Spanish is not silently accepted in English,
   and vice versa.
4. `stt_vocabulary` (`shared/src/transcribe.ts:99`) is **not** part of this change.
   It is a transcription vocabulary — a medication or a name she taught whisper —
   and it stays applied in both languages, exactly as today. It is named here so
   nobody mistakes it for the second half of a migration.
5. `MAX_SPELLING_WORDS = 1000` and `MAX_SPELLING_WORD_CHARS = 60` keep their
   values and now apply **per key**, i.e. per locale. Both lists may hold 1000.
6. **No stored value is rewritten. There is no migration.** No backfill, no
   delete, no schema change, no new migration file in `server/migrations/`.
   `spelling_words` is read as the English list and is written back only when she
   adds an English word, as an array — the shape it already has. `PUT
   /api/settings` merges (`shared/src/settings.ts:21`), so writing the Spanish key
   cannot clobber the English one. If a future card ever changes the stored shape,
   that is that card's work, and this card is its evidence that the English list
   was never disturbed.

**The race guarantee, which the card must state next to this rule.** A word list
is selected by the language at the moment the settings snapshot arrives, and the
provider keeps one `added` list. On a language change the provider swaps the
active key **before** the dictionary load starts and clears the previous locale's
list, so a stale snapshot cannot repopulate the wrong language's list after the
switch. **The word-list half of that guarantee is a case of its own, not a
consequence of the speller one:** a settings snapshot taken under `en` and
delivered after a switch to `es-MX` must leave the active list empty, and a
snapshot taken under `es-MX` and delivered after a switch back to `en` must not
clear the English list or write `spelling_words_es_mx` into it (V1(i)). V1(f)
proves the other direction, for the speller (§5 item 3).

**One sentence for the card, in the implementer's own words:** *the existing
English list migrates unchanged to `en`* means *it is read as `en`'s list and is
never moved, converted or rewritten*, **not** *a migration runs*.

## 5. Design decision 2 — the dictionary-load error surface (D4)

Today `SpellingProvider.tsx:79-81` swallows the failure on purpose
(`// No dictionary, no marks. The editor is entirely usable without them.`) and
the `Spelling` interface (`:21-31`) has no error field, so nothing *can* show
one. The card's promise therefore needs four things named, and all four are new
code.

1. **State, and its type.** `Spelling` gains

   ```ts
   /** The catalogue key to tell her about, or null. Never a literal. */
   readonly error: MessageKey | null;
   ```

   `MessageKey` is `keyof typeof en` (`shared/src/i18n/t.ts:50`), already exported
   at `shared/src/index.ts:566`. Typing the field as the key union rather than
   `string` is what makes a typo in the key a **`npm run typecheck` failure**
   instead of a raw string reaching the UI. `null` means no failure. It is set
   when a locale's dictionary load rejects, cleared on the next successful load,
   and reset to `null` on a language change **before** the new load starts. The
   `INERT` default (`:33-38`) gains `error: null`.

2. **Behaviour while failed — unchanged from today, and stated as such.**
   `speller` stays `null`, no marks are drawn, `findMisspellings` is never called,
   `addWord` and `ignoreWord` still work, and typing is untouched. The card's
   phrase "leaves typing usable" means *exactly* today's behaviour, not a
   degraded mode.

   **The no-retry fact, stated so it is not "fixed" by accident.**
   `ensureLoaded` sets `loadingRef.current = true` and clears it nowhere
   (`SpellingProvider.tsx:72-82`), so a failed load is **never retried** for the
   life of the tab. That is compatible with "leaves typing usable" and with the
   card as written; the card says so explicitly. Making it retryable is a
   behaviour change nobody has asked for and is **out of scope here**.

3. **The race guard is new code, and the card must say so.** The provider today
   has only `mountedRef`; there is **no** request id. The card's own Fixed
   decision ("a request id guards against an old language's load finishing after a
   switch") is therefore a promise with no implementation today, and V1(f) is a
   test of new code, not of an existing one. The guard is a monotonic counter
   incremented on every load start and on every language change; a resolved load
   installs its speller and clears `error` **only if** its own id is still the
   current one. V1(f) asserts both directions: a late `en` load does not install
   after a switch to `es-MX`, and a late `es-MX` failure does not set `error` after
   a switch back to `en`.

4. **Surface.** `web/src/components/SpellLayer.tsx` renders one line per
   **mounted** spell surface, in the editor's own wrap, immediately above or below
   the editor, with `role="alert"`, using `t('spelling.loadFailed')`. It is
   rendered by the shared spell layer rather than by the menu, because with no
   dictionary there are no marks and therefore no menu to open.

   The wording is **one alert per mounted spell surface, not "one line, once"**:
   `SpellLayer` is mounted once per field (`ChatComposer.tsx:60`,
   `NoteBody.tsx:137`, `PatientRenameField.tsx:72`, `AddPatient.tsx:114`,
   `Capture.tsx:447`), so a note page with the chat open renders it twice and
   `role="alert"` fires per mount. Naming a single mount point above them is a
   larger change and is not this card's.

## 6. Design decision 3 — locale-specific spec selection, and the coverage it keeps (A3, X1, review §B)

**The problem is real.** `e2e/playwright.config.ts:107-113` re-runs every spec
except `language-control.spec.ts` a second time in the `es-MX` project, against a
server started with `APUNTA_DEV_SPANISH=1`, whose data folder is shared with —

**Suppressing the English spec in the `es-MX` project is not suppressing a

1. **Project-scoped and minimal**, exactly as above.
2. **The English coverage that is lost is named, and replaced — and what is

## 7. Design decision 4 — NFC tokenisation that leaves English provably unchanged (D1, D6, F1)

`web/src/lib/spelling.ts:27` is `const WORD = /[A-Za-z]+(?:['’][A-Za-z]+)*/g` and
`plainWord` (`:37-39`) only folds `’` to `'`. `allowedWords` (`:160-167`)
re-tokenises every allow-list entry with the same pattern. That is why `José` in a
note becomes `Jos`, why `José Ramírez` in the allow-list contributes `jos` +
`ramirez`, and why `¿Cómo` yields `C` + `mo`.

The card's replacement text, which is small and checkable:

```ts
/**
 * A word: English letters plus the Spanish ones the es-MX dictionary needs,
 * and any combining marks a keyboard or an IME may leave attached — so a word
 * typed as `sesio` + U+0301 is one token, not two.
 *
 * The ASCII letter range comes first and is unchanged, so for text carrying
 * **no Spanish letter and no combining mark (U+0300–U+036F)** this pattern
 * matches exactly what the old one matched, and `plainWord` is a no-op on such
 * text: English tokenisation is provably unchanged. The precondition is those
 * two classes, not the word "ASCII": the combining-mark range below is admitted
 * too, and `'` and `’` are inside the pattern in both versions. `spelling.test.ts`
 * asserts the parity on a corpus meeting it.
 */
const LETTER = '[A-Za-zÁÉÍÓÚÜÑáéíóúüñ\\u0300-\\u036f]';
const WORD = new RegExp(`${LETTER}+(?:['’]${LETTER}+)*`, 'g');
```

```ts
function plainWord(word: string): string {
  // NFC first, so a decomposed `sesión` and a precomposed one are the same
  // word; then the curly apostrophe, which is not part of any word.
  return word.normalize('NFC').replace(/’/g, "'");
}
```

**F1 is closed and it is load-bearing**: the class admits U+0300–U+036F combining
marks, which are not Spanish letters and which the old ASCII pattern did not
match. So the parity claim is about text carrying **no Spanish letter and no
combining mark** — the two classes the new pattern admits and the old one does
not. It is deliberately **not** phrased as "ASCII-only text": the corpus V1(a)
specifies contains `’` and an em dash, so "ASCII-only" is unsatisfiable for it.
The curly apostrophe is **inside** the precondition (the old pattern matches `’`
inside a contraction exactly as the new one does) and so is the em dash (neither
pattern matches it). A parity case run over accented or decomposed input would
not prove what the comment claims.

Five properties the card states, because each is a way this could go wrong:

- **Normalisation is per matched word, never on the whole text.** `Misspelling`
  carries `[start, end)` character offsets into the **original** text
  (`spelling.ts:19-24`) and they drive the caret and the menu
  (`replaceRange`, `:59-61`; `misspellingAt`, `:55-57`). NFC applied to the whole
  text would change the length of a decomposed string and shift every offset after
  it. Per-word normalisation leaves every offset exact, and V1(c) asserts that
  the returned offsets index the original string in both the precomposed and the
  decomposed case. **What is normalised is the value handed to the speller and
  nothing else:** `Misspelling.word` stays the **raw matched substring of the text
  being scanned** (unchanged from `spelling.ts:49`), and the **original text is
  never normalised** — not before tokenising, not after, not for comparison. That
  is what makes `original.slice(m.start, m.end) === m.word` and
  `m.end - m.start === m.word.length` true of every word in *both* encodings, and
  it is why the cross-input half of V1(c) compares `{plainWord(m.word)}` rather
  than the raw `m.word`, which is one code unit longer per decomposed letter.
- **No accent folding, ever.** `ñ` stays `ñ`; there is no `NFD`, no
  diacritic-stripping and no transliteration anywhere in the path. This is the
  card's "without removing accents", and it is testable: V1(c) asserts that a
  decomposed input and a precomposed input give **the same NFC-normalised words**
  and the same flagged set (the two inputs are deliberately **not** byte-identical
  — per-word NFC is what keeps every offset indexing the original, so the token
  after the accented word starts one code unit later in the decomposed string),
  and §9.1's table asserts accented words are not flagged at all.
- **`¿` and `¡` are not letters.** They are outside the class, so they are
  punctuation, and a word after them is matched whole.
- **The allow-list gets the same treatment for free**, because `allowedWords`
  calls the same `WORD` and the same `plainWord`. That is what makes a typed
  `José` match an allow-listed `José Ramírez`, instead of `Jos` matching `jos`.
- **The suggestion alphabet is deliberately left alone** (`spelling.ts:123`,
  `LETTERS = "abcdefghijklmnopqrstuvwxyz'"` — quoted exactly as it stands), because
  widening it would change English suggestions. With it unchanged, an accent-only
  correction comes from `nspell`'s own suggester behind the neighbour search,
  which is the existing fallback, and V2's non-empty-menu assertion is what tests
  it. **This is a note, not a question:** leaving `LETTERS` alone is the status
  quo and the status quo needs no authority (review §E, OD-6).

### 8.2 The version pin, and the install that puts it in the lockfile (D8, A6, A7)

**The pin.** `web/package.json` gets `"dictionary-es-mx": "2.0.0"` — exact, no
caret — which is the same string `shared/src/i18n/locales.ts:74` already carries
and `locales.test.ts:52-59` already asserts. **F2 correction:** the card should
**read** that pin, not invent one; C-LANG@1 clause 2's locale table
(`docs/v2/CONTRACTS.md:292-299`) says *"per S1.5"* and does not itself fix the
version. V1 and V4 assert the three copies agree: `locales.ts`, the resolved
lockfile entry, and the installed `node_modules/dictionary-es-mx/package.json`
version. A mismatch is a `FAIL`.

**The install (A6).** v1 named the `npm install` only as a side effect in the
checkpoint; no row and no Fixed decision contained the command, while V4's whole
licence half depends on the lockfile carrying the package. It is now an explicit
Fixed-decision step, in order, and it runs **after** Stop 1 has cleared:

```
Step 1 (Fixed decision). Edit web/package.json: add "dictionary-es-mx": "2.0.0".
Step 2 (Fixed decision). Install it, from the repository root:
  npm install --workspace @apunta/web --save-exact --no-audit --no-fund dictionary-es-mx@2.0.0
Step 3 (Fixed decision). Record Step 2 in the checkpoint's sideEffectsDone, at
        that moment, with its exit code.
```

Why each flag:

- `--workspace @apunta/web` — `web/package.json` is `"name": "@apunta/web"`, and
  the data files must land where `web/src/lib/speller.ts` addresses them
  (`new URL('../../../node_modules/…')`), i.e. hoisted to the root
  `node_modules`, which npm does for a single occurrence.
- `--save-exact` — guarantees the `"2.0.0"` of Step 1 rather than a caret, so the
  three-copies-agree check of V4 cannot be satisfied by a range.
- `--no-audit --no-fund` — keeps the acquisition to the one host A11 admits.
  **A11's guard, restated:** source `npm` registry only, redirect hosts `n/a`,
  allowed query keys `none` — so a query string is refused (`query_not_allowed`)
  before the URL is requested (`ACQUISITION.md` "Redirect admission", rule 1), and
  a redirect anywhere but `https:`/443/no-user-info/no-fragment is not admitted.
  Nothing else in this card may touch the network, and `installer/` is untouched,
  so the model downloader's allow-list and the server's egress guard are exactly as
  they are.
- The version is **exactly** `2.0.0`. Not `@latest`, not a range, not a bump.
- **Integrity.** A11 requires a digest; `ACQUISITION.md:5-7` accepts *"SHA-256
  (**or** the package manager's integrity string)"*. S1.5 §2.2 records the
  registry `dist.integrity` for `2.0.0` as
  `sha512-EkRPJAgPhY55oMiHqwEBavOpokkvXlOO5jOdwZJmV/B6w9pGpJxlm7YorgHjiB2HqyPGW0FRcOoJRBTspTXUEA==`
  and shasum `30fb094031481fff76cf0fd40bcfd9163149bc00` `[verified]` from
  `https://registry.npmjs.org/dictionary-es-mx`. **V4 compares the lockfile's
  recorded `integrity` for `node_modules/dictionary-es-mx` against that string
  byte for byte** — a mismatch is a `FAIL` and the install is reported, not
  re-pinned. A per-file SHA-256 of `index.aff` / `index.dic` is **optional** and
  may be computed from the installed files with no further download; if it is not
  computed, the evidence records `[not computed]` with the reason, which is an
  honest record and not a gap. The **tarball** digest is not required and is
  recorded the same way if not computed (v1 §2.3's correction of D14 stands, and the review agrees).

**A residual the owner should know about, stated rather than fixed.** The exception
maps are keyed by **package name with no version component**
(`collect-licenses.mjs:48`), so a future bump to a version with a different
licence string would still pass the guard on a stale election. Adding a version
component changes the guard's semantics — stricter, never less — and is therefore
a plan-editor action, recorded as a **follow-up** under §12 item 3, not a question
for this card and not an owner question. The card's own contribution is to make
the bump loud: the `docs/decisions.md` row states the election **at a version**,
and V4's one-row diff means any bump shows up as a change to that row.

### 8.5 The four fields of the Exhibit A template (v1's OD-2)

The notice is not two blanks. It is a **fixed template with four fields**, in the

Original Code is ______."*, then a *"Portions created by … are Copyright (C) …

and its §4 table records, field by field, what the sources support and what they
do not. **Two of the four have no upstream evidence at all on the sources read:**
the *Portions created by …* copyright line and the *Contributor(s)* line. S1.5
§3.7 Q2 records that naming a person in a shipped notice is the owner's call and
that the upstream file itself leaves the fields blank.
