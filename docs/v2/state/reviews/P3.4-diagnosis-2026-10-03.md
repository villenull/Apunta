## (a) The invariant is reachability, and the card's assertion is unsatisfiable by construction

### What Tauri v2 actually injects — local crate source, `tauri = "=2.12.1"`

`src-tauri/Cargo.toml:14`, pinned in `src-tauri/Cargo.lock:3656-3658`. Read at
`~/.cargo/registry/src/index.crates.io-*/tauri-2.12.1/`:

- `src/manager/webview.rs:167-180` — pushed into the **main frame of every
  webview**, unconditionally (no capability, config or feature gate):
  `Object.defineProperty(window, 'isTauri', {value:true})` and, `if
  (!window.__TAURI_INTERNALS__)`, `Object.defineProperty(window,
  '__TAURI_INTERNALS__', { value: { plugins: {} } })`.
- `src/manager/webview.rs:181-192` — `metadata` on the same object.
- `src/manager/webview.rs:158-165` and `:195` push
  `initialization_script(...)`, which renders `scripts/init.js` →
  `scripts/core.js` (`:398-426`), and `scripts/core.js:81` does
  `Object.defineProperty(window.__TAURI_INTERNALS__, 'invoke', …)`. Also
  unconditional. `src/app.rs:1652-1668` builds that script in `Builder::new()`,
  before any user code runs.

So in **any** Tauri v2 webview, shipped or not, `typeof
window.__TAURI_INTERNALS__ === 'object'` and `typeof
window.__TAURI_INTERNALS__.invoke === 'function'`. No configuration value removes
it. There is nothing to fix in the app or in `tauri.conf.json`: the card's second
conjunct demands a value the stack cannot produce.

The only knob is `withGlobalTauri`, set `false` at
`src-tauri/tauri.conf.json:8`. It governs the **global API bundle**, whose last
statement is `window.__TAURI__=__TAURI_IIFE__` (`scripts/bundle.global.js`, final
line). The page reported `tauri=undefined` and `tauriInternals=object` — that is
exactly the knob working and the always-injected stub being present. The recorded
observation is the correct observation of a correct build.

### What C-BRIDGE@1 rule 4 actually requires

`docs/v2/CONTRACTS.md:223-224`: "**No Tauri IPC from web content.** No
capabilities for any webview origin, `withGlobalTauri: false`, no custom
`invoke_handler` commands." Three conjuncts, all of them about **authorisation
and reachability**, none of them about the absence of a global:

1. **No capabilities for any webview origin** — `"capabilities": []`
   (`src-tauri/tauri.conf.json:10`), asserted by V3's greps (V3 PASS).
2. **`withGlobalTauri: false`** — the `tauri=undefined` half of (a), which is the
   one half the stack satisfies and the one that is now **proven in the shipped
   binary**.
3. **No custom `invoke_handler` commands** — there is no `.invoke_handler(` in
   `src-tauri/src/main.rs`; `Builder::default()` keeps the default
   `invoke_handler: Box::new(|_| false)` (`src/app.rs:1661`). The only plugin
   registered is `single-instance` (`src-tauri/src/main.rs:108`), whose commands
   would also need a capability.

With no capability resolved, the ACL denies every command, so the internals
object is a transport stub with no reachable command behind it. **Its presence
is not a rule-4 breach.** The card's `(a)` conflates "no IPC from web content"
with "no IPC object in the webview", and only the second half is unsatisfiable.

The implementer was right to record FAIL rather than reinterpret: HS-7 forbids
loosening a check to make a result pass, and the card itself anticipates the
question ("a config-level grep of the bundled web bundle … [is] weaker and [is] a
**report**", `docs/v2/cards/P3.4.md:241` and `:592`). Deciding how to amend (a)
is a coordinator call.

### Recommended repair for (a) — a card amendment, strictly stricter

Keep the conjunct the stack can satisfy and replace the one it cannot with a
runtime fact that is stronger than the thing it replaces:

- **keep** `tauri === 'undefined'` — the `withGlobalTauri: false` proof;
- **replace** `tauriInternals === 'undefined'` with an in-page **reachability**
  fact: the hook calls `window.__TAURI_INTERNALS__.invoke('<some core command>')`
  and publishes the outcome, and (a) passes only when that call is **rejected**.

This keeps (a) a runtime fact read out of the rendered app page — not a config
grep, which the card forbids as a substitute — and it tests the thing rule 4
actually claims: that the object which is present in every Tauri webview is not a
live door. It adds a conjunct, so it tightens the row rather than loosening it,
which is what HS-7 requires. It needs one line in `readFacts`
(`web/src/main.tsx:69-93`) plus the card amendment; it lands inside the existing
single gate and single poll, so it does not disturb the P3.5 seam
(`web/src/main.tsx:39-184`, `docs/v2/state/cards/P3.4.json:94-101`).

## (d) The fixture insertion, and why the click produced no observation

### What the fixture insertion actually did

`createFixtureNote` (`scripts/v2/tauri-security.test.mjs:579-608`), called at
`:836` **before** the observation gate and before the reload:

1. `POST /api/formats` `{"name":"Progress note","sections":["Subjective","Plan"]}` →
   201; its `id` is the `format_id`.
2. `POST /api/patients` `{"name":"John Smith"}` → 201; its `id` is the `patient_id`.
3. `POST /api/notes` `{patient_id, format_id, content: <the ```md fence of
   e2e/fixtures/csp/injection-probe.md>}` → 201. The fence is located by
   pattern, not by line numbers (`:560-565`), so the fixture's own prose cannot
   reach a note.

All three carry `origin` and `sec-fetch-site: same-origin` (`:584`). The format
must come first because a fresh sandbox data dir has no `note_formats` row and
`web/src/routes/Workspace.tsx:527-530` renders `<Navigate to="/onboarding/format"
replace />` when formats are ready and empty — which is why attempt 3 had no
patient row to click at all. Creating the fixture first and issuing one `ctrl+r`
(`:838-841`) is the fix, and it worked: assertion 7 PASS.

That `ctrl+r` also settles one hypothesis in the app's favour.
`xdotool key --window` uses **XSendEvent** (the key path in libxdo is
`XSendEvent: Sending key …`), and WebKitGTK processed it: a `John Smith`
rectangle exists at all, and `Workspace.tsx` re-fetches only on
`visibilitychange` (`:196`), which a WM-less Xvfb never raises. So **synthetic
input does reach this webview**, and "the click was never delivered by X11" is a
weak explanation.

### Why the failure message cannot say more than it says

The hook publishes facts and rectangles **only when their signature changes**
(`web/src/main.tsx:133-140` and `:171-180`). So "nothing changed" is the only
thing this instrument can observe, and `clickAndWaitForChange`
(`scripts/v2/tauri-security.test.mjs:730-755`) reports it as "so it did not land".
Three concrete gaps make the recorded FAIL undiagnosable rather than merely
unhappy:

1. **`clicked.ok` is discarded.** `clickAt` computes `ok` from an `XError` in
   xdotool's output (`:709-723`); `clickAndWaitForChange` uses only the
   coordinates and never reads `ok` (`:736-751`). A dispatch that failed is
   reported identically to a click that was delivered and ignored.
2. **No coordinate-space conversion — the leading cause.** `readRects` publishes
   `getBoundingClientRect()` values, i.e. **viewport** CSS pixels
   (`web/src/main.tsx:104-110`), and the harness passes them **unchanged** to
   `xdotool mousemove --window <id> x y click 1` (`:709-722`), which is
   **window**-relative: the installed xdotool(1) says "Coordinates 0,0 are at the
   top left of the window you choose", and the move is an `XWarpPointer` (present
   in libxdo's symbol set alongside `XTestFakeButtonEvent`, which the bare `click
   1` uses). The two spaces coincide only when the webview's content area starts
   at the X window's origin. **This exact mismatch was already identified in
   review and left "to the harness"** — "Client-rectangle vs window coordinates …
   the conversion is left to the harness" (`docs/v2/state/reviews/P3.5-ir2.md:562-565`)
   — and P3.4's harness never implemented the conversion.
3. **The window is decorated, so the content origin is displaced.** `show_main`
   sets `.title("Apunta")`, `.inner_size`, `.min_inner_size`, `.position` and
   **never** `.decorations(false)` (`src-tauri/src/main.rs:471-490`; contrast the
   splash at `:445`). On `xvfb-run -a -s '-screen 0 1400x1000x24'`
   (`scripts/v2/tauri-security.test.mjs:373-383`) there is **no window manager**,
   so GTK falls back to client-side decorations and the webview's viewport origin
   sits below a CSD titlebar (~26-40 px) relative to the window origin.

   The geometry is computable from the tree: display 1400x1000, scale 1 →
   window 1216x817 at (35, 91.5) (`src-tauri/src/main.rs:543-573`, `MARGIN 0.95`,
   `WANTED_WIDTH/HEIGHT` 1280x860 at `:71-72`). The click therefore landed at
   page coordinates `(99 − ox, 284 − oy)` where `(ox, oy)` is the content origin
   in window coordinates. With `oy` ≈ the CSD titlebar, that is page y ≈ 244-258
   — tens of pixels **above** the leaf rectangle the click was aimed at, which is
   exactly the failure signature recorded: no navigation, no new fact, no new
   rectangle. Had it landed on a neighbouring row instead, the page *would* have
   changed and the harness would have seen it.

   **This is the leading hypothesis and it is not measured.** Measuring `oy` needs
   the app launched, which is out of scope here, and no rerun is authorised. Its
   falsifiable prediction: a click ~`oy` lower would land; a click at the page
   origin converted correctly would land. The attempted `xdotool windowfocus
   --sync` changed nothing (evidence `:175-179`), which is consistent — focus does
   not move the pointer, and it was never going to correct a coordinate offset.

Two smaller harness facts, relevant to any repair:

- **The landing proof is weaker than the card's.** The card requires that "a click
  that landed is proved by the published **fact set** changing, specifically
  `scriptText` turning true" (`docs/v2/cards/P3.4.md:542`). The harness also
  accepts a `rectSignature` change (`:741`) and passes `undefined` as the patient
  click's predicate (`:1050`). A rectangle change on its own — a scrollbar, an
  animation, a clock, a late layout shift — would satisfy it without the click
  landing. That is a check that can pass without proving its claim, and it should
  be tightened to the card's own fact predicate rather than loosened.
- **Rectangle keys collide across batches.** `readObservations` keys rectangles by
  the index **within** a batch (`i<n>_l`, `:650-656`) while the hook numbers them
  per batch of 40 (`web/src/main.tsx:118-128`). Batches 0-4 therefore all write
  keys `i0..i39`, and each later batch overwrites the earlier ones: on a page with
  more than 40 leaf labels only the last 40 are ever readable, and a label that
  was dropped is reported as "the hook published no rectangle" — a *wrong*
  diagnosis with the same wording as a real absence. Harmless on the six labels
  the evidence quotes; a trap for the next card that relies on it.

### The blast radius, which is why this is not a chore

(b) and (c) are `NOT RUN` behind the click because the hook actuates them only
after `scriptText` has read true on two consecutive polls
(`web/src/main.tsx:149-159`). C-BRIDGE@1 rule 5's coverage in the shipped binary
is therefore entirely hostage to the pointer-click mechanism. Opening the note by
having the page navigate itself would make (b) and (c) green while proving nothing
about pointer input — **not recommended**, and the reverse of what the row is for.

## Recommended repair, and the owner boundary

Nothing below is an implementer's to take on their own; this investigation
changes no source.

**Coordinator decisions**

1. **Amend (a)** from "both globals read `undefined`" to "`__TAURI__` is
   undefined **and** an in-page `__TAURI_INTERNALS__.invoke(…)` is rejected".
   This is the only change that can make (a) decidable, and it is a card text
   change, not a code change.
2. **Authorise the shape of the hook additions** — one `ipcProbe` fact for (1);
   for (d), either the geometry facts (`innerWidth/innerHeight`,
   `outerWidth/outerHeight`) or a capture-phase `click` observer that publishes
   `document.elementFromPoint` at the click point. These live in
   `web/src/main.tsx` (P3.4's May-edit set) but change the Fixed-decisions hook
   contract and share the P3.5 seam, so the coordinator signs the shape first.
3. **Authorise a further V2 run.** The card is 4-of-3 plus AM-138's exception;
   this investigation authorises nothing and ran nothing.

**Implementer work once 1-3 are given** (all of it makes the instrument more able
to fail; none loosens a pass condition, and the last one tightens)

- Convert page coordinates to window coordinates before clicking, using the
  geometry the hook publishes; and assert the click point lies inside the window.
- Record the window geometry and the rectangle's `w`/`h` in the row's output, so
  the evidence carries the numbers the offset is computed from.
- Read the pointer back with `xdotool getmouselocation --shell` after
  `mousemove --sync` and `FAIL` if it is not where it was asked to go — a silent
  warp failure becomes a named cause.
- Honour `clicked.ok` (`:722`) instead of discarding it.
- Require the card's fact predicate for the patient click too, not a rectangle
  change (`:741`, `:1050`).
- Key rectangles by global index, not by index-within-batch (`:650-656`).
- Add a capture-phase `click` listener to the hook that publishes whether a click
  event reached the page at all. That single fact separates "the click never
  arrived" from "it arrived on the wrong element" in one run, which is the
  difference between one more diagnosis and one more blind attempt.

**Explicitly not recommended, and why**

- Widening the 30 s, accepting the enabled assertion as proof the click landed, or
  clicking until something changes — all forbidden by the card and HS-7, and all
  three convert an unproven click into a green row.
- Any `src-tauri/` edit, including to chase `__TAURI_INTERNALS__`: `webview.rs:167-180`
  shows no configuration can remove it, and the card's `srcTauriTouched` must stay
  `false`.
- Reinterpreting (a) as PASS on the strength of V3's greps: the card calls that a
  weaker report, not a substitute (`docs/v2/cards/P3.4.md:241`, `:592`).
