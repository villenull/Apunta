## Defect A — MEDIUM — `closeWindow` discharges by tab identity alone, and deletes **live** records

`closeWindow` (`server/src/maintenance.ts:628-642`) walks **every** record whose
`tabId` matches and, for each, releases its wait and deletes it. There is no
check that the record is retained, no check that it is the caller's, and no
check that there is only one. `registerWindow` was hardened for exactly this in
the last round (finding 8) and `closeWindow` was written afterwards without the
same guard.

Two reachable ways a window holding unsaved text stops existing for the server:

1. **A duplicated tab identity, which the code itself says is real** (`:568-576`
   — Chromium's *Duplicate Tab* copies `sessionStorage`; `web/src/main.tsx:390`
   opens a same-origin `window.open` in the dev diagnostics hook). Duplicate a
   dirty tab, close the clean copy: its beacon deletes the dirty window's live
   record and releases its wait. With any third window registered and answering
   `ok`, the quiesce then settles `ok:true` over text nobody was ever asked
   about — the one direction FD13 is fail-closed about.
2. **A beacon that lands after its own tab re-registered.** `sessionStorage`
   survives a same-tab reload, so a reloaded document registers under the *same*
   id and (finding 10) reuses the record. A late beacon from the outgoing
   document then deletes the incoming document's live record.

The same loop is what makes the retention story reachable at all, so this is not
cosmetic; it is the one place where a claim made by one page acts on another's
state. **Fix:** discharge only records that hold **no** wait (`release === null`,
i.e. genuinely retained), at most one per call, and never release a live wait
from a close claim — a live window that is really going away reaches
`disconnect()` over its own socket anyway.

**On the prompt's other questions about this route:** tab identity is
`crypto.randomUUID()` (`:150-156`), kept in `sessionStorage` and readable by no
other tab, and no route enumerates identities (`status()` returns counts only),
so it is **not guessable or enumerable** — a page can only address its own
record, which is the acceptable trust boundary for a same-origin app under
CSP `script-src 'self'`. The beacon does not trust a tab that *does* hold text:
`isCleanToClose()` is published by the `beforeunload` guard, which recomputes
`latestTextRef !== persistedContentRef || saving || error` **on every fire**, so
mid-debounce and mid-save both publish `true` and a stale `true` cannot outlive a
successful save. A beacon that arrives **during** a quiesce leaves that window
counted as unanswered (`no_response`) — correct and deliberate. The one ordering
it gets wrong is the one above.

## Defect B — MEDIUM — a window that once reported `ok` is never un-resolved, so a later dirty crash is unprotected

`resolved` is set `true` by a clean report (`:664-667`) and is **never set back
to `false`**. `disconnect()` (`:606-614`) stamps `disconnectedAt` and leaves
`resolved` as it was, and `windowPhase` skips any record that is
`!record.release !== null || resolved` (`:376`).

The common sequence in browser mode, all of it ordinary:

1. A quiesce succeeds with this window answering `ok` (nothing unsaved) →
   `resolved = true`.
2. The user keeps working; a new quiesce is not triggered; the tab is killed
   (crash, OS, browser quit) **while holding unacknowledged text**.
3. The record is retained, but `resolved` is still `true`, so it is not a
   `no_response` blocker — and the next quiesce settles `ok:true` over text the
   server never held.

That is the exact hazard AM-215 exists to close, and the clean report in step 1
is what disarms it. The e2e cannot see it: each row's tab either reports clean
and is then closed by a beacon that deletes the record, or crashes having never
reported at all.

FD13(b)'s letter ("unresolved **until** it has reported `ok` for a quiesce that
flushed cleanly") permits today's code, so this is a card-level reading, not an
implementation slip — but the fail-closed reading is one line: **`disconnect()`
sets `resolved = false`**, because a window that goes away without saying its
word has, by definition, said nothing about what it holds *now*. It costs the
ordinary clean close nothing, because AM-215's `clean` claim deletes the record
before any socket close can retain it. **Owner decision** between (a) that reset
and (b) recording this as an accepted risk in the card; I recommend (a), with
the consequence stated: the e2e's `leaveCleanly` teardown would then genuinely
depend on the unload beacon, so `quiescence.spec.ts` should poll
`GET /api/app/quiesce/status` for the record's disappearance instead of assuming
a clean report disarmed it.

## Defect C — MEDIUM — `pagehide` with `persisted: true` sends the last word and stops the poll, and nothing re-arms it

`onPageHide` (`web/src/lib/maintenance.ts:491-494`) sends the close report and
calls `stopMaintenanceReporter()`; it does not look at `event.persisted`, and
there is **no `pageshow` listener anywhere** in `web/src`. So on a
back/forward-cache restore the document comes back with its editor state intact
— while the server has been told "clean, nothing left", had the record
**deleted**, and will never be asked again by a window that is not polling.

Direction matters here: before AM-215 this same gap was *fail-closed* (a bfcached
page left a retained record that blocked every later quiesce, which is Defect 1
of the last round). AM-215 converts it into the fail-open direction — a "clean"
claim that is true of a page which is merely hidden, for a window that still
holds text.

I could not reproduce it in this Chromium, and the evidence suggests the engine
does not bfcache this document in headless (V9 navigates the app tab to
`about:blank` and back and still sees a fresh registration, which a restore
could not produce). It is still reachable where bfcache is on by default —
Firefox, Safari — and browser mode is a supported mode under C-BRIDGE@1 rule 3.
**Fix (small):** in `onPageHide`, `if (event.persisted) return;` and add a
`pageshow` listener that re-arms when `event.persisted` is true.

## Out of scope by the implementer's own account — my call on each

1. **Shell-mode release lives in P5.4 — acceptable to approve, but it needs an
   explicit owner action, not just "P5.4 depends on P5.3".** No P5.3 row asserts
   it (V1 asserts the *opposite*: maintenance stays on), and holding maintenance
   through the snapshot is the direction C-UPD@1 asks for. But C-BRIDGE@1 rule 2's
   inbound vocabulary is `update_status` / `quiesce` / `shutdown` and holds **no
   release verb**, so the mechanism cannot be an existing bridge message without
   a contract change. **Action:** owner records, in C-BRIDGE@1 (or in P5.4's
   card), *which* mechanism releases a successful quiesce in shell mode — a
   route on the update path or a new inbound type — and P5.4's V-row asserts it.
2. **`errors.quiesce.no_response` has no renderer — acceptable to approve.**
   No P5.3 row and no contract sentence puts that sentence on a P5.3 surface:
   C-UPD@1's failure table assigns "notice says what to finish first" to the
   updater notice, which is P5.4's, and the 503 cannot be the vehicle (a
   retained record makes `ok:true`, and so maintenance, unreachable). **Action:**
   P5.4 renders the key on the quiescing-failure row and asserts it; until then
   the key is deliberately unreferenced, which lint accepts and parity is
   type-level.
3. **The refused report's code is still `conflict` — acceptable to approve.**
   The row asks for 409, not for a code; the reason rides `details`, and the
   reporter reads only the status code. The only caller of `/report` is the
   reporter, so nothing can confuse it with a note conflict today.
   **Action:** note the collision in `docs/v2/decisions.md` so the next card that
   opens `ApiErrorCodeSchema` adds `quiesce_report_refused` rather than
   rediscovering it.
4. **V7's (and V9's) row text — a coordinator card edit, not an implementer fix,
   and not a code blocker.** See Nit 4.
