## Numbered findings for the implementer

1. **Evidence sanitization — `docs/v2/evidence/P1.3/v2c.txt`.** The file the
   return cites for V2 carries the machine's real hostname 54 times in its pino
   lines (the value itself is not repeated here), while its six siblings
   (`v1.txt`, `v1-red.txt`, `v1-final.txt`, `v2.txt`, `v2b.txt`,
   `v2-minus-inflight.txt`) all use `"hostname":"<host>"`. Run configuration
   §4: evidence stays sanitized, "never include hostnames, usernames, keys,
   tokens or real names", and this is the only evidence directory in the repo
   that leaks one. Would pass: the same `<host>` substitution the other six
   files already use, applied to `v2c.txt`. No code impact; no verification row
   depends on it.

2. **`server/src/test/real-socket-guard.test.ts:27` — the `APUNTA_PORT`
   override has no C-ISO@1 range check.** `Number(process.env['APUNTA_PORT'] ??
   7812)` is used as both the bind address and the port the client connects
   to. Anyone who runs `npm test` in a shell that already exports
   `APUNTA_PORT` — a sandbox `env` block sets one, and `web/vite.config.ts`
   reads the same variable — silently relocates the test; `APUNTA_PORT=7717`
   would bind and then contact the live instance's port, which HS-1 forbids.
   Would pass: validate the override the way `sandbox.mjs` does (integer,
   7800–7889, refuse 7717, fall back to 7812) before using it, or drop the
   override and keep 7812. The override itself is the card's decision, so if
   the coordinator prefers to amend the card rather than the file, that is a
   legitimate outcome — the range check is the missing part either way.

3. **Proof gap: the main app's `Host` rejection is never asserted.** The
   contract's own rejection example is a foreign `Host` "on both servers",
   but `request-guard.test.ts` only ever gives the main app a *conforming*
   `Host` (that is what the `MAIN_PORT = 80` cases are for), and the only
   foreign-`Host` assertions run against `serveBootError` over a real socket.
   The behaviour is correct by construction — one function, one registration
   per server, and the boot server's reject path is proven — but if
   `hostAllowed` were ever weakened for the main app, no test would notice.
   The card's premise for routing the foreign-`Host` case to a socket is also
   imprecise: `app.inject` *defaults* a `Host` but honours an explicit one,
   which this very file relies on at line 189. Would pass: one line in
   `request-guard.test.ts` injecting the main app with
   `headers: { host: 'evil.example:80' }` and asserting `expectForbidden`.

4. **`server/src/http/request-guard.ts:158` logs `request.url`, which is the
   path *and* the query string.** C-REQ@1 says "method, path"; a query string
   is a little more than that. Harmless today — the only query parameters
   anywhere in `server/src/routes/` are `version` (`plans.ts:85`) and
   `include_archived` (`patients.ts:32`), no free text — so no clinical text
   can reach the log. Recorded so that a future `?q=` search does not quietly
   start putting one there. Optional fix: log the pathname only, or the route
   pattern.

5. **Nothing blocking, recorded as verified rather than assumed:** the
   `same-site` rejection is implemented *and* tested (allow-list of
   `same-origin`/`none`/absent); the two Vite allowances are unconditional
   with no flag and no other exemption; the 403 body is built once and shared,
   so both servers cannot drift; `buildBootErrorApp` now requires the port and
   `serveBootError` passes `config.port`; the three existing-file changes are
   one `APUNTA_PORT` line each, and the harness value (`80`) is exactly what
   `light-my-request` presents for a path-only URL, which the six
   `listen({ port: 0 })` suites never see because the bound port wins.

6. **Dispatch wording, for the coordinator rather than the implementer.**
   HS-2's first sentence now binds — P0.3 was approved in `92c152c`, well
   before this card — and reads as if every command that "opens a database"
   must go through `scripts/v2/sandbox.mjs`, while run configuration §3 runs
   `npm test` bare four times and `sandbox.mjs run`'s ownership check assumes
   the wrapper started the server. P1.3's Fixed decisions resolve it for this
   card (bare, `none` sandbox run IDs) and I ran the rows as written, so this
   is not a card defect; but the same ambiguity will be re-litigated by every
   later card, and the one listener this card adds is a good test case for it.
