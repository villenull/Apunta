## Defect 1 — HIGH — a retained record from an ordinary window close blocks every later quiesce for the life of the process, and the e2e shared tab identity is what hides it

`disconnect()` (`server/src/maintenance.ts:508-516`) marks a record and keeps it;
`resolved` is set **only** by a clean client report (`:534-537`), and a report is
accepted only while a quiesce is in flight (`:518-525`). Outside a quiesce nothing
is ever reported — `stopMaintenanceReporter` on `pagehide` just aborts the poll. So
the ordinary close of an ordinary window leaves a record with `resolved === false`,
and `windowPhase` (`:310-319`) turns every such record into a `no_response`
blocker on every subsequent quiesce.

The only thing that clears it is a registration carrying **the same tab identity**
(`registerWindow`, `:473-488`). A tab identity lives in `sessionStorage`, which dies
with the tab: a window closed and reopened gets a **new** identity, so it cannot
supersede. In browser mode — the mode C-BRIDGE@1 rule 3 and FD1 explicitly support —
the consequence is that after the first tab close (or crash-and-reopen) **no quiesce
can ever return `ok:true` again in that server process**: every update attempt is
refused with "finish this first" and nothing is finishable. The same applies to a
session that ends with an unresolved `conflict`, which is what V3 leaves behind.

**This is FD13 as written** (FD13(b) "until that same tab registers again and
answers", FD13(e) no eviction), so the implementation is faithful and I am not
asking for a threshold or a TTL (HS-7). But it is a production availability and
data-safety hazard that no row covers and the return does not report, and it needs
the owner, not an implementer.

**And the spec masks it.** `e2e/tests/quiescence.spec.ts:47` registers *every* row's
window under one shared identity (`E2E_TAB`, seeded by `addInitScript`), so each row
supersedes the record the previous one left behind. That is exactly FD13(c)'s own
production rule and it is disclosed in `evidence/P5.3/am-213-repair.md` — but the
direction it hides is the one that matters: in production a *different* tab identity
never supersedes, which is the case V4's `ok:true`, the flush-exemption row's
`ok:true` and V9(f)'s final settle all depend on. **Answering the reviewer's
question directly: the shared identity does hide a real bug, not merely reflect the
production rule.** The negative half is proven twice and well — V1's
`maintenance.test.ts:669-701` (a second and a third tab both report `ok` and the
quiesce is still `no_response`) and V9's (f) — but no row shows what a therapist
actually gets: a permanently blocked update after a normal tab close. **Required:**
either a row that demonstrates the production consequence (a retained record from a
closed tab, then a *new* tab identity, still refused), or an explicit owner-visible
statement that this is accepted, plus a decision on the release condition.

## Defect 2 — MEDIUM — a report the server cannot place is applied as clean (fail-open)

`report()` (`server/src/maintenance.ts:533-538`):

```ts
const blockers = input.ok ? [] : claimedBlockers(input.blockers);
if (blockers.length === 0) { record.resolved = true; quiesce?.answered.add(windowKey(record)); }
quiesce?.reported.set(record.id, blockers);
```

`claimedBlockers` silently **drops** anything outside `{conflict, save_error,
recording}`. So a report of `{ok:false, blockers:[]}` — or `ok:false` with a blocker
name this build does not know (a future blocker, a typo, a corrupted body) — narrows
to `[]` and is recorded as a clean answer: `answered` (so the window is never asked
again), `resolved = true` (so its FD13 obligation is **discharged**), and the
quiesce settles `ok:true`. That is the fail-open direction, and it contradicts both
FD8 ("`ok:true` requiring an empty list" — the converse is not stated but is the same
rule read the other way) and the module's own stated principle three lines above
(`app-quiesce.ts:53-56`: "a claim the server cannot place is a claim it will not
act on"). `ok:true` carrying a non-empty blocker list is likewise taken at face
value. No test covers either shape.

## Defect 3 — MEDIUM — `shellMode` is unreachable in production, so the contract's shell-mode release does not exist

`MaintenanceOptions.shellMode` defaults to `false` (`:214`) and **nothing in `server/`
derives it from `APUNTA_SHELL`** (`rg shellMode|APUNTA_SHELL` — only tests set it).
`buildApp` passes `options.maintenance` straight through and production passes
nothing, so `app.ts:66-70`'s claim of an "`APUNTA_SHELL=1`-derived mode" is not true
of the code. Consequences: (a) a packaged shell-mode server behaves as browser mode —
maintenance is released by a window unregistering rather than held through the
snapshot; (b) there is **no mechanism at all** by which "the shell's next transition"
releases a successful quiesce's maintenance (no route, no stdin message), so with the
window still open the server is 503 for every write indefinitely. C-UPD@1's
Quiescence paragraph and C-BRIDGE@1 rule 3 both promise that release, and P5.4 —
which is told to depend on this card — will trip over it.

## Defect 5 — MEDIUM — V7 no longer tests the precondition its row names

The card's V7: "a close attempt **while a `save` registration is open** … The spec
asserts the save registration through `GET /api/app/quiesce/status` before the close
attempt". `quiescence.spec.ts:454-455` asserts the **absence**:

```ts
const status = await readStatus(request);
expect(status.activeJobs.some((job) => job.kind === 'save')).toBe(false);
```

which is true by construction — the `PATCH` is held in the browser by
`page.route` (`:188-208`), so the handler never runs and nothing registers. The row's
title still says "while a save is outstanding", and the close-policy rule FD6 names
first — "close is deferred **while a save is in flight**" — is never exercised with a
real server-side `save` registration. The comment is candid; the reading is not what
the row claims.

## Defects 6-12 — LOW

6. **`run()`'s `finally` does not clear `maintenance`** (`:375-381`). FD5 requires
   maintenance off "on every failure path … in a `finally`". The failure branch sets
   it false (`:367`) but a throw out of `waitForDrain`/`askWindows`/`kindsOf` skips
   that and leaves every write 503 until restart. Latent, not observed.
7. **The flush exemption outlives the flush step.** `flushSaveExempt` (`:430-441`)
   tests `current !== null` and membership of `quiesce.expected`; `current` is cleared
   only in `finally`, and `expected` is never pruned. A save from the same window is
   therefore still exempt after it has already reported, for the whole tail of the
   run. Narrower than AM-213's "during the flush step that asked for it".
8. **A shared tab identity deletes a live window.** `registerWindow` (`:478-484`)
   removes *any* record with the same tab id, **including one currently holding a
   live wait**, and releases that wait as `expired`. Two windows sharing an identity
   — Chromium's *Duplicate Tab* copies `sessionStorage` — makes the first invisible,
   so a quiesce can settle `ok:true` over its unsaved text. That is the one direction
   FD13 is fail-closed about, and there is no server-side guard.
9. **The hot-reload guard does not do what its docstring says.**
   `startMaintenanceReporter` aborts `pollHost()[POLL_HOST_KEY]` (`:319`), but the
   *previous module instance's* `once()` loop catches that abort, waits 500 ms and
   re-arms (`:293-305`) because its own `running` is still `true`. A stop→start or a
   hot reload can leave two poll loops. The V1 reading as named ("arming the reporter
   twice (the StrictMode double-render) never leaves two polls open") **is** proven —
   `maintenance.test.ts:131-144` exercises the `running` early-return path — so this
   is an overstated docstring, not a broken row.
10. **Every poll re-arm recreates the record.** `registerWindow` runs per
    `GET /wait` request (`app-quiesce.ts:97`), deleting the previous same-tab record.
    A duplicate concurrent poll under one identity would leave the old id in
    `expected` forever and force a false `no_response` — fail-closed, so no data loss.
11. **Scope: four stray files.** `a.png`, `b.png`, `c.png`, `d.png` — 8×8 1-bit PNGs,
    untracked, at the repository root. Outside May edit, absent from the return's
    changed-paths list (which is otherwise complete and accurate), and the kind of
    thing a careless `git add` sweeps into a commit. Delete before committing.
12. **Three small things.** The 409 on a refused report carries the code `conflict`
    (`app-quiesce.ts:118`) — a note-conflict code, on a machine-to-machine path;
    `shell-bridge.ts:293-317` carries the same comment paragraph twice; the reporter's
    `fetch` decoration only rewrites **string** URLs (`maintenance.ts:227`), which is
    correct today (`web/src/api/client.ts:80` passes a path string) but silently
    no-ops for a `Request` or `URL`.

## What I checked and found correct

- **Scope.** Every modified path is in May edit, `e2e/playwright.config.ts` under
  AM-213, or one of the two authorised doc sentences. `registry.ts` is a comment
  only — `JOB_KINDS`, `JobKind`, `begin`, `end`, `active`, `anyActive` untouched.
  `settings.ts`, `generate.ts`, `App.tsx`, `sse.ts`, `i18n.tsx`, `ai/fake.ts`,
  `request-guard.ts`, `index.ts` and `src-tauri/**` untouched. `shared/src/errors.ts`
  adds exactly one member; the catalogues exactly one key each. The route diffs are
  `begin`/`finally end` pairs only (verified with `git diff -w`; the one reformat in
  `brainstorm.ts` is a prettier wrap inside the new `try`).
- **The maintenance gate (Q2).** All **eighteen** `GET` routes in `server/src/routes/`
  are in `EXEMPT_READS` — I enumerated them independently; no `GET` escapes the hook
  and no write outside the two protocol writes plus the flush save is served. Every
  documented route writes → 503. The hook is registered immediately after
  `registerRequestGuard`, so C-REQ@1 still runs first (asserted by
  `app-quiesce.test.ts`'s foreign-origin case).
- **The flush exemption cannot be abused** (Q2). Stale/foreign `quiesce` id → 503;
  unknown tab → 503; unregistered window → 503; `/api/notes/:id/chat` and every other
  route → 503 (`matches` compares segment counts); the note handler itself is
  untouched inside its `try`, so the **revision check, the published lock and
  `stale_write` all still apply** to an exempt save. Five V1 cases cover it.
- **Browser-mode release (Q4).** `releaseIfUnheld` fires on every path that removes a
  live wait, holds while a window is registered, releases on the last one; shell mode
  is asserted separately (`maintenance.test.ts:385,408`); a failed quiesce leaves the
  server serving (V1 case, and V2's rollback half end-to-end).
- **The reporter (Q5).** A plain module call at `main.tsx` scope, outside the tree,
  registering no React state — StrictMode cannot double-arm it. The `fetch`
  decoration is scoped to the flush's duration, to `PATCH` + `/api/notes/<id>` +
  relative same-origin URLs, and restored in a `finally` on resolve, throw and abort;
  its own report is passed through untouched. `stopMaintenanceReporter()` aborts the
  poll in flight (V1 case).
- **The close policy (Q6).** The `beforeunload` condition is verbatim FD's
  (`latestTextRef.current !== persistedContentRef.current || saveStateRef.current ===
  'saving' || 'error'`), registered and removed in the effect that already holds
  `pagehide`/`visibilitychange`; the `__apuntaFlushBeforeRelease` hook and the
  `pagehide` flush are read, not edited. `Capture.tsx` is one line plus its effect's
  dependency list (a disclosed deviation, and a necessary one).
- **No test weakening, no retries, no skips, no timeout inflation.** The spec declares
  `mode: 'serial'` in-file; `retries`, `workers`, both `timeout: 60_000` webServer
  startup timeouts and Playwright's 30 s per-test default are untouched; no row calls
  `test.setTimeout`. The `quiescence` project is the `es-MX-language` pattern exactly,
  and the file is `testIgnore`d from the other two projects, so maintenance mode is
  server-isolated as AM-213 requires.
- **Evidence quality is high.** Both deviations that matter (V6's navigation-instead-of-
  close, V9's conflict-instead-of-held-`PATCH`) are recorded with the reasoning and
  with the alternatives that were measured first. The FD13 shared-identity decision is
  disclosed rather than buried — my Defect 1 is about what it does not say, not about
  concealment.
