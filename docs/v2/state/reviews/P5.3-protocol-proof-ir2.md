## Findings

**1 — `closeAnswer` treats an omitted boolean as `false`, so an empty answer closes a
recording window. Report 67–68 is false; data-loss direction.** `326–328` validate only
fields that are *present* (`k in live && typeof live[k] !== 'boolean'`), so `{}` passes,
`publish` updates nothing, and `330–331` fall through the `=== true` chain to `'close'`.
`F1a`: window published `recording:true, unsaved:true`, answer `{}` → `{"code":"decided","decision":"close"}`.
`F1b`: `{recording:false}`, `{unsaved:false}`, `{saveInFlight:false}` each decide `close`.
The proof never observes it: `724` uses `{}` only after the probe was consumed
(`stale_probe`), `459` uses `{}` with an active save job (`defer_save` masks it), `738`
calls `s.closeAnswer('w1', p.token, {})` and **discards the return value**.
Minimal correction (one clause, keeps the sentence the report already makes):
require `typeof live.recording === 'boolean' && typeof live.unsaved === 'boolean'`, else
`malformed_answer`/`defer_malformed`. Otherwise weaken report 67–68 to "absent, non-object,
array or wrongly-typed". *Confirmed deliberate and correct:* a malformed first answer does
consume the probe (`325` clears `pendingClose` before validation) and R16 asserts it —
though report 67–68's "first **accepted** answer" is inaccurate wording for that.

**2 — `b.noteId` is mutable while an admitted save is in flight, so completion evidence
is charged to the wrong note. Data-loss direction; `R14b`'s premise fails.**
`declareOpenNote` rewrites `b.noteId` at `174` with no check against `b.outstanding`.
`F2a`: PATCH admitted for `note-1` → window opens `note-2` with unsaved text →
`settleFlush(b,'saved')` stamps `saveOutcome='saved'` on a binding that now reads
`noteId='note-2'` → **`q.outcome {ok:true,blockers:[]}`**, maintenance on, snapshot taken,
and `note-2` can never be flushed (the token is consumed). `F2b`: same switch with
`settleFlush(b,'error')` charges the failure to `note-2`
(`w.saveFailedNote='note-2'`, `247`); a later success on `note-2` clears it (`248`) and
`q2` settles `ok:true` with **`note-1` never saved**. Report 163's justification — "this
generation saved the same note itself, so the late failure loses nothing" — is a note-id
*equality*, not version or content identity; nothing in the model carries a version.
Minimal correction: freeze the target on admission (`b.savedNoteId = m[1]` at `234`) and
use it for both the completion record and the `unretried` test (`281–282`); refuse or defer
a note switch while `b.outstanding` (`231`), as R11c already refuses a token after release.

**3 — `armSweep` resets one shared timer, so a chatty sibling starves the liveness
sweep; the 2 s bound is not a bound. Fail-closed direction, wrong code.**
`190–197`: every `wait()` (`165`) and `drop()` (`188`) supersedes the single pending
sweep, and `sweep` has **no per-binding due time**. `F3`: `w1` reports clean then re-arms
every 1.9 s (< `LIVENESS_MS`) while `w2` sits silent — no sweep ever fires, at t=57000
`w2.abandoned=false` and the outcome is `{'timeout'}` from the global deadline.
`F3b`: with the chatty loop stopping at 28.5 s the same silent window is abandoned at
**32.5 s instead of 2.5 s** (13× the named bound). This is distinct from the approved
30 s total, which is untouched (`F3c` HELD, and S6/R10's held-wait case is right): the
defect is only that `LIVENESS_MS` is described as governing the re-arm gap (report 46–49,
169–172; proof 44–48) when it governs nothing under activity. Consequence is a
`timeout`/`no_response` vocabulary change (B7) plus an unbounded detection latency.
Minimal correction: give each binding a `dueAt` set when it is asked/registered/dropped
and have `sweep` act on it, or state honestly that the sweep is cadence-driven and the
2 s number is not a bound. (Per coordinator direction: never clear or ignore live jobs to
fix this — `R12`'s leaked-job timeout is the accepted safe direction and stands.)

**4 — a report is an unverified self-attestation, and `report()` rewrites the server's own
published state. Data-loss direction.** `255–270` admits any `blockers:[]` from a valid
(window, quiesce, token) triple and then calls `publish(wid,{recording:…,unsaved:false})`
at `267`, overwriting the honest observation. `F4a`: `w1` published `unsaved:true`, has
**no declared note and therefore cannot flush at all** (R11b, `flush_no_open_note` 232),
yet its clean report is `accepted`, `q.outcome {ok:true,blockers:[]}`, and
`status().unsaved` flips to `false`. Missing invariant (this is D1's discipline applied to
the report path): *a binding may report clean only if `b.saveOutcome === 'saved'` whenever
the window's last published `unsaved` was true; otherwise the outcome is `save_error`.*
Report 46–49 ("never excluded from the settle test", "honest state") is not met.

**5 — a duplicate tab silently removes one window from the drain. Data-loss direction.**
`154–159`: `wait()` does `this.polls.set(wid, poll)`, overwriting the incumbent's held
poll; `sessionId` is written and **never read** (only `157`, plus the field comment at 99).
`F6`: tab A (`recording:true, unsaved:true`) and tab B — same `windowId`, because
`sessionStorage` is copied by the browser's duplicate-tab — share one binding and one
token; A's held poll is orphaned, B reports clean, `q.outcome {ok:true,blockers:[]}`,
`status()` rewritten to `recording=false unsaved=false`. Not adversarial security (same-origin
app); it is a browser behaviour the identity design must survive. Minimal correction: key
polls per `(windowId, sessionId)` and treat a second live session for one windowId as a
new binding, or mint the id per tab load rather than per session.

**6 — malformed report input throws instead of returning a code.** `258–263` dereference
`body`/`headers` unguarded. `F5`: `report(w, hdr, undefined)`, `report(w, hdr, null)` and
`report(w, undefined, body)` each throw `TypeError`. R16 covers a malformed `blockers`
value, not a missing body or header map. Minimal correction: `if (!body || typeof body !== 'object') return {code:'malformed_report'}` and the same for `headers` — matching the never-throw discipline `intercept` already keeps.

**7 — the categorical claim is still an overclaim.** Proof 8–10 and 809 and report 11–12
say passing "proves the protocol internally consistent". 38 hand-authored schedules plus
`R19`'s **eight** permutations (report 91) cannot establish that of the whole state
machine, and this audit reproduced six counterexamples the report's own sentences forbid.
Report 165–178 already concedes the synchronous-world limit; the headline needs the same
honesty. Minimal correction: "no schedule we enumerated failed" plus "P1–P10 hold along
the 38 enumerated schedules", and keep the footer.
