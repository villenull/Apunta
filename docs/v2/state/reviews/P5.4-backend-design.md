## 2. The shared contract proposal

### 2.1 C-BRIDGE rule 2 reconciliation (AM-221's "explicit snapshot request/result and maintenance-release messages")

| # | Direction | Shape | Semantics |
|---|---|---|---|
| M1 | shell→server | `{type:"snapshot_request", id}` | `id` opaque string minted by the shell (its counter as a decimal string), echoed verbatim, never parsed by the server. Sent only from state `snapshotting`, only after `quiesce_result{ok:true}` |
| M2 | server→shell | `{type:"snapshot_result", id, ok, code?}` | **Ack ordering: the `ok:true` line is written only after the snapshot file exists, is integrity-checked, and its journal entry is fsynced durable.** Failure codes: `not_quiesced`, `backup_in_progress` (C-SNAP rule 3's word), `snapshot_failed` (C-UPD step 3's word). One snapshot at a time — a second concurrent request answers `ok:false, code:"backup_in_progress"`, never queues |
| M3 | shell→server | `{type:"maintenance_release"}` (+ optional `code`) | The **only** thing that drops a maintenance state a successful quiesce is holding in shell mode (AM-221: no implicit release transition). Sent on abort/refusal/failure transitions back to `verified`/`available`/`idle`. **Never on the install/relaunch success path** — releasing there would let a write land after the snapshot and die at relaunch |
| M4 | shell→server | `quiesce{reason?: "close"\|"update"}` | optional field on the existing message (rule-2 change, backward compatible) so the server can tag the run's trigger — needed for `closePending` (2.7). If the coordinator rejects M4, the close/ask classification moves to `quiesce_result` (2.7) instead |
| M5 | server→shell | `quiesce_result{ok, blockers[]}` | **unchanged shape**, but see §2.7's open question — V6 demands Rust branch on blocker classes while the fixed decision forbids Rust owning the vocabulary |

Non-conflation rule (AM-221): a `snapshot_request` is answered **only** by `snapshot_result`, a quiesce **only** by `quiesce_result`, even when the two are in flight together; `update_request{action}` stays the server→shell command channel and is the vehicle for the recovery reinstall (§2.10).

No new message is needed for health — `ready` (`shell-bridge.ts:106-121`, parsed `bridge.rs:71-101`) already carries nonce + protocol + version, and `update_status{state:"done", version}` already carries the completion word.

### 2.3 The journal: path, phases, writers, ack order, boot gate

**File** — `<dataDir>/update-journal.json` (name beside `safety/`, `staging/`, `pending-restore/`; helper in `server/src/config.ts` or new `server/src/update-journal.ts`). Written with write-temp → `fsync` → `rename` → `fsync(dir)`.

**Phases (exactly three, per your constraint):**

| Phase | Written by / when | Read at boot |
|---|---|---|
| `pending` | server, **before** writing `snapshot_result{ok:true}` (M2). Payload: `{fromVersion, toVersion, snapshotPath, quiesceId?, createdAt}` — `snapshotPath` is the restore handoff's pointer | — |
| `health_attempted` | server, **once**, early in `start()` when `version === journal.toVersion` — the claim. fsync before any DB open. Never claimed a second time | `pending` + `version == toVersion` → claim, continue **normal** boot (this is why the first new boot is not recovery). `pending` + `version != toVersion` → the target never booted (abandoned install / manual rollback): log, keep the journal, boot normally |
| `recovery` | server, on entering recovery mode (idempotent, so a crash inside recovery re-enters recovery) | `health_attempted` (any version) → **recovery boot, one mandated transition, never a normal-boot retry**; `recovery` → recovery again |

**Clearing** — only on `update_status{state:"done", version}` from the shell (health = shell saw `ready` with its own nonce, `protocol:1`, and `version == target`), which deletes the journal (fsync). No marker-only supervision: if the shell dies before sending `done`, the next boot is recovery (fail-closed by design — document it). No HTTP health-poll anywhere.

**Gate insertion (exact file/lines)** — `server/src/index.ts`: immediately after `acquireDataFolderLock(config.dataDir)` (`:42`) and **before** `applyPendingRestore` (`:43`), `prepareDatabaseForStart` (`:50`), `openDatabase` (`:56`). The recovery branch skips all of `:43-56`, skips `buildApp` (`:99`) and the normal `listen` body, and instead runs a recovery server. C-OWN lock stays acquired first (never touch another owner's folder); in recovery **nothing in the user DB is opened or migrated until the explicit restore**. `writeReady` (`:184`) and `startStdinBridge` (`:195`) still run — the shell needs its ready line either way.

### 2.5 Frontend hold: freeze + smallest `WaitOutcome` change

**Freeze** — one module flag in `web/src/lib/maintenance.ts` (`frozen`), set inside `once()` at `:482` **before** `flushAndReport`, exported as `isWorkspaceFrozen()`. Rendered as a non-interactive overlay from the eager root (`web/src/App.tsx`, above `PrimaryBlocker` `:241`) that blocks pointer/keyboard in the workspace but **must not** block: the flush's own `fetch`, `pagehide`/beacon, navigation, or the close-confirm dialog (dialog layer sits above the overlay).

**Smallest `WaitOutcome` change — one new variant:**

```ts
export type WaitOutcome =
  | { readonly request: 'flush'; readonly quiesceId: string }
  | { readonly request: 'expired'; readonly quiesceId: string }   // meaning unchanged, never a release signal
  | { readonly request: 'settled'; readonly quiesceId: string; readonly ok: boolean;
      readonly held: boolean; readonly blockers: readonly QuiesceBlocker[] };
```

Client rule: unfreeze iff `held === false`. `expired` keeps its three current meanings (budget/supersede/disconnect, `:509 :689 :669`) and is **explicitly not** treated as release — that is the "expired long-poll guessed idle" you rejected.

**Emission sites (the explicit-release enumeration you asked for):**

1. `run()`'s `finally` (`:509`) — emit `settled{…, held: maintenance}` for every record in `quiesce.expected` (replacing the blanket `expired` for that quiesce's participants; non-participants keep `expired`).
2. **Late re-arm**: a per-record `owed: {quiesceId, ok, held, blockers} | null` set in the same `finally`. `holdFor` (`:667-685`) returns the owed outcome immediately when `current === null`. *Without this the design bricks the app:* a client that reports and re-arms after `run()` has already finished would park forever (`:679-684`) and never unfreeze — the race is real because the `finally` runs off the report's completion while the client re-arms on the report's response.
3. `maintenance_release` handler (M3) → new `MaintenanceController.releaseHeld()`: `maintenance=false; heldBySuccess=false;` **and** release every parked/owed hold with `settled{held:false}`. This is the shell-mode abort/refusal/failure release.
4. `disconnect`/`holdFor`-unknown stay `expired` (a dying page needs no release).

Note `releaseIfUnheld` (`:341-346`) needs no hold-release: it only fires when `liveWindows()` (open holds) is empty.

Browser-mode success keeps `held:true` → the window stays frozen while it is registered — the honest reading of "held while at least one window is registered" (rule 3), and writes are 503 anyway. I checked `e2e/tests/quiescence.spec.ts`: after every `ok:true` (rows at `:103`, `:143`, `:456+`, `:720+`) the spec only navigates to `/api/health` and closes — none types after success; refused rows (`:334`) continue interacting, and refusal releases (`held:false`). The freeze should not break the suite as written.

### 2.7 Native close: three transitions and the unassigned confirmation surface

Flow (Rust, `main.rs`):

1. `CloseRequested` (`:519`) → **before** claiming `QuitGate`: write `quiesce{}` (new `bridge::quiesce_line()` beside `shutdown_line()`), register a pending-close oneshot in `Spawned`, await with timeout ≥ server `DRAIN_MS` (30 s) + margin; timeout ⇒ treat as `ok:false, blockers:['no_response']` (fail-closed, never a silent close).
2. `ok:true` → `begin_quit` as today (`:164`, ladder `:651-697` sends `shutdown`). The update-relaunch door also goes straight to `begin_quit` — it already quiesced in state `quiescing`; the close-check belongs only to the window-close door.
3. `ok:false` → confirmation state (V6's three transitions), then either a fresh owned `quiesce{}` retry after the owner confirms (canonical re-run via `quiesce()`'s join, `maintenance.ts:813`), or abandon.

**The gap you need decided:** the card requires Rust to *ask*, but (a) A05 admits four crates and `src-tauri/Cargo.toml` has no dialog crate (tauri, single-instance, updater — AM-225's reqwest makes four), (b) C-BRIDGE rule 4 forbids webview IPC, (c) same-origin navigation to a confirm page would destroy the very recording being protected. So the ask must be rendered **by the page**, which needs a decision path back to Rust:

- **E1 (Recommended)** — page renders the dialog (it already has `ConfirmDialog`, catalogues, and `Capture.tsx`'s `abandonCapture`/`discardRecording` as the discard callbacks; registration point for a "please discard" signal: a small `web/src/lib/close-confirm.ts` that Capture subscribes to). Page → `POST /api/app/close/decision {confirm}` → server → **new outbound `{type:"close_decision", confirm:boolean}`** → Rust retries `quiesce{}` or drops the pending close. Server exposes `closePending` + blockers (it ran the quiesce, so it knows the trigger if M4 lands, otherwise Rust tags it via M4). Adds one outbound type in the rule-2 reconciliation.
- **E2** — reuse `update_request{action}` with a widened action vocabulary (`…|"close_confirm"|"close_cancel"`). No new message type, muddies a type the updater owns.
- **E3** — widen A05 for `tauri-plugin-dialog` and ask natively. Owner decision; the dialog would be English-only (the shell has no i18n — owner-facing bilingual text lives in the catalogues), which I'd treat as disqualifying.

**Second, harder gap:** V6 wants three distinct transitions ("deferred while a save is in flight", "confirmation while a recording is active", "silent close only when neither"), which forces Rust to branch on blocker *classes*, while the fixed decision says Rust "keeps no copy of the vocabulary". These cannot both hold. Recommended fix: the **server** computes a `disposition: "defer" | "confirm"` (server-side classifier over `blockers[]`) and carries it on the reply — `quiesce_result{ok, blockers[], disposition?}` — so Rust branches on an enum it is handed, not on names it interprets. That is a rule-2 field addition for AM-221's reconciliation; the alternative is amending V6's wording.

### 2.8 Single-flight bounds (close vs update; no result conflation)

1. **Join, don't queue**: close `quiesce{}`, HTTP `POST /api/app/quiesce`, and the update's `quiesce{}` all reach `quiesce()`'s existing join (`maintenance.ts:813-818`) — one canonical run, one result shape per caller.
2. **A failed run must not drop maintenance a prior success is holding.** Today both failure paths clear it unconditionally (`:488-490`, `:503-506`). A close-triggered quiesce that refuses while the update is mid-snapshot would flip `maintenance=false` and open writes into the snapshot window — silent loss. Fix: clear only when `!heldBySuccess`; held maintenance is dropped **only** by M3/`releaseIfUnheld`. (Safe because the freeze keeps windows clean while held, so a second run's refusal is essentially unreachable — but it must not be load-bearing.)
3. **Snapshot is its own single-flight**: one at a time, refused with `backup_in_progress`, never answered on the quiesce channel (M2's non-conflation rule).
4. **Close during snapshotting**: close's run returns `ok:true` → ladder `shutdown` lands mid-snapshot → no `snapshot_result{ok:true}` was ever written (ack is post-fsync) → shell never reaches `installing`. Safe by construction; worth a test row.

### 2.9 Post-relaunch health — no new message

Existing `ready` is the health channel (nonce + `protocol:1` + `version`; `bridge.rs:71-101`, `main.rs:292`). Shell compares `version` to the target, then sends `update_status{state:"done", version}` → server clears the journal (§2.3). The only new work is that the server must finally **dispatch** `update_status` (`shell-bridge.ts:216-243`) — it is already typed at `:49-53`. Wrong version ⇒ no `done` ⇒ journal stays `health_attempted` ⇒ relaunch lands in recovery. No HTTP health-poll, no marker-only supervision, no same-mode retry of a normal boot.

### 2.10 End-to-end readonly restore → previous-image reinstall

`health-fail` (P5.5 V2) → relaunch → journal `health_attempted` → recovery boot (no DB open) → `RecoveryView` lists `journal.snapshotPath` (read-only inspection only) → owner confirms → `POST /api/app/recovery/restore` (explicit swap, `rollbackAppliedRestore` on failure) → journal cleared → `POST /api/app/recovery/reinstall-previous` → server writes **`update_request{action:"reinstall"}`** (existing enumerated server→shell channel, `CONTRACTS.md:215`; `action` widened from `check|download|install` — coordinator reconciliation) → Rust spawns the kept `Apunta.previous.AppImage` (P5.4 fixed decision) → previous version boots with no journal → normal. If the previous image is missing or the swap fails, the journal stays `recovery` and the next boot is recovery again (fail-closed, retryable). Browser-mode never sees any of it (updater endpoints 404; quiesce routes stay).

## 4. Decisions I'd put to the owner (one recommended each)

1. **Native-close confirmation surface** — **E1 (Recommended): page-rendered dialog + one new outbound `close_decision{confirm}`**, vs E2 (reuse `update_request` actions), vs E3 (fifth crate for a native dialog, English-only).

3. **V6's three transitions vs the no-vocabulary rule** — **server-computed `disposition` field on `quiesce_result` (Recommended)** vs amending V6's wording to "the reply decides" without classes.
4. **`quiesce{reason}` (M4)** — **add the optional field (Recommended)** so `closePending` is server-known without a second message; dropping it forces the close tag onto `close_decision` only.
5. **Browser-mode success freeze** — **stay frozen while `held:true` (Recommended, contract-honest; e2e as written still passes)** vs releasing at `settled` regardless of `held` (friendlier for test rows that interact after `ok:true`, weakens the "release only authoritatively" rule).
