## Numbered findings

1. **The e2e line is not deterministically green, and the cause is a pre-existing product
   race outside P0 — `server/src/backup/archive.ts`.** One of my five invocations
   (08:48:58Z) failed `tests/backup.spec.ts:51` (41 passed, exit 1); the other three completed
   runs were 42/42. The server log for the failing run names the mechanism exactly:
   `ENOENT: … rename '…/backups/apunta-backup-2026-09-26.zip.part' ->
   '…/backups/apunta-backup-2026-09-26.zip'` → HTTP 500 → the spec's console-error fixture
   fails the test. Two tests in that file (`:20` and `:51`) each click "back up now", and
   Playwright ran the suite with 4 workers, so two `POST /api/backup` requests overlapped.
   I reproduced the underlying defect deterministically at the API level, through the wrapper
   (`run --port 7821`, three concurrent requests): round 1 answered **201 three times, all
   three naming `apunta-backup-2026-09-26.zip`**, and left **one** archive on disk; rounds 2
   and 3 produced `400 online backup failed: disk I/O error`, `400 … unable to open database
   file` and a 500, with the log showing `ENOENT … open '…/backups/.staging/apunta.db.<ms>'`.
   A second probe (`run --port 7822`, two concurrent requests, four rounds) answered **201
   eight times and left four files**, every pair reporting the same filename. The four causes
   are all in `archive.ts`: one shared staging directory per data dir (`:86`), a
   millisecond-resolution staging copy path (`:100`) whose directory one request deletes while
   another is reading it, a fixed `.part` name per destination (`:202`), and a
   check-then-use `uniqueDestination` that `statSync`s for a free name and returns it
   (`:332-341`) — so its own docstring's promise, "Never overwrite — a backup that silently
   replaced this morning's is one backup, not two", is exactly what happens. This is reachable
   without any user error: `server/src/index.ts:94` fires the daily automatic backup
   (`maybeRunDailyBackupAsync`, `server/src/backup/index.ts:175`) unlocked right after
   `listen`, and it runs for seconds — a "Back up now" in that window collides with it. The
   user-visible consequence is the bad one: a **201 for a backup that does not exist**, or a 500
   with a generic "Something went wrong on the server".
   *Scope:* `server/src/backup/archive.ts` is untouched in `3efed5d..7c3e4bb`
   (`git log` → last change `a9f1d35`, v1-era), it is in no P0 May-edit list, and the e2e specs
   that collide are likewise outside them. Nothing in P0 caused or could fix this.
   *To make the L2 suite reliably green:* an amendment naming `server/src/backup/archive.ts`
   (per-run staging directory, an exclusive-create or atomic-rename reservation for the
   destination, a unique `.part` name), plus a unit test that fires two `createBackupAsync`
   calls concurrently and asserts two distinct archives — or, as a stopgap, serialise backups
   behind an in-process mutex and have `POST /api/backup` await the startup one. Until then the
   e2e line will keep failing at some rate, and this review's SUITE row is a PASS on 4 of 5
   invocations rather than a deterministic green. If the coordinator's standard is "the L2
   suite must be deterministically green", this row is a FAIL on the next unlucky run and the
   milestone should not be closed on my say-so.
