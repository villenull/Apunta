1. **The e2e suite is red at the parent's head, and it is not P0's code.**
   `e2e/tests/workspace.spec.ts:121-124` opens a patient row menu and clicks
   `Delete ${patientName}` for a patient it has just created, i.e. one that is not
   archived. In the current UI that item does not exist:
   `web/src/components/PatientMenu.tsx:164-186` renders
   `aria-label={`Delete ${patient.name}`}` **only when `archived` is true**, and
   `Archive` otherwise ("Archived patients offer Restore and, as the red item, Delete",
   and the file's own doc comment: "Archive for a working patient, Delete for an
   archived one"). Before the out-of-band UI baseline the same menu rendered Delete
   unconditionally — `git show b366be1^:web/src/components/PatientsColumn.tsx` lines
   334-341 — so the spec was correct then and `b366be1` (AM-028) changed the UI without
   changing the spec. `git log 3efed5d..cc8ea29 -- e2e/tests/workspace.spec.ts` is
   empty: no P0 card touched it, and `e2e/tests/` is outside every P0 May-edit list.
   Reproduced twice, deterministically, each time in a fresh sandbox run folder
   (08:37:24Z: 41 passed / 1 failed; 08:38:42Z: 41 passed / 1 failed, same test,
   `locator.click: Test timeout of 30000ms exceeded … waiting for
   getByLabel('Delete E2E Patient …')`). The other 41 tests pass, including the sandbox
   integration (the server ran under `<sandbox>/…` on 7820 with the matching
   `testRunId`). Blast radius is one line in one spec: it is the only place in `e2e/`
   that expects the old unconditional Delete. To make it pass, either archive the
   patient first and then delete it from the archived menu, or restore an unconditional
   Delete in `PatientMenu` — the first is what the UI now means, the second reverts an
   owner-approved design decision. Whichever the owner picks, it needs an amendment
   naming `e2e/tests/workspace.spec.ts` (or `web/src/components/PatientMenu.tsx`),
   because no P0 card may edit either. Until then the L2 suite cannot be green at any
