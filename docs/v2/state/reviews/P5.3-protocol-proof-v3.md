The safety invariant, in the file's own header:

- **S1** a quiesce that reports success overlooked nothing: when it settled `ok`, no window
  held content the store does not hold, no two live windows disagreed about any note, none was
  recording, and no operation was live;
- **S2** a close cannot discard unknown or unsaved state, and **the decision path mutates
  nothing**;
- **S3** a clean report cannot erase a published unsaved/recording fact without an evidenced
  transition, and is never itself the evidence;
- **S4** nothing admitted after a successful decision can invalidate it — the epoch fence
  refuses **every mutation that could invalidate a held success**, and the two paths that are
  not fence-guarded cannot do so: `drop` is a **monotone removal** (it can delete a
  previously clean window, which can only shrink `conflictingNotes()` and the blocker sets and
  can never create a new obligation), and the close path consumes its one-shot probe and
  records its decision, which is **bookkeeping**, not application or window state;
- **S5** every admitted job ends exactly once, whenever its own owner ends it, and **a
  completion is charged to the immutable operation it names, never to a binding**.

`invariants()` now runs after **every listed public model event through a dispatcher**
(`PUBLIC_EVENTS` + `installBattery`), **including refused events**, and `status().batteryRuns`
counts the runs so a schedule can assert the coverage rather than the report claiming it.
Symbolic state (`w.held`, `stored`, `w.recording`, `jobs`) is kept apart from claimed fields
(`o.*`, `b.claim`, `b.blockers`). Two honest bounds on that coverage, both from `-v3-ir2`: the
battery covers the **listed public boundary events, not every internal mutator** (`bind`,
`touch`, `armSweep` and `admitFlush` are not on the list, and no enumerated schedule reaches
them as a public boundary — evidence, not a proof of completeness), and `F12`'s structural
assertion is a **list-membership** check: it shows a listed name is wrapped, never that the
list is complete. Separately, `invariants()` is a **self-predicate**: it can catch an internal
inconsistency, never a wrong definition of what is owed. The independent content oracle is the
separate instrument for that, and it has its own stated bounds (§5 (10)).

## 2. The invariant, as it is now enforced

```
identity(w, nk, rev) = `${w.iid}|${nk}|${rev}`          // immutable content identity
unsavedTruth(w)      = ∃ nk: stored[nk].id !== w.held.get(nk)      // equality, never a counter
conflictingNotes()   = notes where two LIVE windows hold different identities
blockers = { save_error : any window unsavedTruth, or an outstanding/failed flush attempt }
         ∪ { recording  : any window whose last client claim says it is recording }
         ∪ { conflict   : two live windows disagree about one note }
         ∪ { claimed blockers from reports }
         ∪ { no_response: an abandoned binding that never reported }
```

Three honest narrowings and one strengthened reading, stated rather than hidden:

1. **Same-buffer supersession, and what a dropped window does to it.** An intermediate revision
   of a buffer the user has since edited past is **not** separately owed — the buffer holds the
   later content, and S1 is a statement about content still held. The cross-instance and
   cross-note cases are *not* narrowed: they are what `F10` and `F13` block on. Revision 3's
   sentence "a newer save never subsumes an older failed edit" is therefore **withdrawn and
   replaced** by this narrower, accurate one. `F2b` was rewritten to say so and to assert the
   case in both directions.
   **"Content still held" has a hard edge, and `-v3-ir2` finding 1 is about it: `drop` DELETES
   the window record, and with it every obligation that window carried.** A dirty disconnect
   *before* a quiesce can therefore settle `ok:true` although typed content was **never
   persisted** — the quiesce cannot overlook a buffer that is no longer in the model. A
   reconnect arrives under a **new instance identity and does not recover or discharge the old
   content**; the old buffer is simply gone. (A disconnect *during* an active quiesce is a
   different case: the binding fails closed with `no_response`, inside the 30 s bound.) So the
   guarantee covers the **current registered/live buffers only**. This is an **unresolved
   production data-loss risk and adoption gap**. It is **not** evidence that shutdown is safe,
   and it is **not** a solution: it needs P5.4's client lifecycle / freeze-ack work *and* a
   preservation-or-recovery design, both validated for real before adoption. **A freeze alone
   recovers nothing that has already been lost.** The reviewer named the minimal model change
   the owner could ask for (keep the record with a `disconnectedAt`, and let "unpersisted"
   range over disconnected-but-present records until a re-register supersedes them); **no such
   change is made here**, and none is authorised by this report.
2. **Two tabs, one note, both flushed.** The store is a single slot per note with no history,
   so the second write replaces the first — the slot is **last-writer-wins**, and this report
   previously mislabelled it "first-writer-wins" (`-v3-ir2` finding 2; the code was always
   last-writer-wins and §6 now says so). The overwrite can never itself be reported as a
   success, because a content identity embeds its instance id: two windows can never hold the
   same identity on one note, so a `conflict` always accompanies an overwrite. The protocol
   does **not** pretend to prevent the overwrite; it refuses to publish a success while it can
   see two live buffers disagreeing about a note (`conflict`). Preventing or merging that
   overwrite is application policy — the client half is P5.4 and is unadopted.
3. **A refused switch is a conservative direction, and closing is not the remedy.** Two tabs,
   one note, neither willing to save first, means no success: the drain reports
   `save_error`/`conflict`, and the next generation keeps reporting `save_error` while the
   surviving window's own buffer is still owed. **Closing a tab resolves nothing by itself.**
   Closing the *offending* tab is exactly the `drop` of finding 1 above — it discards that
   tab's unpersisted content silently; closing the *other* tab does not release the drain
   either, because the surviving buffer is still owed. **The owed surviving content must still
   be flushed**, and the protocol never prescribes discarding unsaved content: on a
   clean-looking answer it refuses to close either conflicting window, so it cannot recommend
   losing a conflict away. Failing closed is the direction this protocol exists for, but it is
   a real cost and it belongs in the card's discussion, not hidden in a limit.
4. **What is stronger than before:** a success now implies, for every live window and every
   note it holds, that the store holds exactly that content — the property ir1's own oracle
   checks (`atOk`).

## 5. Abstract limits — what this does **not** prove

1. **Bounded enumeration, not a proof.** 41 hand-authored schedules plus the mutants
   establish that *no enumerated schedule* violated S1–S5. The old categorical sentence
   ("passing proves the protocol internally consistent") stays withdrawn.
2. **Synchronous world.** Every event is schedule-driven. Real Fastify interleaving could
   expose two binds of one instance between awaits. The invariants are written so such an
   interleaving cannot mint a second token or a second report, but the proof does not
   demonstrate it.
3. **One machine, one process, no history.** `stored` is a model of one content slot per note,
   not a database, and it has no revision history. A crash between save and completion is out
   of scope, and so is any claim about merging two tabs' versions of one note.
4. **Recording is a client claim.** There is no server-side microphone fact in this model and
   none is claimed. `w.recording` moves only when an instance publishes, the blocker rests on
   client honesty, and the P5.4 probe is the only half that could evidence a transition. A
   renderer holding an unsent audio buffer is invisible to this model: **the client freeze/ack
   work is an adoption prerequisite this report may not credit itself with.** The same is true
   of **typed** content in a client that has not registered — see limit 9.
5. **Deferred registrations are counted, not served.** A registration refused by the fence is
   queued and counted; after the release its client is expected to re-register. No service is
   implemented and none is claimed.
6. **`LIVENESS_MS = 2 s` is still a real risk.** A backgrounded renderer can plausibly
   re-arm more slowly; a proposal for the card to decide, not a contract number.
7. **The mutation harness, the adapted probes and the mutant files are scratch** (gitignored
   `test-results/p53-v3-repair-ir1/`): evidence for this report, not a committed test.
8. **Not self-accepted.** An independent review followed (`-v3-ir2`, CLEAR for the stated
   bounded scope, subject to the disclosures in limits 4, 9 and 10); this revision still does
   not accept itself, and nothing here is adopted.
9. **`drop` erases the window record and its obligations — an open production data-loss risk,
   not a solved one** (`-v3-ir2` finding 1). The socket close deletes the record with no
   quiesce-relative qualification and no memory of what the window held, so:
   - a **dirty disconnect before a quiesce** can settle `{ok:true}` although typed content was
     **never persisted** — measured by the reviewer, and hit 143 times in its 500-schedule
     random sweep;
   - a **reconnect** gets a **new instance identity** and does **not** recover or discharge the
     old content; the old buffer is nowhere;
   - a disconnect **during an active quiesce** is a different case: the binding fails closed
     with `no_response` inside the untouched 30 s bound;
   - after a substantiated clean report, a disconnect is correct and safe — the report
     already discharged every obligation and the store really holds that content;
   - S1's scope is therefore the **current registered/live buffers only**. It is **not**
     evidence that shutdown is safe, and it is **not** a remedy. Closing the window, freezing
     the client, or waiting longer recovers **nothing** that was already lost: P5.4's client
     lifecycle / freeze-ack work **plus a preservation-or-recovery design** needs real
     validation before adoption, and this report may not credit itself with either. This is an
     **adoption gap** and it stays open here; nothing in this revision claims to close it.
10. **The battery is bounded in two further ways** (`-v3-ir2` finding 4). It covers the
    **listed public boundary events**, not every internal mutator — `bind`, `touch`, `armSweep`
    and `admitFlush` are not on `PUBLIC_EVENTS`, and no enumerated schedule reaches them as a
    public boundary (evidence, not proof). And `F12`'s structural assertion is a
    **list-membership** check, so it cannot detect an omitted name; the coverage count is
    reported honestly as "every *listed* event", refusals included, and is not restated here as
    anything stronger. The battery is additionally a **self-predicate** — it uses the model's
    own `unsavedTruth`, so it can only catch internal inconsistency, never a wrong definition.
    The independent content oracle is the separate instrument for that, and it is bounded too:
    one buffer per instance (a window returning to a previously written note is not tracked),
    and a `drop` is treated by the schedule as a deletion rather than modelled. Both bounds
    are stated at the oracle's own definition in the proof.

## 8. Remaining tension, stated rather than hidden

A single flush attempt cannot satisfy content that moved on mid-write (`F8`): the report is
refused and the window retries with a `reissue`d credential — safe, and the happy path still
succeeds inside the 30 s bound in the enumerated schedules. Whether a real client retries fast
enough is a question about that client, not about this model; it is recorded, not answered.
And the conservatism of §2 (3) has a price the card must see: two tabs on one note can block a
clean drain, and **closing a tab is not the remedy** — it resolves nothing by itself, the
surviving window's buffer is still owed and must still be flushed, and closing the offending
tab would discard its unpersisted content silently. The protocol fails closed and never
recommends discarding unsaved content; the cost is real and it belongs in the card's
discussion. And §2 (1) / §5 (9) leave an **open** production data-loss risk around a dirty
disconnect, which no wording here closes. **No card, contract, May-edit amendment, acceptance
row, threshold or runtime feature is authorised or implied by this report**, and no owner choice
is adopted by it.
