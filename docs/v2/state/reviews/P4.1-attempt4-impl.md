## Is the fix actually right?

**`queryKeyNames` fails closed.** With the fix, a name that cannot be decoded is
returned exactly as it arrived (`'%zz'`), so it is a string that appears in no
allow-list. Membership in the artifact's allowance is exact-name
(`describeLocation:270`, `allowedQueryKeys.includes(name)`), so an unreadable name
can only produce `query_key_not_allowed`. There is no decode-anyway path and no
wildcard. I confirmed the shape by execution, not by reading the assertion:

```
refusals.length = 2
refusals = ["`scheme_not_https`", "`query_key_not_allowed` — `%zz`"]
domainRule = false
has host_not_allowed = false
queryKeys = ["%zz"]
```

**The shipped guard behaves the same way.** `installer/src/readiness.ts:116-134`,
`queryParameterNames`, wraps the identical decode in `try`/`catch` and leaves an
unreadable name undecoded, with the comment "an unreadable name is not a name
that can be on a list, so it fails closed below"; `readiness.ts:245-250` then
refuses any name not on the artifact's list. It is tested, and the case passed in
my V1 run: `query parameter names > leaves a malformed escape as it arrived, so
it fails closed against any list`. The probe's copy now mirrors it line for line
in behaviour.

**The probe's copy has no caller that would now behave differently.**
`queryKeyNames` has exactly two call sites, both inside `describeLocation`: line
269 (the refusal loop) and line 287 (the `queryKeys` field). Before the fix a
malformed name meant neither ran — the `URIError` escaped at 269, inside
`describeLocation`, inside `main()`'s bare loop, before
`writeFile(evidencePath, …)` at line 487. After the fix both run, and what they
now produce is a diagnostic: one more `query_key_not_allowed` refusal naming the
offending name, and the name in the recorded key-name list. Nothing downstream of
`describeLocation` in the probe makes a *security* decision — `render` only
formats, and `main` only counts hosts it observed. The only caller whose output
changes in substance is the evidence writer, and it changes from "silently no
record" to "a record that names the refusal".

**Is there still an input that crashes the probe?** I could not find one. I ran
the committed `describeLocation` + `renderArtifact` over 18 crafted inputs —
malformed escapes in names and values, a bare `%`, `%ED%A0%80` (lone surrogate),
`%C3` (truncated), `a%zz` beside an admitted `a`, `Expires` beside `%zz`,
`%2500zz`, a name that decodes cleanly to something containing a malformed
escape, an array-bracket name, an empty `Location`, a non-URL string, and a URL
with no query at all. **Total crashes: 0.** The single `decodeURIComponent` call
in the file is the one inside the helper, and the only other throw site
(`new URL(raw)`) is already guarded. The crash class the card describes is
closed.

**Is there still an input that writes something unredacted?** Two, both in
`redactQuery`, both the named follow-up rather than anything this diff
introduced:

1. `redactQuery` (`probe-redirects.mjs:296-299`) redacts only from the first `?`,
   so a `Location` carrying **user-info** is written verbatim. I confirmed it:
   `https://user:secret@127.0.0.1/x?%zz=1` renders with `secret` in the output.
2. A **fragment** token likewise survives: `https://127.0.0.1/x#tok=1?%zz=1`

Neither is in scope: AM-064 authorises a decode and nothing else, and the card
says in terms that changing redaction behaviour is a privacy-relevant change

carried forward.

I also found a third, which the card does **not** name and which I am recording
