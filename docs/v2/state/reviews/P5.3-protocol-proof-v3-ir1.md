## Findings

**1 — SEVERE, data loss. `closeAnswer` publishes the client's answer into the server's
record *before* deciding, so a recording window closes on `recording:false`.**
`closeAnswer` calls `this.publish(wid, iid, live)` (425), overwriting `w.recording` from
the claim; the `recordingTruth(w)` check (430) then reads what it just wrote. This is
**ir2 finding 4's laundering, reintroduced on the close path** — `X10`: window published
`recording:true`; answer `{recording:false,unsaved:false,saveInFlight:false}` →
**`{"code":"decided","decision":"close"}`**. `X10b`: the same lie on the *report* path is
correctly `report_unsubstantiated`. `sawRecording` is captured after the overwrite, so S2
is silent. Report 68–69 and `R18`'s "a clean-looking answer cannot overrule what the server
knows for itself" are false; `R18` tests only the agreeing direction. **Minimal correction:**
delete the `publish` call and compare `live.recording` against the pre-existing
`this.recordingTruth(w)`; if a stop-recording transition must be admissible, admit it as an
explicit guarded operation (the fix already built for the report path), never as a side
effect of reading the answer. **Missing invariant:** *the close decision must be a pure
function of pre-existing server state plus the answer; no accessor on the decision path may
mutate a window record.*

**2 — SEVERE, data loss. `persisted` is a per-note **maximum** while revisions are
per-window counters, so one window's save subsumes another window's different content on
the same note.** `settleFlush` does `if (a.target.rev > p) persisted.set(noteId, rev)`
(298–300); `unsavedTruth(w) = w.rev > persistedRev(w.openNote)` (92). Revisions from two
windows are not comparable numbers. `X1`: w1 saves `note-1@rev2`; **ten milliseconds
later** w2 edits `note-1` (its own `rev1`, never saved); `unsavedTruth(w2)` is `false`,
its clean report is `accepted`, and the quiesce publishes **`{ok:true,blockers:[]}`**
with the fence up while w2's content is nowhere. `X1b`: the same with colliding counters.
Decisive: **inverting only the completion order of the proof's own `F2` schedule** — w2
(rev 3) before w1 (rev 1) — publishes `ok:true` with `note-1@rev1` never written. Report
72–73 ("**a newer save never subsumes an older failed edit**", justified by `F2b`) and the
`F2b` row are false; `F2b` only ever exercises one window.
**Minimal correction:** make revision identity carry across instances — key `persisted`
by `(instanceId, noteId)`, or compare against a server-minted monotonic per-note version
instead of a client counter — and add the inverted-`F2` order as a permanent schedule.
**Missing invariant:** *content is persisted iff the exact `(window, note, revision)`
triple that produced it was proven written; a save of note N at revision r proves nothing
about another window's revision of note N.*

**3 — SEVERE, data loss. `settleFlush` finds "the first unsettled attempt" by scanning
the binding (295) instead of by operation id, so a stale completion for A settles the
newer B.** `X2`: A completes; the user types again; `reissue` mints a fresh credential and B is admitted
at rev 2 (exactly `F8`'s sequence); the **delayed duplicate delivery for A** → `accepted`, marks
**B** settled, advances `persisted['note-1']` to 2, and the
quiesce publishes **`{ok:true}`** over content B never wrote. `X2b`: the same delivery carrying
`error` fails B and destroys A's recorded outcome. S5's "whenever **its own owner** ends it" and
`R15`'s "however often the delivery reports it" hold only because `R15` never reissues; the
record already carries `attempt.jobId` and does not use it.
**Minimal correction:** `settleFlush(b, jobId, outcome)` requiring
`b.attempts.find(a => a.jobId === jobId && !a.settled)`; anything else returns
`stale_completion` and mutates nothing. **Missing invariant:** *a completion is charged to
the operation it names; a binding is not an operation.*

**4 — SEVERE. The epoch fence does not cover `publish` or `declareOpenNote`, so a held success
can be invalidated after the decision.** The fence list (report 78–85) is accurate as far as it
goes — I confirmed registration, edit, job, wait, reissue, non-exempt write and late report are
each refused — but `publish` has no `freeze` check: `X3` shows `publish(recording:true)`
returning `published` under `freeze={epoch:1}`. `declareOpenNote` is likewise unfenced and
worse: it moves `openNote`, manufacturing the very state S1 forbids. `invariants()` **does** catch
both (`S1 recording state overlooked`; `S1 an unpersisted revision overlooked`) — the strongest
evidence these are real defects, not modelling noise — but no schedule reaches them: the battery
runs in only **4 of 34** schedules, so report line 22's "after every event" is false. **Minimal
correction:** guard both with `frozen_no_publish` / `frozen_no_declare`, and wrap `test()` so it
runs for every schedule.

**5 — SEVERE, data loss. A note switch abandons the previous note's unsaved revision
permanently and the quiesce publishes success.** A window record holds one `(openNote, rev)`
pair, so a switch drops the old note's revision out of the model entirely. `X4`: edit
`note-1`, open `note-2`, flush `note-2` cleanly → **`{ok:true,blockers:[]}`**,
`truth.unsaved === 0`, and it is **never flushable again** (next generation a flush of `note-1`
is `flush_wrong_note`). `declareOpenNote` is refused only while a save is *outstanding* — the
wrong window; the dangerous case is a switch with nothing outstanding. **Minimal correction:**
track unsaved state as a set of `(noteId, rev)` per window, or refuse a switch while the open
note is unsaved. **Missing invariant:** *S1 must range over every `(window, note)` held.*

**6 — MODERATE. `settleFlush` validates no outcome shape.** `settleFlush(b,'Save')` returns
`accepted` and ends the job; no invariant reads anything but `'error'`/`'saved'`. **Minimal
correction:** `if (outcome !== 'saved' && outcome !== 'error') return {code:'invalid_outcome'}`
before any mutation — one clause, preserving ir2 D1's discipline. **7 — MODERATE:** "served on
release" is a count, not a service — `releaseByShell` reads `served = this.deferred.length` and
clears the array, and no registration happens, so `X3b` finds `status().windows === 1` and no
`w2|` key after release. Report line 85 and the `F7` assertion overstate; the honest sentence is
"counted, and its client is expected to retry". The safe core — queued, not dropped — is real.

**8 — MODERATE. A stdin-reachable boundary throws instead of returning a code.**
`releaseByShell` asserts on an unrecognised message, and `shutdown` is in the model's own
verbatim `BRIDGE_VOCAB` (71): `X5` shows it throwing `P10: …`. The report's totality claim
(line 51) is accurate for `report`, `intercept` and `closeAnswer` — the same discipline
applied one step short. **9 — MODERATE, related:** recording "truth" is a client claim, so
S3's "evidenced transition" has no evidence — `recordingTruth(w) === w.recording` (93) and
`publish` writes it, so `X6` publishes `recording:true`, then `false` with nothing to show for
it, and the quiesce publishes `ok`. No server-side microphone fact exists; the blocker rests
on client honesty plus the P5.4 probe, and the report should say so rather than listing
`w.recording` among state "kept strictly apart from claimed fields" (23–25).

**10 — LOW. Prose: U3/U4/U6 are reclassified as owner questions.** Report line 130 lists them
under "**Still the owner's**"; revision 2 classified U3/U4 as **engineering** ("same two files
either way, no contract text") and U6 as **authorial**, and ir1's table agrees — contradicting
the same paragraph's line 131 ("No owner engineering question is raised by this revision").
**Correction:** restore the rev2 classification and say only that v3 adds no *new* owner
question. None is implied by this review either.

## Acceptance

**Not CLEAR.** The bounded scope is well built and eight of ten guarantees I could test hold,
but three stated guarantees do not: exact revision identity across instances (2), a close that
cannot discard recording state (1), and a monotone success under the epoch fence (4). Each has
a one-or-two-clause correction, and findings 1–5 belong as permanent schedules beside the ones
they break — all reachable in the model's own event vocabulary, with no browser, server or
production claim needed. The report's **abstract limits** are honest about the
browser buffer (4), the synchronous world (2) and the single machine (3), and I do not dispute them: limit 4 is correctly scoped as *server-state* safety, and what is
missing is only the client freeze/ack half — an **adoption prerequisite**, not something this
report may credit itself with. Recommended: fix 1–5 as permanent schedules, 6 as one guard
clause, correct 7 and 8's wording and guards, reclassify 10, re-audit. Nothing here authorises a
card, contract, May-edit amendment, acceptance row or production change. Model: an Orca worker
on `opencode-go/space-bunny-free`.
