## DEFECTs — settleable now

These are text defects in `docs/v2/cards/P3.6.md`. Each costs a text edit today
and a review round on the critical path after P3.4 and P3.5 land. None of them
depends on a sibling landing.

### D1 — The dispatch does not exist, and cannot be generated
`build-dispatch.mjs:82-83` gates on `PROGRESS.json`; P3.4 is `BLOCKED` and P3.5
is `NOT STARTED`. *Failure scenario:* a coordinator treats P3.6 as
review-ready, hands an implementer the card file directly, and the
implementer runs `npm run tauri:build` against whatever `build/linux-resources/`
a previous attempt left behind — P3.4's V0 explicitly deletes that folder when
it finishes (`P3.4.md:540`), so the bundle is empty or absent and the failure
appears as a mysterious Tauri packaging error with no card text explaining it.
*Correction:* record P3.6 in `BLOCKED.md` naming P3.4 and P3.5, and repair the
card text now against D2-D10 below so that when the dispatch is finally
generated it is correct on the first pass.

### D2 — The card names no port, so no port would ever be dispatched
`P3.6.md` contains no `--port <p>` placeholder anywhere.
`build-dispatch.mjs:126` substitutes the dispatch's port **only** into that
literal; with no literal present, a generated P3.6 dispatch carries no port at
all and V3's "in a sandbox" resolves to whatever the implementer picks.
*Failure scenario:* the implementer picks 7835, which P3.4 holds; P3.4's
sandbox server is already bound, the smoke run fails with `EADDRINUSE` or worse
succeeds against the wrong instance, and ten flows report confusing failures.
*Correction:* give V3 a `--port <p>` placeholder in the card so
`build-dispatch.mjs` pins it, and name a free candidate in the card text the
way P3.8 does (`P3.8.md:274`). **Port check:** P3.4 holds **7835**; P3.5 holds
**7837** and **7839**; P3.7 defaults to **7834**; P3.8 holds **7860**; S3.2
holds **7840**; the orphaned sandbox servers the owner chose to leave sit on
**7861** and **7807**. The whole `7800-7889` sandbox range (`RUN-CONFIG.md` §1)
is otherwise open, so a collision-free pin exists — the defect is that the card
asks for none. I did not touch any port, so the two orphaned listeners are
taken from the coordinator's brief and are unverified by me.

### D3 — V1 runs `tauri build` with no producer in front of it
`P3.6.md:31` is `npm run tauri:build`. `src-tauri/tauri.conf.json` declares no
`beforeBuildCommand`, so `tauri build` copies whatever
`build/linux-resources/` already holds, and
`scripts/v2/package-linux-resources.sh` is the only producer of that folder
(`P3.4.md:540`). *Failure scenario:* the AppImage ships a server binary that
predates its own source — the exact defect that cost P3.4 an attempt, recorded
in that card. *Correction:* make V1 run
`bash scripts/v2/package-linux-resources.sh && npm run tauri:build`, and say
in the card that the literal producer invocation is the only correct one
because there is no `package:linux` script.

### D4 — V3 names no command that builds the test AppImage it runs
`P3.6.md:33` says "`scripts/v2/tauri-e2e-smoke.test.mjs` on the **test**
AppImage", but no row builds it. `package.json:24` already has
`tauri:build:test`. The card also does not inherit P3.4's Rule B re-bundle
trigger — the condition under which the flagged web bundle and a fresh server
must be re-bundled. *Failure scenario:* V3 launches whatever
`src-tauri/target/release/bundle/appimage/*.AppImage` is on disk from a prior
card's run, so ten flows are exercised against a stale binary and the row
reports green on code nobody shipped. *Correction:* add a step before V3 that
runs the re-bundle equivalent of P3.4's V0 for the **test** identity, or state
explicitly that V3 is `NOT RUN` unless the re-bundle condition holds, with P3.4
referenced by name rather than restated.

### D5 — V4 is not a command
`P3.6.md:34` reads "the AppImage contains `THIRD-PARTY-LICENSES.md` | present".
No command, no cwd, no method. An AppImage is a squashfs image; "contains" is
not something a shell can answer by existing. *Failure scenario:* the
implementer `ls`s the artefact directory, sees the file next to it, and records
`PASS` for a licence that was never inside the image. *Correction:* name the
extraction and the assertion — `--appimage-extract` (or the card's agreed
equivalent) into the sandbox, then `test -f` on the extracted path, and state
which path inside the image is required.

### D6 — `Read` omits two of the card's own dependencies
`P3.6.md:18` reads "Outputs of P3.1 to P3.5". `Depends` is `P3.4, P3.5, P3.7,
P2.R` (`P3.6.md:9`). P3.7 is missing and it is the card that makes the SPA
fetch the hashed asset rather than only the shell; its output is what V3's
flows actually run against. P2.R is missing too. *Failure scenario:* an
implementer reads P3.1-P3.5, never learns that the SPA check changed shape,
and treats a bundle that serves `GET /` as sufficient. *Correction:* change the
line to name P3.7 and P2.R explicitly.

### D7 — L3 rows are not run through `sandbox.mjs`
`RUN-CONFIG.md` §2: L3 is "the card's listed commands, **all through
`sandbox.mjs`**". V1 and V2 (`P3.6.md:31-32`) are bare, and V3 says "in a
sandbox" without naming `scripts/v2/sandbox.mjs` or any containment assertion.
*Failure scenario:* V1's `tauri build` runs in the developer's own tree and
`npm run build` underneath the producer overwrites the live `web/dist`, so a
verification run perturbs the working tree of a card that is not this one.
*Correction:* route V1 and V3 through `node scripts/v2/sandbox.mjs` and name
the containment assertions (sandbox path, `APUNTA_DATA_DIR`, port not 7717) as
P3.7 and P3.8 do.

### D8 — May edit grants `tauri.conf.json` with no constraint P3.4's V3 checks
`P3.6.md:21-22` puts `src-tauri/tauri.conf.json` in May edit for "bundle
metadata". P3.4's V3 greps `src-tauri/tauri.conf.json`,
`src-tauri/tauri.test.conf.json` and `src-tauri/build.rs` for
`invoke_handler` and `withGlobalTauri": true` and requires **no match**, and
`test ! -e src-tauri/capabilities` (`P3.4.md:543`). P3.6 promises nothing
about that. *Failure scenario:* P3.6 adds a capability file or a global Tauri
handle while copying bundle metadata; P3.4's V3 goes red on a card already
`APPROVED` or about to be, and the break is discovered at P3.R, not at P3.6.
*Correction:* add a "Must not edit" line carrying P3.4's V3 invariant verbatim
by reference — no `capabilities/`, no `withGlobalTauri`, no `invoke_handler` in
either config.

### D9 — May edit does not cover the test config V3 depends on
V3 runs the **test** AppImage, built from `src-tauri/tauri.test.conf.json`
merged by `tauri:build:test` (`package.json:24`), and that file is **not** in
May edit (`P3.6.md:20-23`). *Failure scenario:* the implementer finds the test
config needs one bundle-metadata change, cannot make it, and either stops
mid-flight or makes it anyway — the exact stop a sibling's implementer had to
take. *Correction:* either add `src-tauri/tauri.test.conf.json` to May edit
with its scope stated, or add a stop condition saying a needed change there is
a report, not an edit.

### D10 — Stop conditions and resume anchors are absent for a launching card
`P3.6.md:36-37` is "Stop conditions: None specific." P3.6 is L3 and V3 launches
a built desktop app through ten flows, writing screenshots. *Failure scenario:*
the session dies in flow six; a fresh attempt-1 session has no checkpoint, no
`changedFiles`, no statement of which flows were already completed, and either
re-runs everything or believes a partial run. *Correction:* add a stop
condition for each of the failure classes P3.4 and P3.5 already named
(missing WebKitGTK/A03, missing whisper candidate, AppImage absent) and a
resume anchor recording the AppImage path, the port used and the flows
completed.

defect that holds P3.4's rows holds P3.5's rows, so P3.5's final shape is not

### B3 — P3.3's lifecycle codes are exercised but never asserted
