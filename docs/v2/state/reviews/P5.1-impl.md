## Numbered findings for the implementer

None of these affects a row above; the verdict stands without them.

1. **`server/src/backup/lock.ts:73-84` (with `index.ts:99`) — the synchronous
   lock can only lose to an asynchronous holder, and it does so by freezing the
   process for the full 60 s.** `withBackupLockSync` waits with
   `Atomics.wait`, which by design gives the event loop no turn. If the lock is
   held by `createBackupAsync` (which is what every production caller uses), the
   sync waiter blocks the loop for the whole wait, so the async holder can never
   resume and release; the waiter then burns all 60 s and throws
   `backup_in_progress` even though the other backup would have finished in
   milliseconds. Rule 3's letter is met (a second request waits, then is told),
   but a sync caller reaching this would stall every HTTP request in the process
   for a minute. It is not reachable today: `runBackup` and
   `maybeRunDailyBackup` have no production caller — `rg` finds them only in
   `server/src/routes/backup.ts:60` (async) and `server/src/index.ts:94` (async),
   with the sync pair used only by `backup.test.ts`. What would make it sound:
   have the sync entry point refuse immediately when the lock is held by an
   async run (a lock that records its holder's kind), rather than busy-waiting
   for a holder it is preventing from finishing. Do not shorten
   `BACKUP_LOCK_WAIT_MS` to achieve it (HS-7).
2. **`server/src/backup/archive.ts:94` and `index.ts:61-74` — `op` is not
   threaded through `RunBackupOptions`, and `pre-migrate` has no case.** A
   pre-migration snapshot taken through `runBackupAsync` would still stage under
   `<dataDir>/staging/backup-<uuid>/`, so the "identifiable by path" property of
   decision 5 only holds for a caller that reaches `createBackup` directly. This
   does not fail decision 5 (it requires `<op>` to be *defined* so P5.2 needs no
   contract change, and `BackupOperation` plus `snapshotDatabase` are exported
   for that), and the return discloses it. What would close it: one optional
   `op` field on `RunBackupOptions` passed into both entry points, plus a case
   asserting a `pre-migrate` run stages under `pre-migrate-<uuid>` and cleans up.
   For P5.2, not for this card.
3. **`server/src/backup/backup.test.ts:179-202` — the WAL case does not assert
   the precondition that makes it a tripwire.** The case never checks that the
   source still has an uncheckpointed `-wal` at the moment of the backup, so if a
   future change checkpointed first, the case would keep passing while no longer
   being able to catch a bare `copyFileSync`. The precondition *is* pinned, for
   both methods, at `server/src/db/snapshot.test.ts:72-81`
   (`expect(existsSync(`${source}-wal`)).toBe(true)`), so the property is not
   unguarded. One extra line in the backup case — asserting
   `existsSync(dbFile + '-wal')` before `createBackup` — would make the case
   self-contained. Step 3's own wording is met as written, so this is a
   strengthening, not a defect.
4. **`server/src/routes/backup.test.ts:18-25` — the hoisted `vi.mock` is more
   than "the 409 assertion, and nothing else".** The card's May edit for that
   file is the 409 assertion; the module-level mock of
   `../backup/index.js` is the mechanism for it, so I read it as in scope, and
   it is a pass-through (`vi.fn(actual.runBackupAsync)`) so every other case in
   the file still writes a real archive — verified by running the file alone
   (15/15, exit 0). Recording it because it is the one place where the diff
   exceeds the file's stated scope, so the coordinator can rule on it. The
   refusal itself is proved for real in `backup.test.ts` through
   `lockWaitMs`, which is the right place for it; the route case tests the
   mapping only, as its own comment says.
