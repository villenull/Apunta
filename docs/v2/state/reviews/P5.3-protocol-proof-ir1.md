## Blocking — the model contradicts a stated guarantee

**D1 — `settleFlush` records the save error too late; a failed save returns `ok:true`.** `165–168`
calls `this.end(b.jobId)` *before* the `save_error` branch, and `end` (93–96) runs `maybeSettle`,
which finds every binding reported and no jobs and settles clean; the `save_error` `settle` then
returns `null` because the quiesce is already settled. Probe **X4**: the window reports while its
admitted save is in flight, the save then fails → `{"ok":true,"blockers":[]}`, `maintenance=true`.
Unsaved text, snapshot taken anyway. **X16** shows the same dismissal across a generation boundary.
This is B8's data-loss direction reintroduced inside the repair; S7 only tests
`settleFlush(b,'error')` *before* any report, so no report can have primed the settle. **Minimal
fix:** record the error and settle in one step — `end` must not reach `maybeSettle` before the
outcome is known (pass a `pendingOutcome` through `end`, or settle before ending the job).

**D2 — a stopped window can be silently ignored; the quiesce returns `ok:true`.** `187` excludes
gone-unreported bindings from the "everyone reported" test but contributes **no** `no_response`
blocker for them (`188` flattens only `b.blockers`), and `135–138` arms the 2 s timer only from
`drop`. **X3**: `drop('w1')` then `w2` reports → `{"ok":true,"blockers":[]}`, `why="clean"`,
`maintenance=true`, and `w1`'s armed timer is now dead. S5 proves only the reverse order, so its
`no_response` comes from the timer, never from the aggregate. **Minimal fix:** a gone binding must
contribute `no_response` in `maybeSettle`, or the drain must refuse to settle while any binding is
unreported regardless of `gone`.

**D3 — P1's "one quiesce at a time" guard is inverted.** `101` asserts `!this.q || !this.q.settled`;
while a quiesce is **in flight** `settled` is `false`, so `!this.q.settled` is **true** and the
clause admits exactly the case P1 forbids. **X1**: two `initiate('shell-stdin')` calls both
succeed, `this.q` becomes `q2`, `q1`'s bindings are orphaned. **Minimal fix:**
`assert.ok(!this.q || this.q.settled, …)`.

**D4 — one timer decides the wrong generation, and a generation is never decided at all.** `106`
arms `() => this.settle(['timeout'], …)` with no generation check and `settle` (191–193) reads
`this.q`. **X2**: `q1` settles `ok`, the shell lifts, `q2` born at t=10000 is failed `['timeout']`
at t=30000 — 10 s early. **X17**: two in-flight quiesces (permitted by D3) → `q2` settles at
t=30000 and `q1` stays `settled=false` forever, its outcome never reported to the shell. **Minimal
fix:** capture `q` in the closure and guard `if (this.q !== q || q.settled) return;` — the guard
`137` already uses.

**D5 — rollback ends no jobs, and a leaked job wedges the next quiesce for the full 30 s.** `199`
clears `maintenance`, `q`, `polls`, `pendingClose` and nothing else, so `this.jobs` survives and
`185` keys `maybeSettle` on `jobs.size > 0` across the boundary. **X6**: after a timeout rollback
`active()` still holds the refine. **X7**: one clean window, no flush, no real work — the next
quiesce cannot settle on its report and ends `['timeout']` after 30 s. Contradicts P9's "end each
job exactly once" outright. **Minimal fix:** `rollback` must terminate inherited jobs, or
`maybeSettle` must ignore jobs not belonging to `this.q` — say which.

**D6 — a window registering mid-quiesce is never bound; the quiesce settles `ok` over it.**
`104–105` binds only the windows present at entry; `118–122` never binds. **X10**: `w2` registers
mid-quiesce with `recording:true, unsaved:true`, gets no binding, `{"ok":true,"blockers":[]}`
settles anyway while `status()` reports `windows=2, recording=true`. Silent-discard direction, and
C-UPD@1's close paragraph is the rule offended. **Minimal fix:** bind on registration while a
quiesce is in flight (with its own token), or exclude late registrants from `status().windows`
until the next quiesce — say which.

**D7 — P8's "neither held wait nor report within a named 2 s bound" is implemented nowhere.** The
only `no_response` timer is armed by `drop` (`137`); `lastSeen` is written at `120`/`121`/`127` and
read by nothing. **X13**: `w2` holds a wait, never answers, socket fine → nothing armed, and after
30 s the outcome is `['timeout']`, `why="global deadline"`. B4's fix (b) — `lastSeen` so a window
with neither held wait nor report is marked gone — is claimed as P8 but not built. **Minimal fix:**
a `lastSeen` liveness sweep at the named bound, and say whether both triggers share one rule.

**D8 — the close probe is not one-shot; a body-less answer is not refused.** `210–213` sets
`pendingClose`; `215–222` never clears it nor records that the probe was answered. **X8**: one
`probeToken` answers twice and the decision flips `close` → `confirm_recording` (overwriting
`p.decision`); `closeAnswer(w, token)` with no `live` throws `TypeError` instead of returning a
code. Contradicts report line 82 ("a one-shot probe") and P8. **Minimal fix:** clear `pendingClose`
on the first accepted answer; default `live` to `{}` with a refusal code for a missing body.

**D9 — P4's "bound to that window's open note" does not hold when the note is undeclared.** `160`
reads `if (b.noteId && b.noteId !== m[1])`, so a binding with `noteId === null` admits **any** note
id. **X11**: no note declared, `PATCH /api/notes/note-somebody-elses` with the window's own live
token → `{"admitted":"flush-save"}`; S3's wrong-note case passes only because it declares the note
first. Not a security hole (self-minted id, same-origin app), but a client bug can flush the wrong
note under a valid credential. **Minimal fix:** refuse when `b.noteId` is null
(`flush_no_open_note`), and say whether an unopened window may flush at all.

## Unproved claims — model omissions, not contradictions

Real but lower: the report asserts a property the model cannot demonstrate either way.

- **D10 — `intercept` never reads `this.maintenance`.** `140–148` gates on `this.q`; after `199`
  sets `maintenance=false, q=null` every non-exempt request is still refused. **X5**: after a clean
  rollback `POST /api/draft` → `{"admitted":"refused","code":"maintenance"}`. Report line 259's "the
  app is writable again" is asserted on the flag alone. Add the `maintenance===false` early-return
  and assert on a write, or withdraw the sentence.
- **D11 — `polls.clear()` (199) leaves registered windows unbindable.** `110–111` requires a held
  wait, so the shell's next `quiesce{}` throws `P2: a registered window must hold a wait` unless
  the window happened to re-arm (**X9**). S7 and S9 survive only because the author calls
  `reg(s,'w1')` by hand (318, 260) — the schedules paper over the race the report describes in
  prose. Either `bind` tolerates a window with no held wait, or show the re-arm on the clock.
- **D12 — `declareOpenNote` (123) is a silent no-op outside a quiesce.** A note opened before the
  quiesce never reaches the binding (**X12**: `b.noteId=null`), which is why D9 is reachable and why
  every S-schedule declares the note *after* `initiate`. Name the ordering the client must use.
- **D13 — `shortWrites` conflates two refusals.** `146` increments on every non-exempt refusal, so
  a bad-token flush (**X15**) inflates the counter offered as evidence of refused work. P4 promises
  narrow codes; `status()` discards them.

**Refuted: X14** — a window knowing another's live token is refused (`bad_token`), so P6's
`(window, quiesce, token)` separation holds against a second tab. Not a finding.

## Bottom line

The four Part-A reproductions are correct and worth keeping, and the ownership list and the honesty
about U1 are good work. But P1–P9 are asserted from fourteen schedules that each walk one path in
one order; change the order and six of the nine rules break, two of them in the direction that
loses unsaved text (**D1**, **D2**). Fix D1–D9, add the ordering cases, re-run. Until then this is a
**DEFECT**, and 14/14 exit 0 is evidence about the fourteen examples only.
