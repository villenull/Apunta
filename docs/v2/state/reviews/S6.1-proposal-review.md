## Verdict: **DEFECT**

The proposal is a strong document. Its two hardest judgements are right — the
correction of D5/D11 in §2.1 (one `sandbox.mjs env`, not two) is correct and
matters, and the storage read rule in §5.1 is implementable exactly as written
with no data movement. The defects below are bounded and mostly mechanical, but
three of them are load-bearing: **V3's second assertion cannot pass as written**,
**the `chromium` project will run the new Spanish spec and fail**, and **V7 fails
on the card's own checkpoint**. None of them is a design disagreement.

Separately, and this is the finding with the widest reach: **the proposal asks the
owner seven questions. Two of them are the owner's alone.** The rest are
coordinator-authority items or, in two cases, no decision at all.

No legal conclusion is drawn anywhere below. No owner's name, identity, intent or
availability is asserted. The licence election and both Exhibit A fields remain
unresolved pending an owner record, and nothing here should be read as supplying

## A. Blocking defects, with the exact bounded fix

### A1 — V3's second half asserts a URL shape the built app does not produce

`docs/v2/evidence/P3.7/v3.md:43-44` records the built bundle's dictionary assets
as `/assets/index-CdfGWZcu.aff` and `/assets/index-CmfKht-g.dic`, and
`P3.7/v1.md:87` lists `web/dist/assets/index-D7iOgJVA.js` in the manifest. The
Playwright web server serves the **built** SPA
(`e2e/playwright.config.ts:119` — `npm run build && node server/dist/index.js`),
and Vite rewrites `new URL('../../../node_modules/dictionary-es-mx/index.aff',
import.meta.url)` to a hashed `/assets/…` name. The URL the browser requests in
V2/V3 therefore does **not** contain `/dictionary-es-mx/`.

§7 V3 requires: *"asserts that **both** `index.aff` and `index.dic` under
`/dictionary-es-mx/` **were** requested from a loopback host."* As written that
assertion is false against the artefact the row runs against, so the row goes red
for a reason unrelated to the code — the exact failure mode §7.1's contingency
clause exists to prevent.

It also removes V3's meaning entirely: the **first** half ("no request URL contains
`/dictionary-es-mx/` on `/`") is trivially true whatever the code does, because no
URL will ever match. The proposal calls this half "the failure this row exists to
catch"; as written it cannot catch anything.

**Fix.** Restate both halves on a basis the build actually produces: record the
emitted asset filenames from `web/dist/manifest.json` during the row, then assert
(a) **zero** requests whose path ends `.aff`/`.dic` on the home route, and (b)
**exactly two** such requests, same-origin loopback, once a note body with the
Spanish dictionary mounted. Keep the `/dictionary-es-mx/` substring only as a
*source-level* assertion, which belongs in V1 (a unit case on the two URL
constants), not in a browser row.

### A2 — V6 is vacuous, and its premise about "populated" run folders is wrong

Three independent reasons, any one sufficient:

1. `--project=chromium` runs against the web server started **without**
   `APUNTA_DEV_SPANISH` (`e2e/playwright.config.ts:140` sets it only for the
   second server). Under C-LANG@1 rule 1 and D12, `spanishAvailable` is therefore
   `false` in that project, the Language control is hidden, and `es-MX` is refused
   by `PUT /api/settings`. The Spanish code path does not exist in that build, so
   "no Spanish dictionary was requested" is true by construction — it is a check
   of the build flag, not of lazy loading.
2. The URL predicate is the A1 one, so it also matches nothing.
3. The stated rationale — *"A green V2 on a **populated** folder and a green V6 on
   a **fresh** one together are what make the lazy-load claim mean something"* — is
   factually wrong about this harness. Every `sandbox.mjs env --port …` call
   mints a **new** run folder (`cmdEnv` → `newRunId()` →
   `ensureRunDir`, `scripts/v2/sandbox.mjs:352-362`). V2's own folder is already
   fresh and unpopulated at the moment its dictionary assertion runs. There is no
   populated-versus-fresh contrast to construct.

**Fix.** Delete V6. Its intent is already carried, correctly, by V3's first half
once A1 is fixed. If a fresh-folder contrast is wanted anyway, it belongs as a
note in V2's evidence ("this run folder was created by this row's own
`sandbox.mjs env` and no earlier run touched it"), not as a second row with a
second run folder and two more ports.

### A3 — One `testIgnore` is not enough: the `chromium` project will run the new Spanish spec

`e2e/playwright.config.ts:98-114`: the `chromium` project has **no** `testIgnore`,
so it collects every spec in `./tests`. The card's new `e2e/tests/spelling-es.spec.ts`
will therefore run there, against a build that does not offer Spanish, and fail.
§3.1 budgets exactly "**one** `testIgnore` entry" in `e2e/playwright.config.ts`,
which is the `es-MX` project's entry for `spelling.spec.ts`.

**Fix.** Budget two entries in the same May-edit file: the `es-MX` project gains
`spelling.spec.ts`, the `chromium` project gains `spelling-es.spec.ts`. Do **not**
solve it with a self-`skip()` inside the spec — a spec that skips itself is a
vacuous green, which §9 stop 6 and §2 of `e2e/support/no-english.ts` both forbid in
this project's own words.

### A4 — V7 fails on a file the card is required to write

§3.1 names three required outputs: `docs/v2/state/returns/S6.1.md`,
`docs/v2/evidence/S6.1/`, **and** `docs/v2/state/cards/S6.1.json`. V7's expected
result admits only *"one of §3.1's May-edit paths or one of the **two** required
outputs (docs/v2/state/returns/S6.1.md, docs/v2/evidence/S6.1/)"*. The checkpoint
is in neither set, and §9 stop 8 requires the card to write it. The row fails on
the card's own bookkeeping.

**Fix.** Add `docs/v2/state/cards/S6.1.json` to V7's allowed set.

### A5 — `shared/src/index.ts` is missing from May edit, and the per-locale key cannot reach `web/` without it

`shared/src/index.ts:499-504` is the only re-export of the spelling vocabulary.
`web/src/components/SpellingProvider.tsx:1` imports `SPELLING_WORDS_SETTING` and
`spellingWordsFrom` from `@apunta/shared`, not from the source file. Any new
per-locale symbol §5.1 requires in `shared/src/spelling.ts` is unreachable from
`web/` until `shared/src/index.ts` exports it — and `shared/src/index.ts` is not
in §3.1's May-edit list, and `Must not edit` (§3.2) is silent on it, so an
implementer following the card literally stops.

**Fix.** Add `shared/src/index.ts` to May edit, scoped in words to *the
`from './spelling.js'` export block only*.

### A6 — No row or fixed decision performs the install that V4 depends on

§9 stop 8 names "the `npm install` of `dictionary-es-mx@2.0.0`" as the card's one
non-repeatable side effect, and §10 records it as evidence. But no verification
row and no Fixed decision contains the command. V4's whole licence half depends
on the lockfile carrying the package, and §3.1's `web/package.json` line only
states the value.

**Fix.** Add the command verbatim, from the repository root, e.g.
`npm install --workspace @apunta/web dictionary-es-mx@2.0.0`, as a Fixed-decision
step immediately after the `web/package.json` edit and before V4, with the
checkpoint clause recording it in `sideEffectsDone` at that moment.

### A7 — The lockfile scope is stated too narrowly

§3.1 says the May-edit lockfile change is *"the resolved
`node_modules/dictionary-es-mx` entry only"*. npm also rewrites the workspace's
own dependency list in the same file (`package-lock.json:5453-5457`, the `"web"`
entry's `dependencies`). A reviewer diffing the lockfile against that wording sees
an unexplained second hunk.

**Fix.** Name both: the `packages["web"].dependencies` line and the resolved
`node_modules/dictionary-es-mx` entry.

### A8 — V0's gate does not prove an election

`rg -n "dictionary-es-mx" docs/decisions.md` returning "at least one line" proves
only that the string occurs. L-POLICY@1 requires the **election** to be stated
there, so a row that merely names the package satisfies the row and not the
policy — and the whole card is gated on it.

The proposal is right that the row is empty today
(`rg "MPL-1\.1|dictionary-es-mx" docs/decisions.md` → no match, confirmed), so
Stop 1 fires correctly. The gate itself is what needs tightening.

**Fix.** Require a quoted line that carries package, elected arm and version
together — e.g. `rg -n "dictionary-es-mx.*MPL-1\.1|2\.0\.0" docs/decisions.md` —
and require `V0-preflight.md` to quote the row verbatim rather than report a
match count. A match count is not evidence.

### A9 — V3 is not a command

§7 V3 reads *"the same command as V2, with `spelling-es.spec.ts` replaced by
`--grep "…"`"*. IR-05 exists precisely to reject rows that name no command, and
"replaced by" leaves two readings open (does the file filter go, does the second
`--project` stay). The sibling cards this proposal cites do not write rows this
way: `S2.11.md:629` writes the whole command out.

**Fix.** Write V3's command out in full in the table.

### A10 — V2's exit code is masked and its cleanup discards another card's work

`… && ( cd e2e && npx playwright test … ) > "$RUN_LOGS/v2.log" 2>&1; rc=$?; echo
"exit=$rc"; git checkout -- docs/v2/evidence/P2.2/screenshots/`

Two problems. First, the row's process exit status is `git`'s, not Playwright's —
the evidence writer has to scrape a printed line instead of reading an exit code,
which RUN-CONFIG §4 asks for directly. (The `&&` chain also means that if the
`sandbox.mjs env` step fails, `rc` captures *that* failure and prints it in a form
that reads like a test failure.)

Second, and worse: `git checkout -- docs/v2/evidence/P2.2/screenshots/` is a
blanket restore of **another card's evidence directory**. Only
`e2e/tests/brand.spec.ts:157` writes there; nothing in `spelling-es.spec.ts` does.
And `docs/decisions.md` (2026-09-22, *"Resolve stale writes with explicit Keep
mine / Take theirs actions"*) records the project's own rule: **a concurrent
change must never be silently discarded or overwritten.** S2.11 used this
cleanup because S2.11 ran `brand.spec.ts`; S6.1 does not.

**Fix.** Delete the `git checkout` from V2 and V6, and end the row with
`exit $rc` so the row's status is the run's status.

## B. The proposed `testIgnore`, examined directly

The instruction to examine this is the right one, so here is the whole analysis.

**Is X1 real?** Yes, and the proposal is right about the mechanism. The `es-MX`
project re-runs every spec but `language-control.spec.ts`
(`e2e/playwright.config.ts:107-113`) against a server started with
`APUNTA_DEV_SPANISH=1`, whose data folder is shared with — and after — the
`es-MX-language` project, which leaves the stored `language` at `es-MX`
(`e2e/tests/language-control.spec.ts`, final assertions). `e2e/tests/spelling.spec.ts:46`
asserts `['Teh', 'criticised']` against whatever dictionary is loaded. Today both
projects load English, so it passes in both. The moment S6.1 ties the dictionary
to the active UI language (§5.1 rule 1), the `es-MX` project loads the Spanish
dictionary and every English assertion in that spec is evaluated against a
Spanish word list. X1 is correct.

**Is suppressing it "suppressing a failing applicable test to pass"?** No — and
the distinction is worth stating in the card, because it is the whole defence.
Under the card's own rule, an English-dictionary assertion in a project whose UI
language is `es-MX` is **not applicable by construction**. There is no
implementation in which it could pass; it is not a code defect being hidden, it is
a test whose precondition the design has deliberately removed. Compare the
alternative framings:

- Making the spec locale-aware (OD-4b) edits the very file D6 makes the English
  non-regression guarantee. Correctly not recommended.
- Making the `es-MX` server load English is not available: the language is one
  stored setting per data folder, which is why the config gives the second server
  a folder of its own (`e2e/playwright.config.ts:19-31`). There is no third shape.

**So option (a) is right, with four conditions that must travel with it.**

1. The ignore is **project-scoped and minimal**: `spelling.spec.ts` ignored in
   `es-MX` only, `spelling-es.spec.ts` ignored in `chromium` only (A3). Neither
   name appears in a global `testIgnore`.
2. **Name the coverage that is genuinely lost.** The English spec asserts four
   things the Spanish spec's V2 expectation does not: `spellcheck="false"` on each
   surface (`:48`, `:75`, `:94`), **applying** a correction from the menu
   (`:64-69`), the caret/menu edge-click behaviour (`:51-59`, `:76-81`,
   `:95-100`), and `checkScreen` on the spelling menu (`:63`). Either
   `spelling-es.spec.ts` reproduces the correction-applied case per surface, or
   the return file records the loss in those words.
3. **The ignore must be visible in evidence, not silent.** `testIgnore` removes a
   file from collection; Playwright does not report it as skipped. V2 must record
   the per-project collected-test counts, and V7's return must state the delta.
   A reviewer must be able to see what stopped running without diffing the config.
4. **No self-skip**, and no loosening of anything inside `spelling.spec.ts`. The
   file stays byte-identical, which is also what §3.2 promises and what V7 checks
   with `git diff -- e2e/tests/spelling.spec.ts e2e/support/`.

## D. Storage, tokenisation, suggestion behaviour, load-error UI — verified

**Storage (§5.1).** Correct and implementable as written. `shared/src/settings.ts`
is a flat key → JSON store (`:6-11`), keys are constrained by
`/^[a-z][a-z0-9_]*$/` (`:12-16`) so `es-MX` is indeed impossible as a key, and
`shared/src/spelling.ts:16` is `spelling_words` with
`spellingWordsFrom` (`:22-31`) already reading defensively — so rule 2's
"absent or malformed reads as `[]`" needs no new code. `PUT /api/settings` merges
(`shared/src/settings.ts:21`), so writing the Spanish key cannot clobber the
English one. `stt_vocabulary` is at `shared/src/transcribe.ts:99` and is correctly
excluded. Rule 6 ("no stored value is rewritten") is the right rule and §2.4's
correction of D3 is right: there is no migration hazard *today*, only a future one,
and the card must not be read as authorising one.

**Tokenisation (§5.3).** The mechanism is right and the reasoning is sound: `WORD`
is at `web/src/lib/spelling.ts:27`, `plainWord` at `:37-39`, `allowedWords`
re-tokenises with the same pattern at `:160-167`, and `Misspelling` carries
`[start, end)` character offsets (`:19-24`) — so per-word normalisation is the
only placement that leaves offsets exact. The claim that `¿`/`¡` fall outside the
class is true of the proposed pattern as written. The claim that accent-only
corrections fall through to nspell's own suggester is plausible and is the reason
OD-6 recommends leaving the alphabet alone; V2's non-empty-menu assertion is the
right thing to test it with.

One accuracy fix: the proposed doc comment says *"for text containing no Spanish
letter this pattern matches exactly what the old one matched"*. That is false —
the class also admits U+0300–U+036F combining marks, which are not Spanish letters
and which the old ASCII pattern did not match. Say **ASCII-only text**, and say so
in V1(a)'s corpus description, or the parity case does not prove what the comment
claims.

**Suggestion alphabet.** Leaving `LETTERS` (`spelling.ts:123`) alone is the right
call and is the smallest surface. OD-6 should be deleted rather than asked — see E.

**Load-error UI (§5.2).** The state/surface/key analysis is correct and the
`check-ui-strings.mjs` reasoning is right: `REPORT_ONLY = false` at `:62`, exit 1
at `:259`, both reached by `npm run lint`, and the type-level parity rule in
`shared/src/i18n/t.test.ts:568-589` means a one-catalogue key is a build failure,
not a runtime surprise. Three additions:

1. **"one line, once" is inaccurate.** `SpellLayer` is mounted once per field
   (`ChatComposer.tsx:60`, `NoteBody.tsx:137`, `PatientRenameField.tsx:72`,
   `AddPatient.tsx:114`, `Capture.tsx:447`), so a note page with the chat open
   renders the alert twice, and `role="alert"` fires per mount. Say *one alert per
   mounted spell surface*, or name a single mount point above them.
2. **The retry story is missing.** `ensureLoaded` sets `loadingRef.current = true`
   and clears it nowhere (`SpellingProvider.tsx:72-82`), so a failed load is
   **never retried** for the life of the tab. That is compatible with "leaves
   typing usable" — but a reader will assume a retry exists. State it, or the
   next card will "fix" it by accident.
3. **`STT_VOCABULARY_SETTING` and the request-id guard** are correctly named as
   untouched. The guard does not exist today — the provider has only
   `mountedRef` — so §5.2's V1(f) case is testing genuinely new code, which the
   card should say rather than implying the promise already has an implementation.

## E. The owner package: seven questions, two of them the owner's

This is the finding I would most want the coordinator to act on, because it changes
what the owner is asked to do.

fill runtime placeholders and correct commands and typos, and **"may not: change
any decision, contract, threshold, acquisition item, hard stop, 'May edit' list,
acceptance row, or dependency."** AM-045 and AM-049 are the precedent: a May-edit
widening was put to the owner precisely because §6 forbids the coordinator doing
it.

**§3.1 widens S6.1's May-edit list from five entries to sixteen, and the proposal
does not flag that this needs an owner-authorised amendment.** That is a bigger
ask than the licence election in some ways, and it is currently presented as
drafting. It should be one bundled amendment row covering the widening (with A5's
`shared/src/index.ts` inside it), the `testIgnore` conditions from section B, and
nothing else.

Against that, five of the seven OD items do not belong in front of the owner:

| **OD-2** Exhibit A fields | **The owner's alone.** Naming a person in a shipped notice, and the provenance statement beside it, are not derivable from the repository | Owner |
| — May-edit widening | **The owner's alone**, and currently unlisted | Owner, bundled with the above |

## G. Advisory, non-gating

- **HS-8 and the Spanish patient name.** §7.1 argues no `NAMES.md` entry is needed
  because no person is named. The argument from what the checker scans is sound —
  `scripts/v2/check-es-fixtures.mjs` reads only the two corpus roots
  (`CORPORA`) — and there is precedent for the narrower reading
  (`language-control.spec.ts` creates patients via `uniqueName('E2E language
  patient')` inside the Spanish run). But HS-8's *text* is broader than the
  script: "Spanish uses only names in `e2e/fixtures/eval-es/NAMES.md`". The
  proposal's reasoning is an interpretation, not a fact. Taking the Spanish
  display name from `NAMES.md` costs nothing and removes the argument entirely;
  worth doing for that reason alone.
- **The non-empty-suggestion contingency.** §7.1's contingency clause covers only
  the flagged/not-flagged tables. The `nertua` non-empty-menu requirement is
  equally dictionary-dependent and has no contingency. Add one on the same terms.

  file filter collects nothing in `es-MX-language` (its `testMatch` is the
  language-control regex). Harmless, but `--project=es-MX` alone is sufficient and
  pulls its dependency in anyway — fewer moving parts in the one row that must go
  green.
- **V7 and a shared tree.** `git status --porcelain` will report any unrelated
  in-flight work as a scope violation. Worth a clause saying the tree was clean at
  the card's base commit, or scoping the command to the card's own paths.

  figures the owner sees") has no named destination in §10. The per-file sizes are
  recorded; the *owner-facing* size figure is not. One line, or an explicit
  "not applicable here".
