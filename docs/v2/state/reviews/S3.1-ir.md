  23–25) against "Verification" V1 (line 50); identical text in

  only `e2e/fixtures/eval-es/{tuning,heldout}/**`,
  `e2e/fixtures/eval-owner-es/{tuning,heldout}/**`,
  `e2e/fixtures/eval-es/NAMES.md` and `e2e/fixtures/eval-es/README.md`. V1

  `Cannot find module`, which reads as a broken repo rather than an

  `scripts/v2/check-es-fixtures.mjs` (new) to "May edit" in

### IR-03 — gold-expectation shape is unnamed, and the count rule breaks the 40% floor

- **ID and location:** IR-03, `docs/v2/cards/S3.1.md` "Objective" (lines 14-16)
  and "Fixed decisions" (lines 35-44), read against
  `server/src/eval/corpus.ts:79-87`; same text at `S3.1-ir.md:64-95`.
- **The text that conflicts, or exactly what is missing:** the objective
  requires "each with gold expectations written independently of the production
  guards", and Read points at `e2e/fixtures/eval/` and
  `e2e/fixtures/eval-owner/` for "file shapes, expected-fact format". The card
  then fixes the transcript layout, `<split>/<trap-type>/<name>.txt`, and says
  nothing further about the gold expectations: no file name, no path, no key
  scheme. That matters because the loader this corpus must eventually feed is
  specific. `corpus.ts:80` reads `join(directory, 'expectations.json')`;
  `:82` globs `/^\d{2}-.*\.txt$/` non-recursively; `:87` throws
  `no expectations.json entry for: …`. Separately: "Author **at least 5
  fixtures per trap type** before splitting. Within each trap type, sort by name
  and hold out indices `i` where `i % 5` is 1 or 3 (exactly 40%)" cannot both
  hold its own parenthetical and C-EVAL rule 2 ("heldout/ (at least 40%)") for
  any count that is not a multiple of 5, and the card never says whether the
  ratio is per corpus or across both.
- **One concrete failure scenario:** an implementer copies the English shape and
  writes `e2e/fixtures/eval-es/expectations.json` at the corpus root — outside
  May edit, so HS-9 stops the card. Move it under `tuning/` to stay legal and
  key it the English way, by bare filename: eleven trap-type subdirectories
  under one split root will each naturally begin `01-…`, the keys collide, and
  `loadCorpus` either throws for most fixtures or silently matches a fixture to
  another trap's expectations. S3.2's V2 (`--corpus
  e2e/fixtures/eval-es/tuning`, RUN-CONFIG line 192) then fails in a way that
  looks like a scorer defect rather than a corpus defect. The count rule fails
  the same way: 6 fixtures per trap type satisfies "at least 5", the index rule
  yields 2/6 = 33% heldout, and "exactly 40%" and the contract's floor are both
  false — with no stated denominator, a corpus at 41% overall and 38% per corpus
  is unjudgeable by anyone.
- **One specific correction or named prerequisite:** add to "Fixed decisions":
  "Gold expectations: one `expectations.json` per split root —
  `e2e/fixtures/eval-es/tuning/`, `e2e/fixtures/eval-es/heldout/`,
  `e2e/fixtures/eval-owner-es/tuning/`, `e2e/fixtures/eval-owner-es/heldout/`
  — same `_schema` keys as the English sidecars, one entry per transcript,
  keyed by `<trap-type>/<name>.txt` relative to the split root" and "exactly 5
  fixtures per trap type per corpus; the heldout share is
  `heldout/(tuning+heldout)` computed separately for `eval-es` and
  `eval-owner-es`, each at least 40%". Name the loader consequence for S3.2 as
  a prerequisite: `loadCorpus` must recurse one level and key by relative path,
  which is inside S3.2's `server/src/eval/**` May edit.

### IR-04 — no criterion has a stated failure outcome, and V2 cannot fail

- **ID and location:** IR-04, `docs/v2/cards/S3.1.md` "Verification" (lines
  47-51); same table at `S3.1-ir.md:98-102`.
- **The text that conflicts, or exactly what is missing:** V1 expects "exit 0
  and prints the coverage table", where the checker's entire specification is
  the parenthetical "shape, NAMES, split ratio, trap coverage table"; V2 expects
  "exit 0". Neither row states what must make the command fail, and no other
  section of the card defines a negative case.
- **One concrete failure scenario:** a session writes a checker that asserts
  only that each trap directory is non-empty and prints a table. V1 exits 0.
  V2 also exits 0 whatever the corpus contains: the layout the card mandates
  produces `.txt` files, for which prettier has no parser, and the card's other
  two named files are `.md`, which `.prettierignore` line 8 excludes — a
  directory holding one English `.txt` and one English `.md` reports "All
  matched files use Prettier code style!" and exit 0 (measured on a copy under
  a scratch directory; the repository was not touched). A corpus with no gold
  expectations, a 33% heldout share, or a personal name missing from NAMES.md
  therefore ships green, and V1's "prints the coverage table" is satisfied by a
  table of the implementer's own choosing.
- **One specific correction or named prerequisite:** state V1's assertions as
  a list — naming matches `<split>/<trap-type>/<name>.txt`; every name in the
  corpus appears in NAMES.md and no other personal name appears; the per-corpus
  heldout share is at least 40%; every transcript has a gold expectation; every
  trap type has the required count; the coverage table is printed — and add one
  negative row, e.g. "V1 must exit non-zero with a named message when a
  transcript's name is absent from NAMES.md or a corpus's heldout share falls
  below 40%; demonstrate it on a copy of the corpus outside the shipped tree, not
  by editing the shipped corpus". Note for the coordinator: AM-014 makes a
  vacuous *markdown* prettier row non-binding, and this is not a markdown row,
  but V2 as written is a directory check whose only permitted content is
  unformattable `.txt` plus ignored `.md`; it becomes a real check as soon as the
  JSON sidecars from IR-03 land inside the split directories, so the two
  corrections belong together.
