## Defects

### D1 — IR-04: three of the five clicks V3/V4 require cannot be placed, because the rectangles they name are P3.4's rule and P3.4's rule does not publish them

- **Location:** `docs/v2/cards/P3.5.md` — Fixed decisions, "The one test-only
  hook", the tagging sentence added by AM-134 ("Of the fact set below, **the
  rectangles** and the reporting cadence are P3.4's and are inherited
  unchanged") against the very next bullet ("the **screen rectangle** of named
  elements … `[data-testid='home-action-note']`, `[data-testid='home-search']`,
  the first `li[role='option']` … `[data-testid='record-start']`,
  `[data-testid='record-stop']`"), read with Verification **V3** ("then **five
  real pointer clicks**, each at a rectangle the hook published for a
  `data-testid` that already existed") and **V4** ("Both cases drive the same
  **five** real clicks as V3"), and with the sibling card
  `docs/v2/cards/P3.4.md` — "What it publishes", "**Separately, the click
  rectangles**: the client rectangle of every element whose trimmed `innerText`
  is 1–64 characters and **which has no element children** — a text leaf …
  published in batches of 40 with a batch index".

- **Text that conflicts / what is missing:** AM-134 transferred the rectangles
  to P3.4 "inherited unchanged", but P3.4's rectangle rule is keyed by **visible
  text leaf**, not by `data-testid`, and it cannot publish three of the five
  selectors P3.5's rows are written against. Checked against the DOM at HEAD:
  - `[data-testid='home-search']` is an `<input>` (`HomeLauncher.tsx:158-176`).
    An input has no `innerText` and no children, so **no** rectangle for it
    exists under P3.4's rule — there is nothing in the page that is a text leaf
    inside it either.
  - `[data-testid='home-action-note']` is a `<button>` whose children are
    `<span class="home-action-icon">` and `<span class="home-action-label">`
    (`HomeLauncher.tsx:135-138`), so the button itself **has element children**
    and is excluded by the rule. The label span is a text leaf, so a rectangle
    exists — but it is published under the label's text, and P3.5's row asks for
    it under the test id `home-action-note`.
  - `[data-testid='record-start']` is a `<button>` containing `<MicIcon />` and
    `<div class="capture-source-copy">` (`Capture.tsx:425-437`), excluded by the
    same clause in the same way.
  - Only `record-stop` (a text-only button, `Capture.tsx:360`) and the first
    `li[role='option']` (`HomeLauncher.tsx:177-198`, whose only child is the
    patient name) are text leaves and are published as P3.5 names them.

  So the card simultaneously (a) requires five test-id-keyed rectangles, (b)
  tells the implementer the rectangles are P3.4's and inherited, and (c) grants
  permission to add only "its own facts (the capture state, the `record-timer`
  text, the `--level` value and `levelPeak`)" and its marker path. Rectangles for
  three selectors are in none of those three.

- **One concrete failure scenario:** P3.4 lands; its hook publishes only
  text-leaf rectangles. The P3.5 implementer, correctly barred from writing a
  second hook and from changing "**none** of P3.4's parts", builds the harness to
  read a rectangle keyed `home-action-note` from the marker, and there is none —
  and for `home-search` there is no rectangle anywhere, input or leaf. Click 1
  therefore has no coordinate, the harness times out, and V3's "the phase marker
  moves `idle → starting → recording` … a missed click times out and fails, it
  cannot pass quietly" turns into a `FAIL`. The implementer's only two moves are
  both out of bounds: stop and report — which the card names as the response for a
  **missing hook**, not for a rectangle that P3.4's hook legitimately does not
  publish, so the card does not tell them that is the response — or add a
  `data-testid`-keyed rectangle set inside P3.4's block, which is a **third** kind
  of edit to `web/src/main.tsx` and therefore an HS-9 breach of an edit AM-134
  did not authorise. The same happens for click 2 (`home-search`), and V4's two
  cases fail identically because they drive the same five clicks.

- **One specific correction:** widen P3.5's own facts by exactly the rectangles
  its own rows need and no others. In the May-edit bullet, change "**add its own
  facts** (the capture state, the `record-timer` text, the `--level` value and
  `levelPeak`)" to "**add its own facts** (the capture state, the
  `record-timer` text, the `--level` value and `levelPeak`, **and the client
  rectangles of the three selectors P3.4's text-leaf rule cannot publish —
  `[data-testid='home-action-note']`, `[data-testid='home-search']`,
  `[data-testid='record-start']` — published keyed by `data-testid` beside those
  facts and leaving P3.4's text-leaf rectangle publication untouched**)", and in
  the tagging sentence change "the rectangles … are P3.4's and are inherited
  unchanged" to "**P3.4's text-leaf rectangles and the reporting cadence** are
  P3.4's and are inherited unchanged; **the three keyed rectangles above are this
  card's own**". The equivalent alternative, if the coordinator prefers the fact to
  live in P3.4 instead, is one amendment to P3.4's rectangle rule adding
  "elements carrying a `data-testid`" to what it publishes — but that is P3.4's
  card to amend, it is in flight, and the P3.5-side fix above is the smaller and
  self-contained one. Either way the two cards must end up saying the same thing;
  this is the only place where, after AM-134, they do not.

## Notes (checked, not defects)

- **The `/p3.5-marker` path lacks the `/api` prefix P3.4 chose, deliberately.**
  P3.4 writes "the `/api` prefix means the server answers its 404 JSON
  (`app.ts:157-161`) and serves no HTML"; P3.5 fetches a bare
  `fetch('/p3.5-marker?...')`. Checked at `server/src/app.ts:157-165`: a GET that
  does not start with `/api` and a built SPA falls back to the SPA shell, so the
  marker request is answered with the index document instead of 404 JSON. **This
  does not weaken anything the card asserts**, because Fastify's request logger
  writes the URL to the bundled server's stdout either way, which is the only
  thing the harness reads; and `connect-src 'self'` permits it. P3.4 itself names
  `/p3.5-marker` as P3.5's marker path, so the difference is sanctioned, not
  accidental. Recorded because the two paths differ in shape and only one of them
  carries the stated reason.
- **P3.4's own sentence "the remedy is never a second hook, never a second
  marker path"** (`cards/P3.4.md:242-243`) sits eight lines below the same
  card's grant of "its own marker path `/p3.5-marker` **inside this block**". In
  context the sentence is about the remedy to a dead channel in a `NOT RUN`, so I
  read it as reconcilable and do not charge it; but it is the one phrase in P3.4's
  text an implementer could quote back, and the coordinator may want it qualified
  ("never a *third* marker path"). P3.4 is not this card and is in flight.
- **Gate attribution is inverted between the siblings** — P3.4 calls it "P3.5's
  gate, unchanged" while P3.5 calls it "P3.4's gate, inherited unchanged". The
  gate's *form* is character-identical in both and only one gate is ever written,
  so nothing behavioural turns on it; recorded because an implementer reading
  P3.4 first meets the phrase "P3.5's gate".
- **P3.5's V2 greps only `p3.5-marker`** for the "exactly 0 in `web/dist`"
  assertion, so a leftover flagged `p3.4-observe` from a P3.4 attempt would not
  be caught by P3.5's own negative count. P3.4's V0 asserts its marker *and* the
  gate string in the same place, so the invariant is not unowned; I am not
  charging it, and P3.5 widening its own grep to "either marker path" would be a
  reasonable one-line improvement if the coordinator wants it.
- **Where P3.5's facts ride** is mildly ambiguous — `levelPeak` is described as
  "published next to the rectangles", while the marker path is said to carry
  "phase, timer, level and `levelPeak` only". Both channels end up in the same
  accumulated stderr buffer, so any of the two readings is testable and nothing
  has to be guessed.
- **`web/src/main.tsx` is a Read source and a May-edit path at once**, which is
  correct now that the hook is inherited (P3.5 reads it to find P3.4's block
  before editing it) and was the shape that made the old contradiction easy to
  miss.
