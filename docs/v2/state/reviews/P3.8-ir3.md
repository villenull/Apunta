### D11's honesty

**Is the Objective now true, not merely less absolute?** Yes. It reads "every line **a run can
produce** after the `ready` has settled is logged and ignored: a `ChildGone`, a `fatal`, an `Other`,
a `Rejection` — with the `ready` line itself still exactly one." The qualifier is load-bearing and it
is the qualifier that makes the sentence true: of the four named types, a run can produce only a
`ChildGone` (`Other` and `Rejection` only log, and `fatal` is written at startup only —
`server/src/index.ts`), and the `ChildGone` case is the one the change fixes. Nothing in the sentence
is now claimed about an event that cannot occur. I checked the residual tension directly: clause (c)
requires that a post-settled line which would still paint is **Stop condition 3**, so if a
post-`ready` `fatal` ever became reachable the objective would not be met by the change — but that
is a stop, not a silent pass, which is the same disposition the card gives the `fatal` case it has
always carried. The clause that worried round 2, the *absolute* "anything … paints nothing", is gone.

**Is the division of labour right?** Yes, and it is the only division AM-140 permits. Handling a
second `ready` means a `settled` test inside the `ready` arm, which is a third part of the change,
which Stop condition 3 forbids and which May edit's "no third part is authorised" forbids in advance.
So (c-ii) does the only three things available: it names the arm as the one other line that can
paint, it records that no guard is authorised and why, and it makes the event **Stop condition 1 —
reported, not repaired**, with "do not 'make it idempotent'" carried over verbatim from Stop
condition 1 so the two texts cannot drift. Reporting is also what Stop condition 1 already demanded
for "treating a later `Ready` as a fresh launch", so (c-ii) closes an enumeration gap rather than
inventing a policy. Round 2's fatal pattern — required to be harmless, forbidden to be fixed, and a
stop — is gone: a second `ready` is now *only* a stop, with a named observer.

**Would an implementer know what to do on seeing a second `ready`, and would the rows catch it?**
Yes, and the two halves are independent. The instruction is unambiguous (stop, report, do not touch
the arm). The observer is V4's `test "$(grep -c 'apunta: the server is ready' $E1)" -eq 1 ||
F="$F c-ready-line-count"`, which is inside the command and reaches the exit code; a second `ready`
line sets `$F` and the row ends `FAIL:… exit 1`. It is not the only witness either: the second
`show_main` also fails to build, so the window list gains or changes a window and `snap.after`
differs from `snap.before`, firing `b-window-set-or-geometry-changed` as well. V3 does not count
`ready` lines, and that is right — V3's job is the ordering, V4's is the count.

### V3 traced

V3's body now ends: `… test -s $D/ready.line || F="$F a-ready-line-missing"; test -s $D/marker.line
|| F="$F b-marker-line-missing"; R=$(cut -d: -f1 $D/ready.line); M=$(cut -d: -f1 $D/marker.line);
test -n "$R" && test -n "$M" && test "$R" -lt "$M" || F="$F c-marker-not-after-ready"; if [ -n
"$F" ]; then echo "NOT RUN:$F"; exit 3; fi; echo "V3 PASS"`, and `F=""` is initialised with the
other locals at the top. **It can fail**, on three distinct conditions, and each maps to a real
failure of the claim "the reader keeps forwarding the child's stdout after `ready`":

| `$F` | Fires when | Failure of the end-to-end claim it represents |
| --- | --- | --- |
| `a-ready-line-missing` | no `apunta: the server is ready` in the captured stderr | Fixed decision 4 — the boundary P3.4's harness reads is gone |
| `b-marker-line-missing` | no line contains the run-unique `p38marker` | **the defect itself is unfixed** — nothing after `ready` reached stderr |
| `c-marker-not-after-ready` | the marker's line number is not greater than the ready line's | forwarding started too late, or not at all |

**Do the captured outputs distinguish "marker absent" from "marker present but before `ready"`?** Yes,
and the distinction is structural, not incidental. `grep -n` writes `LINENO:content`, `head -1` takes
the first match, and `test -s` reads presence while `cut -d: -f1` reads the number, so the two
conditions are carried by different files and different commands: an absent marker leaves
`marker.line` empty (so `b` fires and `M` is empty, which also trips `c`), while a marker present at an
earlier line leaves `marker.line` non-empty with `M < R` (so `b` does not fire and `c` does). The
`test -n "$R" && test -n "$M" && …` chain in V3 — which round 2 noted V4 lacks — makes the empty case
a clean non-zero rather than a `test: integer expression expected` diagnostic.

**Can the row pass while the claim is false?** No, on the paths I can construct. The row's exit code
is the last statement's, and the last statement is `echo "V3 PASS"` reached only when `$F` is empty;
every earlier `exit` in the body is a `3`/`1` on a genuine failure. Two honest notes, neither a
defect: the `||` chain means a missing marker prints both `b-marker-line-missing` and
`c-marker-not-after-ready`, which is noisier than the labels suggest but not misleading; and the
`S=$(sed -n …)` pid extraction returns all matching lines, so if the pid line ever appeared twice `$S`
would be two pids and `kill -TERM "$S"` would fail — that is a `FAIL` (the `test -n` passes, but the
later `kill` errors and the run's stderr excerpt shows it), not a false pass.

## Ruling: V2's `git status --porcelain` residual

**Acceptable residual. Not a defect, and not something a fourth round has to fix.**

V2's command is `npm run lint && npm run typecheck && git diff --name-only c834159 && git status
--porcelain -- src-tauri web server shared`. The row's exit code therefore carries `lint` and
`typecheck` — which is most of what matters, since a hand-edited `web/` or `server/` file that breaks
a lint rule or a type fails the row — but not the *contents* of the two file lists: both `git`
predicates exit 0 whatever they print. So "both file lists name only `src-tauri/src/main.rs`" is an
assertion the implementer discharges by reading two printed lists, not by reading an exit code.

That is a real residual and I want it on the record, but it is not blocking, for four reasons I
checked rather than assumed:

1. **The card never claims otherwise.** V2's Expected cell is a conjunction ("exit 0, **and** both
   file lists name only …"), and the second conjunct is plainly a reading. Nothing in the card tells
   an implementer to trust the exit code for scope, and Stop condition 7 turns a second path into a
   reported stop with a named response. A criterion the card asks you to *read* is not the D3/D12
   failure mode, which was a criterion the card claimed the command *executed*.
2. **Three independent textual guards cover the same ground**: May edit's "no third part and no
   other file", HS-9's "never edit files outside your card's May edit list", Stop conditions 2 and 7,
   and S2's anchor which uses the same pair for the same reason. A second edited path trips four
   instructions, not one.
3. **The realistic violation is caught by the exit code anyway.** The pathspec is
   `src-tauri web server shared` — exactly the trees whose linters and typechecker run first in the
   same `&&` chain.
4. **The repair author's stated reason for leaving it is inaccurate, and I record that as a
   non-defect note rather than a finding**: altering it would *not* reopen D9. D9 was about
   `git diff -- <pathspec>` naming a path whether or not it changed; that predicate is still absent
   and the fix — piping each list through a `grep`/`wc -l` pair that counts exactly one line and
   matches `src-tauri/src/main.rs` — leaves `--name-only <base>` and `--porcelain` both intact as
   the complementary committed/uncommitted pair. So a tightening is available if anyone wants one; it
   is a nicety, not a gap, and it should not cost this card a fourth round.
