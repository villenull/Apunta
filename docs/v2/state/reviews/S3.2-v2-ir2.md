## Part 2 — New findings, with failure scenarios

### N-1 — DEFECT (blocking for V3): the `lexicon` key has no host and no insertion point

**ID and location.** Proposal `:452-457` (FD2b), `:465-469` (invented negation),
`:470-476` (lost negation), `:696` (FD6 key table), `:199-206` and `:208-216`
(Choice 2A).

**The text that conflicts, or what is missing.** FD2b says a sidecar "may carry
`lexicon: "negation"`" and that "the loader expands the named lexicon into one
escaped, whole-phrase pattern per term or multi-word cue at load time"; it then
says the expansion "supplies the negator vocabulary **inside**" patterns the
sidecar authors (`"niega(?:ndo)?"`, `"no refiere"`, `"jam[aá]s"`), and that the
lost-negation class "carries `lexicon: "negation"` on its `mustCapture` fact".
The FD6 key table declares `lexicon` a top-level optional sidecar key and then
says it "hangs on … the invented-negation control's `mustNotContain`, the
lost-negation control's `mustCapture`". Two different hosts, and neither is
representable in the shapes the proposal says are unchanged: `mustNotContain` is
`readonly string[]` (`corpus.ts:51`) and `CaptureFact` is `{ id, any, tags? }`
(`corpus.ts:29-33`). Both are compiled verbatim — `compile(source)` is
`new RegExp(source, anchored ? 'im' : 'i')` (`patterns.ts:66-69`), called on each
`mustNotContain` string at `score.ts:303-310` and on each `mustCapture.any` string
at `score.ts:342-344`. No marker, no anchor syntax, no per-entry field and no
substitution rule is named anywhere in the document.

**One concrete failure scenario.** Two implementers, two instruments, one exit
code. (a) The implementer reads "the loader expands the named lexicon" as a
sidecar-level key whose alternation is concatenated into every pattern of the
named list. That is a negation check inside the scorer by another name — which
2A's own bullet forbids ("`score.ts` … never knows a 'negation check' exists",
`:203-204`) — and V3 then removes vocabulary from a pattern the sidecar authored
directly, so the invented-negation control may un-flag for a reason unrelated to
the mechanism FD8 names. (b) The implementer adds an optional per-entry field
plus a substitution token (say `{{negation}}`) inside the authored regex, which is
the only shape that makes V3 exactly as `:867-870` describes — and that changes
`FixtureExpectations`/`CaptureFact`, the `compile()` call sites and the
`assertFixture` compile checks (`corpus.ts:141-168`), none of which C3's
new-surface paragraph (`:368-374`) lists. Under (b) V3's expected cell is right;
under (a) it is a different test wearing V3's name.

**One specific correction.** One sentence in FD2b plus one row in C3's
new-surface list: the key is a **per-entry** field; a `mustNotContain` string or a
`mustCapture.any` string that contains the token `{{negation}}` has the named
lexicon's escaped whole-token alternation substituted for that token at load
time, before `compile()`; an entry with no token is compiled unchanged; the
substitution happens in the loader, never in `score.ts`; and the type changes are
(a) an optional `lexicon` field on the new control type and on `CaptureFact`, and
(b) no change to `mustNotContain`'s type.

### N-3 — DEFECT (minor): the whole-token boundary is unspecified, and the loader's existing one fails on accented endings

**ID and location.** Proposal `:481-486` and `:511-513` ("one escaped whole-token
or whole-phrase pattern per term", "matched as whole tokens … never … as a
substring"), `:1086-1088`, and the attestation row `dejó | 10` at `:1130`.

**The text that conflicts.** The only whole-token construction in the repository
is `lexicon.ts:39`, `` new RegExp(`\\b${escapeRegExp(stem(term))}\\b`, 'i') ``.
JavaScript's `\b` is defined over `[A-Za-z0-9_]`, so a term whose **last**
character is non-ASCII can never match. The proposal reuses that file format and
that loader and never states a boundary rule.

**One concrete failure scenario.** The implementer reuses `loadLexicon` (the
natural reading: same `term<TAB>category` format, same module, C3 lists only a
category-filter and load-error change) and writes `mié<TAB>number`, the `mié`
alternative of the glossary's `miércoles / mié`. FD2's test — "every one of the
152 entries is present in `es-MX.txt` as at least one alternative" — passes,
because the test is a file-presence test, and the header's `152 = 87 + 65
verified` reads as a live vocabulary. A note saying "mié" can never be flagged,
and no test fails. Measured on the 66 tuning transcripts with an isolated copy of
the loader's construction: `\bdejó\b` matches **0** files while a Unicode-aware
whole-token match matches **10** — so the proposal's own `dejó 10` row is right
about the corpus and only reachable under a boundary the card does not specify.
Of the 217 atomic alternatives of the 152 entries, exactly one (`mié`) ends in a
non-ASCII character; none of the nine owner-approved negation terms does.

**One specific correction.** One clause in FD2b/FD2c: "whole-token boundaries are
Unicode-aware — `(?<![\p{L}\p{N}_])…(?![\p{L}\p{N}_])` — not `\b`, which is
defined over `[A-Za-z0-9_]` and cannot match a term ending in an accented
character"; plus one assertion in V1 that every admitted alternative matches a
synthetic sentence containing it, so "admitted" means matchable and not merely
present.
