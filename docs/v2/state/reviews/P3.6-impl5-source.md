## D2 re-verified against current source — mechanism as specified, but the identity check falsely fails on a healthy run

**What is right, re-derived from source:**

- **Falsifiability.** `ownershipIdentityDiff` fails on `replaced` (an asserted file — lock or database — present at both ends with a different dev+inode), on `appearedOwned`, and on `lost`. A second owner that takes the folder over by C-OWN@1 rule 3 renames a fresh lock over the old one (`data-lock.ts:364-387`) — a new inode — so `replaced` catches what the name set cannot. Helper-tested against real files (`helper-tests.mjs:1029-1045`).
- **The pid comparison is sound.** The lock's `pid` is the server's `process.pid` (`data-lock.ts:344`); the shell spawns the server directly — `Command::new(&config.node_bin)`, no shell in between (`src-tauri/src/main.rs:399`) — and prints that same child (`main.rs:222`, `apunta: spawned the bundled server as pid <N>`), which `serverPidFromStderr` parses (`harness:745-749`). The lock is written **once** at acquisition (`createLockFile`, `data-lock.ts:283-294`) and never rewritten while held; the nonce changes only on a rule-3 takeover. So on a healthy run the holder is stable, and `lockHolderCheck` at the baseline and at the end of the flows (both read **before** the stop, while the server holds it) passes.
- **`size` is not asserted.** The snapshot records it, but `ownershipIdentityDiff` compares only `dev`/`ino` (`harness:1768`) — the database growing as the flows write cannot fail the check.
- **Nothing replaces `apunta.db` during the flows.** The backup flow clicks "backup now" and checks the manifest moved; the server's backup is `VACUUM INTO` (`server/src/backup/snapshot.ts`), which writes a new file under `backups/` and never touches the source's inode. `POST /api/backup/restore` only **stages** a restore, applied at the next start (`server/src/routes/backup.ts:99-116`), and no flow stages one. There is no bare `VACUUM` anywhere in `server/src` (only `VACUUM INTO` and comments forbidding it). Migrations run at startup (`server/src/index.ts:49-54`), before `waitForOwnership` returns and therefore before the baseline.
- **The baseline timing is sound.** `waitForOwnership` (`harness:2194`) polls the server, which takes the lock, applies any pending restore, migrates and opens the db **before** listening (`server/src/index.ts:40-59`); the db is in WAL mode (`server/src/db/index.ts:48`) with the connection held open, so all four C-OWN@1 files exist when the baseline is taken (`harness:2202-2216`), and `ownershipBaselineProof` asserts exactly that.

**The defect — the `lost` path has no volatile exemption, so the check fails on every healthy run.** `VOLATILE_OWNED` (`harness:1693`) marks the WAL pair so that a *changed* inode is only recorded (`volatileChanged`, `harness:1764-1766`). But the disappearance path does not consult it:

```
harness:1759-1762  if (!now.present) {
                   if (before.name === 'apunta.lock') released.push(before.name);
                   else lost.push(before.name);
                   continue;
                 }
```

On a healthy run the stop is SIGTERM-first (`stopPid`, `harness:372-390`), and the server answers SIGTERM with `app.close()` (`server/src/index.ts:147-149`), whose `onClose` hook runs `db.close()` and `lock.release()` (`server/src/index.ts:99-106`). `db.close()` as the last WAL connection makes SQLite checkpoint and **delete `apunta.db-wal` and `apunta.db-shm`**; `lock.release()` unlinks `apunta.lock` (C-OWN@1 rule 5). The end snapshot therefore has the WAL pair absent, and they land in `lost` — `ok: false` — while the lock's release is correctly exempted. The doc comment at `harness:1743-1744` even says `lost` is for "an **asserted** file"; the implementation does not check `before.asserted` on this path. Proven mechanically against the harness's own exported helpers (`docs/v2/evidence/P3.6/attempt-5/source-review/01-healthy-shutdown-simulation.mjs`):

```
baseline present: apunta.lock=true apunta.db=true apunta.db-wal=true apunta.db-shm=true
after present:    apunta.lock=false apunta.db=true apunta.db-wal=false apunta.db-shm=false
identity diff ok: false
identity diff why: gone from the baseline: apunta.db-wal, apunta.db-shm; released on shutdown, as C-OWN@1 rule 5 says: apunta.lock
lost: ["apunta.db-wal","apunta.db-shm"]
```

So the check `smoke the C-OWN@1 files are still the ones this run created (device+inode)` (`harness:2329-2335`) fails on **every** healthy run — the same defect class as F6, in the repair meant to fix D2. The helper tests cover the WAL pair being *recreated* (`helper-tests.mjs:1047-1067`) but never *deleted without recreation*, which is the gap that let this through; the repair map's falsifiability table lists the lock's clean release as a pass case and is silent on the WAL pair's.

The fix is one branch, inside the harness file: on the disappearance path, exempt volatile files the same way the lock is exempted (a volatile file disappearing at shutdown is the same legitimate event as the lock's release — e.g. push them to `released`, or check `!before.asserted` before `lost`). The doc comment already states the intended semantics; the code must match it.

## Observations (not defects, no acceptance change)

- **The helper tests' WAL-deletion fixture is the gap that matters.** Every D2 test that deletes a volatile file recreates it first; the clean-shutdown case (deleted, never recreated) is untested, which is exactly how the `lost` path shipped. One synthetic fixture — delete the WAL pair without recreating, assert `ok: true` — would have caught it, and should accompany the fix.
- **The repair map's "recorded, never asserted on" is half-true.** A *changed* WAL inode is not failed on; a *deleted* WAL file is. The doc comment in the harness already states the intended semantics ("`lost`: an **asserted** file"); the code is one branch away from its own comment.
- **The `vanished` check's name undersells its mechanism**, as attempt 3's F7 noted for its sibling: "not emptied" is implemented as "nothing disappeared", which includes the lock's designed release. Pre-existing; flagged for the coordinator, not fixed here.
- **D1's proof style is the right general answer to the `renders()` blind spot** the attempt-4 review named: a label's proof is its render condition, not the line that writes it. Worth keeping for future labels.
- **OCR matching counts any visible word `Settings`** (`findPhraseBoxes` slides a one-word window, case-insensitive), so a longer visible phrase containing the word would count as a duplicate. None exists at that moment against current source; the residual risks are runtime (below).
