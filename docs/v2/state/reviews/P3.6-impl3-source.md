## Defects (confirmed by code and route/component semantics)

### F1 — HIGH — `Add patient` is not pane-only: the onboarding flow can never pass

`flowOnboarding` confirms the post-Continue screen with `confirmPane(window, 'onboarding', 'Add patient')` (:2108). Continue (standard) navigates to `/patients/new` (`OnboardingFormat.tsx:76`, `returnTo` default `:30`; route `App.tsx:117`). The AddPatient screen renders the dialog with an h2 `Add patient` (`AddPatient.tsx:92`) **and** a submit button `Add patient` (`AddPatient.tsx:152`). Both are visible. `groundPhrase` (:928-941) refuses a label that appears more than once, so the confirmation fails and onboarding records NOT RUN on every healthy run. Exact mechanism: quote a label that appears exactly once on the AddPatient screen (or assert the screen by a different fact).

### F2 — HIGH — `Ask a question or give feedback` is mis-quoted: draft and refine can never pass

The refine input placeholder is `Ask a question or give feedback...` — three ASCII periods (`shared/src/i18n/en.ts:1046`, rendered at `RefineColumn.tsx:284`). The harness quotes `Ask a question or give feedback` with no dots and `findPhraseBoxes` strips only **one** trailing `[.,]` (:910). OCR reads the placeholder as one token `feedback...`; after the strip it is `feedback..`, which never equals `feedback`. Both `flowDraft` (:2281) and `flowRefine` (:2321) confirm the pane with this phrase, so both record NOT RUN on every healthy run. Exact mechanism: quote the full placeholder (`Ask a question or give feedback...`) or strip every trailing dot.

### F3 — HIGH — `Listening for words` is mis-quoted: capture can never pass

`capture.listening` is `Listening for words…` — U+2026 (`shared/src/i18n/en.ts:998`, `…` = `M-bM-^@M-&` in UTF-8; rendered at `LiveRecording.tsx:74`). The harness quotes `Listening for words` with no ellipsis and the strip regex (:910) handles only `[.,]`, not U+2026. If OCR reads the ellipsis (as `…` or `...`), the last word never equals `words`, so `confirmPane(window, 'capture', 'Listening for words')` (:2190) fails and capture records NOT RUN. Exact mechanism: quote the full string `Listening for words…` (and make the strip handle U+2026).

### F4 — HIGH — `Start a plan` is not on screen: the plan flow can never pass

`flowPlan` clicks `Start a plan` (:2461). That label is the plan pane's empty-state control (`PlanView.tsx:348`), visible only when the plan pane is open. The view defaults to `notes` (`Workspace.tsx:84-85`); after `flowPatientList` clicks the patient's row the app is on `PatientWelcome` (the row click navigates to `/?patient=id`, dropping the note param — `Workspace.tsx:222-227`). Nothing in the flow sequence opens the plan pane, so `Start a plan` is not on screen and the flow records NOT RUN. The harness comment "clicking it opens the pane" is wrong: `Start a plan` is inside the pane. Exact mechanism: open the pane first (the `Treatment plan` switch/card is unique before the pane opens), then click `Start a plan`.

### F5 — HIGH — `Prepare for session` and `Brainstorm` each appear twice: briefing and brainstorm can never pass

After `flowPatientList` the app shows the has-notes `PatientWelcome`, whose cards are labelled `Brainstorm` (`PatientWelcome.tsx:66`) and `Prepare for session` (:78). The notes column is visible at the same time (`Workspace.tsx:625`, shown when `!atHome && !atDirectory && !firstNoteOnly`; `firstNoteOnly` is false because the patient has a draft note), and its switches are labelled `Brainstorm` (`NotesColumn.tsx:100`) and `Prepare for session` (:122). `App.test.tsx:185-201` confirms the welcome and the notes column coexist. Each label therefore appears twice, `groundPhrase` refuses, and `flowBriefing` (:2505) and `flowBrainstorm` (:2542) record NOT RUN on every healthy run. Exact mechanism: ground these controls at a moment when only one instance is on screen (e.g. before the welcome cards render, or on the note view where the welcome is absent).

### F6 — HIGH — `Appearance` appears twice on the settings modal: the settings flow can never pass

The settings modal renders the tab label `Appearance` (`Settings.tsx:85` via `settings-nav-label` :181) **and** the open section's heading `Appearance` (`h2.settings-title` :455). `flowSettings` confirms the pane with `waitForScreenLabel(window, 'Appearance')` (:2614); two matches refuse, so the flow records NOT RUN on every healthy run. Exact mechanism: assert the settings pane by a label that appears once (the nav title `Settings` is unique once the menu is closed, or a row inside the Appearance section).

### F7 — HIGH — the ownership containment check fails on the backup's own `backups/` directory

The backup flow writes into `APUNTA_DATA_DIR/backups/` (default backup dir = `join(dataDir, 'backups')`, `server/src/backup/store.ts:37-39`; the sandbox configures no other destination). The containment check (:1993-1999) counts **any** name that appears beside the baseline as a failure (`extra.length === 0`). The helper test itself demonstrates the mechanism (:320-323: a `backups/` directory appearing beside the baseline is caught as `extra`). So after `flowBackup` writes a backup, the check `smoke no second lock, database, -wal or -shm` FAILS on a healthy run. The check's name (the four C-OWN@1 files) does not match its mechanism (any new name). Exact mechanism: compare against the four C-OWN@1 names (a second `apunta.lock`/`apunta.db`/`-wal`/`-shm`), not against every name in the folder.
