## 2. One-point calibration: is it safe enough at a differently-scaled target?

**Yes, under one stated assumption, and it is the better trade.** The page→native map is affine with a **uniform** scale (CSS px → device px is constant across one webview at fixed DPR/zoom). Given uniformity, a single witness fixes the translation completely; `k` need not be solved because the witness *asserts* `k = 1` instead of measuring it. `screenX/screenY` are CSS pixels, so `asked_native == screenX ± 1` holds only when `k = 1` — a DPI or page-zoom mismatch makes the equality fail and the state ends in a **named `NOT RUN` with no click**, which is the correct fail-closed outcome, not a wrong click.

**Two conditions LongCat's text does not state, without which one point is genuinely weaker than two:**

1. **The witness is required twice.** Once at the probe, and once at the click — the native `getmouselocation` read-back ≤ 1 px *and* `|clickCX − T.x| ≤ 2, |clickCY − T.y| ≤ 2`. This closes the residual one-point gap: a scale or origin change between probe and click cannot produce a *counted* landing, because the client-space check fails even if the native read-back succeeds.
2. **Containment after every warp, not before only.** `getmouselocation`'s `WINDOW` field, or `getwindowpid <WINDOW>` equal to the same positive pid `windowInfo` read. This is what makes asking a synthetic screen point safe at all — without it a misdirected probe could sit on the splash, the root window, or an unrelated window.

**Honest cost, stated not hidden:** under `DPR ≠ 1` or page zoom, one-point yields `NOT RUN` where two-point would have *solved* `k` and clicked. Under `xvfb-run` with `1280×860` and DPR 1 this is the unlikely branch, and it is a named, safe, no-click outcome. The calibration is **one probe move, guarded by the first target's deadline, never reset**; its `offset = asked − client` is reused by the second target (it is a property of the window), and reuse is caught by that target's own client-space check.

**No body-click probing** — calibration is a `mousemove` plus a witness, never a press.

## 3. Frame identity — minimum robust alternative (corrects both prior positions)

**Withdrawn:** content signature as `frame`. It is unsound (A→B→A gives a later publication the earlier's signature, so "same signature" ≠ "same publication") and it is oversized (a full JSON rect signature in **every** batch query is precisely what the 40-per-batch batching exists to avoid; it would approach Node's 16 KB header limit on its own).

**Adopted — four parts, each load-bearing:**

1. **Epoch, not content.** `sendRects` increments one counter **once per call** and publishes the same small integer in every batch of that publication. Bounded by construction: inside a 30 s target deadline at ≥250 ms change-only polling, the epoch cannot exceed a few hundred. A content hash is neither needed nor wanted.
2. **Wholesale replace on every sighting.** A sighting of batch `b` **replaces** that batch's entry outright — `{ batch, total, frame, rects }` rebuilt from **only that line's keys** — and never merges into the previous entry. Field-wise merging is what lets a shrinking, reordered or partial batch carry stale rectangles forward, and it is the defect in both the proposal's snippet and my §3.1.
3. **Completeness over actual indices and counts, not metadata.** For candidate epoch `F` and `total N` with `m = ceil(N/40)`: every `b ∈ 0…m−1` present with `frame === F` and `total === N`; **and** the union of global indices across those batches is exactly `{0…N−1}`, each carrying the full field set `x,y,w,h,l,t,d`, with no gap, no duplicate and no index `≥ N`. Metadata agreement alone accepts a truncated batch that merely claims the right epoch.
4. **Newest-epoch selection.** Among complete frames, select the one with the **highest epoch present in the buffer at read time**; a complete older epoch is refused, not used as a fallback. This makes the loop terminate and is decidable from the buffer alone.

**Claimed, and only this:** *a mixture of two publications is not selectable, and the selected frame is the newest publication fully present in the buffer at read time.* **Not claimed:** that this is the page's *current* state — the hook publishes on change and never retracts, so no retraction protocol exists and none is sought. Epoch identity defeats A→B→A; it does not create freshness.
