## D1's guard: scoping, location, and the search for a third place

**Is it correctly scoped and unambiguous?** Yes. May edit part (ii) says the "`show_error` /
`close_window` / `break` block at `:329-335` must not run once `settled` is already true", and Fixed
decision 1(ii) says "log it, and **do not** `show_error`, do **not** `close_window`, and either
`continue` or leave the loop without painting". Read against the source that names exactly two
edit sites: keep `:330-331` (the `code` and the `eprintln!`), wrap `:332-335` in `if !settled`, and
pick either branch. An implementer cannot reasonably land anywhere else. The card also protects the
other side of the same flag: S2 says leave `settled = true` (it is now also part (ii)'s input), and
Stop condition 3 forbids "a second or recomputed `settled` flag" and "a moved assignment".

**Where does the `settled` test go?** `:332-335`. The card does not print the resulting code, but it
names the line range and the four statements, and Fixed decision 1 states the two acceptable shapes.
That is sufficient; I do not charge it as a gap.

**Does the guard weaken C-BRIDGE@1 rule 7 or rule 1?** No, and the card *proves* both rather than
asserting them.

- Rule 7 (early exit before `ready` must still paint). The guard is `if !settled`, and pre-`ready`
  `settled` is `false`, so the arm is byte-for-byte the arm of today. S2 states this ("leave
  `ChildGone`'s early-exit behaviour — before `ready` it must still paint exactly as it does
  today"), and V4(d) **runs** it: a second launch, server pid signalled before `ready`, then an
  assertion that a window titled `exited_before_ready` / `exited_75_without_a_bridge_line` /
  `terminated_before_ready` appears, or `F="d-no-early-exit-error-window"` and `exit 1`. That is a
  runtime assertion from outside the process, not a promise.
- Rule 1 (the single navigation at `ready` and nowhere else). Part (i) removes a `break`, it does
  not move or duplicate the navigation; part (ii) adds no call. V4(a) requires exactly one
  `apunta: the main window is open on` line and exactly one `ready` line, V4(b) requires the window
  set and geometry to be byte-identical across the marker request, and V1 re-runs the thirteen tests
  that carry the nonce/protocol checks and the `on_navigation`/`on_new_window` guards at
  `main.rs:486-487`. The card's assertion that "the single navigation stays single" has three
  independent outside witnesses.

## Is the negative control now real?

**Yes, and (a) is now genuinely asserted rather than inferred.** V4's body contains

```
test "$(grep -c "apunta: the main window is open on" $E1)" -eq 1 || F="$F a-main-window-opened-not-exactly-once"
test "$(grep -c "apunta: the server is ready" $E1)" -eq 1 || F="$F c-ready-line-count"
```

so a second `show_main` is caught by a predicate that reaches the exit code, not by a reading of
the diff. The card states the circularity in the open — "**This assertion is not independent of the
change it judges:** it reads a stream the change itself influences … so it is reported alongside —
never instead of — (b), (c), (e) and (f), which are read from the window list and the painted
windows and can fail on their own" — and (b), (c), (e), (f) are all four in the command cell.

**Is counting a stream the change itself writes honest?** Yes, and the disclosure is the right one:
the honest statement is "this is a real assertion over the shell's own log, it is weaker than a
window-list observation, and here are four assertions that are not". That is precisely what the card
now says. My objection is not to the method — it is to the technical sentence attached to it, which
is false (D10).

## Defects

### D10 — Fixed decision 3's justification is a false statement about the compiler (IR-03)

**Location.** Fixed decision 3, third sentence; repeated in V4's Expected cell: "The count is the
assertion because a second `show_main` **fails to compile** — the window label `main` is already
taken at `main.rs:469` — so a duplicate call can never be built, let alone run, and a check that read
the diff would never see one."

**Conflicting text.** `main.rs:468-471` reads `WebviewWindowBuilder::new(handle, "main", …)`. The
label is a runtime string; a second call to `show_main` **compiles**. What happens at runtime is
worse than the card says it cannot happen: the second `build()` returns `Err`, `show_main` takes its
`Err` branch (`main.rs:529`, `eprintln!("apunta: the main window could not be opened: {error}")`)
and returns `false`, and the `ready` arm then falls into `:302` and paints
`Apunta — the_window_would_not_open`. The card also points at `:469` for the label; the label is at
`:471`.

**Failure scenario.** An implementer reads Fixed decision 3, concludes that a duplicate `show_main`
is impossible by construction, and therefore concludes the `ready` arm needs no `settled` test —
which is exactly the arm that would paint an error window. The row would still catch it
(`c-ready-line-count` fires on the second `ready` line), but the implementer's *reasoning* is wrong
on the record, and the next reader of this card inherits it.

**Specific correction.** Replace the compile claim with the runtime fact, in both places: "a second
`show_main` cannot be *silent* — the duplicate label at `main.rs:471` makes `build()` return `Err`,
`show_main` logs `apunta: the main window could not be opened: …` and returns `false`, so the `ready`
arm falls into its `:302` failure path and paints `the_window_would_not_open`. That is why V4(a)
counts the success line rather than trusting compilation, and why V4's `c-ready-line-count` is the
predicate that catches the case."

### D11 — Fixed decision 6(c)'s enumeration omits the `Ready` arm, the one post-`ready` line that paints besides `fatal` (IR-03)

**Location.** Objective, second clause ("**and anything that arrives on that loop after the `ready`
has settled paints nothing**"), against Fixed decision 6(c), which says "the same holds for **any
other line arriving after a settled `ready`** — a `fatal`, an `Other`, a `Rejection`", and against
Fixed decision 6(c)'s own escalation clause ("if a line arriving after a settled `ready` would still
paint, the shell has lost the distinction and that is Stop condition 3").

**Conflicting text.** The enumeration names `fatal`, `Other` and `Rejection` and stops. It does not
name `Ready`. But with `:298` gone, a second `ready` line arriving on the loop reaches
`main.rs:291-305`, and because the `main` label is taken, `show_main` returns `false` and the arm
executes `show_error(&handle, "the_window_would_not_open")` at `:302`. So the Objective's absolute
"paints nothing" is false as written on the one arm the card itself edits in part (i), and the
enumeration that is supposed to be exhaustive is not.

**Failure scenario.** A reviewer of the finished change, or an implementer who notices a second
`ready` line, has three mutually exclusive instructions and no way to choose: the Objective says it
must paint nothing; clause (c) says a post-settled line that paints is Stop condition 3; Stop
condition 1 says "treating a later `Ready` as a fresh launch" is a stop and "do not 'make it
idempotent'". Worse, clause (c)'s requirement cannot be satisfied for this line **without** editing
the `ready` arm, which Fixed decision 1 does not authorise and Stop condition 3 forbids. So a
theoretical second `ready` — which C-BRIDGE@1 rule 1 says the server never prints, and which V4's
`c-ready-line-count` would catch — is simultaneously required to be harmless, forbidden to be fixed,
and a stop. An implementer can burn a whole attempt on that collision. (The card already took this
exact shape for `fatal`, where the resolution was "name it, declare it unreachable today, assert over
what a run can produce, do not manufacture it" — clause (c) does that for `fatal` and not for
`Ready`.)

**Specific correction.** Add a fourth case to Fixed decision 6(c), in the same register as the
`fatal` one: "**(c-ii) a `Ready` arriving after a settled `ready`** is the same case and the only one
besides `fatal` that can paint: the `main` label is taken at `main.rs:471`, so `show_main` returns
`false` and the arm would paint `the_window_would_not_open`. **C-BRIDGE@1 rule 1 says the server
prints exactly one `ready` line**, so no code path produces one, V4's `c-ready-line-count` asserts
exactly one, and the card does **not** authorise a guard on the `ready` arm — a second `ready` is
Stop condition 1 and is reported, not repaired." Then narrow the Objective's second clause from
"**anything** that arrives … paints nothing" to "any line a run can produce after the `ready` has
settled is logged and ignored — a `ChildGone`, a `fatal`, an `Other`, a `Rejection` — and the `ready`
line itself is still exactly one".

### D12 — V3's Command cell cannot fail: the row ends `; true`, so the end-to-end assertion lives only in prose again (IR-04)

**Location.** V3's Command cell, last four statements: `… kill -0 "$S" 2>/dev/null && kill -KILL "$S";
cat "$E"; grep -n "apunta: the server is ready" "$E"; grep -n "p38marker" "$E"; true` — and its
Expected cell, "exit 0", assertion (b) "a line naming the marker `p38marker` **appears after** it",
and "**If no line naming the marker appears at all, this row is `NOT RUN`** with that cause".

**Conflicting text.** `grep -n` writes to stdout and its exit status is discarded; the literal `true`
is last, so **the row exits 0 whether or not the marker reached stderr**, and whether or not the
marker came after `ready`. V3's Expected cell simultaneously claims an exit code, three ordering
assertions and a `NOT RUN` status, none of which the command distinguishes. This is the same failure
class round 1 charged as D3 — an assertion that exists only in a cell the implementer does not
execute — and D5's residue, in the one row the card calls "the row that proves the defect is fixed end
to end". V4 gets this right: it accumulates `F` and ends `if [ -n "$F" ]; then echo "FAIL:$F"; exit 1; fi`.
V3's mechanism works — a pino line has no `type` field, so `bridge::parse_line` returns
`Err(Unreadable)` (verified at `bridge.rs:62-68`) and the line lands on the `:321-325` forwarding arm.

**Failure scenario.** Attempt 1 forwards nothing — say the marker line is missing because
`logger: true` did not reach fd 1 — and V3 still exits 0. The implementer records "exit 0" in
`docs/v2/evidence/P3.8/V3-forwarding.md` per RUN-CONFIG §4, notices only if they read the excerpt,
and reports V3 green. V4 will not rescue them: its marker assertions run against `$E1` from **its
own** launch, and if the publisher is silent there too it fails at `c-ready-or-marker-line-missing`,
which the implementer is likely to read as "the change did not work" rather than "the publisher is
silent" — the exact misdiagnosis the card's Stop condition 2 and Fixed decision 7 are written to
prevent.

**Specific correction.** Give V3 the same `$F` accumulator V4 has and drop the trailing `true`: set
`F="$F b-marker-line-missing"` when `grep -n p38marker "$E"` is empty, set
`F="$F c-marker-not-after-ready"` when the marker's line number is not greater than the ready line's,
and end `if [ -n "$F" ]; then echo "NOT RUN:$F"; exit 3; fi; echo "V3 PASS"` so the card's own
"this row is `NOT RUN` with that cause" is an exit code rather than a reading. Keep the `cat`/`grep`
excerpts before the verdict so the evidence file still carries them.

## Non-defect notes

1. **Copying a row's command from the raw Markdown on disk yields `\|\|` and will not parse.** Every
   pipe in these table cells is backslash-escaped for GFM. Rendered, the rows read `||` and all five
   parse; extracted raw, `bash -n` fails on `\|\|`. This is a property of every card in the plan, not
   of P3.8, and no implementer reads the rendered file by hand-editing the escapes. Not charged.
2. **`main.rs:469` should be `:471`** for the `"main"` label (`:469` is the
   `WebviewWindowBuilder::new(` line). Cosmetic; AM-140 records the author already correcting one
   line number by hand, so it is the kind of thing that gets fixed in passing.
3. **A surviving AppImage launcher between V3 and V4 is an unpriced attempt-1 hazard.** Both rows
   signal the pid they captured (`$C`, `$C1`, `$C2` — the AppImage launcher) and never `pkill`
   (C-ISO@1 rule 7, correctly). If the launcher dies and the app does not, V4's second launch can
   hit `tauri-plugin-single-instance` (`main.rs:108`), hand off, spawn no server, and land on
   `NOT RUN: launch 2 never printed the main.rs:221 pid line` — a `NOT RUN`, so nothing false is
   reported, but an attempt is spent. Worth one sentence in the row telling the implementer to
   confirm no `Apunta` process remains before launch 2, and to record it if one does.
4. **The post-`ready` `ChildGone` log line reads `the server exited before it was ready
   (exited_before_ready)`**, which is misleading after `ready`. V4(f) greps exactly that literal
   (`f-child-gone-not-logged`), and Fixed decision 1(ii) requires the log to survive the guard, so
   the wording is load-bearing and correct as written. Changing the message would be a third part.
5. **`pino` writing the request URL including the query string to fd 1 is attempt-1's biggest
   unknown and the card handles it correctly.** I confirmed the two halves that are checkable by
   reading (`logger: true` at `app.ts:70`; `parse_line` → `Err(Unreadable)` → the `:321-325` arm),
   and could not confirm by reading that Fastify's default request serializer emits `req.url` with
   its query string intact. Fixed decision 7 and Stop condition 2 already say what to do if it does
   not: record `NOT RUN` naming it, report it to the coordinator, and **do not** add a log line, a
   route, an env var or a build flag. That is the right instruction and needs no change.
6. **Port 7860, Level `L3`, Depends `P3.3`, May edit, the 13-test expectation and the Objective are
   all unchanged** across the repair commit, and `check-plan.mjs --no-write` exits 0.

## Verdict

**DEFECT — 8 CLEAR / 2 DEFECT / 0 UNKNOWN.** D1–D9 are closed as claimed, with D2 closed in part;
the repair is real, specific and mostly careful, and the two blocking risks of round 1 are genuinely

changes scope, and none requires re-opening any of D1–D9** — with them fixed this card is fit, and
because P3.4 and P3.5 both gate on the same forwarding fix, a third round should be short.

I would not dispatch on "8 CLEAR" while V3 can exit 0 with the defect unfixed.
