**Correction:** §4 row 2 must drive the capture UI — harness sets up the virtual source/sink (P3.5's mechanism; the new harness file is in May edit and free to adopt it), clicks record-start/record-stop via xdotool, lets the app POST the WAV itself, and reads the fact from the API. Two defects (`04-coordinate-frame.txt`). **(a)** The §4 table says "Actuation (xdotool, in the app window)" for every flow but never says where the coordinates come from. With the hook provably absent (`main.tsx:401` gate is build-time; the producer sets no `VITE_*`), the harness has no machine-readable rectangles and no page pointer facts. The harness must not guess coordinates and assert green. **(b)** §3c's "With `GDK_SCALE=1` … window geometry is already in one frame, so the calibration is not needed" is wrong twice over: `GDK_SCALE=1` normalises **scale**, not the frame→client **translation** (the decoration offset exists whenever a WM is present — including the card's own fallback branch, which launches in the inherited desktop session that exports `GDK_SCALE=2`); and P3.4's own harness comment (`tauri-security.test.mjs:465-468`) says the AM-188 calibration "still solves the real per-axis scale from two measured points" even with `GDK_SCALE=1`. The brief's child-env table also omits `GDK_DPI_SCALE` (P3.5 sets it at `:682`). **Correction:** set both `GDK_SCALE=1` and `GDK_DPI_SCALE=1`; assert the no-decoration property in the `rectInsideWindow` shape on every click, never assume it; source coordinates from per-flow screenshot grounding recorded in evidence; copy AM-188's calibration in as a helper only — never an assertion, never a threshold — and only after the property is asserted.
