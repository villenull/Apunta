## F1 - the raw-`Location` branch: two defects, and the leak is currently masked by a crash

`scripts/v2/probe-redirects.mjs:249-251` writes the unparsed header verbatim, and
the implementation review's write-up (`docs/v2/evidence/P4.1/review-probe.md`)
is right that the line is the one place the file's stated property -
*"an observed query string is written `<redacted>`, never pasted"*, the card's
Egress section - is false. Its **consequence is wrong**, and the correction
matters because it decides the fix and the test.

A relative `Location` is legal HTTP and Node hands the header back as sent.
`describeLocation` decides how to describe it with `new URL(raw)`, a relative
reference throws `ERR_INVALID_URL` (confirmed, exit 0), so the `catch` at
`:178-194` returns. That object sets `queryKeys: '(unparseable)'` - a **string**
sentinel (`:188`) - while `renderArtifact` assumes an array and calls
`location.queryKeys.map(...)` whenever `location.queryKeys.length !== 0` (`:258-262`).
A 13-character string has a length and no `.map`, so the render throws
`TypeError` (confirmed, exit 0). `render()` is evaluated as the argument to
`writeFile` at `:381`, so the throw happens **before** any byte is written.

Therefore, today, on a relative `Location`:

1. the raw echo at `:250` is pushed into an in-memory array and **never reaches
   disk** - the file is not written at all, so the review's "written verbatim
   into a committed file" is not what would happen;
2. the probe dies with a `TypeError` instead of exit 0, V2's row fails, and the
   run record for that run is **lost** - which is the opposite of what stop
   conditions 1 and 2 ask for ("record the exact `Location` with any query string
   written `<redacted>`");
3. the moment anyone fixes the `TypeError` without also fixing `:250`, the
   signature lands in a committed file. The leak is real and latent, and it is
   **masked by a crash**, not merely unexercised.

That makes this a correctness defect first and a security defect second, and it
makes the review's severity framing ("a guard that is one `catch` away from
writing the secret") true for the wrong reason. There is still no incident: the
committed `redirects.md` carries 14 `<redacted>` and no value, and the branch did
not fire in either recorded run.

**Minimum corrective scope, exactly three lines, all inside May edit:**

- `scripts/v2/probe-redirects.mjs:250` - `` lines.push(`  - raw: \`${redactQuery(location.raw)}\``); ``
  (`redactQuery` is already defined at `:222` and already used by the parsed
  path's last line, so this is the file's own idiom);
- `scripts/v2/probe-redirects.mjs:188` - make the sentinel an **array** (`[]`)
  rather than a string, so `renderArtifact` cannot throw. `[]` is the honest
  value: no parameter name was established. The four other `'(unparseable)'`
  sentinels are strings consumed as strings and are fine;
- in the same branch, push one line saying the record is **incomplete** - the
  branch already has that vocabulary in `refusals` at `:192` - so a reviewer can
  tell "the vendor sent something I could not describe" from "there was nothing
  to describe".

**Needed test scope, and why it needs more than a new file.** The probe exports
nothing and calls `await main()` at top level (`:400`), so importing it from a
test would perform the seven live `HEAD`s - forbidden twice over, because the
egress grant is spent and because a test must never open a socket. The minimum
that makes the branch testable:

- `scripts/v2/probe-redirects.mjs` - `export` the two pure functions
  (`describeLocation`, `renderArtifact`) and guard the entry point so `main()`
  runs only when the file is invoked directly (the standard
  `import.meta.url === pathToFileURL(process.argv[1]).href` test, or a
  `process.env`-free argv check). Five lines, same file, already writable.
- `scripts/v2/probe-redirects.test.mjs` (**new, and outside May edit - owner
  decision D3**) - `node:test` + `node:assert/strict`, the shape
  `scripts/v2/sandbox.test.mjs` already uses. Exactly two cases:
  1. `describeLocation('/ggml/resolve/main/ggml-tiny.en.bin?Expires=1&Signature=<32-char synthetic placeholder>')`
     returns `unparseable === true` and its `raw` still carries the placeholder;
  2. `renderArtifact(...)` over that observation **returns a string** (this is
     the assertion that pins the `TypeError`), and that string contains
     `<redacted>`, does **not** contain the placeholder, and carries the
     "incomplete record" sentence.

  Two constraints on that test, both load-bearing. The placeholder must be an
  invented constant, never a value copied from `redirects.md` or from any real
  `Location` - the ten parameter *names* are public vocabulary already committed
  in `redirects.md` and `catalog.ts:121` and may be named freely, but no *value*
  may be pasted into a test, a fixture or a commit. And the fixture must be a
  **relative** reference: the `NON_LOOPBACK_URL` selector
  (`eslint.config.js:12`, applied to every `.{ts,tsx,js,mjs}` at `:47`) rejects
  any literal matching `^https?://` to a non-loopback host, so a test built from a
  path-relative string lints clean with no exemption and no edit to
  `eslint.config.js` - the one exemption at `:144` stays one.

**No later card can hold this fix.** `docs/v2/cards/P4.1.md` is the only card in
`docs/v2/cards/` that names `probe-redirects.mjs` (verified by grep). P4.3 owns
`catalog.ts`, `plan.ts`, `shared/src/transcribe.ts` and two `scripts/*.sh` - not
the probe; S4a.2 owns `stt-benchmark.mjs` - not the probe. So the choice is
P4.1's last attempt, a new card, or a widening of some other card, and the
cheapest is P4.1 attempt 3.

## F4 - rule 5's parenthetical versus Fixed decision 10: an unresolved contradiction in the plan

C-ACQ@1 rule 5 (`docs/v2/CONTRACTS.md:259-262`) ends *"or a fresh hash matches
(then a receipt is written)"*. Fixed decision 10 (`cards/P4.1.md:284-288`) says
*"Readiness is computed on every run and repairs nothing... A run that only
probes, such as the one behind the plan, writes nothing on disk."* The code took
the card: `assessModel` never writes (`installer/src/readiness.ts:450-453`), the
only `writeReceiptFor` call is inside the step loop
(`installer/src/run.ts:318`), and a test asserts the disk is untouched
(`installer/src/readiness.test.ts:313-327`). The review and the return agree the
implementer chose correctly and flagged it; both hand the decision on.

The cost is bounded and permanent for one class of file: a model file restored
from a backup - correct size, correct digest, no receipt - is hashed on **every**
launch instead of once, ~1/3 s for 75 MiB, because the run that hashes it is
forbidden from recording the result.

**Recommended: amend the contract, not the card** (owner decision D2). The
invariant "a probe writes nothing" is worth more than a third of a second: a
plan may be rendered on a volume the user cannot write, and a probe that writes
is the kind of side effect the whole checkpoint-and-resume design is built to
avoid. Proposed wording, `docs/v2/CONTRACTS.md:262`:

> …or a fresh hash matches (then the receipt is written **by the run that
> verified the file, never by a run that only probed it**).

That closes the contradiction in the direction the code already takes, changes no
behaviour, and needs no code and no test change. The alternative (rule 5's letter
wins: let `probeState` write the receipt it just earned) requires amending Fixed
decision 10 *and* changing one test's expectation *and* accepting a write on the
plan path - three changes instead of one sentence in a document, for 0.3 s. If
the owner prefers the letter of rule 5, say so and the packet inverts, but I do
not recommend it.

## F5 - the size pin: the suspicion is reasonable, the record is better than the review says, and the loop is narrower than it looks

Impl review finding 4 and the return's deviation 4 both say the same thing:
`sizeBytes: 77_704_715` "is a transcription, not a measurement", and "no machine
in this project has measured the file". **The second sentence is false, and it is
false on the record.** Three v1 documents, all of which v2 inherited, state that
on 2026-09-20 a **real 77,704,715-byte download** happened on this Linux box, that
whisper.cpp's published SHA-1 matched it, and that Apunta's SHA-256
`921e4cf868…` was computed *from those same bytes* and is what `catalog.ts:224`
pins:

- `docs/MANUAL-VERIFICATION.md:337` - "☑ done 2026-09-20 on Linux, on a real
  77,704,715-byte download: whisper.cpp's published SHA-1 ... matched, and
  Apunta's own SHA-256 ... was computed from it and is pinned for both the note
  and the preview entry";
- `docs/HANDOFF.md:612` - "The pin is verified: the published SHA-1 and Apunta's
  SHA-256 match a real 77,704,715-byte copy";
- `docs/decisions.md:209` - "verified here against a real 77,704,715-byte
  download (2026-09-20, Linux)".

So the honest statement, stated in three parts, is:

1. **Published evidence: yes, and it is the strongest kind here.** The size figure
   and the digest pin describe **one and the same verified artifact**, not two
   independent measurements. A file of 77,704,715 bytes whose SHA-256 is
   `921e4cf8...` is not a claim anybody made in the abstract; it is a file that
   was fetched, hashed and matched on this machine.
2. **Synthetic evidence: yes, and it proves only arithmetic.** P4.1's tests pin
   the number's *use* - `catalog.test.ts:202` pins the literal, and the six
   migrated `run.test.ts` fixtures place a **sparse** file of exactly the pinned
   length plus a valid receipt (return deviation 5). Sparse because 75 MiB
   should not be written by a test. That is a correct fixture and it validates
   nothing about the number's truth; the review is right about that much.
3. **What no evidence establishes:** an *independent* measurement of the byte
   count. The 77,704,715 also appears verbatim as upstream's published figure
   (which is what the base's `approxBytes` comment cited, `catalog.ts:174-179`),
   and no record in the repository states that the byte count was read off the
   download rather than quoted from the same README. The two figures therefore
   corroborate each other without being independent, and a HEAD cannot settle it:
   the probe is `HEAD`-only by grant and receives a `302`, so it never sees a
   `Content-Length` (`redirects.md:31` records `302` on all seven). Settling it
   further would need either a new network grant or an actual acquisition - S4a.2
   - and I did neither.

**And the failure the review traces is much narrower than "a 75 MiB re-download
on every launch, forever".** Two orderings, both read at the tip, close it down:

- `installer/src/run.ts:282` verifies the pinned digest **before** `:296` commits
  and before `:304` compares sizes. So if upstream ever republishes
  `/resolve/main/` (a mutable branch, `catalog.ts:222`), the digest check fires
  first and the outcome is a clean `checksum_mismatch` with `discardDownload` -
  no commit, no receipt, no loop.
- The `size_mismatch` branch at `run.ts:304-311` is therefore reachable **only**
  when the downloaded bytes match the pinned digest **and** the size differs. A
  digest is a function of the bytes, so that condition is reachable only if the
  **size pin itself is wrong**.

The review's own mechanism claim is right and its severity is not: this is a
wrong-pin tripwire, not a general fragility. Its consequence, if it ever fires, is
that `readiness.assessModel` returns `size_mismatch` at
`installer/src/readiness.ts:511` **before** hashing (`:544`), so the plan marks
the step needed and the download runs again - once per launch, indefinitely, with
the honest message "the pin is wrong rather than the download; this is not
something trying again can fix" printed each time. The code says the right thing
and the run loop then does exactly the thing the message denies. The review is
also right that detecting the *second* mismatch is not possible inside May edit
without a write on a probe.

**Recommended: owner decision D1 - one sentence in C-ACQ@1 rule 5, and three
lines in `readiness.ts`.** Make the digest decisive over the size, which is what
removes the consequence:

- `docs/v2/CONTRACTS.md:259-262`, rule 5: *"its size equals the pinned size, and
  either a receipt..."* → *"its size equals the pinned size **or a fresh hash
  matches the pinned digest**, and either a receipt..."*
- `installer/src/readiness.ts:511-517` - on a size disagreement, hash the file and
  compare: a match is `ready` with `proof: 'hashed'` and a reason that names the
  disagreement; a mismatch is `size_mismatch` exactly as today. `run.ts:304-311`
  keeps its throw - on a fresh download a digest match with a size mismatch still
  means the pin is wrong and something must say so out loud - but the next probe
  then reports `ready`, so the cost is **one** wasted download instead of one per
  launch for ever.
- The receipt shape does not move. `writeReceiptFor` must keep refusing to write a
  receipt whose `sizeBytes` is not the pin (`readiness.ts:388`), and
  `receiptFor` must keep treating one as no receipt (`:364`); Fixed decision 4's
  eight pinned keys and its "a receipt whose `sizeBytes` disagrees with the
  catalogue is treated as no receipt" are untouched. The price is that a
  wrong-pinned file is re-hashed on every launch - the F4 cost, in the one
  scenario the evidence says will not occur.

Is that loosening a guard (HS-7)? It is a change to `CONTRACTS.md`, so it is the
owner's and not the coordinator's either way; my judgement is that it **adds** an
identity check rather than removing one - a file failing the digest is still
refused, and the size gate is not an independent source of truth about a file
whose bytes are pinned. Say so in the amendment row, because a future reader will
ask.

**The alternative, if the owner will not touch rule 5: D1'.** Change no code and
no contract; record the corroboration above in the evidence directory and in
AM-052's follow-up, and accept that a wrong pin costs a per-launch re-download
until someone notices. On the evidence in (1) that is defensible - the pin is
corroborated by the record that produced the digest, and the tripwire fires loudly
and correctly - and it is the zero-change option. I recommend D1 because the
