## Step 4 — the diff against the Fixed decisions and C-OWN@1

**`processStart` is a raw kernel number, read as written, compared as a string.**
`linuxProcessStart` (`data-lock.ts:110-123`) reads `/proc/<pid>/stat` and takes
`fields[19]` of the slice taken **after the last `)`** — correct, because `comm`
is parenthesised and may itself contain spaces and parentheses, so counting from
the `)` is the only safe origin. I checked the index rather than trusting it:
field *N* after `)` is index *N−3*, so index 19 is field 22, `starttime`; and on
this box `starttime / SC_CLK_TCK` equals `/proc/uptime` to the second for a
process started now, which is exactly "clock ticks since boot". The value is
written into the lock file **as read**, with no formatting, and compared with
`===` as a string (`ownerIsAlive`, `:187`). The strongest evidence is
behavioural and already in hand: case 1 passes. If an ISO-8601 timestamp were
written here, `current === contents.processStart` could never hold, the second
in-process acquisition would have *taken over* rather than refused, and case 1
would have failed with two owners — the exact failure the first Fixed decision
exists to prevent. Case 1 refuses, so the value round-trips. `macProcessStart`
uses `ps -o lstart= -p <pid>` as specified, and `processStartOf` dispatches on
`process.platform`.

**Liveness is `process.kill(pid, 0)` with the specified error mapping.**
`processIsAlive` (`:152-159`): no error → alive; `ESRCH` → dead (take the lock);
anything else, `EPERM` included → alive, so a live process owned by another user
is **refused**, never taken from. `ownerIsAlive` (`:182-188`) then returns
**`true` when a live pid's start time cannot be read at all** (`current ===
undefined → return true`), so the takeover branch is not taken on an unreadable
`/proc`, a failed or unparsable `ps`, or a missing field. That is the Fixed
decision's rule verbatim, and it is the conservative direction.

**The exported surface, fixed.** `data-lock.ts` exports exactly the three values
the decision names — `DATA_FOLDER_IN_USE` (`:42`), `DataFolderInUseError`
(`:73`), `acquireDataFolderLock` (`:309`) — plus the two interfaces
`LockContents` and `DataFolderLock`, which are the handle's and the file's types
rather than extra state. `acquireDataFolderLock(dataDir)` returns
`{ nonce, release() }` (`:340`, `handleFor` `:276-299`) and **throws** on
refusal. `DataFolderInUseError` carries `code === 'data_folder_in_use'` as a
field (`:74`, the same constant, so the two cannot drift) and the live owner's
`pid` (`:83`; `undefined` only in the one refusal where the file stopped being
readable between the rename and the re-read, which the implementer documents
and which is the honest answer). The nonce is generated **inside**
`acquireDataFolderLock` (`:322`) and returned on the handle, so rule 3's re-read
compares the file on disk against the caller's own nonce. **No other module
state**: `release()`'s idempotency is a closure flag per handle, not a singleton,
and the test releases between cases (`first.release()` in 1, `taken.release()` in
2 and 3) instead of resetting anything.

**The refusal exits 75 and binds nothing, and does not go through the boot-error
path.** In `index.ts` the branch is the **first** statement of the `catch`
(`:46-49`) — before the rollback at `:50`, before `storageBootMessage` at `:57`,
before `serveBootError` at `:58`, and therefore before `buildApp` (`:69`),
`app.listen` (`:117`), and by construction before `applyPendingRestore` (`:33`)
and `openDatabase` (`:34`), since the throw is at `:32`. So it does not take
today's path at `index.ts:27-44` (as the pre-card file had it): no boot-error
page, no bound port, no `return`, and it leaves with 75 rather than 0. A
genuine storage failure still gets the boot-error page — the branch is
`instanceof DataFolderInUseError` and nothing else is diverted. V2 observed all
of this from outside the process.

**Release happens in the existing `onClose` hook, idempotently, and only while
the file still carries this process's nonce.** `index.ts:70-77` adds
`lock.release()` **beside `db.close()`** in the hook that already existed — the
one the `SIGINT`/`SIGTERM` handlers at `:110-114` reach through `app.close()`,
and the one any other orderly close reaches. `handleFor.release()` (`:280-297`)
returns immediately if already released, re-reads the file and unlinks **only**
on a nonce match, and swallows every error. A lock already taken over by someone
else is never removed; a crash leaves the file behind and rule 3 takes it over.
V2 saw the end of that path: after the wrapper's `SIGTERM`, no `apunta.lock`
remained in the run folder.

**Rule 1's ordering.** `ensureDataDir` (`:31`) → `acquireDataFolderLock` (`:32`)
→ `applyPendingRestore` (`:33`) → `openDatabase` (`:34`): the folder, then the
owner, then everything that touches the database. No snapshot is called and
nothing blocks on one — that step is P5.1's, and C-OWN@1 rule 1's pre-migration
snapshot is correctly left alone. Rule 4's backstop is
`db.pragma('locking_mode = EXCLUSIVE')` in `db/index.ts`, placed **after**
`migrate` with a comment saying why (migrations write; the lock must be taken
once the schema is in place).

**Rule 2's content and rule 3's mechanics.** The lock file is
`<dataDir>/apunta.lock`; the JSON is `{ pid, processStart, appVersion,
protocol: 1, nonce }` — the contract's five keys, in the contract's order, with
`protocol: 1`. The stale branch (`takeOver`, `:344-367`) is the contract's
sentence almost literally: write a new lock to a temporary file, `renameSync` it
over the old one atomically, then re-read and confirm the nonce is ours, and
**refuse if not**. A file that is not one of ours (unparsable, or missing a
positive integer `pid` / non-empty `nonce` / non-empty `processStart`) is treated
as stale by `isLockShape` (`:170-179`) rather than as a live owner — a
deliberate, disclosed choice (return Deviations 3) that keeps a hand-edited or
foreign file from bricking the folder, and that keeps the app recoverable.

### The `link()` change: matches the Fixed decisions, and is disclosed besides

The implementer changed rule 2's exclusive create from `open(path, 'wx')` plus a
follow-up write to a private temporary file `link()`ed into place
(`createLockFile`, `:263-274`), with an `open(wx)` fallback for filesystems with
no hard links, plus a settle-and-re-read in `readLockFile` (`:223-230`). The
coordinator asked me to say whether this matches the card's Fixed decisions or
is a disclosed, justified deviation. **It matches, and it is disclosed anyway —
both answers, which is the strongest position available.**

*Why it matches.* The seven Fixed-decision bullets constrain `processStart`'s
semantics, the exported surface, the exit-75 refusal, the `onClose` release, the
absence of a shell carrier, the absence of a snapshot call, and V1's folder
location. **None of them mentions which syscall performs the create**, and none
is changed by it. C-OWN@1 rule 2 requires the file to be "created with exclusive
create", and `link()` **is** an exclusive create: it fails with `EEXIST` if the
destination exists, it does so atomically, and — the point — it cannot publish a
name that exists but is not yet a lock. The stated guarantee of rule 2 is
therefore preserved exactly; only the window in which the name is visible but
the body is missing is removed. The fallback path is the literal
`openSync(path, 'wx', 0o600)`, also an exclusive create, and the `'wx'` flag
means it can never overwrite an existing lock either. The change also brings the
fresh branch into line with the contract's own idiom for the stale branch, which
rule 3 already prescribes as "write a new lock to a temporary file and atomically
rename it over the old one".

*Why it is justified.* The race is real, and the implementer reports it was
found by case 4 under `npm test`'s 142 parallel files rather than by inspection:
with `open(wx)` then write, the file exists and is **empty** between the two
calls, and a second process that reads it in that window sees something that is
not a lock, decides it is stale, and takes the folder over — both processes then
believe they own one practice's records, which is precisely the outcome
C-OWN@1 exists to prevent. That is not a hypothetical; the return and the
evidence both quote the failing run. Refusing to apply the fix would have been
the wrong call, and the fix does not weaken any other guarantee.

*Why it is disclosed.* Not buried: it is named in the return's summary paragraph
before the criteria ("case 4 found a real race in the first implementation and
the fix changed how rule 2's exclusive create is made"), again as Deviations 1
with the mechanism, the fallback's justification and the residuals; in
`docs/v2/evidence/P3.2/verification.md` §"A fourth race, found by case 4 and
fixed rather than slept through"; and in the code at `data-lock.ts:242-262`. The
mechanism, the reason, the platform limitation and the residual window are all
in the open.
