## Defects

### D-8 — the Read plumbing sentence asserts existing wiring that does not exist

- **ID and location.** IR-01 (and IR-03). `docs/v2/cards/S3.2.md`, `## Read`,
  line 59.
- **The conflicting text.** "The locale-scoped terms reach `scoreNote` through
  the **existing** `ScoreOptions.lexicon` option (`score.ts:111-124`,
  **populated at `run.ts:144`**)". The option exists (`score.ts:111-116`) but is
  populated **nowhere** in the repository: `run.ts:144` builds
  `scoreNote(fixture, sections, { model, run, stats })` with no `lexicon` field,
  and a repo-wide search finds no other `ScoreOptions` construction — only
  `lexicon(options)` at `score.ts:120-124` falling back to the module-level
  `cachedLexicon ??= loadLexicon()` (`score.ts:122`), which reads
  `e2e/fixtures/eval/lexicon/clinical-terms.txt` unconditionally
  (`lexicon.ts:26-27`, `EVAL_DIR` at `corpus.ts:19`). Every es-MX run at the base
  commit is scored with the **English** clinical lexicon.
- **Failure scenario.** An implementer trusts the sentence, opens `run.ts:144`,
  finds no `lexicon` field, and concludes the locale must travel through the
  cached default — i.e. by changing `loadLexicon()`'s default in `lexicon.ts`,
  which is a process-wide, module-cached singleton. Under that reading
  `--locale en` and `--locale es-MX` cannot both be right in one process, and
  FD2c's "nothing is shared across locales" and the "legacy path byte-identical"
  claims stop being true by construction. The alternative reading — thread the
  terms into the options object at `run.ts:144` — is the correct one, but the
  card nowhere lists that edit: its "New surface this card creates" enumerates
  the flags, the runner, the controls loader, the `loadCorpus` change and the
  `lexicon.ts` changes, and says the pipeline runner is "a new code path … **not
  an edit to `run.ts`**". A correct implementation therefore requires an edit to
  a file the card's own inventory says is not edited, and the implementer has to
  guess that it is permitted.
- **Specific correction.** Rewrite the `## Read` sentence as: "`ScoreOptions.lexicon`
  (`score.ts:111-124`) is **declared but never populated** at the base commit;
  this card's plumbing edit is to add a `lexicon:` field to the options object
  `run.ts:144` already builds, carrying the locale-scoped terms the FD2c loader
  returns, so `score.ts` and its `cachedLexicon` default stay untouched (a diff
  touching them is a defect) and a locale-specific lexicon never reaches the
  module-level cache." Add `run.ts:133-152` to Read and add `run.ts`'s options
  object to the "New surface" inventory.

### D-9 — FD2b's normative example violates FD8's author-time rule and V1's assertion (D-2 and D-3 collide)

- **ID and location.** IR-03, and IR-04 because it makes a mandated V1 test
  unpassable. `docs/v2/cards/S3.2.md`: FD2b's `invented-negation` worked JSON,
  line 322 (`"mustNotContain": ["{{lexicon}} refiere", "{{lexicon}} reporta",
  "niega(?:ndo)?", "{{lexicon}} ha tomado"]`), against FD8 lines 908-911 and V1
  line 1114.
- **The conflicting text.** FD8: "**author-time rule, not a description**:
  EVERY `mustNotContain` entry of the `es-MX` invented-negation control carries
  that token in the negator's slot, and a single entry without it makes the
  control unreachable for V3's exit 3." V1: "one assertion that EVERY
  `mustNotContain` entry of the `es-MX` invented-negation control carries the
  `{{lexicon}}` token in the negator's slot, so one entry without it fails V1".
  The card's own worked JSON — introduced as "**The exact JSON, in the exact
  shape**" for that class — has one entry, `niega(?:ndo)?`, that carries **no**
  token, exactly as AM-117's D-2 required.
- **Failure scenario.** The implementer copies the normative example into
  `server/src/eval/fixtures-controls/es-MX/expectations.json` and writes V1's
  mandated assertion. V1 fails on the card's own example. To make it pass they
  must either delete `niega(?:ndo)?` from the control — silently narrowing the
  invented-negation class to the three token-bearing shapes and diverging from
  FD2b's "exact JSON" — or weaken the assertion, which is precisely the
  D-3 scenario round 2 warned about (V3 then exits 0 instead of 3, because
  `niega(?:ndo)?` still fires under blinding). Either way the first
  implementation attempt is spent on a contradiction between two of the card's
  own sentences, and HS-7 forbids solving it by loosening the assertion.
- **Specific correction.** Resolve the collision in one direction, in the card
  text: state that the `es-MX` invented-negation control's `mustNotContain` is
  **exactly** the token-bearing entries (`"{{lexicon}} refiere"`,
  `"{{lexicon}} reporta"`, `"{{lexicon}} ha tomado"`, plus the rest of that
  sidecar's own token-bearing list) and that a phrase with no negator of its own
  — `niega(?:ndo)?`, `jam[aá]s` — is therefore **excluded from that control**,
  because a de-tokenised entry would defeat both FD8's rule and V1's assertion;
  say in FD2b where the `niega`-shaped coverage lives instead (the class's
  `controlSource`/`controlNote` pair and the S3.1 gold's own entries, which
  `mustNotContain` never receives). Then delete the fourth entry from FD2b's
  worked JSON so the example and the rule agree.
