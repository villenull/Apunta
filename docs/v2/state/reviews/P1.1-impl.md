## Step 4 — the diff against the card's fixed decisions and C-SETTINGS@1

Contract bullets, one at a time.

1. **"`SettingsProvider` exposes `update(patch)`. It applies the patch to the
   provider's state immediately (optimistic), then calls `putSettings`."** Met.
   `web/src/components/SettingsProvider.tsx:97` declares
   `update: (patch: UpdateSettingsRequest) => Promise<void>`; `:118` runs
   `applyLocal(patch)` before `putSettings(patch)` is invoked at `:123`, so the
   apply strictly precedes the call. The `INERT` default at `:29` keeps the
   context total for consumers rendered outside a provider.
2. **"Each key has a sequence number. A response for an older sequence than the
   latest request for that key is ignored (last intent wins)."** Met, and
   per-key as the contract says rather than per-request: `sequenceRef` hands out
   a number, `latestSeqRef` records it for **each** key in the patch
   (`:105`), and `stillMine()` (`:114`) filters to the keys whose latest sequence
   is still this request's. Both the success path (`:129-138`) and the failure
   path (`:126`) go through it, so a late success cannot overwrite a newer
   choice and a late failure cannot roll a newer choice back.
3. **"On failure: the provider restores the value from before *that* request
   for the failed keys only, and the control shows the existing error message
   style."** Met. `before` is captured per key from `loadedRef.current` before
   the apply (`:107-108`), the rollback applies `before[key]` for `stillMine()`
   keys only, and `update` rethrows the API error (`:127`). A key that was unset
   is put back by deletion, not by writing `undefined` — `mergePatch` (`:44-49`)
   deletes on `undefined`, which is what `UpdateSettingsRequest` needs since a
   JSON body cannot carry one. The control's error block is untouched: both
   `save` handlers keep the pre-existing `error` / `role="alert"` markup and
   only add `setSaved(false)` on the rejection path
   (`Settings.tsx:335-338`, `:427-430`), so "the existing error message style"
   is literally the same block the contract points at.
4. **"No control keeps a persisted setting in local component state as its
   source of truth."** Met for everything in this card. All five
   `useState` copies of stored appearance values are deleted —
   `accentColor`, `fontSize`, `animations`, `theme` and the `savedRef` record
   (`Settings.tsx:396-404` in the diff) — and each control now derives what it
   shows straight from `settings.state.data` (`Settings.tsx:418-421`), as does
   the Drafting model group (`:309`, `:321-326`). The only `useState` left in
   `Settings.tsx` is `saved`/`error` (transient) and the UI-only
   `section`/`advancedOpen`/`wantArchives` (`:95-101`), none of them persisted
   settings. `putSettings` now has exactly **one** caller under `web/src` that
   is not the API client itself: `SettingsProvider.tsx:123`.
5. **"Radio groups follow native radio keyboard behaviour: arrow keys move and
   select within the group; Tab enters at the selected option."** Met for the
   group the card puts in scope. `role="radio"` buttons are kept — they did not
   become `<input type="radio">` — and the Drafting model group gains
   `tabIndex={effective === profile ? 0 : -1}` (`Settings.tsx:349`) and an
   `onKeyDown` that moves and selects (`:357-369`). It reuses the file's
   existing `rovingTarget` helper (`:634`, unchanged, already used by the font
   size and theme groups) and the same `requestAnimationFrame` focus move, so
   the three groups now behave identically. Tab therefore enters at the
   selected option, asserted at `Settings.test.tsx:193-195`. P1.2 keeps the
   theme group's own keyboard behaviour, as the card said.
