## The exit-code design, pressed four ways

### Press 1 — Is this unambiguous to someone who has never read AM-158?

**Partly. The cell is legible on a first encounter and the reading is correct;
what it lacks is a stated outcome for the case where the evidence is absent.**

Read cold, V2's cell says **Exit 1, and that is the expected process exit**, and
then spends the rest of the cell on the measurement. An implementer who runs the
command and sees `exit 1` has, on the card's own word, passed. So the answer to
"would they report FAIL from a correct run?" is: **no, not if they read the
cell** — the cell leads with the exit and marks it expected, and the AM-158
paragraph sits *inside* the cell rather than in an amendment row, which is the
right place for it. The `What this row proves / does not prove` pair removes the
remaining ambiguity about scope.

The residual risk is not comprehension, it is **what the row concludes when the
line is not printed at all** — see Press 2 and **D7**.

### Press 2 — Printed line versus exit code, here specifically

I read the committed formatter (`server/src/eval/cli.ts:418-421`):

```
`\nHarness sensitivity: ${String(found.bannedStrings)} runs with a banned string, ` +
  `${String(found.gatingConclusions)} with a gating unsupported conclusion, ` +
  `${String(found.filledBlanks)} filled blanks, ${String(found.cleanFixtures)} clean runs.`
```

**Good news, measured:** it is a single fixed template, printed once, to
**stderr**, with the numbers rendered by `String(n)` — plain decimal integers,
no `toLocaleString`, no padding, no alignment, no units, no locale-dependent
formatting. The leading `\n` means it starts its own line. The prefix
`Harness sensitivity: ` is unique in the codebase and greppable. There is no
formatter here that can emit `1.0`, `1,0`, ` 1` or a reordered clause.

**Three real fragilities, none of them about formatting:**

1. **The card names the conjuncts by identifiers that never appear in the
   output, and lists them in a different order from the print order.** The cell
   says `bannedStrings`, `filledBlanks`, `cleanFixtures`, `gatingConclusions`, in
   that order; the line prints banned, gating, filled, clean. Positions 2–4 are
   permuted. Nothing in the card tells the reader to match by the printed nouns
   rather than by position. **D6.**
2. **The card does not say which stream.** The line is on stderr; an implementer
   capturing stdout sees no line. **D6.**
3. **Nothing states what an absent line means.** **D7.**

So: on this codebase the printed line is a *stable* witness and is defensible as
the verdict — but only if the parse is pinned, and it is not.

### Press 3 — Does this invert an existing convention? And does exit 1 collide with a real failure?

Two sub-questions, and the second is the sharp one.

**Convention.** V3's control miss is exit **3** (`cli.ts:389`), reserved,
distinct from 1 and 2, and FD6 says so explicitly. V2's exit 1 does **not**
introduce a second non-zero meaning where there was none: exit 1 was already the
fake-mode "did not deflect" code (`cli.ts:428`) *and* the real-mode gating code
(`cli.ts:435`). What is genuinely new is that **a row's expected value is now a
non-zero code that also means "the run did not do what it was supposed to"** —
the expectation itself is inverted, not the code space. That is a real ergonomic
cost, and it is the cost AM-160 flagged. It is mitigated, not eliminated, by V2
naming the exit as expected in its own first sentence.

**The collision, answered directly: yes, and a genuine infrastructure failure
exits 1 too.** In this CLI the *handled* failures are all distinguishable —
every `CorpusError`, every `--instructions` read failure, the `--controls`
refusal, the `--out` refusal and every `PipelineRefusal` are caught and exit
**2** (`cli.ts:297-307`, `:523`, `:530`, `:543`, `:566-571`), and a missed
control exits **3** before the fake branch. But anything *unhandled* — an
exception escaping `runProvider`, a missing build, an OOM kill's parent npm, a
`tsx`/module-resolution failure — reaches Node's top level, and an uncaught
exception is **exit 1**. So exit 1 carries at least three distinct causes:
"deflected=false on a completed measurement", "a real run had gating", and
"the process fell over".

**Would the row's verdict logic treat a crash as a measurement?** As written,
**yes, and this is the finding.** The row's verdict is "the printed line", so a
correct reading of the card means a crash produces *no line* and therefore no
verdict — which is safe. But the cell's own first token is "Exit 1 … expected",
so the failure mode is an implementer who checks the digit, sees the expected
value, and records PASS on a run that never scored a fixture. Nothing in the
card closes that: the stop condition's own payload ("with all four counts
printed verbatim from the `Harness sensitivity:` line") is *unproducible* in the
crash case, so the stop does not fire either. **D7** is exactly this, and it is
the one part of the flagged design I would not ship as written.

### Press 4 — Is `gatingConclusions > 0` correctly a FAIL?

**Yes, the polarity is right, and I could not trip it wrongly.** The conjunct is

**Recorded as CLEAR, with the caveat stated.**
