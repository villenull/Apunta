## Finding 1 — HIGH — `answered` is keyed by tab identity, so one duplicate-tab window's clean answer hides the other's unpersisted obligation

**The invariant broken.** FD13/AM-215 are fail-closed: a quiesce can never settle
`ok:true` while any window holds text the server was never told about. Chromium's
*Duplicate Tab* copies `sessionStorage`, so two windows really can share one tab
id (`registerWindow`'s duplicate branch and `closeWindow`'s multi-record no-op
both exist for exactly this, and `web/src/main.tsx:390`'s dev hook opens a
same-origin `window.open`). The per-document `doc` nonce was added in round 4 to
tell those two documents apart — but the `answered` set still uses
`windowKey(record) = record.tabId ?? record.id` (`maintenance.ts:578-580`), and
two records under one tab id collide on that key:

- `report()` adds the key — `maintenance.ts:798`;
- `holdFor()` skips asking a window whose key is present — `maintenance.ts:668`;
- `windowPhase()` skips *blocking* on any record whose key is present —
  `maintenance.ts:426`.

`expected` and `reported` are keyed by `record.id` and are correct; only
`answered` conflates duplicates.

**Reproduced against the shipped controller** (`npx tsx` script under `/tmp`, no
repo file written; both scripts are reproduced verbatim in
`evidence/P5.3/impl4-review.md`):

1. **Retained duplicate (the data-loss direction).** A and B share tab id `T`
   with different `doc`s. B's socket closes dirty — retained, `resolved=false`,
   the exact obligation FD13 keeps. A reports `ok` and the quiesce settles:

   ```
   registered records (expect 2): 2
   after B dirty disconnect, live windows (expect 1): 1
   A report outcome: accepted
   QUIESCE RESULT: {"ok":true,"blockers":[]}
   FAIL-OPEN: settled ok:true over the crashed duplicate B with an unpersisted obligation
   ```

   This is the hazard AM-215 exists to close, reached through a browser feature
   the code itself documents as real.

2. **Live duplicate registering mid-quiesce.** A reports clean and re-arms; B
   (same tab id, own `doc`) registers while the quiesce is in flight and is
   **never asked**; the quiesce settles `ok:true` with B live:

   ```
   B is a live, registered window: 2 live
   QUIESCE RESULT: {"ok":true,"blockers":[]}
   FAIL-OPEN: settled ok:true while a live duplicate window B was never asked
   ```

**Why the tests miss it.** `maintenance.test.ts`'s duplicate-identity cases
(`:1083-1157`) never combine a clean report under the shared tab id with a second
record that is not the reporter's. `never makes a live window invisible` has both
live and neither reports; `a clean claim under a duplicated identity` has both
records but no clean report under `T` before the refusal. The impl3 mutation
sweep therefore could not see it.

**Fix direction (not applied — no source edits in this review).** Key `answered`
by the record's own identity (`record.id`, or `record.doc`), which is unique per
document; `registerWindow` already reuses the same `record.id` across an
ordinary re-arm (`maintenance.test.ts:1159`), so the transport-loop property the
set exists for is preserved. A V1 case should assert: two records under one tab
id, one clean report, the other retained/dirty → `ok:false` `no_response`.

## Finding 2 — MEDIUM — V8 does not exit 0: the flush-exemption row's release poll flakes under the whole suite

The card's V8 command (`sandbox.mjs env --port 7853`, whole suite) exited **1**:
**117 passed, 1 failed, 6 skipped, 7 did not run**. The failure:

```
1) [quiescence] › tests/quiescence.spec.ts:447:3 › … the flush exemption: unsaved text
   reaches the disk and the quiesce settles ok:true
   Error: maintenance is released when the last window unregisters
   Expected: false   Received: true   (Timeout 15000ms exceeded)
```

The row's product assertions all passed — the quiesce settled `ok:true`, the
exemption carried the text to disk, and the row reached its final release poll.
The poll then timed out. Diagnosis from the run's server log:

```
…/quiesce/wait?tab=e2e-quiescence-flush&doc=a53aec3b…  held      (req-ca)
…/quiesce/wait…  -> 200, responseTime 237ms  at 1791214143028     (req-ca released `expired`)
…/quiesce/close?tab=e2e-quiescence-flush&doc=a53aec3b… -> 204 at 1791214143057   (beacon, banked)
… (no further wait request from that tab; the release poll follows)
```

The held wait had already been released `expired` by the quiesce's `finally`,
and no re-armed wait was registered before the beacon and `page.close()`, so the
server never observed a socket close and the banked clean claim was never spent:
`releaseIfUnheld` is reached only from `disconnect()` / `closeWindow`'s release
paths. Isolated, the same row passes 3/3 in 5.5 s.

This is the same family impl3-repair §G measured and fixed **only in
`leaveCleanly`** ("a bare `page.close()` does not always reach the server as a
socket close"; the fix was `page.goto('/api/health')` before closing). V4
(`quiescence.spec.ts:437`) and the AM-215 clean-close row (`:710`, `:714`) still
close with a bare `close()`. It is a **spec-side teardown artefact**, not a
product defect, but the card requires V8 exit 0 and this run did not.

**Product-side corollary, fail-closed.** A clean close beacon that arrives on a
connected record holding **no** wait (the between-polls gap) is *banked* and
waits for a socket close that may never come, so browser-mode maintenance can be
stranded until another window event or a restart. That is over-holding, not
fail-open, and the ordinary production gap is milliseconds — but it is the same
shape that made this row red.

## Finding 5 — LOW — AM-217's Capture line has no unmount reset (the E fix's mirror)

`web/src/components/NoteView.tsx` resets `setEditorUnpersisted(false)` in its
effect cleanup (the round-4 E fix). `web/src/routes/Capture.tsx:161` publishes
`setEditorUnpersisted(unfinished)` from an effect with **no cleanup**. A
therapist who types capture notes, discards them through the leave blocker
(`abandonCapture` clears `wav`/`busy` but not `text`, then unmounts), and lands
on a screen with no editor can leave `editorUnpersisted` stuck `true`; a later
clean close of that window then reports dirty, retains a record, and refuses
every later quiesce `no_response` until restart. Fail-closed (over-block), but
the same user-hostile class impl3 Defect E fixed for `NoteView`, and the AM-217
line reintroduces it for `Capture`. (Whether React flushes the abandoned state
before unmount is not proven here; the `NoteView` precedent argues for the
one-line cleanup regardless.)
