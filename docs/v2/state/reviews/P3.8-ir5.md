## Could a lost (d2) race still produce `PASS`?

**No.** There are three distinct outcomes and none of them is a pass.

1. **The pid line is never seen within the 60 s budget** → `NOT RUN`, `exit 3`.
2. **A `ready` line is present when the row signals** → `NOT RUN`, `exit 3`, explicitly before the kill.
3. **A `ready` line appears after the signal** — the lost race — → the row re-reads the whole capture after the window poll and `NOT RUN`s there too. That guard is real and I traced it: the ready event was already queued when the `SIGKILL` landed, so `drive` processes it first, writes `apunta: the server is ready` (`:292`) before any break, and the capture therefore carries the line the second `grep -q` looks for.
4. **The one path I could construct that escapes both `ready` checks** — the error window never being painted, whatever the cause — ends at `d2-no-early-exit-error-window`, which is a **FAIL**, not a pass. There is no arrangement in which a lost race yields a green row.

**The margin is real but not load-bearing.** Detection latency is one poll iteration (50 ms of `sleep` plus the fork of a `sed`, in practice well under 100 ms) against a ~580 ms gap that is the server's *own* startup work and therefore lengthens under load; `SIGKILL` is then delivered before the server can finish. The verdict does not rest on that arithmetic, and the card says so.

**One race I looked for and did not find:** whether the error window survives long enough to be sampled. After the pre-`ready` `break`, `drive` returns, and the caller is a `spawn_blocking` whose comment states the shell's life is the app's life — the shell does not exit on an early failure — so the error window stays up for the whole 20 s sampling window. (d1) has the same shape and an even longer one.
