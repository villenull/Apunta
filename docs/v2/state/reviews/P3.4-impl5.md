## 6. Observations (non-blocking; no criterion fails)

**O1 — tag discovery requires label uniqueness (latent false-FAIL, fail-closed).**
`tagForLabel` (`scripts/v2/tauri-security.test.mjs:1739`) returns `null` unless
exactly one rectangle carries the label; `waitForLabel` (`:1748`) then waits 30 s
and the (d) handler FAILs. The contract §C.4 and model `H1` explicitly design for
a same-label, different-tag hover tooltip (`PatientsColumn.tsx:1439` renders
`John Smith` again in a `div.project-tip-name`). `selectTarget` handles that pair
correctly; `tagForLabel` does not. Demonstrated in
`08-tag-capture-risk.txt`: `tagForLabel(row+tooltip) = null` while
`selectTarget(frame, {label:'John Smith', tag:'SPAN'})` succeeds. The harness
captures the tag **before any pointer move**, so in the normal run the tooltip is
absent and the tag is `SPAN`; the risk only bites if a tooltip is already visible
at capture. It fails closed (no mis-click). Not a criterion failure: the
contract's pair selection is faithfully implemented.

**O2 — `runFlowGuarded`'s deadline-kill branch does not fire for a hung
mousemove/click (containment preserved by the `finally`).** `runFlowGuarded`
(`:1803`) kills active commands only when `result.reason === DEADLINE_EXPIRED`,
but `runFlow` always prefixes that reason (`…; the target deadline expired`), so
a hung target warp/click leaves its child running until `modeSecurity`'s
`finally` (`:1946`) calls `killActiveCommands()`. My probe pins the mismatch
(`03-…probe.txt`, "reason carries the deadline but is NOT exactly
DEADLINE_EXPIRED"). The observable requirement — a hung command stopped **by
pid**, no stranded process, no `pkill` — is still met by the `finally`; only the
early-kill branch is inert. Non-blocking.

**O3 — the tag-discovery wait sits outside the immutable 30 s target deadline.**
`waitForLabel` (30 s) runs before `createTargetDeadline(clock.now())` (`:2123`,
`:2151`), so the (d) handler half can spend 30 s + 30 s per target. The flow's own
deadline, commands, awaits, witness and landing are all inside the one budget as
required; the pre-step is a bounded wait on the observation channel, analogous to
the gate's 45 s window. No existing timeout was widened. Non-blocking.

**O4 — the tooling guard-matrix replay is stale, not the guard.** The
`guard-matrix.mjs` case that expects `docs/v2/state/dispatch/P3.4.md` to carry
the **attempt-4** line now mismatches (`112/113`), because the coordinator
regenerated that dispatch for attempt 5. The guard itself is correct (P3.4
attempt 5 → 0; other card attempt 5 → 2; attempt 6 → 2). Evidence:
`07-tooling-guard.txt`.
