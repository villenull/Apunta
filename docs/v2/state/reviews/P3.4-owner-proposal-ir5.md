## B1 — BLOCKER — `runClick` requires the pointer to be at the target *before* it warps there

`model.mjs:446-457`:

```js
const witness = ops.nextFact();
const dx = Math.abs(Number(witness?.ptrCX) - target.x);
const dy = Math.abs(Number(witness?.ptrCY) - target.y);
if (witness === null || !Number.isFinite(dx) || !Number.isFinite(dy))
  return finish({ ok: false, reason: 'the page published no usable pointer observation before the click' });
if (dx > WITNESS_TOLERANCE_PX || dy > WITNESS_TOLERANCE_PX)
  return finish({ ok: false, reason: `the fresh pointer observation is ${String(dx)},${String(dy)} px from the target centre` });
```

The contract (proposal §D.8) requires exactly **one** fresh observation, and it
comes **after** the warp: *"Warp to the target centre, re-read (≤1 px, over the
app), then require a fresh pointer observation within 2 client pixels of that
centre … and only then dispatch one `xdotool click 1`."* The model instead
fetches `ops.nextFact()` **before** the move and demands it already be at the
target. On any real run the newest fact before the target warp is the last
**calibration** pointer (the second bootstrap point, `P2`), which is not the
target, so the model returns early with no move and no click.

Reproduced (`docs/v2/evidence/P3.4/proposal-ir5/click-witness.mjs`, `P3`):

```
P3 ok=false dispatched=[] reason=the fresh pointer observation is 100,70 px from the target centre
```

`J1` (`model.test.mjs:527-549`) passes only because its fixture sets
`FACT_BEFORE = { ptrCX: CLIENT_TARGET.x, ptrCY: CLIENT_TARGET.y, … }` — the
pre-warp fact is placed exactly on the target. That is the author's green verdict
standing in for the contract: the model's "fresh witness" is a pre-warp witness,
and the post-warp `fresh` check (`:481-487`) is a second, different gate. The
pre-warp gate is an unmotivated mechanism that the proposal nowhere describes.

**Remedy.** Delete the pre-warp `witness` block (`model.mjs:451-457`); keep the
post-warp `fresh` check; or, if a pre-warp observation is genuinely wanted, make
it a *presence/freshness* check (e.g. `ptrN` strictly greater than the last
calibration `ptrN`) and never a proximity-to-target check.

## B2 — BLOCKER — a hung dispatch is not bounded by the deadline

`model.mjs:113-122`:

```js
export function dispatchGuarded(deadline, clock, name, run) {
  if (deadline.expired(clock.now())) return Promise.resolve({ ok: false, reason: DEADLINE_EXPIRED, name });
  let out;
  try { out = run(); } catch (error) { … }
  return Promise.resolve(out).then((value) => ({ ok: true, name, value }));
}
```

It checks expiry only **before** the operation. If `run()` returns a
never-resolving promise — a hung `xdotool mousemove --sync` or a hung
`xdotool click 1` — `dispatchGuarded` never settles, so the row hangs forever.
Contract §E says the opposite: *"the only bound any await gets is the deadline's
own remaining time, so a hung command ends at the deadline instead of extending
the row"*, and *"every dispatch and every await is guarded."*

Reproduced (`docs/v2/evidence/P3.4/proposal-ir5/hung-dispatch.mjs`):

```
hung-move: DID NOT RESOLVE after the deadline advanced; dispatched=["mousemove"]
```

`J5` tests a hung **await** (`awaitGuarded`), which does race the deadline; no
test covers a hung **dispatch**. This is a real model-vs-contract gap, not a
naming nit: the two commands the click run actually dispatches are exactly the
ones a hung X server would stall.

**Remedy.** Race the dispatched promise against the deadline in
`dispatchGuarded` (the same timer pattern `awaitGuarded` already uses), and add a
`J` case with a hung `move` and one with a hung `click`.

## B3 — BLOCKER (spec vs root) — a newer malformed header raises nothing, so the reader falls back

Proposal §C.2: *"A malformed or truncated sighting is discarded: never merged,
never installed, never a conflict, and it raises nothing."* `model.mjs:298-299`
raises `highestSeenEpoch` only after the whole batch's field set and slice have
validated. Root (`P3.4-committee-resolution.md` line 8): *"A valid header
identifying a newer epoch still prevents fallback to an older epoch while that
publication remains incomplete."*

Reproduced (`reader-epoch.mjs`, `P2`):

```
P2 before: frame.ok=true epoch=5 highestSeen=5
P2 newer header (epoch=6) truncated -> kind=malformed highestSeenAfter=5
P2 after: frame.ok=true epoch=5 reason=undefined
```

After a complete epoch-5 frame, a line carrying a **parseable newer header**
(`epoch=6`) with a truncated body is discarded and the reader returns the older
epoch-5 frame as `ok=true`. Whether this is a violation turns entirely on what
root means by "valid header": if it means a *well-formed batch sighting* (the
model's reading, and `G3` covers that case), the model is consistent and the
proposal should say so in one clause; if it means a header whose
`rects`/`batch`/`epoch` parse, then the model permits a fallback root forbids,
and the epoch must rise as soon as the header is valid — before body validation.
The proposal does not reconcile the two, and no test pins the reading. `G3`
tests only a **well-formed** newer batch (batch 0 of 5, every field present);
the header-only case is exactly the removed fixture `MODEL.md` §6 describes as
"an epoch-5 sighting that was not a complete header" — see N1.

## B4 — DEFECT — `G4` is mislabelled and its truncation is never exercised

`model.test.mjs:263-283` builds
`batchLine({ epoch: 7, batch: 1, total: 6, entries: good }).slice(0, 120)`. With
`total=6`, `ceil(6/40)=1`, so `batch 1` is outside `0..0` and the line is
discarded by the **batch-index** rule before truncation is reachable.
Reproduced (`reader-epoch.mjs`, `P1`):

```
P1 untruncated line -> kind=malformed reason=batch 1 is outside 0..0
P1 truncated line   -> kind=malformed reason=batch 1 is outside 0..0
```

The untruncated line is malformed for the identical reason, so the test does not
demonstrate that a **truncated** sighting is discarded whole, and its
`highestSeenEpoch === 7` assertion is vacuous — the discarded line carries the
same epoch 7 as the installed one, so it could not have raised anything even if
the reader did raise on malformed lines. No test covers a truncated body with a
**valid, in-range header** (the case B3 turns on).

**Remedy.** Replace the fixture with a line that is well formed except for being
cut mid-body (e.g. `batch 0` of a `total=6` publication with the `i0_*` group
truncated), and add a second case with a **newer** epoch, so the "raises nothing"
rule is actually asserted against a higher epoch.

## B5 — DEFECT — the bootstrap exemption contradicts §D.4 and root; the flow is unmodelled

Proposal §D.7: *"Containment before every move and read-back after every move,
on every point computed through the solved transform — including the target — and
the two bootstrap points of step 4 are its only exemption."* But §D.4 says move 2
*"is containment-checked **before** the warp, and a point outside the window is
`NOT RUN`"* — so the two clauses disagree about move 2, and §D.7's blanket
exemption contradicts root's *"Check native containment and native read-back for
both moves"* (`P3.4-committee-resolution.md` line 11). The ir4 review already
recorded the arithmetic that makes the exemption unnecessary: move 1's
containment is decidable with no transform (`windowX + cx₁` against
`windowX … windowX+WIDTH`), so checking both bootstrap points costs one
comparison and removes the exemption entirely.

The model cannot catch this because it has **no calibration flow**. `P6`
confirms the model exports no `calibrate`; `runClick` receives a pre-solved
`transform` and starts at the target warp, so the two bootstrap moves, their
containment, their read-back, and their `ptrN` waits are unmodelled. The root
list the model "must cover" includes scaling, offset, command failures,
interrupted/late awaits and no-click terminal paths — but the bootstrap half of
contract 2 is only tested as isolated functions (`D1`–`D7`).

## D1 — the named `ptrN` field and the three-field `clickEl` comparison are under-modelled

- Contract §D.5 requires *"record `ptrN`, dispatch, then require a fact line
  whose `ptrN` is **strictly greater**."* The model never reads `ptrN`; `P4`
  passes with a post-move fact whose `ptrN` never advances

- Contract §D.8 requires `clickEl`'s `tagName`, `data-testid` and trimmed

  `model.mjs:508-509`). The spec names the three fields (so ir4's **M3** is
  closed on paper), but the model does not exercise the comparison the spec
  describes.

## D2 — the URL-length claim is false

§C.1: *"no URL-length increase beyond two short scalars."* The baseline
`sendRects` (`git show 8783181:web/src/main.tsx:117-131`) publishes five keys per
rectangle (`i{n}_x/_y/_w/_h/_l`) plus `rects` and `batch`. The delta adds
`epoch` **and** two keys per rectangle (`i{n}_t`, `i{n}_d`) — up to 80 extra
key/value pairs per 40-rectangle batch. That is not "two short scalars"; the
claim should name the per-rectangle cost or drop the bound.
