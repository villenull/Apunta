## Verdict

**DEFECT.** The proposal is well evidenced and mostly correct, and roughly
two thirds of it can be pasted as card text unchanged. But it cannot be pasted
as a whole, for three independent reasons:

1. **Two of its "no baseline redefined / no acceptance change" claims are not
   true of its own text.** FD9 turns an existing English non-regression gate
   into divergence reporting for this card, and A5 relaxes V4's only pass/fail
   criterion — while §"What this proposal does not do" says no gate is widened
   and no baseline is redefined (proposal `:596-599`). Both are owner
   decisions, correctly routed to Part A, but they are **acceptance changes**,
   not the "no baseline redefinition" the summary claims, and FD9's mechanism
   (an append-only precedence clause) cannot achieve what option A says
   without reinterpreting §5 through an append.
2. **A2 + A3 + FD6 + FD8 + V3 are mutually inconsistent.** As written, the
   negation lexicon has **no scoring consumer anywhere**, the positive control
   has **no defined way to produce a bad note**, and therefore neither V2's
   "all controls behave as specified" nor V3's "exit non-zero" can be
   satisfied by a correct implementation. This is the load-bearing part of the
   card (C-EVAL@1 §3) and it is currently unpassable by construction.
3. **A set of concrete, source-confirmed corrections is missing or wrong** —
   the pipeline runner's drafting language, the sandbox's build prerequisite,
   V4's report paths, the negation lexicon's loader compatibility, FD3's
   factual premise, and the proposed port block.

Everything below is either a **routine source-confirmed correction** (class R —
coordinator may apply under `COORDINATOR.md` §6 "correct a command … without
changing what it checks", or as a card-text correction under the AM-024
blanket) or an **owner decision** (class O — `COORDINATOR.md` §6 forbids the
coordinator changing an acceptance row or a baseline gate). I recommend no
removal, weakening or reinterpretation of any existing gate anywhere in this
review; where the proposal's own text contradicts a gate, the honest
disposition is **BLOCKED pending owner**, not "unpassable".

## D-1 — FD9 / A1 option A is an acceptance change, and append-only cannot deliver it

**Evidence.** `docs/v2/BASELINE.md:196-198` (§5, verbatim): *"This is the table
C-EVAL@1 §8 refers to. A later English **pipeline** measurement on either corpus
must fall inside these ranges or it has regressed."* `docs/v2/CONTRACTS.md:445-448`
rule 8 names "the min–max range recorded in `docs/v2/BASELINE.md` (P0.4, pipeline
section added by S3.2)". The card's May edit is "`docs/v2/BASELINE.md` (append
the English **pipeline** section)" (`S3.2.md:24`) and the proposal's C3 keeps
"**append only**: … Sections 1 to 8 are not edited, and no existing number,
range, numerator or denominator in them changes" (`:233-235`).

So under option A the sentence at `:196-198` stays exactly as written and still
says a later English pipeline measurement must fall inside §5's ranges — while
FD9 says that same measurement is "a recorded divergence and not a gate". The
only way to make both true is for the appended §9 to carry a precedence clause
that overrides §5 for pipeline measurements. That is an append-only route to
reinterpreting an existing gate, and it is why "No gate is widened. No baseline
is redefined" (`:596-599`) is not an accurate description of FD9.

What option A legitimately does preserve is worth keeping: §5's numbers,
numerators and denominators stay byte-identical, the appended table is a
measured min/max and nothing else, and §9 becomes the §8 gate from S3.3 onward
(FD9 `:433-438`). That part is a genuine improvement over option B, which the
proposal itself calls "unpassable by construction" (`:84`) — a phrase this
review also rejects as a disposition.

**Exact bounded options for the owner** (mutually exclusive; all keep every
existing number and every existing gate):

- **O1 (recommended).** Authorise **one sentence** of owner-recorded edit to
  `BASELINE.md:196-198` — from "A later English **pipeline** measurement on
  either corpus must fall inside these ranges" to "A later English **provider**
  measurement on either corpus must fall inside these ranges; the **pipeline**
  gate is §9, added by S3.2" — leaving every number, range, numerator and
  denominator in §5 untouched. This is the only option in which §8's gate for
  pipeline measurements is stated by the document that holds the gate instead of
  being overridden by a later section. It requires a May-edit amendment
  (currently append-only) and an `AM-<nnn>` row recorded as owner-approved.
- **O2.** Keep May edit append-only and accept the precedence clause in §9
  verbatim, with FD9's anti-widening sentence retained. Honest, but it leaves
  §5 and §9 in visible contradiction for any later reader.
- **O3.** Defer: this card appends nothing, V4's criterion is the eight reports
  only, and §9 (and the §8 gate question) is settled by S3.3 before any card
  relies on it. C-EVAL@1 §8 then stays unsatisfied by this card and S3.2's
  return file records that as `BLOCKED`, owner — not as pass.
- **O4 (not recommended).** Both tables gate pipeline measurements (intersection).
  The proposal's objection stands: the two measurements come from different
  code paths (`BASELINE.md:8-12`, `:281-284`).

**Required accompanying amendment whatever is chosen.** FD9's "it does not
fail this card" must not mean "it passes silently". Replace that clause with:

> A pipeline number outside the corresponding §5 provider range is recorded in
> the appended section with both values and the delta, and is reported in the
> card's return file as a **REGRESSION FINDING for the owner**. It does not
> move a number in §5, and it does not by itself mark the card's acceptance
> rows green; a row whose only criterion was the written reports records the
> finding alongside them.

This keeps the divergence visible and keeps `BLOCKED` available, instead of
converting a regression into a passing row.

## D-2 / D-3 — A5's "exit 0 or 1" is an acceptance change resting on an inference

**Evidence.** The card's V4 expected result is `exit 0` (`S3.2.md:48`).
`BASELINE.md:60-62` and `:80-83` record that the **provider** measurement on
`e2e/fixtures/eval` exited 1 on all four invocations (4 of 20 runs gated), and
`server/src/eval/cli.ts:293` is `process.exit(gated ? 1 : 0)`. The proposal
infers (`:150-156`) that "Pipeline mode uses the same exit rule, so V4 will
return 1 on that corpus for the same reason, on a correct implementation."

Three things are wrong with that inference, and the proposal's own routing
admits the change is the owner's (`:158-161`):

- The 4/20 gating is a **provider-path** measurement. Nothing in the repository
  measures gating on the pipeline path. The pipeline path adds the retraction
  pass, absent-preservation and discussion subheadings (`BASELINE.md:281-284`)
  and may gate more or less. "Same exit rule" is a statement about `cli.ts`, not
  about the number.
- `e2e/fixtures/eval-owner` is the corpus P0.4 recorded at **0/4** gated runs
  (`BASELINE.md:198-215`, §5 `Gated runs 0/4 – 0/4`). There the provider
  baseline is clean, so an exit 1 there is not "expected for the same reason" —
  it is a new fact.
- Under `--runs 1` with the same exit rule, "exit 0 **or 1**" accepts *any*
  amount of gating. The card's original `exit 0` was V4's **only** pass/fail
  criterion besides the append. After A5, V4 has no failing criterion at all:
  any pipeline measurement whatsoever produces eight reports and an appended
  table. That is a wider acceptance surface than the card had, presented as a
  bookkeeping correction.

The **wording** is well precedented — `docs/v2/cards/P0.4.md` V1 already reads
"Exit **0 when no run gated, 1 when a gating failure is found** — that digit is
the eval's own signal … the criterion is the written report and its recorded
rates", and `AM-029` recorded making that change to P0.4. So the exit-code half
of A5 is defensible as an owner-authorised expectation correction. The
**criterion** half is not, as written.

**Exact bounded replacement for V4's expected cell** (owner decision; this
restores a failing criterion without inventing a threshold — every number
quoted is one `BASELINE.md` already records):

> Eight sandbox invocations, one process each, `--runs 1`, V1 corpus first then
> V2 as P0.4 ordered. Each writes a report. Exit **0 or 1 per invocation** as
> the eval's own gating signal (`cli.ts:293`), which is the P0.4/AM-029
> precedent and not a pass/fail of this card. The criterion is: eight reports
> present with numerators, denominators and the FD7 metadata; §9 appended with
> a measured min and max per corpus and per metric; **and**, per corpus, the
> recorded gated-run count. `e2e/fixtures/eval` may gate (P0.4 recorded 4/20 on
> the provider path) and its count is recorded as a measurement.
> `e2e/fixtures/eval-owner` recorded **0/4** gated on the provider path
> (`BASELINE.md` §5), so a pipeline gated-run count above 0 there is recorded as
> a **REGRESSION FINDING and the row's status is `BLOCKED`, owner** — not a
> pass. Any invocation in which the eight-invocation set is incomplete, a
> report is missing, or a pipeline number falls outside the corresponding §5
> provider range is reported the same way: numbers recorded, row `BLOCKED`,
> owner. No gate is removed by any of this.

Owner options: **O5 (recommended)** adopt the cell above; **O6** keep A5's cell
verbatim and accept that V4 cannot fail on quality — in which case the card's
return file must state that S3.2 establishes no pipeline acceptance criterion
and that C-EVAL@1 §8's pipeline gate is first exercised at S3.3; **O7** keep
`exit 0` for `eval-owner` (where the provider baseline is clean) and allow 0/1
only for `eval`. Note the routing: `COORDINATOR.md` §6 forbids the coordinator
changing an acceptance row, so A5 as written is correctly an owner item — it
should not be relabelled a §6 command correction, and the AM-029 precedent
supports asking the owner rather than assuming.

## D-4 — The negation lexicon has no scoring consumer (blocking)

**Evidence.** `server/src/eval/score.ts` and `server/src/eval/lexicon.ts` were
read in full. The only lexicon in the scorer is the clinical-terms list behind
F7 `novel_clinical_term_rate`: `lexicon.ts:7-10` (header), `score.ts:4`
(`import { loadLexicon, … }`), `score.ts:112-124` (`ScoreOptions.lexicon`,
cached), `score.ts:264-289` (the F7 check). Grepping the eval module for
`negation` returns nothing. Negation today is caught **per fixture** by the gold
sidecar's `mustNotContain` / `mustCapture` regexes, exactly as A3 option A
states (`proposal:120-121`).

Consequences, all internal to the proposal:

- FD2/A3-A state the lexicon "supplies the **vocabulary** … for the negation-class
  controls and for the negative control V3" (`:125`, `:554-558`). Vocabulary for
  *authoring* is not a runtime input.
- FD6 asserts "blinding the lexicon (V3) blinds the control too" (`:405-409`).
  It cannot. A control is a **file on disk** (`FD6` layout, `:365-376`).
  Emptying a runtime lookup does not alter a file's bytes, so an unblinded and a
  blinded run score identically unless something reads the lexicon at scoring
  time — and under A3-A nothing does.
- Therefore V3's expected `exit non-zero` (`:456`) cannot occur on a correct
  implementation, and V2's "all controls behave as FD6 states" has no mechanism
  either.

This is the IR-02 failure mode the proposal was written to close, reappearing
one level up: an instrument whose negative control cannot fail.

**Exact bounded options** (owner decision — each adds a small amount of scoring
surface, none adds a threshold):

- **O8 (recommended).** Name the consumer explicitly, keeping A3-A's "no general
  lost-negation check". Gold sidecars may reference a lexicon by name, e.g. a
  required key `lexicon: "negation"` alongside `mustNotContain` / `mustCapture`;
  the loader expands the named lexicon into one escaped, whole-token pattern per
  term at load time, and the scorer applies it with the same
  `compile()`/`collapse()` machinery the sidecar patterns already use
  (`corpus.ts:96-163`, `patterns.ts`). The judgement stays per fixture (the
  sidecar says which direction is the error); the lexicon supplies vocabulary
  (A3-A preserved). `--blind-lexicon negation` then genuinely removes the terms,
  the negation positive control stops being flagged, and V3's non-zero exit is
  real. Replacement text for FD2's negation paragraph: *"Negation: … The
  negation lexicon is a **scoring input** through the sidecar key `lexicon`,
  never read directly by `score.ts` and never imported from a guard module."*
- **O9.** Keep the lexicon authoring-only (A3-A as written) and **retarget V3**
  to a lexicon the scorer already consumes: `--blind-lexicon clinical` blanks
  `clinical-terms.txt`, F7 stops firing, and a positive control containing a
  novel clinical term stops being flagged. This proves the control *mechanism*
  honestly but proves nothing about negation, and the card must say so in V3's
  expected cell. Cheapest change; weaker claim.
- **O10.** Adopt A3 option B (a general lost-/invented-negation check) — which
  the proposal defers to S5 — and drop V3 from this card, recording V3 as
  `NOT RUN` with the reason. Honest, and it leaves the card with no negative
  control, which C-EVAL@1 §3's spirit disfavours.

O10 and O9 are strictly weaker than O8 for the contract's purpose; I recommend
O8 and flag that the owner may reasonably prefer O9 on cost grounds.

## D-5 — A control has no defined way to produce a bad note (blocking)

**Evidence.** Every fixture in this harness is scored on **model output**
(`run.ts:88-110`: `scoreOneRun(provider, fixture, …)`). A *positive* control must
be flagged, i.e. it needs a note that commits the error. Under `--fake`
(V2, V3) the note comes from `FakeLlmProvider.generateNote` →
`fakeSectionsFor` (`server/src/ai/fake.ts:216-231`): the canned entry matching
the source, else `condense(source)` in section 0, else `"None."` for
owner-convention sections, else empty. That function echoes the source and has
no mechanism to drop one negator while keeping the rest, or to introduce a
negator absent from it. So:

- a `lost-negation` positive control is **not** flagged under `--fake` unless the
  negation happens to sit in a section the fake leaves empty — in which case the
  control is flagged for missing content, not for a lost negation, i.e. it is
  vacuous;
- an `invented-negation` positive control cannot be produced by the fake at all.

The obvious way to make one — editing the canned responses — is
`server/src/ai/fake.ts`, which the proposal's own C4 Must-not-edit list forbids
("nothing under `server/src/ai/`").

**Exact bounded recommendation (owner decision, small and in-May-edit).** Add
one required key to the control sidecar and one clause to FD6:

> A control fixture carries its own note text: `controlNote`, the exact text the
> control is scored on. Controls are **scored on injected text, never on model
> output** — a control exists to prove the *scorer* sees an error, so the error
> is supplied, deterministically, by the fixture. The corpus path is untouched:
> corpus fixtures are still scored on provider or pipeline output, and no
> `controlNote` key exists in a corpus sidecar. `scoreNote` is the same function
> in both cases; only the provenance of the text differs.

This makes V2 hermetic and deterministic, makes V3 real (blinding changes the
score of an injected note), removes the dependence on the fake provider's
behaviour, and needs no change to `server/src/ai/fake.ts`.

## D-6 — `empty` and `degenerate` are collapsed, so a required class is untested

**Evidence.** C-EVAL@1 §3 (`CONTRACTS.md:427-429`) names four control kinds:
"Positive controls (must be flagged), clean negatives (must pass), **empty** and
**degenerate** outputs (must fail)". The card's Fixed decision 3 says the same
(`S3.2.md:37-38`). FD6's schema allows three values — `positive | clean |
degenerate` (`proposal:384`) — and its layout gives one file per locale,
`degenerate/01-nota-vacia.txt` / `degenerate/01-empty-note.txt` (`:370`, `:376`):
an **empty** note filed under the name `degenerate`. Nothing in FD6 tests a
degenerate-but-non-empty output (headers with no body, one section repeated, a
note of boilerplate), which is the class that catches a scorer which passes
anything non-empty.

**Replacement.** FD6 key row: `control` takes `positive | clean | empty |
degenerate`, and the layout gains two files per locale:

```
│   ├── empty/01-nota-vacia.txt
│   └── degenerate/01-plantilla-repetida.txt
```

with `expect` derived `positive→flagged`, `clean→pass`, `empty→fail`,
`degenerate→fail`, and the report table printing all four lines with their own
denominators. No threshold changes; a class C-EVAL@1 §3 already requires becomes
testable.

## D-7 / D-8 — Pipeline mode: the locale check that cannot fail, and the locale that is actually used

**Evidence.**

- `server/src/routes/generate.ts:39` — the drafting locale is
  `storedLanguage(db)`, i.e. the **`language` setting**
  (`server/src/http/locale.ts:56-59`, falling back to `DEFAULT_LANGUAGE`).
- `server/src/routes/draft.ts:230` — the persisted note's `locale` is
  `format.locale`.
- FD4 step 2 creates the format with `locale: <run locale>`, and FD5 fails the
  run when "`note.locale` does not equal the run's `--locale`" (`:352-354`).
  Since `note.locale` is copied from the format, **that check can never fail**,
  and it says nothing about the language the note was drafted in.
- Worse: with `--locale es-MX` and a fresh sandbox database (no `language` row),
  the server would draft **in English** while stamping the note `es-MX`.
- `server/src/routes/settings.ts:31-33` and `:84-86` — writing `es-MX` is
  refused unless the process was started with `APUNTA_DEV_SPANISH=1`
  (`spanishAvailable()`), and `sandbox.mjs` does not set that variable
  (`sandbox.mjs:238-247` `serverEnv`, `:249-257` `childEnv`; it only inherits
  `process.env`).

Scope note, stated honestly: **V4 as written measures the two English corpora
only**, so D-8 does not affect this card's own acceptance rows. It does affect
FD4 as a contract for later cards (S5.6), which is where the Spanish pipeline
measurement lives.

**Replacement for FD4** (routines; owner only for the last sentence):

> 0a. When `--locale es-MX`, the sandbox server must have been started with
> `APUNTA_DEV_SPANISH=1`; the runner then `PUT /api/settings {"language":
> "es-MX"}` once per invocation, requires the response's `language` to be
> `es-MX`, and re-reads `GET /api/settings` before the first fixture and after
> the last. A refusal (`language_unavailable`) is `BLOCKED`, owner, with the
> response recorded. `note.locale` is **not** evidence of drafting language
> (`draft.ts:230` copies the format); the settings read is. FD5's `note.locale`
> check is retained as a format-integrity check and is described as such.

And for FD5, replace the `note.locale` clause with "`note.format_id` does not
equal the created format's id" (an integrity check that *can* fail), keeping the
locale equality as a settings-level assertion per D-8.

## D-11 — The format `name` is unpinned, so the two modes can measure different prompts

**Evidence.** `server/src/eval/run.ts:67-78` selects instructions as
`defaultInstructionsFor(formatNameFor(fixture), fixture.sections)` with
`formatNameFor` returning the literal `'Intake note'` / `'Progress note'`
(`:77-80`). `server/src/ai/default-instructions.ts:644-657` matches the
**section list first**, then the **format name**, then a generic fallback. FD4
step 2 sends `{"name": …}` without a value (`proposal:311-318`). If a corpus
format's section list matches no `BY_SECTIONS` entry — which is exactly the
owner's own format, the `eval-owner` corpus — then the name alone decides, and
an unnamed or differently named format silently gets `GENERIC_INSTRUCTIONS`
while the provider path gets the owner's progress instructions. FD4's claim that
"both modes measure the same prompt" (`:317-318`) is then false.

**Replacement:** FD4 step 2 becomes `{"name": "Progress note" | "Intake note",
"sections": [...], "locale": <run locale>}` — the exact `formatNameFor(fixture)`
value — and the runner records `formatName` per fixture in the report. The
assertion list also gains: the read-back format's `instructions` is `''`
(`shared/src/note-format.ts:43-57` returns the stored string), its `sections`
deep-equal the fixture's, and `format.locale` equals the run locale.

## D-16 — The control-miss exit is unordered, and its effect on the CI self-check is unstated

**Evidence.** `server/src/eval/cli.ts:274-288`: in `--fake` mode the exit
status is decided by `sensitivity(result.models)`; if the harness "deflects" it
exits **0** regardless of how many runs gated. So FD6's "A missed control makes
the run inadmissible: exit non-zero, naming the control, in fake mode as well as
real" (`:400-404`) only holds if a control-miss branch is evaluated **before**
the fake branch — which FD6 does not say. As written, a blinded V3 run that
still deflects on the corpus exits 0 and V3's expectation fails for the wrong
reason.

Second, `CLAUDE.md` records `npm run eval -- --fake` as the CI self-check that
"passes when the scorer *deflects* on the canned notes". If a control-miss exit
pre-empts it, a missed control in the **default** English fake run turns CI red.
That is arguably correct (C-EVAL@1 §3: "An instrument that misses a control is
broken"), but it is a change to an existing gate's behaviour and must be stated
as such, not discovered.

**Replacement for FD6's admissibility bullet:**

> A missed control is checked **before** the fake-mode deflect branch and makes
> the run inadmissible: exit non-zero, naming the control and the class. The
> message is the control's, not the generic harness message (`cli.ts:280-286`).
> This applies to every run that loads controls, including the default
> `--fake` self-check, and that is deliberate: C-EVAL@1 §3. The self-check's own
> meaning is unchanged (it still passes when the scorer deflects and the
> controls hold); a missed control is now a second, separately reported reason
> for a non-zero exit. No threshold is relaxed to accommodate it.
