## F1 — the geometry command's outcome is never classified (fail-open)

`runFlow` reads the window with `awaitGuarded(...)`, then consumes the raw fields
directly and never calls `checkCommand` (`model.mjs:684-697`):

```js
const geometry = await awaitGuarded(deadline, clock, () => {
  dispatched.push('getwindowgeometry');
  return ops.windowGeometry();
});
if (!geometry.ok) return finish({ ok: false, reason: geometry.reason });
const raw = geometry.value ?? {};
const window = { id: raw.id, x: Number(raw.x), ... };
if (!Number.isInteger(window.w) || ... ) return finish(...);
```

`checkCommand` exists and is applied to `mousemove` (`:527`), `getmouselocation`
(`:535`) and `click` (`:595`) — but not to `getwindowgeometry`, which the model
itself records as a dispatched command. Proposal §F.1 says: *"Fail closed on
**every** command. … Any signal, any non-zero status, or `XError` in either
stream is an immediate failure naming the command, the status and the line —
before the click is dispatched."* §D.1 names `xdotool getwindowgeometry --shell`
as a command. The model therefore does not prove §F.1.

Reproduced (`docs/v2/evidence/P3.4/proposal-ir6/geometry-command.mjs`):

```
healthy geometry (code 0): ok=true clicked=true
geometry code=1 + stderr:  ok=true clicked=true
geometry XError on stdout: ok=true clicked=true
geometry signal SIGKILL:   ok=true clicked=true
```

A geometry command that exited 1, printed `XError`, or was killed by `SIGKILL`
is accepted as long as the raw fields are numeric, and the row clicks. The
numeric validation catches a command that prints nothing usable, but not a
command that failed *and* printed plausible geometry — exactly the fail-closed
case §F.1 requires. `F11` covers only non-integer geometry, a non-positive pid
and a tiny viewport, never a command outcome.

**Remedy.** Run `checkCommand('getwindowgeometry', geometry.value)` immediately
after the await, before the field validation; add a fixture with a non-zero
status and one with `XError` on the geometry stream.

## F2 — no deadline-raced observation poll; a delayed healthy observation is refused

Every fact read in the flow is a single synchronous `nextFact()` call, or one
one-shot call wrapped in `awaitGuarded`:

- `guardedMove`: `const before = ops.nextFact()` (`:517`) and
  `const fresh = ops.nextFact()` (`:540`), both synchronous;
- `runFlow`: `const viewportFact = ops.nextFact()` (`:699`), synchronous;
- `runClick`: `const before = ops.nextFact()` (`:585`), synchronous, and
  `const after = await awaitGuarded(deadline, clock, () => ops.nextFact())`
  (`:598`) — one read, not a poll.

The contract's "require a fact line" is a wait: §D.4 *"record `ptrN`, dispatch,
then require a fact line whose `ptrN` is strictly greater"*; §D.8 the patient-open
step *"requires a fact line published after the click whose `href` differs"*.
Root lists *"interrupted or late awaits"* among the cases the model must cover.
The model has no such wait, so:

- a **healthy but delayed** observation (the hook publishes on its 250 ms
  change-only poll) is refused immediately, and
- no fixture can make an observation wait consume the immutable deadline, nor
  show a late observation failing to dispatch the next operation.

Reproduced (`docs/v2/evidence/P3.4/proposal-ir6/observation-wait.mjs`):

```
(a) delayed pointer observation: ok=false nextFactCalls=3
    reason=bootstrap 1: ptrN read 0, not strictly greater than 0; no click issued
(b) delayed landing observation: ok=false readsAfterClick=1
    reason=... href did not change ("http://127.0.0.1:7717/")
```

In (a) the new pointer counter is visible on the *second* read after the move;
the model reads once and fails. In (b) the href transition lands on the second
read after the click; the model reads once and fails. The coordinator's concern
is confirmed: `nextFact` is synchronous in these phases and the observation waits
are **not** represented — the fixtures are self-shaped instantaneous queues.
This also means `F4`/`F5` (undelivered `pointermove`) conflate "never delivered"
with "not yet published".

**Remedy.** Model the wait: poll `nextFact()` until the counter advances (or the
landing fact arrives), each attempt raced against the same deadline; add a
delayed-delivery fixture that succeeds, and a missing-observation fixture that
ends at the deadline with no click. The proposal should say in one clause that
the "require a fact line" step is a deadline-bounded wait, not a single read.

## F3 — the solve uses the commanded native point, not the measured read-back

`guardedMove` returns only the client `seen` point (`:561`); the native read-back
it just validated is discarded. `runFlow` then solves from the **commanded**
native points (`:727-730`):

```js
const transform = solveTransform([
  { cx: one.seen.x, cy: one.seen.y, sx: naive.x, sy: naive.y },
  { cx: two.seen.x, cy: two.seen.y, sx: displacement.x, sy: displacement.y },
]);
```

But proposal §A row 2 and the committee resolution both say the calibration is
from **measured** native/client points: §A *"Two measured points → per-axis
affine"*; resolution line 11 *"Calibrate with two distinct measured native/client
points"*. The measured native point is `read.value.X/Y`, not the commanded
`naive`/`displacement`. The ≤1 px read-back tolerance does not make the two
equivalent: it bounds the error, it does not make the commanded point measured.

Reproduced (`docs/v2/evidence/P3.4/proposal-ir6/measured-native.mjs`): two flows
identical except the read-back differs by exactly 1 px (inside tolerance) ask for
the **same** target native point, so the read-back is not what is solved.

```
commanded solve: read-back delta 0 -> target asked {"x":627,"y":653} (ok=true)
commanded solve: read-back delta 1 -> target asked {"x":627,"y":653} (ok=true)
measured solve (sx = commanded + 1) would ask x=628
```

**Remedy.** Return the read-back native point from `guardedMove` and use it as
`sx/sy` in the solve (the proposal's §D.5 is silent on this; state "measured"
there, or reconcile §A and root to "commanded"). Add a fixture whose read-back
differs from the command and assert the solved target moves.

## F4 — a reordered identical duplicate is a false conflict (minor)

The conflict check compares serialized objects (`model.mjs:360-373`):

```js
[...rects].every(([i, f]) => JSON.stringify(previous.rects.get(i)) === JSON.stringify(f))
```

`JSON.stringify` is key-order sensitive, so two **complete** sightings of the
same `(epoch, batch)` with identical field values but a different query-parameter
order are reported as a conflict and the frame fails closed, where root makes an
identical duplicate idempotent. Reproduced
(`docs/v2/evidence/P3.4/proposal-ir6/reordered-duplicate.mjs`):

```
reordered identical duplicate: kind=conflict conflict=SET frame.ok=false
reason=two complete sightings of epoch 2 batch 0 differ
```

The hook's own `sendRects` uses a fixed field order (`8783181:web/src/main.tsx:122-131`),
so this is unlikely in production, but it is a genuine logic gap and it is
untested. **Remedy.** Compare each of the seven fields individually rather than
serializing the object.
