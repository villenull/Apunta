## 1. IR-03 — the leak count is now cumulative over the whole listing

The old `awk` reset its counter inside the record block and `END` printed only
the last record's verdict, so a leak on the first or middle line with any
unrelated line after it exited 0. **The fix is one token moved:** the counter is
now initialised in `BEGIN` beside the token split and is never reset per record.

```
was:  'BEGIN {t=split(toks,A,",")}                  {c=0; for (i=1;i<=NF;i++) … c=1} END {print c+0}'
now:  'BEGIN {t=split(toks,A,","); c=0}             {for (i=1;i<=NF;i++) … c=1} END {print c+0}'
```

Both call sites (the `sources`/`sinks` loop and the two module loops) use the
identical form; no other byte of either `awk` changed, so the **exact token
equality** of the earlier repair is untouched — `$i==A[k]` against the same
`apunta_p35,apunta_p35_mic` and `sink_name=…/source_name=…/master=…` token sets.
No new literal hardware rule, no new device name, no `grep -c` reintroduced.

## 2. IR-05 — the baseline is bound to this attempt and to these three runs

The coordinator's chosen anchor is the checkpoint's **existing** `sandboxRuns`
field — the shape IR-05's own §2 named as the alternative to the `/tmp` env-file
variant, and the field a resumed session needs the run folder name for. This is
**existing restoration provenance, not a new feature assertion**: no new
checkpoint field, no new file, no new requirement on what the implementation
proves about itself.

**What is now specified, in the trap bullet and enforced by the row.** Each of
the three capture runs appends one object to `sandboxRuns` as well as one to
`sideEffectsDone`, carrying **the same four fields — `attempt`, `step`, `runId`,
`dateUtc`** — and nothing else. `attempt` is the implementation attempt number
the checkpoint held when that row wrote the record: an integer `>= 1`, already
the meaning of the checkpoint's own `attempt` in `COORDINATOR.md` §4 and in
`build-dispatch.mjs --attempt` (which defaults to `1`). Nothing is redefined;
the field is made load-bearing. The three steps are exactly `V3`, `V4-tone`,
`V4-silence`, in creation order, and the run ids are distinct — the three
capture runs are three `sandbox.mjs env` invocations on three ports (V3 on
7837, tone on 7837, silence on 7839), so they were never going to collide.

At the checkpoint's own current `attempt` N — a **positive integer**, `0` and a
non-integer both a `FAIL` — V5 now requires all of:

1. exactly one `sandboxRuns` entry per step at attempt N;
2. exactly three `sideEffectsDone` records at attempt N, in creation order
   `V3`, `V4-tone`, `V4-silence`, with three distinct `runId`s;
3. **each record's `attempt`, `step`, `runId` and `dateUtc` equal to that step's
   `sandboxRuns` entry field for field** — the one-to-one anchor, checked on all
   four fields, with a per-mismatch reason naming both values;
4. the live default source equal to the recorded `prevDefault` (unchanged).

**History is kept, never deleted, and never excuses anything.** Records and
entries from earlier attempts stay in the checkpoint exactly as written. V5
excludes them by an explicit `attempt` selection and *prints* how many it
ignored, rather than by deleting, truncating or last-match-fallback. The residue
checks read the live `pactl` listings directly and are not attempt-scoped at
all, so a leak left behind by an earlier attempt is still a `FAIL` on its own
merits — measured: attempt-1 history plus a live source leak exits **1**.

**`dateUtc` is a field that must match, not evidence.** No predicate in this
row sorts by timestamp, takes the last record, or compares a date against "now";
IR-05's clarification is honoured and the paragraph says so explicitly. A record
whose `dateUtc` disagrees with its own `sandboxRuns` entry is a `FAIL`, not a
pass — including when the record's timestamp is *newer*, which is measured and
still exits 1. Freshness is established by the attempt anchor plus the run
anchor, never by a clock.
