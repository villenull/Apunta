### 1 — a parseable-but-wrong-shape manifest or record **crashes** the validator (blocking)

`parseJson` wraps `JSON.parse` (`:265-273`), so unparseable *text* is handled (N17, N19c).
Parseable *shapes* are not: `man.value.schema` (`:290`) and `record.schema` (`:304`) are
read off whatever parsed. Measured against the verbatim core (exit 0):

```
manifest = null                      THREW TypeError: Cannot read properties of null (reading 'schema')
record   = null                      THREW TypeError: Cannot read properties of null (reading 'schema')
build manifest = null                THREW TypeError: names.join is not a function
manifest = []                        rejected  E-SCHEMA          (accidentally fine)
manifest = 3                         rejected  E-SCHEMA
manifest = {"artifacts":null}        rejected  E-MANIFEST-KEYS
record without statuses / statuses:null / build:null   rejected (E-RUN fires first)
```

ir1 finding 5 said a crashing validator is not a failing-closed one, and its correction was
"wrap each `JSON.parse` and return `E-UNPARSEABLE`". That is done, and report §4 marks
finding 5 **Fixed** — but the crash survives for the most obvious malformed shape, so the
header's "each gate failing closed" and §3's "every `JSON.parse` is wrapped" overstate what
the code does. **Minimal fix.** In `parseJson`, reject anything that is not a non-null
non-array object (`E-SCHEMA`), and apply the same shape check to the build manifest before
`build.schema`. One line each; then one adversarial case for `null`.

### 2 — `mintBuild` rewrites the four asset files on every call; only the manifest is immutable (major)

The JSDoc says "Mint one immutable build. Written once with O_EXCL and never mutated
afterwards" (`:141-148`) and the in-function comment says "a build already on disk is
returned AS IT IS, never rewritten" (`:164-166`); report §3 says "Re-minting a build returns
it unchanged rather than rewriting it". Measured: tamper an asset of `b1`, then re-mint —

```
re-mint after an external tamper:  reused = true
asset bytes after re-mint:         "SET UTF-8\n# dictionary-es-mx@2.0.0 aff …"   <- restored
```

The asset writes at `:157-159` use the plain `write()` helper (`writeFileSync`, no flag) and
run **before** the `existsSync(manifestPath)` reuse check, so a re-mint silently repairs a
tampered shared build. It is invisible today only because `ASSET_STUB` is deterministic. It
also undercuts N18's stated reason ("b1 is immutable and shared, so an in-place edit would
silently invalidate every digest"). **Minimal fix.** Write the assets with `flag: 'wx'`, or
on the reuse path re-hash each asset against the manifest and refuse on mismatch — the latter
keeps re-mint idempotent and makes "immutable" a measured property.

### 3 — `\p{M}` is **not** "the same set" as U+0300..U+036F, and the lint reason does not reproduce (major, provenance)

Script comment `:651-652`: "`\\p{M}` rather than an explicit U+0300..U+036F range: **the same
set**"; report §1: "rewritten as **the equivalent** `\\p{M}`". Measured: `\p{M}` matches
U+0483, U+05B0, U+0903, U+093C, U+1AB0 and U+FE0F, all outside U+0300–U+036F — it is a strict
**superset** (every sampled difference, 6/7). For the D-06 sentence the measurement is
unaffected, so the finding stands; the equivalence claim does not.

The stated *cause* is also not reproducible in this repo: `no-misleading-character-class` is
not enabled (`eslint.config.js` uses `js.configs.recommended`, which does not include it;
`grep -n misleading eslint.config.js` → no match), and a file containing
`const A = '[\u0300-\u036F]';` passes `eslint --no-ignore` with **exit 0**. The rewrite may
well be the better code — it is simply not what the report says forced it. **Minimal fix.**
Say "\p{M} is a superset of U+0300–U+036F; identical for the Latin text this clause covers",
and drop the lint justification (or state the rule the repo would need to enable).

### 4 — N19b creates and deletes a path it may not own (major, ownership)

`:572-576` builds `join(SCRATCH, '..', 'foreign-<pid>')` — **outside** the `mkdtemp` root —
with `mkdirSync(..., {recursive:true})` (silent no-op if it exists) and an unconditional
`rmSync(..., {recursive:true, force:true})`, and with no `try/finally`, so a failed assertion
leaks it. Measured: `mkdirSync` on an existing path succeeds silently; after the
proof-style `rmSync` the path and a file placed there by "someone else" are gone. Nothing at
that path exists today, and pid reuse is the only way to collide, so the practical exposure
is small — but it contradicts the script's own "Remove exactly the directory this process
created… Nothing else is ever removed" (`:18-19`) and report §3's "Ownership is exclusive".
**Minimal fix.** `mkdtemp` the foreign folder (so the refusal target is unique to this
process), guard with `existsSync` before adopting, and wrap the removal in `try/finally`.

### 5 — Part A fidelity: the `export PATH=… && OBS=…` prefix is dropped (minor)

The V9 row (`docs/v2/state/S6.1-AMENDMENT-PROPOSAL-v2.md:864`) begins
`export PATH="…" && OBS=/tmp/apunta-v2/s6.1-observed && sort -c -u …`. The proof's `v9`
(`:65-72`) keeps the gates, the `chain`/`n`/`m` arithmetic and the final `test`/`exit $rc`
verbatim, and redirects `OBS` into scratch — but drops the `PATH` export too, so "transcribed
verbatim with only OBS redirected" (report §2) is loose. No gate changes (the prefix is
environment setup and an assignment inside the `&&` chain, which does not affect `chain=$?`).
**Minimal fix.** Say "with the `PATH` export and `OBS` dropped".

### 6 — the third observation copy is sealed but never checked (minor)

`collect` writes `logs/observed-<project>.txt` (`LOG`) alongside the raw record and the
sorted copy; `validate` digest-checks it but never compares it to anything, and
`E-DERIVATION` only relates the record to `evidence/…txt`. Tampering is caught by the digest
walk, so this is not a hole — it is an artefact whose relationship to the record is
undocumented. **Minimal fix.** One line: either drop the file or say what it is for.

`EMITTED_A`/`EN_PAIR`/`ES_PAIR` (`:58-60`) are hardcoded cosmetic names used only by Part A;
fine, but they read like build facts next to genuinely derived ones.
