## IR-04 — DEFECT

- **ID and location:** `docs/v2/cards/P5.2.md`, **Steps** (card 98-103, "retention keeps 3"), read against the **Staging, the destination, and the stamp** bullet (card 82-88) and the Must-not-edit rule that the snapshot destination "must not already exist" (`snapshot.ts:30-36`, quoted into card 31-36).

- **The text that conflicts, or exactly what is missing.** Card 85-88 pins `<utc>` to "`now.toISOString().replace(/[:.]/g, '-')` — which sorts lexically, so 'keep the last 3' is orderable by that stamp." That is millisecond resolution, and the card gives the function **no way to control the clock**: unlike every other timestamped seam in this repo, it names no `now` option. The two precedents the card itself leans on both have one — `CreateBackupOptions.now?: Date` consumed at `archive.ts:82,124`, and `StageRestoreOptions.now?: Date` consumed at `restore.ts:129,169`. The Steps case "retention keeps 3" needs four safety snapshots in one data folder with four orderable stamps, and the natural way to produce them (four copies of the same synthetic v7 database, each migrated) yields the **same** `<from>-<to>` pair, so the filename's only variable is the millisecond. Between two consecutive calls the card's own sequence runs: read-only open, read the version, `mkdir` a staging folder, a SQLite online backup, `PRAGMA integrity_check`, a `rename`, then the retention scan. For a kilobyte fixture on tmpfs that can finish inside one millisecond, and nothing in the card requires it not to.

  So the test either collides or the implementer invents something the card never authorised. I want to be exact about the alternatives, because one of them is legitimate and the others are not: a test may legitimately sleep 2 ms between iterations, or build the four fixtures at four different `<from>` levels so the pairs differ — either makes the case pass, so the case is not *impossible*, and that is why this is a narrow DEFECT and not an UNKNOWN. But the two ways an implementer is most likely to react to the collision are both forbidden by the card's own words: `snapshot.ts:30-36` says "a reused path is a bug in the caller rather than something to paper over by deleting a file that might still be in use", so unlinking the old file is out; and adding a counter or a uuid suffix to the safety name contradicts C-UPD@1 step 3's path (`CONTRACTS.md:212`) and HS-7. Nor is the collision harmless when it happens in production rather than in a test: the staged file is *moved* into `safety/`, and `rename` over an existing file succeeds silently on POSIX, so a second migration inside the same millisecond would quietly replace the older safety snapshot with the newer one — losing a copy the contract exists to keep, and leaving "keep the last 3" counting one file where the owner expects three.

- **One concrete failure scenario.** The implementer writes `safety.ts` with the card's naming and a hard-wired `new Date()`, plus a retention test that loops four synthetic v7 databases in a temp data dir. Iterations 2-4 land in the same millisecond as iteration 1, each `rename` silently overwrites `safety/pre-migrate-7-8-2026-09-26T18-52-07-412Z.db`, and the assertion "keeps 3" sees one file. The implementer cannot fix it inside the card: deleting the destination is forbidden by `snapshot.ts:30-36` and renaming the file is forbidden by C-UPD@1 step 3, and neither `safety.ts`'s signature nor any Fixed decision says a clock may be injected. The row goes back as FAIL on a criterion the card never gave them the means to meet, and burns the round. The same trap, one level up: an implementer who hits the collision in the *snapshot-restores* case (card 102) has the same dead end with the same two forbidden exits.

- **One specific correction or named prerequisite.** Append one sentence to the **Staging, the destination, and the stamp** bullet (card 82-88), verbatim:

  > The exported function takes its inputs as an options object with an optional `now?: Date`, defaulting to `new Date()`, exactly as `CreateBackupOptions` (`archive.ts:82,124`) and `StageRestoreOptions` (`restore.ts:129,169`) do, so a test can give four runs four stamps; the destination-must-not-exist rule (`snapshot.ts:30-36`) stands unchanged, and two runs sharing a `<from>-<to>-<utc>` name is a caller bug to fix at the call site, never by deleting or renaming the file.

  Nothing else in the card needs to move: that one clause gives the retention case a lawful way to be deterministic, keeps the contract's path exactly as C-UPD@1 step 3 fixes it, and leaves the five working cases untouched.
