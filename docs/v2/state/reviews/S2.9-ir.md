## Defects

### D1 — Fixed decision 1 names a lock but not the coordination primitive, and the one shape that would silently not work is the one a reader reaches for first

- **ID and location.** `docs/v2/state/dispatch/S2.9.md`, §Fixed decisions,
  decision 1, third paragraph (`:204-210`); reinforced by V1 (`:313`).
- **The text that conflicts, or exactly what is missing.** The card sanctions
  "a **narrow lock** around the appearance tests only, in `support/fixtures.ts`,
  held for the duration of the test: every spec that writes or asserts the theme
  row takes it, and nothing else in the suite does." It never says *across
  processes*. Playwright runs each test in a worker **process**; with
  `fullyParallel: true` (`playwright.config.ts:85`) and four workers, the three
  racing specs routinely land in three different processes, and I confirmed in
  the installed Playwright that repeats are deliberately spread:
  `playwright/lib/common/index.js:2115` sets
  `test._workerHash = \`${project.id}-${test._poolDigest}-${repeatEachIndex}\``,
  i.e. each repeat is meant for a *different* worker. An in-process `await`
  chain or a module-level promise in `fixtures.ts` would therefore coordinate
  nothing, and the eight tests that must serialise (2 in
  `settings-appearance.spec.ts`, 1 in `workspace.spec.ts`, 5 in `brand.spec.ts`)
  would still overlap.
- **One concrete failure scenario.** The implementer writes the lock as the
  obvious thing — a `let tail = Promise.resolve()` in `fixtures.ts`, or a
  `Map` of in-flight keys — because the card's rationale ("Playwright's `serial`
  mode orders tests **within** a file or block and does not stop another worker
  entering the same row at the same moment") reads as a reason to add *a* lock,
  not as a requirement that it be cross-process. V1 then fails at
  `settings-appearance.spec.ts:39-40` or `:64-65` with exactly the recorded
  theme race, and the honest conclusion — "the sanctioned fix does not work" —
  is wrong. The implementer's next move is to reach for the thing Must-not-edit
  names (`playwright.config.ts:88`), which is Stop condition 2.
- **One specific correction or named prerequisite.** One sentence in decision 1:
  the lock is a **file lock in a path every worker can see** — atomic create
  (`fs.open(path, 'wx')` or `mkdir`), bounded retry, release in fixture
  teardown — not an in-memory mutex, because Playwright workers are separate
  processes. Say where the lock file goes; the only sandbox-legal answer is
  inside a run folder (`/tmp/apunta-v2/<runId>/…`, C-ISO@1 rule 1), and
  `APUNTA_DATA_DIR` is already in every worker's environment
  (`playwright.config.ts:13`). Add the matching half: the fixture must be
  **explicitly requested**, not `{ auto: true }`, because an auto fixture is
  taken by every test in the suite and decision 1 says in so many words that
  "nothing else in the suite does".

### D2 — V1's `--repeat-each=3` puts three copies of the formats test on one server at once, which the sanctioned fix cannot answer

- **ID and location.** `docs/v2/state/dispatch/S2.9.md`, Verification **V1**
  (`:313`); Fixed decision 2 (`:211-220`).
- **The text that conflicts, or exactly what is missing.** V1's expected result
  is "exit 0 on **all four** files, three repetitions each, at 4 workers", and
  its justification is that "`--repeat-each=3` multiplies the exact overlap
  window the races live in". Decision 2 fixes the formats race *only* by
  scoping the assertion: "the count of formats named `Progress note` is exactly
  `before + 1`, and the created row is that one". Scoping the assertion removes
  the interference of **other** specs. It does nothing about interference from
  **another copy of the same test**, and `--repeat-each=3` at 4 workers creates
  exactly that: three independent instances of
  `formats.spec.ts:34` ("is one click from first run …"), all in the `chromium`
  project, all on the one server, all running the same
  `POST`-and-`GET /api/formats` sequence within a second or two of each other.
  Each reads `before` (`:39-40`), each creates one format named
  `Progress note` (`:49-56`), each re-reads and sees **three**. All three fail
  `before + 1`. The scoped assertion is strictly stronger than the global count
  against *foreign* rows, which the card says correctly — it is not stronger
  against its own test's other two copies.
- **One concrete failure scenario.** The implementer does exactly what the card
  says: scopes the count to `Progress note`, scopes `created` to that row, and
  puts the theme lock in the two appearance specs and `workspace.spec.ts` per
  decision 1. V1 is then run. Three workers pick up the three repeats of
  `formats.spec.ts:34`; all three read `before = 0`; all three create; all
  three see 3 and fail. The implementer's available responses are all traps:
  putting a lock on the formats test is not sanctioned by decision 1 ("a narrow
  lock around the appearance tests only" … "nothing else in the suite does"),
  weakening the count is Stop condition 3, `test.describe.configure({ mode:
  'serial' })` on the formats describe would not help because the three copies
  are three *tests*, and Stop condition 3's text ("The formats count cannot be
  scoped without losing an assertion") does not describe what just happened, so
  the natural reading is that the stop condition was missed rather than
  triggered.
- **One specific correction or named prerequisite.** Pick one and write it into
  V1. Cheapest: **drop `--repeat-each=3` for `formats.spec.ts`**, or run V1 as
  two commands — the four files at `--repeat-each=3` for the *theme* racers
  (`settings-appearance.spec.ts`, `workspace.spec.ts`, and `brand.spec.ts`
  added to the list, which V1 currently omits even though decision 1 makes
  `brand.spec.ts` a lock-taker) and `formats.spec.ts` at `--repeat-each=1`. If
  the amplification is kept for `formats.spec.ts` instead, decision 2 must say so
  and sanction the mechanism — and then the lock in D1 is not "around the
  appearance tests only" any more, which is a scope change the owner owns under
  §6, not the coordinator. While there, make decision 2 say that `before` itself
  becomes the scoped count; as written, "the count of formats named `Progress
  note` is exactly `before + 1`" is satisfiable against the *global* `before` at
  `:39-40`, which is the flaky reading, so the sentence as it stands sanctions
  a fix that still fails.

### D3 — The two-server sandbox arrangement in V1 and V3 does not give the es-MX server a port or a data folder, and sourcing order hides it

- **ID and location.** `docs/v2/state/dispatch/S2.9.md`, Verification **V1**
  and **V3** (`:313`, `:315`) and the paragraph under the table (`:318-328`);
  Fixed decision 8 (`:262-272`).
- **The text that conflicts, or exactly what is missing.** Both rows run
  `node scripts/v2/sandbox.mjs env --port <p1> > … && . … && node scripts/v2/
  sandbox.mjs env --port <p2> > … && . … && npm run e2e`, and the paragraph adds
  "the second env's lines must be sourced **after** the first, since both export
  `APUNTA_*` names". Two facts about the repo make that arrangement not do what
  the card says it does. First, `printEnv` exports exactly seven names —
  `APUNTA_DATA_DIR`, `APUNTA_PORT`, `APUNTA_NO_OPEN`, `APUNTA_TEST_RUN_ID`,
  `APUNTA_V2`, `APUNTA_CHECK_URL`, `APUNTA_E2E_PORT`
  (`scripts/v2/sandbox.mjs:301-307`) — and **no `APUNTA_E2E_ES_PORT` and no
  `APUNTA_E2E_ES_DATA_DIR`**, which are precisely the two variables
  `playwright.config.ts:32` and `:34-36` read. Second, sourcing the second env
  last overwrites `APUNTA_E2E_PORT` and `APUNTA_DATA_DIR` with the *second*
  run's values, so the English server lands on `<p2>` and the es-MX server falls
  back to `port + 1` (`playwright.config.ts:32`) and `<dataDir>-es-MX`
  (`:36`). `<p1>` is never used at all. This repo has already found this exact
  trap twice: `reviews/S2.6-ir.md:290-322` filed it as an IR-05 DEFECT and
  `reviews/S2.6-postUI-ir.md:54` recorded that "**one** `env` is correct" and
  that a second env "with `APUNTA_E2E_ES_PORT`/`APUNTA_E2E_ES_DATA_DIR` is the
  documented alternative, not a requirement" — and
  `evidence/S2.6/attempt3-am073-guard-and-navigation.md:109-111` shows what a
  working run actually looks like, with the two `export`s written by hand.
- **One concrete failure scenario.** The coordinator assigns `<p1>=7889` and
  `<p2>=7890`… or more likely `<p1>=7806`, `<p2>=7807`; the implementer runs the
  row verbatim. `<p1>` is never bound. The English server starts on `7807` with
  the second run's data folder; the es-MX server starts on **7808**, a port
  nobody allocated and `assertPortFree` never checked. If the pair is
  `7888`/`7889` the es-MX server starts on **7890** — inside the range C-ISO@1
  rule 2 reserves for the updater test server and the card's own paragraph
  forbids ("never 7717 or 7890-7899"), started by Playwright rather than by the
  wrapper, so nothing refuses it. The run goes green, and the evidence records a
  port that was never used and an es-MX server that was never in a sandbox.
- **One specific correction or named prerequisite.** Either (a) use **one** env
  for both rows — `node scripts/v2/sandbox.mjs env --port <p1> > … && . … && npm
  run e2e` — which is what `playwright.config.ts:28-30` documents as sufficient
  and what S2.8's implementer actually ran (`returns/S2.8.md:46`), the es-MX
  server taking `<p1>+1` and `<runFolder>/data-es-MX`; or (b) keep two envs and
  add the two lines the wrapper will not print, after both are sourced:
  `export APUNTA_E2E_PORT=<p1> APUNTA_DATA_DIR=<run1>/data` and
  `export APUNTA_E2E_ES_PORT=<p2> APUNTA_E2E_ES_DATA_DIR=<run2>/data`, so the
  English server gets the first run's port and folder and the es-MX server the
  second's. Whichever is chosen, the sentence "the second env's lines must be
  sourced after the first" should go or be corrected — as written it is the
  instruction that produces the wrong arrangement.

## Summary

IR-05, IR-07. The card's diagnosis is right and its file list is exactly right:

`settings-appearance.spec.ts` and `workspace.spec.ts:553`, and the global
formats count by precisely `formats.spec.ts:56`, so the five-spec May edit needs
no seventh file and the fix is implementable inside `e2e/support/fixtures.ts`
with no production code touched. Three things would nonetheless strand an
implementer. The lock in Fixed decision 1 is not specified as **cross-process**,
and an in-process mutex is the shape a reader reaches for first — it would
coordinate nothing, V1 would fail with the very race the card exists to remove,
and the tempting next move is `playwright.config.ts:88`, which is Stop
condition 2. V1's `--repeat-each=3` at 4 workers puts three copies of
`formats.spec.ts:34` on one server simultaneously (Playwright deliberately
spreads repeats across workers — `playwright/lib/common/index.js:2115`), and
Fixed decision 2's scoped count cannot answer interference from its own test's
other two copies, so V1's "exit 0 on all four files" is not reachable with the
sanctioned changes; decision 2 should also say that `before` itself becomes the
scoped count, since as written the global `before` is a sanctioned reading. And
the two-`sandbox.mjs env` arrangement in V1 and V3 never gives the es-MX server
a port or a data folder — `printEnv` exports no `APUNTA_E2E_ES_PORT` or
`APUNTA_E2E_ES_DATA_DIR` (`scripts/v2/sandbox.mjs:301-307`), sourcing the second
env last also moves the **English** server onto `<p2>`, `<p1>` is never bound,
and the es-MX server silently falls back to `<p2>+1` — unallocated, unchecked,
and inside the reserved 7890-7899 range if the pair ends at 7888/7889; this
repo has already filed the identical defect at `reviews/S2.6-ir.md:290-322` and
recorded the working one-env form at `reviews/S2.6-postUI-ir.md:54`. V1's
working directory is given twice and both readings break. All four are one-line
repairs to the card text; none touches a threshold, a contract, a May-edit entry
or any production code, and I would expect the owner to authorise them under
§6 as a card repair and a single re-review.
