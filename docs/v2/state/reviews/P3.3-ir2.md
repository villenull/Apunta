### IR-04 — D3: `writeFatal` before `process.exit(75)` is a flush race unless the write is synchronous

- **ID and location.** `docs/v2/cards/P3.3.md:115-129` (the `writeFatal`
  bullet, site 1) against `:232` (V4's `fatal-folder` assertion) and
  `:189-190` (S3's test list).
- **The text that conflicts, or exactly what is missing.** The bullet fixes
  the *order* — `writeFatal('data_folder_in_use')` **before** `process.exit(75)`
  — and the transport — one JSON object on the child's **stdout** — but never
  the write itself. On a pipe, which is exactly what a Tauri child's stdout
  is, Node's `process.stdout` is asynchronous, and `process.exit()` does not
  wait for pending writes: the documented consequence is that a line queued
  immediately before the exit can be discarded. The card does not require
  `fs.writeSync(1, …)` (or any other flush), and the existing
  `console.error` at `index.ts:60` is irrelevant here because it goes to
  stderr, which is unbuffered and which the shell does not read.
- **One concrete failure scenario.** The implementer writes
  `console.log(JSON.stringify({ type: 'fatal', code }))` in
  `server/src/shell-bridge.ts` — the obvious spelling, and the one the card's
  S3 test list would exercise against a captured stream, where it always
  passes. In V4's real `fatal-folder` case the line is queued to a pipe and
  `process.exit(75)` runs in the same tick, so the shell sees a child that
  exited 75 with **no** `fatal` line: the harness's assertion "the fatal line
  arrived on the child's stdout carrying that code and not the other one" fails
  intermittently, and the natural reading is that the bridge is broken rather
  than the write — a defect the next two attempts then chase in the wrong file.
- **One specific correction or named prerequisite.** In the `writeFatal` bullet:
  "the line is written **synchronously** — `writeSync(1, …)` — or the call
  site awaits a flushed write; a `console.log`/`process.stdout.write` followed
  by `process.exit` may be discarded on a pipe, which is precisely the stream
  the shell reads." And in S3's case list, require one test that spawns the
  real writer as a child with a piped stdout, calls it immediately before
  `process.exit`, and asserts the line arrived — so the property is proven by
  a test rather than by a paragraph.
