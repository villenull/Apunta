## 3. Provenance and anchors: five attempt-1 records vs fresh attempt-3 anchors

At HEAD the checkpoint is `attempt: 3`, `status: BLOCKED`, `sandboxRuns` 5,
`sideEffectsDone` 8 (5 `PREV_DEFAULT` objects + 3 prose entries, none naming
`PREV_DEFAULT`), `records at attempt 3: 0`. The V5 program requires **exactly
three** records at attempt N and **exactly one** `sandboxRuns` entry per step at
attempt N, in creation order `V3`, `V4-tone`, `V4-silence`, with matching
`runId`/`dateUtc`, distinct run ids, and the live default source equal to the
recorded `prevDefault`. The five attempt-1 `V3` records and their anchors are
**preserved and excluded by the `attempt === 3` selection** (V5 prints how many
it ignored); earlier history is never deleted.

**The one coordination point — a one-writer handoff.** The harness writes its
record to the run folder (`<sandbox>/p3.5-capture-record.json`) and prints
`RECORD {…}` to stdout; it does **not** write the checkpoint. But V5 reads the
checkpoint and needs the three attempt-3 records to exist before it runs.
Therefore, between V4 and V5, **one writer — the root — must append** the three
`RECORD` objects to `sideEffectsDone` and their four fields
(`attempt`,`step`,`runId`,`dateUtc`) to `sandboxRuns`, in order, from the
harness output. The runtime worker must **not** write the checkpoint; it owns
only evidence and its return. Root and worker must not append in parallel. This
is the card-required durable anchor (the card says `PREV_DEFAULT`/`SINK_ID`/
`SRC_ID` are written to `sideEffectsDone` as each row creates them); it is a
handoff, not a source change, and needs no code fix.
