# Answers to the four questions

## (a) Is the lock correct? **Yes.**

Read at `e2e/support/fixtures.ts:90-237` (the diff adds exactly this block after
`export { expect }` and touches no existing fixture, helper or export line):

- **Cross-process and atomic.** A lock file under `APUNTA_DATA_DIR`
  (`<sandbox>/data/appearance.lock`), taken with `openSync(path, 'wx')` — create
  or `EEXIST`, no read-then-write window. The holder's pid is written at once so
  a waiter can name who is holding it.
- **Bounded retry, with the number.** 50 ms poll against a **20 s** deadline;
  on expiry the waiting test fails with a named message giving the elapsed wait,
  the deadline, the holder's pid and the path. Below Playwright's 30 s default
  test timeout, so a long queue ends with this card's own message.
- **Released in a `finally`, only by the holder.** `releaseAppearanceLock()`
  removes the file it created. All **10 call sites** (8 lock-taking tests + the
  `brand.spec.ts` hook pair) use `try { … } finally { releaseAppearanceLock(); }`
  — verified by grep: 7 pairs in `brand.spec.ts`, 2 in
  `settings-appearance.spec.ts`, 1 in `workspace.spec.ts`. The `afterAll`'s
  release sits after its assertions, never before.
- **Never auto.** It is an exported `acquire`/`release` pair called by name; it
  is not a fixture, so nothing else in the suite takes it. Proof: every V3 run
  took **exactly 20 holds** (8 tests + 2 hook holds, per project, two projects),
  and V1 took exactly 30 (8 × 3 + 2 × 3).
- **Never nested.** A per-process `heldSince` guard throws at once if a worker
  acquires while it already holds, so a test inside `brand.spec.ts`'s describe
  never waits on its own `beforeAll`. No nested-acquire error was produced by
  any run.
- **Two short holds in the `brand.spec.ts` hooks, never one across the
  describe.** `beforeAll` acquires before the `GET /api/settings` read and
  releases right after the `record`; `afterAll` acquires before the restore
  `PUT` and releases after the last per-key assertion. The five tests between
  them each take their own short hold. The only other change in that block is
  hoisting the `settings` const to the describe scope so the `record` after the
  `finally` reads the row the restore left without taking it out of the hold
  that verifies it.
- **No assertion weakened.** Every assertion in the five specs is preserved
  verbatim; the lock windows only re-indent them. `formats.spec.ts` keeps
  `expect(formats).toHaveLength(before.length + 1)` and identifies `created` by
  `id` (`formats.find((f) => !beforeIds.has(f.id))`), with the seven section
  assertions unchanged — strictly stronger than the global count it replaces,
  scoped by `name === 'Progress note'` **and** the seven section names, so
  `workspace.spec.ts`'s four-section `Progress note` row is in neither operand.
- **Measured `H` under the cap.** V1: 661 ms; V3: 678 ms max across the five
  runs; both against the 6 s cap and the 20 s deadline at `W = 4`. No hold was
  narrowed and no deadline, `test.slow()`, retry or config change was needed.

## (c) Is the residual outside S2.9's cause and pre-existing? **Yes, on both counts, for both residuals.**

**The `plan.spec.ts:58` notes-404** is a cross-spec race on shared stored
state, but not the theme row and not the formats count. Its mechanism and its
proof are in (d). Both racing files (`import.spec.ts`,
`halaxy-import.spec.ts`) and the app hook that fires the request
(`web/src/hooks/usePatientRecency.ts`) are byte-identical at the base commit —
neither appears in `git diff --name-only ff31d42..22920ce` — and the
implementer reproduced it at the base with the change reverted and the
appearance and formats changes out of the picture
(`docs/v2/evidence/S2.9/findings.md` §F1). It is outside May edit, and §6
reserves widening to the owner.

**The `spelling.spec.ts:14` failure** is a different, state-dependent flake. It
does not touch the theme row or the formats count, and there is no causal path
from this card's change to it: the change does not touch the speller
(`web/src/lib/speller.ts`), the Add-patient dialog (`web/src/routes/AddPatient.tsx`)
or `spelling.spec.ts`, and the lock is taken only by the eight appearance tests,
never by the spelling test. I characterised it further: run **alone** with
`--repeat-each=5` it still fails 1 of 5, and run alone in a **fresh** sandbox
(new data folder) it passes **6 of 6**. It is therefore an inherent flake that
the V3 design provokes — five consecutive runs in one sandbox accumulate shared
state (hundreds of patients and notes), and with that accumulated state the
Add-patient name field loses its filled value (the field is empty and the
"Add patient" button disabled at assertion time) and the `.misspelt` mark never
appears. The implementer saw it once in 8 change-runs and never in 7 base
runs; at an inherent rate of roughly one in five, 0-of-7 at base is unlucky but
not evidence of a change. It is reported, not touched.

## (d) The notes-404 source spec, pinned.

**The author is the import specs' undo; `plan.spec.ts:58` is the victim, not
the author.**

1. `e2e/tests/import.spec.ts` and `e2e/tests/halaxy-import.spec.ts` create
   patients through the import flow (`POST /api/import/claude/run`,
   `POST /api/import/halaxy`) and delete them again with
   `POST /api/import/batches/<id>/undo`.
2. Every workspace page lists **all** patients in the shared database, and
   `usePatientRecency` (`web/src/hooks/usePatientRecency.ts:56`) fires
   `GET /api/patients/<id>/notes` for **every** listed patient, concurrency 6,
   once per patient per tab. The `catch` swallows the JS failure, but the
   failed HTTP request still logs a browser console error, which the
   `consoleErrors` auto-fixture (`e2e/support/fixtures.ts:70-85`) turns into a
   test failure for whichever test's page made the request.
3. So a page that listed a not-yet-undone imported patient gets a 404 when the
   recency fetch lands after the undo, and the test whose page it was fails —
   in my runs, `plan.spec.ts:58` (chromium in run 2, es-MX in run 4).

The timeline is in run 2's own server log, on the English server:

```
00:54:42.082  POST /api/import/halaxy            ← creates patients (incl. …7ca3)
00:54:42.386  POST /api/import/claude/run        ← creates patients (incl. …7039, …703a)
00:54:42.448  POST /api/import/batches/01a0efce-7dd5-7038-…/undo
00:54:42.553  GET  /api/patients/01a0efce-7dd5-7039-…/notes  → 404   ← recency fetch lands after the undo
00:54:42.554  GET  /api/patients/01a0efce-7dd5-703a-…/notes  → 404
00:54:43.099  POST /api/import/batches/01a0efce-7ca3-70a1-…/undo
00:54:43.124  GET  /api/patients/01a0efce-7ca3-70a2-…/notes  → 404
```

The 404'd patient ids were created by the imports in the same two milliseconds
as the undos that deleted them, and the recency fetches landed 50–100 ms after
the deletes. `plan.spec.ts:58`'s own patient is `uniqueName`'d and is not the
one 404ing; its page is simply the one that held the deleted patients in its
sidebar list. This is the same family the implementer filed as F1, with the
source now pinned to the import undo rather than left as "no identified author".
