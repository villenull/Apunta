## DEFECT details

### IR-04 — D8: V4's `fatal-folder` case puts two processes on one pinned port and never waits for the lock

- **ID and location.** `docs/v2/cards/P3.3.md:268` (V4, the `fatal-folder`
  sentence and the containment sentence), against `:257-259` (three ports
  pinned "rather than substituted"), the `writeFatal` site's own code path at
  `server/src/index.ts:59-62`, and the launch contract V4 cites,
  `docs/v2/cards/P3.1.md:271-279`.
- **The text that conflicts, or exactly what is missing.** V4 now says the
  lock holder is "a **plain server process the harness starts itself, before
  the launch**, on the same `APUNTA_DATA_DIR`: P3.1's bundled server …
  under P3.1's launch contract (`cards/P3.1.md:271-279`: `cd /`, a `PATH`
  holding no host Node, and this run's `APUNTA_DATA_DIR` and
  `APUNTA_PORT`)". Two things follow that the row never says:
  1. **The port cannot be shared.** `fatal-port` puts a dummy listener on
     **this run's `APUNTA_PORT`**, which is 7832, and `fatal-folder` puts a
     *real server that must keep running* on **this run's `APUNTA_PORT`**,
     which is also 7832. Both are described as started "before the launch".
     A server that cannot bind does not hold anything: the holder's own
     `app.listen` fails with `EADDRINUSE`, the card's own new rule at
     `index.ts:155-158` writes `{"type":"fatal","code":"port_in_use"}` to
     *its* stdout — which nobody is reading — and the process exits 1
     without ever releasing the lock.
  2. **Nothing establishes that the holder owns the lock before the app
     launches.** P3.1 solved exactly this in its own harness with the C-ISO
     rule-5 ownership poll, and V4 cites P3.1's *stop* discipline
     (`:280-286`) but not its *wait*. A process started and immediately raced
     loses the race about as often as it wins, and a launch that wins the
     lock is a perfectly healthy app: no `fatal` line, no error screen, and
     the row fails for a reason that has nothing to do with the bridge.
- **One concrete failure scenario.** The implementer writes the two cases as
  the row reads them — `caseFatalPort()` starts the dummy, `caseFatalFolder()`
  starts the holder, and (naturally) both before their launch. The holder
  dies on 7832 and leaves `apunta.lock` with a dead pid. The app launch then
  meets a **stale** lock, which C-OWN@1 rule 3 says to take over atomically —
  so it starts normally, prints `ready`, and shows the app. The harness's
  assertion "the fatal line arrived on the child's stdout carrying that code
  and not the other one" fails, and the natural reading — the one the card
  itself warns about two paragraphs earlier, "the intermittent failure would
  be read as a broken bridge rather than a lost write" — is that the
  `writeFatal` site at `index.ts:59-62` is still wrong. Attempt 2 then edits
  the one file the card says to touch exactly twice, and the card burns a
  third attempt. The compliant escape routes are all closed: the ports are
  pinned, there is no test hook, and the dummy must survive its own
  assertion.
- **One specific correction or named prerequisite.** Two clauses in V4, in the
  same register as the rest of the row: "**the two cases run in sequence and
  the harness stops the `fatal-port` dummy before it starts the lock
  holder, so 7832 is free when the holder binds; and the holder is known to
  own the folder before the app launches — the harness polls the holder's
  `/api/health` for up to 30 s and proceeds only when `testRunId` equals
  `$APUNTA_TEST_RUN_ID`, exactly as C-ISO@1 rule 5 and P3.1's own harness do
  (`cards/P3.1.md:280-286`)**." No new threshold, no new port, no new file and
  no change to `writeFatal`; the containment assertions are untouched and
  remain per-case.
