## 2. Is the V4 case un-vacuous, and can it be built as written?

### 2.1 The vacuity is gone. Confirmed by construction, from source.

The card's requirement 1 forces a bare malformed escape in a **query name**;
requirement 2 forces the `Location` to **parse**. Together those guarantee the
unfixed code throws. Traced from source:

- `describeLocation` wraps only `new URL(raw)` in `try`/`catch`
  (`probe-redirects.mjs:217-238`); anything that parses leaves that branch.
- With a query, the non-unparseable path always calls `queryKeyNames` twice —
  the refusal loop at `:248` and the returned `queryKeys` at `:266`. The
  `allowedQueryKeys.length === 0` shortcut at `:245-246` skips only the *loop*,
  never line `:266`.
- `queryKeyNames` (`:188-199`) splits each pair at its first `=` (`:196`) and
  calls `decodeURIComponent` on the **name** with no `try`/`catch` (`:196`).
  A malformed escape in a name therefore throws `URIError`; a malformed escape
  in a *value* never reaches the decode.

My offline probe (Node v24.19.0, no network, no repository import):

```
node v24.19.0
literal (bare %zz in NAME) starts with https:// ->                             true
new URL(literal) throws?                                                       false
parsed.search                                                                  ?%zz=fabricated-signature-value
decodeURIComponent('%zz')                                                      THREW URIError: URI malformed
new URLSearchParams via .set('%zz') -> search                                  ?%25zz=v
decodeURIComponent('%25zz')                                                    %zz
withQuery(search) as the test file builds it                                   ?%25zz=v
loopback literal parses?                                                       true
'ftp://h/p?%zz=v' parses?                                                      true
name-with-valid-escape-plus-malformed                                          THREW URIError
```

So: a `Location` of the shape the card describes **parses** (line 2 of the
transcript) and its malformed name **throws** (line 4). **I could not construct
a fixture that satisfies requirements 1, 2 and 3 and still passes against the
unfixed code.** Requirement 1 says *name*; requirement 3 says the name must be
present **undecoded** in the result; a `%zz` in a value satisfies neither, and
requirement 3 fails. Requirement 5 additionally demands the control be run.

**M3: resolved on substance** — and it is resolved by the card's own text, not
by the earlier reviewer's phrasing: `:433-439` names the `URLSearchParams` trap
and the mirror-image control at `:437-440`, and `:507-510` makes the control
mandatory.

### 2.2 But the fixture the card orders cannot be built without breaking a prohibition

This is the new MAJOR, and it sits inside the section the amendment added.

| Constraint | Where |
| --- | --- |
| "Build the `Location` as a **literal string constant** whose query name contains a bare malformed escape" | `cards/P4.1.md:442-444` |
| "Assert the `Location` **does** parse — `new URL(...)` does not throw" | `:445-447` |
| "Derive nothing from a catalogue URL for this case" | `:444` |
| "**No URL literal in either file.**" (under "Prohibitions, unchanged and absolute") | `:466-468` |
| "The `.test.mjs` file has no outbound-URL lint exemption" | `:397-399` |
| V3 fails a URL literal and it is "a defect in the script, not a reason to touch `eslint.config.js`" | `:491` |

The rule behind the last two: `eslint.config.js:13`
(`NON_LOOPBACK_URL = /^https?:\/\/(?!127\.0\.0\.1|localhost|\[::1\])/`) wired in
at `:16-28` as `no-restricted-syntax`, applied to `**/*.{ts,tsx,js,mjs}` at
`:89`. The test-file exemption at `:168-172` is
`files: ['**/*.test.{ts,tsx}', 'e2e/**/*.ts']` — **it does not cover `.mjs`**.
So `scripts/v2/probe-redirects.test.mjs` is linted for real, and an
`https://…` string constant in it is an error.

Requirement 2 is what forces the collision: a string that `new URL()` accepts
without a base must be absolute, and an absolute `https://` literal is exactly
what the prohibition and the lint rule forbid. Requirement 1 forbids the two
legal escapes (deriving from the catalogue URL, or building through `URL` /
`URLSearchParams`). The three shapes an implementer would actually try:

1. **A realistic CDN `Location` literal** — `'https://us.aws.cdn.hf.co/…?%zz=…'`.
   Faithful to the defect, passes requirements 1-3, and **fails V3**. (Transcript
   line 1: it does start with `https://`.)
2. **A relative string**, which is what the card's *own attempt-3 paragraph*
   still instructs: "use a fabricated relative string for the malformed case"
   (`:397-399`) — the shape the existing fixture uses
   (`probe-redirects.test.mjs:40-41`) and the one the existing control at
   `:113-115` asserts. It **fails requirement 2** (a bare relative reference
   makes `new URL` throw — which is precisely the `unparseable` branch the
   defect is not in), and it directly contradicts `:445-447`.
3. **A loopback or non-`https`-scheme literal** — `'http://127.0.0.1/p?%zz=v'`
   or `'ftp://h/p?%zz=v'`. Both parse (transcript, last three lines) and are
   lint-clean, so this *works* — but the card never sanctions either, and a
   loopback fixture contradicts the spirit of Fixed decision 6 (`:250-256`,
   "`127.0.0.1` never enters any allow-list") while changing what
   `describeLocation` reports: a non-`https` scheme adds
   `` `scheme_not_https` `` to the `refusals` array (`:240`), so an implementer
   asserting requirement 4's "query verdict is the not-allowed verdict" by
   comparing the array gets a different shape than the card describes.

So the case is *satisfiable* — that is what stops this being impossible — but
only by inventing a fixture shape the card neither names nor sanctions, on the
one point the card itself flags as "**this is the part that is easy to get
wrong**" (`:428-430`).

- **One concrete failure scenario:** the implementer writes the faithful
  `https://…?%zz=…` literal, because requirements 1 and 2 tell them to and
  because the defect is about an https CDN `Location`. V3 goes red on
  `no-restricted-syntax`. The card forbids the only three repairs — derive from
  the catalogue (`:444`), edit `eslint.config.js` (`:468`), weaken the assertion
  (`:445-447`) — so the implementer either invents the loopback fixture on their
  own authority or reports a `FAIL`/stop on a one-function fix.
- **One specific correction, one sentence, coordinator authority:** say in the
  card that the literal may be a **loopback address** (or a scheme the outbound
  rule does not match), that an `https://` literal in either file is forbidden
  and V3 will fail it, and that the attempt-3 sentence at `:397-399` is
  superseded for *this* case. Alternatively state that the requirement-2
  assertion is on a loopback literal and that an accompanying
  `scheme_not_https` refusal is expected. Either closes it; both are card-text
  edits, which HS-9 (`:43-44`) forbids the implementer making.

I checked whether the prohibition might mean "outbound http(s) literal" rather
than "URL literal", which would dissolve the conflict. The card glosses it that
way once — V3's row says a literal "in `scripts/v2/probe-redirects.mjs` fails
`no-restricted-syntax` here" (`:491`) and names only the probe, not the test
file. But the prohibition's own words are "No URL literal in either file"
(`:468`), "either file" being the probe and its test, and the card gives an
implementer no basis to prefer the narrow reading. Given the card spends 30
lines teaching the implementer how not to write a vacuous case, leaving the
shape of the fixture unspecified is the wrong place to be brief.

## 5. Is the fix the right behaviour, and does it change nothing else?

repository already ships rather than against the card's description of it.**

`installer/src/readiness.ts:116-134` `queryParameterNames` is the model: split
at the first `=`, `try { decoded = decodeURIComponent(name) } catch { /* a
malformed escape is left as it arrived: an unreadable name is not a name that
can be on a list, so it fails closed below */ }`, then membership-test
(`:245-249`). The card's wording — "left as it arrived, exactly as
`queryParameterNames` already does — an unreadable name is not a name that can
be on an allow-list, so it fails closed downstream" (`:421-424`) — is a faithful
description of that code, not an invention. The direction is correct for a
second reason: it makes the diagnostic **agree** with the shipped guard rather
than diverge from it.

input the decoded name is identical, so the `Set` de-duplication (`:191-197`),
the `.sort()` (`:198`) and the array return type are untouched. The only
behaviour that changes is the one for an undecodable name, and there the
fallback is a *narrowing*: the raw name is not on `A07_ALLOWED_QUERY_KEYS`
(`installer/src/catalog.ts:121-131`), so `describeLocation:249` refuses it and
`:250` names it — which is what stop condition 2 (`:530-540`) asks a plan editor
to be able to see. `queryKeys` stays an array, so the renderer's `.length` and

path.
