## Proposed mechanical rules

What should be **regenerated, never hand-edited**:

1. **`DEPENDENCIES.md` stays generated.** It is currently correct and that is only because `check-plan.mjs` owns it. Rule: run `node docs/v2/tools/check-plan.mjs` and commit its output in the same commit as any card-header edit; a commit that touches a card header and does not touch `DEPENDENCIES.md` is suspect.
2. **Derive card statuses from the checkpoints, not from a second hand-edited list.** `state/cards/<id>.json` already carries `status` for all 45 cards that have one and it agreed with `PROGRESS.json` on 44 of 45 (only `P3.4` diverged). Make `PROGRESS.json` a generated projection of the checkpoints plus an explicit `parentReviews` map for the 12 `.R` rows, and fail the build when a checkpoint and `PROGRESS.json` disagree. That one rule kills finding 1.1 and makes 1.3 impossible.
3. **Make `BLOCKED.md` generated from the same source as the statuses.** A row should exist for exactly the cards whose status is `BLOCKED`, and a card whose status becomes anything else should have its row deleted by the tool, not by a reader. Never resolve a row by appending a `→ RESOLVED` line: the row is removed, and the resolution is already recorded in `AMENDMENTS.md` (which is where `AM-038`, `AM-049`, `AM-086` and `AM-022` live).
4. **Add the three `BLOCKED.md` rows that are missing** (`S3.2`, `P5.3`, `S6.1`) by hand once, then let rule 3 own them. Three `BLOCKED` cards with no row is the other half of finding 6.1.
5. **Make `OWNER-ACTIONS.md` a table with an explicit status column** (`outstanding` / `satisfied` / `withdrawn`), and require every owner gate named in an `AMENDMENTS.md` row or a `NEXT-SESSION.md` block to have a row — including the sub-actions nested inside a `RESOLVED` line, which is how the `systemctl enable --now ollama` action became unclosable.
6. **Give `AMENDMENTS.md` a continuity check**: ids strictly increasing by 1 from `AM-001`, no duplicates, and every commit token in a "what" resolving in `git rev-list --all`. All three pass today except the `AM-039` gap, so the gap is the only thing the check would have caught.

What should be **checked at the end of every card transition** (`COORDINATOR.md` §3 steps 7 and 8), as one command, run before commit:

7. **Status transition check.** `PROGRESS.json` status == checkpoint `status`, is inside the `RUN-CONFIG.md` §4 vocabulary, and moves only along allowed edges (`NOT STARTED → IN PROGRESS → SUBMITTED → APPROVED`; any of those → `CHANGES REQUESTED` or `BLOCKED`). The `P3.4` case (`NOT STARTED` while the checkpoint said `IN PROGRESS`) is exactly what this catches, and the reverse case — `APPROVED` with no checkpoint — is the same check run the other way.
8. **Blocked-set check.** The set of cards with `BLOCKED` in `PROGRESS.json` equals the set of cards with a row in `BLOCKED.md` equals the set with a row in `OWNER-ACTIONS.md` that is not `satisfied`. One `diff` of three sorted lists.
9. **Dispatchability check.** For the first card in `DEPENDENCIES.md` order whose dependencies are all `APPROVED` and which is not itself `APPROVED`, assert that it is either dispatched, owner-parked with an `OWNER-ACTIONS.md` row, or `BLOCKED` with a `BLOCKED.md` row. Today that card is `P3.4` (correctly in flight), and the check would additionally have surfaced `S4a.2` as a fourth state the schema cannot express — which is why **owner parks need a status word of their own in `RUN-CONFIG.md` §4**, chosen by the coordinator and recorded, rather than a sentence in a handoff file. (I am not proposing the word here.)
10. **Anchor check.** For every `state/cards/*.json`, assert `baseCommit` is a commit that actually modified that card file, and that no later commit touched it. Five anchors have gone stale in this session alone (`AM-123`, `AM-129` D-17, `AM-132`, `AM-133`, and `AM-125`/`d9c38aa`), and `AM-133` currently claims a correction the file does not carry — this single check would have caught all of them, including the one still open on `S3.2`.
11. **Row-to-review check.** For every card `APPROVED` in `PROGRESS.json`, assert a checkpoint exists and its `criteria` hold a `PASS` per verification row id, and that the implementing review file exists. This is finding 1.3 (six approvals with no checkpoint).
12. **Log check.** Assert the newest `AMENDMENTS.md` id is represented in `ORCHESTRATION-LOG.md`. `AM-116`..`AM-133` are not, which is why the log's last word on P3.4 is "attempt 1 has not started".
