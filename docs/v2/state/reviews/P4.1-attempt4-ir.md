## 4. Is the offline V4 case sufficient, and can it be written without fabricating a run?

**Sufficiency: yes, if — and only if — it carries a negative control. Without one
it is not merely weak, it is vacuous.** This is the most important technical
result of this review.

The obvious way to write the fixture reuses the test file's own helper
`withQuery()` (`probe-redirects.test.mjs:70-74`), which goes through
`url.searchParams.set`. **`URLSearchParams` percent-encodes the `%`**, so asking
it for the name `%zz` yields `?%25zz=…` — a perfectly well-formed escape that
decodes cleanly to the *string* `%zz` (my probe, line 7). Against the **unfixed**
code that fixture:

- does not throw (`decodeURIComponent('%25zz')` returns `'%zz'`);
- produces `refusals: ["\`query_key_not_allowed\` — \`%zz\`"]` — which contains
  the literal text `%zz`;
- renders without any query value, because only the *name* was ever materialised.

So assertions 1, 2, 3 and 5 of the proposal's own table
(`P4.1-FOURTH-ATTEMPT-PROPOSAL.md:120-126`) would **all pass with the defect
still present**. A green V4 would certify nothing. The control must be on the
fixture's *raw* escape, not merely on the fixture's parseability:

```js
assert.doesNotThrow(() => new URL(fixture));            // it IS a parseable URL
assert.throws(() => decodeURIComponent('%zz'));          // and the NAME really is malformed
```

which is what the proposal already specifies as its assertion 4
(`P4.1-FOURTH-ATTEMPT-PROPOSAL.md:125`, *"the negative control the existing file
already uses in the other direction at `:113-115`"*). **The file's existing
control is the mirror image — `assert.throws(() => new URL(MALFORMED_LOCATION))`
at `:113-115` — so an implementer copying the neighbouring case verbatim writes
the wrong-direction control, lands in the unparseable branch, and the case passes
without ever reaching `queryKeyNames`.** That is the trap.

**What the case must assert** (the union of AM-064's own terms and the proposal's
five, with the control promoted to mandatory):

1. `assert.doesNotThrow(() => describeLocation(fixture, allowedQueryKeys))`, and
   the record is complete: `unparseable === false`, a real `host`, `refusals`
   containing `` `query_key_not_allowed` `` **naming `%zz`**.
2. The rendered record matches `/query_key_not_allowed/` and contains `%zz` — so
   it fails closed *and* named, which is what stop condition 2 needs.
3. No query value in the rendered text: `!includes(FABRICATED_VALUE)`,
   `!includes(FABRICATED_EXPIRES)`, `doesNotMatch(/Signature=/)`,
   `doesNotMatch(/Expires=/)`, `match(/\?<redacted>/)` — mirroring the existing
   case at `probe-redirects.test.mjs:137-147`.
4. **The negative control, both directions** (above).
5. `fetchCalls === 0` at the end, with the stub installed before the dynamic
   import as the file already does (`:55-61`).

**Fabrication: no.** The case fabricates *input* (HS-8 permits exactly this) and
asserts against pure functions. It must not write, read or assert anything about
`docs/v2/evidence/P4.1/redirects.md` as though a probe run had happened — that
file is the attempt-3 V2 record dated `2026-09-27T23:24:48.835Z`, committed at
`88ef838`, and asserting against it as "this run's output" would be exactly the
false-evidence move V2's row exists to prevent (`P4.1-ir.md:456`, *"The script
wrote the file; a hand-transcribed one is `FAIL`"*). The proposal gets this
right: it scopes the case to `describeLocation` and `renderArtifact` and never to
the evidence file.

**Verdict on Q4: sufficient with the control, vacuous without it — and the
control is the one thing not in the instruction set the implementer will see
(M3).**
