## 3. AM-059 forward-only semantics — ACCEPT

`plans.ts:226` reads `storedLanguage(db)` **once**, before `activatePlan`, and
`:232` persists `msg(locale, 'plan.attestationStatement')`. The already-active
and superseded checks and `resolveClinician(db)` are untouched and still run
first. This is exactly the authorized shape, and it is the right one: activation
is not a generation job, so there is no job context to inherit and reading the
setting at the top of the handler is the whole contract.

Forward-only holds structurally, not by promise:

- The sentence is **written once** and there is no other writer, so no later
  language change can re-word it.
- Nothing reads the setting on the way out. `plan-document.ts` and
  `PlanView.tsx` render `attestation_text` as stored.
- V11 reads the **raw `treatment_plans` row**, not the API, so "unchanged" is a
  statement about the bytes on disk rather than about a read path that happens
  to agree. It also checks `attested_at` is not re-dated, and that **zero rows
  anywhere** hold the Spanish sentence, which is the assertion a backfill would
  fail first.

One design consequence worth naming, which I judge correct rather than a defect:
`storedLanguage` (`server/src/http/locale.ts:59-61`) does **not** consult
`spanishAvailable`. A database that somehow held `language = 'es-MX'` while the
dev switch is off would write a Spanish attestation. That state is unreachable
through `PUT /api/settings` (`settings.ts:84-95` refuses `es-MX` without the
flag), and the card explicitly says to capture `storedLanguage(db)`, so this is
the authorized behaviour and the honest reading of "the language stored". Noted,
not objected to.

## 5. V1's single failure — independent classification

### 5.1 The guard's report is **true**. Do not touch the guard.

Reproduced directly against the matcher:

```
englishMatches('English (United States)') -> [ 'language.en.english:text' ]
englishMatches('Inglés (Estados Unidos)') -> []
```

The two catalogues genuinely disagree about the string `English (United States)`
under the key that the Spanish screen prints as its **English** line. The
identical-value rule is not being evaded; it is correctly declining to fire on
the two keys whose values agree. The report is actionable and correct. No
waiver, no `ALLOWED` entry, no narrowing of V1's screens.

### 5.2 Intended endonym semantics, against the existing contract

The question is what `language.<l>.endonym` and `language.<l>.english` are
*contracted* to mean. The contract is not the card; it is the code the owning
review landed, and it is unambiguous in four independent places:

1. `web/src/components/LanguageDialog.tsx:14-19` — "Each option is the
   language's **own** name for itself with the region, and under it **the name
   in English** — so someone who has landed here in Spanish can still find
   their language from the English line… **The one place they would be
   identical is English, and there the second line is dropped** rather than
   printed twice."
2. `LanguageDialog.tsx:95` — the drop rule is
   `t(english) !== t(endonym)`, i.e. it is written to fire **for English**, in
   **every** locale.
3. `web/src/components/LanguageDialog.test.tsx:64-73` — a committed test named
   *"drops the English line where it would only repeat the endonym"*, asserting
   `language-option-en` is exactly `'English (United States)'`, one line.
4. `shared/src/i18n/es-MX.ts:1229` — `language.es-MX.english` is
   `'Spanish (Mexico)'` in **both** catalogues. The `.english` key's established
   convention is therefore: *it carries the name in English and is never
   translated.*

`language.en.english` in `es-MX.ts` is `'Inglés (Estados Unidos)'` — the only
one of the four keys where that convention is broken. The consequence is not
merely a catalogue inconsistency; it is that **in Spanish the second line is not
in English at all**. The helper line whose entire purpose is to be readable by
someone who does not read the current UI language is printed in that same
language, for the one option where it is needed. And the drop rule at `:95`,
designed to fire for English, does not fire, so the English option prints two
lines in Spanish where the English build prints one.

**Therefore: this is not "changing a translation to evade the English guard".**
It is the reverse. The guard caught a real mistranslation; the repair removes an
incorrect translation and restores the key to the convention its own sibling and
its own component already follow. I checked the direction of the change matters:
making the values *identical* is not a trick to slip past the identical-value
rule — it is what the component's `:95` comparison was written to detect.

I want to be explicit about the line I am not crossing, because it is close: if
the Spanish value had been `'Inglés (Estados Unidos)'` because a translator
believed that was the right string for the second line, the component's comment
and its unit test would both be wrong and the *component* would be the defect.
They are not. The contract is settled and the catalogue is what drifted.

F2 claims `.language-option:disabled { opacity: 0.7 }` makes
`checkVisibility({checkOpacity: true, checkVisibilityCSS: true})` return
`false`, so the walker reads none of a disabled control's text, and it says this
was "measured, not inferred, including an isolated probe".

I reproduced the probe on this box's own browser (`/usr/bin/chromium`,
152.0.7977.82, the executable the card mandates), against a DOM using the app's

```
disabledOption        : true      enabledOption      : true
endonymInDisabled     : true      englishInDisabled  : true
h2                    : true      displayNone        : false
visibilityHidden      : false     opacityZero        : false
walker output: ["English (United States)","Inglés (Estados Unidos)",
                "English (United States)","Inglés (Estados Unidos)",
```

Exit 0. **A sub-1 opacity does not hide an element from `checkVisibility`.**
Only `display:none`, `visibility:hidden` and `opacity:0` return false. The
walker reads every one of the disabled control's strings. The claimed isolated
probe is not reproducible: a bare `<button disabled>` and the app's

Three independent reasons F2 cannot stand as written:

1. **The mechanism is false**, as above.
2. **It is internally inconsistent with its own evidence.** The five "missing"

Consequences:

- The observation underneath (the in-flight reading found fewer strings) may

## 7. The GPU / CPU contamination claim — NOT ACCEPTED

The return says "no inference ran here, so **no model timing is affected**", and
the evidence says "The model executor (`490ebfe8`) holds the GPU throughout".
Neither survives checking:

- **`490ebfe8` is not a process.** `ps -p 490ebfe8` fails with
  `process ID list syntax error` and `/proc/490ebfe8` does not exist. It is
  cited as the identity of the thing whose GPU state the claim rests on.
- **There is no `nvidia-smi` on this host and no `/dev/nvidia*`.** The GPU is
  reached through `/dev/dri` (`card0`, `card1`, `D128`, `D129`). Whatever query
  the author believed it was making, it could not have been an NVIDIA one, and
  "holds the GPU" is not a claim this box's tooling can produce.
- **A model executor was resident across the whole window, and the box was
  oversubscribed.** `ollama` (pid 301080, up 1d15h) and `llama-server`
  (pid 1649535, started 15:33:34, i.e. before and throughout 16:22–17:01) were
  both running. Load average during my own read-only checks was
  **9.07 / 8.42 / 8.16 on 8 cores**. The author's window contained two node
  servers, a chromium, vitest, and a full four-project `tsc` typecheck.

The claim as written is therefore a category error: it reasons from "this
session submitted no GPU work" to "model timing is unaffected". Those are
different propositions. Local model inference on a shared host is sensitive to
CPU contention, host memory bandwidth and power/thermal headroom, and none of
that is zero merely because this session did not enqueue a request. What *is*
true, and all that should be claimed, is the narrower statement: **this session
performed no model inference and produced no model-quality evidence**, so the
coordinator's own model runs remain the instrument and no model number in this
card should be read as re-verified by it.

The four-timezone suites were not re-run, and I accept that decision on its
merits: the only shared-module change is one catalogue key with no placeholder
and no date or zone logic, and the card changes no time code. That argument is
sound and does not need the GPU claim to support it. **Delete the GPU sentence
rather than restating it.**
