## The shape of the thing under review — read this first

**`docs/v2/cards/P3.R.md` does not exist, and that is by design, not a missing
file.** Parent review cards have no card file: `check-plan.mjs:31` walks
`plan.cards` (files in `docs/v2/cards/`) and enforces `Objective`, `Read`,
`May edit`, `Must not edit`, `Verification` only on those; parent reviews are
built by `parseMilestones` (`plan-lib.mjs:114-136`) from a **single row** of
`docs/v2/MILESTONES.md`. I confirmed there is no `docs/v2/cards/*.R.md` in the
repository at all, and that `P0.R`, `P1.R` and `P2.R` — the three already run —
were reviewed the same way, from a generated `docs/v2/state/dispatch/P*.R-review.md`.

So P3.R's entire textual content is:

- `docs/v2/MILESTONES.md:19` — `| P3.R | P3 | Linux desktop shell | L2+L3 | P3.3 V3-V5, P3.4 V2, P3.5 V2-V3, P3.6 V3 on the parent commit |`, plus the preamble's rule that the review "re-runs every child's verification rows on the parent's final commit, then the level below … It never fixes code";
- `docs/v2/DEPENDENCIES.md:53` — depends on `P3.1 … P3.8`, regenerated, not hand-written;
- and, at generation time, **the union of all eight children's verification
  rows**, copied verbatim by `build-dispatch.mjs:97-119`.

**Consequence for this review, and it is the whole method:** P3.R's command
cells are not authored anywhere. They are *machine-copied* from eight child
cards through `parseCard` → `verification[].command` → a GFM table. Anything
that survives a human reading a rendered card but does not survive that
round-trip is invisible to P3.7's own implementer and **fatal to P3.R**, whose
reviewer has nothing but the generated table. Two such defects exist today
(D1, D2) and they are the reason this review is worth running now.

The table header is `| ID | Command (cwd: repo root) | Expected |`
(`docs/v2/cards/P3.3.md:262`, `P3.7.md:236`): cell 0 is the id, **cell 1 is the
command**, cell 2 is the expected result. Every scan below used the parser's
own `[vid, command, expected] = splitRow(line)` assignment, and the header was
read before the non-ASCII sweep for the reason the brief gives.

## DEFECTS — settleable now

### D1 — `P3.7-V3` reaches P3.R as a truncated, syntactically invalid command (IR-03, IR-05)

**Location.** `docs/v2/cards/P3.7.md:240`, the `| V3 |` row. Two shell pipes in
the command are written **unescaped**: `m=$(find "$b/assets" -type f | wc -l)`
and, later, the `… | grep -q … FAIL spa-asset …` predicate. `splitRow`
(`plan-lib.mjs:36-52`) only honours `\|`, so the row parses into **6 logical
cells instead of 3** (`V3` / command / `wc -l); echo "restored-files=…` / empty /
`exit 1; exit $rc` / the real Expected). `parseCard` destructures
`[vid, command, expected]`, so cell 4 — the last half of the negative control,
including `exit $rc` — is silently **discarded**. `build-dispatch.mjs:99-112`
copies `c.verification[].command` verbatim into the parent's table.

**Conflicting text.** `docs/v2/cards/P3.7.md:240` (six cells) versus
`docs/v2/evidence/P3.7/v3.md:19`, which records the *correct* command with both
pipes present and `exit $rc` at the end. P3.7 passed because a human read the
rendered card; `check-plan.mjs:42-49` validates ids, ports, emptiness and nothing
about cell count, so nothing caught it.

**One concrete failure scenario.** P3.R's reviewer copies the inherited
`P3.7-V3` cell into a shell. It ends mid-word at `m=$(find "$b/assets" -type f`
— an unbalanced `$(` — and bash exits 2 before `package-linux-resources.test.sh`
is ever reached. The reviewer records `FAIL` on a correct implementation, or
records `NOT RUN` and moves on, and the parent's only negative control over the
whole SPA-bundle work silently never runs. Either way the row that was designed
to prove `spa-asset` is not vacuous is the row that proves nothing.

**Correction.** Escape both pipes in `P3.7.md:240` as `\|`, and add to
`check-plan.mjs`'s row loop an assertion that every `| V<n> |` line splits into
exactly three cells and that the command cell has an even number of backticks —
so the next card cannot ship the same shape silently.

### D2 — `APUNTA_P31_PORT=<p>` is not the token the generator substitutes, and is a shell syntax error (IR-05)

**Location.** `docs/v2/cards/P3.7.md:239` (V1) and `:240` (V3).

**Conflicting text.** `build-dispatch.mjs:126` substitutes exactly one string:
`body.replaceAll('--port <p>', '--port ' + port)`. Both cells write
`APUNTA_P31_PORT=<p>` — an env-var assignment, not a `--port` argument — so
neither matches and the literal reaches the shell. I ran the shape:
`X=<p> echo hi` gives `bash: line 1: p: No such file or directory`, exit 1,
because `<p` parses as an input redirection from a file named `p`. The
implementer substituted `7841` by hand in both runs and recorded it
(`evidence/P3.7/v1.md:4,15`, `evidence/P3.7/v3.md:4,19`), so the convention is
real and undocumented.

**One concrete failure scenario.** P3.R is dispatched with its own port. Its
reviewer runs the inherited `P3.7-V1`; `bash` tries to read a file called `p` and
the row dies at once. If instead the reviewer "helpfully" substitutes P3.R's
header port, that port is one of the ten P3.R is already reusing across eight
children in one session, and the packaging test's server can collide with a
still-running neighbour from the previous child's row.

**Correction.** Put a literal in-range port in both cells (one no other P3 row
uses), or extend `build-dispatch.mjs:126` to substitute `APUNTA_P31_PORT=<p>`
as well — the second is the better fix, because it makes the placeholder mean
one thing everywhere.

### D4 — three inherited negative guards cannot fire: BRE alternation read as a literal (IR-03)

**Location.** `docs/v2/cards/P3.4.md` row `V3`, both greps, and
`docs/v2/cards/P3.5.md` row `V5`, third predicate.

**Conflicting text.** As parsed (the `\|` correctly unescaped to `|` by
`splitRow`, which is the whole point of that function):

- `grep -rn "invoke_handler|withGlobalTauri\": true" src-tauri/src src-tauri/tauri.conf.json src-tauri/tauri.test.conf.json src-tauri/build.rs`
- `! grep -rn "VITE_APUNTA_TEST_IDENTITY|p3.4-observe" …`
- `pactl list short modules | grep -c 'module-null-sink|module-remap-source'`

All three are **BRE** (no `-E`, no `-e`): in BRE `|` is an ordinary character, so
each pattern is the literal string `a|b`. I proved it rather than asserting it —
against fixtures containing the forbidden text:

| Fixture content | as written (BRE) | same pattern with `-E` |
| --- | --- | --- |
| `invoke_handler\|withGlobalTauri": true` | 0 matches | 1 match |
| `VITE_APUNTA_TEST_IDENTITY\|p3.4-observe` | 0 matches | 1 match |
| `module-null-sink sink_name=apunta_p35` | 0 matches | 1 match |

The card text makes the intent unambiguous — `P3.5.md:626` says "**neither**
`module-null-sink` **nor** `module-remap-source` is loaded", and its own next
sentence says "the row greps for `apunta_p35` in the module arguments, not for
the module name alone", which is a *third* predicate the command does not
contain. `AM-152` D9 already spotted the P3.4 pair by eye and recorded it as a
quote-drift problem; it is worse than drift — the guards are inert. Note the
sign convention is the dangerous one: `P3.4-V3`'s pass condition is *exit 1 from
the first grep*, and a literal pattern exits 1 **always**.

**One concrete failure scenario.** P3.R re-runs `P3.4-V3` on the parent commit
and records "no capability-adjacent config, no test hook reachable from the
release build" — while `src-tauri/build.rs` has grown a
`withGlobalTauri": true` line. The row exits 1, the reviewer writes `PASS`, and
the parent green-lights a Tauri config that exposes the whole IPC surface to
web content. Symmetrically, `P3.5-V5` reports `0` leaked PulseAudio modules
whatever is loaded.

**Correction.** Drop the alternation rather than reaching for `-E` (the brief's
preference, and it keeps the pattern readable in a GFM cell): a loop over words
in each case, e.g. `for w in invoke_handler 'withGlobalTauri": true'; do
grep -rn -- "$w" src-tauri/src src-tauri/tauri.conf.json src-tauri/tauri.test.conf.json src-tauri/build.rs && exit 1; done; exit 1`, and for P3.5 two `grep -c -e module-null-sink -e module-remap-source` predicates over the module arguments with `apunta_p35` in them, matching the sentence the card already writes. If a repair round prefers `grep -E`, that is also acceptable — what is not acceptable is leaving a bare `|` in a BRE.

### D5 — `{{BASE}}` is substituted into the return template only, never into a borrowed row or its Expected cell (IR-05)

**Location.** `docs/v2/tools/build-dispatch.mjs:86-92` (`fill`), `:100-119`
(parent body assembled), `:154-162` (`fill` applied to the **return-file
template**), `:197` (the body is emitted un-`fill`ed). Then
`docs/v2/cards/P3.6.md:397` (V3, Expected) and `docs/v2/cards/P3.7.md:239`
(V2, Expected), both of which P3.R inherits verbatim.

**Conflicting text.** `P3.6.md`'s Expected cell instructs the reader to run
"the primary predicates `git diff --name-only {{BASE}}...HEAD` … where `{{BASE}}`
must be written exactly like that and never as `<base>`", and explains at length
that the angle-bracket form "reaches git as a pathspec that matches nothing, the
diff comes back empty, and the predicate **passes vacuously**". The three ASCII
dots are there — AM-152 D8 is closed. But the token itself is not substituted in
a parent review: the same argument `fill()` satisfies for a card's own dispatch
is not applied to the body a parent borrows, so P3.R's `P3.6-V3` and `P3.7-V2`
cells contain the literal string `{{BASE}}`. `git diff --name-only {{BASE}}...HEAD`

**One concrete failure scenario.** The P3.R reviewer obeys the Expected cell
verbatim. `git` exits 128 with `fatal: bad revision`, the `&&` chain aborts, and
the freshness predicate — the one thing P3.6's V3 exists to prove — is neither
run nor reported; a reviewer who instead shrugs and runs `git diff --name-only
HEAD` gets an empty list and concludes the bundle is fresh. Either way the
staleness check the row was written for is absent from the parent's report.

**Correction.** One line in `build-dispatch.mjs`: apply `fill(body)` after the
body is assembled and before `:197` emits it, so borrowed rows and Expected cells
get the same substitution as the return template. Failing that, reword both
Expected cells to "the dispatch's **Base commit**" and name no token. I checked
the blast radius first: across all 70 cards only `P4.5-V3`, `S2.11-V1` and
`S2.11-V3` carry `{{BASE}}` in a **command** column, and **no P3 row does**, so
no P3.R row fails to execute because of this — it is a stale-readable-instruction
defect for two rows, not a cannot-run one.

### D6 — P3.R inherits the `.AppImage` counting collision, in five rows rather than one (IR-02, IR-10)

This is the question the brief asked me to answer directly, and the answer is
**yes, and AM-152's note understates it**.

**The mechanism, read from source.** `scripts/v2/tauri-lifecycle.test.mjs:88-94`:

```js
const found = readdirSync(dir).filter((name) => name.endsWith('.AppImage'));
if (found.length === 0) return { error: `no .AppImage in …` };
// …and
return { error: `${found.length} .AppImage files in …: ${found.join(', ')}` };
```

`scripts/v2/tauri-security.test.mjs:262-268` is the same function, same refusal.
Both look in `src-tauri/target/release/bundle/appimage/`. P3.6's `V1`
(`P3.6.md:397`) builds `Apunta_<version>_amd64.AppImage` — **the production
identity** — into that same directory, and counts only `Apunta_*.AppImage` so it
is safe against the test image; nothing in any P3 card removes the production
file afterwards (I grepped every P3 card for `rm -rf …bundle` / `rm -f …AppImage`:
no card cleans it). P3.6's own rows dodge the collision by scoping their own
launch to `'Apunta (test)_'*.AppImage`, which is right and is not inherited by
anyone else.

**Who inherits it.** `build-dispatch.mjs:98-99` gives P3.R *every* row of *every*
child, and `MILESTONES.md:19` additionally names `P3.3 V3-V5` and `P3.4 V2` as
extra checks. So on the parent's commit, after P3.6 has run at least once — and
P3.R only becomes dispatchable after P3.6 is `APPROVED` — **at least five rows
refuse on a bookkeeping fact, not on behaviour**: `P3.3-V3`, `P3.3-V4`,
`P3.3-V5`, `P3.4-V2`, and `P3.5-V3` (whose card repeats the "zero-or-many a
failure" resolution in prose). P3.R is also the one session that runs them **all
in one working tree**, so it is the card where the two identities are guaranteed
to be side by side. Row order does not save it: the children are emitted
P3.1, P3.2, P3.3, … so P3.3's rows run *before* P3.6's `V1` inside P3.R, but the
production image from P3.6's own implementation run is already in the tree.

**One concrete failure scenario.** P3.R runs `P3.3-V3`. `resolveAppImage()`
returns `2 .AppImage files in src-tauri/target/release/bundle/appimage: Apunta
(test)_0.0.0_amd64.AppImage, Apunta_0.1.0_amd64.AppImage`, the harness exits
non-zero, and the reviewer records `FAIL` on the launch/lifecycle suite — the
single most important row in the parent — for a reason that has nothing to do
with the implementation under review. Worse, the natural reviewer reaction, to
delete the "extra" file, deletes the production artefact P3.6 exists to produce.

**Correction — and P3.R does need a change; AM-152's note does not suffice.**
P3.3 and P3.4 are both `APPROVED` and neither has the harness in its May edit,
so no existing card will ever fix this; it has to be fixed in P3.R's own
instruction or in the harnesses under a new card. Cheapest correct fix, and the
one that needs no new card: P3.R's instruction carries a **precondition row** —
before the test-identity rows, move `src-tauri/target/release/bundle/appimage/Apunta_*_amd64.AppImage`

## Non-defect notes

1. **Alternation in P3 command cells is *not* unsafe here, and the premise in
   the brief needs one correction.** `splitRow` unescapes `\|` → `|` when parsing
   a card (`plan-lib.mjs:42-44`) and `build-dispatch.mjs:111` re-escapes `|` → `\|`
   when writing a parent's table, so a card **can** hold a real alternation; the
   round trip is sound. The dangerous part is narrower and sharper than "a card
   cannot hold alternation": **a card cannot hold alternation in a BRE**, because
   nothing in the toolchain knows which of the three grep flavours a cell uses.
   That is exactly D4. My sweep found five alternation sites across all eight P3
   children: `P3.4-V3` ×2, `P3.5-V5` ×1 (all BRE, all inert — D4) and
   `P3.8-V4` ×2, both correctly written as `grep -Eq`.
2. **Non-ASCII in P3 command columns: 12 occurrences, all harmless, verified
   individually.** Every one is either inside a double-quoted `echo` string
   (`P3.7-V3`'s `STOP: before-list is empty — …`; `P3.8-V4`'s four
   `NOT RUN`/`FAIL` messages) or in prose that sits in the command cell *after*
   the closing backtick (`P3.6-V3` U+2014/U+2192, `P3.8-V3`/`V4`'s parenthetical
   notes). **No non-ASCII byte appears in a path, a glob, a regex, or an unquoted
   argument** — which is the only way it could change a command's meaning. The
   AM-152 ellipsis (`U+2026`) does not appear in any P3 command cell; the
   separator in `P3.6-V3` is three ASCII full stops, confirmed at the byte level.
3. **`bash -n` inventory.** 34 command cells across the eight children. 32 parse
   clean. Two do not, and both are findings above: `P3.7-V3` (whole-cell, exit 2,
   "unexpected EOF" — the truncated cell, D1) and `P3.1-V4` (odd backtick count,
   exit 2 — see note 4). Six cells mix code and prose (`P3.6-V3` with 12 spans,
   `P3.8-V1` 2, `P3.8-V3` 4, `P3.8-V4` 4); in each the code span parses clean on
   its own, which is how they have been read and run.

   command cell opens with a backtick and never closes it, so GFM renders the
   rest of the row as code and a copy-paste carries a trailing backtick. Stripped
   of that one character the command is syntactically valid and is P3.1's own
   lane on an `APPROVED` card. Cosmetic, recorded, not filed as a defect — and it
   is the same `cells/backticks` assertion D1 asks for that would catch it.
