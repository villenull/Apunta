## B1 — BLOCKER — §T.1(b) is not byte-identical, and test 5 is written against a false claim

§T.1(b) says, of its own after-text: "For attempt 4 this expands to the existing
sentence **byte for byte**". It does not. Evaluated with `attempt = 4`,
`exception = 'AM-049'`, `id = 'P3.4'`:

```
BEFORE: - Attempt 4 of 3, plus one corrective attempt the owner authorised by AM-049 — there is no attempt 5. Checkpoint: `docs/v2/state/cards/P3.4.json`.
AFTER : - Attempt 4 of 3, plus 1 corrective attempt(s) the owner authorised by AM-049 — there is no attempt 5. Checkpoint: `docs/v2/state/cards/P3.4.json`.
identical: false
```

Two substitutions: `one` → `1`, and `attempt` → `attempt(s)`. The proposed
after-text is `attempt - 3` + a fixed `corrective attempt(s)`, so it cannot
produce the English the AM-049/AM-064 precedent already put in two shipped
dispatch documents.

§T.2 **test 5** is then specified as asserting "the attempt line is byte-identical
to what it says today — the existing precedent cannot regress". Run against
§T.1(b) as written, that test **fails**. So the tooling grant ships a required
regression test that its own patch breaks. That is the same class of failure as
IR-03 (a check that cannot pass) and it is the single most load-bearing claim in
§T: the whole point of the guard change is that nothing that exists today moves.

**Exact remedy — make §T.1(b) branch per attempt, with the existing literal
preserved:**

```js
// build-dispatch.mjs:344
    `- Attempt ${attempt} of ${
      attempt === 4
        ? '3, plus one corrective attempt the owner authorised by ' + exception + ' — there is no attempt 5'
        : attempt === 5
          ? '3, plus two corrective attempts the owner authorised by ' + exception + ' — there is no attempt 6'
          : '3'
    }. Checkpoint: \`docs/v2/state/cards/${id}.json\`.`,
```

With that, attempt 4 is byte-identical (so test 5 passes as written and the
precedent cannot regress), attempt 5 reads as the parallel sentence an owner
reading AM-049 and AM-064 expects, and the claim in §T.1(b)'s prose becomes
true. **If the coordinator prefers the arithmetic form**, then §T.1(b)'s
"byte for byte" sentence must be deleted and §T.2 test 5 must be rewritten to
assert the *new* literal rather than today's — but that gives up the regression
guarantee, which is the only reason the test exists. The branching form is the
one to take.

## D1 — DEFECT — §E's completeness rule cannot see a mid-publication frame

§E asserts the completeness loop makes "**stale or mixed frames are never
selectable**". It does not. `readObservations` accumulates batches in a map that
lives for the whole run, and the hook's `sendRects` republishes **all** batches
whenever the rectangle signature changes — but as **separate `fetch` requests**,
so a read taken mid-publication sees some batches from the new frame and some
still holding the previous frame's values. The stated rule checks only that
batches `0 .. ceil(total/40) − 1` are present and that all of them declare the
**same `total`**. A hover that inserts and removes a text leaf keeps `total`
unchanged, so that frame passes the rule while being a mixture.

This is the exact defect §E exists to remove, one level down: the old code read a
partial frame as an absence; the new code can read a *mixed* frame as complete.

It is largely mitigated downstream — §C.2 step 9 re-reads the target rectangle
after the warp and re-warps once if it moved — so this is not a blocker to the
owner's decision. But the sentence "never selectable" must not ship.

**Exact remedy — give every batch of one publication a nonce, and require the
nonces to agree.** In `sendRects` (`web/src/main.tsx:118-128`), add
`query.set('frame', frameNonce)` inside the batch loop with a single nonce per
`sendRects` call; in the harness's batch loop, collect `frame` per batch;
replace "all declaring the **same** `total`" with "all declaring the **same**
`total` **and the same `frame`**, and every batch of that `frame` present". A
mixture then fails the rule and the read restarts, exactly as a `total` change
does. This adds one query parameter inside the existing gate and changes no
publication rule (AM-138 is honoured: *which* rectangles are published is
untouched, and the cap, the 1–64 bound, the text-leaf rule and the batch size
are all untouched). And delete "**stale or mixed frames are never selectable**",
replacing it with "a frame is complete only when every batch of one publication
is present; a mixture is not a frame".

## D2 — DEFECT — bootstrap failures are classified two different ways

§C.2 step 4 makes the bootstrap point's failure a named `NOT RUN`. §C.2 step 8
then says containment "applies from the **second** move onward" — so the *second*
bootstrap move, which is a displacement `(X₁ + Δcx, Y₁ + Δcy)` from an
untransformed first point, is subject to containment and **FAILs** if it lands
outside the window. With the step-3 targets that displacement is
`≈0.25·vpW` in x and `≈0.10·vpH` in y; at `k = 1` on the requested `1280×860`
inner geometry it stays inside, but the first point is the naive 1:1 guess and
`k` is not yet known, so there is no guarantee.

An implementer must choose, and the two choices are `NOT RUN` (calibration
diagnostic, consistent with step 4) and `FAIL` (a safety failure on a point the
method itself asked for). Pick the first and say so.

**Exact remedy — append to §C.2 step 8:** "The step-4 bootstrap's **second** move
is part of the bootstrap, so a containment violation there is the same named
`NOT RUN` as the first move's missing `pointermove` — 'the second bootstrap
displacement left the window rectangle' — and **no click is issued**. Containment
as a `FAIL` begins with the first point computed through the solved transform
(the step-9 click point)."

## D6 — DEFECT (minor) — no bound on the pointer-frame freshness wait

§C.2 step 5 says to "wait for a fact line whose `ptrN` is **strictly greater**",
and step 10 requires `clickN` to advance by exactly 1. Both are the right
instruments. Neither is given a timeout, and §C.2 step 11 forbids "widening of
the 30 s window" without saying what bound applies to the calibration waits. An
implementer will pick one, and the choice is not neutral: a wait long enough to
be safe on a slow warp is a wait that turns IR-19 (synthetic motion may never
reach the page) into a long hang rather than a prompt named `NOT RUN`.

**Exact remedy — one sentence in §C.2 step 5:** "Each freshness wait is bounded
at **10 s**, inside the row's existing 45 s first-fact window and **not** inside
any widened click window; a wait that expires is the step's named `NOT RUN` with
the count of pointermoves it did see, and **no click is issued**."
