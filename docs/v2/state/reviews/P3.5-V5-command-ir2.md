## IR-03 — **DEFECT (blocker 1)** — the residue count is a *last-line* predicate, not a count

Coordinator finding, independently reproduced: the shipped `awk` resets its
counter on **every record** and `END` prints only the final line's result.

```
awk -v toks=apunta_p35,apunta_p35_mic 'BEGIN{t=split(toks,A,",")} {c=0; for(i=1;i<=NF;i++) for(k=1;k<=t;k++) if($i==A[k]) c=1} END{print c+0}' <file>
```

Whole-row replay of the extracted command, fake `pactl`, clean baseline:

| Fixture | Row exit | Correct |
| --- | --- | --- |
| clean, unrelated `module-null-sink sink_name=other_sink` and `module-remap-source source_name=other_mic` loaded | **0** | yes |
| `apunta_p35_mic` in sources, **first** line, unrelated sources after | **0** | **no — false pass** |
| `apunta_p35_mic` in sources, **middle** line | **0** | **no — false pass** |
| `apunta_p35_mic` in sources, **last** line | 1 (names the line) | yes |
| `apunta_p35` in sinks, **first** line | **0** | **no — false pass** |
| `apunta_p35` in sinks, last line | 1 | yes |
| `module-null-sink sink_name=apunta_p35` **first**, unrelated null sink after | **0** | **no — false pass** |
| the same module, last line | 1 | yes |
| unrelated names containing the substring (`other_apunta_p35_helper`, `source_name=apunta_p35_mic_backup`) | 0 | yes (IR-09.2 closed) |

Two things make this a blocker rather than a note.

1. **It is a regression against `7220507`.** The previous row counted with
   `grep -cF -e apunta_p35 "$b/$l"`, i.e. over **all** lines. Replaying the old
   cell against the leak-first fixture: **OLD ROW EXIT=1**, against the same
   fixture the new cell exits **0**. So the repair that removed IR-09.2's
   substring false-`FAIL` bought it with a false **pass** in the only *outside*
   witness the card has for its host-global cleanup obligation (V3/V4 assert
   teardown from inside the harness, i.e. from their own bookkeeping). HS-7 is
   about loosening an instrument to make a result pass; nobody intended this,
   but the effect is the same class and the direction is the dangerous one.
2. **The exposure is the case the row exists for.** The residue is missed
   whenever any unrelated line of the same listing follows ours: a Bluetooth
   headset paired after the run, a USB microphone re-enumerated, another
   application's `module-null-sink`. A leak from an **earlier attempt** is by
   construction the *oldest* such line, so precisely the resumed-session leak the
   card's stop condition warns about is the one this predicate can miss.

The Expected cell is explicit — "`pactl list short sources | grep -c apunta_p35`
is `0`" — so the shipped form does not implement the cell it sits in.

**Minimal fix, one token, no new criterion, no hardware name, no new microphone
action:** initialise the counter in `BEGIN` and never reset it inside the record
block — `BEGIN {t=split(toks,A,","); c=0} {for (i=1;i<=NF;i++) for (k=1;k<=t;k++) if ($i==A[k]) c=1} END {print c+0}`. Measured in evidence §D: leak-first, leak-middle and leak-last all become `1`; the empty listings and the unrelated `other_apunta_p35_helper` names stay `0`.

## IR-05 — **DEFECT (blocker 2)** — the baseline is not bound to this attempt, and not to this run's captures

The durable-record *shape* is well judged and the fail-closed list is real: I
replayed all of it and every malformed, ambiguous, contaminated, absent and
disagreeing case fails with its own message — `[]`, a non-array, a bare-string
JSON, unparseable JSON, a prose entry naming `PREV_DEFAULT`, four records,
duplicate `step`, duplicate `runId`, empty `runId`, unknown `step`, empty /
padded / multi-line / contaminated `prevDefault`, a missing `sinkId`/`srcId`, and
three records that disagree. Unrelated entries (a prose note, a P3.3-shaped
object) are ignored, not rejected. The record-precedent argument (P3.3's one
structured object) is sound, and "a free-form entry naming `PREV_DEFAULT` is
itself a `FAIL`" is the right call.

What the shape does **not** do is answer the provenance question, and it is
answerable:

```
grep -c "APUNTA_TEST_RUN_ID\|v3.env\|v4-tone.env\|v4-silence.env\|dateUtc\|attempt" <decoded command>
0
```

The command never reads `attempt`, never reads `dateUtc`, never looks at any env
file, and never compares a `runId` with anything outside the JSON it is already
reading. `runId` is checked only for **non-emptiness and mutual distinctness**.
The card's new paragraph claims `runId` "is what distinguishes this run's
pre-state from an earlier attempt's"; the command implements "three distinct
non-empty strings".

Reproduced, exactly as the coordinator found it:

| Branch | Row exit | Should be |
| --- | --- | --- |
| **A18** checkpoint `attempt: 2`, three **stale** records (`old-run-0/1/2`, `dateUtc` 2026-09-01), `prevDefault` equal to the current default | **0** | **1** |
| A20 the same, with `old-run-*` run ids from an unrelated run | **0** | **1** |
| A21 records that carry `attempt: 1` while the checkpoint says `2` — the field is ignored entirely | **0** | **1** |
| A18b records with no `attempt` field at all | **0** | **1** |
| A19 the same three records in permuted order (`V4-silence`, `V3`, `V4-tone`) | **0** | 1 — the card says "appended in creation order" and the report leans on "the last of them is V4-silence's" |
| A22 records with no `dateUtc` at all, though the paragraph requires it | **0** | 1 |
| A15 a stale set whose value no longer matches the live default | 1 | yes (the one staleness case the current code does catch) |

So a **stale COMPLETE set from an earlier attempt whose `prevDefault` happens to
equal the current default passes as this run's original pre-state.** The
author's §4 is honest that this residual exists and that closing it "needs an
attempt anchor in the checkpoint schema"; I disagree with the conclusion that it
is outside reach, because the anchor field already exists and no schema *meaning*
changes (see the proposal).

One clarification about a phrase that should not be inherited: **no predicate
anywhere sorts by timestamp or takes "the last record".** The row uses a `Set`
of steps, so there is no date-order reasoning to audit, and no universal
"stale because older" claim to make. The defect is the opposite one — the row
considers *no* freshness evidence at all.

**Minimal attempt-bound record and expected run identity, inside the existing
obligations.** Three additions to the card's new paragraph and to the `node`
block, prototyped in scratch (evidence §E) and measured on all the branches
above:

1. **Attempt anchor (closes A18, A20, A21, A18b).** Each record carries
   `attempt`, the integer `attempt` the checkpoint held when the row wrote it;
   V5 requires `j.attempt` to be a number `>= 1` and every record's `attempt` to
   equal it, failing closed otherwise ("the baseline was recorded by attempt N,
   this dispatch is attempt M"). `attempt` is already a field of
   `templates/CHECKPOINT.json`, already in `P3.5.json`, and already means "the
   implementation attempt" in `COORDINATOR.md` §4 and in `build-dispatch.mjs`
   (`--attempt`, budget 3). Nothing is redefined; the field is simply made
   load-bearing instead of decorative.
2. **Run identity (closes A18's "any three ids" half, and A24).** Each record
   carries the env file its own row already writes — the literal
   `/tmp/apunta-v2-p3.5-v3.env`, `-v4-tone.env`, `-v4-silence.env` from the V3
   and V4 command cells — and V5 reads `APUNTA_TEST_RUN_ID` out of that file and
   requires it to equal the record's `runId`, failing closed if the file is
   absent or does not carry the variable. This is a read of the card's own
   scratch; no device is touched and no host-specific name appears. If the
   coordinator judges a `/tmp` dependency too fragile for a cleanup witness, the
   equivalent inside the checkpoint is to require the three `runId`s to appear in
   the checkpoint's own `sandboxRuns` entries (whose run-folder names embed the
   run id, `P3.4.json:79-81`); that variant needs a shape decision on
   `sandboxRuns`, which today is free-form prose, so I recommend the env-file
   variant.
3. **Creation order (closes A19).** Require `recs[i].step === ["V3","V4-tone",
   "V4-silence"][i]`. Two tokens, and it makes the report's "the value V5
   compares against is the one the final teardown was required to re-apply"
   actually true rather than asserted.

With 1 and 2 the false pass needs a stale set **and** an unchanged host default
**and** a teardown that silently failed — three conditions, one of which the row
can now see. With 1 alone it needs two. All of it is inside the card's own May
edit (`docs/v2/state/cards/P3.5.json` is listed) and inside the trap bullet's
existing recording duty.

## Verdict and blockers

**DEFECT. Not approved. No P3.5 implementation, audio row, model download or
microphone action is authorised by this review.** Attempt budget unchanged: no
implementation has run and an instruction review spends no attempt.

Blockers, both inside the V5 row:

1. **IR-03** — residue detection is order-dependent and is a **regression**
   against `7220507`. Fix: initialise the `awk` counter in `BEGIN` and never

   host default is unchanged. Fix: `attempt` on each record compared with the
   checkpoint's own `attempt` (failing closed on `0`/absent), each `runId`
   checked against the `APUNTA_TEST_RUN_ID` in its own row's env file (or, if the
   coordinator prefers, against the checkpoint's `sandboxRuns`), and records
   required in creation order. Then bring the added paragraph's three
   over-claims into line with what the command checks.

Non-blocking, unchanged from the earlier rounds: IR-09.1 (Expected quotations),
IR-09.2 now closed.

**Boundaries.** No owner decision is required for either blocker: nothing here
changes a contract, a threshold, a protected grant, a port or a stop condition,

three field comparisons inside the card's own May edit, against the run's own
