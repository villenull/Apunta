## The three earlier findings, independently re-checked

**D1 — partially fixed; the correction introduced a worse defect (F1).** The
source-shape requirement is **correct and sufficient**, and I confirmed it
independently rather than taking it on trust:

- The type-stripping case is real and the card names it correctly. The evidence
  is `scripts/v2/sandbox.mjs:46-48`: the wrapper imports
  `shared/src/platform-paths.ts` directly and comments "Node 24 strips the
  annotations". Under stripping, `declare const __APUNTA_VERSION__: string;` has
  no initializer and is erased, so the *only* safe access is
  `typeof __APUNTA_VERSION__`, which returns `"undefined"` for an undeclared
  identifier and therefore never throws. A bare reference throws
  `ReferenceError` in precisely the case the card names. The required shape is
  the one that survives, and it is the only one that does.
- Nothing in the card contradicts the source-execution fallback requirement. The
  two readers resolve to the same file from both execution shapes —
  `config.ts:12` `'../package.json'` and `data-lock.ts:53`
  `'../../package.json'` are two levels up from `src/` and from `dist/` alike
  (the comments at `config.ts:14` and `data-lock.ts:51-52` say so), so from tsx,
  from `server/dist`, and from Node's stripped `.ts` the fallback yields
  `server/package.json`'s `0.0.0` — identical to today's behaviour and to
  health's current `version` (`health.ts:107` ← `config.ts:175`). "Lazy" is the
  right word for the fallback and is load-bearing: today `pkg` is a module-level
  const (`config.ts:11-12`, `data-lock.ts:50-53`), so an esbuild that inlines it
  travels with the bundle — the exact failure D1 was about.
- **The replacement fingerprint is the problem (F1).** It cannot pass, and its
  stated justification reasons about the repository when the check runs against
  a bundle of `node_modules`.

**D2 — fixed, and the fix is genuinely strong. I traced the real ordering and
attacked it; it holds.** IR-07 CLEAR.

- Ordering, in the committed source: `server/src/index.ts:32` `ensureDataDir` →
  `:33` `acquireDataFolderLock` → `:34` `applyPendingRestore` → `:41`
  `prepareDatabaseForStart` → `:47` `openDatabase` → catch at `:52` → `:71`
  `serveBootError` → `server/src/boot-error.ts:82` `app.listen`. This matches
  C-OWN@1 rule 1 (`docs/v2/CONTRACTS.md:182-184`) exactly, and it is the *same*
  order the production path uses. **There is no window in which `/api/health`
  can answer before the lock is written** — `acquireDataFolderLock` is
  synchronous and completes (including its `link()`-based atomic create,
  `data-lock.ts:263-274`) before the first `await` on the failure path.
- The lock's contents are the contract's: `{pid, processStart, appVersion,
  protocol, nonce}` (`data-lock.ts:58-64,323-329`; C-OWN@1 rule 2 at
  `CONTRACTS.md:185-186`), file name `apunta.lock` (`:45`).
- The start-time comparison checks what the card claims.
  `linuxProcessStart` (`data-lock.ts:110-123`) reads `/proc/<pid>/stat` and
  takes `fields[19]` of the fields **after** `comm` — which is field 22 overall,
  the card's wording — precisely because `comm` is parenthesised and may contain
  spaces. `ownerIsAlive` (`:182-188`) compares it as a string, and
  `acquireDataFolderLock` refuses to take a lock at all when the value is
  unreadable (`:311-319`). The card's "what the production helper computes" is
  literally true.
- Reading the lock **while alive** is coherent with the release path. In the
  healthy path, `lock.release()` is registered on `onClose`
  (`index.ts:87-94`) and unlinks only while the file still carries our nonce
  (`data-lock.ts:276-299`), so a post-mortem read genuinely would prove nothing.
  In the **boot-error** path there is no `onClose` hook at all — `start()`
  returns at `index.ts:82` — so the file is never unlinked and is present for
  the whole life of the process. The card's choice is the only one available
  there.
- Stale lock cannot be mistaken for a live one, and the card's claim is right
  for a source-verifiable reason: `takeOver` (`data-lock.ts:344-367`) renames a
  new lock over a dead owner's and then re-reads and confirms its own nonce.
  Combined with the fresh `runId` per run (`sandbox.mjs:355`), a lock from a
  previous run cannot be present in this run's data dir anyway.

| A **stale lock from a previous run** left in the data dir | **Yes** | `takeOver` replaces a dead owner's file and re-verifies the nonce; and the run folder is per-`runId`, so a previous run's lock is in a different directory. |
| The **healthy** server still alive, holding the port and the lock, when the broken copy launches | **Yes** | The card requires stopping the first owned PID and re-establishing the port free. If it were still alive, `acquireDataFolderLock` would find a live owner and `openDatabase` would never be reached — `index.ts:59-62` exits 75 with no port bound, so the health poll times out and the test fails. |
| A foreign process writing a plausible lock into the run folder | **No, but it does not need to** | The card's clause 3 ("the folder is the wrapper's own `0700` run directory, so no foreign process can have written our pid's kernel start time into it") is **overstated**: every actor on this box is the same uid, so any same-user process can write into a `0700` directory. The clause is not load-bearing, though — the `pid` + `processStart` + aliveness triple is the actual discriminator and it does not care who wrote the file. Worth rewording to "no *other* Apunta writes this folder", not "no foreign process". |
| A dummy that grabs the port **while our process is alive but still pre-`listen`** (a long `prepareDatabaseForStart`, a hang) | **No** | This is the one real residual, and it is the sense in which "equal or better strength" overreaches (F6): the proof establishes that the *lock owner* is our live process, not that the *HTTP responder* is. It requires a third party to bind the port inside the launch window while our process blocks before `listen`. Narrow, and no worse than C-ISO rule 2's own bind-then-release TOCTOU — but not "better". |

  **Bottom line on Q4: the ownership proof is as strong as the card claims for
  every attack the contract's rule 5 exists to catch, and it is stronger than
  an environment echo on pid reuse. It is not strictly "equal or better" than
  rule 5, because it proves a different (complementary) property, and one
  narrow residual survives. I would not block on this.**
