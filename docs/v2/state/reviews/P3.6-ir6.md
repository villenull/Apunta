## DEFECTs — settleable now

### D11 — the identity-count assertion stores a *table* escape for a *shell* pipe, so four rows abort at exit 2 on a correct tree (IR-03, IR-04)

- **Where:** `docs/v2/cards/P3.6.md:394` (V0), `:395` (V1), `:397` (V3), `:398`
  (V4) — the final assertion of each of the four launching rows, in the form
  `test "$(ls -1 <pattern> \| wc -l)" -eq 1`.
- **Conflicting text.** The card stores a **backslash-escaped pipe** inside a
  double-quoted command substitution: `"$(ls -1 "$B"/Apunta_*.AppImage \| wc -l)"`.
  Two rules collide over that one character. **GFM** requires a `|` inside a table
  cell to be written `\|`, or it splits the cell — so the card is *forced* to store
  the escape. **bash** treats `\|` as an **escaped literal `|`**, not as the pipe
  operator, so `\|` is passed to `ls` as an ordinary argument. I confirmed
  `build-dispatch.mjs` does **not** undo it: an implementation card's dispatch
  body is `card.text` verbatim (`:123`), and the only substitutions are
  `{{…}}` tokens and `--port <p>`.
- **Executed, in both directions.** With one production image present:
  - escaped form → `ls: cannot access '|'`, `ls: cannot access 'wc'`, then
    `bash: test: …/Apunta_0.0.0_amd64.AppImage: integer expected`, **exit 2**;
  - unescaped form → **exit 0**;
  - with **two** production images: unescaped → **exit 1** (the sibling becomes
    visible, which is the guard working); escaped → **exit 2** again, i.e. the
    same failure whether the tree is right or wrong.
  The same result holds with the test identity's pattern, and for both a top-level
  `ls -1 \| wc -l` and the form inside `"$()"`; the collapsing happens in the
  shell's own parsing, not in the substitution.
- **Failure scenario.** P3.4 and P3.5 are eventually approved, a dispatch is
  generated, and the implementer runs V0. The producer and `tauri:build:test`
  both succeed and produce exactly one correct test AppImage. The row's
  `test -f "$B/Apunta (test)_${VER}_amd64.AppImage"` passes; the last assertion
  then dies with `integer expression expected` and **exit 2**. The row is `FAIL`
  with an excerpt that names a file called `|` and a command called `wc`. The
  implementer reaches **Stop 3** ("no AppImage at the expected path… or the
  row's own identity-specific glob resolves to zero or more than one file") whose
  route is *"re-running V0 or V1, never a hand-copied artefact"* — and re-running
  reproduces the identical exit 2, because nothing about the tree changed. Worse,
  **the two-new-versions branch of Stop 3 is unreachable**: with the pipe broken
  the count never becomes visible in the first place, so the honest escalation
  Stop 3 promises for a stale sibling never triggers. **All four launching rows
  are red on a perfect implementation, and the card's identity guard — the whole
  mechanism AM-147 built the row order around — asserts nothing.**
- **Correction.** Drop the pipe rather than manage the escape, which is the same
  route AM-157 endorsed for the ERE case: replace
  `test "$(ls -1 "$B"/<pattern> \| wc -l)" -eq 1` with a loop, keeping the glob
  **inline and quoted** so no word-splitting is introduced and no `|` appears for
  GFM to escape —
  `C=0; for f in "$B"/'Apunta (test)_'*.AppImage; do [ -e "$f" ] && C=$((C+1)); done; test "$C" -eq 1`
  (and the `Apunta_*.AppImage` form for V1 and V4; V3's row uses the same pattern
  V0's does). **I executed this replacement**: one production image → **exit 0**;
  two → **exit 1**; zero → **exit 1**; the test pattern inline-quoted → **exit 0**.
  The `[ -e "$f" ]` test is load-bearing — without it an unmatched glob yields
  the literal pattern and the loop counts one, which would be a *new* cannot-fail
  pass. Add one sentence to each affected expected cell saying the count is taken
  by a loop, and adjust the two sentences that describe the assertion as
  `test … -eq 1` over `ls -1 | wc -l`.
- **Provenance, and why it survived five rounds.** This is the **fourth
  cannot-fail-family defect on this card** (AM-153's typographic ellipsis, AM-154's
  de-escaped alternation, this one, and the class AM-157 diagnosed on P3.8) and
  the **fourth instance of the GFM-`\|` root cause AM-157 named**: "GFM table
  escaping forces a `\|` into the card to mean alternation, and every shell tool
  reads `\|` differently — a card cannot safely hold a regex that needs
  alternation". Here the member of the family is not a regex but a **shell
  pipe**, and the direction is a **false red** rather than a false green. It
  survived a round that ran `bash -n` on all six cells, because `bash -n` only
  parses and `\|` parses perfectly — **the same gap that let AM-156 certify this
  exact construct as "correct as written and correctly left alone", on the
  reasoning that the backslash is "a shell pipe … so the shell still reads it as
  a pipe". That reasoning is wrong and I measured it.** AM-156's other near-miss
  catch (V5's `\*` escapes) *is* correct and I confirmed it fires.
- **Not a re-run of a closed finding.** No prior round raised it. Round 5's press
  3 and press 5 covered non-ASCII bytes, placeholders and `bash -n` on the
  command column; none of them executed a fragment. Per AM-153's rule — *a finding
  about a command must come from running the command* — this one comes from
  running it.
