## (1) A1 — `parseCompareMetric` parses the forms the tool prints, and the caller's decision is unchanged

**The repair** (`tauri-e2e-smoke.test.mjs:725-738`, new, exported; call site `:769-772`):

```
-  const differing = Number(String(compared.stderr).trim());
-  if (!Number.isInteger(differing)) return null;
+  const differing = parseCompareMetric(compared.stderr);
+  if (differing === null) return null;
```

**Forms accepted** — verified against the installed ImageMagick 7.1.2-31 on this machine (probe re-run by this review on `build/p36-a7/`'s synthetic PNGs, matching `03-imagemagick-probe.txt` byte for byte): IM6's bare integer (`1234`), IM7's parenthesised pair (`0 (0)` for a perfect match, `0.666667 (0.0104167)` for one differing pixel, `2.66667 (0.0416667)` for four), and scientific notation (`1.5e+3`). The metric is read from the **last** non-empty stderr line, so a diagnostic before it cannot turn a parseable metric into an unparseable one. My 23-case battery (including `28.0142 (0.233452)` from the shipped doc page, `1.42109e-14 (0)`, `6.02E+23 (1)`, warning-then-metric, and `undefined`) passes 23/23.

**Fail-closed** — empty/whitespace-only stderr, `nan`, `NaN (NaN)`, `0 (`, `0 ()`, `(0)`, `0 0`, `12 (0.5) trailing`, `pixels (12)`, `0 (0) (0)`, `-1`, `-0.5 (0)`, `1e400 (0)`, `inf`, and the IM7 MAE form `0 (0) @ 417,44 [0]` all return `null`, which stops the run (`:2377-2383`) rather than grounding a click. The helper test asserts each.

**The caller's decision is unchanged in meaning.** The only threshold in `measureFrameClient` is `differing !== 0` (`:771`): 0 means the captures agree (client origin = window origin), anything else means they differ and the run stops. That comparison is float-safe — `0.666667 !== 0` and `0 !== 0` behave exactly as the integer forms did — and `differing` now flows nowhere except a message string (`:2388`). There is no `=== 0` assertion, no integer threshold and no other consumer of the value anywhere in the file (grep-verified: 7 matches, all accounted for). The float changes no behaviour; it only makes a real comparison readable.

**A fail-open hole the repair also closes** (noted because it is the same defect class): the old expression evaluated `Number('')` to `0`, so *empty* stderr — a `compare` that never ran — grounded every click as a perfect match. The new parser returns `null` for empty stderr. Strictly safer, and inside A1's "fail closed on anything unparseable".

**CLEAR.**

## (2) A2 — the history arm compares against the commit the AppImage was built from

**The repair**: `resolveBuildCommit` (`:2080-2130`, new, exported) reads the AppImage's mtime, runs `git rev-parse --verify HEAD`, `git log -1 --format=%H --before=<mtime ISO> HEAD`, requires a 40-hex answer, and requires `git merge-base --is-ancestor <commit> HEAD`. `ruleBFreshness` (`:2157`) takes `{ cwd, root }` (both default to this repository, so the row's own call is unchanged) and diffs `<build commit>...HEAD` over `RULE_B_PATHS`; `ruleBHistoryVerdict` (`:2199`) splits the verdict out so each fail-closed case is assertable; `newestRuleBInput(root)` (`:2236`) threads the root for the source walk. `RULE_B_BASE` (`'62abb28'`) is kept, exported and **reported** — named in the verdict detail as the recorded dispatch base that was deliberately *not* compared against.

**`--before` uses the committer date — verified empirically**, not assumed. In a throwaway repository: a commit with author date 11:00 and committer date 13:00 is *excluded* by `--before=12:30` (committer 13:00 > 12:30) even though its author date is before it. So the resolution keys on committer date, which is the date that tracks when a commit actually landed — the right clock for "what existed when the artefact was written".

**Fail-closed in every branch, no fallback.** All eight branches verified by reading and by tests: unreadable/missing mtime → `commit: null`; `rev-parse` fails (non-repo, unborn HEAD) → null; `git log` fails → null; a non-40-hex answer (including git's empty answer when the mtime predates the first commit) → null; a resolved commit that is not an ancestor of HEAD → null; `git diff` fails → `diffOk: false`; `git status` fails → `statusOk: false`; any moved Rule B input → `moved` non-empty. `ruleBHistoryVerdict` checks `buildCommit === null` **first**, so the empty `committed` list that a null build commit produces cannot become a vacuous pass, and the dispatch base is never substituted. The mutation test (`helper-tests.mjs:1703`) drops the unknown-build-commit guard and shows the case then PASSES vacuously — the guard is load-bearing, and it is present. The real-repo probe confirms the dirty-tree behaviour: 25 in-flight Rule B inputs are reported and the verdict is `ok: false` with each named.

**Adversarial analysis** (each case probed in the throwaway repository):

| Case | Behaviour | Direction |
| --- | --- | --- |
| Commit lands after the build moment but carries a **backdated committer date** | `--before` includes it; the diff is empty; a bundle lacking its changes **passes** | **Fail-open** — see LOW-2 |
| **Amend** after the build | New committer date is after the mtime → excluded → diff non-empty → **FAIL** | Fail-closed, correct (the bundle predates the amendment) |
| **Rebase** after the build | git 2.55.0 **preserves** committer date (verified) → the rebased commit stays included → diff empty → PASS, and content-correct (rebase preserves changes; the bundle's content matches HEAD) | Correct |
| Commit lands **during** the build (A5's `74cc340` shape) | Committer date < mtime → included → diff empty → PASS. Correct if the producer saw it; a false pass only if it touched a Rule B input *and* landed after the producer compiled | Fail-open window — see LOW-2 |
| Stale AppImage, post-build committer date | Excluded → diff non-empty → **FAIL** | Correct |
| Fresh AppImage | Resolves to HEAD or the newest commit ≤ mtime → diff empty → **PASS** | Correct |
| Fresh AppImage, clock jumps **backward** during the build, or the artefact is copied with `cp -p` | mtime behind reality → older commit resolved → diff non-empty → **FAIL** | Fail-closed (safe direction) |
| Dirty (uncommitted) Rule B input | Untouched `git status --porcelain` arm → **FAIL** | Correct, and required by AM-212 |
| AppImage older than its newest input | Untouched fresh-build anchor (`artifactNewer`) → **FAIL** | Correct, and required by AM-212 |

So: a stale AppImage can pass only through a backdated committer date or a Rule B commit landing mid-build; a fresh one can fail only through a clock backward jump or an mtime-preserving copy. Both fail-open paths require conditions this repository's workflow makes unlikely (single-machine commits and builds; the tree is verified clean over Rule B's set before V0; commits land between rows, not during a multi-minute build — and attempt 6's mid-V0 commit `74cc340` touched only `docs/v2/state/NEXT-SESSION.md`, not a Rule B input, so it had no effect on this arm).

**Would a recorded build commit be strictly more reliable, and is it within AM-212?** Yes, strictly — it is immune to clock skew, backdating and the mid-build window. But it is **not within AM-212**, and the implementer was right not to build one: nothing in V0's path records a commit (verified — `package-linux-resources.sh` and the Tauri build print no git ref, and attempt 6's V0 log contains no hash), the harness has no channel to V0's stdout (V0 and V3 are separate rows), and adding a sidecar, an env var or a recorder means editing the producer (Must not edit) or V0's command (card text, coordinator-owned) — all forbidden by AM-212's "Nothing else". The AppImage's mtime is the only artefact-level record of the build moment that V0 already produces, and `git log -1 --before` over it is the only in-bound derivation. On this repository it resolves attempt 6's artefact to `74cc340`, exactly the commit that run recorded as HEAD when V0 finished — the derivation matched reality where it could be checked. The residual risks are recorded as LOW-2, not defects.

**CLEAR.**
