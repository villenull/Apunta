## The native close: investigated, not accepted

Attempt 2 records the cooperative native close as `NOT RUN` because
`xdotool windowquit` sends `_NET_CLOSE_WINDOW`, which needs a window manager.
That is true of the tool and false as a statement about this host. Reading only
what is already installed — `strings /usr/lib/libxdo.so`,
`/usr/include/X11/Xatom.h`, `xprop`, and the existing `libX11.so.6` through
`ctypes` — I sent the **ICCCM `WM_DELETE_WINDOW` client message directly to the
app's own toplevel window** on an isolated Xvfb with no window manager, no
install, no new package and no owner focus:

- the window **advertises** `WM_DELETE_WINDOW` (atom 233, alongside
  `WM_TAKE_FOCUS`, `_NET_WM_PING`, `_NET_WM_SYNC_REQUEST`) — confirmed by `xprop`
  and independently by my own property read;
- the app logged `apunta: the window close is closing the app; starting the quit
  ladder` — the **real** `CloseRequested` door, not a simulated gate callback;
- the shell exited **on its own in ~300 ms**: no SIGKILL, no SIGTERM, no
  harness escalation; the port was released, **no bundled server process
  survived**, `apunta.lock` was removed, the unrelated dummy was still alive,
  Ollama answered 200 before and after, and no window or AppImage FUSE mount was
  left behind.

So D1 — the card's own objective — is now verified on the door the owner will
actually use, not only on the forced-destroy path. Full detail, including the
honest reproducibility table (six deliveries, three acted on; the discriminator
is `XSync` versus `XFlush` in **my scratch helper**, not anything in Apunta), is
in `review2-native-close.md`, along with the screenshots I read myself.

## Numbered findings for the implementer

1. **The cooperative-close `NOT RUN` cause is over-generalised (evidence, LOW).**
   `docs/v2/evidence/P3.3/attempt2-findings-disposition.md` and the harness
   comment at `scripts/v2/tauri-lifecycle.test.mjs:798-821` both say
   `CloseRequested` "cannot be reached from outside" on a WM-less display. That
   is true of `xdotool windowquit` and false of the host: an ICCCM
   `WM_DELETE_WINDOW` sent straight to the window reaches the app, every time,
   as `review2-native-close.md` shows. Narrow the claim to the tool ("no window
   manager here to route `_NET_CLOSE_WINDOW`") or record the working scratch
   route so a later card can turn the door into a row. Nothing else depends on
   it, and I propose no change to the harness.
2. **The two quit modes that cover D1's door are in no verification row
   (evidence, LOW).** The card's V3 runs `launch` only; `window-close` and
   `forced-close` exist in the harness and are exercised only by hand. I ran all
   three myself and they behave correctly (`window-close` → honest `NOT RUN`;
   `forced-close` → 12/12), so this is a coverage gap in the rows rather than a
   defect — but the card's own objective is asserted solely by the signal door
   unless a human runs the others by hand.
3. **V4 does not assert the error screen's content (evidence, LOW).** It proves
   the window title carries the right code and the splash is gone; nothing reads
   the page. I read both screens myself and they are bilingual, carry the right
   code, and have no spinner — so the product is fine and this is a row-strength
   point, not a defect.
4. **A launcher that inherits the desktop session's Wayland variables will put a
   window on the owner's screen (informational).**
   `tauri-lifecycle.test.mjs:214-236` unsets `WAYLAND_DISPLAY` and forces
   `XDG_BACKEND=GDK_BACKEND=x11` for the app, which is why the rows are safe; I
   hit the opposite twice with my own scratch launcher before copying that
   discipline. Worth a line in `docs/v2/HARNESS.md` for anyone who launches the
   AppImage by hand.
5. **D10 stays open by instruction (informational).** No action proposed here.
