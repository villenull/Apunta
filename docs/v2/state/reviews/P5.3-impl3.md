## Defect D — MEDIUM — a banked claim can be made by one document and spent by the next

The coordinator's ruling (impl2, Defect A, item 2) was: *"a beacon that lands
after its own tab re-registered … must not touch the new document's live
record."* The shipped design handles one order of those two events and not the
other.

`registerWindow` drops a banked word when the registration lands **after** the
claim (`:593`), and `maintenance.test.ts:922` proves it. The reverse — the
registration lands **first**, and the *outgoing* document's beacon arrives
afterwards — is not guarded: `closeWindow` sees one record under that tab,
`disconnectedAt === null` (the new document is connected), and banks
`cleanClaimed = true` **on the new document's record** (`:704`). Nothing
distinguishes "the socket is still open because *this* document is still here"
from "the socket is open because *another* document took this record over".
Then, if the new document goes away **without saying anything** — killed, crashed,
or its socket dropped — `disconnect()` finds `cleanClaimed` and **deletes the
record** (`:646-662`), and the next quiesce settles `ok:true` over text the new
document was holding and never got asked about.

Reproduced against the shipped controller (`tsx`, `createMaintenance`, no test
file written into the repo; scripts under `/tmp`):

```
first  = m.registerWindow('T');  holdFor(first)
m.disconnect(first)                       // outgoing document's socket goes first
second = m.registerWindow('T');           // same-tab reload: same record (FD13(c))
m.closeWindow('T', true)                  // the OUTGOING document's beacon, late
m.disconnect(second)                      // the new document dies holding an edit
other  = m.registerWindow('OTHER'); holdFor(other)
m.report({ …, ok: true }); await m.quiesce()
```

```
same record reused: true
status after the crash: {"windows":0,…}
quiesce: {"ok":true,"blockers":[]}
```

Control, identical but with `closeWindow` removed:

```
status after the crash: {"windows":0,…}
quiesce: {"ok":false,"blockers":["no_response"]}
```

So the stale beacon is exactly what turns a fail-closed outcome into a fail-open
one. `evidence/P5.3/impl2-repair.md`'s claim that a claim "cannot survive into the
next document under the same tab identity" is **false as shipped**, and that
sentence should not stand even after a fix — the fix has to make it true, not
re-describe it.

**Reachability, honestly.** I could not produce this ordering from a browser in
this engine: the server log shows the beacon reaching the server *before* the
socket close every time (the evidence's measurement, which I reproduced in the
V7 logs — `POST /api/app/quiesce/close?tab=e2e-quiescence-v7` answered while that
tab's own `GET …/wait` was still open), and a new document's registration cannot
precede its predecessor's `pagehide`. So this is MEDIUM, not HIGH: it needs the
beacon to lose a race it currently wins by a few milliseconds, on the same
localhost path where the runner's own requests are already observed arriving
150 ms late (Defect G). But it is the exact case the ruling named, it is the
fail-open direction the whole card is fail-closed about, and it is one boolean
away.

**Fix (small, and it does not re-create the AM-215 problem).** The server cannot
tell two documents apart with a `sessionStorage` identity, so give it something
that does distinguish them: a **per-document** nonce — module scope in
`web/src/lib/maintenance.ts`, *not* in `sessionStorage` — sent as `?doc=` on the
wait registration and echoed in the close beacon. The record stores the `doc` of
the registration that owns it, and `closeWindow` banks a claim only when
`record.doc === doc`. Then:

- beacon-first ordinary clean close: same document, banked, spent by its own
  socket close — unchanged, so AM-215 stays reachable;
- socket-first: discharged outright — unchanged;
- a predecessor's beacon after a same-tab reload: `doc` differs, **no-op**;
- Chromium's *Duplicate Tab*: two documents, two `doc`s, the claim still touches
  neither — unchanged.

This widens FD1's "the query string is the one non-`{quiesceId}` value the
channel sends", so it wants a coordinator sentence in FD1 (or AM-217) rather
than a silent second identity. A V1 case for it: a claim carrying a stale `doc`
after a same-tab re-register leaves the live record asked and counting, and the
incoming document killed holding an edit still refuses a bystander's `ok`.

**Cheaper alternative if the coordinator will not widen FD1:** keep the boolean
but let `disconnect()` refuse to spend a banked word on a record that has been
registered *since* the word was made — i.e. stamp the record with a
`registeredAt`/generation and compare. That closes the hole without a protocol
change, at the cost of refusing a genuine beacon-first close that raced a
re-register by milliseconds — the safe direction, and a rare one.

## Defect E — LOW — the `clean` claim is a cache that outlives the editor

`setEditorUnpersisted` is called from exactly one place: `NoteView.tsx`'s
`beforeunload` handler (`web/src/lib/maintenance.ts:176`, `NoteView.tsx:373-375`).
`editorUnpersisted` is module state and **nothing resets it** — not the effect's
cleanup, which only removes the listener.

Reachable, ordinary, fail-closed: a therapist types in a note, tries to leave, the
`beforeunload` dialog appears and they dismiss it (`setEditorUnpersisted(true)` is
now published), then they navigate in-app away from the note screen — `NoteView`
unmounts, its pending save flushes, the published value stays `true` — and later
close the tab cleanly. No `NoteView` is mounted, so nothing republishes;
`isCleanToClose()` answers **dirty**, `closeWindow` does nothing, the record is
retained, and **every later quiesce is refused `no_response` until Apunta is
restarted** — with nothing anywhere unsaved. That is precisely the user-hostile
outcome AM-215 was decided to remove, reached without any fault.

The mirror image is harmless (a stale `false` can only follow an editor that had
already flushed), so this is one line: publish `false` in the effect's cleanup,
or have the reporter read a live getter. Worth fixing because it is a support
problem, not a correctness one — but it is LOW.

**The rest of "is `clean` computed at the right moment?" holds up.** The guard
recomputes from the live refs on **every** fire (`latestTextRef !==
persistedContentRef || saving || error`), so a mid-debounce or mid-save window
publishes `true` and a stale `true` cannot outlive a successful save *while the
editor is mounted*; and `beforeunload` always precedes `pagehide`, so nothing can
be typed between the two events. I could not construct a same-document
"banked at `pagehide`, page not actually unloaded" case that is not already
closed: a cancelled `beforeunload` dialog means `pagehide` never fires, and the
bfcache path is Defect C's fix.

## Defect F — LOW — the claim is broader than what the client can see

FD8 defines `clean` as "no unpersisted text in the editor and no recording
running", and the module implements exactly that — but the only editor it hears
about is `NoteView`'s. The Capture screen holds a typed-notes textarea, a
salvaged WAV and an in-flight transcription, **all purely client-side and never
persisted** (`Capture.tsx:150`, `unfinished = text || recording !== 'idle' ||
wav !== null || busy`), and its own `beforeunload` guard (`:159-167`) is the only
thing that knows. Closing that tab sends `clean: true` and discharges.

Nothing is silently discarded — Capture's dialog fires first, so FD6's browser
half holds — but the server acts on a claim the client cannot support, and the
card's own sentence for `clean` is the thing that is too narrow. A one-line
`setEditorUnpersisted(unfinished)` in the effect that already publishes
`reportDirty(unfinished)` would close it, except that `Capture.tsx`'s May-edit
bullet licenses **one** added line and it is spent on `setRecordingActive`. So
this is a coordinator decision (widen FD8's wording and the bullet, or accept it
in the card) rather than an implementer fix.

## Defect G — LOW — V7's row is flaky at ~9%, and it is the spec's race, not the product

This is the failure the implementer's run 1 lost the text of. Both of mine are
identical:

```
Error: expect(received).toMatchObject(expected)
-   "blockers": Array [],  "ok": true,
+   "blockers": Array [ "no_response" ],  "ok": false,
    at leaveCleanly (e2e/tests/quiescence.spec.ts:109:34)
    at quiescence.spec.ts:544            (V7's own teardown)
```

**Cause, from the full server log of the failing run** (`/tmp`, timestamps in ms;
the v7 tab is the row's own window, the witness is `leaveCleanly`'s):

```
141939  GET  /                      the new document (leaveCleanly step 1)
141953  POST /api/app/quiesce/close?tab=e2e-quiescence-v7      -> 204   beacon, banked
142028  GET  /api/app/quiesce/wait?tab=e2e-quiescence-v7       (held)
142063  POST /api/app/quiesce       -> 200 (251 ms)                   quiesce #1: ok:true
142314  …  page.close()                                                      <-- socket close
142431  GET  /api/app/quiesce/wait?tab=…teardown-witness…     (held)       witness registers
142461  GET  /api/app/quiesce/status -> windows >= 1                       satisfied…
142463  POST /api/app/quiesce       -> 200 (251 ms)                       …by the witness itself
```

The v7 tab's beacon was delivered, so its record was banked; the only way the
quiesce 150 ms later still sees an obstruction is that **the server had not yet
observed that socket close**. The ghost window is still holding a wait, so
`askWindows` asks it, and a document that no longer exists can never answer:
`no_response`. `untilStatus(…, windows >= 1)` at `:108` cannot detect it,
because the fresh witness satisfies that condition by itself.

So: **a race in `leaveCleanly`, not a product bug.** The product behaved
correctly throughout — it cannot know a socket is gone before the OS tells it —
and the runner simply asserted faster than the kernel. The fix is one condition:
wait for `windows === 1` after the witness registers, i.e. for the closed tab to
be gone, which is what the row means. (`quiescence.spec.ts:98`'s `>= 1` is fine —
that tab supersedes its own record, so only one can exist.)

Two things worth recording alongside it:

- The same root makes a **real** transient: for the few hundred milliseconds
  between a clean close and the server observing the socket, a quiesce can be
  refused `no_response` over a window that said `clean` in its beacon. It clears
  itself, and impl2 already decided deliberately that a beacon arriving during a
  quiesce leaves that window counted as unanswered, so I am not calling it a
  defect — but it is the honest cost of FD13 and belongs in the card.
- `impl2-repair.md`'s "V7's flakiness under a loaded suite is unexplained" can
  now be closed as **explained**: not load-sensitive in V7's own assertions at
  all (it never failed there), but in the shared teardown every row uses.

## What I checked and found correct

- **Scope.** Every modified path is in May edit, `e2e/playwright.config.ts` under
  AM-213, or one of the authorised card/contract sentences. `registry.ts` is a
  comment; `settings.ts`, `generate.ts`, `App.tsx`, `sse.ts`, `i18n.tsx`,
  `ai/fake.ts`, `request-guard.ts`, `index.ts` and `src-tauri/**` are untouched.
  The route diffs are `begin` / `finally end` pairs; I re-read `notes.ts` (the
  revision check, the published lock and `stale_write` are all still inside the
  new `try`, which is what keeps them applying to an exempt save).
- **The gate.** All eighteen `GET` routes are in `EXEMPT_READS`; the hook is
  registered immediately after `registerRequestGuard`, so C-REQ@1 still runs
  first; a request already past the hook is never cut.
- **The flush exemption.** Method and path exact, the id must equal the in-flight
  one, the tab must resolve to a window asked and not yet reported, and
  `matches()` compares segment counts, so `/api/notes/:id/chat` is never exempt.
- **The reporter's transport.** One long-poll; abort on `pagehide`, after a report
  and at the deadline; the `owner` token makes the hot-reload guard real; the
  `fetch` decoration is scoped to the flush, to `PATCH /api/notes/<id>`,
  same-origin only, and restored on resolve, throw and abort.
- **The disconnect is watched on the response**, not the request, with
  `writableEnded` as the test — the reason `http/sse.ts` gives. That is also why
  the ghost window of Defect G is a *live wait* rather than a retained record,
  and I confirmed it in the log.
