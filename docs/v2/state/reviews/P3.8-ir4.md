**The two vacuity traps I specifically hunted are closed, and I checked them rather than reading them:**

1. **Can `appsnap`'s pid selection be fooled by a window the row owns, or by one the launch does not own?** *Mechanically yes; from this app, no — and the gap between those two is D1.* `appsnap() { snap | grep -F ":$1:" || true; }` does **not parse the owner-pid field**; it substring-matches the whole `id:pid:title:geometry` line. I executed it: given `952:777777::1071966::X=0 …` (a window owned by pid 777777 whose **title** contains `:1071966:`), `appsnap 1071966` selects it. The card's text — "`appsnap <pid>` … selects the windows the launch's **own shell** owns, by owner pid from `getwindowpid`, so identification is **owner pid plus an exact title**" — describes field equality, and the code does a substring search. Nothing this app paints puts a colon-digit-colon in a title (`Apunta`, `Apunta — starting`, `Apunta — <code>`, `apunta`), and the geometry block has no colons, so on this host the selection is correct in practice — which is why I grade it DEFECT rather than a soundness hole.
2. **Is "a re-shown window is a new owned id" true?** *True within one X client, and the row only ever compares windows of one launch.* X allocates window ids monotonically from the owning client's range and does not reuse an id within that client's lifetime, so a destroy-and-recreate by the shell necessarily yields a higher id — I proved the *consequence* by execution (the new-id case fires both (b) labels). I did **not** observe an X server allocating ids, because that would mean starting one; the protocol claim is reasoned, not measured. Cross-client id reuse is filtered by the pid selection, and pid reuse across launches cannot occur inside the row because each launch's shell is confirmed dead before the next starts.

## Defects — settleable now

**D1 (IR-03) — `appsnap`'s selection is a substring match, not owner-pid attribution.**
*Location:* V4 Command cell, `appsnap() { snap \| grep -F ":$1:" \|\| true; }`.
*Conflicting text:* the same cell's Expected column — "`appsnap <pid>` then selects the windows the launch's **own shell** owns, **by owner pid** from `getwindowpid`, so identification is **owner pid plus an exact title**".
*Failure scenario:* any window on the display whose **title** embeds `:<launch pid>:` is admitted to the launch's own window set. Its `Apunta`-titled descendants then satisfy the `grep -cF ":Apunta:" -eq 1` gate, its id becomes `$M0`, and (b)/(d1)/(d2)/(e) then assert about **that** window — the change's own window being merely absent from the comparison would no longer be visible, because the count would still be 1 and the id would still be "present".
*Correction:* anchor the match to the field, e.g. `appsnap() { snap | grep -E "^[^:]+:$1:" || true; }`, which selects on the pid **field** and keeps `|| true` so the poll loops still run.

**D2 (IR-04) — the (d2) alternation is written `\|` inside an ERE, so the row as it sits in the file cannot match.**
*Location:* V4 Command cell, twice — the poll `grep -Eq ":Apunta .*(exited_before_ready\|exited_75_without_a_bridge_line\|terminated_before_ready):" $D/win.d2 && break` and the bare re-grep that sets `d2-no-early-exit-error-window`.
*Conflicting text:* the command uses `grep -Eq`, where `|` is the alternation metacharacter; the file carries `\|` because a GFM table cell escapes a pipe. Executed both ways against a snapshot titled `Apunta — exited_before_ready`: the **de-escaped** form (what GitHub renders, and what ir3 extracted) **MATCHES**; the **raw-file** form **DOES NOT MATCH**. An implementer who reads the `.md` and copies the command verbatim — the normal path for a shell-using agent, and the path the card invites with "the row's *exact command* field has to be a command that can be pasted and run as it stands" — gets a row that polls 60 s, then polls (d2) for 20 s, and then reports `FAIL:… d2-no-early-exit-error-window` **even when the guard is perfect**.
*Why it is a defect and not a note:* this is the AM-154 class in new dress — a pipe whose meaning depends on an escape the card never explains — and it is the single most consequential thing I found, because it makes the card's core new witness unrunnable as written. It **fails safe** (red, never a false green), so it does not undermine the repair's soundness; it burns the last attempt instead.
*Correction:* add one sentence to V4's Expected cell stating that the three pipes inside the `(…)` group are GFM table escapes and must be plain `|` when the row is run — or, better and escape-proof, drop the alternation and loop over the three words with `for w in exited_before_ready exited_75_without_a_bridge_line terminated_before_ready; do grep -Eq ":Apunta .*${w}:" "$D/win.d2" && break; done`, so no pipe exists in the cell at all.

**D3 (IR-07) — the row's own "leaves 7860 free" claim is unconditional, but the port holder has no `trap` and a 600-second life.**
*Location:* V4 Command cell, `python3 -c "…s.bind((…,7860));s.listen(8);time.sleep(600)" & HP=$!`.
*Conflicting text:* the cell's own close — "releases the port holder it started before the launch that needs the port free, and **leaves 7860 free**".
*Failure scenario:* every exit path the row controls does release the holder — I checked all twelve `exit 3` sites and the final `exit 1`, and each one kills `$HP` first or is reached before the holder exists. But a `SIGINT`, a closed terminal or a harness timeout leaves a `python3` listener on `127.0.0.1:7860` for up to ten minutes. A re-run's `sandbox.mjs env --port 7860` then refuses the port (P3.3 records exactly this failure — "refusing port 7832: already in use"), which on the card's last attempt costs a run for a reason the row itself created.
*Correction:* add `trap 'kill "$HP" 2>/dev/null' EXIT INT TERM` immediately after `HP=$!`, or drop `time.sleep(600)` to a bound the row itself outlasts (its longest remaining path is 60 s + 20 s).
