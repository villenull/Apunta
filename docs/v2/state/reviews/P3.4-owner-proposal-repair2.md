## D1 — DEFECT — §C.2 step 8 names a command that does not exist

§C.2 step 8 says: "where `xdotool windowancestry` reports that id as an ancestor,
the check is satisfied". **There is no such command.** Verified on this machine,
not assumed:

```
$ xdotool windowancestry
xdotool: Unknown command: windowancestry
$ xdotool help | grep -i 'parent\|ancestry'
(no output)
```

`xdotool help`'s 46 commands include `getwindowpid`, `getwindowname`,
`getwindowgeometry`, `search`, `getmouselocation` — and **neither**
`windowancestry` **nor** `getwindowparent`. `/usr/share/man/man1/xdotool.1.gz`
has no `windowancestry` entry either (grep over the whole page: no hit). The
installed version is `4.20260303.1`, the same one the previous review version-
printed.

This is not cosmetic. §C.3 of the same proposal makes **"any non-zero `code` on
either command" an immediate `FAIL`**, and `xdotool` exits non-zero for an
unknown command — so the containment step would `FAIL` on **every** run, on the
very first `mousemove` that reaches step 8, exactly as IR-03's unsatisfiable
predicate would have failed attempt 5's only chance at (a). The fail-fast in §C.3
and the bad command in §C.2 step 8 compound.

**Exact repair — replace the disambiguation clause in §C.2 step 8 with:**

> … After every `mousemove`, `moveTo` also returns `getmouselocation`'s
> **`WINDOW`** field — the window id of the window directly underneath the mouse
> (`xdotool.1`, `getmouselocation --shell`). The check is satisfied when
> `at.WINDOW` equals the app window id, **or** when
> `xdotool getwindowpid <at.WINDOW>` — a command that exists in the installed
> xdotool — returns the same pid `windowInfo` already read for that window
> (`scripts/v2/tauri-security.test.mjs:476-483`), which is what covers a child X
> window of the app process. `getmouselocation` reports the window *directly
> underneath* the pointer, so the ancestor case is real and the pid clause is not
> optional; where neither holds, and **including when `getwindowpid` returns
> nothing**, the step `FAIL`s with both ids — fail-closed, because an empty
> answer must not be read as "fine". **`xdotool windowancestry` does not exist in
> this xdotool and may not be used** (`xdotool help`; the command list is 46
> entries and it is not among them).

This keeps IR-08's property — "the pointer is over the app" — on commands the box
actually has, and it needs no new import and no second `PATH` assumption:
`getwindowpid` is already spawned at `:472`.

## D2 — DEFECT — the widened gate inherits a cause sentence that can now be false

§A.3 widens the gate at `scripts/v2/tauri-security.test.mjs:843-847` to
`(fact) => fact['href'] !== undefined && fact['ipcProbe'] !== undefined` and adds
the words "including the IPC probe facts" to the existing cause. But the existing
cause sentence (`:849-853`) reads:

> "no `/api/p3.4-observe` line **ever appeared** in the AppImage child's captured
> stderr … (`N` marker line(s) read), so the observation hook publishes nothing
> this harness can read."

With the old gate that sentence was always true — no `href` means no marker line
existed. **With the widened gate it can be false**: a page that publishes facts
perfectly well but never sets `ipcProbe` (a hook half-implemented, or a
regression that drops the probe) now takes this branch with `N > 0`, and the
report simultaneously says *no line ever appeared* and *N lines read*. That is
the same self-contradiction attempt 4 recorded in its own evidence (a count read
from the live buffer beside a sentence denying any buffer), and this card has
already been charged once for a report that contradicted its own count.

**Exact repair — the gate becomes conditional, and the cause has two arms:**

```js
    if (first === null) {
      const { markerLines } = readObservations(run.output.stderr);
      const dead = markerLines === 0;
      const cause =
        (dead
          ? `no ${MARKER_PATH} line ever appeared in the AppImage child's captured stderr while the app window was up and the server was answering (0 marker line(s) read), so the observation hook publishes nothing this harness can read. `
          : `the hook published ${String(markerLines)} marker line(s) but none carried href and ipcProbe together, so the fact set this harness reads is incomplete (including the IPC probe facts). `) +
        "Nothing here may be read without it, so (a), (b), (c), (d)'s handler half and (e) are NOT RUN together and none of them is a PASS.";
```

Only the cause text moves. The five `notRun` rows, their labels, their order and
the card's cascade contract are untouched, and both arms still record all five
`NOT RUN` together — which is what the card requires (`docs/v2/cards/P3.4.md:237-243`,
`:584-593`) and what IR-05 was about.

## D3 — DEFECT (minor) — §T.2's success test can pass for the wrong reason

§T.2's test 3 asserts that `--attempt 5 --attempt-exception AM-nnn` for a plan
whose card **is** `P3.4` exits 0. It does not say how that plan is built, and the
helper's default is the synthetic card `T1` with `| Depends | none |`. If a test
renames the card to `P3.4` but keeps the real plan's dependency expectations —
or, worse, points `APUNTA_V2_PLAN_DIR` at the repository plan — the generator's
dependency gate (`build-dispatch.mjs:174-177`) fires first and the run exits
**3**, which a loose `assert.notEqual(status, 2)` would happily call success.

**Exact repair — add to §T.2 test 3:** the plan is built with
`makePlan(card('<command>', '<expected>'), reviewRow, 'P3.4')` — the synthetic
card text **with `| Depends | none |` kept**, so the dependency gate is not what
is under test — and the assertion is `assert.equal(result.status, 0)` **plus**
`assert.match(result.stdout, /no attempt 6/)`. If a test instead needs the real
dependency set, its `PROGRESS.json` must mark those dependencies `APPROVED`
explicitly; no test may read or write the repository's `state/` files.

## Confirmations

### C-01, C-02, C-03 — the three blockers, closed at the named places

- **IR-03.** `line['ipcProbe'] !== 'pending'` is in the predicate, and it is in
  the right place: the hook's first `poll()` is called synchronously at
  `web/src/main.tsx:182` and `readFacts()` builds the whole query at `:67-93`, so
  the first line carries every key including `ipcProbe=pending`. The old
  predicate therefore matched instantly and (a) failed on a correct build. The
  repair removes that guaranteed failure. And `found === null` is now a `FAIL`
  rather than a `NOT RUN`, which is right twice over: the card's own wording says
  "`pending` when the 30 s window ends … is a **`FAIL`**", and a `NOT RUN` here
  would have been the *second* cascade IR-05 forbids.
- **IR-04.** `clickPath` is gone from §B's table and §D uses `href`. Verified in
  source: `web/src/routes/Workspace.tsx:221-225` is
  `navigate(\`/?patient=${encodeURIComponent(id)}\`)`, so the **path** is unchanged
  by a patient open and `clickPath` would have been unsatisfiable — a permanent
  harness-caused `FAIL`. `href` is published at `web/src/main.tsx:71` and has been
  since attempt 2. The predicate is also **not** loosened by anything the page
  does on its own: it requires `clickN` to have advanced, and only the click can
  advance it, so a boot-time or first-run rewrite of `location.href` cannot
  satisfy it (the workspace's first-run redirect, `Workspace.tsx:210`, has
  already happened by then — attempt 4 fixed that ordering).
- **IR-05.** The five-row cascade lives in exactly one place, the `first === null`
  branch (`:849-873`), and revision 2 **widens the existing gate instead of adding
  a second one**, then deletes the cascade from `assertNoIpc`. One gate, one poll,
  one marker path, one hook — unchanged, as §G states.

### C-04 — IR-06 and IR-07 closed

The bootstrap is a **displacement** (`(X₁ + Δcx, Y₁ + Δcy)`), which is invariant
under any affine map, so `k` falls out of the second observation without having to
be known when the second point was asked for; the 1:1 first point is explicitly
labelled an assumption used only to obtain the first observation, presses nothing,
and its failure is a named `NOT RUN` with no click issued. That is the only sound
two-point bootstrap available. The tautology is gone: revision 2 states that two
observations fix two unknowns per axis, so the fit is exact by construction and is
**not** validation, and names the out-of-sample test instead (step 10's ±2 px loop
closure on a click point that is at neither calibration target). Only assertions
that can fail remain in step 7: `0 < k <= 4` per axis, and containment.

### C-05 — IR-08 closed in substance (command defect in D1)

Both halves are present: the geometric containment assertion before every move,
and the use of `getmouselocation`'s `WINDOW` field, which the previous review
found being parsed and thrown away. The `WINDOW` field is real — the man page's
example output is `X=880 / Y=443 / SCREEN=0 / WINDOW=16777250` — and the strict
parser regex `/^([A-Z_]+)=(.*)$/` matches every one of those keys, including
`WINDOW`. The single defect is the *disambiguation command*, fixed in D1.

### C-06 — IR-09 closed

Hovering a patient row inserts `div.project-tip` into the DOM
(`web/src/components/PatientsColumn.tsx:1174-1184`, `:1425-1442`) at
`rect.right + 20, top: rect.top`, which is the notes column at the patient's
vertical band, so a stale tooltip can swallow the press. Revision 2 therefore
waits **600 ms = two poll intervals** after the warp before clicking, re-reads the
target's rectangle **from the live buffer**, re-warps **once** (a move, not a
click) and re-reads once more. The `clickEl` rule is now exact — three fields
compared against the same three fields published for **the rectangle the harness
selected**, which is why §B adds `rectTag`/`rectTestId` — and "first match wins"
is explicitly forbidden, with a named `FAIL` when two live rectangles carry the
label. `tagName` is a genuine discriminator here: the row's `span.name` versus the
tooltip's `div.project-tip-name`. The one-click-per-target rule is untouched.

### C-07, C-08, C-09, C-10 closed

The not-found example is now `Command listen not found`, with the reason
(`webview/mod.rs:2071-2074` strips the prefix, `:2155-2162` formats from the
stripped name) stated so the next reader is not taught a wrong discriminator. The
cascade is "preserved **except** that its (a) label becomes the new title", with
the card V2 cell's `NOT RUN` sentence moving by exactly that substitution and
nothing else in that cell. `rectForLabel` is polled through the same
`waitForFact`-shaped loop **within the click's own 30 s window**, an incomplete
frame is a `FAIL` naming "incomplete frame: 3 of 5 batches", a changed `total`
restarts the read and says so, and "sampling once and reporting no rectangle" is
forbidden. The strict parser is the one already in the file (`:475-477`), so
there is no second, looser parser.
