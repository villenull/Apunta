## Finding

### IR2-01 (bounded) — the prepared step-0 preflight cannot fail

**Before (proposal §7 step 0, `:193-196`).** The acceptance is fail-closed:

> `command -v patchelf` exits 0; four separate
> `gst-inspect-1.0 appsink|autoaudiosrc|alsasrc|pulsesrc` each exit 0; the
> scanner exists. Expected now: `patchelf` absent and the last three exit 255;
> the install makes them pass.

**What the repair actually prepared (`verify.mjs:152-159`, the only concrete
command):**

```sh
command -v patchelf || echo "FAIL: patchelf absent"
for e in appsink autoaudiosrc alsasrc pulsesrc; do
  gst-inspect-1.0 "$e" >/dev/null 2>&1 && echo "OK $e" || echo "MISSING $e"
done
test -f /usr/lib/gstreamer-1.0/gst-plugin-scanner && echo "scanner present"
```

**Why that is wrong.** Every check is `|| echo` (or `&& echo || echo`), so the
script's status is always 0; `set -e` cannot fire on a failed prerequisite. It
is exactly the `command -v … || echo` then continue-to-build pattern: on a
missing `patchelf` or element it prints a failure and proceeds to step 1 (the
build) and step 2. The only later thing that happens to catch a missing
`patchelf` is the plugin script's own `exit 2`; the preflight itself is
vacuous. It also does not implement the stated "the scanner exists" assertion
beyond an `echo`.

**Counterexample, on this host, exact exits** (`ir2-checks.mjs`, `output.txt`):

```
$ bash <the prepared step-0 snippet verbatim>
v24.19.0
FAIL: patchelf absent
OK appsink
MISSING autoaudiosrc
MISSING alsasrc
MISSING pulsesrc
scanner present
prepared step-0 exit=0        <-- cannot fail
```

The fail-closed form the acceptance requires, run against the same host:

```sh
set -e
command -v patchelf >/dev/null 2>&1 || { echo "FAIL: patchelf absent"; exit 1; }
for e in appsink autoaudiosrc alsasrc pulsesrc; do
  gst-inspect-1.0 "$e" >/dev/null 2>&1 || { echo "FAIL: $e not visible"; exit 1; }
done
test -x /usr/lib/gstreamer-1.0/gst-plugin-scanner
```

```
FAIL: patchelf absent
fail-closed exit=1            <-- stops, as the acceptance demands
```

**After (recommended).** Make each check fail-closed (`command -v patchelf
>/dev/null || { echo …; exit 1; }`, the same for each `gst-inspect-1.0 "$e"`
and for the scanner `test -x`), and say in §7 step 0 that the same read is
re-run **after** the install and must exit 0 before step 1. The step-2 dry
visibility row (`:203-210`) is already fail-closed (`test -x` and per-element
`|| exit 1`), so the capture gate is sound; the defect is confined to the
prerequisite read and to the validation evidence that claims to represent it.

## Notes (not blockers)

### IR2-N1 — §7 step 2's prose is thinner than the prepared command and the real hook

The hook the flag installs sets both `GST_PLUGIN_SYSTEM_PATH_1_0` and
`GST_PLUGIN_PATH_1_0` to `$APPDIR/usr/lib/gstreamer-1.0` and
`GST_REGISTRY_REUSE_PLUGIN_SCANNER=no` (`linuxdeploy-plugin-gstreamer.sh:145-147`).
The prepared command mirrors that (`verify.mjs:173-177`), and it is what keeps
a host/ambient user plugin path from falsely proving bundle visibility. The
proposal's §7 step 2 prose names only `GST_PLUGIN_SYSTEM_PATH_1_0` and
`GST_PLUGIN_SCANNER_1_0`. The command is safe; the prose should name the same
four variables so the two cannot drift.

### IR2-N2 — the V0 Expected clarification is bundled, not named in the choice

The V0 *Expected* cell is a protected acceptance row (COORDINATOR §6). The
repair's §6 (`:168-174`) and the repair `README.md` say the clarification is
"bundled into Decision 1" / "bundled into the capture grant", and the wording
is truthful (`Server Name:` names a PipeWire-backed Pulse server, this host
printing `Server Name: PulseAudio (on PipeWire 1.6.8)`; the default read with
`pactl get-default-source` because `pactl list short sources` carries no `*`
marker). But §3's Decision 1 option text (`:109-119`) does not name it, and §6
sits under the heading "Repairs that are not owner questions". No hidden
adoption was found, but the owner's choice should name the V0 acceptance
clarification on its face so approval cannot be read as covering only the
config/install/scanner/A03 parts.

### IR2-N3 — V1's duration is recorded, not asserted

The repaired V1 command loops the clip to 30 s (`-stream_loop -1` before `-i`,
`-t 30` after it) and then runs `ffprobe -show_entries format=duration`. The
30 s outcome is produced by construction and the `>10 s` assertion lives in V3
and is untouched; the `ffprobe` line only prints the duration. That is a
recording, not a duration assertion, and the proposal should say so rather than
imply the duration is checked.
