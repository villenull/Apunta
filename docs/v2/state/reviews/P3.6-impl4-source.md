### D2 — MEDIUM — F7's narrowed containment check is structurally unable to fail, and its only remaining firing mode is a false positive

`ownershipContainment` computes `appeared = after.filter((name) => !baseline.includes(name))` and `secondOwned = appeared ∩ ownershipFiles()` (`harness:1713-1721`). But `ownershipBaselineProof` asserts that **all four** C-OWN@1 names are already **present** in the baseline (`harness:1689-1693`, checked at the run's baseline step). A name already in the baseline can never appear in `appeared`, so `secondOwned` is `[]` by construction and the check `smoke no second lock, database, -wal or -shm` (`harness:2045-2055`) **can never fail**.

The consequence is not cosmetic. That check is one of the five containment assertions the card names, and the thing it is supposed to catch — a second server owning the data folder — cannot present itself as a *new filename* in that folder: a second instance either fails to take the lock or writes the same four names. The pre-repair version failed loudly on the backup's own `backups/` (attempt 3's F7, correctly identified); the repaired version is green unconditionally. That is the HS-7 shape — a guard moved from falsely-red to falsely-green — and it should not ship as the card's isolation proof without either a mechanism that can fail or an honest restatement of what is being asserted.

Two ways forward, both inside the harness file:

- make it falsifiable against the same four names without going back to "every name": record each of the four files' **identity** (device+inode, or mtime+size) in the baseline and assert it is unchanged at the end, and/or read the lock holder out of `apunta.lock` and assert it is still this run's pid; or
- keep the name-set check as a **re-assertion of baseline presence** and say so in the check's name and in the header, so a reader does not take it for a second-owner detector.

Note also the one way the check *can* still fire: `apunta.db-wal` is created and removed by SQLite. If it were absent at baseline and re-created by the first instance's own later writes, it would be reported as `a second owner appeared` — a false positive of exactly the class F7 was raised for. The baseline's "all four present" assertion is what keeps that unlikely; it should not be the only thing between the row and that failure.

## Observations (not defects, no acceptance change)

- **The D6 helper test's relaxation is defensible but untested in the direction that matters.** It dropped `moved === []` — which could not hold on a shared tree — for "both git halves succeed, every reported name is a real Rule B input, two reads agree". That is honest, and the **predicate** is unchanged and still fails V3 at run time. But nothing now asserts that the predicate *detects* a moved input (there is no negative fixture), so a regression that made `ruleBFreshness` always return `moved: []` would pass the suite. One synthetic assertion over an injected path list would close that.
- **`renders()`-style proof cannot see mounting.** Every F1–F7 helper assertion that reads the app's source counts `t('key')` occurrences on a line. That is a sound check of "written once in this file" and a silent no-op on "this component is mounted", which is exactly how D1 passed. Worth stating in the evidence rather than leaving implicit: a label's proof needs its render *condition* named, not just its render line.
- **The freshness checks record a FAIL and continue.** They do not return, so the run still launches the app against a stale bundle; the row exits non-zero, so a stale bundle cannot pass, but the comment "a stale bundle must not be driven" is not enforced. Pre-existing from attempt 3, unchanged here. Relevant to V0 planning: a re-run is required, not optional.
- **F3's label is conditional.** `Listening for words…` renders only while the capture preview is empty (`LiveRecording.tsx:73`), and `flowCapture` starts fixture playback *before* reaching the capture screen, so on a fast fixture the preview may already be non-empty when `confirmPane` reads the screen. Pre-existing and not raised in attempt 3; whether it fires is UNKNOWN without a native V3.
- **The card's "ten flows" phrase lists eleven names.** The harness implements all eleven (`harness:110-122`); the count cannot make a row pass or fail wrongly. Unchanged.
- **`startedPids` does not remember the app child** (only the playback pid), so a signal path SIGTERMs the remembered pids and relies on the app's own lifecycle; the normal path stops the child explicitly. Pre-existing from attempt 3.
