## DEFECTs — settleable now

### D8 — V3's primary freshness predicate carries a Unicode ellipsis and git rejects it (IR-04)

- **Where:** `docs/v2/cards/P3.6.md:373` (V3 expected cell), in *Freshness*.
- **Conflicting text:** *"the primary predicates are `git diff --name-only
  {{BASE}}…HEAD -- <Rule B set>` together with `git status --porcelain -- <Rule B
  set>`"* — and, one clause later, *"**where `{{BASE}}` must be written exactly like
  that and never as `<base>`**"*. The card polices the spelling of the token to the
  character while carrying a **non-ASCII** range separator in the same sentence.
- **Byte-level fact, not a reading impression:** the three bytes between `}}` and
  `HEAD` are `e2 80 a6` — U+2026 HORIZONTAL ELLIPSIS — not three ASCII full stops.
- **Verified, read-only:** with a literal hash substituted,
  `git diff --name-only 9f21457…HEAD -- <path>` → **`fatal: bad revision
  '9f21457…HEAD'`, exit 128**; `git rev-parse` on the same string returns
  *"ambiguous argument … unknown revision or path not in the working tree"*.
- **Failure scenario:** the implementer copies the predicate as the card prints it.
  Git refuses the revision, so the predicate cannot run at all. The two ways that
  resolves are both bad. Either the implementer drops the failing predicate and
  keeps `git status --porcelain`, which sees only the **working tree** and so cannot
  see a change *committed* since the base — precisely the stale-bundle case Rule B
  exists to catch, the same defect that cost P3.4 an attempt. Or the implementer
  "fixes" the token the way the card warns about and writes `<base>`, which reaches
  git as a matching-nothing pathspec and **passes vacuously on a stale bundle** —
  the identical hazard AM-142 fixed on P3.8, and the one this very sentence names.
  The card has done everything right about `{{BASE}}` and then shipped a predicate
  that cannot execute.
- **Correction:** replace the U+2026 with ASCII in the predicate, so it reads
  ``git diff --name-only {{BASE}}...HEAD -- <Rule B set>``, and state once in the
  same clause that the separator is three ASCII full stops and not `…`. No other
  change: the token, the "never `<base>`" rule and the literal-hash fallback are
  all correct as written.
- **Not raised by any earlier round.** Round 3's A2 note inspected the *token* and
  concluded correctly that `{{BASE}}` is the one the generator substitutes; it did
  not look at the character after it.
