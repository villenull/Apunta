## Numbered findings for the implementer

1. **V2 cannot detect a truncated `web/dist`, which is the one thing the SPA
   check exists to detect.** `scripts/v2/package-linux-resources.test.sh:432-448`
   (and `:429-430` for the body). I copied the bundle inside the run folder,
   deleted `web/dist/assets/` and `web/dist/fonts/`, and started the bundled
   server under the same launch contract. `GET /` still returned `200`,
   `text/html`, 1265 bytes — so `spa-status`, `spa-content-type` and `spa-body`
   **all three pass on a bundle containing no JavaScript and no fonts at all**.
   Worse, the truncation is not visible at the HTTP layer: the missing script
   `index.html` itself loads (`/assets/index-D7iOgJVA.js`) is answered
   **`200 OK` with `content-type: text/html`**, the SPA fallback, not `404`. The
   control against a complete `web/dist` returns the same `200` with
   `application/javascript` and 169523 bytes, so a real bundle and a truncated
   one are **indistinguishable to this row**, and the only signal is a
   JavaScript parse error in a person's browser — precisely the failure Step 3
   says must not happen. The card fixed this check, so the implementer built what
   was asked; but the return presents the SPA trio as covering truncation, and it
   does not. *Severity: major.* Not blocking (the row passes as written), but the
   criterion behind it is unmet and should be recorded for P3.5/P6.1 rather than
   treated as covered. Fixable by asserting one hashed asset from `index.html`
   returns 200 with a JS content type and a plausible length, which also needs
   the static handler to stop answering `200 text/html` for unmatched asset
   paths.

2. **The build is not hermetic, and the A06 fetch repeats on every run rather
   than happening once.** `scripts/build-whisper-candidate.sh:77` fetches
   unconditionally, with no `git rev-parse HEAD` short-circuit, even though the
   clone is already at the pinned revision. I observed the outbound request
   during **this** review's V1: `.git/FETCH_HEAD` mtime moved to 18:28:44Z, and
   the build log's first line is
   `From https://github.com/ggml-org/whisper.cpp … -> FETCH_HEAD`. The card
   sanctions this as "a redundant fetch, not a second acquisition" and
   `github.com` is an allowed host, so this is **not** a hard-stop violation —
   but `docs/v2/evidence/P3.1/acquisition-A06-completed.md:67-77` frames it as
   "One, to `github.com`… this session", and a reviewer re-running V1 performs
   another one, as I did. The practical consequence is that the bundle cannot be
   rebuilt on an airgapped host. *Severity: minor.*
   `build-whisper-candidate.sh` is outside this card's May edit, so the fix
   belongs to whoever owns it.

3. **V1's own log contains no evidence that whisper was built, and leaks the log
   that would have.** `scripts/v2/package-linux-resources.sh:205-215`.
   `WHISPER_LOG="$(mktemp)"` is `rm -f`'d **only inside the failure branch**, so
   on success the entire A06 build output is orphaned in `/tmp` and never shown.
   V1's stdout jumps straight from `== Building whisper-cli (A06)` to
   `copied whisper-cli and 15 shared libraries into bin/`. For a row whose
   acceptance is "a missing `bin/whisper-cli` is the Stop-condition path", a
   successful build is therefore indistinguishable in the log from a copy out of
   a stale build tree — I had to go and read the leaked file to establish that a
   real 139-TU compile had happened. 38 such files have accumulated; the newest
   two are my run's and the implementer's cold run's, and their sizes and mtimes
   match the recorded cold-run timestamps exactly. *Severity: minor.*

4. **The manifest's symlink convention is recorded nowhere, so a verifier has to
   guess it.** `scripts/v2/package-linux-resources.sh:310-344`. The integrity
   half of the claim is sound and I confirmed it (§5b of the evidence): all 13
   symlinks resolve to a listed target, every ultimate realpath is a listed
   regular file with a content hash, 0 dangling, 0 escaping. The usability half
   is not. I measured that a verifier doing the obvious thing —
   `sha256(readFileSync(path))` — **disagrees with the manifest on 13 of 4804
   entries**, all of them symlinks, because `bytes` and `sha256` are now the
   length and hash of the *target string*. The manifest is verifiable, but only
   by a verifier that already knows to `lstat` and already knows what the hash of
   a link entry means. `manifest.json` has no room for a `type` field — the card
   fixes the entry shape to exactly `{path, bytes, sha256}` — and nothing in the
   repository documents the convention for whoever verifies the bundle next.
   *Severity: minor.* The card's shape is the constraint; a line in the install
   guide or a `manifest.md` beside it would close the gap.

5. **The deployment-consequence list names one requirement of several.**
   `docs/v2/state/returns/P3.1.md:156-162` and
   `docs/v2/evidence/P3.1/attempt1-verification.md:273-280`. The return is
   right that the bundle requires a host Vulkan driver, and it does say so — the
   coordinator's concern that V1 might be presented as unconditionally green is
   **not** realised. But the return presents the Vulkan driver as *the*
   consequence. `readelf -d` and `ldd` on the reviewer's own bundle show the
   binary also needs, from the host: `libstdc++.so.6`, `libgomp.so.1`,
   `libgcc_s.so.1`, `libm.so.6`, `libc.so.6`, the dynamic loader, and
   `libvulkan.so.1` transitively — at a **glibc floor of 2.44**. The manifest
   records `glibc` as a string that nothing checks. The install guide needs more
   than the Vulkan line. *Severity: minor.*

6. **`.gitignore` adds repo-wide `build/`, not `build/linux-resources/`.**
   `.gitignore:50`. `git check-ignore` reports `server/build/z`, `docs/build/y`
   and `src-tauri/target/build/x` as all ignored. **Zero tracked files are
   shadowed today** (`git ls-files | grep -cE '(^|/)build/'` → 0), so there is no
   data loss, and the dispatch's May edit says "`build/` is added to
   `.gitignore`", so the implementer wrote exactly what the card fixed. The
   consequence is latent: any future `*/build/` source directory is silently
   untracked. *Severity: minor.* Worth narrowing to `/build/` when convenient.

7. **The sandbox port is hard-coded into a committed script.**
   `scripts/v2/package-linux-resources.test.sh:22-23` and `:28`
   (`PORT="${APUNTA_P31_PORT:-7834}"`). This dispatch allocates **7845** and its
   Step 1 says "`<p>` is `--port` from the dispatch". Run exactly as the V2 row
   is written, the script would have bound **7834** — the implementer's port, not
   this review's. I therefore set `APUNTA_P31_PORT=7845` and got 7845, which is
   why the recorded run is on 7845. `sandbox.mjs` still validates the range, so
   no contract is broken, and 7834 was free. But the port is a per-dispatch value
   frozen into a committed script, so two card sessions that both ran the row
   literally would collide. *Severity: minor.*

8. **`whisper-cli --help` never exercises the Vulkan ICD.**
   `scripts/v2/package-linux-resources.test.sh:451-455` and
   `scripts/v2/package-linux-resources.sh:293-298`. Both gates pass on this host
   because `libvulkan.so.1` resolves from `/usr/lib`; the ICD is never opened and
   the GPU is never touched. A bundle shipping a corrupt or wrong-ABI
   `libggml-vulkan.so` would pass both. The card fixed this check, so it is
   faithful — recorded so the coordinator does not read "the whisper binary
   works" as "STT on Vulkan was exercised". *Severity: minor / observation.*
   A real transcription is A07/S4a.2's to prove.

## The three claims worth an avil eye, answered

1. **V3's symlink claim — the second half is TRUE.** Not merely asserted. I
   resolved all 13 links, looked each target up in the manifest, and confirmed
   that every direct target is a listed entry and every ultimate realpath is a
   listed **regular file** with its own content hash; 0 dangling, 0 escaping. A
   substituted library is still caught, because the substituted bytes live on a
   listed regular-file entry. The gap is documentation, not integrity — finding 4.
2. **V2's negative case IS asserted, and it discriminates.** This was the
   strongest thing about the implementation. The bundle still contains a loadable
   addon at `node_modules/better-sqlite3/prebuilds/linux-x64.node`, so the
   failure is not trivially reachable; and `APUNTA_SQLITE_BINDING` is
   authoritative rather than advisory — `server/src/db/index.ts:44-46` passes it
   as better-sqlite3's `nativeBinding`, so the loader does **not** fall back to
   `prebuilds/`. The observed `503 storage_error` is therefore caused by the
   rename and by nothing else, and a healthy server would have failed the check.
   The weak spot in V2 is a different one: the happy-path SPA check (finding 1).
3. **The Vulkan deployment consequence — the return does state it, but the list
   is incomplete.** It is not glossed as a clean V1. See finding 5: the install
   guide needs the glibc floor and the host `libstdc++`/`libgomp` requirement
   too, not just the driver.

## Verdict

**PASS.** V1, V2, V3 and V4 all re-ran against a real, cold-built bundle with
exit code `0`, and the three checks the coordinator flagged as worth suspicion —
the symlink integrity claim, the negative case, and the Vulkan consequence —
hold up under independent measurement. No finding is blocking.

V2's SPA check does not detect a truncated `web/dist`, the card's stated reason
for having it, and the return implies that it does. That is a gap in what the
row proves, not a failure of the row, and it should be carried to P3.5/P6.1 as
an open item rather than closed by this card's green.
