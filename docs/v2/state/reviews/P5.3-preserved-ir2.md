## 3. The surviving blockers, with sequences (B1–B9 and B3-bis)

### B1 — the admitted save has no carrier for either identity it requires (blocking)

FD4a admits a request "presented while **all** of: a quiesce is in flight; **the
presenting `windowId`** is registered for that quiesce; the header
`x-apunta-quiesce-id` equals that quiesce's id; and the flush phase is open."
Neither identity can reach the server.

- **`windowId`: no carrier exists at all.** There are no cookies in this
  codebase — `grep -rn -i cookie server/src web/src shared/src` → no hit, no
  `@fastify/cookie` — and every window shares one origin, one cookie jar and one
  connection. `web/src/api/client.ts` sets exactly one header anywhere
  (`buildInit`, `:45-59`: `content-type`), and `RequestOptions` (`:36-42`) has
  no `headers` field. A `PATCH` from a second window is byte-identical to one
  from the first. So "the presenting `windowId`" is not a fact the hook can
  read. **OA-1 invariant (ii) — "no other … *window* … admits anything" — is
  therefore unenforced as written.**
- **`x-apunta-quiesce-id`: cannot be attached inside the card's edit surface.**
  `NoteView.flush()` → `enqueue` → `persist` → `updateNote`
  (`NoteView.tsx:294-330` → `:276` → `:223-273`) → `requestJson`
  (`client.ts:89-97`) → `buildInit` → `fetch`. The only option `updateNote`
  accepts is `Pick<RequestOptions, 'keepalive'>` (`web/src/api/notes.ts:28-34`).
  `web/src/api/client.ts` is **Must-not-edit** (§2.5) and
  `web/src/api/notes.ts` is **named nowhere** in the proposal — not in §2.3
  Read, not in §2.4 May edit, not in §2.5 (it falls under "every other file
  not named above"), and HS-9 makes it a stop. §2.4 also fixes `flush`,
  `persist` and `enqueue` as "read, not edited", so there is no injection point
  in `NoteView` either.

**Sequence.** Therapist types a paragraph (debounce 400 ms) → the shell's
`quiesce{}` arrives → the wait is answered → the reporter calls
`window.__apuntaFlushBeforeRelease()` → `flush(true)` → `enqueue` → `persist` →
`updateNote` → `fetch('/api/notes/:id', {method:'PATCH', headers:{'content-type':
'application/json'}})` → the maintenance hook sees a non-`GET` under `/api/*`
and refuses 503 `maintenance` → `persist`'s catch sets `saveState='error'` and
rethrows (`:268-270`) → `flush` throws `t('note.unsavedError')` (`:325`) → the
reporter maps it to `save_error` → `quiesce_result{ok:false, blockers:
["save_error"]}` → the shell returns to `verified` and says "finish the save
first", for a save the server itself just refused. **Every future update fails
the same way.** That is F1's failure mode, and V1 Blocker A's success case is
unreachable in the product build (it can only be driven by `app.inject` with a
hand-built header, which is exactly the shape the browser cannot produce).

**Minimal repairs, all owner-level because each crosses a protected file:**
(i) add `headers?: Record<string,string>` to `RequestOptions` + `buildInit` +
`updateNote`'s options — **two** files, one of them Must-not-edit; (ii) a
`Set-Cookie` on the wait answer (the wait response already exists) read by the
maintenance hook by hand-parsing `request.headers.cookie` — no client edit at
all, and it carries **both** ids; (iii) admit by time alone — this is the
"global flush interval" hazard and is exactly what the proposal claims to have
excluded; (iv) move the save into the reporter — rejected, the text lives in
`NoteView`'s refs and `NoteView` is read-only beyond two lines. **(ii) is the
only one that needs no protected file**, and the proposal does not consider it.

### B2 — generation correlation: the report POST is refused by the literal predicate (blocking)

FD5 defines the refusal as "under `/api/*`, **a method that is not `GET` or
`HEAD`**, and a `GET`/`HEAD` outside the **enumerated** exempt read set — … and
the three quiesce routes of FD1". The exempt clause is scoped to `GET`/`HEAD`,
but `POST /api/app/quiesce/report` is a **POST**. Read literally,
`wouldRefuse(report) = true`, so the report is 503; FD4(a) then also *counts*
it, since the counted set is `wouldRefuse` evaluated before admission.

**Sequence.** Quiesce begins → window flushes → `POST …/report` → hook: method
is POST → **503** → the reporter swallows it (FD3(g)) → no report ever arrives →
the flush phase can only close at the 30 s bound → `ok:false, blockers:
["no_response"]`. This is precisely the failure F6 was raised for, resurrected
by F5's repair — and now for *every* quiesce, deterministically rather than as a
race. **V1 Blocker C cannot catch it**: its success case holds a `GET` wait and
polls a `GET` status, both of which the predicate exempts.

**Fix.** Define the exempt set as **method + path**, consulted for **every**
method, and add a V1 case: a `POST /api/app/quiesce/report` is served (200 or
409), never 503, and leaves `shortWrites` at 0.

### B3 — registration is per quiesce, so the preconditions and OA-2's aggregate are unreachable (blocking)

FD3(a): "the entry it made stays in **the quiesce's map** for the life of that
quiesce"; FD3(c): the report applies only when "the body's `windowId` is in
**that quiesce's** registered map". FD1 then aggregates `recording`/`unsaved`
"over the windows registered for the in-flight quiesce (**the falsy pair when
none is**)". But V3 and V4 both require, **before any quiesce exists**, "poll
`GET /api/app/quiesce/status` until `windows >= 1`".

**Sequence (V4).** Page loads → the reporter arms one wait → the spec polls
`status` → no quiesce is in flight → there is no quiesce's map → `windows` is
0 (or undefined) → the precondition never holds → the row burns Playwright's
30 000 ms default and fails **on its own precondition**; the quiesce line is
never written, so the row's actual subject (`ok:true`, then a 503 on
`POST /api/generate`) is never reached. V3 fails identically.

**Same root, worse consequence, for the native close.** A close with no quiesce
in flight reads `recording:false, unsaved:false` — so P5.4's handler defers on
nothing, confirms nothing, and closes. That is C-UPD@1's third close rule
("unsaved text is never discarded silently") violated in the shell, with P5.4's
new V6 green. **V1 Blocker D's success case cannot detect it**, because it sets
the flag directly rather than through a quiesce-free window.

**Fix (one change fixes all three uses).** Keep a **persistent** per-window
table `windowId → { registeredAt, lastSeen, recording, unsaved }` maintained by
the waits, and create a **per-quiesce binding** `windowId → quiesceId` at entry
from that table. Then define `windows`, `recording` and `unsaved` for both cases
(no quiesce / quiesce in flight) and add the V1 case that the close check is
**non-vacuous with no quiesce in flight**.

### B3-bis — `unsaved` cannot be kept fresh within the stated May edit (blocking)

§2.4 puts the `unsaved` publication in "the effect that already registers
`pagehide`/`visibilitychange` (`NoteView.tsx:339-361`)". That effect's
dependencies are `[flush]` (`:361`), and `flush` is memoised over
`[cancelPending, enqueue, t]` (`:329`) — which change only when the **language**
changes. `handleChange` (`:362`) touches refs and React state but not `flush`.

**Sequence.** The therapist opens a note and types for ten minutes → the effect
last ran at mount, when the note was clean, so the published value is `false`
and is never refreshed → the user closes the window natively → the handler reads
`unsaved:false` → the close proceeds → the typed text is discarded silently.
The stale direction is exactly the dangerous one, and **V1 Blocker D's failure
case only tests the opposite** ("with no window registered, `recording` and
`unsaved` are false … so a native close can never see a leftover `true`").
**Fix.** The publication needs its own effect keyed on the state that actually
moves (`text`, `saveState`, `stale` are all React state: `setText` at `:181` and
`:367`, `setSaveState` at `:151`, `setStale` at `:166`, `:173`, `:180`). That is
**one more effect,
not "one added line"** — so OD-5's "two added lines" in `NoteView.tsx` is
materially wrong, and the honest count for the card is: one `beforeunload`
handler + one `unsaved` effect in `NoteView`, and one `recording` effect in
`Capture` (**B9**). With that, the value is at most one render old, which is
acceptable for a close request — but the card must say "the last value the
window published", and the stale bound must be named, because that is a
guarantee weaker than §2.8's Objective sentence as written.

### B4 — gone-detection needs an in-flight socket, and there is none when a window vanishes (blocking)

FD3(f): the wait is answered at entry, and the reporter "re-arms immediately
after each" — after the report. Between the answer and the re-arm the window is
**registered with no open wait**. FD3(d)'s only gone-detector is "`reply.raw`
closes and the reply was never sent".

**Sequence.** Quiesce begins → W is asked, its wait is answered → W's tab is
closed by the user (or the renderer crashes during the flush) → the server holds
no socket for W, so FD3(d) can never fire → no report arrives → the quiesce waits
the **full 30 s** and returns `ok:false, ["no_response"]`. The same happens if
W's flush hangs. Playwright's per-test default is 30 000 ms and no row may
inflate it (§0, FD11), so **V2–V4 cannot contain this** — the row dies on the
timeout and the report reads as a drain failure. Note also that a 30 s stall is
contract-legal ("waits **up to** 30 s"), so nothing in the contract catches it.

**Fix.** Two parts, one normative: (a) the reporter **re-arms the wait before
flushing** (so a socket always exists for a registered window), and (b) the
persistent window table carries `lastSeen`, so a window that has neither a held
wait nor a report within a named bound is marked gone. Then say what the quiesce
does when a window is marked gone **mid-flush** — wait for the report, or fail
fast — because that choice is currently unstated and is the difference between a
1 s and a 30 s quiesce.

### B5 — the drain's registry can be emptied by the very job OA-1 adds (blocking)

`registry.begin(kind, id)` is keyed by **id** and its own docstring says an
already-active id "is taken over by the newer job: from outside, the same id
*is* the same work" (`registry.ts:47-52`). `routes/chat.ts:122` deliberately
registers `refine` with the note id — "The job is the note being refined, so
`active()` can name it" (`:119-121`) — and FD7 puts `save` on the note PATCH
without saying which id it passes.

**Sequence.** A refine is streaming on note N: `begin('refine', N)` → the map is
`{N: refine}`. The flush's admitted save lands and, if the implementer passes the
note id (the only id in scope, and the one `chat.ts` sets the precedent for),
`begin('save', N)` → the map is now `{N: save}` and the **live refine has
vanished from `active()`**. The save's `finally` runs `end(N)` → the map is
**empty while a refine stream is still writing** → the drain returns `ok:true` →
the shell takes its snapshot of a database a stream is mid-write on. Any two
kinds sharing an id collide the same way.

**This falsifies four claims in the proposal** that "the snapshot boundary is
unchanged" (header table F1 row, FD4a, OA-1 invariant iii, §3) — the boundary is
not merely unchanged, it is *weaker* than before, because the new job evicts an
old one.

**Fix.** State the id rule as a fixed decision: **one id minted per job, never a
note, patient or session id** (`draft.ts:88-90` already does exactly this, with
the reason in its comment). Name `routes/chat.ts:122` as a site whose argument
must change — which also touches `chat.test.ts`'s `active()` assertions
(`:1587-1634`) and therefore needs a May-edit wording that authorises changing an
**existing** wired argument, not only "the begin/end pair and the assertions the
registration requires". Add the V1 case: two kinds on the same note are both
visible to `active()`.

### B6 — a *successful* quiesce has no way to leave maintenance (blocking, contract)

FD8: a failed quiesce "returns `ok:false` **and** puts the server back into
normal service in a `finally`"; a successful one "leaves maintenance **on** in
shell mode". A `finally` runs on both paths, so the stated mechanism cannot be a
`finally` — it must be an explicit branch on the settled result (minor), and the
larger problem is that **the server has no way to be told to lift it**.

C-UPD@1's failure table: "snapshotting (no space, write error, integrity fail) →
back to `verified`; nothing installed". At that point the app is still in
maintenance, refusing every write, and nothing will re-quiesce until the next
update attempt — possibly hours. C-BRIDGE@1 rule 2's vocabulary is
server→shell `ready`, `fatal`, `update_request`, `quiesce_result`; shell→server
`update_status`, `quiesce{}`, `shutdown{}`. **None of them lifts maintenance.**
`update_status{state}` is the only existing candidate, and giving it that meaning
is itself a change to what rule 2's message does.

**Fix (owner line).** One of: a new inbound `maintenance_off{}`; or
`update_status{state:'verified'}` given a defined effect on the server; or the
shell restarts the app after a snapshot failure. Whichever is chosen, the
registered-window map's lifetime and the admitted-save allowance's end must be
stated alongside it.

### B7 — the blocker vocabulary grows from two to four while the failure table keeps three (blocking, contract)

C-UPD@1's Quiescence paragraph says the client "reports `ok` or `conflict`".
Its failure table lists the quiescing failures as "**active job, failed save,
edit conflict**". OD-8 rewrites the paragraph to a four-member set
(`conflict`, `save_error`, `recording`) and amends **only that clause** — but
`recording` appears in neither the paragraph as written nor the failure table,
and the table is normative and unamended.

**Consequence.** After OD-8 the contract's own paragraph and its own failure
table disagree, and no row asserts the table, so the drift would land silently.
**Fix.** OD-8 amends the `quiescing (…)` failure-table row as well (naming the
recording refusal), or `recording` is recorded as a client-side-only refusal and
removed from the blocker set.

### B8 — `flush` throws a localized message, so the blocker word is not derivable (blocking, client)

`NoteView.tsx:322,325` throw `new Error(t('note.unsavedConflict'))` and
`new Error(t('note.unsavedError'))`. The strings differ per catalogue:
`shared/src/i18n/en.ts:1159-1160` ("Unresolved conflict" / "Unsaved changes
could not be saved") vs `es-MX.ts:797,800` ("Conflicto sin resolver" / "No se
pudieron guardar los cambios pendientes"). `web/src/lib/i18n.tsx` exports only
`useI18n()` — a hook — and is Must-not-edit; `web/src/lib/maintenance.ts` is a
non-React module, so it has no `t` and no locale. FD6 asserts the three outcomes
"map onto the three outcomes `NoteView.flush()` already has" with **no
mechanism**.

**Sequence (Spanish build).** A forced `stale_write` → `persist` takes the
`stale_write` branch (`:250-267`) → `flush` throws "Conflicto sin resolver" → the
reporter cannot match the English string → it either falls back to `ok:true`
(**a silent success with an unresolved conflict and unsaved text — the
data-loss direction**) or reports `save_error`, which sends the therapist to
"finish the save first" for a conflict instead. The shell config pins
`appLocale: 'en'`, so **V3 — the only row that asserts a blocker word — cannot
detect it**, and no es-MX row covers the shell channel at all (V7 runs
`quiescence.spec.ts` in both projects, but that spec has no flush-blocker
assertion).

**Fix.** Make the classification locale-independent: a third published value
from `NoteView` (`flushOutcome: 'clean' | 'conflict' | 'error'`) — which is a
**third** added line in a file OD-5 authorises two, hence a new owner line — and
name the locale question explicitly rather than relying on `appLocale: 'en'`.
This does not touch the Spanish release restriction; it only stops the client
from depending on a rendered string.

### B9 — the May-edit'd Capture line publishes a stale `recording` (blocking, client)

§2.4: publish `recording !== 'idle'` "in the effect that already calls
`reportDirty(unfinished)` (`:146-148`)". That effect's deps are
`[reportDirty, unfinished]` (`:147-148`), and `unfinished` is
`text.trim().length > 0 || recording !== 'idle' || wav !== null || busy`
(`:150`) — already `true` whenever the therapist has typed anything. Starting or
stopping a recording therefore **does not change the deps**, so the added line
never re-runs. (No `react-hooks` lint rule is configured — `grep react-hooks
eslint.config.js` → no hit — so nothing catches the stale closure.)

**Sequence.** Type text → open Capture → press record → the published value is
still `false` → the quiesce reports no recording blocker → the shell proceeds
with a live recording. The cleanup the review asked for makes it worse: whenever
`unfinished` *does* change, the cleanup publishes `false`. **No row covers it** —
V6(b) tests the `beforeunload` guard, which reads `unfinishedRef.current`
(`Capture.tsx:151`),
not the published flag, and Blocker D sets the flag directly in a unit test.

**Fix.** A separate effect keyed on `recording` (`live.phase`, `:119`): roughly
four lines in a different effect, not "one added line" in this one — and say so
in OD-5, because the May-edit line count is what the owner approves.
