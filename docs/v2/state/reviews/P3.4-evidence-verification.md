## 4. The V2 failure analysis — VERIFIED

This is the load-bearing claim, because attempt 3's premise is that the diagnosis
was right. I checked it against the scripts and the card, not the write-up.

**Part one — the bundle really does carry `server/dist`, `web/dist` and
`bin/whisper-cli`.** `scripts/v2/package-linux-resources.sh` at `ee2ab00` sets
`OUT="$REPO_ROOT/build/linux-resources"` (`:38`) and then, in order:

- runs its own `npm run build:shared && npm run build` at the repository root
  (`:103`) — i.e. it rebuilds the server and the web app itself, with the comment
  that an already-present `server/dist` "may be stale";
- bundles `server/dist/index.js` through esbuild into `$OUT/server/server.mjs`
  (`:141`–`:146`);
- copies `server/migrations/*.sql` into `$OUT/migrations` (`:151`–`:153`);
- copies `web/dist` into `$OUT/web/dist` (`:155`–`:158`);
- copies `whisper-cli` into `$OUT/bin/whisper-cli` and its shared libraries beside
  it (`:246`–`:253`, `:282`), and refuses to continue if the binary cannot run.

All three are confirmed present in the committed producer. And `tauri.conf.json`
at `ee2ab00` has `bundle.resources` mapping `../build/linux-resources/` →
`linux-resources/`, with **no `beforeBuildCommand`** anywhere in the file. So
`tauri build` copies whatever that folder already holds.

**Part two — the old trigger really did watch only `src-tauri/`.** The card's
pre-repair text is recoverable from the diff at `cae4975` (the removed lines). The
old V0 read: *"Run this row whenever any `src-tauri/` file changed"* and *"the row
runs if and only if `git diff --name-only <baseCommit>…HEAD -- src-tauri/` is
non-empty **or** the checkpoint's `changedFiles` lists any path under
`src-tauri/`"*, and its command was a bare
`export PATH=… && npm run tauri:build:test` — no producer. The old V2 freshness
walk likewise enumerated only `src-tauri/**` less `target/` and `gen/`.

**So the reasoning holds.** A server-side or web-side change reaches the AppImage
only through the producer, the producer was never invoked by the old trigger, and
attempt 1 therefore launched a binary whose bundled server predated its own source.
The diagnosis is correct, and the repair (Rule B plus running the producer in
front of the build) addresses the actual mechanism.

**One caveat on the write-up, not the diagnosis.** The task framed this as "the
card at `cae4975` watched only `src-tauri/`". Strictly, `cae4975` *is* the repair
— it is the commit that introduced Rule B. The `src-tauri/`-only trigger is in the
card as `cae4975` **deleted** it. The diagnosis is unaffected; the attribution is
just inverted.

**Verdict: VERIFIED**, with the attribution note above.

## 5. The hook's absence claim — PARTLY VERIFIED, PARTLY UNVERIFIABLE

**The zero-count in `web/dist` itself: UNVERIFIABLE-FROM-COMMITTED-STATE, plainly.**
`web/dist` is gitignored and its bytes are not in any commit. I cannot confirm
zero occurrences of the marker path or the gate string in it, and I am not going
to treat the recorded count as if I had. Same for the "exactly one occurrence in a
deliberately flagged bundle built outside the repository": both artefacts were
built in scratch space and deleted, so there is nothing left to inspect. What
follows is what I *can* establish from committed bytes, and it supports the
mechanism without substituting for the count.

**What is verifiable, and it holds.**

- **The gate is real and correctly placed.** `web/src/main.tsx` at `ee2ab00`
  installs the hook through a single `if
  (import.meta.env.VITE_APUNTA_TEST_IDENTITY === '1')` at `:183`–`:185`. The
  entire hook is the function `installObservationHook` (`:39`–`:181`), and that
  function is referenced from **nowhere else in the file** — I checked every
  occurrence. The gate is therefore not merely surrounding a call; the whole body
  is unreachable when the condition is false, which is what makes dead-code
  elimination able to take the block and its string literals with it.
- **Vite would statically replace it, so the branch is decidable at build time.**
  `web/vite.config.ts` at `ee2ab00` declares no `envPrefix`, no `define` and no
  test environment; there is no `.env*` file anywhere in the committed tree at
  `ee2ab00` (I listed the tree). With the variable absent, the `VITE_`-prefixed
  expression resolves to `undefined`, the comparison is `undefined === '1'`, and
  the branch is statically false — the minifier can drop it and its strings. This
  is the reasoning the evidence gives and it is sound.
- **Nothing in the committed source sets the variable.** `VITE_APUNTA_TEST_IDENTITY`
  appears exactly four times in the whole tree at `ee2ab00`, and I checked each:
  the gate itself in `main.tsx:183`, a doc comment in `main.tsx:27`, and twice in
  the harness — a comment at `:46` and `const GATE_STRING` at `:91`, which exists
  precisely to *grep for* the string. No build script, no `package.json`
  (root or `web`), no CI config and no `.env` sets it. The only place the
  variable is ever set to `'1'` is the V0 command line, which the card builds into
  a git-ignored scratch directory precisely so it cannot reach `web/dist`.

**What that leaves.** The *mechanism* claim — "a release build cannot carry this
hook" — is supported by the committed source: the gate is the only entry point,
nothing in the repository sets the variable, and the flag exists only on a build
command line. The *measurement* claim — "zero occurrences in `web/dist/assets/*.js`
after the producer ran, exactly one in a flagged bundle" — is not something I can
confirm, and V0, the row the card assigns that invariant to, **did not run**
(`BLOCKED`). Note the consequence: the row that was supposed to assert this
invariant is the row that was blocked, so at present the invariant rests on the
mechanism plus a scratch-space measurement that left no artefact. That is a
reasonable position and the evidence is candid about it; it is simply not the same
as a verified count, and attempt 3 should not inherit it as one.

**Verdict: the gate mechanism is VERIFIED; the two occurrence counts are
UNVERIFIABLE-FROM-COMMITTED-STATE.**

## 7. Honesty markers — two findings, one of them substantive

I looked specifically for a row marked PASS whose evidence shows a partial run, a
NOT RUN reported as PASS, and a caveat contradicting a summary line.

**No PASS row rests on a partial run.** V1's collection is real and its negative
control is genuine. V4's file count is exactly reproducible and its totals are
consistent across attempts. V3 I re-ran the three commands myself over committed
bytes and got precisely the recorded exits: command 1 `grep` returns 1 (no matches
— the documented pass), `test ! -e src-tauri/capabilities` returns 0 because the
directory is absent, and the inverted third grep returns 0 because
`VITE_APUNTA_TEST_IDENTITY` and `p3.4-observe` appear nowhere under `src-tauri/`.
**V3 is independently confirmed**, which is the one PASS row I could fully
re-derive from committed state.

**No NOT RUN is reported as a PASS — and the return is conspicuously careful about
this.** V2's five `NOT RUN`s are labelled `NOT RUN` everywhere, the return says so
three times, the checkpoint says so, and `V2`'s evidence states that a `NOT RUN`
(a) blocks approval per the card. That is the right handling and I want it on the
record as such.

**Finding 1 (substantive) — the harness's own summary line counts NOT RUN as
"passed".** `scripts/v2/tauri-security.test.mjs` at `ee2ab00` pushes NOT RUN
results with `ok: true` (`:181`), and the summary line subtracts only entries that
are not `ok` (`:1217`). The result is the committed output line
`13/16 assertions passed, 5 NOT RUN`. Counting the committed output directly:
**8** lines are `PASS`, **3** are `FAIL`, **5** are `NOT RUN` — 16 total. So
"13 passed" is 8 real passes **plus the 5 NOT RUNs**. The trailing `, 5 NOT RUN`
discloses the arithmetic and the row's exit code is correctly 1 (`:1222` returns
non-zero when `notRunCount > 0`), so **the row is not green and no NOT RUN became a
PASS**. But the literal word "passed" covers five items the card says are *never*
`PASS`, printed by the instrument itself. This is the exact confusion the card's
"`NOT RUN` is never `PASS`" rule exists to prevent, and it is the one place in
the two attempts where a summary line overstates. Attempt 3 should fix the tally
to report passes and not-runs as separate figures before it re-runs the row, or
the next reader inherits the same miscount.

**Finding 2 (arithmetic, propagated) — the V2 evidence miscounts its own results.**
`V2-appimage-security.md` opens with "Of sixteen assertions: **11 `PASS`, 3 `FAIL`,
5 `NOT RUN`**". Those sum to **19**, not sixteen, and the committed verbatim block
directly beneath it contains 8 `PASS`. The same wrong figure is repeated in
`docs/v2/state/cards/P3.4.json` (V2's `verification`) and in
`docs/v2/state/returns/P3.4.md` (the criteria table: "11 PASS, 3 FAIL, 5 NOT
RUN"). The correct figures are 8 / 3 / 5. No conclusion changes — the row is FAIL
either way, all five containment assertions are unaffected, and the five NOT RUNs
are unaffected — but the error is in three committed places and would mislead a
reader auditing the assertion inventory. This is a transcription error, not a
misrepresentation of outcome; the honest reading of the surrounding prose is that
the author knew the outcome and simply mis-tallied.

**Finding 3 (minor) — V4's "two independent instruments" argument.** Covered in
§2: `check-no-external-urls.mjs` searches for non-loopback URL hosts, not for the
marker path or the gate string, so it is not a second watcher of that invariant.

**Statements that overreach their own evidence, listed for completeness.** The
return asserts "Every path above is in the card's May edit list, and nothing else
was written" — which is contradicted both by the card's literal text (the returns
are not in May edit) and by `S3.2-ir5.md` being present in `ee2ab00`. And V4's
statement that `web/dist` "holds the producer's own unflagged build" is not
establishable from committed state, since V0 was `BLOCKED` and the producer never
ran in either attempt; whatever `web/dist` held at lint time is unknown to me. The
underlying lint result is not in question.

**Credit where the evidence earned it.** Three things are better than the card
required and should not be lost in the findings above: attempt 1 recorded its own
first V4 failure (exit 2, an unused-parameter error) and the fix rather than
quietly re-running; attempt 2 refused three separate workarounds for V0 and
documented each refusal as the content of the row, including refusing to fabricate
a `whisper.cpp/build-vulkan/bin/` to satisfy a precondition; and both attempts
flagged their own judgement calls for review — the `.invalid` URL assembled to
route around the eslint tripwire, and the pre-open window baseline — rather than
burying them. The `.invalid` workaround is verified as necessary and effective
against the committed rule at `eslint.config.js`, which bans non-loopback URL
literals in both `Literal` and `TemplateElement` positions.
