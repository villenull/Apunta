## Findings

### F1 — DEFECT (blocking). The maintenance hook refuses the flush's own save, so the feature cannot succeed with unsaved text

- **Location:** FD2 ("the flush request is answered to every registered window
  **at entry**"), FD5 ("It refuses 503 `maintenance`: every request under
  `/api/*` whose method is not `GET` or `HEAD`"), FD3(f), V2, V3.
- **The conflict:** maintenance turns **on** at entry, and the flush is asked
  **at entry**. The flush is `NoteView.flush()` → `enqueue` → `persist` →
  `updateNote` (`web/src/components/NoteView.tsx:294-330` → `:276` → `:223-273`),
  which is `PATCH /api/notes/:id` (`web/src/api/client.ts`, and the handler at
  `server/src/routes/notes.ts:76`). A `PATCH` under `/api/*` is on the refused
  side of FD5. `persist`'s catch then marks the save `error` and rethrows, and
  `flush` throws `note.unsavedError` (`NoteView.tsx:325`) — which FD6 maps to
  the `save_error` blocker. So the one case quiescence exists for, **a note
  with a pending debounced edit, always returns `ok:false` with `save_error`
  and the text stays unsaved.** V2's `ok:true` is reachable only because that
  row's editor happens to be idle; V3 escapes it only because the conflict path
  calls `cancelPending()` and enqueues nothing (`NoteView.tsx:295-298`). The
  proposal nowhere states which save the hook must let through.
- **Why the proposal's own escape hatch does not cover it:** FD5's "a request
  already past the hook when maintenance began is never cut" applies only to
  requests **already in flight** at entry. The flush's save starts *after*
  entry.
- **Concrete failure scenario:** a therapist has typed an unsaved paragraph,
  the shell updates, `quiesce{}` arrives; the window flushes, gets 503
  `maintenance`, reports `save_error`; `quiesce_result{ok:false}`; the shell
  goes back to `verified` and says "finish the save first" — for a save the
  server itself just refused. Every future update fails the same way.
- **Bounded fix (one owner choice, see Choice 1):** state the rule explicitly
  and add the matching V1 cases. Either **(A)** the refusal becomes active only
  after the flush phase of the current quiesce has ended (the registry's `save`
  kind plus the short-write counter keep the flush's own save inside the
  drain), or **(B)** `PATCH /api/notes/:id` is exempt from the hook **only
  while a quiesce is in flight**, and the registry `save` kind at
  `routes/notes.ts:77` plus the counter are what the drain waits on. Nothing
  else may be exempted, and the 30 s bound and the "new jobs and writes get
  503" sentence are unchanged under either. V1 gains: *a flush-triggered
  `PATCH /api/notes/:id` inside a quiesce is served and counted; the same
  `PATCH` outside a quiesce's flush is refused 503 with `error:"maintenance"`.*

### F5 — DEFECT (blocking). The short-write counter cannot be told apart from the held long-poll, and "a streaming request is never counted" is not decidable in `onRequest`

- **Location:** FD4 ("the counter is incremented for every request that
  **passes** the hook and decremented in a second `onResponse` hook … at most
  once per request, and a streaming request is never counted"), FD1's
  `GET /api/app/quiesce/wait`, FD2 (the drain waits for the counter), N1.
- **The conflict:** FD4 counts **every** request that passes the hook. The hook
  refuses only non-`GET`/`HEAD` and non-exempt `GET`s (FD5), and FD1's
  `GET /api/app/quiesce/wait` is explicitly in the exempt set — so it passes the
  hook and is counted, and it is held open **for the whole quiesce**. The drain
  then waits for the counter to reach zero while the counter cannot reach zero
  until the drain is over: a self-deadlock. Every quiesce would end
  `ok:false`, and V2 and V4's `ok:true` are unreachable. The same applies to
  V2's own polling of `GET /api/app/quiesce/status`: each poll is a short
  exempt `GET` that increments, so the drain can observe a non-zero counter
  caused by its own observer. "A streaming request is never counted" cannot be
  implemented as written either: at `onRequest` time the response's
  content-type is unknown, and the existing streams
  (`/api/chat/stream`, `/api/generate`, `/api/transcribe`) are `POST`s, which
  the counter's own rule would already have to classify.
- **Concrete failure scenario:** V4 runs; the window's long-poll is counted; the
  drain spins to the 30 s bound; `quiesce_result{ok:false, blockers:["no_response"]}`;
  the row fails against an idle app with nothing running, and FD2's own
  "succeeds when the registry is empty" is untestable.
- **Bounded fix:** make the counted set the *only* thing that can hold a
  connection open being excluded, by name: the counter increments in the same
  `onRequest` hook that refuses, **only** for a request that the refusal rule
  would have refused had maintenance been on — i.e. non-`GET`/`HEAD`, or a
  `GET`/`HEAD` outside the enumerated exempt set — and **never** for the three
  quiesce routes or any exempt read. That is decidable in `onRequest`, needs no
  content-type, cannot count a long-poll, and cannot count the status poll.
  V1 gains: *the held `GET /api/app/quiesce/wait` and every exempt read leave
  the counter at zero while held;* and *a `GET` that passes the hook is not
  counted, a `PATCH` is counted and released.*

### F6 — DEFECT (blocking). Exactly-once release is not guaranteed, and the window registration cannot survive the answer the server sends it

- **Location:** FD3(a), FD3(c), FD3(d), FD3(f); V1's cases for aborts and stale
  reports.
- **Two conflicts, both blocking.**
  1. **Release.** FD4 releases in a second `onResponse` hook "at most once per
     request". Fastify is 5.12.1 (`node_modules/fastify`), where a client that
     aborts before the response completes does **not** produce `onResponse`;
     `onError` fires only for a thrown error, and `onRequestAbort` plus
     `reply.raw`'s `close` are the hooks that do fire. A browser that navigates
     away, a long-poll the reporter aborts, or a socket dropped by the OS
     therefore leaks a count of 1, the drain never reaches zero, and the next
     quiesce on that process ends `ok:false` forever — a leak, not a flake.
  2. **Correlation.** FD3(c) applies a report "only when its `quiesceId` equals
     the in-flight quiesce's id **and that window holds a registered wait in the
     current quiesce**". But the wait is *answered* at entry (FD1, FD2), the
     answer ends that request, and FD3(f) says the reporter aborts the wait
     "after a report is sent". So at the moment the report arrives the window's
     wait is over: under FD3(c) **every legitimate report is a 409**, and with
     FD3(d)'s unregistration the set is empty, so every quiesce ends
     `no_response`. FD3(a) has the same shape — "holds the request open until
     it is asked and then answers `ok` immediately" ends the registration
     before the answer it was waiting for.
- **Concrete failure scenario:** V3 — the window is asked, answers `ok` with
  `conflict`, POSTs the report; the server refuses 409 (no registered wait), the
  quiesce ends `no_response` instead of `conflict`, and the row fails for the
  wrong reason while the text is in fact preserved.
- **Bounded fix (two sentences each, no new route).**
  - Release: the increment sets a per-request flag (a `WeakSet<FastifyRequest>`
     or a symbol-keyed field) and **all** of `onResponse`, `onError`,
     `onRequestAbort` and `reply.raw.once('close')` call one `release(request)`
     that decrements only if the flag is still set, then clears it. V1 gains an
     aborted-request case: *a request aborted mid-flight leaves the counter at
     zero*, and *two terminal hooks for one request decrement once*.
  - Correlation: registration is keyed to the **window**, not to one request.
     The reporter mints a `windowId` (uuidv7) once per window; `GET
     /api/app/quiesce/wait` takes it as a query parameter, `POST
     /api/app/quiesce/report` carries it in the body beside `quiesceId`, and
     the server keeps `{ windowId → quiesceId }` for the life of the quiesce.
     Answering one wait does **not** unregister the window; a window is
     unregistered only when its **currently held** wait's socket closes with no
     replacement wait for the same `windowId` inside the quiesce, and rule (c)
     then reads "the `windowId` is registered **for this `quiesceId`**", which
     a re-armed wait re-establishes before the report is sent. V1 gains: *a
     report whose `windowId` is registered for the in-flight `quiesceId` is
     applied even though its wait was already answered* and *a report from a
     window that never re-armed is refused 409*.

### F7 — DEFECT. "Counted" has no observable home, and the 409 body is unspecified

### F8 — DEFECT. The status route cannot carry the close policy §2.8 hands to P5.4

- **Location:** FD1's status shape `{quiescing, activeJobs, shortWrites,
  windows, maintenance}`; FD9; §2.8's Objective sentence, Fixed-decision bullet
  and new V6.
- **The conflict:** §2.8 promises P5.4 that the native close request "runs the
  same check as the browser close … close is deferred while a save is in flight,
  an active recording asks for confirmation, and unsaved text is never discarded
  silently". The route carries **one** of those three: a save in flight is
  visible as `activeJobs` containing `save` (once FD7 registers
  `routes/notes.ts:77`) and as `shortWrites > 0`. It carries **neither** of the
  other two: `recording` has no server-side signal at all (FD7 states this, and
  `web/src/lib/recorder.ts` is Must-not-edit), and unsaved text exists only in
  `NoteView`'s refs. The native handler cannot read them another way:
  **C-BRIDGE@1 rule 4 forbids Tauri IPC from web content**, so `src-tauri`
  cannot ask the webview. So the amendment as drafted either cannot be
  implemented or silently delivers one third of the guarantee it promises.
  Separately, §2.8's new P5.4 V6 bundles "the browser-mode `404` assertion for
  `GET /api/app/quiesce/status`" into a `cargo test` row — a Rust unit test
  cannot make an HTTP request to a browser-mode server, and that assertion
  already exists in P5.3's V1.
- **Concrete failure scenario:** P5.4 implements the bullet as written, reads
  `activeJobs`, and closes the window during a recording; C-UPD@1's "an active
  recording asks for confirmation" is enforced in the browser and nowhere in the
  shell, and P5.4's new row is green.
- **Bounded fix (one owner choice, see Choice 2):** either **(A)** the status
  route gains two booleans, `recording` and `unsaved`, aggregated over the
  registered windows and published by each window on the wait it re-arms (the
  `windowId` from F6 carries them as query parameters; `recording` from the
  `Capture.tsx` line of F2, `unsaved` from one further added line in
  `NoteView.tsx`, which is already OD-5-gated), and §2.8 stands as written; or
  **(B)** §2.8's Objective sentence is narrowed to the half the route can carry
  and the amendment says in terms that the recording and unsaved-text halves
  stay browser-side (V6(b)) because C-BRIDGE@1 rule 4 forbids the IPC that
  would carry them. **(B) is a reduction of a contract guarantee and needs its
  own owner line; (A) is additive.** And in either case P5.4's V6 becomes the
  three Rust transitions only, with the 404 cross-referenced to P5.3's V1
  instead of asserted from `cargo test`.

### F9 — DEFECT. V3 and V4 have no waited-for precondition for the window's registration

- **Location:** V3, V4, FD3(e).
- **The conflict:** V2 polls `GET /api/app/quiesce/status` until it reports an
  active `refine` job, which is the right pattern. V3 and V4 have no
  equivalent: the trigger line is appended as soon as the page state is observed,
  and if the reporter's first long-poll has not been registered the quiesce
  hits FD3(e) ("the set empty since entry") and returns `no_response`. V4's
  expected cell is `ok:true`, so a startup race fails the row for a reason that
  has nothing to do with quiescence.
- **Concrete failure scenario:** V4 loads the app, appends `{"quiesce":{}}`
  immediately, and the reporter's first `GET …/wait` lands after the drain has
  already taken its "empty since entry" reading; `ok:false, blockers:
  ["no_response"]`; a re-run passes; the row is a coin flip.
- **Bounded fix:** V3 and V4 both start by polling `GET
  /api/app/quiesce/status` until `windows >= 1` (the same waited-for
  precondition, named in the row), and every shell row states that a quiesce
  line is written **only** after that precondition, never on a timer.

### F10 — DEFECT. V6(a)'s mechanism is not the one Playwright uses

- **Location:** V6(a), OD-5, FD9.
- **The conflict:** V6(a) expects that "a close attempt **raises a
  `beforeunload` dialog**, and after the dialog is dismissed the editor **still
  holds the typed text**". Playwright **auto-dismisses** dialogs when no
  `dialog` listener is registered, and the row does not say that one is. It
  also does not name what a "close attempt" is in a browser tab (`page.reload()`,
  `page.goto` elsewhere, `window.close()`), nor which observable proves the
  navigation was refused.
- **Concrete failure scenario:** the spec calls `page.goto('/')`; Chromium's
  dialog is auto-dismissed, the navigation is refused, and the assertion "a
  dialog was raised" fails because nothing listened for one — or, if the spec
  asserts on the thrown navigation error, it asserts on Playwright's wording,
  which is not a contract.
- **Bounded fix:** V6(a) states — register `page.on('dialog', …)` **before** the
  close attempt and assert the dialog's `type() === 'beforeunload'`; dismiss it
  explicitly; then assert the app is still mounted and
  `note-body` still holds the typed text. The close attempt is named once
  (`page.reload()`). No assertion on a thrown navigation error, and no
  assertion that the text is recoverable after a reload (the proposal already
  refuses that claim, correctly).

### F15 — DEFECT (blocking). "A FIFO and two control paths" does not say which is which, and the FIFO reading cannot work

- **Location:** §1.3, V2, V3, V4 ("the spec appends `{"quiesce":{}}` to the
  harness's command path", "reads the result from the harness's output path").
- **The conflict:** the harness "creates a FIFO **and** two control paths" —
  three things, or a FIFO that is one of the two? Nothing states how the spec
  learns either path (there is no env var, no printed line and no fixed
  location), so the spec cannot be written at all. And if the command path is
  the FIFO, the row is broken three ways: opening a FIFO for writing **blocks
  until a reader has it open**, so a spec that appends before the harness has
  read hangs until Playwright's 30 000 ms budget; a FIFO has **no line
  framing**, so a partial write is delivered as a chunk and the server's reader
  must do its own buffering; and when the harness exits, the spec's next write
  takes `EPIPE`. "Appending" is also the wrong verb for a FIFO.
- **Concrete failure scenario:** the implementer creates a FIFO for commands and
  a regular file for output; the spec appends the quiesce line before the
  harness's read end is open and the row times out at 30 s — reported as a
  drain failure.
- **Bounded fix (exact, and it removes all three hazards):**
  - Both paths are **regular files**, named deterministically from the run
    folder so the spec computes them without asking: `APUNTA_DATA_DIR` is
    `<runFolder>/data`, so the two are `<runFolder>/quiesce/stdin.cmd` and
    `<runFolder>/quiesce/stdout.log`, i.e.
    `join(dirname(APUNTA_DATA_DIR), 'quiesce', 'stdin.cmd')` and
    `…/stdout.log`. Both are created mode `600` and both `realpath`s must stay
    under `/tmp/apunta-v2/` (C-ISO@1 rule 1).
  - The spec appends exactly one complete line per trigger with a single write:
    `fs.appendFileSync(path, JSON.stringify({ quiesce: {} }) + '\n')`
    (`O_APPEND`, one line, well under any atomicity limit). Never `echo >>` on a
    FIFO; never a partial line; never a second line in one write.
  - The harness forwards stdin by **watching the file's size** (poll or
    `fs.watchFile`), reading from its last offset to EOF, splitting on `\n`,
    forwarding only complete lines, and keeping the remainder for the next
    pass. It ignores an empty or non-JSON line and logs it; it never exits and
    never throws on the child's behalf.
  - The harness appends the child's stdout to `stdout.log` as it arrives. The
    spec reads that file and matches **only** lines that `JSON.parse` to an
    object with `type === 'quiesce_result'`, and asserts exactly one such line
    per trigger — because under `APUNTA_SHELL=1` the same stream also carries
    pino log lines and P3.3's `ready` and `fatal` lines (C-BRIDGE@1 rules 1, 2).

### F16 — DEFECT (blocking). The harness states no ownership check and no ready-line check

### F17 — DEFECT (blocking). The harness's process ownership is unspecified, and "kills only what it started" is the rule that matters here

- **Location:** §1.3 ("exits with the child's code"), §2.5 (Must-not-edit
  `scripts/v2/sandbox.mjs`), C-ISO@1 rule 7.
- **The conflict:** C-ISO@1 rule 7 is "Cleanup kills only the process group the
  wrapper created. **Never `pkill`, never the Ollama daemon**", and
  `sandbox.mjs` implements it precisely: spawn `detached: true`, then
  `process.kill(-child.pid, 'SIGTERM')`, then `-SIGKILL` after 5 s, and nothing
  else (`scripts/v2/sandbox.mjs:254-280`). The proposal says only "exits with
  the child's code", which leaves the SIGTERM path unspecified — and Playwright's
  `webServer` **kills its command** when the run ends. Without an explicit
  ladder the natural implementations are the two forbidden ones: `pkill -f
    'server/dist/index.js'` (which would also kill a developer's live instance
  and any other sandbox row's server) or killing whatever holds the port.
- **Concrete failure scenario:** the harness is written with
  `pkill -f "node server/dist"` in its cleanup; a developer's own `npm start`
  dies, and a second sandbox row on another port dies with it.
- **Bounded fix:** the harness spawns the server exactly as `startServer` does
  — `spawn(process.execPath, ['server/dist/index.js'], { cwd: repoRoot, env,
  detached: true, stdio: ['pipe', logFd-ish, …] })` — and its only ever
  signals are `process.kill(-child.pid, 'SIGTERM')` then
  `process.kill(-child.pid, 'SIGKILL')` after 5 s, guarded by the same
  exit-code checks. `SIGINT`/`SIGTERM`/`SIGHUP` to the harness are forwarded to
  that group and the harness then exits with the child's code. **Never `pkill`,
  never `kill` by port, name or pattern, never the Ollama daemon, never any
  process the harness did not spawn.** Add one V1 case (or one assertion inside
  the harness's own `--selftest` mode, mirroring `sandbox.mjs selftest`) that
  the harness's cleanup signals exactly one pid and that the recorded signal
  list contains no pattern kill.
