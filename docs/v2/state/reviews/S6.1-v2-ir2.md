## D. Surviving defects, with the failure scenario for each

### R-01 — V1(b) is unsatisfiable as written: the allow-list it names absorbs two of the five words it expects — **DEFECT**

> **(b) Spanish whole-word** — `findMisspellings('¿Cómo amanece, ñandú? José Ramírez', …)`
> with an allow-list built by `allowedWords(['José Ramírez'])` records the words
> `Cómo`, `amanece`, `ñandú`, `José`, `Ramírez` …

`findMisspellings` consults the allow-list **before** it records anything:
`if (allow.has(plain.toLowerCase())) continue;` (`spelling.ts:47`), and the row's
own allow-list is built from `allowedWords(['José Ramírez'])`, which under the
new `WORD` yields exactly `{'josé','ramírez'}` (`spelling.ts:160-167`). So
`José` and `Ramírez` can be neither pushed to `found` nor asked of the speller.
Driving a faithful transcription of `spelling.ts:41-52`/`:160-167` with the new
`WORD` on that sentence: `found[].word` is `['Cómo','amanece','ñandú']`, the
speller was asked about `['Cómo','cómo','amanece','amanece','ñandú','ñandú']`,
and the five-word expectation is `false`. This is IR-04's own mechanism error
("the recorded list is neither the old pattern's output nor the new pattern's
output") surviving in the row IR-04 did not name.

**Failure scenario.** The implementer writes the case as specified, it returns
three words, the row goes red, and §9.1's contingency ("the only responses are
to fix the implementation or bring the discrepancy to the coordinator") points at
the wrong thing — the implementation is right and the expectation is wrong. Worse,
the tempting "fix" is to drop `allowedWords` from the call, which deletes the
allow-list half of the case and with it the `José Ramírez` path §7 claims the
allow-list proves for free.

**Bounded fix.** Split (b) into two assertions, both satisfiable and together
stronger: with an **empty** allow-list and a stub that flags everything,
`found.map((m) => m.word)` is exactly `['Cómo','amanece','ñandú','José','Ramírez']`
and none of `C`, `mo`, `n`, `Jos`, `ramirez` appears; and with
`allowedWords(['José Ramírez'])`, `found` is exactly `['Cómo','amanece','ñandú']`
**and** the stub was never asked about `josé` or `ramírez`. The second half is
also what proves the allow-list improvement, because the old pattern tokenises
that entry to `jos` + `ram` + `rez`.

### R-02 — V1(c)'s offset half is under-specified and, under the reading §7 suggests, cannot hold — **DEFECT**

> **the offsets are exact in each input separately** — `original.slice(m.start, m.end) === m.word`
> holds for both, and each `m.end` is the code-unit length of `m.word` **in that string**.

Two problems. First, the row never says what `Misspelling.word` is. Today it is
the **raw** match (`spelling.ts:49`, `word: match[0]`), and §7's per-word NFC is
applied to the value handed to the speller; if the implementer instead reports the
normalised token — the natural reading of "per matched word" — then in the
decomposed input the slice is 7 code units of `o` + U+0301 and `m.word` is the
6-code-unit NFC form, and the conjunction is false. Demonstrated on
`Vino a la sesión con José mañana` and its NFD form: precomposed span 6,
`slice === word` true both ways; decomposed span 7, `slice === word` true for the
raw match and **false** for `plainWord(match)`. Second, `m.end` is an absolute
index, not a length: in the decomposed case `m.end` is 17 and the length is 7,
so the clause is false as written even under the raw reading, for any word that
does not start at offset 0.

**Failure scenario.** A correct implementation goes red on a self-contradictory
assertion — the exact contingency §9.1 exists to prevent — and the natural
"repair", deleting the offset half, would drop the one property per-word NFC
exists to provide.

**Bounded fix.** One sentence in V1(c), and no change to §7: `Misspelling.word`
is the **raw matched substring of the input being scanned** (unchanged from
`spelling.ts:49`), the speller is asked with `plainWord(word)`, and the offsets
half asserts `original.slice(m.start, m.end) === m.word` and
`m.end - m.start === m.word.length` **in each input separately**; the
cross-input half compares `{plainWord(m.word)}` over the flagged words, not the
raw `m.word` set. That makes every clause true as written, in both encodings,
under one implementation.

### R-03 — V1(a)'s corpus cannot be ASCII-only, and the precondition is repeated in four places — **DEFECT**

The row calls the corpus "**fixed ASCII-only**" and then specifies it as
containing "contractions with `'` and `’`, digits, punctuation, a URL fragment,
**an em dash**" — and the literal old pattern it compares against is
`/[A-Za-z]+(?:['’][A-Za-z]+)*/g`, which itself contains U+2019. Checking the
corpus I built to that specification: the characters above U+007F are `['’',
'—']`, so the corpus is not ASCII-only and cannot be. The same over-tightened
wording is load-bearing in three more places: §7's proposed source comment (`:482-486`, "for **ASCII-only text** this pattern matches exactly what the old one matched"), §7's F1 paragraph (`:500-504`), and §1's changelog row for F1 (`:74`).

**Failure scenario.** Two directions, both bad. An implementer who reads
"ASCII-only" as a hard requirement drops `’` and the em dash from the corpus and
loses the two contractions and the dash the row exists to cover; an implementer
who follows the corpus keeps them and then cannot satisfy the row's own
description of it, so the case is either weaker than specified or self-contradicting
on review.

**Bounded fix.** One substitution, in all four places: the precondition is "the
corpus contains **no Spanish letter and no combining mark** (U+0300–U+036F) — the
two classes the new pattern admits and the old one does not", and the curly
apostrophe and the em dash are explicitly *inside* the precondition because the
old pattern matches `’` and neither matches `—`. Verified on the corpus above: the
two tokenisations are identical, and on a Spanish corpus they diverge exactly as
the row says they would (`cómo` … `sesión` against `c`, `mo`, `sesi`, `n`).

### R-04 — V3's identity half feeds `comm` unsorted input, and no row executes it — **DEFECT**

The set difference that identifies the Spanish pair is specified as
`comm -23 observed-es-MX.txt observed-chromium.txt`, and V3's command sorts only
the asset list (`… | rg '\.(aff|dic)$' | sort`), never the observed file, which
the test writes "one per line" in observation order. `comm` requires sorted input.
Demonstrated on two synthetic observed files: with the two lines in one order
`comm -23` exits 1 and prints both; with the same two files' lines in the other
order it exits 0, prints the same two lines **and** writes `comm: file 1 is not in
sorted order` / `comm: input is not in sorted order` to stderr. A wrong-but-green
result is the failure mode this row was written to catch.

Separately, `comm` appears only in *Expected* and in §10 — the same
"prose about a step rather than the step" shape IR-03 removed from V4. It cannot
sit in V3's command (V6's file does not exist yet), but no row runs it either.

**Bounded fix.** Two clauses: the case writes its two observed names **sorted**
(`sort` before the write, or one per line in sorted order), and §10's
`V3-assets.md` names the executed command —
`comm -23 <(sort observed-es-MX.txt) <(sort observed-chromium.txt)` — with its
output and both inputs recorded, so the identity half is a recorded result rather
than an instruction to a reader.
