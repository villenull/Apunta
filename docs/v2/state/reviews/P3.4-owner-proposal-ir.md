## IR-01 — CLEAR — §A.1 is correct, from the pinned source

`src/manager/webview.rs:167-180` pushes, into the **main frame of every
webview**, `Object.defineProperty(window, 'isTauri', …)` and, when absent,
`Object.defineProperty(window, '__TAURI_INTERNALS__', { value: { plugins: {} } })`
— no capability, config or feature gate on that path. `scripts/core.js:81` then
does `Object.defineProperty(window.__TAURI_INTERNALS__, 'invoke', …)`. So
`typeof window.__TAURI_INTERNALS__ === 'object'` and
`typeof window.__TAURI_INTERNALS__.invoke === 'function'` hold in every Tauri v2
webview, and `src-tauri/` cannot be edited to change that (the card's
`srcTauriTouched: false` must stay false — confirmed in
`docs/v2/state/cards/P3.4.json`).

`withGlobalTauri: false` governs `window.__TAURI__` only: the global bundle's
last statement is `window.__TAURI__=__TAURI_IIFE__`
(`scripts/bundle.global.js`, final line), and that script is what the flag
gates. The recorded observation `tauri=undefined&tauriInternals=object`
(`docs/v2/evidence/P3.4/V2-appimage-security.md:35`) is therefore the correct
observation of a correct build. **The amendment is unavoidable, not optional.**

## IR-02 — CLEAR — §A.2's probe is real, and the denial string is the right one

Checked in the pinned crate, not assumed:

- `src/app.rs:1259` — `self.handle.plugin(crate::event::plugin::init(self))?`
  inside `register_core_plugins`, unconditional in every app.
- `src/event/plugin.rs:68-75` — the handler is exactly
  `listen, unlisten, emit, emit_to`, so `plugin:event|listen` names a command
  that **exists**.
- `src/webview/mod.rs:2076-2109` — the ACL branch is
  `(plugin_command.is_some() || has_app_acl_manifest || !is_local)
  && request.cmd != FETCH_CHANNEL_DATA_COMMAND && invoke.acl.is_none()`.
  `plugin_command` is `Some` for a `plugin:` command, so the branch is taken
  regardless of origin; and `resolve_access` (`src/ipc/authority.rs:462-489`)
  returns `None` for an unknown/denied command, so `invoke.acl.is_none()` holds
  with `"capabilities": []`. **The ACL gate fires before any argument is
  deserialised**, which is why a `null` payload cannot turn into a serde error
  here.
- Release vs debug: `src-tauri/Cargo.toml:22-28` sets
  `[profile.release]` with no `debug-assertions`, and `package.json:24` runs
  `tauri build …` (release by default). So the `#[cfg(not(debug_assertions))]`
  arm at `mod.rs:2105-2108` is the one taken, and the string is
  **`Command plugin:event|listen not allowed by ACL`**, built from `request.cmd`
  — the *full* command name.
- Discrimination is real: the two other rejections are
  `Command listen not found` (`mod.rs:2162`/`:2167`, from `command_name`, the
  **stripped** name) and the debug-only `resolve_access_message` prose. Neither
  can produce the ACL string. And the value reaches JavaScript as a plain string:
  `reject` (`src/ipc/mod.rs:409`) serialises the `Err`, and `format_callback`
  emits `runCallback(<errorId>, "…")` — a JS string literal — which `core.js:88`
  passes straight to `reject`. So `String(e)` in the hook is exactly that text.
- Harmlessness is not load-bearing, and the proposal says so correctly: a
  *reachable* `listen` with a `null` payload could not resolve — it would reject
  with a serde error, i.e. `FAIL` loudly. Pass requires the ACL text.

**Conclusion: §A.2 is correct as written.** One wording defect only — see IR-10.

## IR-03 — DEFECT · BLOCKER — as written, (a) cannot pass on a correct build

§B sets `ipcProbe` to `pending` at install and publishes the fact set from the
**first** `poll()`, which runs synchronously at `web/src/main.tsx:182` —
i.e. **before** the `invoke` promise can settle. So the *first* fact line on
stderr carries `ipcProbe=pending&ipcProbeMsg=`. §A.3's
`waitForFact` predicate accepts it (all five keys are present), returns it
immediately, and the `check` then fails because `ipcProbe !== 'rejected'`.

This is not a flake and not a race: it is the guaranteed ordering. **As drafted,
attempt 5's only real chance to go green on (a) fails on the first poll.**

**Exact repair — §A.3's `assertNoIpc` predicate gains one clause (and only
this):**

```js
  const found = await waitForFact(
    () => run.output.stderr,
    (line) =>
      line['tauri'] !== undefined &&
      line['ipc'] !== undefined &&
      line['ipcInvoke'] !== undefined &&
      line['ipcProbe'] !== undefined &&
      line['ipcProbe'] !== undefined &&
      line['ipcProbeMsg'] !== undefined &&
      line['ipcProbe'] !== 'pending',        // <-- the added clause
    30_000,
  );
```

and the `observed` string keeps naming `ipcProbe` verbatim, so a genuine
`pending` at the 30 s mark is still visible in the detail. The card's
"Outcomes are told apart" wording (`pending` when the 30 s window ends is a
`FAIL`) then holds as written, because the harness no longer returns early.

*Alternative, equally valid and arguably cleaner:* have the hook omit `ipcProbe`
and `ipcProbeMsg` from the fact set until the promise settles. Then "no `ipc*`
fact line arriving at all is `NOT RUN`" already covers the pending case, and no
predicate clause is needed. **Either repair is acceptable; the first is the
smaller diff and keeps §B's table exactly as the coordinator signed it.** The
proposal must pick one and say so.

## IR-04 — DEFECT · BLOCKER — `clickPath` cannot change; the fix is already in the fact set

§D makes the patient-open proof "`clickPath !== preClickPath`", with `clickPath`
defined as `location.pathname`. In this app, selecting a patient does **not**
change the path:

```
web/src/routes/Workspace.tsx:221-225
  const selectPatient = useCallback((id: string) => {
    navigate(`/?patient=${encodeURIComponent(id)}`);
  }, [navigate]);
```

`navigate('/?patient=…')` changes the **query string**, not the pathname. The
row that would consume it is `clickAndWaitForChange(…, PATIENT_LABEL,
undefined, 30_000)` (`scripts/v2/tauri-security.test.mjs:1046-1052`). So the
predicate is unsatisfiable on the very product behaviour it is meant to prove —
a permanent FAIL caused by the harness, exactly the trap §10.5 anticipates and
§8.4 defers to the owner. **It does not need the owner at all.**

The fix needs **no new hook fact and no card amendment**: `href`
(`location.href`) has been in the fact set since attempt 2
(`web/src/main.tsx:71`, asserted in the card at `:176-178`) and already changes
on this navigation, while nothing else in this app changes `location.href`
without a navigation. That is precisely the property that makes it the right
instrument — and it is stronger than `rectSignature`, because a scrollbar, an
animation, a clock and a late layout shift all leave `href` alone.

**Exact repair — §D's first bullet, before:**

> **Patient-open fact:** the most recent fact line with `clickN` > pre-click
> `clickN` **and** `clickPath !== preClickPath**. …

**after:**

> **Patient-open fact:** a fact line with `clickN` > pre-click `clickN`
> **and** `href !== preClickHref`, read from the already-published `href` fact
> (`location.href`). **Not `location.pathname`:** this app's patient row
> navigates to `/?patient=<id>`, which leaves the path unchanged
> (`web/src/routes/Workspace.tsx:222-224`), so a pathname predicate would be
> unsatisfiable on the very behaviour it is meant to prove. `href` changes only
> on a navigation, and nothing in this app navigates on a timer, a clock or a
> layout shift.

and drop `clickPath` from §B's table entirely — **one fewer fact, one fewer
string in the shipped bundle, no card change beyond §A.3's.** Consequently
**§8.4 disappears from the owner's list**: the `rectSignature` demotion is a
tightening the card already demands ("a click that landed is proved by the
published fact set changing", `docs/v2/cards/P3.4.md:542`), and the fact it now
demands to is one the page already publishes.

## IR-05 — DEFECT · BLOCKER — the `NOT RUN` cascade is dropped

The card requires that an unreadable hook makes **(a), (b), (c), (d)'s handler
half and (e) `NOT RUN` together** (`docs/v2/cards/P3.4.md:237-243`, restated at
`:584-593`). Today that cascade lives in exactly one place — the
`first === null` branch (`scripts/v2/tauri-security.test.mjs:843-873`). §A.3's
new `assertNoIpc` adds a **second** `notRun` + `return` that marks (a) alone and
lets (b), (c), (d) and (e) run on. So a run where the probe fields never arrive
would report (a) `NOT RUN` alongside a `PASS` on (b) or (c) — a card-contract
violation, and a report that reads as if part of the row was decided.

**Exact repair — one line, and it removes the second cascade rather than
writing it.** Widen the *existing* gate so it waits for the same complete fact
line, and `assertNoIpc` then never has to invent its own:

```js
    const first = await waitForFact(
      () => run.output.stderr,
      (fact) => fact['href'] !== undefined && fact['ipcProbe'] !== undefined,
      45_000,
    );
```

The existing `first === null` branch then fires for "the probe fields never
arrived" as well as "the channel is dead", and its five-row `notRun` block —
verbatim, unchanged, with its existing cause text extended by the words
"including the IPC probe facts" — covers both. **With this one line, §A.3's
`if (found === null) { notRun(...); return; }` becomes unreachable and should
be deleted**, leaving `assertNoIpc` with one `check` and one pass condition,
which is what the card asks for.

## IR-06 — DEFECT — the calibration is circular as specified

§C.2 step 4 says to `xdotool mousemove --sync <X> <Y>` "in screen coordinates"
for a target `P1`/`P2` expressed in **CSS client pixels**. Nothing says how `X`,
`Y` are obtained, and computing them requires the transform step 5 is about to
solve. As written an implementer must invent the bootstrap, and the two
"identical on both sides" targets are not.

**Exact repair — insert as §C.2 step 3a, and make step 4 reference it:**

> **Bootstrap (the only place an untransformed native point is asked for).**
> Move 1 places the pointer at `(windowX + cx₁, windowY + cy₁)` — the naive
> 1:1 assumption, stated as an assumption and used only to obtain the first
> observation. If no `pointermove` arrives for it, the calibration is `NOT RUN`
> with the cause "the first bootstrap point produced no pointermove"; **no click
> is issued**. Move 2 places the pointer at `(X₁ + Δcx, Y₁ + Δcy)` where
> `Δcx = cx₂ − cx₁` and `Δcy = cy₂ − cy₁` — a *displacement*, which is
> transform-independent and needs no solved `k`. Both moves press nothing.
> Every other native point in this procedure is computed through the solved
> transform.

This is the only sound two-point bootstrap: a displacement is invariant under
any affine map, so `k_x` and `k_y` fall out of the second observation even
though `k` was unknown when it was asked for.

## IR-07 — DEFECT — §C.2 step 6's validation is an identity

Per axis the transform has two unknowns (`k`, `o`) and step 4 supplies exactly
two observations, so the fit is **exact by construction**. "The per-axis `k`
computed from the pair must be the same to within `0.01`" compares a quantity
with itself, and "re-deriving the origin from each observation separately must
agree within 1 px" is likewise automatic. A check that cannot fail is the exact
family of defect AM-183 records as having cost this card three attempts; it
should not be re-introduced as validation.

**Exact repair — replace step 6 with a statement of what the real third-point
test is:**

> **6. The two-point fit is exact by construction and is therefore not a
> validation.** Two observations fix two unknowns per axis, so nothing is left
> over to disagree. The out-of-sample test of the transform is **step 8**:
> the click point is at neither calibration target, its predicted native
> position is read back within 1 px, and the page's own `clickCX/clickCY` must
> land within 2 px of the point aimed at, in a direction the calibration never
> constrained. Steps 6–8 assert, in order: `0 < k ≤ 4`; the click point's
> predicted native position lies **inside the window rectangle** read in step 1;
> and the loop closure of ±2 px in client space. A run that cannot produce two
> observations is `NOT RUN` with "the page published no pointermove for
> calibration target N", and **no click is issued**.

## IR-08 — DEFECT — no containment assertion, and a free check is discarded

§C.2 never asserts that any point it asks for lies inside the window. The
diagnosis prescribed exactly this (`P3.4-diagnosis-2026-10-03.md:242`: "assert
the click point lies inside the window"), and the proposal drops it. Without it,
a mis-solved `o` can put the pointer on the root window, on the splash, or — on
the desktop-session fallback the harness takes when `xvfb-run` is absent
(`scripts/v2/tauri-security.test.mjs:367-372`) — over an unrelated application.
A warp alone presses nothing, so the blast radius is small, but it is exactly
the "arbitrary positions must not leave the app" property, and it is cheap.

Meanwhile `getmouselocation --shell` also prints a **`WINDOW`** field ("the
window id of the window directly underneath the mouse",
`xdotool.1:286-300`) and §C.3's `moveTo` parses the whole line into a map and
then uses only `X`/`Y`.

**Exact repair — add to §C.2 as step 4a, and to `moveTo`'s consumers:**

> Before every `mousemove`, the point asked for must satisfy
> `windowX ≤ X < windowX + WIDTH` and `windowY ≤ Y < windowY + HEIGHT`;
> otherwise the step `FAIL`s with the point and the window rectangle and
> **issues no move and no click**. After every `mousemove`, `moveTo` also
> returns `getmouselocation`'s `WINDOW`; where it equals the app window id, or
> where `xdotool windowancestry` reports that id as an ancestor, the check is
> satisfied, and where it is neither the check `FAIL`s with both ids. This is
> the "the pointer is over the app" half of the loop closure, and it is what
> makes an arbitrary synthetic position safe to request at all.

Note the calibration bootstrap of IR-06 is deliberately allowed to violate the
containment rule's *first* clause — it must, or it cannot bootstrap — so the
rule applies to every point **from the second move onward**, and its
`NOT RUN`/`FAIL` reason is then "the bootstrap point produced no pointermove",
which is a diagnostic, not a safety failure.

## IR-09 — DEFECT — hover state races the click, and the `clickEl` rule is unnamed

This is the finding that would most plausibly cost attempt 5, and it is not in
the proposal.

Hovering a patient row **inserts a tooltip into the DOM**:
`web/src/components/PatientsColumn.tsx:1174-1184` (`onMouseEnter` →
`setTip({ id, rect })`), rendered at `:1425-1442` as an absolutely positioned
`div.project-tip[data-testid="patient-tip"]` at
`left: rect.right + 20, top: rect.top`. Three consequences:

1. **The tooltip is a text leaf.** `readRects` (`web/src/main.tsx:99-113`)
   collects every childless element with 1–64 characters of `innerText`, so
   hovering adds a leaf whose text is the patient name. A second rect labelled
   `John Smith` therefore exists while the pointer rests on that row — and
   `rectForLabel` returns the **first** match in the map, silently.
2. **The tooltip is positioned to the right of the row, at the row's own
   `top`.** The patients column is the left sidebar, so `rect.right + 20` lands
   in the notes column at the patient's vertical band. If the pointer is still
   inside the tooltip when `xdotool click 1` fires, `elementFromPoint` returns
   the tooltip's `div`, the click goes to a non-interactive `div`, and the note
   never opens — a clean, diagnosable failure only because of `clickEl`.
   `setTip(null)` on `onMouseLeave` is a React state update, so it is not
   guaranteed to have flushed before the press that follows the warp.
3. §C.2 step 8 says "a `clickEl` that is not the label's own leaf is a `FAIL`"
   without saying what "the label's own leaf" is. As written that is a judgement
   call at the moment it is least wanted.

**Exact repair — three concrete clauses, appended to §C.2 step 7, before the
click:**

> After the warp and the ±1 px read-back, **wait 600 ms — two poll intervals**
> — so the hover transition the warp itself caused has flushed, and the warp
> publishes a `pointermove` fact line in that time, so the wait costs nothing
> against the 30 s window. Then **re-read the target's rectangle from the live
> buffer** and recompute `T` from it; if the rectangle has moved, re-warp once
> (a move, not a click — §C.2 step 9's "exactly one click per target" is
> untouched) and re-read once more. Then click.
>
> **The comparison rule for `clickEl` is exact:** the harness compares
> `clickEl`'s `tagName`, its `data-testid` (empty when absent) and its trimmed
> `innerText` against the same three fields read from the **rectangle it
> selected**, which the hook already publishes per rectangle. Equality on all
> three is the pass; any difference is the `FAIL`, naming both descriptors.
> `tagName` alone separates the two `John Smith` leaves in play — the row's
> `span.name` from the tooltip's `div.project-tip-name` — so no
> "first match wins" rule is needed and none may be used: **`rectForLabel`
> selecting among several same-labelled rectangles is forbidden.** If more than
> one live rectangle carries the label, the step `FAIL`s naming the count and
> the global indices, because the frame is ambiguous.

The global index from §E is what makes that last sentence possible, so IR-09 and
IR-12 are one repair seen from two sides.

## IR-10 — DEFECT — one example string in the card text cannot occur

§A.3's "Outcomes are told apart" clause says a rejection "whose message is
anything other than the ACL string above (including `Command
plugin:event|listen not found`)" is a `FAIL`. That string is **not producible**.
The not-found arm builds its message from `command_name`, which
`webview/mod.rs:2071-2074` has already stripped of the `plugin:event|` prefix,
and `mod.rs:2155-2162` formats it as `format!("Command {command} not found")` —
so the only reachable string of that shape is **`Command listen not found`**.
Listing an unreachable string in a card is not harmless: it teaches the next
reader the wrong discriminator.

**Exact repair:** replace `Command plugin:event|listen not found` with
`Command listen not found`, and add "(`webview/mod.rs:2162` formats this from
the **stripped** command name, so it reads `Command listen not found`, never the
prefixed form)".

## IR-11 — DEFECT — "preserved verbatim" cannot be literally true

§A.3 renames assertion (a) from `(a) window.__TAURI__ and
window.__TAURI_INTERNALS__ are undefined` to `(a) __TAURI__ is absent and the
built-in IPC command is ACL-denied`. The five-row `NOT RUN` block at
`scripts/v2/tauri-security.test.mjs:855-859` carries the **old** title, and the
card's V2 cell names it too. The proposal says that block "is preserved
verbatim". It cannot be: the label inside it must move with the assertion.

**Exact repair:** say that the block is preserved **except** that its (a) label
becomes the new title, that no other row's label, order, cause text or
`NOT RUN`/`PASS` semantics changes, and that the card's V2 cell's
`NOT RUN` sentence is updated by exactly that substitution. Nothing else in
that cell moves.

## IR-12 — DEFECT — §E's completeness test is sampled once

§E makes `rectForLabel` return `null` unless every batch `0 … ceil(total/40) − 1`
is present with a consistent `total`. Batches arrive as **five separate
same-origin `fetch` requests** (`web/src/main.tsx:117-131`), logged to separate
stderr lines. `rectForLabel` today is called once per click
(`:1050`, `:1065`) and returns whatever frame exists at that instant. The new
check makes a partial read *observable as a failure* rather than as a harmless
short frame — so it introduces a flake the old code could not have.

**Exact repair — in §E, and it is a loop, not a guard:**

> `rectForLabel` is polled, not sampled. It is called through the same
> `waitForFact`-shaped loop every other read in this harness uses, within the
> click's own 30 s window, and returns as soon as a **complete** frame is
> available. A frame that is still incomplete when the window ends is `FAIL`
> with the reason §E already names ("incomplete frame: 3 of 5 batches"), and a
> frame whose `total` changed mid-read restarts the read and the reason says so.
> **Sampling once and reporting "no rectangle for the label" is forbidden** —
> that is the wrong diagnosis the diagnosis report identified.

## IR-13 — DEFECT (minor) — a looser parser than the one already in the file

§C.3's `moveTo` splits on `line.indexOf('=')`, which yields key `line.slice(0,
−1)` for any line without `=`. The same file already does it correctly at
