## (3) A healthy end state passes, and nothing else in the harness fails one for the same reason

**The real end-of-run sequence, traced from source:**

1. `runSmoke`'s `finally` calls `stopPid(serverPid)` (`harness:2286`), which sends **SIGTERM**, polls `pidAlive` for up to 5 s, then escalates to SIGKILL and polls again (`:372-390`). Never a pattern, never `pkill` (C-ISO@1 rule 7). The shell child is stopped the same way (`:2293`).
2. The server answers SIGINT/SIGTERM with `void app.close().then(() => process.exit(0))` (`server/src/index.ts:161-165`).
3. `app.close()` runs the `onClose` hooks in registration order: the first (`server/src/index.ts:99-106`) calls **`db.close()`** then **`lock.release()`**.
4. `db.close()` is the last WAL connection, so SQLite checkpoints and deletes `apunta.db-wal` and `apunta.db-shm` (WAL mode set at `server/src/db/index.ts`/migrations). `apunta.db` keeps its inode and only grows.
5. `lock.release()` (`server/src/platform/data-lock.ts:297-318`) unlinks `apunta.lock`, but only while the file still carries **its own nonce** — so a takeover's lock is left alone, which is what keeps a foreign lock file visible to `replaced`.
6. The containment snapshot is taken **after** both stops (`:2313-2314`), so the end state is the post-shutdown one. With AM-209's two exemptions, `ownershipIdentityDiff` reports `ok: true` and `ownershipContainment` reports `vanished: []`.
7. **The SIGKILL branch is also green**, which is the case worth naming: if `app.close()` had not completed inside 5 s, the lock and the WAL pair would still be present, `vanished` would be `[]` and `ok` `true` — so neither shutdown shape fails. The exemption cannot turn a crash into a pass, because the WAL pair's *identity* is still only recorded, never asserted (`:1768-1770`).
8. The backup flow's `backups/` is a **new** name, not a vanished one: `otherNew` reports it and does not fail on it (`:1960`, `server/src/backup/store.ts:38`). Its per-operation staging folder under `staging/` is removed by the backup's own `finally` (`server/src/backup/archive.ts:123-229`) while the `staging/` root itself is created with `recursive: true` and stays — and on a first-run sandbox `staging/` and `safety/` already exist in the baseline from `prepareDatabaseForStart` (`server/src/db/safety.ts:192-228`), so they are baseline entries that are **not** deleted later.

- The added comment (`:912-916`) records the change and its cause, and the helper's own doc block (`:35-46`) states the new semantics, including that the exemptions are pinned "from the other side" by the AM-209 tests.

On this repository's Linux box the local AI server is the standing arrangement (`CLAUDE.md`), so it is a risk to note before the native V3 rather than a predicted failure. I did not probe the port (no network use in this mode).
- **O-4 (LOW, observability, outside AM-209) — the two exemptions are now invisible in the evidence.** Before the repair the healthy end state *named* the WAL pair in `lost` (wrongly, as a failure); now their deletion is not recorded anywhere — not in `lost`, not in `released`, not in `volatileChanged`, and not in `vanished`. The run's evidence therefore no longer states that the WAL pair was deleted by SQLite on close, which is a fact about the shutdown worth having on the record. Purely additive; no acceptance depends on it.
