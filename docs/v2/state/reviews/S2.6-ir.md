## The attestation finding

### What is actually true at `e9e8c8b`

The stored attestation is a server-written English constant, not a catalogue
value and not a model reply:

| Where | What | In May-edit? |
| --- | --- | --- |
| `shared/src/plan.ts:260-261` | `ATTESTATION_TEXT = 'I authored and reviewed this treatment plan. Attested in Apunta — sign the copy in your records system.'` | **no** |
| `server/src/routes/plans.ts:219` | `attestation_text: ATTESTATION_TEXT` written at activation | **no** |
| `web/src/components/PlanView.tsx:511` | `<p>{current.attestation_text}</p>` | **no** (not a job-starting component) |

Grep confirms the sentence appears in neither `shared/src/i18n/en.ts` nor
`es-MX.ts` (exit 0 on the negative assertion), so it has no `MessageKey` and
cannot be named in `ALLOWED`, which is keyed by `MessageKey`
(`e2e/support/no-english.ts:46`).

### The evidence distinction the coordinator asked for

The run's assertion **is a true positive on the text and a false positive on
the key.** Two separate claims, and the card's response to them must differ:

- **Genuinely English.** The text node on the Spanish plan screen is
  `ATTESTATION_TEXT`, byte-for-byte English, on a screen whose `<html lang>` is
  `es-MX`. A clinician activating a plan in Spanish gets an English attestation
  on the record a payer reads. That is a real product defect.
- **Wrongly attributed.** The reported key is `chat.change.summary`, whose
  English is `'I {changes}.'` with `kind: { changes: 'text' }`
  (`en.ts:796-799`). `no-english.ts:74-89` widens a `text`-kind placeholder to
  `(.*?)` and anchors `^…$` with the `s` flag, so that entry compiles to
  `^I (.*?)\.$` — a whole-sentence catch-all for *any* English string starting
  `I ` and ending `.`. The stored attestation is exactly that. The matcher is
  not wrong about the text; it is wrong about which key owns it, because
  `ALLOWED` is keyed by key and this broad pattern collides with unrelated
  English.

Consequence, and it is the sharp edge of this card: the laziest way to make
V1 green is to add `'chat.change.summary'` to `ALLOWED`. That would silence
every real `chat.change.summary` leak **and** every future collision of
`^I (.*?)\.$`, in exchange for one green run. It is a direct HS-7 violation and
exactly what AM-054's "**Do not weaken this to make V1 pass**" forbids. It must
not be done, and the card should say so at the point of failure.

### Does repairing it violate the persisted-content contract?

**No — provided the repair is confined to new writes and no stored row is ever
rewritten.** The reasoning, against the contract as written:

- C-LANG@1 rule 3 ("Existing notes and formats are never translated or
  relabelled") and rule 5 ("Stored strings are not rewritten") both bind
  *existing* content. Rows already holding the English sentence in
  `plan_versions.attestation_text` are dated, activated, payer-facing records;
  they stay English, untouched, no migration and no backfill.
- C-LANG@1 rule 4 lists `plan` among the jobs that capture `{ locale, … }` at
  start, and "persistence uses the captured context, never the current
  setting". Writing the attestation in the **captured** locale at activation is
  that rule applied forward, not a rewrite.
- S2.5's FD6 rule — every English value a card writes is the string the server
  sends today, character for character — binds a **model reply on the wire**.
  `ATTESTATION_TEXT` is a server constant, not a wire value, so FD6 does not
  reach it. Nothing in the contract freezes it.
- The existing comment at `PlanView.tsx:508-510` cites "C-LANG@1 rules 3 and 5"
  as authority for rendering it as it stands. That is a **mis-citation**: rule 3
  is about note/format rows, rule 5 about section-role mapping. Neither is about
  a sentence the server itself writes at activation. The mis-citation is why the
  code reads as deliberately correct while the surface is English.

**So this is a contract gap, not a contract violation.** C-LANG@1 has no rule
covering server-written stored text. That distinction is what decides who may
act: an implementer may not, a plan editor may.

Nothing here widens May-edit for the implementer and nothing weakens a check.
Two items, both outside this card's authority, both for the owner / plan editor:

1. **One fixed-decision line in the card**, so the implementer has an
   instruction instead of a judgement call. Suggested text, in the card's own
   register and no longer than the AM-054 amendment:

   > The stored plan attestation is **out of scope for this card**.
   > `shared/src/plan.ts:260` holds `ATTESTATION_TEXT` in English;
   > `server/src/routes/plans.ts:219` writes it at activation and
   > `web/src/components/PlanView.tsx:511` renders it, so a plan activated in
   > Spanish carries an English attestation. All three paths are outside May
   > edit and C-LANG@1 has no rule for server-written stored text, so this is a
   > **contract gap for the plan editor, not a defect this card may fix**
   > (HS-9). Do not add `chat.change.summary` to `ALLOWED`: the run reports
   > that key, but the text belongs to the attestation and the entry would
   > silence a catch-all pattern. Record the gap in the return with both
   > `file:line` references and report the row as `FAIL` for the reason above.

   The last clause matters: the honest outcome is a **named `FAIL` with the

2. **A separate card for the fix itself**, scoped to *new writes only*:

I am not proposing a code change, and I am not proposing that the plan-editor
item be folded into S2.6. Adding three non-writable paths to this card's May-edit
