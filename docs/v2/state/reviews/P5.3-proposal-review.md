### F1 — DEFECT (blocking). V2 cannot reach a timeout: the fake stream ends long before 30 s, so FD 4 makes V2 expect the opposite result

- **Where:** FD 4 (the drain's exit condition) against V2's expected cell;
  §5 "No assertion is weakened".
- **Conflict.** FD 4 fixes the drain as: "polls `active()` and returns when the
  registry is empty (**success**) or when **30 000 ms** have elapsed
  (**failure**)". V2 still expects `ok:false` with blocker `refine`. Under FD 4
  those two statements agree only if the `refine` job is still open 30 s after
  the quiesce begins.
- **Source facts.** `server/src/ai/fake.ts:73-74`: `DEFAULT_FAKE_STREAM_DELAY_MS
  = 12` and `MAX_FAKE_DELAYED_WORDS = 200`. The fake delays at most 200 chunks,
  so no fake-mode stream can exceed roughly **2.4 s** however long the note is.
  `e2e/tests/language-control.spec.ts:104-113` uses a 120-sentence plan and
  says in its own comment that this "keeps the server's refine job open for
  **seconds** rather than milliseconds" — the repository's own precedent agrees
  with the cap. `e2e/playwright.config.ts:127,139` sets a 60 s per-test timeout,
  so even a deliberate >30 s hold would be a slow, fragile row.
- **Failure scenario.** The implementer follows FD 4 to the letter. The refine
  registration releases at ~2 s, the drain returns *success*, the quiesce
  returns `ok:true`, and V2 fails. The two "honest" repairs an implementer can
  reach for are both worse: making the fake hold a stream open for 30 s+ means
  editing `server/src/ai/fake.ts` (outside May edit, and a fake-mode timing knob
  is a new threshold under HS-7), or writing `ok:false` for a non-empty
  registry, which is FD 4 without the wait. §5's claim that V2 "still expects
  `ok:false` with blocker `refine`" is true of the row's text and false of the
  row's behaviour.
- **Bounded correction (one of two, owner picks; the first is recommended).**
  1. **Refuse immediately on a non-empty registry (recommended).** FD 4 becomes:
     a quiesce snapshots `active()` at entry; if the snapshot is non-empty the
     quiesce **fails at once** with those kinds as blockers and the drain is
     never entered; if it is empty the drain still runs (a job already past the
     hook must be allowed to finish) under the same 30 000 ms bound. The 30 s
     then bounds the client flush/report window (F4). This makes V2
     deterministic, keeps `ok:false` + blocker `refine`, keeps the stream
     completing (FD 9), and matches C-UPD@1's own failure row — "quiescing
     (active job …) → back to `verified`; notice says **what to finish first**"
     — which describes an immediate, named refusal, not a silent 30 s wait.
     The contract sentence "waits up to 30 s for its registry … to drain" is
     preserved as an upper bound and must be recorded in the amendment as a
     **reading** the owner approves, not as a silent re-interpretation.
  2. **Keep the wait and change V2's expectation** to `ok:true` once the stream
     drains. This is a *weaker* row than the card's own V2 (it no longer proves
     a quiesce is refused while a refine runs), so it is listed only to be
     rejected, not recommended. Partial acceptance of this shape is not on the
     table.
- **Also required with either choice:** FD 10's "not a timeout inflation" clause
  stays, and V2 must state that the refusal is observed *while* `chat-streaming`
  is visible, with the `refine` registration asserted by the server's own view
  (V1's registry cases), not by elapsed time.

### F2 — DEFECT (blocking). V6(a) has no mechanism: there is no unsaved-text guard on the note screen, and no durable copy of the text

- **Where:** §1.3 and FD 6 ("The browser half is **already implemented** and
  this card verifies it"), and V6(a).
- **Conflict.** FD 6 names `NoteView.tsx:347-354` and `Capture.tsx:150-160` as
  the two halves already built. `Capture.tsx:150-160` is real: `unfinished` is
  `text || recording !== 'idle' || wav || busy` and `onBeforeUnload` calls
  `preventDefault()`. `NoteView.tsx:347-354` is a **best-effort flush**
  (`flush(true)`, keepalive, `.catch(() => undefined)`) on `pagehide` /
  `visibilitychange` — it is not a guard, it is a request that may or may not
  leave the browser. `grep localStorage|sessionStorage|indexedDB web/src`
  shows the only stored web state is chat-open, sort, widths, pins and boot
  theme: **no draft of the note text exists anywhere.** So on the note screen
  today there is no `beforeunload`, no confirm, and no recoverable copy.
- **Failure scenario, two directions.**
  (a) *Passes for the wrong reason.* `NoteView.tsx:31` sets
     `SAVE_DEBOUNCE_MS = 400`. A spec that types, waits a beat and reloads has
     already saved through the ordinary debounce; "the text is recoverable
     after reload" is then true with no unload path involved at all. That is
     the same wrong-reason failure the instruction review named for V3 (D10).
  (b) *Fails for a real reason.* A spec that reloads inside 400 ms depends on
     Chromium honouring a keepalive `PATCH` during unload. That is exactly the
     "unload saves are best effort" the card's own Confidence line names, so the
     row asserts a guarantee the card simultaneously disclaims.
- **Bounded correction (recommended).** Put `web/src/components/NoteView.tsx`
  back in May edit for **one** addition: a `beforeunload` handler mirroring
  `Capture.tsx:150-160`, reading the refs that already exist
  (`latestTextRef`, `persistedContentRef`, `saveStateRef`, `staleRef`), attached
  in the effect that already registers `pagehide` / `visibilitychange`, and
  deleted in the same cleanup. That makes C-UPD@1's three close rules true on
  the screen where the text actually lives, gives V6(a) a deterministic
  assertion (a dialog appears; the typed text is still in `#note-body`
  afterwards because the navigation was refused), and keeps the flush hook as the
  `read`-only interface the reporter uses. Then rewrite V6(a) as: unsaved text
  in the editor, a close attempt raises a `beforeunload` dialog, and after the
  dialog is dismissed the editor still holds the typed text — **not** "reloads
  and the text is recoverable". If the owner prefers no `NoteView.tsx` edit,
  then V6(a) must be marked `BLOCKED` with the reason "no unsaved-text guard
  and no durable draft exists on the note screen", which is honest but leaves
  the contract sentence unverified by anyone.
- **Consequence to state in the card.** A `beforeunload` guard on the note
  screen is global unload behaviour, so other e2e specs (`save-integrity`,
  `plan`, `capture`) can feel it. V5 is `npm test && npm run lint && npm run
  typecheck` and never runs Playwright, so add a row **V7**: the full
  `npm run e2e` inside `sandbox.mjs env --port <p5>` (7853+4 is taken by V2-V6;
  the coordinator assigns), expected exit 0. CI runs `npm run e2e` (AM-099), so
  this is the only place the card's own web change is seen by the rest of the
  suite.

### F3 — DEFECT. FD 1 and FD 3 contradict each other on which windows report, and "the primary only" is not implementable from May edit

- **Where:** FD 1 ("held open by **each window that has an editor**") against
  FD 3 ("**The primary window is the only reporter**"), and the May-edit mount
  at `web/src/main.tsx`.
- **Conflict.** The reporter is mounted once per window (`main.tsx` is outside
  `App.tsx`'s primary logic), so *every* window opens the long-poll. FD 1 says
  each window with an editor holds it; FD 3 says only the primary reports.
  Separately, FD 3's premise — that a covered secondary holds neither unsaved
  text nor a microphone — is true (`App.tsx:64-88` sets `inert` on the content
  for `secondary`/`unsupported`, so it cannot type or record), but the
  *reporter* cannot know whether it is primary: that state lives in
  `usePrimaryWindow` inside `App.tsx`, which the proposal puts in **Must not
  edit**. A "primary only" rule therefore has no source of truth the reporter
  can read.
- **Bounded correction.** Delete FD 3's "primary only" clause and make the rule
  the stronger one: **every window that has an editor registers and reports**;
  a window with no editor (or whose hook has been torn down) reports `ok`
  immediately; a window with an editor that holds unsaved text reports
  `conflict` or `save_error` even if it is secondary. Nothing is lost — a
  secondary that cannot hold text cannot produce a blocker — and the guarantee
  gets strictly safer, with no `App.tsx` edit. If the owner insists on
  primary-only, then `web/src/App.tsx` must be added to May edit for exactly one
  line exposing the phase through the existing `window.__apunta…` convention,
  and V1 must gain a case proving a secondary does not report.

### F4 — DEFECT. The client report has no correlation id, so a late or stale report can satisfy a *later* quiesce

- **Where:** FD 1 ("A window that answers after the deadline is ignored") and
  FD 3's report body.
- **Conflict.** The report is `{"ok":…, "blockers":[…]}` with nothing tying it
  to a particular quiesce, and nothing tying it to a window the server is
  actually waiting on. The server therefore cannot distinguish "the report for
  the quiesce I am running" from "a report produced for the quiesce that timed
  out thirty seconds ago, arriving during the next one".
- **Failure scenario.** Quiesce #1 hits the deadline with the report still in
  flight (a slow flush, or a report POST that was queued behind the deadline).
  FD 1 ignores it. Quiesce #2 starts, and the ignored report from #1 lands —
  `ok:true` — and #2 is satisfied **without any window having flushed for it**.
  The unsaved text the second quiesce existed to protect is exactly what gets
  lost, and both rows go green. Nothing in FD 1, FD 3 or FD 5 prevents this.
- **Bounded correction.** Mint a `quiesceId` (`uuidv7`, the repository's
  convention) when the quiesce begins; the flush request body becomes
  `{"request":"flush","quiesceId":"<id>"}`; the report body becomes
  `{"quiesceId":"<id>","ok":boolean,"blockers":string[]}`. The server accepts a
  report **only** when `quiesceId` equals the in-flight quiesce's id **and** the
  reporting window has a registered pending wait; anything else is rejected with
  409 and counted, never applied. The drain deadline **resolves every
  outstanding wait** (no request is left hanging past the budget) and the client
  **re-arms** the long-poll after each report or deadline. V1 gains one case: a
  report carrying a stale `quiesceId` during a live quiesce is refused and the
  quiesce still ends `ok:false`.

### F5 — DEFECT. The flush request is sequenced *after* the drain, so at the deadline the editor is never asked to flush at all

- **Where:** FD 4 ("blocks for the drain and then for the report, inside the
  same 30 s budget") against FD 1 and against V3.
- **Conflict.** If the report phase is entered only after the drain returns,
  then a drain that consumes the whole 30 s ends the quiesce before any window
  is ever asked to flush. The editor's unsaved text is never flushed, no
  conflict is ever detected, and the client channel is dead in precisely the
  case the client channel exists for.
- **Failure scenario.** A long refine is active. The drain waits. At 30 000 ms
  the drain fails, maintenance is left on by FD 5's `finally`, the window is
  never asked, and the therapist's unsaved text is still unsaved — with no
  `no_response` blocker to say so, because nobody was asked. FD 1's
  "unanswered window is `no_response`, never read as `ok`" does not fire,
  because there was no request to leave unanswered.
- **Bounded correction.** FD 4 becomes one deadline measured from the instant
  the quiesce begins, with the two phases **concurrent**: the flush request is
  answered at quiesce entry (not after the drain), the drain runs alongside it,
  and each phase is allowed `deadline − elapsed`. A window that has not answered
  by the deadline is `no_response`; a report that arrives after it is refused
  (F4). State explicitly that the drain's exit is F1's rule and that the two
  phases never extend the budget between them.

### F6 — DEFECT. "No primary" and "client disconnect" are undefined, and FD 1's own no-editor rule makes a window invisible

- **Where:** FD 1 ("A window with no editor answers `ok` immediately **without
  holding a request open**") and §1.1 ("the server waits for a report from every
  window that registered").
- **Conflict.** If registration *is* the held-open `GET`, then a window that
  answers immediately without holding a request open was never registered, and
  the server cannot tell "one window, no editor, nothing to flush" from "no
  window at all" from "the window's connection died mid-quiesce". None of those
  three has a stated outcome, and two of them must not be `ok`.
- **Failure scenario.** The primary window is closed (or its long-poll socket
  dies) after the quiesce begins. The server's registered set empties. If it
  reads "no registered windows" as "nobody to wait for", it returns `ok:true`
  and the update proceeds — a spurious `ok` from a *disconnected* client, which
  is the failure mode the whole design was chosen to avoid. Conversely if it
  waits, a headless or already-closed app burns the full 30 s.
- **Bounded correction.** Three named rules in FD 1/FD 4:
  (i) registration is the held-open `GET`, and a window with no editor still
  registers and answers `ok` immediately (so remove "without holding a request
  open" — it is what makes the window invisible);
  (ii) a registered wait whose socket closes is removed from the set, and if the
  set is empty when the drain ends the quiesce returns `ok:false` with blocker
  `no_response` — a disconnect is never read as `ok`;
  (iii) the one exception, stated explicitly: a server started with **no
  browser attached at all** (shell up, window not yet loaded) is a distinct
  state from a disconnect, identified by the set having been empty since entry,
  and returns `ok:false` with `no_response` as well unless the card names a
  different, sourced answer. V1 gains a case for (ii).

### F7 — DEFECT. Transport cleanup is not instructed, and the long-poll is a permanently held request

- **Where:** May edit (`web/src/lib/maintenance.ts`), FD 1, FD 9.
- **Conflict.** FD 1 has every window hold a `GET` open from mount until a
  quiesce begins. Nothing states who aborts it, when, or what happens to it when
  the page navigates, when the hook is torn down, or when the budget ends; and
  nothing says the new transport must not touch the existing one. Source facts
  that make this a real question rather than a nit: `web/src/api/client.ts`
  applies **no** global timeout (`buildInit` only passes `signal`/`keepalive`),
  so nothing would kill the request for the reporter; `App.tsx:298-306` deletes
  `__apuntaFlushBeforeRelease` in `NoteView`'s cleanup, so the hook can vanish
  mid-quiesce; and `web/src/api/sse.ts` is a `fetch` body reader used by the
  refine/plan/brainstorm streams, so the app already has one long-lived response
  the card must leave alone.
- **Bounded correction.** Add one Fixed decision: the reporter holds **exactly
  one** long-poll, armed with an `AbortController`, aborted on unmount, on
  `pagehide`, when a report has been sent, and when the server resolves it at the
  deadline; it re-arms immediately after; it never reuses, wraps or aborts the
  SSE reader in `web/src/api/sse.ts`; it uses `window.__apuntaFlushBeforeRelease`
  **if it is a function** and reports `ok` when it is not (the hook's own
  cleanup removes it); and it is mounted once per window, never per route.
  V1 gains a case that unmounting the reporter aborts the request.

### F9 — DEFECT (protocol). The quiesce trigger's authorization is unstated, and it collides with C-BRIDGE@1 rule 3

- **Where:** §3.8's trigger (`POST /api/app/quiesce`, "one function, two
  callers, the shell and the test") and §1.4 Option A.
- **Conflict.** C-BRIDGE@1 rule 3: "Update endpoints … exist only when the
  server was started by the shell; in browser mode they return 404." The
  proposal adds three `/api/app/*` routes with the opposite policy — always
  present, including browser mode — and never says so. Two consequences:
  (i) browser mode gains an authority it did not have: any same-origin script
  can put the app into maintenance, and with FD 5's "a successful quiesce leaves
  maintenance **on**", that state persists until restart;
  (ii) the asymmetry is a contract fact, not an implementation detail, so it
  belongs in C-BRIDGE@1 rule 3 or C-UPD@1's Quiescence paragraph.
- **The sharper half, and it interacts with §1.4.** If the trigger *is* gated on
  shell mode — the consistent choice — then §1.4 Option A (adopt `Depends: P3.3`)
  does not make V2-V4 runnable either: `scripts/v2/sandbox.mjs env --port <p>`
  sets `APUNTA_DATA_DIR`, `APUNTA_PORT`, `APUNTA_NO_OPEN`, `APUNTA_TEST_RUN_ID`,
  `APUNTA_V2`, `APUNTA_CHECK_URL`, `APUNTA_E2E_PORT` and **no** `APUNTA_SHELL`
  (C-ISO@1 rules 4 and 6 are the whole environment list), and the shell-mode
  predicate does not exist in code yet — `grep APUNTA_SHELL` matches P3.3's card
  text only. So a shell-gated trigger makes every browser row `BLOCKED`, in
  browser mode *and* under the dependency the proposal recommends.
- **Bounded correction, and it needs an owner answer (decision E below).**
  Recommended: state in a Fixed decision that `POST /api/app/quiesce` is
  **available in browser mode and is not gated on shell mode**, with the reason
  in the card (quiescence is a server mode whose participant is the web client,
  and rule 3's gate exists because update endpoints are shell-only features),
  and add one clause to the amended C-UPD@1 Quiescence paragraph recording the
  asymmetry so rule 3 and the new route cannot be read as contradicting each
  other. The alternative — gate on shell mode and mark V2-V4, V6 `BLOCKED`
  "no shell in the sandbox" — is coherent but leaves four of six rows
  unevidenced, which the proposal's own D15 closure claims to have solved.
