## F1 deep-dive (read end to end, as asked)

`web/src/components/SpellingProvider.tsx`, the switch path after a dictionary
has loaded:

1. **The new locale's pair is requested and installed.** On a locale change the
   effect at `:139-158` runs: `previousLocaleRef` guard → `loadIdRef += 1`
   (invalidates any in-flight load) → `loadingRef = false` → `setError(null)` →
   `setAdded([])` → **`spellerRef.current = null`** → `setSpeller(null)` →
   `if (requestedRef.current) ensureLoaded()`. `ensureLoaded` (`:111-129`) now
   passes its guard (`loadingRef.current || spellerRef.current !== null` — both
   false/null), captures a fresh id, and calls `load(localeRef.current)`.
   `localeRef.current` is assigned during render (`:103`), so by effect time it
   is the **new** locale. On resolution the id guard at `:119` installs the new
   speller and clears the error. The old code never cleared `spellerRef`, so
   the guard returned early and the tab kept no dictionary and no error — the
   reported symptom.
2. **A late response for the OLD locale is still discarded.** The id captured
   at `:116` is compared against `loadIdRef.current` on both resolve (`:119`)
   and reject (`:126`). A switch increments the counter at `:142`, so any load
   that started under the previous locale installs neither the dictionary nor
   the error. The two original V1(f) cases (in-flight load, resolve/reject
   after a switch) prove both directions and still pass.
3. **No double-load.** `ensureLoaded` is called once per switch; `loadingRef`
   blocks re-entry while the new load is in flight, and once it resolves
   `spellerRef.current !== null` blocks any further ask. The settings effect
   never calls `ensureLoaded`; `useSpelling` asks once, on mount.
4. **No flash of the wrong dictionary.** The old speller is cleared in the same
   effect that starts the new load, so there is no interval in which the wrong
   locale's dictionary is active *and* expected. Between the locale-change
   render and the effect, the already-painted marks are the old dictionary's
   marks on unchanged text — not new marks drawn with the wrong dictionary —
   and the id guard makes it impossible for the old speller to be re-installed
   after a switch. (One paint of stale marks before `setSpeller(null)` lands is
   inherent `useEffect` timing and is not a defect the card names.)
5. **StrictMode double-effect safety.** The switch effect's first line
   (`previousLocaleRef.current === locale` → return) makes any double
   invocation a no-op, so a replayed effect cannot double-ask or double-clear.
   The pre-existing StrictMode mount case is untouched and green.

**The new tests genuinely start from a loaded dictionary.** Both cases in
`describe('the language switch after a dictionary has loaded (D4.3, V1f)')`
(`SpellingProvider.test.tsx:219-290`) use a `recordingLoader` that answers
immediately and records every locale asked for, and each **waits until the
probe reads the active dictionary** (`active-speller` = `english` / `spanish`,
read through the speller's own `correct` on a marker word) before rerendering
with the other language. The post-switch assertions are two-sided: `asked`
equals `['en', 'es-MX']` / `['es-MX', 'en']` **and** the active speller reads
`spanish` / `english`. Fail-before is unambiguous in the code path (pre-fix,
`spellerRef.current` still held the old speller, so the guard returned and
`asked` stayed `['en']`); the return file records the pre-fix run failing
exactly there, and the post-fix run passes — re-confirmed here by name:

```
✓ … > the language switch after a dictionary has loaded (D4.3, V1f) > asks for the es-MX pair and makes it the active dictionary (en → es-MX)
✓ … > the language switch after a dictionary has loaded (D4.3, V1f) > asks for the English pair and makes it the active dictionary (es-MX → en)
```
