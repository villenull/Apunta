## 1. O3 — a real contradiction of approved §E. The root is right. **PASS**

Approved §E (`state/P3.4-REPAIR-PROPOSAL-v5.md:191-204`, quoted exactly in the
proposal): *"One deadline is taken once, before the first dispatch, and it
covers calibration, **selection**, every command, **every await**, the witness
and the landing. … There are no phase timers and no second budget."*

Shipped (`b19e59f`): `waitForLabel(stderrSource, PATIENT_LABEL, 30_000)` at
`:2112` builds its **own** wall-clock budget (`Date.now() + timeoutMs`, `:1749`)
and only afterwards does `createTargetDeadline(clock.now())` at `:2123` open
the flow's budget (`:2151` for the note). Label discovery **is** selection (the
(d) handler's own comment: "The tag is captured from the frame as it stands
before the pointer moves") and it **is** an await — so the one deadline neither
covers selection nor covers every await, and the 30 s label wait is a second
budget in front of the immutable one. The (d) half can spend 30 s + 30 s per
target. The contradiction is textual, not a style quibble.

Is the shipped code arguably compliant? The impl5 reviewer's mitigation — "the
pre-step is a bounded wait on the observation channel, analogous to the gate's
45 s window" (`P3.4-impl5.md` §6) — does not hold: §E explicitly preserves only
"The row's 45 s first-fact window and 30 s click window". The label wait is
neither; it is a third window, and §E says there is none. **My verdict: the
root's reading is the correct one; the shipped code is not compliant with §E
as written.** The impl5 non-blocking call was a judgment the root is entitled
to escalate, since §E is approved text.

## 4. The patched code satisfies §E. **PASS** (one residual observation)

Trace of the patched `assertInjectedNoteInert`: the deadline is taken once per
target, before the first dispatch (`:2133`, `:2162`); the **same object** goes

neither widened nor added here and is outside this patch's claimed scope; the
owner should know it stands as shipped.

## 5. The O2 change keeps the kill scoped to this harness's own tracked pids. **PASS**

The change replaces only the branch *condition* (reason string → the
deadline's own state). `killActiveCommands` is byte-identical: it iterates
`activeCommands` — children registered solely through `trackCommand` inside
`spawnAsync` — and SIGKILLs them by pid, skipping already-closed children. It
cannot kill a foreign process, before or after. The branch now fires in
strictly more failure cases (any failure once the deadline is expired); the
cases where it still does not fire are success, or a deadline that is not
expired — where no command should be hanging, since every dispatch is raced
against the deadline. My probe: tracked child killed after the patch, foreign
child survives after **and** before.

## 7. Non-vacuity — proven with my own probe. **PASS**

My probe (`review/probe.mjs`, output `review/07-probe-output.txt`) drives the
actual functions of both copies through synthetic IO only. Scale, stated: 800 ms
stands in for `TARGET_BUDGET_MS = 30_000`; the 250 ms poll is the real
`OBSERVATION_POLL_MS`; 150 ms per move stands in for unmeasured xdotool
latency. What is proved is **which deadline object governs** each await and the
click, not absolute timing.

- **(a) Delayed label, one shared deadline.** Label appears 400 ms into the
  800 ms budget. Shipped: flow `ok=true`, **1 click**, wall **952 ms > 800 ms** —
  the second budget let the flow click after label discovery spent the first.
  Patched: `ok=false`, **0 clicks**, wall **800 ms** — the row ends at the one
  deadline. Positive control: label at 100 ms → patched still returns the tag
  and the flow clicks (wall 701 ms), so the patched `waitForLabel` is not
  vacuously failing.
- **(b) Prefixed-reason kill.** Hung target warp (3rd move): the reason is the
  genuine `:1712` prefix `bootstrap 2: …; the target warp: the target deadline
  expired`. Shipped: tracked child **survives** `runFlowGuarded` (branch
  inert). Patched: tracked child **killed by pid**. Control B2: hung geometry →
  exact `DEADLINE_EXPIRED` → the branch fires **even on shipped** — the string
  match is the bug, not dead code.
- **(c) Untracked process never killed.** A bare-spawned foreign child survives
  the cleanup in both copies.
- My own static §E text checker: **13 problems on the shipped file, 0 on the
  patched file** — matching the evidence's count independently.

## 8. Authority, scope and the one material omission. **CHANGES REQUESTED**

The proposal correctly: claims **no authority** ("Status: `SUBMITTED`. No
authority is adopted here"); states **nothing was executed** and V0–V4 remain
`NOT RUN`, once-only; rules out attempt 6, counter reset and retry; says
declining means **BLOCKED**; and discloses the retained **O1** risk as
fail-closed and out of scope. AM-189 is verified in `AMENDMENTS.md` ("bounded
P3.4-only attempt5 exception … V0/V1/V2/V3/V4 once each … no retry/partial
rerun/hidden sixth"), and the card checkpoint (`attempt 5`, `BLOCKED`,
`implementationCandidate b19e59f`) matches the exhausted-budget framing.

**The omission:** evidence `03-patch-replay.txt` claims "prettier exit=0" for
the corrected copy. That check was run against the gitignored `build/` path —
and prettier **skips** gitignored files, so it never checked anything. I proved
the vacuity with a deliberately broken control file in `build/` (passes from
the root, fails via stdin at the real path). Checked the way `npm run lint`
will check it (`prettier --check .` sees `scripts/v2/tauri-security.test.mjs`),
**the patched file fails prettier at its real path**: the `classify` arrow in
the patched `waitForLabel` is 112 chars against `printWidth: 110`. ESLint, by
contrast, is genuinely clean at the real path (verified via
`eslint --stdin --stdin-filename`, exit 0). Applying the patch as committed
would therefore fail the repo's own `npm run lint` the moment it lands — and
the format wrap is a fifth hunk beyond "the four hunks in `02-patch.diff`" the
owner is being asked to approve.

Minor, immaterial: the proposal's "31 other harness functions byte-identical" is
a different counting basis (I count 76 of 79 identical, 3 changed); the
substantive claim — only the three seam functions change — is true.
