## The single most important thing an implementer could get wrong

**Editing the wrong catalogue.** The instinct on "the English name is showing in
the Spanish build" is to stop the English from being *English* — to change
`shared/src/i18n/en.ts`. That file is licensed to this card (AM-054, and AM-059),
so nothing stops the edit, and it works: setting
`en['language.en.english']` to `'Inglés (Estados Unidos)'` makes the two
catalogues agree, removes the key from `ENGLISH_FORMS`
(`no-english.ts:103-117`), and turns **V1 green with the defect still on
screen** — and **V15 still passes**, because all four keys remain byte-identical
pairwise. The only row that catches it is **V16** (`:277`), because under the
es-MX provider the English cell would then read
`English (United States)Inglés (Estados Unidos)`. The card forbids it at
`:54-55`, but an implementer who treats that clause as a formality and V15 as
the oracle will ship a Spanish build whose English option is mislabelled and a
green V1. Read the fixed decision at `:98-109` before touching either catalogue:
the four keys are never translated in *either* locale, and the fix is one value
in `es-MX.ts:1231`, nothing else.
