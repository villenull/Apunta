## DEFECT

### IR-07 — V1 and V2 open a database and are not routed through `sandbox.mjs`

- **ID and location:** `docs/v2/state/dispatch/P0.5-ir.md`, hard stops
  **HS-2 Isolation** (lines 22-24) versus the card's `## Verification` rows
  **V1** and **V2** (lines 97-98); the same gap exists in the implementation
  dispatch `docs/v2/state/dispatch/P0.5.md` and in the run configuration's L1
  recipe, `docs/v2/RUN-CONFIG.md` §2 ("`npm run build:shared`, then the card's
  named test files with `npx vitest run <paths>`").

- **The text that conflicts:** HS-2 reads "Every command that starts an Apunta
  server, **opens a database** or launches the app runs through
  `scripts/v2/sandbox.mjs` **once card P0.3 is APPROVED**. Before that, only
  non-launching edits and unit tests that use in-memory or temporary databases
  created by the test." `docs/v2/state/PROGRESS.json` (AM-023) shows
  `"P0.3": "APPROVED"`, so the carve-out's "Before that" window is closed and
  the first sentence is the rule in force. Yet V1 (`TZ=$z npm test`) and V2
  (`TZ=$z npx vitest run … server/src/routes/import.test.ts`) open a database
  and are written as bare commands: `server/src/routes/import.test.ts` calls
  `createTestApp()` (`server/src/routes/import.test.ts:61`), which runs
  `openDatabase({ file: config.dbFile, migrationsDir: config.migrationsDir })`
  against a real SQLite file in `mkdtempSync(join(tmpdir(), 'apunta-test-'))`
  with real migrations (`server/src/test/harness.ts:42-58`). Nothing in the card
  says whether these two rows are exempt as "temporary databases created by the
  test" or must be wrapped. Note what is *not* in conflict: no server listens
  and no app is launched — the harness sets `APUNTA_PORT: '0'`, calls
  `app.ready()` and drives requests with `app.inject` — so the "starts a server"
  and "launches the app" clauses are not triggered; the database clause is. The
  implementation dispatch does assign this card sandbox port **7809**, and
  `scripts/v2/sandbox.mjs` exists (created by P0.3, `APPROVED`), so wrapping is
  available — the card simply never says to.

- **One concrete failure scenario:** the implementer reads HS-2 as written
  (P0.3 approved, so a database-opening command goes through the sandbox) and
  either (a) runs
  `node scripts/v2/sandbox.mjs run --port 7809 -- npm test`, so the command in
  `docs/v2/evidence/P0.5/` no longer matches the card's V1 row and the
  implementation reviewer has to judge a row against a command the card did not
  name; or (b) concludes the card's own required verification crosses a hard
  stop, reports V1 as `BLOCKED` and spends attempt 1 of 3 on a question the
  coordinator can answer in one line. A third implementer will simply run the
  rows bare, exactly as P0.2's implementation review did — but that reading was
  available there because P0.3 was still unapproved at the time
  (`docs/v2/state/reviews/P0.2-impl.md`: "per HS-2", while
  `docs/v2/state/reviews/P0.3-ir.md` post-dates it).

- **One specific correction or named prerequisite:** add one Fixed-decision
  line to the card, in the style of AM-017, choosing one of —
  (i) *exemption*: "V1 and V2 run bare, not through `sandbox.mjs`: every
  database they open is a temporary SQLite file the test itself creates and
  deletes (`server/src/test/harness.ts`), no server listens and no port is
  bound, so HS-2's sandbox clause is not engaged"; or
  (ii) *wrapping*: rewrite the rows as
  `for z in …; do TZ=$z node scripts/v2/sandbox.mjs run --port 7809 -- npm test || exit 1; done`
  and the V2 equivalent, and record run IDs in the return file. The same line
  belongs in `docs/v2/RUN-CONFIG.md` §2's L1 recipe, since every later L1 card
  that runs integration tests inherits the identical gap. No code change is
  needed for this defect; it is purely an instruction-routing decision.
