**One actual counterexample — the duplicate rule contradicts itself and is wrong under either reading.**

Inputs: a healthy page publishes epoch `F`, batch `b`. The first stderr sighting of `(F,b)` is truncated mid-URL (the marker regex captures the prefix, so `batch`, `rects`/total, `frame`, and only some `iN_*` keys parse). A second, complete sighting of the same `(F,b)` follows.

Wrong outcome: under "wholesale replacement," the truncated entry is installed and then overwritten by the complete one (last-wins), so "conflicting duplicate FAIL" can never fire — the rule is inert. Under the literal conflict rule, the complete sighting *differs* from the truncated one, so the reader FAILs a healthy page. Either way the resolved contract is wrong; the model's required truncated-message fixture will hit it.

One-clause fix: only complete, well-formed sightings are installed and eligible; a malformed/truncated sighting is discarded — never merged, never replaces a good entry, never counts as a conflict. Conflict-FAIL applies only between two **complete** sightings of the same `(epoch,batch)` whose field values differ.

Boundary notes (fail-closed, not counterexamples): "newest-incomplete forbids older-complete fallback" turns a lost batch fetch into a deadline FAIL on a healthy page — safe direction, but the model should assert it explicitly; and a warp to the pointer's current position may emit no `pointermove`, yielding a named NOT RUN.
