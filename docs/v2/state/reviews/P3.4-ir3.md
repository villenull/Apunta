## Non-defect notes

- **N1 — the `content-length` question, answered (the brief's highest-risk item).
  There is no stale-length hazard, and the card needs no correction for it.**
  Evidence used: the installed Fastify source, not docs — `server/package.json`
  declares `fastify: ^5.12.1` and `node_modules/fastify/package.json` is
  **5.12.1**. In `lib/reply.js`, the `onSend` chain runs **before** the payload is
  measured: `onSendHook` (`:558-566`) runs the route's `onSend` hooks with a
  `wrapOnSendEnd` continuation, and only `onSendEnd` (`:595`) computes and writes
  headers. For a string or Buffer payload, `onSendEnd` at `:691-699` reads any
  existing `content-length` and **overwrites it** whenever
  `Number(contentLength) !== Buffer.byteLength(payload)` (the sole exception is
  `HEAD`). `safeWriteHead` then writes the corrected headers. So Fastify does
  *not* compute `content-length` before `onSend`: it computes it *after*, from the
  payload as the hook left it. Rewriting the boot page's HTML string in the hook
  (which grows it by `nonce="…"` ≈ 24 bytes) therefore yields a correct
  `content-length` on the wire, and no truncation and no corrupted connection.
  Two related facts, from the same file: `reply.header()` inside `onSend` mutates
  `reply[kReplyHeaders]` before `writeHead`, so the CSP header is unaffected by
  hook ordering; and `lib/error-handler.js:53,119` recompute `content-length` on
  the error path too, so a payload rewritten on a 503 (the boot page is `503`) is
  still measured. The card is silent on the header, and silence here is safe — I
  would still add one clause ("no `content-length` adjustment is needed or
  permitted; Fastify recomputes it after `onSend`") purely so an implementer does
  not defensively delete a header the framework owns, but this is **not** a
  blocking defect and it is **not** something the card's stop conditions should
  have to discover.
- **N2 — `@fastify/static` interaction: inert, by construction.** It sends a
  stream (`@fastify/static/index.js:455`) and takes its `content-length`, `etag`,
  `last-modified` and content type from `send`'s own metadata (`:442`). Because
  the card's rewrite is gated on a **string** payload, no byte of a static
  response is ever changed, so nothing `send` computed is invalidated: no stale
  `etag`, no stale length, no changed content type. The one theoretical hazard —
  a future string-served `.html` asset that did carry a `<style>` — would be
  caught by V1(iii)'s "no other directive" sweep and by V1(ii)'s byte-identity
  check, and the card's sentence about non-string payloads already covers the
  general case.
- **N3 — the boot server's two `send(html)` calls are safe as the card describes.**
  `boot-error.ts:67` and `:71` both send the one frozen string computed at `:65`;
  both set `text/html` before `send`, so the hook can identify them by content
  type; both are `503`, and the 503 path is measured by `onSendEnd` like any other;
  and because the nonce is generated inside the hook, the *same* frozen string
  yields two different nonces on two consecutive responses, which is exactly what
  V1(ii) asserts. Verified also that instance `onSend` hooks reach the boot
  server's not-found handler (same `four-oh-four.js:149-156` mechanism). R1's
  chosen route works on this stack.
- **N4 — the CSP decision itself is spelled and scoped correctly.** `style-src-attr`
  is the correct CSP3 directive for style **attributes** (with
  `style-src-elem`/`style-src`/`default-src` as its fallbacks, in that order), so
  `style-src-attr 'unsafe-inline'` permits `style="…"` and nothing else: it grants
  no script (there is no `script-src-attr`, so attributes fall back to
  `script-src 'self'`, which has no `'unsafe-inline'` and no nonce), no `eval`,
  no remote source, no origin; it does not reach `<style>` **elements**, which
  still require the nonce in `style-src`; and it leaves all six of rule 6's
  directives untouched. Rule 6's wording in `docs/v2/CONTRACTS.md:230` is "with
  **at least**:" followed by the six, so adding two directives that weaken
  nothing is additive, exactly as the card argues — and rule 6's "any extra source
  must be justified in the card's evidence by a failing test without it" is met in
  spirit and letter by V1(vi) ("fails outright if `style-src-attr` is missing") and
  V2(e) (fails if the attribute is blocked). The card's own statement that with no
  `style-src` a style attribute falls back to `default-src 'self'` and is blocked
  is correct, as is its statement that a nonce never applies to an attribute.
- **N5 — V1(vi) and V2(e) are decidable and non-vacuous.** V1(vi) is a header
  assertion on two named HTML responses and fails outright if `style-src-attr` is
