## 5. What I verified about the two cases asked about

**Case (b) — is the frame recipe implementable, and does it fail at the base?
Both yes.** jsdom 30.0.1 does not implement `inert` at all
(`'inert' in HTMLElement.prototype === false`), so the flag is an expando and
focus inside the subtree still works — which is exactly what lets the case
assert *cause* and *steal* instead of a swallowed keystroke, and what lets
case (e) read `inert` as a property. vitest 4.1.11's jsdom env defaults
`pretendToBeVisual` to true, so `requestAnimationFrame` exists, and
`global.window === global`, so one stub covers both spellings. The base tree's
`becomePrimary` schedules `App.tsx:269-274` inside the grant, so after the
post-release drain `document.activeElement` is `#apunta-content` and the case
fails; with decision 2's `phase === 'secondary'` guard the initial `'acquiring'`
grant schedules nothing, nothing moves the caret from the field the case placed
it in, and the case passes. Case (a) fails at the base for the independent
reason that `blocked = phase !== 'primary'` makes `#apunta-content.inert` true.
The three placements are each load-bearing, and the card now says what a
misplaced case costs (Stop 1 firing on a correct diagnosis) — which is the
right way to prevent the one ambiguity that made this worth reviewing.

**Case (e) — is the safety guarantee still pinned? Yes.** `(e)` asserts
`inert` while `'secondary'` and still `inert` once `pending === true`, and it
passes at the base, so it is a genuine guard rather than a description of the
fix. `web/src/App.test.tsx:1515-1516` independently pins `'unsupported' →
inert`, and `e2e/tests/save-integrity.spec.ts:80` and `:87` are the e2e half
(I read both: `expect(await pageB.evaluate(contentInertScript())).toBe(true)`).
Stop condition 4 therefore has three independent pins, one of them a unit test
the card itself writes. The residual decision 2 admits — the app behind the
blocker is in the tab order for the `'acquiring'` interval — is recorded in the
return file by name, and the covering prompt's full-screen backdrop holds
pointer throughout it (`app.css:2520-2523`), with the blocker's own rAF
(`:505`) focusing its `tabIndex={-1}` dialog div (`:545`) a frame after mount.
So decision 2's phrase "holds pointer and keyboard throughout it" is very
slightly stronger than the code shows for the one frame before that focus lands
— about 16 ms, on a path where the grant usually arrives first anyway. It is
recorded rather than hidden, it is the residual of the stated residual, and
nothing in it touches `'secondary'`, which is what case (e) and stop 4 protect.
Noted, not filed.
