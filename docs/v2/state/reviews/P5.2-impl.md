## 5. The properties, inspected one at a time

### 5.1 Order — C-UPD@1 steps 1-5, and C-OWN@1 rule 1

`safety.ts:83-161` runs, in this order and nothing else: `applyPendingRestore`
(step 1's tail) → `existsSync(dbFile)` early return for a first run (step 2's
exclusion) → read-only open → `readAppliedVersions` → `newer_schema` refusal
(step 2) → pending computation → `takeSafetySnapshot` (step 3) → `runMigrations`
(step 4) → `pruneSafetySnapshots` (step 5) → `inspection.close()` in `finally`.
`index.ts:41-46` places the call between `applyPendingRestore` (`:34`) and
`openDatabase` (`:47`), which is the one position C-OWN@1 rule 1 allows, and
`openDatabase` still takes `locking_mode = EXCLUSIVE` (`db/index.ts:70`) only
after the schema is in place. The order claim is asserted through observable
effects, as the card directs: `safety.test.ts:70-104` proves the *restored*
file is the one the snapshot copied (`patientNames(snapshot)` is `['Maria Ruiz']`,
the restored practice, not `['John Smith']`, the one that was live) and that the
copy is pre-migration (`schemaLevel(snapshot)` is 5 while `schemaLevel(live)` is
the current level).

One consequence of the wiring, stated because it is easy to over-read: in
production `prepareDatabaseForStart`'s own `applyPendingRestore` is a no-op,
because `index.ts:34` already consumed the pending restore and
`restore.ts:217` removes the directory. So `PreparedDatabase.restored` is
`{applied:false}` in production and `true` only in the unit test, which calls
the function on its own. The restore-rollback and the warn log at `index.ts:120`
still read `index.ts`'s own result, exactly as the return claims. The card fixed
this redundancy in its own text ("`index.ts`'s entire edit is that call"), so it
is conformant; the residual is that the *wired* order is verified by reading
`index.ts:34-47` and by the implementer's two boots, not by a unit test. See §8.

### 5.2 The snapshot: staging, the destination, and the no-overwrite claim

`safety.ts:185-229` stages under `staging/pre-migrate-<uuidv7()>/` at mode `700`,
copies with `snapshotDatabase`, `PRAGMA integrity_check`s the copy
(`archive.ts:404`, already exported and already used the same way by
`restore.ts:160` and `archive.ts:178`), creates `safety/` at `700`, checks the
destination, and moves the verified file in. Cleanup in `finally` removes only
its own uuid folder, as C-SNAP@1 rule 3 promises. `safety.test.ts:156` asserts
the staging folder is empty afterwards, and `:103` asserts the staged copy was
*moved*, not copied.

**F2 (non-blocking, claim accuracy).** The comment at `safety.ts:209-211` says
"the move below is a move rather than a copy **for the same reason**: two runs
landing on one name is a caller's bug, never something to solve by deleting a
snapshot" — but `renameSync` *does* replace an existing destination; a move
gives no no-overwrite property at all. Probed directly:

```text
PROBE E renameSync over existing destination: destination now = "the verified safety snapshot", source exists = false
```

The only thing standing between a snapshot and a silent replacement is the
`existsSync` check at `:212`, which is check-then-act. In the single-threaded
replay the guard fires correctly and nothing is lost — probed by running the
whole sequence twice with the same injected stamp:

```text
PROBE 1 same-stamp replay: SECOND RUN THREW snapshot_failed: the pre-migration safety snapshot could not be taken,
        so the schema was left exactly as it was: a safety snapshot is already at …/safety/pre-migrate-5-11-2026-09-27T10-00-00-000Z.db
PROBE 1 safety dir after replay: ["pre-migrate-5-11-2026-09-27T10-00-00-000Z.db"]   (one file, not two)
PROBE 1 first snapshot still level 5, live now level 5
```

And in production a collision is unreachable anyway: C-OWN@1's lock means one
process per data folder, and the stamp is millisecond-resolution, so two starts
cannot share `<from>-<to>-<utc>` unless they land in the same millisecond. So
this is **not a reachable defect** — I am recording it because a future reader
will take the comment's word for a guarantee the code does not provide. The
one-line repair is a rewording (say that the `existsSync` check is the guard and
that C-OWN's lock plus the stamp make the race unreachable), not a behaviour
change. `snapshot.ts:30-36`'s own "must not overwrite" rule is untouched and
still enforced where it is enforced by SQLite: `VACUUM INTO` refuses a reused
path.

### 5.3 Read-only inspection, `VACUUM INTO`, and the write-ahead log

One handle, opened `{readonly: true}` (`:294-298`), serves both the inspection
and the copy, and `snapshotDatabase` is the same primitive the backup path uses.
`safety.test.ts:404-425` pins the WAL property with a real, uncheckpointed
committed write (`expect(existsSync(`${file}-wal`)).toBe(true)`) and asserts the
copy carries it; `safety.test.ts:371-402` pins that the handle rejects writes
and that `migrationLevel` — which runs `CREATE TABLE IF NOT EXISTS`
(`migrate.ts:81`) — throws `attempt to write a readonly database` when the table
is absent, which is why the module selects the table itself.

I checked the two facts the design most easily gets wrong, because they are not
covered by the test file and the first one would have been a boot-stopping
regression:

1. **The inspection handle is still open while the migration handle opens and
   runs** (`safety.ts:158-160` closes it only in the outer `finally`, and
   `runMigrations` is inside that `try`). A restored database is the one shape
   that is *not* in WAL mode — a `VACUUM INTO` product is in `delete` mode — and
   changing `journal_mode` needs a lock no other connection may hold. Probed
   against the real `better-sqlite3` on a `delete`-mode database with a read-only
   handle open and a completed `SELECT` on it:

   ```text
   PROBE A source journal_mode = delete
   PROBE A readonly-open + journal_mode=WAL: journal_mode set OK -> wal
   PROBE B WAL source, readonly handle open, write tx: write transaction OK
   ```

   No `SQLITE_BUSY`, in either journal mode, and the migration's write
   transaction is not blocked either. **Not a defect**; the sequence is sound.
2. **A read-only data folder.** With the folder at mode `0500` and no sidecars,
   the inspection open fails — but with `SQLITE_READONLY_DIRECTORY`, the same
   code today's `openDatabase` produces when it sets `journal_mode = WAL`, and
   one `storageErrorFor` branch (`errors.ts:189-197`) already maps it to
   `errors.storage_error.read_only`:

   ```text
   PROBE read-only folder, no sidecars: THREW SQLITE_READONLY_DIRECTORY attempt to write a readonly database
   ```

   So a read-only data folder is reported identically before and after this
   card. No regression, and no fourth code is needed.

### 5.4 `newer_schema`: never a downgrade, and the no-write claim

The refusal is raised in the inspection (`safety.ts:123-128`) before any folder
is created, and `migrate.ts:110-118` keeps the same guard for the direct path, so
both surfaces produce the same code and the same sentence.
`safety.test.ts:106-127` asserts the code, that `safety/` and `staging/` do not
exist afterwards, that the level that caused the refusal is still what the file
says, and that the practice's rows are intact.

**Precision, so the next reader does not over-read the test's name.** "Writes
nothing at all" is true of the database and of the app's own artifacts, not
literally of the folder: opening a WAL database read-only makes SQLite create
its `-wal`/`-shm` index sidecars, which a writable open does too, on any start,
before and after this card.

```text
PROBE entries before the read-only open: ["apunta.db"]
PROBE (a) writable folder, entries while the read-only handle is open: ["apunta.db","apunta.db-shm","apunta.db-wal"]
```

No practice data is in a sidecar beyond what the database already holds, and
nothing is written to the database file — `safety.test.ts:375-379` asserts an
`INSERT` through that handle throws. Not a defect; a wording caveat.

### 5.5 All pending migrations in one transaction, bookkeeping included

`migrate.ts:132-141` replaces the per-migration `db.transaction` with **one**
outer transaction over every pending migration, and the `schema_migrations`
insert is *inside* it (`:135`), which is what the contract's "all or nothing"
requires — a row can no longer claim a migration the schema does not have. The
IR asked for exactly this to be checked rather than assumed ("the loop really
became one transaction rather than N"): it did, and the bookkeeping is inside,
not after. `if (pending.length > 0) applyAll()` keeps a current database from
beginning a transaction at all. Both halves are asserted, not inferred:
`migrate.test.ts:135-176` (001's row *and* its table gone with 002's, and
`appliedVersions` is `[]`) and `safety.test.ts:159-208` (the same through the
whole sequence, with the pre-migration snapshot still on disk and nothing
pruned). The rewritten `migrate.test.ts` case is a strengthening, not a
weakening: the old expectation (`[1]` survived) was precisely the per-migration
behaviour the contract replaces, and the return discloses the change.

The card's stop condition is not triggered: no shipped migration contains
`VACUUM`, `BEGIN`, `COMMIT`, `journal_mode` or `PRAGMA` (checked across all
eleven files), so nothing had to be reported instead of edited. `migrate()` is
also the function `openDatabase` and the seed CLI use, and the change is
behaviour-preserving for them apart from the all-or-nothing property and the
error type.

### 5.6 Retention only after success, and only this module's files

`pruneSafetySnapshots` is called at `safety.ts:156`, inside the same expression
that already returned a successful `runMigrations` — an exception from the
migration propagates out of `prepareDatabaseForStart` before step 5 is reached.
`safety.test.ts:159-208` proves it with three older snapshots that would have

`/^pre-migrate-(\d+)-(\d+)-(.+)\.db$/` (`:57`) claims only this module's naming,

whose name sorts last and whose stamp sorts first. Keeping three *includes* the

## 6. F1 (non-blocking): a raw errno can escape after a successful migration

`pruneSafetySnapshots` is the only step in the sequence that can throw something
outside the three-code vocabulary: `rmSync(old.path, { force: true })` at
`safety.ts:283` re-throws anything that is not `ENOENT`, unwrapped and un-coded.
Probed with an undeletable entry that wears a snapshot's name (a directory, which
is the only such shape I could construct — unlinking a regular file depends on
the *directory's* write permission, and the rename into `safety/` at `:215` has
already proved the directory writable by then):

```text
PROBE THREW code=ERR_FS_EISDIR name=SystemError
PROBE message=Path is a directory: rm returned EISDIR (is a directory) …/safety/pre-migrate-5-11-2020-01-01T00-00-00-000Z.db
PROBE live level after the throw = 11 (shipped maximum 11)
PROBE safety dir = [ …the three 2020 entries…, "pre-migrate-5-11-2026-09-27T10-00-00-000Z.db" ]
```

So the escape happens **after** the migration succeeded (live is at level 11)
and after the new snapshot was taken. In production that means a boot-error page
for a fully migrated database, with a generic `errors.storage_error.cause`
sentence rather than one of the three codes, and — if a restore had been applied
— `index.ts:63-69` rolling that restore back. No snapshot is lost and no schema
is lost, so I do not treat this as acceptance-gating: nothing in the app's own
operation can produce a non-regular file in `safety/` (a `rename` is atomic and
never produces a directory; a crashed run leaves its folder under `staging/`).
It is reachable only from a hand-edited or damaged data folder, which is a
support case rather than a start-up path. The repair is one line — wrap the
removal, or ignore anything but a real failure — and it belongs to whoever owns
the next touch of this file; I am recording it, not requiring it.

## 7. The three questions I was asked to assess specifically

**(a) The broad `readAppliedVersions` catch returning `[]` on any error
(`safety.ts:174-183`).** Assessed, and it is safe in the direction that matters.
The dangerous answer would be "already current", because that is what lets a
database through untouched; `[]` is the opposite — it makes *every* migration
pending, which forces a snapshot and then a migration attempt that has to succeed
on its own merits. It also cannot silently pass a newer database through, because
no shipped migration is idempotent (`rg -c "IF NOT EXISTS" server/migrations/*.sql`
matches **nothing**; `001_init.sql` alone has six plain `CREATE TABLE`), so a full
re-run of all eleven on a level-11 practice fails at 001 rather than "succeeding".
Probed on a level-11 practice whose `schema_migrations` table exists but cannot
answer the query:

```text
PROBE 3 unreadable bookkeeping table on a level-11 practice: THREW migration_failed: the database could not be brought up
        to this build's schema, and nothing was changed: no such column: version
PROBE 3 live level now -1 (patients table still there: true), safety dir: pre-migrate-0-11-2026-09-27T10-00-00-000Z.db
```

The start stops with a refusal, the rows are intact, nothing was written to the
schema, and the snapshot of the current state is on disk. The two costs are
cosmetic and both point the same way: a redundant snapshot is taken (it consumes
one of the three retention slots, and its name reads `pre-migrate-0-11-…`), and a
`SQLITE_NOTADB` file is reported as `snapshot_failed` rather than as a corrupt
database, because `VACUUM INTO` fails on the same file right after
(`PROBE C not-a-database: SELECT SQLITE_NOTADB file is not a database` /
`VACUUM INTO threw SQLITE_NOTADB`). The docstring at `:163-173` states this
reasoning and the reasoning is correct. **No defect**; the catch is
deliberately broad and its worst case is a safe refusal.

**(b) Snapshot destination collision and the rename no-overwrite claim.** Covered
in §5.2: the guard fires and preserves the earlier snapshot in a single-threaded
replay, the collision is unreachable in production (C-OWN's lock, one process per
folder, millisecond stamps), and the `renameSync` overwriting behaviour means the
comment overstates the guarantee. Finding F2, non-blocking, comment-only fix.

**(c) `nativeBinding` propagation.** **Correct and complete for the handles this
module owns.** `PrepareDatabaseOptions.nativeBinding` (`:66`) is threaded to both
handles — `openReadOnlyHandle` (`:294-298`) and `openWritableHandle` (`:300-302`)
— and `index.ts:45` passes `config.sqliteBinding`, the same value `openDatabase`
receives at `:50`. One handle in the path is *not* this module's: the
`integrityCheck(copyPath)` at `:203` opens its own read-only handle inside
`archive.ts:400-412` without a binding, which in the packaged M8 app (where the
addon lives in `Contents/Helpers` and `APUNTA_SQLITE_BINDING` names it) would
fail to locate `better_sqlite3.node` and surface as `snapshot_failed`. That is
**not a P5.2 defect**: it is the existing P5.1 pattern, used the same way at
`restore.ts:160` and `archive.ts:178`, in a file this card may not edit, and the
implementer's boots ran unbundled so they could not have surfaced it. Recorded
as a handoff to M8: when the packaged layout is exercised, `integrityCheck`
needs the same binding its callers hold.

**(d) The restore-rollback interaction the IR handed over** (IR-08's last
paragraph). Dispositioned: **not a defect, and the worst case is unreachable.**
`index.ts:63-69` rolls an applied restore back on any boot failure, which
predates this card (`restore.ts:226-231` documents it as the intended behaviour
when a restored file cannot be opened), and this card adds triggers to it — but
the alarming one cannot fire. `stageRestore` refuses an archive above the running
build's level (`restore.ts:141-149`, `schema_too_new`, surfaced as a 409 at
`routes/backup.ts:123-125`), and the running build's level is its own maximum, so
a **restored database is never newer than the code that restores it** and
`newer_schema` is unreachable on that path. The reachable triggers are
`snapshot_failed` and `migration_failed`; both roll back to the pre-restore
database, and the archive itself is untouched by staging, so the restore can be
re-attempted. The one real gap is that nothing tells her *on the page* that the
restore was undone — the log line at `index.ts:76` does, and the page's sentences
are S2.5's file, outside May edit.
