### D-01 — V3/V6/V9 identify the language from `APUNTA_DEV_SPANISH`, which proves availability, not the active stored language — **DEFECT (material)**

Both V6 (`:861`) and V9 (`:864`) rest the cross-project attribution on the flag:

> the `es-MX` project runs against a server started **with** it, and §4 rule 1 ties
> the dictionary to the active UI language

Two links, and the first is wrong. `APUNTA_DEV_SPANISH` is read in exactly one
place for this purpose: `server/src/routes/settings.ts:26-33`, `spanishAvailable()`,
whose sole effect is to set `spanish_available` in the `GET /api/settings`
response (`:52`) and to decide whether a `PUT { language: 'es-MX' }` is *accepted*
(`:74-80`). It **does not choose the language**. The language is the **stored**
setting, and `storedLanguage` (`:42-45`) returns `DEFAULT_LANGUAGE` when there is
no row; `DEFAULT_LANGUAGE = DEFAULT_LOCALE = 'en'` (`shared/src/settings.ts:43`,
`shared/src/i18n/locales.ts:22`). The `es-MX` server's data folder is
`${APUNTA_DATA_DIR}-es-MX`, created empty by `mkdirSync(esDataDir, { recursive:
true })` at `e2e/playwright.config.ts:34-37`. So on a fresh folder the active
language is **`en` even with the flag set** — a server that offers Spanish and
serves English.

The second link — §4 rule 1 tying the dictionary to the *active* language — is
correct and is exactly what makes the first link insufficient.

**Nothing in V3's evidence records the active language.** §10's `V3-assets.md`
carries the exit code, the emitted names, the observed URLs for both halves, the
observed file and its sorted copy, and the collected counts — no language. V3's
*Expected* asserts `exit=0`, exactly four emitted names, and the (a)/(b) halves;
the clause "the stored language is `es-MX` at the moment the assertions run" is in
**V2's** Expected, not V3's. So the fact V9's attribution depends on is asserted
in a different row, on a different run, and is not carried into the evidence file
V9's own argument cites.

**Contributing mechanism, stated as read and not measured:** V3's invocation is
`--project=es-MX --grep "no dictionary asset is requested until a spell surface
mounts"`. `--grep` is a global title filter applied across the selected projects
*and their dependencies* (Playwright 1.62.1, `package-lock.json:1256-1258`), and
the `es-MX` project declares `dependencies: ['es-MX-language']`
(`playwright.config.ts:111`) whose tests are the ones that switch the stored
language. If the filter does reach the dependency, then V3 inherits
`language = es-MX` only as a **side effect of V2 having run first** on the shared
run folder — an ordering precondition stated nowhere in V3's command or Expected.
Either way the conclusion is the same: **V3 cannot establish the active language
from its own evidence, and V9's stated basis does not establish it.**

**Failure scenario.** V3 runs before V2, or V2 is skipped or red. The `es-MX`
folder's stored language is `en`; the assets case loads the **English** pair; V3
is **green** (its halves are project-agnostic and both hold for the English pair);
V6 also observes the English pair; V9's `comm` yields an empty difference and V9
fails with `difference-lines=0` — a red row whose message ("zero lines means the
two runs observed the same pair") points at the wrong cause. Or, in a resumed
session where V3 is skipped, V9 can read a stale `observed-es-MX.txt` from an
earlier run and pass on it (D-02). Neither is the failure the row was written to
catch, and §9.1's contingency ("bring the discrepancy to the coordinator") would
be aimed at the implementation rather than at the row.

**Parked fix (bounded, two sentences, no command change).** In V3's *Expected* and
in V9's attribution sentence, replace the flag as the basis with the stored
language and say how it is recorded: *the `es-MX` folder's stored `language` is
`es-MX` because V2 ran the `es-MX-language` dependency on this run folder before
V3; V3's command asserts it directly by reading `GET /api/settings` on the Spanish
base URL and failing unless `language === 'es-MX'`, and `V3-assets.md` records that
value.* The flag may stay in the text, but only as what it is — the offer, and the
reason the `chromium` run cannot select the Spanish pair at all.

### D-03 — "both runs share one build" is false about these executions, only one build's emitted list is recorded, and a two-line *hash* difference satisfies every V9 gate — **DEFECT (material)**

V9's attribution paragraph asserts:

They do not share a build. `e2e/playwright.config.ts:115-141` is a `webServer`
**array**; the first entry's command is `npm run build && node server/dist/index.js`
(`:119`) and the second's is `node server/dist/index.js` (`:133`) — the second
server reuses the first's build. `reuseExistingServer` is `false` under
`APUNTA_V2` for **both** (`:124`, `:136`), and V3 and V6 each mints or sources a
sandbox env, so each Playwright invocation builds once. **V3 and V6 are two
invocations, hence two builds.** They will normally be byte-identical (Vite names
are content-hashed, and the inputs come from the same `node_modules`), which is
probably why nobody noticed — but it is an inference, and nothing records it.

Only **V3's** emitted list is captured. V6's command contains no `ls
web/dist/assets` and no `cp` into the observed directory; it writes
`observed-chromium.txt` and nothing else. So `$OBS/emitted-dictionary-assets.txt`
is one build's list, presented as both runs'.

**Counterexample (synthetic):** the same source built twice, the Spanish pair
hashing differently on the second build (a changed `node_modules`, a rebuild after

difference is equally consistent with the builds differing, and the row cannot
tell them apart. `emitted-matches=2` does not help: both names are in the emitted
list by construction.

**Failure scenario.** Exactly the wrong-but-green the card exists to avoid. The

### D-04 — on a failed chain V9 prints, and §10 transcribes, a `spanish-pair.txt` left by an earlier run — **DEFECT (material, evidence integrity)**

V9's chain is
`… && sort -c -u A && sort -c -u B && comm -23 A B > spanish-pair.txt`. When either
sorting gate fails, the `&&` short-circuits, so `spanish-pair.txt` is **not
rewritten** — a pre-existing one survives. The statements after the `;` then `cat`
it, take `wc -l` of it and `grep` it.

**Counterexample (synthetic, the sharp case):** `spanish-pair.txt` left holding two
names that *are* in the current emitted list, and one input made unsorted:

```
sort: …/observed-es-MX.txt:2: disorder: index-B2yR7tLp.dic
sorted-and-comm-exit=1
es-MX minus chromium:
index-B2yR7tLp.dic
index-Dq1xK9ab.aff
difference-lines=2 emitted-matches=2
exit=1
```

`comm` never ran, yet the row prints `difference-lines=2 emitted-matches=2` — the
precisely the pair of figures §10 requires `V9-asset-identity.md` to record as the
executed `comm`'s printed output. The **row's** exit is 1, so this is bounded: V9
does not pass. But a reviewer transcribing §10's evidence gets a stale difference
beside `sorted-and-comm-exit=1`, and nothing in the printed block says the `comm`
was skipped. In the milder fixture the printed lines are
`STALE-FROM-AN-EARLIER-EXECUTION.*`, which is at least visibly wrong; the sharp
case is the one that could survive review.

**Failure scenario.** V9 fails for a sorting reason, the return file quotes the
figures per §10, and the evidence shows a two-name difference that no execution
produced. This is the "match count is not evidence" mistake the proposal has
corrected twice, reappearing one level down.

**Parked fix (bounded, one clause).** Have V9 remove `spanish-pair.txt` before the
chain — `rm -f "$OBS/spanish-pair.txt" &&` as its first statement after `OBS` is
set — and change the `&&` to `;` before the redirect so the file is always
(re)created, empty on a failed chain. Then `cat` prints nothing, `n` is 0, and the
printed figures cannot be stale. Alternatively gate the `cat`/`n`/`m` block on
`test "$chain" -eq 0`.

### D-05 — V3 and V6 read only Playwright's exit status, so a failed `sort -u` or `cp` leaves the row green with an empty observed copy — **DEFECT (moderate)**

`rc` is captured immediately after Playwright and is the row's only propagated
status; the `sort -u … > "$OBS/…"` and `cp …` steps that follow are separated by
`;`, and the row ends `exit $rc`. Both V3 and V6 *print* the result of the copy
("observed-es-MX, sorted and de-duplicated for V9:") but never check it.

**Counterexample (synthetic):** the case never wrote its observed file (a new file
whose write path is not taken, a rename, a crash after the assertions):

```
sort: cannot read: …/observed-es-MX.txt: No such file or directory
sort exit=2
row still ends 'exit $rc' -> exit 0, i.e. GREEN
  observed-es-MX.txt is 0 bytes
  but V3's own log prints 'observed-es-MX, sorted and de-duplicated for V9:' followed by nothing
```

The redirect creates the file, so a **zero-byte** observed file is what V9 sees. The
damage is bounded — V9's `difference-lines=0` catches it (measured, V9-7) — but V3
and V6 are green while having contributed nothing, and the failure surfaces two
rows later with a misleading message. This is the same class as the `git checkout`
defect v1 had (A10): a row's exit status must carry its own postprocessing.

**Parked fix (bounded, one clause each).** `sort -u "$RUN_LOGS/observed-*.txt" > "$OBS/observed-*.txt" || exit $?`
and `cp … || exit $?`, or fold the postprocessing into the status:
`… ; rc=$?; sort -u … || rc=$?; cp … || rc=$?; …; exit $rc`. Also worth requiring
the two observed copies to be **two lines** in the row that wrote them, so an
empty or one-line copy is caught where it is made.

### D-06 — V1(c) still asserts "the flagged sets are equal" without naming a representation, and it is false under the raw reading — **DEFECT (narrow)**

V1(c) reads: "the *projections* `{plainWord(m.word)}` over the flagged words, and

**Failure scenario.** An implementer reads the bare clause as a second, independent
assertion about the flagged words and writes `expect(a.words).toEqual(b.words)`.
The test goes red for a correct implementation — §9.1's contingency again, aimed
at the wrong thing. This is R-02's own defect surviving in the one sentence R-02
asked to be rewritten, one clause narrower.

**Parked fix (bounded, three words).** Delete "and the flagged sets are equal", or
change it to "and the flagged sets, as `{plainWord(m.word)}` sets, are equal".

### D-07 — `emitted-matches` records blank rather than `0`, and the row then dies on an arithmetic error — **NIT**
