## Defects (confirmed by code and route/Rust semantics)

### D1 — HIGH — Self-proving API facts: six flows can be recorded PASS without reaching their screen

The card's flow-completion rule is "the app reached the next screen **and** the
harness read the fact proving it", and the clarification says "API reads prove
resulting application facts, not substitute for … interactions". For these
flows the asserted fact is true before the UI action and is unchanged by it, so
the flow passes on the API alone:

- `flowPatientList` (`:1579-1590`) asserts `patients.length > 0` — the patient
  was created by API in `flowCapture` (`:1359`); the list endpoint
  (`server/src/routes/patients.ts:32`) answers independently of any screen.
- `flowPlan` (`:1593-1620`) asserts `planFor(...) !== null`, but
  `GET /api/patients/:id/plan` returns `{ plan: null, goals: [] }` when no plan
  exists (`server/src/routes/plans.ts:91`), so `planFor` (`:803-806`) returns a
  non-null object and the check (`:1615-1619`) passes with **no plan and no
  pane**.
- `flowBriefing` (`:1623-1645`) asserts `briefsFor(...) !== null`, but
  `GET …/prep` always returns `{ briefs: [...] }` (`server/src/routes/prep.ts:51`),
  so `briefsFor` (`:808-811`) is never null.
- `flowBrainstorm` (`:1648-1670`) asserts `read.ok`; the GET returns 200 for any
  existing patient (`server/src/routes/brainstorm.ts:127`).
- `flowSettings` (`:1673-1693`) asserts `apiGet('/api/settings').ok`; the GET is
  always 200 (`server/src/routes/settings.ts:60`).
- `flowDraft` (`:1456-1480`) never drives the draft screen at all: it re-reads
  the note `flowCapture` created and checks its content for `Subjective`. The
  "draft" screen is never reached or verified.

The screenshots are saved but never asserted on, so they cannot distinguish a
reached screen from an unreached one. Exact mechanism: replace each always-true
API read with a fact that only exists once the pane is open (a pane-only state,
or a screenshot-grounded assertion of a distinctive element), make `flowPlan`
assert `plan.plan !== null` or drive a real plan, and record the flow `NOT RUN`
when the screen cannot be confirmed. This is the review's central finding.

### D2 — HIGH — The ownership containment is guaranteed to FAIL on a healthy run

`ownershipBefore = snapshotOwnership()` is taken at `:1149`, **before**
`launchApp` (`:1153`). The app creates `apunta.lock` and `apunta.db` in
`APUNTA_DATA_DIR` at startup (`server/src/index.ts:39-40`,
`server/src/config.ts:185`), and the shell passes `APUNTA_DATA_DIR` to the
child (`src-tauri/src/main.rs:407`). The sandbox data dir is empty before the
launch (verified: `sandbox.mjs env` creates only empty `data/`, `logs/`, `tmp/`).
So `created = after.filter((file, index) => file.present && !ownershipBefore[index].present)`
(`:1283`) flags the run's **own first set**, and
`check('smoke no second lock, database, -wal or -shm', created.length === 0)`
(`:1285-1288`) fails every healthy run. The sibling `tauri-lifecycle.test.mjs`
snapshots **after** the first instance is up and says why (`:1064-1075`); the
security sibling snapshots before but compares against the four fixed names
(`:2038-2048`, `:2343-2347`). Exact mechanism: move the baseline to after the
first instance is up (and assert the first set exists), or compare by
name-set beyond the four C-OWN@1 names. As written, V3 cannot exit 0.

### D3 — HIGH — The virtual-audio containment has no signal teardown, though the file claims one

The header comment (`:59-60`) states the teardown "restores the remembered
default and unloads both modules on every exit path, **including signals**". The
file installs **no** `process.on('SIGINT'|'SIGTERM'|'SIGHUP'|'exit')` handler
(grep: none); `containment.teardownSync()` is called only in `runSmoke`'s
`finally` (`:1264`). A Ctrl-C or SIGTERM during capture leaves the owner's
default capture device pointed at `apunta_p35_mic` (silence for any other app)
and both `module-null-sink`/`module-remap-source` loaded. The audio sibling
installs exactly the missing traps (`tauri-audio.test.mjs:518-528`). Exact
mechanism: install the same `installTraps` (SIGINT/SIGTERM/SIGHUP plus `exit`)
calling `containment.teardownSync()`.

### D4 — HIGH/MEDIUM — The observation-channel containment passes vacuously when the bundle is absent, and scans a path the card does not name

`observationChannelGone()` (`:935-951`) returns `{ occurrences: 0, files: 0 }`
when `build/linux-resources/web/dist/assets` does not exist, and the check
(`:1294-1298`) passes on `occurrences === 0` alone. A missing or differently
laid-out bundle therefore reports the channel "gone". The card names
`web/dist/assets/*.js`, and the security sibling's `countInShippedWebDist`
returns `-1` when its directory is absent so the check fails
(`tauri-security.test.mjs:2300-2305`). Exact mechanism: fail when `files === 0`
(and scan the card's path, or assert the shipped path exists).

### D5 — MEDIUM — `NOT RUN` is counted `ok: true` and exits 0

`notRun` (`:113-117`) pushes `{ ok: true, notRun: true }`; the summary
(`:1744-1754`) filters only `!r.ok`, so a run in which every flow is `NOT RUN`
and no `check` failed exits **0**. V3's mechanical criterion is exit 0, and the
card says "NOT RUN is never PASS" and "a NOT RUN blocks approval". A single
`NOT RUN` flow (e.g. copy) would be recorded as a passing row. Exact mechanism:
return a non-zero code when any flow is `NOT RUN`, or have the V3 row read the
`NOT RUN` count rather than only the exit code. (Also: `blocked` is never set,
so the `blockedCount > 0 ? 3` branch at `:1753` is dead code.)

### D6 — MEDIUM — No freshness predicate is implemented anywhere in the row

The V3 Expected cell requires the freshness walk over Rule B's set — `git diff
--name-only <base>...HEAD -- <set>` plus `git status --porcelain -- <set>`,
with `<base>` the literal hash on the dispatch header — as the thing that makes
a stale bundle visible. Neither the V3 command (`dispatch/P3.6.md` line 447) nor
the harness contains any `git` call (grep: none). The sibling
`tauri-security.test.mjs:1900` implements the equivalent `RULE_B_BASE_COMMIT`
freshness assertion; this harness does not. The resume anchor asserts freshness
in prose, but the executable row has no mechanism. Exact mechanism: implement
the predicate in the harness (reading the base from the dispatch header or an
env var the V3 command exports) or add it to the V3 command.

## Risks (runtime-dependent; a defect only if the assumption fails)

### R1 — MEDIUM — Colour-cluster selection is not ambiguity-fail-closed

`findClusters` sorts components by size (`:655`) and every caller clicks
`clusters[0]` — the **largest** accent cluster (`:1334`, `:1427`) — with no
check that exactly one plausible cluster exists. On any screen with more than
one accent element the wrong control may be clicked; combined with D1, a wrong
click can still produce an always-true API fact and record PASS. The requested
"ambiguous → fail closed" behaviour is absent. Exact mechanism: require a unique
top cluster by a size margin, or record `NOT RUN` on ambiguity.

### R2 — MEDIUM — The copy assertion is a colour count, not the Copied state

`flowPublishAndCopy` (`:1570-1575`) asserts `distinctColours(copyShot) >= 8`,
which is true of any rendered window. The clarification permits asserting the
Copied feedback "by native screenshot/state"; a raw colour count is neither and
does not assert the Copied control. Exact mechanism: assert a Copied-specific
fact (a changed control label/colour region, or a state read over the origin).

### R3 — MEDIUM — The physical microphone is never checked, despite the claim

The header (`:58-59`) says "a stream on it is a stop, not a warning", but
`containment.create` (`:981-1029`) only reads back the default source; there is
no `pactl list source-outputs` (or monitor) check for a stream on a non-virtual
source. Exact mechanism: while recording, assert no source-output is attached to
a non-virtual source, or remove the claim.

### R4 — MEDIUM — Zero windows is recorded FAIL, not NOT RUN, and the flows are not individually recorded

`runSmoke` (`:1156-1165`) records one `check` FAIL for the window and returns
without recording the eleven flows as `NOT RUN`. The fixed decision and Stop 5
require "zero windows found on the display is `NOT RUN`". The per-flow `NOT RUN`
list S4 needs is therefore absent on an early abort. Exact mechanism: record the
affected flows `NOT RUN` with that cause.

### R5 — LOW/MEDIUM — Importing the module executes top-level code and `main()`; no entry-point guard

Lines `:122-143` run on import and call `process.exit(2)` when the sandbox
variables are absent; `:1757` unconditionally awaits `main()`. A safe probe
confirmed that importing the module terminates the process at the precondition
(exit 2) rather than returning. The security sibling guards with an
`isEntryPoint` test and exports helpers for exactly this purpose. Exact
mechanism: add the `isEntryPoint` guard and move the precondition checks inside
`main`.

### R6 — LOW — Undeclared runtime dependencies (ImageMagick, `paplay`) are not in Stop 2

The harness shells out to `import`, `identify`, `convert`, `compare` and
`paplay`; Stop 2 names only `webkit2gtk-4.1`, `libxdo`,
`libayatana-appindicator` and `xvfb-run`/`xdotool`. All are present on this
machine, but on one without ImageMagick the capture returns null and the result
is a generic FAIL/`NOT RUN`, not a named BLOCKED. Exact mechanism: name these in
Stop 2 or add a named precondition probe.

### R7 — LOW — Redundant double `xvfb-run`

V3's command already wraps the harness in `xvfb-run -a` when available
(dispatch line 447), then `ensureDisplay` (`:274-301`) re-execs under
`xvfb-run -a` again because the guard env var is set only by the harness's own
re-exec. The outer display is discarded. It works, but wastes a server and
subverts the card's "the command chooses the display". Exact mechanism: honour
an already-set `DISPLAY` (or set the guard when `DISPLAY` is present) so the
harness does not re-wrap.
