## 1. The defect, and the recommended source-level fix

`config.ts:11-12` and `platform/data-lock.ts:50-53` each build a runtime `createRequire(import.meta.url)` and require a *relative* `package.json`. From source both land on the same file, `server/package.json`, and both are `0.0.0` today, so a wrong-file bug is invisible. In a bundle at `<folder>/server/server.mjs` the specifiers split: `../package.json` is inside the folder, `../../package.json` is one level above it. The throw is at import time, ahead of `index.ts:19` and long before `serveBootError`, so the card's missing-SQLite negative case is unreachable and every Step-3 check dies alike.

Two script-only routes, each closed by a check rather than by taste:

- **`package.json` outside the folder** (the readiness report's option (b)) — **rejected**: not self-contained, and the test copies *only* the folder, so the copy could never resolve it. `package-mac.sh:225-229` records that a package-less bundle is deliberate (`.mjs`; "of which there is none inside an app bundle").
- **Move the bundle** — impossible while `migrations/` stays at `<folder>/migrations`: `config.ts:15,165` derives `migrationsDir` from the bundle's parent and has **no** `APUNTA_*` override (grep: 0 hits). The bundle's directory is therefore pinned one level below the folder root, and from *any* single-level name the two specifiers resolve to `<folder>/package.json` and `<folder>/../package.json` — the escape does not move. Only a two-level bundle captures both, and that forces `migrations/` to `<folder>/server/migrations` and rewrites V1's path list.

A scoped source-level amendment is the recommendation; the review did not prove that every script-only approach is impossible. The layout stays unchanged.

## 2. Recommendation — one build-time constant, lazy read, specifiers unchanged

The version becomes a **build-time injected constant**, with the existing `createRequire` read as the from-source fallback. `server/src/config.ts`, replacing `:11-12` (and `:174` → `version: APP_VERSION,`):

```ts
/** Substituted by the release bundler (esbuild `--define`); absent from source. */
declare const __APUNTA_VERSION__: string | undefined;
const require = createRequire(import.meta.url);
function packageVersion(): string {
  const pkg = require('../package.json') as { version?: string };
  return pkg.version ?? '0.0.0';
}
const APP_VERSION = typeof __APUNTA_VERSION__ === 'string' ? __APUNTA_VERSION__ : packageVersion();
```

`server/src/platform/data-lock.ts` replaces `:50-56` with the identical block using `'../../package.json'`; `:326` is unchanged. **No new local import**: `data-lock.test.ts:112,131` imports the bare `.ts` under Node 24 type-stripping, where a `./x.js` specifier would not resolve. The existing esbuild step of `scripts/v2/package-linux-resources.sh` gains:

```sh
APP_VERSION="$("$BUNDLED_NODE" --input-type=module -e "import {readFileSync} from 'node:fs';process.stdout.write(JSON.parse(readFileSync(process.argv[1],'utf8')).version)" "$REPO/server/package.json")"
run npx --yes esbuild "$REPO/server/dist/index.js" --bundle --platform=node --format=esm --target=node24 \
  --external:better-sqlite3 "--define:__APUNTA_VERSION__=\"$APP_VERSION\"" --outfile="$FOLDER/server/server.mjs"
```

Read from `server/package.json`, **not** the root manifest: that is the file both callers read today, and the two versions are independent. Rejected alternatives, briefly: a static `import … with { type: 'json' }` needs `resolveJsonModule` (absent repo-wide) and puts a file outside `rootDir: ./src` into the program — a `tsc` risk for the whole server I cannot test here; an esbuild plugin could transform source through onLoad, but introduces a second build-specific source transformation to maintain; it is not categorically impossible; a `try/catch` alone yields a **silent `0.0.0`** in health and in the lock, failing the correct-version requirement. This design fails **loudly** instead: drop the define and the bundle throws at import, exactly as today.
