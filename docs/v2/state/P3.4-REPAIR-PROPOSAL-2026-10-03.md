### A.2 What the conjunct is replaced with, and the exact evidence required

C-BRIDGE@1 rule 4 (`docs/v2/CONTRACTS.md:223-224`) has three conjuncts, all
about **authorisation and reachability**, none about the absence of a global:
`"capabilities": []`, `withGlobalTauri: false`, no custom `invoke_handler`
commands. The proposal keeps `withGlobalTauri: false` as the runtime proof
(`tauri === 'undefined'`, which the shipped binary already satisfies) and adds
the runtime fact that the always-present object is **not a live door**.

**Probe target — a real, known-existing, harmless built-in command:**
`plugin:event|listen`. Verified in the pinned source, not assumed:

| Claim | Local source |
| --- | --- |
| The `event` core plugin is registered in **every** app, unconditionally, by `register_core_plugins` | `tauri-2.12.1/src/app.rs:1257-1260` (`self.handle.plugin(crate::event::plugin::init(self))?;`) |
| Its commands are `listen, unlisten, emit, emit_to` | `tauri-2.12.1/src/event/plugin.rs:69-75` |
| The shipped app registers only one extra plugin besides those core ones, and that one has **no commands at all** (no `#[command]`, no `invoke_handler`, no `permissions/`) | `src-tauri/src/main.rs:106-116`; `~/.cargo/registry/src/index.crates.io-*/tauri-plugin-single-instance-2.5.2/src` |
| Nothing in `src-tauri/` registers an event handler or capability that could allow it | `src-tauri/tauri.conf.json:10` `"capabilities": []`; V3's word loop passes |

`listen` is harmless in the sense that matters here: even if it were ever
reachable, it registers a listener and mutates no state, writes no file and sends
nothing. **The pass condition does not depend on that**, because pass requires a
**rejection carrying the ACL text** (§A.3), and a reachable-but-ill-argumented
`listen` would reject with a *serde/argument* error, not with the ACL string —
i.e. it would FAIL loudly rather than pass quietly.

**Why the ACL path is the one this command takes** (`tauri-2.12.1/src/webview/mod.rs:2076-2109`):

```
if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
   && request.cmd != crate::ipc::channel::FETCH_CHANNEL_DATA_COMMAND
   && invoke.acl.is_none()
```

`plugin:event|listen` sets `plugin_command` to `Some`, so the branch is taken
regardless of origin and regardless of whether the app has an ACL manifest, and
with `"capabilities": []` no capability resolves, so `invoke.acl.is_none()`.
The **release** build (the AppImage is `tauri build` →
`[profile.release]`, `src-tauri/Cargo.toml:22-28`, so `debug_assertions` is off)
rejects with, at `webview/mod.rs:2105-2108`:

```
Command plugin:event|listen not allowed by ACL
```

**This exact string is the evidence.** It is produced by the Rust ACL gate and is
*distinguishable* from the "no such handler" rejection
(`webview/mod.rs:2162`, `:2167` — `Command {command} not found`) and from
`Plugin not found` / `Command not found` in the debug path
(`src/ipc/authority.rs:403-406`). That discrimination is the whole point of
requiring ACL-denial text instead of accepting "any rejection": a rejection
proves nothing about *which* gate stopped it, and a rejection from a command
that does not exist proves nothing at all.

## C. Native ↔ CSS geometry and the click, measured rather than guessed

### C.1 What stays a hypothesis

`docs/v2/state/reviews/P3.4-diagnosis-2026-10-03.md:173-181` attributes the
failed click to a window-relative vs viewport-relative mismatch plus a CSD
titlebar displacement `oy ≈ 26-40 px`. **That stays a hypothesis, and this
proposal adds nothing that could launder it into a fact.** Specifically:

- `innerWidth/innerHeight` and `outerWidth/outerHeight` **do not establish where
  the content origin is.** The difference between outer and inner is *some*
  chrome; it is not attributable to a titlebar rather than a border or a shadow,
  and under a WM-less Xvfb GTK's client-side decorations make that attribution
  worse, not better. They are published **as diagnostics and as a sanity bound
  only**, and the transform used for clicking is **solved from two observations**,
  never from them.
- **No titlebar height is guessed anywhere, and app decoration is not changed.**
  `show_main` keeps `.title("Apunta")` and no `.decorations(false)`
  (`src-tauri/src/main.rs:471-490`); `src-tauri/` is not in this proposal's
  permitted paths (§7).
- **The diagnosis's window-size arithmetic does not check out**, which is a reason
  to measure rather than to trust it. It states window `1216x817` at
  `(35, 91.5)`. From the code: display `1400x1000` (`-screen 0 1400x1000x24`,
  harness `:373-383`), `MARGIN = 0.95` (`main.rs:544`), `WANTED 1280x860`
  (`main.rs:71-72`), scale 1 ⇒ physical `min(1280, 1330) x min(860, 950) =
  1280x860` at `((1400-1280)/2, (1000-860)/2) = (60, 70)`. Those are the numbers
  the code gives; they are not the numbers the failure was attributed to. **The
  reviewer should treat the whole displacement paragraph as unmeasured**, and the
  proposal is built so that its truth value does not matter to the method.

### C.2 The calibration: two fixed observations, solve, validate, then one click

The method, in order, with **no click until a change has been measured**:

1. **Read the window in native coordinates.** `xdotool getwindowgeometry --shell
   <id>` → `X`, `Y`, `WIDTH`, `HEIGHT` (already spawned at `:468-484`; the
   fields parsed at `:475-478` today discard `X`/`Y` and must be kept).
2. **Read the viewport in CSS pixels.** From a fact line: `vpW`, `vpH`, `dpr`,
   `scrX/Y/W/H`, `outerW/H`. Assert `vpW >= 400 && vpH >= 300`; otherwise the
   calibration is `NOT RUN` with that cause.
3. **Two fixed calibration targets, computed identically on both sides.** The
   harness derives them from the published viewport — never from a hardcoded
   pixel:
   `P1 = (round(vpW*0.50), round(vpH*0.50))`, `P2 = (round(vpW*0.75),
   round(vpH*0.60))`. Both are interior, both avoid the top edge (where a CSD
   titlebar would swallow the move), and they differ by `≈0.25*vpW ≥ 100` px in x
   and `≈0.10*vpH ≥ 30` px in y, which is what makes both axes solvable.
4. **Move, without pressing anything.** For each of `P1`, `P2`: record `ptrN`
   before, run `xdotool mousemove --sync <X> <Y>` in **screen** coordinates,
   then wait for a fact line whose `ptrN` is **strictly greater** and whose
   `ptrCX/ptrCY/ptrSX/ptrSY` are present. Read the pointer back with `xdotool
   getmouselocation --shell` and require `|X_read − X_asked| <= 1` and the same in
   y, so a silently-failed `XWarpPointer` becomes a **named** cause
   (`diagnosis:244-247`).
5. **Solve the transform, per axis, from the two observations:**
   `k_x = (sx2 − sx1) / (cx2 − cx1)`, `ox = sx1 − k_x * cx1`; likewise `k_y`, `oy`.
   Assert `0 < k <= 4`, and **record `k` next to the published `dpr` without
   equating them** — page zoom is exactly the case where they differ.
   Consequently the content origin in native coordinates is
   `(ox − windowX, oy − windowY)`, **derived**, and it lands in the evidence as a
   measured number rather than an assumption.
6. **Validate before the first click.** The two observations must be mutually
   consistent: the per-axis `k` computed from the pair must be the same to within
   `0.01`, and re-deriving the origin from each observation separately must agree
   within 1 px. A run that cannot produce two observations is `NOT RUN` with
   "the page published no pointermove for calibration target N", and **no click
   is issued** — which is the required "no click-until-change" discipline.
7. **One click, in screen coordinates.** Convert the rectangle's centre
   `T = (cx + floor(w/2), cy + floor(h/2))` to
   `(round(k_x*cx + ox), round(k_y*cy + oy))`, then:
   `xdotool mousemove --sync <X> <Y>` → read back and require the ≤1 px match →
   `xdotool click 1`. **The `--window` form is dropped on purpose**: it is
   window-relative (`xdotool.1`, "Coordinates 0,0 are at the top left of the
   window you choose"), which is the space whose ambiguity produced the failure;
   screen coordinates are the space `getmouselocation` reports, so the same
   instrument both sets and verifies them.
8. **Close the loop on the click itself.** Require `clickN` to have advanced by
   exactly 1, and require `|clickCX − T.x| <= 2 && |clickCY − T.y| <= 2`, and
   record `clickEl`. A `clickEl` that is not the label's own leaf is a **FAIL
   naming `clickEl`** — the wrong-element case, finally diagnosable. **The
   landing is still proved by a fact change (§D), never by the click
   succeeding.**
9. **Exactly one click per target.** No second attempt at a different point, no
   retry after a `FAIL`, no widening of the 30 s window (`diagnosis:259-261`;
   card stop conditions). If step 6 or 7 cannot produce a measured, verified
   click, the row `FAIL`s with the numbers it does have.

### C.3 The clicked command's exit status, stdout and stderr are all checked

Today `spawnAsync` (`:1215-1229`) resolves on `close` and returns **only**
`{ stdout, stderr }`; the exit code is discarded, and `clickAt` (`:722`) collapses
everything into `ok = !stdout.includes('XError')`, which `clickAndWaitForChange`
then ignores entirely (`:736-751`). Proposed, in the same file only (no shell is
involved anywhere — every invocation stays the array form of `spawn`, so there is
no `sh -c` and no shell change to review):

```js
// spawnAsync: resolve with the exit status too. No caller changes shape except
// the ones below, and no caller may treat a non-zero status as success.
child.on('close', (code, signal) => done({ code, signal, stdout, stderr }));
child.on('error', (error) => done({ code: null, signal: null, stdout: '', stderr: String(error) }));
```

```js
// clickAt: every dispatched command's exit status, stdout and stderr are read.
async function moveTo(x, y) {
  const result = await spawnAsync('xdotool', ['mousemove', '--sync', String(x), String(y)]);
  const read = await spawnAsync('xdotool', ['getmouselocation', '--shell']);
  const at = Object.fromEntries(
    read.stdout.split('\n').map((line) => line.trim()).filter((l) => l !== '')
      .map((line) => [line.slice(0, line.indexOf('=')), line.slice(line.indexOf('=') + 1)]),
  );
  return { x, y, result, at, read };
}
```

`moveTo` returns the raw `code`, `signal`, `stdout` and `stderr` of **both**
commands; every consumer puts them in the assertion detail on a failure, and
**any non-zero `code` on either command, or an `XError` in either stream, is an
immediate `FAIL`** naming the command, the code and the line — not a click that
proceeds and is then judged by a page fact. `clicked.ok` stops being discarded
(`diagnosis:149-151`).

## D. Landing proof — two facts, told apart, and no rectangle movement

**Before** (`:730-755`, `:1046-1068`): the predicate is `changed = after !==
before || fact !== null`, where `before`/`after` are `rectSignature` (a JSON of
every published rectangle) and the patient click passes `undefined` as its
predicate (`:1050`), so a rectangle-only change satisfies it. The card requires
the opposite (`docs/v2/cards/P3.4.md:542`: "A click that landed is proved by the
published **fact set** changing").

**After** — `rectSignature` is retained **only** as diagnostic text in the
detail; it is never a pass condition. Two predicates, one per click, each
requiring a **fact** observed on a line published **after** the click's
`clickN` advanced:

- **Patient-open fact:** the most recent fact line with `clickN` > pre-click
  `clickN` **and** `clickPath !== preClickPath`. That is "the workspace view
  changed", read off the page. If measurement shows the patient row does not
  change `location.pathname`, that is a **finding reported to the coordinator**,
  not a licence to fall back to `rectSignature` — the fallback is exactly the
  weakness the diagnosis names (`diagnosis:192-199`).
- **Final proof:** the most recent fact line with `clickN` > pre-click `clickN`
  **and** `scriptText === 'true'`. Unchanged in substance from `:1066`, now also
  requiring the click to have been observed by the page.

Each click produces its own named assertion (`… row was clicked, the click
reached the page, and the workspace view changed`), and the two are **separate
rows** so a failure names which step failed. `scriptText` (the literal `<script>`
visible in the rendered body) remains the *final* `scriptText` proof for
`assertInjectedNoteInert`, and the patient-open fact is a **different** fact — the
proposal does not let the patient-open step borrow the final proof.

## E. Batched rectangle identity, corrected

**The defect** (`diagnosis:200-207`): the hook numbers rectangles per batch of 40
(`web/src/main.tsx:118-128`) while `readObservations` keys them by the index
*within* the batch (`scripts/v2/tauri-security.test.mjs:650-656`). Batches 0-4 all
write keys `i0..i39` and each later batch overwrites the earlier ones, so on a
page with more than 40 labels only the last 40 are readable, and a label that was
dropped is reported with the same wording as a real absence.

**After — two changes, no change to which rectangles are published.** AM-138
records the owner's decision that *P3.4's publication rule stays exactly as
written*, so the text-leaf rule, the 1–64 character bound and the cap of 200 are
all untouched; only the **key** changes, from index-within-batch to **global
index**, and the harness learns to validate it:

```js
// hook, readRects/sendRects: the global index is the identity, in one place.
const global = index * batchSize + at;                       // instead of `at`
query.set(`i${String(global)}_x`, String(rect.x));
query.set(`i${String(global)}_y`, String(rect.y));
query.set(`i${String(global)}_w`, String(rect.w));
query.set(`i${String(global)}_h`, String(rect.h));
query.set(`i${String(global)}_l`, rect.label);
```

```js
// harness, readObservations: keep the batch index and the declared total beside
// every rectangle, so a caller can refuse a mixed or partial frame.
const batch = Number(params.get('batch'));
const total = Number(params.get('rects'));
for (const [key, value] of params.entries()) {
  const rect = /^i(\d+)_(x|y|w|h|l)$/.exec(key);
  if (rect === null) continue;
  const entry = batches.get(batch) ?? { batch, total, rects: new Map() };
  entry.rects.set(Number(rect[1]), { ...(entry.rects.get(Number(rect[1])) ?? {}), [rect[2]]: value });
  batches.set(batch, entry);
}
```

**Completeness and freshness rule, and the rule is a `FAIL`, not a `NOT RUN`:**
`rectForLabel` returns a rectangle only when **all** of the following hold —
every batch index `0 .. ceil(total/40) − 1` is present, all of them declare the
**same** `total`, and no batch has arrived with a different `total` since (a
`total` change invalidates the frame and restarts the read). Otherwise it returns
`null` with a reason that distinguishes "incomplete frame: 3 of 5 batches" from
"no rectangle for the label" from "the page published a new total while we read".
**Stale or mixed frames are never selectable**, which is the trap the diagnosis
names for the next card. The read stays a live thunk (`stderrAt`,
`:613-623`) so the frame is the live buffer, not a snapshot.
