### A.2 What the conjunct is replaced with, and the exact evidence required

C-BRIDGE@1 rule 4 (`docs/v2/CONTRACTS.md:223-224`) has three conjuncts, all
about **authorisation and reachability**, none about the absence of a global:
`"capabilities": []`, `withGlobalTauri: false`, no custom `invoke_handler`
commands. The proposal keeps `withGlobalTauri: false` as the runtime proof
(`tauri === 'undefined'`, which the shipped binary already satisfies) and adds
the runtime fact that the always-present object is **not a live door**.

**Probe target — a real, known-existing, harmless built-in command:**
`plugin:event|listen`. Verified in the pinned source, not assumed:

| Claim | Local source |
| --- | --- |
| The `event` core plugin is registered in **every** app, unconditionally, by `register_core_plugins` | `tauri-2.12.1/src/app.rs:1260` |
| Its commands are `listen, unlisten, emit, emit_to` | `tauri-2.12.1/src/event/plugin.rs:68-75` |
| The shipped app registers only one extra plugin besides those core ones, and that one has **no commands at all** (no `#[command]`, no `invoke_handler`, no `permissions/`) | `src-tauri/src/main.rs:109-117`; `~/.cargo/registry/src/index.crates.io-*/tauri-plugin-single-instance-2.5.2/src` |
| Nothing in `src-tauri/` registers an event handler or capability that could allow it | `src-tauri/tauri.conf.json:14` `"capabilities": []`; V3's word loop passes |

`listen` is harmless in the sense that matters here: even if it were ever
reachable, it registers a listener and mutates no state, writes no file and sends
nothing. **The pass condition does not depend on that**, because pass requires a
**rejection carrying the ACL text** (§A.3), and a reachable-but-ill-argumented
`listen` would reject with a *serde/argument* error, not with the ACL string —
i.e. it would FAIL loudly rather than pass quietly.

**Why the ACL path is the one this command takes** (`tauri-2.12.1/src/webview/mod.rs:2076-2109`):

```
if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
   && request.cmd != crate::ipc::channel::FETCH_CHANNEL_DATA_COMMAND
   && invoke.acl.is_none()
```

`plugin:event|listen` sets `plugin_command` to `Some`, so the branch is taken
regardless of origin and regardless of whether the app has an ACL manifest, and
with `"capabilities": []` no capability resolves, so `invoke.acl.is_none()`. The
gate fires **before any argument is deserialised**, which is why a `null` payload
cannot turn into a serde error on this path.

The **release** build (the AppImage is `tauri build` →
`[profile.release]`, `src-tauri/Cargo.toml:32-38`, so `debug_assertions` is off)
rejects with, at `webview/mod.rs:2104-2107`:

```
Command plugin:event|listen not allowed by ACL
```

**This exact string is the evidence**, built from `request.cmd`, the **full**
command name. It is *distinguishable* from the two other rejections:

- the "no such handler" rejection, whose message is built from `command_name` —
  which `mod.rs:2068-2074` has already stripped of the `plugin:event|` prefix —
  so the only reachable string of that shape is **`Command listen not found`**
  (`mod.rs:2155-2167`), never the prefixed form;
- and the debug-only `resolve_access_message` prose
  (`src/ipc/authority.rs:403-409`), which a release AppImage does not take.

That discrimination is the whole point of requiring ACL-denial text instead of
accepting "any rejection": **a rejection proves nothing about *which* gate
stopped it**, and a rejection from a command that does not exist proves nothing
at all. The value reaches JavaScript as a plain string — `reject`
(`src/ipc/mod.rs:409`) serialises the `Err`, `format_callback` emits
`runCallback(<errorId>, "…")`, and `core.js:89` hands it to `reject` — so
`String(e)` in the hook is exactly that text.

**What (a) will not claim.** One denied command is **not** a proof that every
command is denied. The universal half of rule 4 stays where it has always been,
in the static checks: no `invoke_handler`, no `withGlobalTauri: true`, no
`src-tauri/capabilities/` directory — **V3's two IPC-relevant words
(`invoke_handler`, `withGlobalTauri": true`) and its `test ! -e`, all unchanged,
none removed, none relaxed. V3 does not read `app.security.capabilities`, and
this amendment adds no check there, so the static half is what it has always
been and no more is claimed for it; `"capabilities": []` is the state of the
shipped config and is not an asserted fact.** A config grep is **never** allowed
to stand in for the runtime fact (`docs/v2/cards/P3.4.md:241`, `:592`). If the
owner ever wants a check on `app.security.capabilities`, that is a **separate
decision on a separate card**, and it would be an addition — never a
substitution for the runtime fact in (a).

## C. Native ↔ CSS geometry and the click, measured rather than guessed

### C.1 What stays a hypothesis

`docs/v2/state/reviews/P3.4-diagnosis-2026-10-03.md:173-181` attributes the
failed click to a window-relative vs viewport-relative mismatch plus a CSD
titlebar displacement `oy ≈ 26-40 px`. **That stays an unmeasured hypothesis,
and this proposal adds nothing that could launder it into a fact.** Specifically:

- `innerWidth/innerHeight` and `outerWidth/outerHeight` **do not establish where
  the content origin is.** The difference between outer and inner is *some*
  chrome; it is not attributable to a titlebar rather than a border or a shadow,
  and under a WM-less Xvfb GTK's client-side decorations make that attribution
  worse, not better. They are published **as diagnostics and as a sanity bound
  only**, and the transform used for clicking is **solved from two observations**,
  never from them.
- **No titlebar height is guessed anywhere, and app decoration is not changed.**
  `show_main` keeps `.title("Apunta")` and no `.decorations(false)`
  (`src-tauri/src/main.rs:472-501`); `src-tauri/` is not in this proposal's
  permitted paths (§7).
- **The diagnosis's window-size arithmetic does not check out**, which is itself
  a reason to measure rather than to trust it. It states window `1216x817` at
  `(35, 91.5)`; from the code, display `1400x1000`
  (`-screen 0 1400x1000x24`, harness `:373-383`), `MARGIN = 0.95`
  (`main.rs:556`), `WANTED 1280x860` (`main.rs:72-73`), scale 1 ⇒ physical
  `min(1280, 1330) x min(860, 950) = 1280x860` at
  `((1400-1280)/2, (1000-860)/2) = (60, 70)` (`main.rs:569-575`). The diagnosis
  applied `MARGIN`
  **twice** — once to the wanted size and again inside the centring — which is
  where `1216`, `817`, `35` and `91.5` come from.
- **Precision, so no implementer conflates two numbers:** `1280x860` at `(60,70)`
  are the **requested inner size and requested position** the builder is given —
  `main.rs:478` calls `.inner_size(width, height)` and `main.rs:480` calls
  `.position(x, y)`, and those two arguments are the **variables** computed at
  `main.rs:569-575`, not the literals `1280.0, 860.0` and `60.0, 70.0` (reading
  the literals into that source is the mistake this sentence exists to stop).
  `xdotool getwindowgeometry --shell` reports the
  **outer** X geometry of the toplevel, which with GTK client-side decorations is
  the same width but **taller than 860** by whatever the titlebar occupies. The
  two must never be conflated, and **neither is what the click needs**: the
  content origin in native coordinates is `(ox − windowX, oy − windowY)`, solved
  from two observations and **derived**, never read off this paragraph.
- **The coordinate cause remains unmeasured.** The reviewer confirms the
  arithmetic above and the refusal to attribute the outer-minus-inner difference
  to a titlebar specifically; neither it nor this proposal measured the outer
  geometry, the decorations, or any titlebar height, and **no session is
  authorised here to open a display to find out.** Everything below is built so
  that its truth value does not matter to the method.

### C.2 The calibration: bootstrap, solve, validate, then one click

The method, in order, with **no click until a change has been measured**:

1. **Read the window in native coordinates.** `xdotool getwindowgeometry --shell
   <id>` → `X`, `Y`, `WIDTH`, `HEIGHT`. The existing parser at `:475-478`
   (`/^([A-Z_]+)=(.*)$/`) already reads all four and `windowInfo` (`:468-484`)
   throws `X`/`Y` away; it must return them. Non-integer `WIDTH`/`HEIGHT` is
   `NOT RUN` with that cause.
2. **Read the viewport in CSS pixels.** From a fact line: `vpW`, `vpH`, `dpr`,
   `scrX/Y/W/H`, `outerW/H`. Assert `vpW >= 400 && vpH >= 300`; otherwise the
   calibration is `NOT RUN` with that cause.
3. **Two fixed calibration targets, computed identically on both sides.** The
   harness derives them from the published viewport — never from a hardcoded
   pixel: `P1 = (round(vpW*0.50), round(vpH*0.50))`, `P2 = (round(vpW*0.75),
   round(vpH*0.60))`. Both are interior, both avoid the top edge (where a CSD
   titlebar would swallow the move), and they differ by `≈0.25*vpW ≥ 100` px in x
   and `≈0.10*vpH ≥ 30` px in y, which is what makes both axes solvable.
4. **Bootstrap (the only place an untransformed native point is asked for).**
   Move 1 places the pointer at `(windowX + cx₁, windowY + cy₁)` — the naive
   1:1 assumption, **stated as an assumption** and used only to obtain the first
   observation. If no `pointermove` arrives for it, the calibration is `NOT RUN`
   with the cause "the first bootstrap point produced no pointermove" and **no
   click is issued**. Move 2 places the pointer at `(X₁ + Δcx, Y₁ + Δcy)` where
   `Δcx = cx₂ − cx₁` and `Δcy = cy₂ − cy₁` — a **displacement**, which is
   transform-independent and needs no solved `k`. Both moves press nothing. Every
   other native point in this procedure is computed through the solved transform.
   *(Revision 1 said "in screen coordinates" without saying how `X`, `Y` are
   obtained, which made the step circular: computing them requires the transform
   step 5 is about to solve. A displacement is invariant under any affine map, so
   `k_x` and `k_y` fall out of the second observation even though `k` was unknown
   when the second point was asked for — this is the only sound two-point
   bootstrap.)* **Both bootstrap moves are containment-exempt from the `FAIL`
   rule of step 8, and each has exactly one named outcome, which is never a
   safety failure and never a pass:** move 1 is the naive 1:1 guess, cannot be
   checked before it is issued (the check needs the transform it exists to
   obtain), presses nothing, and produces the named `NOT RUN` "the first
   bootstrap point produced no pointermove" if nothing comes back; move 2 is
   **checked before it is warped** — if `(X₁ + Δcx, Y₁ + Δcy)` would fall outside
   the window rectangle, the calibration is `NOT RUN` with the cause "the second
   bootstrap displacement left the window rectangle" and **the move is not
   issued at all**, so no warp is ever sent outside the window; if it is inside
   and produces nothing, it is `NOT RUN` with the cause naming move 2. **No click
   is issued in any of these cases.** The exemption covers those two points and
   nothing else, and every later point is computed through the solved transform
   and checked, so no point outside the window can ever be warped or clicked.
5. **Move, without pressing anything.** For each target: record `ptrN` before,
   run `xdotool mousemove --sync <X> <Y>` in **screen** coordinates, then wait
   for a fact line whose `ptrN` is **strictly greater** and whose
   `ptrCX/ptrCY/ptrSX/ptrSY` are present. Read the pointer back with `xdotool
   getmouselocation --shell` and require `|X_read − X_asked| <= 1` and the same in
   y, so a silently-failed `XWarpPointer` becomes a **named** cause
   (`diagnosis:244-247`). **That wait is bounded, so no implementer picks the
   bound:** each freshness wait is capped at **10 s**, measured per move, and the
   cap is spent out of time the method already spends — **no timeout is widened**
   (the row's 45 s first-fact window and its 30 s click window keep their current
   lengths, and neither is lengthened to accommodate a wait), **the cap does not
   renew**, and a target's budget is per move and is never re-armed. A wait that
   expires is that step's named `NOT RUN` — "the page published no pointermove for
   calibration target N" (step 7's cause), carrying the `ptrN` count it *did* see
   — and **no click is issued**.
6. **Solve the transform, per axis, from the two observations:**
   `k_x = (sx2 − sx1) / (cx2 − cx1)`, `ox = sx1 − k_x * cx1`; likewise `k_y`, `oy`.
   Record `k` next to the published `dpr` **without equating them** — page zoom is
   exactly the case where they differ. The content origin in native coordinates
   is `(ox − windowX, oy − windowY)`, **derived**, and it lands in the evidence as
   a measured number rather than an assumption.
7. **The two-point fit is exact by construction and is therefore not a
   validation.** Two observations fix two unknowns per axis, so nothing is left
   over to disagree; "the `k` from the pair must agree with itself within `0.01`"
   and "re-deriving the origin from each observation must agree within 1 px" are
   identities, and a check that cannot fail is the exact family of defect AM-183
   records as having cost this card three attempts. **The out-of-sample test of the
   transform is step 9**, not this one. What is asserted here, in order, is only
   what can fail: `0 < k <= 4` per axis; and the click point's predicted native
   position lies **inside the window rectangle** read in step 1. A run that cannot
   produce two observations is `NOT RUN` with "the page published no pointermove
   for calibration target N", and **no click is issued**.
8. **Containment, before every move and after every read.** Before every
   `mousemove` other than the two step-4 bootstrap points, the point asked for
   must satisfy `windowX <= X < windowX + WIDTH`
   and `windowY <= Y < windowY + HEIGHT`; otherwise the step `FAIL`s **with the
   point and the window rectangle**, and **issues no move and no click**. After
   every `mousemove`, `moveTo` also returns `getmouselocation`'s **`WINDOW`** field
   ("the window id of the window directly underneath the mouse",
   `xdotool.1:286-300`); where it equals the app window id, or where
   `xdotool getwindowpid <at.WINDOW>` returns the same positive pid that
   `windowInfo` read for the app window, the check is satisfied. A missing,
   malformed or different pid fails with both window ids. The installed command
   is `getwindowpid`; `windowancestry` does not exist. This is the "the pointer
   is over the app" half of the loop closure, and it is what makes asking for an
   arbitrary synthetic position safe at all — without it a mis-solved `o` could
   put the pointer on the root window, on the splash, or over an unrelated
   application on the desktop-session fallback the harness takes when `xvfb-run`
   is absent (`:367-372`). **The rule starts at the first point computed through
   the solved transform — the step-9 click point — and the two step-4 bootstrap
   points are its only exemption, for the reason step 4 gives.** So the
   classification is unambiguous, with no case where the same point is both
   exempt and checked: a containment violation on the step-9 click point, on
   step 9's one re-warp, or on any step-5 repeat, is a **`FAIL`** carrying the
   point and the window rectangle, with **no move and no click issued**; a
   bootstrap move that would go out of bounds is caught **before** the warp and
   is the step-4 named **`NOT RUN`**, as is a bootstrap move that produces
   nothing, again with **no click issued**. Neither is ever reported as the
   other, and neither is ever reported as a pass.
9. **One click, in screen coordinates, on a re-read target.** Convert the
   rectangle's centre `T = (cx + floor(w/2), cy + floor(h/2))` to
   `(round(k_x*cx + ox), round(k_y*cy + oy))`, then: `xdotool mousemove --sync
   <X> <Y>` → read back and require the ≤1 px match → `xdotool click 1`. **The
   `--window` form is dropped on purpose**: it is window-relative
   (`xdotool.1`, "Coordinates 0,0 are at the top left of the window you choose"),
   which is the space whose ambiguity produced the failure; screen coordinates are
   the space `getmouselocation` reports, so the same instrument both sets and
   verifies them. **After the warp and the ±1 px read-back, wait 600 ms — two poll
   intervals — so the hover transition the warp itself caused has flushed**, and
   so a `pointermove` fact for the warp has had time to arrive. Then **re-read the
   target's rectangle from the live buffer** and recompute `T` from it; if the
   rectangle has moved, re-warp **once** (a move, not a click) and re-read once
   more. Then click. *(The wait and the re-read exist because hovering a patient
   row inserts a tooltip into the DOM — `web/src/components/PatientsColumn.tsx:1174-1184`
   `onMouseEnter` → `setTip({ id, rect })`, rendered at `:1425-1442` as an
   absolutely positioned `div.project-tip` at `left: rect.right + 20, top:
   rect.top`, which lands in the notes column at the patient's vertical band.
   `setTip(null)` is a React state update and is not guaranteed to have flushed
   before the press that follows the warp; if the pointer is still inside the
   tooltip, `elementFromPoint` returns a non-interactive `div` and the note never
   opens.)*
10. **Close the loop on the click itself, against a unique target.** Require
    `clickN` to have advanced by **exactly 1**, and require `|clickCX − T.x| <= 2
    && |clickCY − T.y| <= 2`. **The `clickN` wait carries the same 10 s per-move
    cap as step 5** — it is not a new budget and it does not renew — and a wait
    that expires is this step's **`FAIL`** naming the `clickN` count observed,
    never a pass and never a click retried. **The `clickEl` comparison rule is
    exact:** the harness compares `clickEl`'s `tagName`, its `data-testid` (empty when absent)
    and its trimmed `innerText` against the same three fields read from **the
    rectangle it selected** — which §B's `rectTag`/`rectTestId` publish. Equality
    on all three is the pass; any difference is the `FAIL`, naming both
    descriptors. `tagName` alone separates the two `John Smith` leaves in play —
    the row's `span.name` from the tooltip's `div.project-tip-name` — so **no
    "first match wins" rule is needed and none may be used:**
    **`rectForLabel` selecting among several same-labelled rectangles is
    forbidden.** If more than one live rectangle in the selected frame carries
    the label, the step
    `FAIL`s naming the count and the global indices, because the target in that
    frame is ambiguous. The loop closure of ±2 px in client space is the out-of-sample test
    of the transform from step 7. **The landing is still proved by a fact change
    (§D), never by the click succeeding.**
11. **Exactly one click per target.** No second attempt at a different point, no
    retry after a `FAIL`, no widening of the 30 s window (`diagnosis:259-261`;
    card stop conditions). If steps 7–10 cannot produce a measured, verified click,
    the row `FAIL`s with the numbers it does have.

**The largest remaining unknown, stated plainly rather than left to be discovered
as a `NOT RUN`:** synthetic key input reaching WebKitGTK under `xvfb-run` was
proven (attempt 3's `ctrl+r`), but that is `XSendEvent`. Whether an
`XWarpPointer`/`XTest` warp produces a `pointermove` in the page with no window
manager is **unmeasured** and is not measured by this proposal. §C.2 is built so
this cannot be laundered: if no `pointermove` arrives, steps 4/7 are `NOT RUN`
with a named cause and **no click is issued**. The same holds for the outer X
geometry and any CSD titlebar height (§C.1): unmeasured, and correctly kept out of
the method.

### C.3 The clicked command's exit status, stdout and stderr are all checked

Today `spawnAsync` (`:1215-1229`) resolves on `close` and returns **only**
`{ stdout, stderr }`; the exit code is discarded, and `clickAt` (`:722`)
collapses everything into `ok = !stdout.includes('XError')`, which
`clickAndWaitForChange` then ignores entirely (`:736-751`). Proposed, in the same
file only (no shell is involved anywhere — every invocation stays the array form
of `spawn`, so there is no `sh -c` and no shell change to review):

```js
// spawnAsync: resolve with the exit status too. No caller changes shape except
// the ones below, and no caller may treat a non-zero status as success.
child.on('close', (code, signal) => done({ code, signal, stdout, stderr }));
child.on('error', (error) => done({ code: null, signal: null, stdout: '', stderr: String(error) }));
```

```js
// clickAt: every dispatched command's exit status, stdout and stderr are read.
async function moveTo(x, y) {
  const result = await spawnAsync('xdotool', ['mousemove', '--sync', String(x), String(y)]);
  const read = await spawnAsync('xdotool', ['getmouselocation', '--shell']);
  // The same strict parser windowInfo already uses (:475-478): a line with no
  // '=' must not become a key. indexOf('=') would give line.slice(0, -1) for it.
  const at = Object.fromEntries(
    read.stdout
      .split('\n')
      .map((line) => line.trim())
      .map((line) => /^([A-Z_]+)=(.*)$/.exec(line))
      .filter((match) => match !== null)
      .map((match) => [match[1], match[2].trim()]),
  );
  return { x, y, result, at, read };   // at carries X, Y and WINDOW
}
```

`moveTo` returns the raw `code`, `signal`, `stdout` and `stderr` of **both**
commands plus the `WINDOW` id §C.2 step 8 needs; every consumer puts them in the
assertion detail on a failure, and **any non-zero `code` on either command, or an
`XError` in either stream, is an immediate `FAIL`** naming the command, the code
and the line — not a click that proceeds and is then judged by a page fact.
`clicked.ok` stops being discarded (`diagnosis:149-152`, remedy at
`diagnosis:248`). The five existing
`spawnAsync` call sites (`:470-472`, `:712`, `:839`) read only `.stdout`, so
adding `code`/`signal` breaks none of them.

## D. Landing proof — two facts, told apart, and no rectangle movement

**Before** (`:730-755`, `:1046-1068`): the predicate is `changed = after !==
before || fact !== null`, where `before`/`after` are `rectSignature` (a JSON of
every published rectangle) and the patient click passes `undefined` as its
predicate (`:1050`), so a rectangle-only change satisfies it. The card requires
the opposite (`docs/v2/cards/P3.4.md:542`: "A click that landed is proved by the
published **fact set** changing").

**After** — `rectSignature` is retained **only** as diagnostic text in the
detail; it is never a pass condition. Two predicates, one per click, each
requiring a **fact** observed on a line published **after** the click's `clickN`
advanced:

- **Patient-open fact:** a fact line with `clickN` > pre-click `clickN`
  **and** `href !== preClickHref`, read from the already-published `href` fact
  (`location.href`). **Not `location.pathname`:** this app's patient row navigates
  to `/?patient=<id>`, which leaves the path unchanged
  (`web/src/routes/Workspace.tsx:221-225`, `navigate(\`/?patient=${…}\`)`), so a
  pathname predicate is **unsatisfiable on the very behaviour it is meant to
  prove** — a permanent `FAIL` caused by the harness. `href` changes only on a
  navigation, and nothing in this app navigates on a timer, a clock or a layout
  shift; it is also stronger than `rectSignature`, because a scrollbar, an
  animation and a late layout shift all leave `href` alone.
- **Final proof:** the most recent fact line with `clickN` > pre-click `clickN`
  **and** `scriptText === 'true'`. Unchanged in substance from `:1066`, now also
  requiring the click to have been observed by the page.

Each click produces its own named assertion (`… row was clicked, the click
reached the page, and the workspace view changed`), and the two are **separate
rows** so a failure names which step failed. `scriptText` (the literal `<script>`
visible in the rendered body) remains the *final* `scriptText` proof for
`assertInjectedNoteInert`, and the patient-open fact is a **different** fact — the
patient-open step does not borrow the final proof.

## E. Batched rectangle identity, corrected

**The defect** (`diagnosis:200-207`): the hook numbers rectangles per batch of 40
(`web/src/main.tsx:200-214`, the numbering at `:205-211`) while
`readObservations` keys them by the index
*within* the batch (`scripts/v2/tauri-security.test.mjs:649-656`). Batches 0-4 all
write keys `i0..i39` and each later batch overwrites the earlier ones, so on a
page with more than 40 labels only the last 40 are readable, and a label that was
dropped is reported with the same wording as a real absence.

**After — three changes, and no change to which rectangles are published.** AM-138
records the owner's decision that *P3.4's publication rule stays exactly as
written*, so the text-leaf rule, the 1–64 character bound and the cap of 200 are
all untouched; what changes is the **key** (index-within-batch → **global
index**), one **frame identity** per publication, and the **validation** the
harness now does over both:

```js
// hook, readRects/sendRects: the global index is the identity, in one place.
const global = index * batchSize + at;                       // instead of `at`
query.set(`i${String(global)}_x`, String(rect.x));
query.set(`i${String(global)}_y`, String(rect.y));
query.set(`i${String(global)}_w`, String(rect.w));
query.set(`i${String(global)}_h`, String(rect.h));
query.set(`i${String(global)}_l`, rect.label);
query.set(`i${String(global)}_t`, rect.tagName);
query.set(`i${String(global)}_d`, rect.testId);   // data-testid, '' when absent
```

```js
// harness, readObservations: keep the batch index, the frame identity and the
// declared total beside every rectangle, so a caller can refuse a partial frame
// and can tell two publications of the same rectangle set apart.
const batch = Number(params.get('batch'));
const total = Number(params.get('rects'));
const frame = params.get('frame') ?? '';
for (const [key, value] of params.entries()) {
  const rect = /^i(\d+)_(x|y|w|h|l|t|d)$/.exec(key);
  if (rect === null) continue;
  const entry = batches.get(batch) ?? { batch, total, frame, rects: new Map() };
  entry.rects.set(Number(rect[1]), { ...(entry.rects.get(Number(rect[1])) ?? {}), [rect[2]]: value });
  batches.set(batch, entry);
}
```

**This snippet replaces the rectangle-key loop inside `readObservations` only.**
The function still returns `{ facts, rects, markerLines, last }` unchanged: `rects`
is the same `Map` keyed by the same **global** index, rebuilt from `batches` at
the end; `facts` is untouched; `markerLines` still counts **every** marker line
including the rectangle batches, which is what the two-arm cause in §A.3 reads.
`rectSignature` (diagnostic) and `rectForLabel` read that same map. Nothing in the
snippet adds, removes or renames a return value.

**Frame identity, because completeness alone cannot see a mixed frame.** The
batches arrive as **separate same-origin `fetch` requests** logged to separate
stderr lines, so a read taken mid-publication sees some batches from the new
frame and some still holding the previous frame's values — and `sendRects`
republishes **all** batches whenever the rectangle signature changes. With only
the `total` rule, a hover that inserts and removes a text leaf leaves `total`
unchanged, so such a mixture reads as complete: the exact defect this section
exists to remove, one level down (the old code read a partial frame as an
absence; without a frame identity the new code can read a *mixed* frame as
complete). So every batch of **one** publication carries one **frame identity**,
one value per `sendRects` call:

```js
// hook, sendRects: one frame identity per publication, the same on every batch.
let frameSeq = 0;
const sendRects = (rects: ReturnType<typeof readRects>): void => {
  frameSeq += 1;
  const frame = `f${String(frameSeq)}`;
  for (let index = 0; index * batchSize < rects.length; index += 1) {
```

That is one counter and one query parameter inside the **existing** batch loop of
the **existing** `sendRects`. The hook's one gate, one 250 ms change-only poll,
one marker path and P3.5's seam are all untouched — the frame identity lives
inside `sendRects` at `main.tsx:200-214`, and `poll()` at `:254-264` still calls
it on a signature change and by no other route.

**Completeness and freshness — a polled read, not a sampled one, and the rule is
a `FAIL`, not a `NOT RUN`.** A publication arrives as several stderr lines, so it
can be observed mid-arrival. `rectForLabel` is therefore called through the same
`waitForFact`-shaped
loop every other read in this harness uses, **within the click's own 30 s window**,
returning as soon as a **complete** frame is available — every batch index
`0 .. ceil(total/40) − 1` present, all declaring the **same** `total` **and the
same `frame`** (a `total` or `frame` change invalidates the frame and restarts the
read, exactly as a `total` change alone did). A frame still
incomplete when the window ends is a `FAIL` with
the reason "incomplete frame: 3 of 5 batches"; a `total` or `frame` that changed
mid-read says so. **Sampling once and reporting "no rectangle for the label" is
forbidden**
— that is the wrong diagnosis the diagnosis report identified, and today
`rectForLabel` is called once per click (`:1050`, `:1065`), which is exactly how a
partially-arrived frame would have read as an absence. The read stays a live thunk
(`stderrAt`, `:613-623`) so the frame is the live buffer, not a snapshot.

**What is claimed, and what is not.** Claimed: **a frame is complete only when
every batch of one publication is present and every one of them carries that
publication's `frame` and `total`; a mixture of two publications is not a frame
and is not selectable, and the read restarts exactly as a `total` change does.**
Not claimed, because nothing here makes it true: that a read can never observe a
frame *after* it was published and *before* the page changed again — the hook
publishes on change and does not retract, so the live buffer keeps older frames
and a "current" frame is not a decidable property. No sentence in this document
asserts that stale frames are unselectable; the enforceable statement is the one
above, and an implementer who wants a stronger guarantee needs a retraction
protocol the hook does not have (which would be a new mechanism, not a
correction, and is **not** sought here).
