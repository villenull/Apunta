## 1. Owner decisions — four items a contract cannot settle

Each is stated with what the existing contracts *do* pin, what they leave open,
the recommendation, and the alternative. Everything in §2 onward is a
correction and needs no judgement.

### 1.1 The browser flush transport, end to end (review D8)

**What is pinned.** C-BRIDGE@1 rule 3: "The web page talks only to the server
over HTTP." So the server→browser direction cannot be the `BroadcastChannel`
(`web/src/App.tsx:308` `postControl`, whose whole vocabulary today is
`apunta:takeover-request` and `apunta:primary-closed`) and cannot be Tauri IPC
(rule 4). The web half of the flush hook already exists and is not a channel at
all: `NoteView.tsx:339` publishes `window.__apuntaFlushBeforeRelease`, and
`App.tsx:299-307` already calls it across a window handoff. The card needs a
*server*→*browser* request, and a *browser*→*server* answer.

**What is open.** Which HTTP shape. Three candidates:

| Option | Shape | Cost |
| --- | --- | --- |
| **(a) Long-poll + report (recommended)** | `GET /api/app/quiesce/wait` held open by the primary window; the server answers it when a quiesce is requested; the window flushes and `POST`s `{"ok":…,"blockers":[…]}` to `/api/app/quiesce/report` | two routes, no new shared SSE event name, no new browser API, works unchanged in browser mode and under Playwright |
| (b) Server-sent events | a permanent per-window stream carrying a new `quiesce` event | a new event name in `shared/`, a second long-lived transport beside the existing fetch-stream one, and `web/src/api/sse.ts` is a `fetch` body reader, not an `EventSource` — so this is a new pattern, not an extension |
| (c) Browser polls a status route | the window polls every N ms | needs the same new route, plus a poll interval that is a new number, plus up to N ms of latency inside a 30 s budget |

**Recommendation: (a).** It is the only one that adds no new event name, no new
number, and no second transport, and it is the only one whose "no answer" case
is naturally expressible: the server waits for a report from every window that
registered, and a window that has not answered when the 30 s budget ends is a
blocker named `no_response` — never read as `ok`.

### 1.2 The client report vocabulary, and whether C-UPD@1 changes (review D5, D10)

**What is pinned.** C-UPD@1: "the web client flushes the editor and reports
`ok` or `conflict`", and `quiesce_result{ok, blockers[]}`. The eleven-job
registry it lists includes `recording`.

**What is open.** `recording` is browser-only: there is no route that records
audio — the microphone is in `web/src/lib/recorder.ts:239` and the audio is
posted to `/api/transcribe` — so there is no `begin('recording', …)` call site
to exist. Yet the contract also says the server waits for `recording` to drain.
And the client's `flush()` already has **three** outcomes, not two:
`NoteView.tsx:321-327` throws `note.unsavedConflict` for a stale write and
`note.unsavedError` for any other save failure.

- **Option A (recommended): amend one sentence of C-UPD@1** so the client
  reports a *status* plus a *blocker list* rather than a bare `ok`/`conflict`,
  and state that `recording` travels on that client channel rather than in the
  server registry. Proposed wording is in §3.2. The server registry keeps the
  ten kinds it can actually observe; the client's three blockers are `conflict`,
  `save_error` and `recording`.
- **Option B: change no contract at all**, and let the client report stay
  `ok | conflict`, folding a failed save into `conflict` and an active
  recording into… nothing. This is the defect the review found: V3 would pass
  for the wrong reason, and a recording would silently not block a quiesce.
  **Not recommended** — it is the one option that loses a guarantee the contract
  states in words.

**Recommendation: Option A**, and note what it costs: one sentence of
C-UPD@1. It makes the contract's own two statements consistent with each other
instead of widening the product.

### 1.3 Which card enforces the close policy natively (review D2)

**What is pinned.** C-UPD@1: "Window close uses the same check: close is
deferred while a save is in flight; an active recording asks for confirmation;
unsaved text is never discarded silently." The web half of that sentence is
**already implemented today** and needs no new mechanism:
`NoteView.tsx:347-354` flushes on `pagehide`/`visibilitychange`, and
`Capture.tsx:150-160` sets `unfinished` — which is true while

**What is open.** The *native* half. A Tauri window close request is
`src-tauri/**`, which **does not exist yet** at this base and is P3.3's May
edit; P5.4's May edit also lists `src-tauri/**`, and P5.4 already `Depends
P5.3`.

- **Option A (recommended): P5.3 owns the rule and the web half; P5.4 enforces
  it natively.** P5.3 states the three close rules normatively in Fixed
  decisions, adds the browser-side V-row that proves unsaved text survives a
  close attempt (§3.9), and names P5.4 in one line as the card that reads the
  same check from the same server route. No `src-tauri` in P5.3's May edit, no
  collision with P3.3 or P5.4, no new card.
- **Option B: P5.3 takes `src-tauri/**`.** Rejected: two live cards would hold
  the same directory, P3.3 has not created it, and the card is L1 — it has no
  Rust toolchain, no display, and no `tauri:*` script.
- **Option C: split the close policy into a new card.** Rejected: this proposal
  does not invent cards.

**Recommendation: Option A.**

### Fixed decisions

1. **The flush channel is two routes, and only HTTP.** `GET /api/app/quiesce/wait`
   is held open by each window that has an editor and answers
   `{"request":"flush"}` when a quiesce begins; the window then flushes through
   `window.__apuntaFlushBeforeRelease` (`NoteView.tsx:339`) — the same hook
   `App.tsx:299` already uses for a handoff — and `POST`s its report to
   `/api/app/quiesce/report`. There is no SSE event for this, no
   `BroadcastChannel` message (C-BRIDGE@1 rule 3: the page talks only to the
   server over HTTP), and no new browser API. A window with no editor answers
   `ok` immediately without holding a request open. **A window that has not
   answered when the budget ends is a blocker named `no_response` and is never
   read as `ok`.** A window that answers after the deadline is ignored, not
   applied.
2. **The registration rule, and the eleven sites.** A route is registered when
   it **writes** or **holds an open stream**; a read-only parse is not
   registered, because a cut parse loses time and no data. Each of the eleven
   `JobKind`s gets exactly one site:

   | Kind | Site | Note |
   | --- | --- | --- |
   | `draft` | `routes/draft.ts:90` | already wired by S2.1 |
   | `refine` | `routes/chat.ts:122` | already wired by S2.1 |
   | `transcription` | `routes/transcribe.ts:232`, `:170`, `:94` | `/api/transcribe`, `/dictation`, `/preview` |
   | `plan` | `routes/plans.ts:325` | `/plan/suggest`, the SSE route; `:109` creates a version from typed fields and is not a generation job |
   | `briefing` | `routes/prep.ts:54` | `/prep`, the SSE route; `/prep/save` (`:133`) is a write |
   | `brainstorm` | `routes/brainstorm.ts:134` | the SSE route |
   | `import` | `routes/import.ts:69`, `routes/halaxy.ts:49` | the two run/import routes; the previews are read-only parses |
   | `restore` | `routes/backup.ts:103` | the staging POST; the swap happens at the next start, so only the staging is in flight |
   | `backup` | `routes/backup.ts:60` | `POST /api/backup` |
   | `save` | `routes/notes.ts:77` | `PATCH /api/notes/:id`, the debounced edit |
   | `recording` | **no server site** | the microphone is in the browser; it travels on the client channel (FD 3) |

   Every `begin(kind, id)` is released in a `finally`, so a stream that ends in
   an error releases its registration. `settings.ts:92` reads `anyActive()` for
   C-LANG@1 rule 6 and keeps working unchanged; P5.3 does not weaken or widen
   that check.
3. **The client report has a status and a blocker list.** The body is
   `{"ok": boolean, "blockers": string[]}` where `blockers` is a subset of
   `conflict`, `save_error`, `recording`, and `ok: true` requires an empty list.
   The three map exactly onto the three outcomes `NoteView.flush()` already has:
   clean; `note.unsavedConflict` for `stale_write`/`conflict`; `note.unsavedError`
   for any other save failure. **This is the one sentence of C-UPD@1 this card
   amends** — see §1.2 Option A — and the server turns the report into
   `quiesce_result{ok, blockers[]}` unchanged in shape. A `recording` blocker
   comes from the browser and is never registered server-side, because there is
   no route that records audio. **The primary window is the only reporter**
   (one editable primary at a time, `App.tsx` Web Lock; a covered secondary
   window is inert and holds neither unsaved text nor a microphone).
4. **The 30 s drain has an exit condition and a clock seam.** `drainJobs` polls
   `active()` and returns when the registry is empty (**success**) or when
   **30 000 ms** have elapsed (**failure**, with the still-active kinds as
   blockers). It never returns `ok: true` on a timeout and never waits past the
   bound. The bound is exactly C-UPD@1's 30 s and is not tunable from outside
   the module; the seam is an options object in the house style of
   `BackupOptions.now?: Date` (`server/src/backup/archive.ts:82`) —
   `{ now?: () => number; sleep?: (ms: number) => Promise<void>; drainMs?: number }`
   — so a unit test drives the 30 s boundary in milliseconds without a
   30-second test. Production passes none of it, so the default is the contract's
   value. The shell's `quiesce{}` call **blocks** for the drain and then for the
   report, inside the same 30 s budget; it does not return early on an active
   job.
5. **Maintenance mode is left on every path.** A quiesce that fails — an active
   job at 30 s, a client `conflict`, a `save_error`, a `no_response` — returns
   `ok: false` **and puts the server back into normal service in a `finally`**,
   so the next request is not a 503 until restart. Re-entry is idempotent: a
   second `quiesce` while one is in flight joins the first and returns its
   result; it does not nest, and no state is left set. A quiesce that succeeds
   leaves maintenance **on**, because the next contract step (the snapshot) must
   not be able to write either.
6. **The close policy: the rules, the web half, and the native owner.** The
   three rules are normative here and are not reworded: close is deferred while
   a save is in flight; an active recording asks for confirmation; unsaved text
   is never discarded silently. The browser half is **already implemented** and
   this card verifies it (V6) rather than rebuilding it:
   `NoteView.tsx:347-354` (best-effort flush on `pagehide`/`visibilitychange`)
   and `Capture.tsx:150-160` (`unfinished` is true while `recording !== 'idle'`,
   and `onBeforeUnload` calls `preventDefault()`). The **native** close request
   is a Tauri window event, so it belongs to **P5.4**, which already holds
   `src-tauri/**` and already depends on this card; P5.4 reads the same check
   from the same route this card builds. This card does not create
   `src-tauri/**` and does not add a rule of its own.
7. **The contract this card needs is C-BRIDGE@1 rule 2 only** — the JSON-line
   vocabulary `quiesce{}` in and `quiesce_result{ok, blockers[]}` out, plus rule
   3's "the page talks only to the server over HTTP". Rules 4-7 are P3.4's and
   are **not** a dependency of this card. The bridge file is P3.3's; the one
   sentence of P3.3's stdin reader that this card's May edit adds is the
   `quiesce` case, and nothing else in that file changes.
8. **`maintenance` is a real API error code, and the body is a real
   `ApiErrorSchema`.** `maintenance` joins `ApiErrorCodeSchema` next to
   `language_change_blocked` and `backup_in_progress`, with a comment saying
   which contract sentence produces it. The 503 body is
   `{"error": "maintenance", "message": <rendered from `errors.maintenance`>}`,
   which is `ApiErrorSchema`, so `web/src/api/client.ts:66` parses it and every
   existing client error path keeps working — unlike the request guard's
   deliberately non-conforming `forbiddenBody`, which has no message to show.
   English: "Apunta is finishing something and cannot take new work right now.
   Wait a moment and try again." Spanish: "Apunta está terminando algo y no
   puede aceptar trabajo nuevo en este momento. Espera un momento e inténtalo de
   nuevo."
9. **Which requests are refused, and by which hook.** A second `onRequest` hook
   in `server/src/maintenance.ts`, registered in `app.ts` **immediately after**
   `registerRequestGuard` so C-REQ@1 still runs first. It refuses **503
   `maintenance`**: every request to `/api/*` whose method is not `GET` or
   `HEAD`; and every `GET`/`HEAD` to `/api/*` except the read routes listed in
   the same file — `GET /api/health` above all, so the shell's liveness and V4's
   idle case both keep working. The three quiesce routes are exempt, or the
   client could never report. A request that was already past the hook when
   maintenance began is **never cut** — it finishes, which is why V2's stream
   completes. The exemption list is a named constant with a comment per entry.
10. **One quiesce at a time, and the browser rows are serial.** A quiesce in
    flight is joined, not queued and not refused (FD 5). Maintenance mode is

### 3.2 D5, D10 — the client report, and the one contract sentence **[O] §1.2**

> **Quiescence.** The server enters maintenance mode: new jobs and writes get
> 503 `maintenance`; it waits up to 30 s for its registry of active jobs

## 4. Two things I found that the review did not

Both are small and both are in the text above; they are listed so the owner can
see them rather than discover them in review.

1. **The browser rows would have raced each other.** `e2e/playwright.config.ts:84`

   maintenance mode is server-global. Three cases each entering maintenance would

   `S2.11.md:184-186` forbids. `e2e/playwright.config.ts` stays unedited.

   sandbox run.** Under the review's own failure scenario the server stays 503

   has nothing to do with itself. FD 5's `finally` closes that, and V1 names the

## 5. Preserved constraints

**The 30-second drain is the contract's 30 seconds.** Not 30 s of polling
*after* something else, not a value a test can raise, not a value a caller can
pass. The seam exists so the boundary can be *tested* in milliseconds; the
production default is the contract's number, and the module is the only thing
that sets it.

**No assertion is weakened and no acceptance row is deleted.** V2 still expects
`ok:false` with blocker `refine` **and** the stream completing. V3 still expects
`ok:false` with `conflict` and text preserved — and is now *more* specific,
because it names both observation points instead of leaving "preserved" to the
reader. V4 still expects `ok:true` and a 503 `maintenance` on a new draft. V1
and V5 are unchanged in what they prove and stronger in how they are pinned. V6
is added, not substituted.

**Every close, save, conflict and recording guarantee survives.** Unsaved text is
still never discarded silently, now with a browser row that proves it. A save in
flight still defers a close. An active recording still asks before anything is
lost. A conflicting save still refuses the transition and still keeps the
therapist's text in the editor, and the stored note is still left alone. A
recording still blocks a quiesce — which is the one the card previously could not
express at all.

**Privacy and the hard rules are untouched.** Nothing here adds a host, a socket,
an outbound call, a CDN asset, a font, a telemetry path or an update check. The
two new browser-facing routes are loopback HTTP like every other route in the
app, guarded by the unchanged C-REQ@1 hook. No audio, no note text, no patient
name and no machine identifier crosses either new route: the long-poll carries a
flush instruction and the report carries three status words and a blocker list.
The Web Speech API stays absent (`Capture.tsx:43`). HS-1 through HS-10 all hold
as written, and the card's `Must not edit` list *narrows* — it now also protects
`src-tauri/**`, the request guard, the `JOB_KINDS` union and
`e2e/playwright.config.ts`, none of which the review said were at risk.

**HS-8 holds.** Every fixture the browser rows need is synthetic and none of them
names a patient: the streaming control is a long synthetic plan built in the spec,
the note is created through the API with a synthetic string, and the recording
is `e2e/fixtures/audio/dictation-10s.wav`, the file the repo already ships for
exactly this. No Spanish fixture is required by this card.

**HS-7 holds.** No scorer, guard, lock, test or threshold is loosened. Nothing
here lowers a bar: the 30 s bound is asserted, the "no test files" clause is
added, `0 skipped` is required, and a V-row that cannot pass is reported
`BLOCKED` rather than retired.

**The dependency graph stays acyclic.** P5.3 gains P3.3, which depends on P3.1
and P3.2; P5.4 already depends on P5.3 and P3.R. No cycle is created, and P5.3's
new route file cannot collide with P5.4's `app-update.ts`.
