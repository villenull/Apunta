   rules, not from the rule functions themselves.** Fixed decision 4 calls

   edit's Must-not-edit forbids touching the rule functions, the regexes at

   cannot both hold unless the dump reads a second, pinned copy. So each pattern
   is a real `RegExp`/string literal in a `PINNED_*` block, byte-identical to the
   one the rule uses, and
   `print-rules-shape: each pattern is the literal the rule function uses`
   asserts that byte-presence mechanically — so the copy cannot drift silently.
   Every dumped literal was also checked against `git show 9d92d7b:…` (16/16 and
   10/10 present; `NOTES.md`). If the coordinator prefers extraction to
   duplication, it is a mechanical follow-up and no row changes.
2. **`check-refine.mjs:223`'s inline `['scenarios.json','owner-progress.json']`
   is now the named constant `FIXTURE_FILES`.** Fixed decision 4 defines
   `fixtureFilter` as "the ordered list of fixture file names the filter
   accepts (`check-refine.mjs:223`)" and code `6` needs the same list enumerated
   up front; a second copy of that literal would be a claim the loop does not
   back. The change is behaviour-identical (same array, same iteration order) and
   the loop's body is untouched. It is one line of the fixture loop, which
   Must-not-edit names, so it is flagged here rather than buried.
   Symmetrically, `check-note-format.mjs`'s three-line fixture listing now reads
   the enumerated list — the same array, the same regex, the same sort, so
   `--expect-fixtures` counts fixtures the loop actually read (Fixed decision 5).

   and a repeated `--only` is `2`.** Fixed decision 1 lists "a repeated flag"
