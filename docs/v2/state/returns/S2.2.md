## What this attempt changed

Attempt 1's review found one behavioural defect and one documentation gap, both
in `shared/src/i18n/t.ts`, and said the repair was "a two-line change in
`t.ts:132-135` plus one `t.test.ts` case, after which the four rows need
re-running and nothing else in the card moves". That is what this attempt did,
in `shared/src/i18n/t.ts` and `shared/src/i18n/t.test.ts` only.

**Finding 1 — a counted parameter that is not a `number`, and a missing one,
threw in every build. Fixed.** `form()` read the counted parameter and threw
unless it was a `number`, which contradicted Fixed decision 7 twice over: a
`string` count is a legal argument (FD 2's `MessageParams` admits it, `tsc
--strict` accepts it, and both oracles FD 6 pins `notes.count` to — `noteCountLabel`
`format.ts:60` and `plural` `plural.ts:3` — stringify the count), and a count
`params` does not carry must answer with the **English** string outside a test
build rather than crash a render in the browser. Now:

- the counted parameter is coerced with `Number(value)` — the same coercion
  `format()`'s `number` branch already used — and `Intl.PluralRules` selects on
  the coerced number, so `{ count: '3' }` renders `3 notes` / `3 notas` and
  `{ count: '1000000' }` still takes es-MX's `many` and en's `other`;
- a value that will not coerce (`NaN`) is treated as the **missing-value case**,
  not as a category, so it takes FD 7's third path: the same throw in a test
  build as a missing `{name}`, and the English entry's `other` form with the
  hole left empty everywhere else;
- the English fallback drops that name from the bag (`without()`), because a
  value that will not coerce would otherwise reach
  `Intl.NumberFormat` and render as `NaN` inside the sentence. That was caught
  by the new test case, not by inspection, and is the one place the repair went
  a line beyond the review's sketch — it is still inside `t.ts` and still one
  answer to one question.

**Finding 2 — the doc block claimed test-build behaviour for a throw that
happened in every build. Fixed.** `t()`'s comment now names, in one numbered
place, the three runtime paths FD 7 fixes — a key in no catalogue (**throws in
every build**: there is no English string to return, which this return's
Unresolved item 4 has always said), a key the locale has not translated (test
build throws, otherwise English), and a value the chosen form needs and `params`
does not carry, counted parameter included (test build throws, otherwise the
English entry with the hole empty) — and says which of the two catalogue-defect
throws (a plural entry with no `kind: 'number'`, or with no `other`) are
unconditional and why no caller can reach them.

Two cases were added to `t.test.ts` for this, and **no existing case was changed,
weakened or removed** — the pre-existing test-build throw for
`t('notes.count', {}, 'en')` is still asserted, which is the strictness the
review asked to keep. Nothing was loosened in the other direction either: a
guard that was stricter than its contract became exactly the contract, which is
not an HS-7 loosening.
