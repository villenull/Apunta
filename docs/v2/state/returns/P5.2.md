## What was built

`prepareDatabaseForStart` (`server/src/db/safety.ts`) is the one exported
function, and `server/src/index.ts`'s entire edit is the call for it in the one
position C-OWN@1 rule 1 gives it — between `applyPendingRestore` and
`openDatabase`, with the `restored` local and the existing restore ordering
untouched, so the rollback at `index.ts:50-56` and the log at `:107-112` still
read the value `:33` recorded. In order:

1. `applyPendingRestore` — the sequence is correct on its own. `index.ts` also
   calls it and keeps its own result on purpose (it is what the rollback and the
   log read); the second call finds nothing pending because the first removed
   `pending-restore/`, which is readiness finding **F3**, now measured rather
   than argued: a no-op, no second `before-restore-*` copy, no throw.
2. No `apunta.db` → return immediately. No read-only open, no `safety/`, no
   snapshot, and retention never runs, so a first run cannot evict a real
   snapshot. `openDatabase`, called next, creates the database at the current
   level.
3. Inspect through **one read-only handle**, which also serves the copy. The
   version comes from a direct `SELECT` on `schema_migrations`; "no such table"
   is level 0. Above the highest shipped migration →
   `MigrationSafetyError(…, 'newer_schema')`, having written nothing.
4. Pending migrations → stage `staging/pre-migrate-<uuidv7()>/` at mode 700,
   copy with `snapshotDatabase` (C-SNAP@1's one primitive, not reimplemented),
   `PRAGMA integrity_check` the copy, move it to
   `safety/pre-migrate-<from>-<to>-<utc>.db` (`restore.ts`'s stamp convention,
   so it sorts lexically), delete only that staging folder. Any failure →
   `snapshot_failed`, the old schema untouched, the plain `Error`s from
   `snapshotDatabase` and `integrityCheck` wrapped rather than re-thrown.
5. Migrate all of it in **one** outer transaction, or `migration_failed` with
   everything rolled back and the snapshot kept. `locking_mode = EXCLUSIVE` is
   deliberately not taken here: C-OWN@1 rule 4 takes it after the schema is in
   place, which is `openDatabase`'s next act.
6. Only after a successful migration, keep the last three by **stamp** and
   delete older ones — files this module's own naming claims, and nothing else.

The three codes are the whole vocabulary, each the `code` property of a thrown
`MigrationSafetyError`, modelled on P5.1's `BackupError`. Every case asserts
`code`; no test greps a message. `shared/src/errors.ts` is untouched, and the
refusal reaches the existing bilingual boot-error page through the catch
`index.ts` already had — no file outside May edit was needed for that
(readiness **F1**).

## F5 and F6, settled with tests rather than assumptions

Both were unknown when the card was written and are now pinned in
`safety.test.ts`, from probes run first through the sandbox wrapper:

- **Read-only `VACUUM INTO` works** (F5) — including committed WAL content,
  with another writer attached, and on a database a crash left with an
  unrecovered `-wal`. So one read-only handle both inspects and copies, and
  nothing on the path to a snapshot can write to the practice's database.
- **`migrationLevel` cannot be used for the inspect** (F6) — with
  `schema_migrations` present its `CREATE TABLE IF NOT EXISTS` is a no-op, but
  with no table at all it is `SQLITE_READONLY`. Using it would have broken
  `newer_schema` detection on the path it exists for and made a level-0
  database refuse to start. Hence the direct `SELECT` with "no such table" as
  level 0.
