## Deviations

None that change behaviour. Five things a reviewer should look at, all recorded
in `docs/v2/evidence/P5.1/verification.md`:

1. **The route's 409 case is a spy, not a real wait.** Rule 3's 60 s is the
   contract's and a test may not shorten it (HS-7), so
   `server/src/routes/backup.test.ts` mocks `runBackupAsync` with a
   pass-through spy (`vi.fn(actual.runBackupAsync)` — every other case in the
   file still writes a real archive) and rejects once with
   `new BackupError('another backup is already running…', 'backup_in_progress')`.
   The case therefore tests the **mapping** (409, the `backup_in_progress`
   body, no archive, no `last_backup_at`), while the refusal itself is proved in
   `backup.test.ts` through the real `lockWaitMs` override. The first attempt
   used `vi.useFakeTimers()`; fastify's `inject` never settled under the fake
   clock and the leak hung the ten cases after it, so the spy replaced it. No
   production seam was added for this.
2. **The daily-path case asserts that it waits, not that it is refused.**
   `maybeRunDailyBackupAsync(db, config, now)` takes no options, so there is no
   way to hand it a short wait without a 60-second test. The case instead shows
   the coverage decision 2 asks for: the daily backup is still unresolved 50 ms
   into a 200 ms hold and completes when the hold is released.
3. **`withBackupLock` / `withBackupLockSync` are exported** from the backup
   module. A test has to be able to *be* the other backup, and the alternative
   is to start a real one and hope it is slow enough — timing, not evidence.
   The lock itself is unchanged production behaviour; only its handle is
   public.
4. **`snapshotDatabase` is one function with overloads, not two functions.**
   Both `VACUUM INTO` and the online backup are reachable from the single
   `snapshotDatabase` name (`snapshotDatabase(db, dest)` and
   `snapshotDatabase(db, dest, 'online-backup')`), because decision 4 keeps both
   entry points and `better-sqlite3`'s online backup is the only one of the two
   that can be awaited. The third overload
   `(db, dest, method: SnapshotMethod)` returns `string | Promise<string>` so a
   caller holding a `SnapshotMethod` in a variable still compiles. Rule 1's
   substance — one place that knows how to copy, and no copy path of its own in
   `archive.ts` — holds; `vacuumInto` and `backupInto` are kept as the backup's
   own vocabulary over it, as decision 4 requires.
5. **Two cases were rewritten after a mutation showed they were not
   tripwires.** The first `deletes only its own staging folder` passed even
   when the cleanup was widened to `rmSync(join(prepared.staging, '..', '..'))`
   — deleting the whole data directory also leaves no `<op>-<uuid>` folder
   behind. It now starts a second backup, leaves it mid-copy, runs a failing and
   then a successful backup to completion around it, and asserts the other
   run's folder survives each. Four mutations in total (rule 2's derivation, the
   over-broad cleanup, the missing lock, the unguarded legacy tidy-up) were each
   proved to fail the corresponding case, and every source file was restored
   byte for byte afterwards.

## Unresolved items

1. **The consistency risk was not reproduced end to end on the base commit**,
   and this card could not reproduce it: on `68f8786` the copy and the
   derivation are joined by no await, so within one process the interleaving
   cannot be constructed through the public API — which is why the card's
   Confidence field says so. The property is now structural (every derived
   representation comes from the read-only copy) rather than dependent on there
   being no interleaving point, and mutation 1 shows the new cases fail if that
   is undone. Recorded rather than papered over.
2. **P5.2 has two things to pick up that this card deliberately did not
   build.** `BackupOperation` is exported (`'backup' | 'pre-migrate'`) and
   `CreateBackupOptions.op` selects the staging folder's name, and
   `snapshotDatabase` is re-exported from `server/src/backup/index.ts` — but
   `op` is **not** threaded through `RunBackupOptions`, so a pre-migration
   snapshot taken through `runBackupAsync` would still stage under `backup-`.
   If P5.2 wants a full archive rather than a bare `.db` safety copy, that
   plumbing is one line in each of the two entry points. Nothing in C-SNAP@1 or
   C-UPD@1 requires it here, and adding it untested would have been worse.
3. **`errors.backup_in_progress` has no i18n catalogue key.**
   `shared/src/i18n/en.ts` carries `errors.language_unavailable` and says in so
   many words that "S2.5 owns the rest of the list"; `shared/src/i18n/**` is
   outside this card's May edit, so the key was not added. The code is raised
   with a plain English message from the server, exactly as
   `language_unavailable` was before its catalogue entry existed. S2.5 should
   know one more code is in the enum.
4. **The web client does not yet branch on the new code.**
   `web/src/components/BackupCard.tsx` is outside May edit, so a 409 still
   renders through whatever path it already uses for a failed backup. The
   server's body carries `error: "backup_in_progress"` for a client that wants
   to say "a backup is already running" rather than "the backup failed".
