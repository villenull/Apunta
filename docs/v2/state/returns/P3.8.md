### The one deviation, for the coordinator to rule on: the `else`

Removing the success `break` alone does not compile, and the compiler is right
about why. **The window-would-not-open path at the base is not in an `else`** —
it is straight-line code at `:299-304` that only the success `break` skipped
over. So a literal one-line removal routes every successful launch straight into
`show_error("the_window_would_not_open")`, `close_window`, `settled = true` and
`break`: the loop would still die at `ready`, the marker would still never
reach stderr, and V3 would still fail — with the original defect plus a painted
error window.

`cargo clippy -- -D warnings` caught it as `unused_assignments` at
`main.rs:297` ("this value is reassigned later and never used"), because with
the `break` gone the `settled = true` on the success path is overwritten by the
failure path's own assignment before anything reads it.

The `else` is what makes Fixed decision 1(i)'s own stated post-condition true —
"After `show_main` succeeds the `ready` arm **falls through to the next event
like every other arm**" — and Fixed decision 3 already describes `:301-304` as
the arm's separate "`:302` failure path". It is inside part (i)'s named region
(the `ready` arm's control flow), it adds no new arm, no flag, no painting
behaviour, and it leaves the `:305` `break` exactly where the card requires.
This is reported rather than assumed to be inside the grant, because Stop
condition 3 says a third part is the coordinator's call and not this attempt's.
**A reviewer should rule on it explicitly.** The two-line alternative — replacing
the success `break` with `continue` — is smaller still and needs no `else`; it was
not taken because Fixed decision 1 says *remove*, not *replace*.
