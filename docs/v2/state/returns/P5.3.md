## Deviations

Recorded in full in `docs/v2/evidence/P5.3/README.md`; the substance:

1. **V8 is blocked** (above). This is the only deviation that changes a row's
   outcome, and it is a scope blocker, not a pass.
2. **The report's identity rides the query string.** FD1 fixes the report body as
   `{quiesceId, ok, blockers}` and says `tabId` "rides the registration that the
   report is matched against". A body with no identity cannot be matched to a
   window, and the row's own case ("a report from a window that is not registered
   is refused") requires the match. So the report is sent as
   `POST /api/app/quiesce/report?tab=<tabId>` with FD8's body byte for byte. The
   query string is the only place the channel carries the identity, which is what
   FD1 says it is for.
3. **The drain always waits one interval before believing the registry is empty.**
   FD4's entry rule means a non-empty snapshot never reaches the drain, so a drain
   that decided on its first look could never reach the bound — and the bound is
   half of FD4. One poll interval (250 ms, module-internal) of patience is what
   makes "a job already past the refusal hook still gets to finish" true. It is
   the only addition to the rule and it is fail-closed.
4. **A window that registers *during* a quiesce is asked at once**, and a window
   that has already answered cleanly is not asked again. Both were forced by the
   reporter's own loop: it re-arms the moment it reports, so without this a
   quiesce would ask one window forever and a late window would never be asked.
   The "never asked" blocker is kept for a registration that has not been asked
   *yet* and for a retained record's undischarged obligation.
5. **The 409 on a refused report carries a hand-written English sentence**, not a
   catalogue key: this card is licensed exactly one key per catalogue
   (`errors.maintenance`), and the reporter ignores that body's words. The count
   is on `maintenance.refused()` and in a content-free log line.
6. **`shell-bridge.ts` takes the quiesce entry point by injection**, not by import.
   P3.3's own suite loads that file in a bare `node` process that resolves nothing,
   so a value import of `maintenance.ts` breaks a test this card may not edit. The
   route module installs `quiesceFromBridge` — the same function
   `POST /api/app/quiesce` calls — so it is still one function with two callers.
7. **V3's case opens its own browser context.** It deliberately provokes a real
   `409 stale_write` at the page, and Chromium logs every non-2xx resource load as
   a console error; the `consoleErrors` fixture watches the `page` fixture, not
   every window in the run. `save-integrity.spec.ts` opens its own context for the
   same class of case. Nothing is suppressed and no assertion is weakened: the
   conflict is the server's real answer to the page's real request.
8. **V6/V7 assert the refusal, and V6 asserts its control.** In this headless
   Chromium a *close* (`page.close({runBeforeUnload: true})`) is refused silently —
   no `dialog` event — while a *navigation* surfaces the dialog. The rows use a
   navigation, assert the dialog appeared and the URL did not change, and V6 pairs
   that with the control that a clean screen leaves without asking.
9. **V9's dirty disconnect is produced by losing the connection and then unloading

   intercept the unload's `keepalive` flush, `context.setOffline` does not close an

## Change 1 — AM-215: the window's last word

`POST /api/app/quiesce/close?tab=<tabId>` with `{"clean":boolean}`, sent on
`pagehide` as `navigator.sendBeacon` (a `Blob` typed `application/json`, so the
route reads a JSON body) with a `fetch`-keepalive fallback if the beacon is
refused. `clean` **discharges** that tab's record — a wait the closing window
still holds is released with it, so no request handler is left hanging, and a
quiesce in flight still counts that window as unanswered. `dirty`, an absent body,
an unknown tab and a send that never arrives all leave FD13's obligation in place,
and the route is exempt from the maintenance refusal hook because a window
closing *during* a successful quiesce is what releases browser-mode maintenance.

"Clean" is the window's own claim about two facts: no unpersisted text in the
editor, and no recording running. The first is published by `NoteView.tsx`'s
existing `beforeunload` guard — the only place that knows, since no draft of the
note text is stored anywhere in `web/src` — as one added line inside the one
handler this card already added. The second was already published by
`Capture.tsx`.

The refusal notice for a retained record is `errors.quiesce.no_response`, in both
catalogues, and it says what clears it: restarting Apunta.

**Transport choice, measured.** In headless Chromium `page.close()` fires
`pagehide` and the beacon reaches the server; `context.close()` does not deliver
it, and `page.route` cannot intercept it.

## Change 1 — Defect A: a claim is spent by the socket, not applied on its own

`closeWindow` no longer walks every record carrying a tab id. It now takes exactly
one of three paths: **two or more** records under that identity (Chromium's
*Duplicate Tab* really does copy `sessionStorage`) → it touches nothing, because a
clean claim cannot say which window it is about; **one record whose socket is
already gone** → discharged, as AM-215 decided; **one record still connected** →
the word is *banked* on it and nothing else happens — no wait released, no record
deleted. `disconnect()` spends a banked word (that is the ordinary clean close), and
`registerWindow()` drops one, because a registration is a new document arriving and
has said nothing.

**Why not the literal rule, which was implemented and measured first.** A rule that
only ever discharges an already-disconnected record makes AM-215 unreachable: the
e2e server log shows this engine delivering `POST /api/app/quiesce/close` **while
the tab's own wait is still open**, every time, so the socket close is always
observed second and the row's own `ok:true` came back `no_response`. What shipped
keeps the ruling's substance — a claim never acts on a connected record, never
releases a live wait, never deletes a live record, is ignored outright when two
windows share an identity, and cannot survive into the next document under the same
identity — and ends in the same place for either order of the two events, which is
what makes the word reliable rather than a race. One detail worth recording:
`release === null` is *not* the test for "gone", because a connected window holds no
wait between a quiesce asking it and the browser re-arming; `disconnectedAt` is.

Six V1 cases, by name (A): a claim on a connected record is remembered and the
window is still asked; a banked claim is spent at that window's own socket close;
a claim after the socket close discharges outright; a late beacon never touches a
reloaded tab's record; a banked word is dropped at the re-register; and a claim
under a duplicated identity acts on neither copy. Five mutations were measured
against them; the duplicated-identity guard is the one no assertion can
distinguish, and the evidence says why rather than claiming otherwise.

The client half is in the same commit's spirit: `onPageHide` aborts the poll before
sending the word, so the two events go out in the order the server prefers — not
relied upon, but not left to chance either.

## Change 2 — Defect B: `disconnect()` un-resolves

The review's reading is AM-215's own: an `ok` covers what the window held when it
said so, not what was typed after it, so `disconnect()` sets `resolved = false`.
One V1 case (`refuses a later quiesce after a window reported ok and then went

**What it forced in the e2e.** A record that leaves *cleanly* is now retained until
