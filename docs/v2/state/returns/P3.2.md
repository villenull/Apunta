## Deviations

None that change behaviour. Six things a reviewer should look at, all in
`docs/v2/evidence/P3.2/verification.md`:

1. **Rule 2's exclusive create is `link()`, not `open('wx')` + write — found
   by case 4, not by inspection.** With `open(path, 'wx')` followed by the
   write, the file exists and is *empty* between the two calls, and a second
   process reading it in that window sees something that is not a lock, decides
   the lock is stale and takes the folder over. Both processes then believe
   they own one practice's records: exactly the outcome C-OWN@1 exists to
   prevent. This is not theoretical — case 4 hit it on the first full-suite run
   under `npm test`'s 142 parallel files. The create is now a private
   temporary file `link()`ed into place: still `EEXIST` on an existing lock
   (so still an exclusive create, and rule 2's guarantee is unchanged), but it
   cannot expose an empty or partial name. There is an `open(wx)` fallback for
   filesystems with no hard links — a data folder on exFAT or some network
   volumes is a documented, supported setup (`data-at-rest-2026-08.md` §2.2) and
   `link()` fails there — and `readLockFile` re-reads a file that exists but
   does not parse, three times at 40 ms, before calling it garbage. That settle
   also covers the file a `SIGKILL` between create and write can leave behind,
   so a corrupt lock stays recoverable instead of bricking the folder. After the
   fix, case 4 passed 15 of 15 runs with all 8 cores saturated, and `npm test`
   passed three times in total.
2. **Case 4 is two processes, not two promises.** The card's exported surface is
   synchronous, so two in-process "concurrent" acquisitions are just two
   sequential calls — which is case 1. Case 4 therefore starts two real
   processes that import the real module (Node 24 strips the annotations, the
   same thing `sandbox.mjs` does for `shared/src/platform-paths.ts`; `dist/` is
   not an option because V1 builds `shared` only) and each racer **holds its
   lock until the other has reported**. That last part is the correction worth
   noting: the first version let a racer exit as soon as it had acquired, and
   then the loser's takeover was *correct* — the winner was gone, the lock was
   genuinely stale — so both processes reported success and the case was
   measuring the wrong thing.
3. **A lock file that is not one of ours is treated as stale, not as a live
   owner.** A file that does not parse, or that parses without a positive
   integer `pid` and a non-empty `nonce` and `processStart`, cannot be a live
   owner of this protocol, and refusing on it would leave Apunta permanently
   unable to start with no way out short of editing the folder by hand. A file
   that *is* one of ours is judged on the contract's terms only. There is no
   sixth case for this: the card fixed the list at five.
4. **The module cannot read its own start time ⇒ it refuses to start.** A
   plain `Error`, so it takes today's boot-error page path rather than exit 75,
   which is the honest classification: it is a genuine platform failure, not a
   second Apunta. It cannot happen on Linux with `/proc` or on macOS with `ps`.
   The alternative — writing a placeholder and carrying on — would produce
   exactly the "live owner's lock declared stale" failure the card's first Fixed
   decision warns about, so the lock is simply not taken.
5. **`release()` never throws.** It reads the file, unlinks only while the nonce
   still matches, and swallows every error: a lock that cannot be unlinked is
   taken over by rule 3 on the next start (the pid is dead by then), which is
   better than failing a shutdown. Only `ENOENT`-shaped outcomes are expected,
   but the hook runs on the signal path, where an exception would take
   `app.close()`'s promise down with it.
6. **A boot failure after the lock is acquired leaves the lock file behind**,
   and that is deliberate. The card's fourth Fixed decision puts the release in
   the `onClose` hook, and a process serving a boot-error page is still running
   and still owns the folder; on exit its pid is dead and rule 3 takes the lock
   over. Releasing there would have been a change the card does not ask for.

   pragma. On this box a write after the pragma makes a second process's
   `INSERT` fail with `SQLITE_BUSY` on 5 of 5 runs, while a read alone did not.
   C-OWN@1 rule 4 asks for the database to be *opened* with the pragma, which is
   what the code does; the backstop is fully effective from the app's first
   write, which is what case 5 drives. Recorded so nobody has to guess.
2. **Two residuals are inherited from rule 3 as the contract states it**, and
   neither is reachable by any of the five cases. (a) Two processes that both
   find the lock *garbage* can both rename over it and both read their own nonce

   escape hatch is the same as for a corrupt file: delete `apunta.lock` with the
   app closed.
