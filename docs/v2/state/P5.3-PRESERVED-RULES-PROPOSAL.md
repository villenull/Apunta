## 1. The one technical spine: controlled dependencies, not moved boundaries

Two seams and one test-only harness carry all the determinism. Neither seam is
reachable from production, and neither is keyed to the sandbox.

**1.1 The clock seam (V1, in-process).** `BuildAppOptions`
(`server/src/app.ts:34-61`) gains one optional field,
`maintenance?: { now?: () => number; sleep?: (ms: number) => Promise<void> }` —
the **same kind of seam, in the house style** as P5.2's optional injected clock
(`server/src/backup/archive.ts:82`). (The shapes differ on purpose and the claim
is only "the same seam, in the house style": `BackupOptions.now` is a `Date`,
because an archive wants a stamp, while the drain wants a monotonic reading and
a sleep it can advance.) **Production passes nothing.** `DRAIN_MS` is not
exported, not read from `process.env`, not in a request body, not in a query
string, and not writable from a route, so the bound is the contract's 30 s in
every mode. A unit test drives a *busy* registry past the bound in
milliseconds: the fake `sleep` advances a virtual clock and records the
requested total, and the assertions are "`ok:false` with the still-active kinds
as blockers", "the virtual elapsed time is exactly 30 000 ms", and "the drain
never returned `ok:true` on a timeout". This is a **deterministic busy
timeout**, and it needs no fake-mode change, no env knob and no 30-second test.

**1.2 The registry input, through the real registry.** The drain reads the same
module-level `active()` every other reader uses. The test begins a real
registration (`registry.begin('refine', id)`) and ends it in a `finally`
(`end` is documented idempotent, `registry.ts:57-62`), so the busy state under
test is the production one. No registry is injected and no registry seam is
added — the seam is the clock only.

**1.3 The shell-mode harness (browser rows), specified exactly.** Because the
trigger is shell-only (and must stay so), the browser rows need a server in
shell mode whose stdin the spec can write and whose stdout the spec can read.
That is obtained with **two new test-only files and no change to any product
file**. Every point below is stated because it is a way the first draft of this
section was unimplementable or unsafe; the review's F3, F13, F15, F16, F17, F18
and F19 are each answered here.

**The two paths are regular files, not a FIFO.** The earlier text said "a FIFO
and two control paths" and was wrong three ways: opening a FIFO for writing
blocks until a reader opens it, a FIFO has no line framing, and after the child
exits the next write takes `EPIPE`. Both control paths are **regular files**,
created mode `600`, whose `realpath` must stay under `/tmp/apunta-v2/`
(C-ISO@1 rule 1):

| Path | Computed by the spec as | Written by | Read by |
| --- | --- | --- | --- |
| `<runFolder>/quiesce/stdin.cmd` | `join(dirname(APUNTA_DATA_DIR), 'quiesce', 'stdin.cmd')` | the spec, one complete line per trigger, one write | the harness |
| `<runFolder>/quiesce/stdout.log` | `join(dirname(APUNTA_DATA_DIR), 'quiesce', 'stdout.log')` | the harness, appending the child's stdout as it arrives | the spec |

`APUNTA_DATA_DIR` is `<runFolder>/data` (C-ISO@1 rule 1), so the spec computes
both paths without asking anything and without printing an env var. A trigger is
written as exactly one complete line in exactly one write —
`fs.appendFileSync(stdinCmd, JSON.stringify({ quiesce: {} }) + '\n')` (`O_APPEND`,
one line, far below any atomicity limit). Never a partial line, never two lines
in one write, never `echo >>` on a FIFO.

**The harness's five refusals and checks, in this order.**

1. Refuse unless `APUNTA_V2 === '1'` **and** `APUNTA_TEST_RUN_ID` is set **and**
   `APUNTA_PORT` is an integer in 7800–7889 and is not 7717 and not 7890–7899 —
   the same three refusals `validatePort` makes (`scripts/v2/sandbox.mjs:61`),
   re-implemented as three lines in a test-only file rather than by importing
   the wrapper, which C-ISO@1 rule 4 keeps unedited.
2. Generate its **own** bridge nonce — `randomBytes(16).toString('hex')` — and
   pass it to the child as `APUNTA_SHELL_NONCE` with `APUNTA_SHELL=1`. A *fixed
   literal* nonce is a shared secret committed to a repository; the earlier
   claim that "the harness nonce is a fixed literal" is withdrawn. The nonce is
   never committed and is asserted only in the harness's own run record.
3. Read the child's stdout and accept **only** the first line that parses to
   `{type:'ready', nonce}` with `nonce` equal to the value *it* generated; any
   other line is ignored (C-BRIDGE@1 rule 1: the shell trusts only its own
   child's stdout and navigates only on its own nonce; P3.3 fixes the same
   treatment at `cards/P3.3.md:99-106`).
4. Poll `GET /api/health` for up to 30 s at 250 ms and require
   `testRunId === APUNTA_TEST_RUN_ID`, refusing on no answer, a wrong id or no
   id (C-ISO@1 rule 5, the same three refusals `waitForOwnership` makes,
   `sandbox.mjs:212-236`). `env --port` prints variables only (`:361`), so under
   these rows the harness is the only thing that can perform this check.
5. On any failure: stop **only its own child** (below), exit non-zero with the
   reason on stderr.

**Process ownership — the ladder, stated, because "kill only what you started"
is the rule that matters here.** The harness spawns the built server exactly as
`startServer` does: `spawn(process.execPath, ['server/dist/index.js'], { cwd:
repoRoot, env, detached: true, stdio: ['pipe', logFd, logFd] })`. Its **only**
signals are `process.kill(-child.pid, 'SIGTERM')` and then
`process.kill(-child.pid, 'SIGKILL')` after 5 s, guarded by the same exit-code
checks (`sandbox.mjs:254-280`). `SIGINT`/`SIGTERM`/`SIGHUP` delivered to the
harness are forwarded to that group and the harness then exits with the child's
code. **Never `pkill`, never a kill by port, name or pattern, never the Ollama
daemon, never any process the harness did not spawn** — Playwright's `webServer`
kills its own command at the end of the run, so without the explicit ladder the
natural implementations are the two forbidden ones. The harness also has a
`--selftest` mode, mirroring `sandbox.mjs selftest`, which asserts that its
cleanup signals exactly one pid and that its recorded signal list contains no
pattern kill.

**Forwarding.** The harness watches `stdin.cmd`'s size (`fs.watchFile` or a poll
at 50 ms), reads from its last offset to EOF, splits on `\n`, forwards **only
complete lines** to the child's stdin, and keeps the remainder for the next
pass. An empty or non-JSON line is logged and ignored and never fatal (the same
treatment C-BRIDGE@1 rule 2 gives an unknown inbound message type). It never
exits on the child's behalf.

**Reading the result.** The spec reads `stdout.log` and matches **only** lines
that `JSON.parse` to an object with `type === 'quiesce_result'`, and asserts
exactly one such line per trigger — because under `APUNTA_SHELL=1` the same
stream also carries pino log lines and P3.3's `ready` and `fatal` lines
(C-BRIDGE@1 rules 1, 2).

**`e2e/playwright.shell.config.ts`, stated exactly, because "sets no project
shape of its own" was false.** The base config ships **three** projects, the
second with `dependencies: ['es-MX-language']` and its own `baseURL` at
`port + 1` (`e2e/playwright.config.ts:98-114`, `:32`), and **two** `webServer`
entries (`:115-142`); keeping one project and replacing `webServer` *is* a
project and server shape. The shell config therefore overrides exactly:

```
projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'], appLocale: 'en' } }],
testMatch: /quiescence-shell\.spec\.ts$/,
webServer: [{ command: 'node e2e/support/shell-bridge-harness.mjs', cwd: repoRoot,
              url: `${baseURL}/api/health`, reuseExistingServer: false,
              stdout: 'pipe', stderr: 'pipe', timeout: 60_000, env: { …serverEnv } }],
retries: 0,
```

`reuseExistingServer: false` **unconditionally**, never
`!process.env['CI']`, because the harness owns the port and a stale Apunta on it
must never be attached to. `retries: 0` **in this config only** (the review's
recommendation): the base config's `retries: process.env['CI'] ? 2 : 0`,
`forbidOnly: Boolean(process.env['CI'])` and `workers: 1` (`:86-88`) are
inherited otherwise untouched, and V2–V4 are run locally with `CI` unset, so no
row is ever retried. No timeout, worker count or project shape beyond the three
lines above is set.

**What CI actually runs, stated so nobody reads more into it.** CI runs
`npm run e2e` (`.github/workflows/ci.yml:61`) under the **base** config only, and
that workflow is not in May edit, so **the shell rows are local evidence**. The
rows need a host `/usr/bin/chromium`, not `npx playwright install`. This is why
V7 exists: it is the row CI does run, over the whole suite, and it is where the
browser-mode half of the client channel (the reporter's dormancy, the 404s) is
seen.

**Failure modes with a stop response (three sentences, because two of them are
the ones that would otherwise be worked around).** An ownership or ready-line
failure → the harness stops its own child, exits non-zero with the reason, and
the row is **`BLOCKED`**, never `PASS` and never retried on another port. A
`fatal` line on the child's stdout or an exit 75 (`data_folder_in_use`,
`port_in_use` — P3.3's codes) → the harness surfaces the `fatal` line verbatim on
its own stderr and the row is `BLOCKED` carrying that code; it never retries the
port and never starts a second server. A malformed line on `stdin.cmd` → logged
and ignored; the row then fails on the **missing `quiesce_result`**, not on a
crash.

**Three failure modes have no stop response in the first draft and are named
here so they cannot be improvised around:** the build being stale (F13 — the
harness never builds; §2.7's V2–V4 each run `npm run build` first), the
playwright config never being built at all (V6), and `e2e/screenshots/workspace-1280x800.png`
being **tracked** (V7's `git checkout -- e2e/screenshots/`, copied from AM-103).

The two browser-visible facts this buys are exactly the two the rows need: the
trigger arrives the way it arrives in production (a `quiesce{}` line on the
shell's stdin) and the result is read the way the shell reads it (one
`quiesce_result{ok, blockers[]}` line on stdout). That is a **stronger** row than
an HTTP trigger: it exercises C-BRIDGE@1 rule 2 end to end.

Neither file is inside any existing card's May edit (`P3.3`'s list has no `e2e/`
path and no harness beyond its own `scripts/v2/tauri-lifecycle.test.mjs`), so
their inclusion is an owner decision — **OD-2/OD-3** — with the exact scope in
§3. If they are refused, V2–V4 are `BLOCKED` "no shell-mode harness", recorded,
never `PASS`, and no substitute is improvised at implementation time.

### 2.2 Objective

The server can enter maintenance mode safely: every long-running writer is
registered, new work is refused, active work drains — up to 30 s — the editor
flushes, and conflicts refuse the transition. **The shell starts the quiesce**
(`quiesce{}` on its stdin) and reads `quiesce_result{ok, blockers[]}` from the
server's stdout; window close uses the same rules. The rules and the browser half
are this card's; the native close request is **P5.4's** (§2.8). One narrow
exception to "new work is refused" is **proposed, not adopted**: the one editor
save a flush in flight asks for (OA-1, §2.6 FD4a, §3).

### 2.6 Fixed decisions

1. **The trigger is the shell's stdin line; the client channel is three
   shell-gated routes; there is no HTTP trigger.** `shell-bridge.ts`'s
   `quiesce{}` case calls the exported `beginQuiesce()` — one function, one
   caller, not a test-only switch — and writes `quiesce_result{ok, blockers[]}`
   on stdout in P3.3's existing shape (C-BRIDGE@1 rule 2). **No
   `POST /api/app/quiesce` route exists**, so no same-origin script in browser
   mode can put the app into maintenance and nothing about route authorization
   changes. The client channel, named with method, path, query and body:
   - `GET /api/app/quiesce/wait?windowId=<uuidv7>&recording=<0|1>&unsaved=<0|1>`
     — held open by **every** window from mount; answers `200
     {"request":"flush","quiesceId":"<uuidv7>"}` when a quiesce begins,
     otherwise stays open until the server resolves it. `recording` and `unsaved`
     are this window's published state, carried on the wait it re-arms; they are
     booleans about *this* window and carry no note text.
   - `POST /api/app/quiesce/report` — body
     `{"quiesceId":"<id>","windowId":"<id>","ok":boolean,"blockers":["conflict"|"save_error"|"recording"]}`.
   - `GET /api/app/quiesce/status` —
     `{"quiescing":bool,"activeJobs":[{"kind"}],"shortWrites":n,"windows":n,"maintenance":bool,"recording":bool,"unsaved":bool}`.
     Read by V2 to wait for a precondition, and by P5.4's native close handler
     (§2.8). `recording` and `unsaved` are the **any**-of over the windows
     registered for the in-flight quiesce (the falsy pair when none is), which is
     what makes FD9's three close rules readable from one route (F8); the
     "a save is in flight" half is already `activeJobs` containing `save`
     (FD7) together with `shortWrites > 0`.
   All three are registered **only when the server was started by the shell** and
   answer **404 in browser mode**, exactly as C-BRIDGE@1 rule 3 requires of the
   update endpoints (OD-1). The reporter is therefore **dormant in browser
   mode**: one 404 marks the channel unsupported and it never re-arms, so no
   browser-mode row polls and no interval number is introduced. There is no SSE
   event, no `BroadcastChannel` (rule 3: the page talks only to the server over
   HTTP) and no new browser API. A `quiesceId` (UUIDv7, the repository
   convention) is minted at entry; a `windowId` (UUIDv7) is minted **once per
   window** by the reporter, is stable for that window's life, and is what ties
   a report to a window across more than one request (FD3c). Neither id is a
   machine identifier, a patient id or a token; both are per-process and die
   with the window.
2. **One deadline of 30 000 ms from the instant the quiesce begins, two
   concurrent phases, and a drain that is the contract's drain.** `DRAIN_MS` is
   module-internal, **not exported**, not read from `process.env`, not in any
   request body, not settable by a caller or a route; production passes no seam
   and runs a real clock. The flush request is answered to every registered
   window **at entry**, the drain runs alongside it, each phase gets
   `deadline − elapsed`, and the two never extend the budget between them — a
   drain that would consume the whole bound must not leave the editor unasked,
   which is the hole the instruction review named. The **flush phase** is the
   window of that one deadline during which a registered window may present the
   save OA-1 admits; it opens at entry and **closes when every registered window
   has answered (reported) or the deadline passes, whichever comes first**, and
   the drain's exit is checked only after it closes. The drain's own exit:
   success when the registry is empty **and** the in-flight short-write counter
   is zero (FD4); `ok:false` with the still-active kinds as blockers when the
   bound is reached; **never** `ok:true` on a timeout and never a wait past the
   bound. The clock seam is the options object of §1.1, in the house style of
   P5.2's injected clock. The contract sentence "waits **up to** 30 s" is an
   upper bound and is honoured literally: a quiesce entered with a busy registry
   *waits*, it does not refuse.
3. **Registration, reporting, disconnect and transport lifecycle — seven named
   rules.** Registration is keyed to the **window**, never to one request: the
   first draft keyed it to a request the server itself answers at entry, which
   made every legitimate report a 409 and every quiesce `no_response`.
   - (a) **Registration is the held-open `GET /api/app/quiesce/wait`, and it
     survives being answered.** Every mounted window registers, including one
   with no editor; such a window holds the request open until it is asked, and
   once asked it answers `ok` immediately. **Answering a wait does not
   unregister the window** — the entry it made stays in the quiesce's map for
   the life of that quiesce. (The earlier draft's "without holding a request
   open" is deleted; it is exactly what makes a window invisible and turns "no
   editor" into "no window".)
   - (b) **Every window with an editor registers and reports**, primary or not.
     There is no "primary only" rule: the reporter mounts once per window at
     `main.tsx`, outside `App.tsx`'s primary logic, and cannot read
     `usePrimaryWindow` without editing `App.tsx`, which is Must-not-edit. A
     covered secondary is `inert` (`App.tsx:67-91`) and can hold neither unsaved
     text nor a microphone, so the stronger rule loses nothing.
   - (c) **A report is applied only when all four hold:** the body's
     `quiesceId` equals the in-flight quiesce's id; the body's `windowId` is in
     that quiesce's registered map; that window is not marked gone; and the
     quiesce has not already settled. Anything else — stale id, foreign id, an
     unregistered window, a window whose wait closed unanswered, a settled
     quiesce — is **refused 409** (body of FD6) and **never applied**. The map
     is keyed by `windowId` and its value is the `quiesceId` the window
     registered for, so a report of a *previous* quiesce can never satisfy this
     one even if the window is still open: without this, a timed-out quiesce's
     report satisfies the next one and the text it was protecting is lost with
     both rows green.
   - (d) **A wait socket that closes *unanswered* removes that window from the
     map** — that is, the server marks the window gone when `reply.raw` closes
     and the reply was never sent (an abort, a dropped socket, a navigation). A
     wait that closes because the server **answered** it is not a disconnect and
     changes nothing. **A replacement wait for the same `windowId` un-marks the
     window** — it is the re-arm the reporter does after reporting — so a
     re-armed window is registered for the quiesce it re-armed against. If the
     registered set is empty when the bound is reached, the result is `ok:false`
     with blocker `no_response`: a disconnect is never read as `ok`.
   - (e) **"No browser attached at all" is a named state, distinct from a
     disconnect** (the set empty since entry — a shell with no window loaded). It
     is also `ok:false` with `no_response`, never a silent success.
   - (f) **Transport lifecycle.** Exactly one long-poll per window, armed with an
     `AbortController`, aborted on unmount, on `pagehide`, after a report is sent,
     and when the server resolves it at the deadline; it re-arms immediately after
     each. It never reuses, wraps or aborts the SSE reader in
     `web/src/api/sse.ts`. It calls `window.__apuntaFlushBeforeRelease` **if it is
     a function** and reports `ok` when it is not (that hook is deleted by its own
     owner cleanup, `NoteView.tsx:357`), so a torn-down editor cannot make the
     reporter throw. Mounted once per window, never per route. Nothing kills it
     for it otherwise: `web/src/api/client.ts` applies no global timeout.
     **A window that has not answered when the budget ends is the blocker
     `no_response`, never `ok`; a report arriving after the deadline is refused
     under (c).**
   - (g) **How the reporter issues its two requests, pinned to the existing
     client module.** `web/src/api/client.ts` is Must-not-edit, so the choice is
     stated rather than discovered: the **`POST …/report` goes through the
     module's exported `requestJson`** with a small zod parser, so `toError`'s
     `ApiRequestSchema` parsing and the `AbortError` rethrow in `send` apply and
     a 409 surfaces as an `ApiRequestError` like every other server answer; the
     **held `GET …/wait` uses `requestStream`** (which returns the `Response`
     and already distinguishes a non-2xx from a body) or the module's own
     `fetch` with an `AbortSignal` — never a JSON helper, because a long-poll's
     answer is consumed by the reporter itself. Imports only; **no edit to
     `client.ts`**, no global timeout, no new fetch wrapper.

4. **Short writes: counted by a decidable predicate, released exactly once.**
   A patient rename, a format edit, a plan-version activation, `prep/save` or a
   settings write is **not** a registry job — `JOB_KINDS` is closed (FD7) — so
   the maintenance hook counts it. Two rules make the counter decidable and make
   it impossible for the drain to wait on its own observer:
   - **(a) The counted set is exactly the requests the refusal predicate would
     refuse**: `wouldRefuse(request)` is one pure function — under `/api/*`,
     method not `GET`/`HEAD`, or method `GET`/`HEAD` and the path not in the
     enumerated exempt set of FD5 — and it is evaluated **before** any admission,
     so admission changes only the outcome and never the counting. Therefore
     **the three quiesce routes and every exempt read are never counted**, the
     held long-poll cannot be counted, a status poll cannot be counted, and no
     content-type or streaming test is needed (at `onRequest` time there is none,
     which is why the earlier "a streaming request is never counted" is
     withdrawn). A streaming `POST` is a refusable write, so it **is** counted;
     it is also a registry job, and the drain waits on both — they release at the
     same moment, so the extra count changes nothing.
   - **(b) Release is exactly once across every terminal path.** The increment
     sets a per-request flag (`WeakSet<FastifyRequest>` or a symbol-keyed field)
     and **all** of `onResponse`, `onError`, `onRequestAbort` and
     `reply.raw.once('close')` call one `release(request)` that decrements only
     if the flag is still set, then clears it. Fastify is 5.12.1, where a client
     that aborts before the response completes does **not** produce `onResponse`;
     with only `onResponse` the count leaks and the next quiesce on that process
     ends `ok:false` forever — a leak, not a flake.
   - **(c) The drain waits for the counter to reach zero under the same bound**
     (FD2), after the flush phase has closed. This closes the race the card
     would otherwise have: a rename that started before maintenance and is still
     inside its SQLite write when the quiesce reports success, while the
     updater's snapshot copies the file. It adds no kind, widens no gate and is a
     counter in the module that already owns the refusal.

- **FD4a — OWNER AMENDMENT OA-1, the one admitted save (a save allowance;
     proposed, not adopted).** Without this rule the feature cannot succeed: the
     flush is `NoteView.flush()` → `enqueue` → `persist` → `updateNote`
     (`NoteView.tsx:294-330` → `:276` → `:223-273`), which is
     `PATCH /api/notes/:id` (`routes/notes.ts:76`), and FD5 refuses every
     non-`GET`/`HEAD`. The server would 503 the flush's own save, `persist`'s
     catch marks the save `error`, `flush` throws `note.unsavedError` (`:325`),
     FD6 maps that to `save_error`, and **every quiesce taken with unsaved text
     fails for a save the server itself just refused.** FD5's "a request already
     past the hook is never cut" does not cover it: that save starts *after*
     entry. The rule proposed:
   - **Admitted:** exactly one request shape — method `PATCH`, path matching
     `/api/notes/:id` and nothing else — presented while **all** of: a quiesce is
     in flight; the presenting `windowId` is registered for **that** quiesce
     (FD3c); the header `x-apunta-quiesce-id` equals **that** quiesce's id; and
     the **flush phase is open** (FD2). No other method, no other path, no other
     header value, no other quiesce, and never after the flush phase closes.
   - **Everything else is refused exactly as FD5 says.** In particular the header
     alone admits nothing: a request without a registered window, or with a
     stale id, or after the flush window, gets 503 `maintenance`.
   - **The admitted save is still inside the drain, twice over**: the route's own
     registry `save` kind at `routes/notes.ts:77` (FD7) and the short-write
     counter (FD4). So the snapshot boundary is exactly as safe as before; what
     changes is only *who may write during the flush phase*.
   - **The window is small and stated**: from entry until that quiesce's flush
     phase closes — in production, a few hundred milliseconds of a 30 s budget.
     Writes the therapist did **not** ask for are refused from the instant the
     quiesce begins, which is the property the earlier drafts' alternatives
     ("refuse only after the flush phase" / "exempt `PATCH /api/notes/:id` for
     the whole quiesce") gave up: those admit unrelated writes for up to 30 s,
     and the second also lets a note keep changing during the drain. This
     revision recommends the header-scoped rule over both.
   - **What it costs, honestly:** C-UPD@1's sentence "new jobs and writes get
     503 `maintenance`" is **no longer literally true for one request during one
     phase**, so that sentence is amended in the same AM-108 row (exact text in
     §3, OA-1). This is why it is labelled and not adopted here, and why this
     file does **not** claim the sentence survives unchanged.
5. **Which requests are refused, and by which hook — and the one admission.**
   A second `onRequest` hook in `server/src/maintenance.ts`, registered
   immediately after `registerRequestGuard` (`app.ts:75`), so C-REQ@1 still runs
   first. It refuses **503 `maintenance`** every request for which
   `wouldRefuse(request)` is true (FD4a): under `/api/*`, a method that is not
   `GET` or `HEAD`, and a `GET`/`HEAD` outside the **enumerated** exempt read set
   — a named constant with one commented entry per route, not a delegated rule:
   `GET/HEAD /api/health` (the shell's liveness), `GET /api/licenses`,
   `GET /api/settings`, the read routes for patients, patient groups, notes,
   formats, plan, prep, brainstorm, import batches and backup, and the three
   quiesce routes of FD1. All `GET` handlers in `server/src/routes/` were
   checked: none writes, so the exempt set is reads only and "new jobs and writes
   get 503" is honoured literally **except for the one admitted save of OA-1,
   which is the amendment §3 proposes**. A request **already past the hook** when
   maintenance began is **never cut** — it finishes, which is why V2's stream
   completes. The same predicate decides the counter, so the two can never
   disagree about what a request is.
6. **The client report has a status and a blocker list, and the refusal bodies
   are specified.** Body
   `{"quiesceId":…,"windowId":…,"ok":boolean,"blockers":[…]}` with
   `blockers ⊆ {conflict, save_error, recording}` and `ok:true` requiring an
   empty list. The three map onto the three outcomes `NoteView.flush()` already
   has (`:322`, `:325`): clean; `note.unsavedConflict` for `stale_write`/`conflict`;
   `note.unsavedError` for any other failure. This is **the report clause of
   C-UPD@1 this card amends** (OD-8). The server turns the report into
   `quiesce_result{ok, blockers[]}`, unchanged in shape. A `recording` blocker
   comes from the browser and is never registered server-side, because no route
   records audio. **The recording flag is not `useReportWork`**: the counter in
   `web/src/lib/i18n.tsx:100-155` is module-private with one reader
   (`useWorkInFlight()`), and `Capture.tsx:120` already reports a recording
   *through* it for the Language control; the reporter gets its own
   `setRecordingActive`/`isRecordingActive` pair instead. **The 409 body is
   `{"error":"conflict","message":<rendered from `errors.maintenance`>,
   "details":{"reason":"unknown_quiesce"}}`** — reusing the existing
   `conflict` member rather than adding a second `ApiErrorCodeSchema` entry,
   because `conflict` here is a *correlation* failure and never reaches the
   therapist's notice path (the reporter swallows it), while a new member would
   be a new code with no user-visible meaning. The 503 body is FD10's real
   `ApiErrorSchema`. **"Refused reports are counted" is withdrawn**: no status
   field exposed it and V1 asserted a number nothing showed; the only counter in
   the module is the short-write count of FD4, and it is asserted directly in
   `maintenance.test.ts`.
7. **The registry is job-shaped: eleven kinds, and every excluded write is named.**

#### 2.7.1 V1's named cases — paired success and failure for the four central blockers

Each of the four blockers the review called load-bearing has a **success** case
and a **failure** case, so none of them can pass for the wrong reason. All are
unit/integration cases driven through `app.inject()` or the reporter's own test,
with the FD2 clock seam where the 30 s bound is involved.

**Blocker A — the admitted save (OA-1, F1).**
*Success:* a registered window's flush-triggered `PATCH /api/notes/:id`, with
`x-apunta-quiesce-id` equal to the in-flight id, inside the flush phase, is
**served** (not 503), is counted by the short-write counter, appears as a `save`
in `activeJobs` while in flight, and the quiesce settles `ok:true` — the drain
waits for it. *Failure, three of them:* the same `PATCH` **without** the header
is refused 503 `error:"maintenance"`; with a **stale** `quiesceId` it is refused
503; and the same header-carrying `PATCH` issued **after the flush phase closed**
is refused 503. A fourth case asserts an **unregistered** window cannot use the
header to admit anything.

**Blocker B — window-keyed registration and correlation (F6).**
*Success:* a report whose `windowId` is registered for the in-flight
`quiesceId`, **even though its wait was already answered**, is applied — the
quiesce ends `ok:true` (or with the reported blocker), which is the case the
first draft turned into a 409. *Failure:* a report from a window that never
registered, a report carrying a previous quiesce's `quiesceId`, and a report
whose wait socket closed **unanswered** with no re-arm are each refused **409**
with the FD6 body `{"error":"conflict",…,"details":{"reason":"unknown_quiesce"}}`
and are never applied; the quiesce then ends `ok:false`, and the refusals do not
appear in `shortWrites` (the withdrawn "counted" assertion is not resurrected).

**Blocker C — the counter cannot count its own observer (F5).**
*Success:* while a `GET /api/app/quiesce/wait` is **held open** and while a
`GET /api/app/quiesce/status` is being polled repeatedly, `shortWrites` stays
**0** and the drain reaches zero and returns `ok:true` — the self-deadlock is
gone. *Failure:* a `PATCH` in flight holds the drain until its release and the
quiesce cannot settle `ok:true` before it; a request **aborted mid-flight**
(`onRequestAbort`) leaves the counter at 0; and two terminal hooks firing for one
request decrement **once**, asserted by the per-request flag.

**Blocker D — the status route carries all three close rules (F8).**

`status.recording` is `true`; with a window holding unsaved text,
`status.unsaved` is `true`; with a save in flight, `activeJobs` contains `save`.
The three facts P5.4's handler needs are therefore all present. *Failure:* with
no window registered, `recording` and `unsaved` are **false** (never `undefined`,

## 5. Preserved guarantees, checked

- **The drain is 30 s in production.** Not 30 s after something else, not a value
  a caller, a route, a query string, an environment variable or a test can raise.
  `DRAIN_MS` is module-internal and unexported; the seam exists so the boundary
  can be *proved* in milliseconds, and production passes none of it.
- **A busy registry is waited for, then refused by name.** The therapist sees the
  maintenance refusal for new work while the drain runs, and if the bound is
  reached the result names what was still running.
- **Recording still blocks a quiesce and still asks before anything is lost.**
  `Capture.tsx:150,157-165` is unchanged and verified by V6(b); the `recording`
  blocker travels on the client channel because no route records audio, and
  under OA-2 it is also readable from the status route so the shell's native
  close asks too.
- **A conflict still refuses the transition and still keeps the therapist's
  text.** V3 asserts both observation points; the stored note is still left alone
  by the conflict path.
- **Close still defers, asks, and never discards silently** — enforced on the
  screen where the text lives (OD-5), with the native verifier named in P5.4 and
  all three rules readable from one status route (OA-2).
- **Privacy is untouched.** No host, socket, outbound call, CDN asset, font,
  telemetry path or update check is added. The three routes are loopback HTTP
  behind the unchanged C-REQ@1 hook, shell-gated like the update endpoints. The
  long-poll carries a flush instruction, a `quiesceId`, a `windowId` and two
  booleans about one window; the report carries a `quiesceId`, a `windowId`, a
  boolean and up to three blocker words; the stdin line carries `{}`. No audio,
  note text, patient name or machine identifier crosses any of them. The Web
  Speech API stays absent (`Capture.tsx:43`).
- **HS-1…HS-10 hold.** No threshold, scorer, guard or lock is loosened and none is
  tightened by moving a boundary; HS-7 holds, HS-8 holds (every fixture is
  synthetic — the long plan is built in the spec, the note is created through the
  API, the recording is `e2e/fixtures/audio/dictation-10s.wav`, the file the repo
  already ships for exactly this; the harness's bridge nonce is **generated per
  run** with `randomBytes(16)`, asserted in the run record, and never committed);
  HS-9 stops stand for a file outside May edit; `Must not edit` genuinely narrows
  and now also protects `server/src/ai/fake.ts`, `web/src/api/sse.ts`,
  `web/src/api/client.ts`, `server/src/index.ts` beyond one entry,
  `server/dist/**`, `scripts/v2/sandbox.mjs` and `e2e/playwright.config.ts`.
- **The dependency graph stays acyclic.** P5.3 gains P3.3 (which depends on
  P3.1/P3.2); P5.4 already depends on P5.3 and P3.R; `shell-bridge.ts` keeps one
  writer; `app-quiesce.ts` cannot collide with P5.4's `app-update.ts`.
