## 1. The one technical spine: controlled dependencies, not moved boundaries

Two seams and one test-only harness carry all the determinism. Neither seam is
reachable from production, and neither is keyed to the sandbox.

**1.1 The clock seam (V1, in-process).** `BuildAppOptions`
(`server/src/app.ts:67`) gains one optional field,
`maintenance?: { now?: () => number; sleep?: (ms: number) => Promise<void> }` —
the shape of `BackupOptions.now` (`server/src/backup/archive.ts:82`), the
precedent P5.2 set in this same contract. **Production passes nothing.** `DRAIN_MS`
is not exported, not read from `process.env`, not in a request body, not in a
query string, and not writable from a route, so the bound is the contract's 30 s
in every mode. A unit test drives a *busy* registry past the bound in
milliseconds: the fake `sleep` advances a virtual clock and records the
requested total, and the assertions are "`ok:false` with the still-active kinds
as blockers", "the virtual elapsed time is exactly 30 000 ms", and "the drain
never returned `ok:true` on a timeout". This is a **deterministic busy timeout**,
and it needs no fake-mode change, no env knob and no 30-second test.

**1.2 The registry input, through the real registry.** The drain reads the same
module-level `active()` every other reader uses. The test begins a real
registration (`registry.begin('refine', id)`) and ends it in a `finally`
(`end` is documented idempotent, `registry.ts:49-52`), so the busy state under
test is the production one. No registry is injected and no registry seam is
added — the seam is the clock only.

**1.3 The shell-mode harness (browser rows), isolated.** Because the trigger is
shell-only (and must stay so), the browser rows need a server in shell mode
whose stdin the spec can write and whose stdout the spec can read. That is
obtained with **two new test-only files and no change to any product file**:

- `e2e/support/shell-bridge-harness.mjs` (new, Node, no dependencies, imported
  by nothing under `server/`, `web/`, `shared/` or `src-tauri/`): creates a FIFO
  and two control paths **inside the sandbox run folder**, spawns the built
  server with the sandbox's own environment plus `APUNTA_SHELL=1` and a fixed
  synthetic `APUNTA_SHELL_NONCE`, forwards each line appended to the command path
  into the child's stdin, appends the child's stdout to the output path, and
  exits with the child's code. It writes no product code and starts nothing else.
- `e2e/playwright.shell.config.ts` (new): imports `playwright.config.ts`,
  spreads it, restricts `testMatch` to `quiescence-shell.spec.ts`, keeps the
  English `chromium` project, drops the es-MX second server (this card's browser
  rows are English-only), and replaces `webServer` with the harness on the same
  port and data folder. It sets **no** timeout, no worker count and no project
  shape of its own.

The two browser-visible facts this buys are exactly the two the rows need: the
trigger arrives the way it arrives in production (a `quiesce{}` line on the
shell's stdin) and the result is read the way the shell reads it (one
`quiesce_result{ok, blockers[]}` line on stdout). That is a **stronger** row than
an HTTP trigger: it exercises C-BRIDGE@1 rule 2 end to end.

Neither file is inside any existing card's May edit (`P3.3`'s list has no `e2e/`
path and no harness beyond its own `scripts/v2/tauri-lifecycle.test.mjs`), so
their inclusion is an owner decision — **OD-2/OD-3** — with the exact scope in
§3. If they are refused, V2–V4 are `BLOCKED` "no shell-mode harness", recorded,
never `PASS`, and no substitute is improvised at implementation time.

### 2.6 Fixed decisions

1. **The trigger is the shell's stdin line; the client channel is three
   shell-gated routes; there is no HTTP trigger.** `shell-bridge.ts`'s
   `quiesce{}` case calls the exported `beginQuiesce()` — one function, one
   caller, not a test-only switch — and writes `quiesce_result{ok, blockers[]}`
   on stdout in P3.3's existing shape (C-BRIDGE@1 rule 2). **No
   `POST /api/app/quiesce` route exists**, so no same-origin script in browser
   mode can put the app into maintenance and nothing about route authorization
   changes. The client channel, named with method, path and body:
   - `GET /api/app/quiesce/wait` — held open by **every** window from mount;
     answers `200 {"request":"flush","quiesceId":"<uuidv7>"}` when a quiesce
     begins, otherwise stays open until the server resolves it.
   - `POST /api/app/quiesce/report` — body
     `{"quiesceId":"<id>","ok":boolean,"blockers":["conflict"|"save_error"|"recording"]}`.
   - `GET /api/app/quiesce/status` — `{"quiescing":bool,"activeJobs":[{"kind"}],
     "shortWrites":n,"windows":n,"maintenance":bool}`. Read by V2 to wait for a
     precondition, and by P5.4's native close handler (§2.7).
   All three are registered **only when the server was started by the shell** and
   answer **404 in browser mode**, exactly as C-BRIDGE@1 rule 3 requires of the
   update endpoints (OD-1). The reporter is therefore **dormant in browser
   mode**: one 404 marks the channel unsupported and it never re-arms, so no
   browser-mode row polls and no interval number is introduced. There is no SSE
   event, no `BroadcastChannel` (rule 3: the page talks only to the server over
   HTTP) and no new browser API. A `quiesceId` (UUIDv7, the repository
   convention) is minted at entry and is the **only** thing that ties a report to
   a quiesce.
2. **One deadline of 30 000 ms from the instant the quiesce begins, two
   concurrent phases, and a drain that is the contract's drain.** `DRAIN_MS` is
   module-internal, **not exported**, not read from `process.env`, not in any
   request body, not settable by a caller or a route; production passes no seam
   and runs a real clock. The flush request is answered to every registered
   window **at entry**, the drain runs alongside it, each phase gets
   `deadline − elapsed`, and the two never extend the budget between them — a
   drain that would consume the whole bound must not leave the editor unasked,
   which is the hole the instruction review named. The drain's own exit: success
   when the registry is empty **and** the in-flight short-write counter is zero
   (FD4); `ok:false` with the still-active kinds as blockers when the bound is
   reached; **never** `ok:true` on a timeout and never a wait past the bound. The
   clock seam is the options object of §1.1, in the house style of
   `BackupOptions.now`. The contract sentence "waits **up to** 30 s" is an upper
   bound and is honoured literally: a quiesce entered with a busy registry
   *waits*, it does not refuse.
3. **Registration, reporting, disconnect and transport lifecycle — six named
   rules.**
   - (a) **Registration is the held-open `GET /api/app/quiesce/wait`.** Every
     mounted window registers, including one with no editor; such a window holds
     the request open until it is asked and then answers `ok` immediately. (The
     earlier draft's "without holding a request open" is deleted — it is exactly
     what makes a window invisible and turns "no editor" into "no window".)
   - (b) **Every window with an editor registers and reports**, primary or not.
     There is no "primary only" rule: the reporter mounts once per window at
     `main.tsx`, outside `App.tsx`'s primary logic, and cannot read
     `usePrimaryWindow` without editing `App.tsx`, which is Must-not-edit. A
     covered secondary is `inert` (`App.tsx:67-91`) and can hold neither unsaved
     text nor a microphone, so the stronger rule loses nothing.
   - (c) **A report is applied only when its `quiesceId` equals the in-flight
     quiesce's id *and* that window holds a registered wait in the current
     quiesce.** Anything else — stale id, foreign id, unregistered window, a
     quiesce that already settled — is **refused with 409, counted, never
     applied**. Without this, the report of a timed-out quiesce satisfies the
     next one and the text it was protecting is lost with both rows green.
   - (d) **A closed socket removes that window's wait.** If the registered set is
     empty when the bound is reached, the result is `ok:false` with blocker
     `no_response`: a disconnect is never read as `ok`.
   - (e) **"No browser attached at all" is a named state, distinct from a
     disconnect** (the set empty since entry — a shell with no window loaded). It
     is also `ok:false` with `no_response`, never a silent success.
   - (f) **Transport lifecycle.** Exactly one long-poll per window, armed with an
     `AbortController`, aborted on unmount, on `pagehide`, after a report is sent,
     and when the server resolves it at the deadline; it re-arms immediately after
     each. It never reuses, wraps or aborts the SSE reader in
     `web/src/api/sse.ts`. It calls `window.__apuntaFlushBeforeRelease` **if it is
     a function** and reports `ok` when it is not (that hook is deleted by its own
     owner cleanup, `NoteView.tsx:356`), so a torn-down editor cannot make the
     reporter throw. Mounted once per window, never per route. Nothing kills it
     for it otherwise: `web/src/api/client.ts:55-58` applies no global timeout.
     **A window that has not answered when the budget ends is the blocker
     `no_response`, never `ok`; a report arriving after the deadline is refused
     under (c).**
4. **Short writes: refused like every other write, and counted while in flight.**
   A patient rename, a format edit, a plan-version activation, `prep/save` or a
   settings write is **not** a registry job — `JOB_KINDS` is closed (FD7) — so
   the maintenance hook counts it: the counter is incremented for every request
   that **passes** the hook and decremented in a second `onResponse` hook of the
   same module, at most once per request, and a streaming request is never
   counted. The drain waits for the counter to reach zero under the same bound
   (FD2). This closes the race the card would otherwise have: a rename that
   started before maintenance and is still inside its SQLite write when the
   quiesce reports success, while the updater's snapshot copies the file. It
   adds no kind, widens no gate and is a counter in the module that already owns
   the refusal.
5. **Which requests are refused, and by which hook.** A second `onRequest` hook in
   `server/src/maintenance.ts`, registered immediately after
   `registerRequestGuard` (`app.ts:75`), so C-REQ@1 still runs first. It refuses
   **503 `maintenance`**: every request under `/api/*` whose method is not `GET`
   or `HEAD`, and every `GET`/`HEAD` outside the **enumerated** exempt read set —
   a named constant with one commented entry per route, not a delegated rule:
   `GET/HEAD /api/health` (the shell's liveness), `GET /api/licenses`,
   `GET /api/settings`, the read routes for patients, patient groups, notes,
   formats, plan, prep, brainstorm, import batches and backup, and the three
   quiesce routes of FD1. All `GET` handlers in `server/src/routes/` were
   checked: none writes, so the exempt set is reads only and "new jobs and writes
   get 503" is honoured literally. A request **already past the hook** when
   maintenance began is **never cut** — it finishes, which is why V2's stream
   completes.
6. **The client report has a status and a blocker list.** Body
   `{"quiesceId":…,"ok":boolean,"blockers":[…]}` with
   `blockers ⊆ {conflict, save_error, recording}` and `ok:true` requiring an
   empty list. The three map onto the three outcomes `NoteView.flush()` already
   has (`:321-327`): clean; `note.unsavedConflict` for `stale_write`/`conflict`;

## 5. Preserved guarantees, checked

- **The drain is 30 s in production.** Not 30 s after something else, not a value
  a caller, a route, a query string, an environment variable or a test can raise.
  `DRAIN_MS` is module-internal and unexported; the seam exists so the boundary
  can be *proved* in milliseconds, and production passes none of it.
- **A busy registry is waited for, then refused by name.** The therapist sees the
  maintenance refusal for new work while the drain runs, and if the bound is
  reached the result names what was still running.
- **Recording still blocks a quiesce and still asks before anything is lost.**
  `Capture.tsx:150,157-165` is unchanged and verified by V6(b); the `recording`
  blocker travels on the client channel because no route records audio.
- **A conflict still refuses the transition and still keeps the therapist's
  text.** V3 asserts both observation points; the stored note is still left alone
  by the conflict path.
- **Close still defers, asks, and never discards silently** — enforced on the
  screen where the text lives (OD-5), with the native verifier named in P5.4.
- **Privacy is untouched.** No host, socket, outbound call, CDN asset, font,
  telemetry path or update check is added. The three routes are loopback HTTP
  behind the unchanged C-REQ@1 hook, shell-gated like the update endpoints. The
  long-poll carries a flush instruction and a `quiesceId`; the report carries a
  `quiesceId`, a boolean and up to three blocker words; the stdin line carries
  `{}`. No audio, note text, patient name or machine identifier crosses any of
  them. The Web Speech API stays absent (`Capture.tsx:43`).
- **HS-1…HS-10 hold.** No threshold, scorer, guard or lock is loosened and none is
  tightened by moving a boundary; HS-7 holds, HS-8 holds (every fixture is
  synthetic — the long plan is built in the spec, the note is created through the
  API, the recording is `e2e/fixtures/audio/dictation-10s.wav`, the file the repo
  already ships for exactly this, the harness nonce is a fixed literal);
  HS-9 stops stand for a file outside May edit; `Must not edit` genuinely narrows
  and now also protects `server/src/ai/fake.ts`, `web/src/api/sse.ts`,
  `server/src/index.ts` beyond one entry, `scripts/v2/sandbox.mjs` and
  `e2e/playwright.config.ts`.
- **The dependency graph stays acyclic.** P5.3 gains P3.3 (which depends on
  P3.1/P3.2); P5.4 already depends on P5.3 and P3.R; `shell-bridge.ts` keeps one
  writer; `app-quiesce.ts` cannot collide with P5.4's `app-update.ts`.

## 6. True unknowns, not resolved by convenience

1. **P3.3's readiness.** `server/src/shell-bridge.ts` does not exist, `APUNTA_SHELL`
   exists only in card text, and P3.3 is itself `BLOCKED` on the A03 owner action.
   With the shell-only trigger preserved, P5.3 inherits that wait honestly. It is
   the cost of not widening authorization, and the owner should see it before
   approving, not at dispatch.
2. **Whether the owner accepts V2's moved cell (OD-4).** The guarantee is
   unchanged and the coverage is wider, but the *row* that carries the busy-timeout
   assertion is now V1, not V2. A reviewer who wants it in a browser must accept a
   fake-mode timing change or a timeout inflation, and this proposal does neither.
3. **Ports are placeholders until the coordinator assigns them.** `<p1>`…`<p5>`
   are recommended as 7847, 7848, 7849, 7850 and 7843 (with 7844 free for es-MX),
   chosen to avoid every port recorded in `state/cards/*.json` (7807, 7826, 7834,
   7836, 7845, 7852, 7861) and every port the unapproved v2 draft had reserved.
   Re-confirm against the inventory at dispatch; an unassigned port is a `BLOCKED`
   stop, never a default.
4. **The shell harness is a new surface.** It is two files that spawn the built
   server with a synthetic nonce inside the sandbox run folder. The protection
   against it becoming a product dependency is V1's import assertion plus
   `Must not edit`; if the owner would rather not carry a second config at all,
   the honest outcome is V2–V4 `BLOCKED` and a card that ships V1, V5, V6 and V7
   only — with the browser half of the client channel unproven.
