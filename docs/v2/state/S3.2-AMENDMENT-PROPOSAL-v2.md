## Choice 2 — How a control proves anything (closes D-4, D-5)

Revision 1 made the negation lexicon authoring-only and left the control scored
on model output. As written that leaves the negative control with no mechanism:
`--blind-lexicon negation` empties a lookup nothing reads, so V3 cannot fail on a
correct implementation and V2's "all controls behave as specified" has nothing to
behave. Both halves are load-bearing for C-EVAL@1 §3.

## 2A (Recommended). Sidecar-referenced lexicon + bounded injected `controlNote`.

- A fixture or control sidecar may name a lexicon: `lexicon: "negation"`. The
  loader expands the named lexicon into one escaped whole-token pattern per term
  at load time and the scorer applies it with the existing
  `compile()`/`collapse()` machinery (`patterns.ts:58-70`). `score.ts` never
  reads the lexicon file directly, never knows a "negation check" exists, and
  never imports a guard module. The judgement stays per fixture: the sidecar says
  which direction is the error, the lexicon supplies vocabulary. A3's "no general
  lost-negation check" is preserved.
- Which sidecars may name it: **only the new controls sidecars this card
  authors.** `e2e/fixtures/eval-es/tuning/**` and
  `e2e/fixtures/eval-owner-es/tuning/**` are Must-not-edit and S3.1's gold stays
  byte-identical; a test asserts those two files are unchanged at the base
  commit's hash. Corpus negation detection therefore stays exactly as it is today
  — the per-fixture `mustNotContain` / `mustCapture` regexes — and nothing about
  the Spanish corpora's scoring changes.
- A control carries its own text: `controlNote`, bounded (≤ 4 000 characters),
  scored by the **same** scoring function as a corpus note, with only the
  provenance of the text differing. Controls are scored on injected text, never
  on provider output; corpus fixtures are scored on provider or pipeline output
  and no corpus sidecar gains a `controlNote` key. The fake provider is
  untouched, which is what makes V2 and V3 hermetic and deterministic.
- Coverage: **one positive control per C-EVAL@1 §4 critical class** (lost
  negation, invented negation, wrong dose or number, wrong experiencer, past risk
  reported as current or the reverse, retracted content kept, content invented for
  an uncovered section — the seven map one-to-one onto the Spanish trap-type
  directories `lost-negation/`, `invented-negation/`, `dose-and-number/`,
  `experiencer/`, `past-vs-current-risk/`, `spoken-correction/` and
  `section-never-covered/`), **plus a clean, an empty and a degenerate control**,
  per locale: 10 per locale, 20 in total, and no more without a card amendment.
- Cost: a required key in the controls' own type, a loader expansion, and a
  scoring entry point. No threshold, no contract rule, no `fake.ts` edit.

**FD1 — New flags, and what "unchanged" means.**

`provider`), `--blind-lexicon <negation|clinical|number|unit|medication|all>`

`expectations.json`, is exit 2 with a named reason, matching FD1's flag
discipline.
`--blind-lexicon` is a **test-only negative control**: it empties that lexicon
for the run and changes nothing else. It is not a scoring option, not a
threshold, and not something any acceptance run passes.
Provider mode with no new flag behaves exactly as it does at the base commit:
same prompts, same corpus handling, same report. A test asserts that
`runEval({models, runs, fake}, no locale)` and the same call with
`locale: 'en'` produce identical reports.

**FD2 — Where the Spanish lexicons come from, and how they load.**
Number words, units and medications: `docs/research/es-mx-clinical-glossary.json`,
filtered to `category ∈ {number, unit, medication}` — 51 + 8 + 93 = 152 entries,

Negation: the rule in §B-negation below. It is the one lexicon with no entry in

**FD2b — The negation lexicon is a scoring input, reached through the sidecar.**
A fixture or control sidecar may carry `lexicon: "negation"`. The loader expands
the named lexicon into one escaped, whole-token pattern per term at load time,
and the scorer applies those patterns with the same `compile()` / `collapse()`
machinery the sidecar's own patterns use (`patterns.ts:58-70`). `score.ts` never
reads a lexicon file directly and never contains a negation rule; the sidecar
decides the direction of the error (`mustNotContain` for a lost negation,
`mustCapture` for an invented one) and the lexicon supplies the vocabulary. This
is what "a lexicon" means here: **vocabulary, consumed per fixture, never a
general lost-negation detector and never a threshold.** A fixture with no
`lexicon` key is scored exactly as it is at the base commit.

**FD2c — Loader compatibility, stated so the file cannot load half-empty.**

`e2e/fixtures/eval/lexicon/clinical-terms.txt`, and `--locale es-MX` loads only
`server/src/eval/lexicons/es-MX.txt`. Nothing is shared across locales —

English run would match it in every note.

widened set is a **load-time error naming the file and the line**, not the silent
`continue` at `lexicon.ts:35`. A half-empty lexicon is the failure this prevents.

the term and to the note text, as F7 already does (`score.ts:495-500`), so a term

`ing|es|ed|ly|s`, the inventory's attested forms are the ones quoted in the file's
header (`nunca`, `jamás`, `nada`, `tampoco`; `ningún` and `ninguna` stem to

The real defect is the transcript inventory at `corpus.ts:82`: a **non-recursive**

**FD4 — Pipeline mode: the exact call sequence.**
Pipeline mode drives the HTTP surface; it does not call a provider. Per
invocation, once:

0. Refuse and exit 2 unless `APUNTA_CHECK_URL` is set, matches
   `^http://(127\.0\.0\.1|localhost)(:\d+)?$`, and its port is 7800–7889 and
   not 7717 — the check `scripts/check-note-format.mjs:37-56` already makes, for
   the same reason. Then `GET /api/health` and require `ok: true`,
   `fakeAi: false`, and a `testRunId` equal to `APUNTA_TEST_RUN_ID`
   (C-ISO@1 rule 5). Record `ollama.tag` and `ollama.model`. Any of these
   failing is exit 2 before a single fixture is touched: a pipeline run against
   a fake or foreign server measures nothing and says so.
0a. **The drafting language is a setting, not the format's locale.**
   `routes/generate.ts:39` reads `storedLanguage(db)`, and
   `routes/draft.ts:230` copies `format.locale` onto the note — so a run with
   `--locale es-MX` against a fresh sandbox database would draft **in English**
   and stamp the note `es-MX`, and `note.locale` could not reveal it. When
   `--locale es-MX`: require the server to have been started with
   `APUNTA_DEV_SPANISH=1` (`routes/settings.ts:26-32`; the sandbox wrapper's
   `serverEnv` inherits `process.env`, `sandbox.mjs:246-252`, so the implementer
   exports it), then `PUT /api/settings {"language":"es-MX"}` **before the first
   fixture**, require the response's `language` to be `es-MX`, and re-read
   `GET /api/settings` before the first fixture and after the last. A
   `language_unavailable` refusal (`routes/settings.ts:84-85`) or a 409
   `language_change_blocked` (`routes/settings.ts:88-90`) is `BLOCKED`, owner,
   with the response recorded. The settings read is the evidence of drafting
   language; `note.locale` is not.
1. `POST /api/patients` **once per invocation**, `{"name": …}` — `John Smith`
   for the English corpora (HS-8, the prototype's sample practice), a name from
   `e2e/fixtures/eval-es/NAMES.md` when `--locale es-MX`. One patient for the
   whole invocation, never deleted mid-run.
2. `POST /api/formats` **once per distinct `(format, sections)` pair** in the
   corpus, `{"name": <formatNameFor(fixture)>, "sections": [...], "locale":
   <run locale>}`, with **no `instructions` field**. The `name` is pinned to the
   exact literal the provider path uses — `"Progress note"` or `"Intake note"`
   (`run.ts:77-80`) — because `defaultInstructionsFor`
   (`default-instructions.ts:644-656`) matches the **section list first**, then
   `BY_FORMAT_NAME`, then a generic fallback, and the owner's own format (the
   `eval-owner` corpus) matches no `BY_SECTIONS` entry, so the name alone decides
   its instructions there. An unpinned or differently named format would get
   `GENERIC_INSTRUCTIONS` while the provider path gets the owner's progress
   instructions, and the two modes would stop measuring the same prompt. With no
   instructions field the server applies `instructionsFor('', name, sections)` →
   `defaultInstructionsFor(...)` (`default-instructions.ts:659-666`), the same
   selection the provider path makes (`run.ts:67-75`). The runner asserts the
   created format's `sections` deep-equal the fixture's, `format.locale` equals
   the run locale, `format.instructions` is `''`
   (`shared/src/note-format.ts:43-57` returns the stored string), and records
   `formatName` per fixture in the report.
3. Per fixture, per run: `POST /api/generate`
   `{"patient_id", "format_id", "title", "typed_notes" | "transcript"}`, with
   the source field chosen by the existing `draftSourceFor(fixture)`
   (`corpus.ts:215-219`), and `accept: text/event-stream`. Frames `status` and
   `token` are progress and are ignored. Frame `note` yields `note.id`. Frame
   `error` is a failure under FD5.
4. **The read-back is the scored artefact, and it is not optional.**
   `GET /api/notes/:id`, then score
   `textToSections(note.content, format.sections)` from `@apunta/shared`
   (`shared/src/sections.ts:179`, exported at `shared/src/index.ts:297`). The SSE
   `note` payload is **not** scored and is not a fallback: C-EVAL@1 §1 says the
   pipeline measurement is the note read back from the API *after persistence*,
   and the difference between what the stream carried and what was stored is
   exactly what this mode exists to see. The note stays `draft`; the runner never
   calls `POST /api/notes/:id/publish`, so `fitDraftingPriorNotes` — which keeps
   only published notes (`server/src/ai/prior-notes.ts:101, 109`) — can never feed
   one fixture's note to another. A test asserts it.
5. `--prior-notes > 0` and any `--instructions` are **refused in pipeline mode**
   with exit 2 and a named reason: the draft route reads prior notes from the
   database itself (`routes/draft.ts:97`) and `POST /api/generate` takes a
   `format_id`, so the two flags would otherwise measure something the pipeline
   does not do. V4 uses neither.
6. `--models` is a **label** in pipeline mode, not a control: the server
   resolves its own model (`defaultModelForMachine()` →
   `PROMOTED_DEFAULT_MODEL` = `qwen3.5:4b-q4_K_M`,
   `server/src/ai/model-picker.ts:88-90`). The runner cross-checks
   `/api/health`'s `ollama.tag` against `--models` and exits 2 on a mismatch.
   A silent difference between the tag in the report and the tag that answered
   is the one failure mode that makes a whole baseline section worthless.

**FD5 — The error rule. One rule, no judgement.**
Any of the following is recorded through the existing
`failedNote(fixture, model, run, message)` (`score.ts:127-158`) with
`gating: ['call_failed']`: a non-2xx from `POST /api/generate`; an `error`
frame; a stream that ends with no `note` frame; a non-2xx or 404 from
`GET /api/notes/:id`; a `note.content` that is empty or whitespace; a
`textToSections` result whose every section body is empty; a `note.format_id`
that does not equal the created format's id; a `note.locale` that does not equal
the created format's `locale`. The last two are **format-integrity checks** and
are described as such: `note.locale` is copied from the format
(`routes/draft.ts:230`), so on its own it says nothing about the language the note
was drafted in — FD4 step 0a's settings read is what says that. A failed run
**counts**: one run in that fixture's denominator, `safetyPassed: false`,
printed per fixture with its message verbatim. It is never retried inside the
invocation, never dropped from the min or the max, and never replaced by a
re-run — a re-run is the next invocation, in a fresh run folder, and its result
stands on its own. Bounded: four invocations per corpus, nothing repeats.

**Admissibility, ordered before the fake-mode branch.** A missed control is

control's, not the generic harness message at `cli.ts:280-286`. This applies to
every run that loads controls, **including the default `npm run eval -- --fake`

a control is broken; nothing it scores counts". The self-check's own meaning is
unchanged — it still passes when the scorer deflects *and* the controls hold — and
a missed control is a second, separately reported reason for a non-zero exit. No
threshold is relaxed to accommodate it, and no existing gate is removed.

**pipeline** measurement on either corpus must fall inside these ranges or it has

**FD10 — The numeric acceptance rule, and what is a measurement versus what is an
inadmissible run.**
Two different failures must not be confused, so they are named apart:

- **Inadmissible (the measurement does not exist).** A control miss (FD6); a
  corpus or controls directory that loads zero fixtures; the sandbox, `/api/health`
  or `testRunId` refusals of FD4 step 0; a `language_unavailable` or 409 from
  FD4 step 0a; an `ollama.tag` that disagrees with `--models`; a missing or
  blank digest; a format-integrity failure from FD4 step 2; an incomplete set of
  the eight reports. An inadmissible run is **fixed and re-run**; it is never
  converted into a pass, a partial average, or a "reported anyway".
- **Measured (a number exists).** Exit 0 or 1 per invocation, the gated-run
  count, and every rate. These are results, not verdicts. The verdict is computed
  per corpus and per metric by this rule and nothing else:

  For each corpus `C` in {`e2e/fixtures/eval`, `e2e/fixtures/eval-owner`} and
  each metric `M` in exactly §5's seven rows — fabrication rate, safety facts
  (C2), salient facts (C1), gated runs, schema valid, unwarranted blanks, blank
  preserved — take the four invocations' numerators and denominators as printed,
  form `min(C,M)` and `max(C,M)`, and compare against §5's recorded range for
  that cell (`BASELINE.md:202-212`):

  - **IN RANGE** iff `min(C,M) ≥ §5min(C,M)` **and** `max(C,M) ≤ §5max(C,M)`.
  - **FAIL** otherwise, recorded with the §5 value, the measured value and the
    delta. "Outside → fail" is C-EVAL@1 rule 8's own words; the runner implements
    it and does not soften it.
  - **NOT MEASURED** when a report carries no denominator for that cell. Never
    IN RANGE, never PASS.
  - No tolerance, no rounding, no interpolation, and no metric outside §5's
    seven rows enters the verdict — other rates are recorded in §9 as
    measurements and gate nothing.
  - The integers, not the rounded percentages, are the comparison, per §7 of
    `BASELINE.md`.

  Row status: **PASS** only when every cell of both corpora is IN RANGE and the
  run was admissible; **FAIL/BLOCKED, owner** when any cell is FAIL, with the
  cells listed; **BLOCKED, owner** when the run was inadmissible. The eight
  provider measurements of §5 are the comparison point and nothing more: an exit
  1 on `e2e/fixtures/eval` is **not** accepted by inference from P0.4's provider
  exit codes (4 of 20 runs gated, exit 1 on all four invocations,
  `BASELINE.md:60-62, 80-83`) — it is measured and compared, like every other
  number, and on `e2e/fixtures/eval-owner`, where §5 records **0/4** gated, a
  pipeline count above zero is a FAIL.
